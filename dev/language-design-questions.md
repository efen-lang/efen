# Вопросы по синтаксису и семантике Efen

Дата: 2026-09-14. Основание: языковые документы из `docs/efen/`, действующие
решения и описание компиляции Amber. Начальный HEAD Efen: `3677f34`.

Это список вопросов к автору языка, а не новые нормативные правила. Проверялось
описание языка; принятие примеров компилятором и поведение runtime не проверялись.
Фрагменты ниже служат проверочными ситуациями: их допустимость, тип или поведение
как раз могут требовать решения.

В Efen уже определены основные механизмы: отдельные compile-time contracts и
runtime interfaces, явные generic-параметры, пакетный выбор стратегий, права и
origin ссылок, логический layout и отдельная representation. Основная потребность
в проработке — правила их совместного применения. Без них можно реализовать
каждый механизм по отдельности и получить несовместимые трактовки одной программы.

Приоритеты:

- **P1** — влияет на разбор обычного кода, типизацию, владение или наблюдаемое
  поведение; ответ нужен до фиксации соответствующей части frontend.
- **P2** — нужен для полного контракта расширенной возможности; её можно явно
  ограничить в первой версии.

Каждый номер обозначает один предмет решения. Внутри приведены последствия,
которые позволят проверить полноту ответа. Исходно найдено **36** пунктов;
решённые пункты сохраняются с соответствующей пометкой. Начать дальнейший
разбор предлагается с **Q04, Q05, Q09, Q10, Q11, Q25, Q29**.

## Синтаксис и выражения

### Q01 · P1 · Где именно перенос строки завершает обычное выражение?

Продолжение строк, начинающихся с `.` или бинарного оператора, уже определено;
оно присоединяется к целому предыдущему выражению. Не хватает общего правила
для незаконченного выражения, `return` и пробельного вызова:

```efen
let result =
    calculate()

return
    calculate()

print
    value
```

**Какие из этих переносов продолжают выражение, какие завершают инструкцию,
а какие запрещены?** Нужно также закрепить, считается ли перевод строки внутри
комментария границей инструкции. Это определяет смысл программы, а не только
работу форматировщика.

Основание: [вызовы](../docs/efen/function-call-syntax.md),
[замыкания: перенос строк](../docs/efen/closure.md#перенос-строк),
[правило пробелов](../docs/efen/operators.md#правило-пробелов).

### Q02 · P1 · Как отделяются generic-аргументы от сравнений и сдвигов?

Generic принимает произвольные compile-time значения, поэтому внутри `<...>`
возможны выражения, а не только имена типов:

```efen
Buffer<Size: 1 << 4>
Choice<Flag: a > b>
Array<Array<Int>>
```

**Требуются ли скобки вокруг выражения, содержащего закрывающий `>` или сдвиг,
и какое синтаксическое правило отличает generic-применение от сравнения?**
Правило должно работать и для callable с именем со строчной буквы, не требуя
сначала разрешить символ и его тип. Отдельный проверочный случай — несколько
закрывающих `>` без пробелов.

Основание: [compile-time аргументы](../docs/efen/generics.md#compile-time-значения),
[операторы](../docs/efen/operators.md).

### Q03 · Решено 2026-09-14 · Ленивые операторы не перегружаются

Для `a && b`, `a || b`, `a ?? b` и optional-вызова значимо не только полученное
значение, но и то, выполняется ли правая часть. Обычная функция с двумя готовыми
аргументами этого не выражает.

`&&`, `||` и `??` являются встроенными неперегружаемыми операциями. Правая
часть вычисляется условно и не более одного раза. Пользовательская ленивая
операция выражается функцией с closure/autoclosure.

Основание: [операторы](../docs/efen/operators.md),
[autoclosure](../docs/efen/closure.md#автозамыкания-autoclosure),
[полномочия определения класса](../docs/efen/aspects/compile-time/class.md).

## Вызовы, вывод типов и сигнатуры

### Q04 · P1 · Каков наблюдаемый порядок вычисления частей вызова и присваивания?

```efen
makeReceiver().save(second: next(), first: next())
array[nextIndex()] += makeValue()
consume(take resource, operationThatMayThrow())
```

**Фиксирует ли Efen порядок слева направо по исходному тексту, включая receiver,
именованные аргументы, неявные coercion и копии?** Для последнего вызова ответ
определяет, успел ли `resource` перейти во временный владеющий слот к моменту
исключения. Для составного присваивания нужно определить однократность
вычисления receiver/индекса и момент чтения старого значения.

Разрешение оптимизации переставить независимые действия при сохранении
поведения не заменяет исходного порядка для действий с наблюдаемыми эффектами.

Основание: [вызовы](../docs/efen/function-call-syntax.md),
[pack значений](../docs/efen/generics.md#pack-значений),
[контракты копирования](../docs/efen/contracts.md#контракты-копирования-и-перемещения).

### Q05 · P1 · Как выбирается перегрузка, когда ожидаемый тип нужен для coercion?

```efen
fn process(value: Int) { }
fn process(value: String) { }

process(source)
```

Предположим, для типа `source` доступны прямые преобразования в обе цели.
Ожидаемый тип аргумента зависит от выбранной перегрузки, а применимость
перегрузки — от допустимого преобразования.

**Когда нет точного совпадения, считаются ли все такие перегрузки равноправными
или существует дополнительное ранжирование?** Нужно определить место generic-
перегрузки и влияние ожидаемого типа результата. Точное совпадение и запрет
цепочек coercion уже приняты; вопрос только о конкуренции оставшихся кандидатов.

Основание: [выбор стратегий и Coerce](../docs/efen/strategies.md#правила-выбора-стратегии),
[вывод generic](../docs/efen/generics.md),
[частное правило owning/read-перегрузок Range](../docs/efen/types/collections.md#создание-snapshot).

### Q06 · P1 · Как выводится общий тип нескольких значений без аннотации?

```efen
let value = if condition { 1 } else { "one" }
let values = [1, "one"]
let empty = []
```

**Когда Efen сам строит structural union, когда ищет общий базовый тип,
а когда требует явную аннотацию?** Это же правило должно объяснять смешение
числовых типов, `null` и отложенный вывод типа пустой коллекции. Возможность
синтезировать union для `opaque`-результата уже задана, но из неё не следует
автоматически аналогичный вывод для всех обычных выражений.

Основание: [if-выражения](../docs/efen/blocks/if.md#if-как-выражение),
[словари](../docs/efen/types/dictionaries.md),
[opaque-результат](../docs/efen/types/type.md#opaque-результат).

### Q07 · Решено 2026-09-14 · Результат обычной функции не выводится

```efen
fn answer {
    return 42
}
```

Описание функций устанавливает `Void` при отсутствии `return`, но общего
контракта для приведённого объявления не формулирует. Примеры в других
разделах используют функции без указанного результата, возвращающие значения.

Это ошибка: отсутствие `-> Type` означает результат `Void`, поэтому
`return 42` недопустим. Готовая сигнатура из явно указанного прототипа,
contract или interface остаётся отдельным случаем и не является выводом из тела.

Основание: [определение функций](../docs/efen/functions.md#определение-функций),
[функции с контекстом](../docs/efen/context-and-effects.md).

### Q08 · P1 · В чьём окружении вычисляется значение параметра по умолчанию?

```efen
fn save {
    param path: String
    param mode: Mode = chooseMode(path)
}
```

**Default — это выражение, выполняемое при каждом пропущенном аргументе,
и какие имена, контексты и стратегии оно использует?** Проверочный случай:
библиотека объявляет `save`, а пакет-потребитель выбирает другую стратегию для
`Mode`. От ответа зависят время выполнения `chooseMode`, видимость `path`,
порядок относительно явных аргументов и экспортируемые `throws`/`in` вызова
с пропущенным аргументом.

Основание: [значения параметров по умолчанию](../docs/efen/functions.md#значения-по-умолчанию-для-параметров),
[пакетная конфигурация](../docs/efen/packages.md#локальная-конфигурация-зависимостей).

### Q09 · Решено 2026-09-14 · Итоговые эффекты callable не стираются

```efen
let callback: (Int) -> Int = operation
```

У `operation` могут быть выведенные `throws`, `in`, требования к правам и
особенности захвата. Точный exception pack уже требуется сохранять, если его
затем выводят из callable.

Отсутствие эффекта в написании `(P) -> R` не означает его отсутствия. Итоговые
`throws` уже сохраняются отдельно от идентичности обычного функционального типа;
то же принято для `in Context`. Сохранённый callable переносит контекстную
сводку, а косвенный вызов распространяет её вызывающей функции. Права вызова
замыкания решены отдельно в Q12.

Основание: [тип функции](../docs/efen/types/function-type.md),
[права параметров](../docs/efen/types/ownership.md#параметры),
[точный throws callback](../docs/efen/throws.md#throws-добавление-исключения).

## Типы, владение и доступ к данным

### Q10 · P1 · Какое право имеет результат `return value`, если параметр не владеющий?

```efen
fn identity -> T {
    generic T: Type
    param value: T
    return value
}
```

Этот пример используется как универсальная identity. При этом неаннотированный
параметр не получает `own`, а `T: Type` не обещает `Copyable` или
`ImplicitlyCopyable`.

**Для некопируемого владеющего значения такой результат является заимствованием
с origin, требует более сильного контракта или делает инстанциацию ошибочной?**
Нужно закрепить права результата и границу вывода: может ли компилятор менять
ссылочную форму опубликованного `-> T`. То же решение определяет обычные
getters, возвращающие owning-поле через `return field`.

Основание: [generic identity](../docs/efen/generics.md#дженерик-функции),
[ownership](../docs/efen/types/ownership.md),
[независимость копирования и перемещения](../docs/efen/contracts.md#контракты-копирования-и-перемещения).

### Q11 · P1 · Когда захваченная локальная переменная получает самостоятельное время жизни?

```efen
fn makeCounter -> () -> Int {
    var count = 0
    return () -> Int {
        count += 1
        return count
    }
}
```

Документ о замыканиях разрешает такой возврат и называет захват ссылочным.
Ownership требует, чтобы origin жил не меньше среды захвата.

**Компилятор автоматически переносит захваченный слот в живущую дольше общую
ячейку или пример требует явной модели владения?** Для двух возвращаемых
замыканий над одним `count` нужно сохранить общую ячейку и определить права
каждого. Это выбор семантики захвата, а не вопрос о конкретном heap allocator.

Основание: [захват по ссылке](../docs/efen/closure.md#захват-по-ссылке),
[хранимые и захваченные ссылки](../docs/efen/types/ownership.md#хранимые-и-захваченные-ссылки).

### Q12 · Решено 2026-09-14 · Права вызова замыкания

Рассмотрим замыкание, которое владеет некопируемым ресурсом и при первом
вызове передаёт его через `take`. Второй вызов уже не может выполнить то же
тело. Отдельный случай — замыкание, которое изменяет захваченное значение,
но не потребляет его.

Efen использует логику Rust, выраженную существующими правами языка. Только
читающее тело требует `read`, изменяющее — `write`, а извлекающее захват через
`take` — `own`. Последний вызов потребляет всё замыкание и записывается
`(take task)()`. Режим зависит от операций тела, а не от самого факта захвата по
значению. Отдельные встроенные аналоги `Fn`, `FnMut` и `FnOnce` не вводятся.

Основание: [режимы захвата](../docs/efen/closure.md#типы-захвата-переменных),
[тип функции](../docs/efen/types/function-type.md),
[take](../docs/efen/types/ownership.md#явное-извлечение).

### Q13 · P1 · Какие свойства считаются местами, доступными через `ref`, `take` и `replace`?

Вычисляемое свойство может не иметь собственного физического слота. При этом
операции выглядят так же, как над полем:

```efen
object.property += value
let old = take object.property
let previous = replace(object.property, value)
```

**Достаточно ли пары getter/setter или свойство должно предоставлять отдельный
контракт доступа к месту и атомарной замены?** Нужно определить момент вызова
`willSet`/`didSet`, поведение при их исключении и допустимость ссылок на
свойство. Принятая атомарность `replace` не должна превращаться в наблюдаемую
последовательность «прочитать — очистить — записать».

Основание: [свойства класса](../docs/efen/classes.md#свойства-класса),
[member resolver](../docs/efen/aspects/members-resolving.md),
[семантика replace](../docs/efen/types/ownership.md#явное-извлечение).

### Q14 · P1 · В каком состоянии остаётся `&out T` при исключении?

```efen
fn initialize {
    param result: &out Resource
    result = createResource()
    operationThatMayThrow()
}
```

**`out` гарантирует инициализацию только при нормальном возврате или также
задаёт состояние места на исключительном выходе?** Нужно определить, можно ли
передать уже инициализированное место, кто уничтожает прежнее значение и кто
владеет новым, если запись состоялась до исключения. Для нескольких `out`
нельзя считать все места инициализированными только по факту входа в функцию.

Основание: [ссылки и out](../docs/efen/types/ownership.md#ссылки).

### Q15 · P1 · Как refinement-предикат сохраняется после изменения значения?

```efen
type Positive: Int { value > 0 }
var value: Positive = 1.refine()
value -= 2
```

`.refine()` описывает проверку на входе в тип, но не полный контракт его
дальнейших операций.

**Изменяющая операция обязана доказать сохранение предиката, выполнить
runtime-проверку до публикации результата или вообще недоступна без явно
объявленной реализации для нового типа?** Особенно важно уточнить типы поверх
изменяемых классов: предикат может стать ложным через другой alias, хотя само
связывание не менялось. Номинальная идентичность и отсутствие автоматического
widening в базовый тип уже определены.

Основание: [refinement types](../docs/efen/types/refinement-types.md),
[новый номинальный тип](../docs/efen/types/type.md#новый-тип).

### Q16 · P2 · Как состояния конкретного класса отображаются в протокол интерфейса?

Interface может объявлять `Connected`, а реализация — дополнительные приватные
состояния. Через interface клиент должен понимать доступность `send` и смысл
`value is Connected`.

**Каждое приватное состояние явно отображается в публичное или соответствие
выводится из допустимых операций и переходов?** Нужно определить, что именно
проверяет runtime-проверка состояния и как две разные реализации интерфейса
сохраняют одинаковый публичный протокол. Одного разрешения дополнительных
приватных состояний для этого недостаточно.

Основание: [typestate: интерфейсы](../docs/efen/types/typestate.md#интерфейсы),
[ветвление и уточнение состояния](../docs/efen/types/typestate.md#ветвление-и-слияние).

### Q17 · P1 · Когда проекция с ослабленными требованиями может сосуществовать с исходным значением?

Именованная projection может ослаблять nullability и доступ, сохраняя тот же
участок памяти. Если через неё записать `null` в исходно обязательное поле,
обычный alias исходного типа временно станет недостоверным.

**Создание такой проекции временно забирает право использовать исходное
значение до проверки обратного преобразования или ослабление разрешено только
в специальных состояниях construction/destruction?** Требуется определить
поведение на `throw`: бинарная совместимость сама по себе инвариантов не
сохраняет. Обычный выбор колонок через `.{...}` не требует такого ослабления.

Основание: [projection types](../docs/efen/types/projection.md),
[проекции класса](../docs/efen/classes.md#проекции-класса),
[region preserve](../docs/efen/code-regions.md).

## Контексты, эффекты и завершение

### Q18 · P1 · По какой идентичности связывается требование контекста?

Два контекста могут содержать поле `db`; составной контекст объявлен
эквивалентным набору объединённых полей. При этом сигнатуры требуют именованный
`in ContextA`, а выражение `%db` называет только поле.

**Зависимость определяется номинальным контекстом, типом эффекта или структурой
полей, и как выбирается привязка при совпадении имён?** Проверка ответа:
удовлетворяет ли `CombinedContext`, включивший `ContextA`, требованию
`in ContextA`; что происходит при двух доступных `db`; чем повторный `with`
того же контекста отличается от явного `override`.

Основание: [контексты: композиция, наследование и override](../docs/efen/context-and-effects.md).

### Q19 · P1 · Какой контекст использует отложенное вычисление после выхода из `with`?

```efen
fn makeCallback {
    with localEnvironment {
        return () { useContext() }
    }
}
```

**Замыкание сохраняет привязку контекста места создания или предъявляет
требование к окружению будущего вызова?** То же различие возникает у генератора
и задачи. В первом случае нужны владение и origin сохранённой привязки; во
втором `in` должно сохраниться в типе callable. Принятое значение `without`
этот выбор не определяет и здесь не пересматривается.

Основание: [with и распространение контекста](../docs/efen/context-and-effects.md),
[захваты](../docs/efen/closure.md),
[генераторы](../docs/efen/generators.md).

### Q20 · Решено 2026-09-14 · Основное и suppressed-исключения cleanup

```efen
defer { cleanup() }
operation()
```

Принята модель Java `try-with-resources`. Если `operation()` уже бросила
`PrimaryError`, она остаётся главным исключением, а `CleanupError` добавляется
в её упорядоченный список `suppressed`. Если основного исключения нет, первая
ошибка cleanup становится главной. Все последующие `defer` и автоматические
`dispose` продолжают выполняться в порядке LIFO, а их ошибки добавляются в
порядке возникновения.

Обычный `catch` сопоставляется с главным исключением; цепочка доступна через
`error.suppressed`. `cause` остаётся отдельной явной причинной связью.
`MustHandle`-ошибка cleanup должна быть поймана внутри `defer` и не может быть
только suppressed. Правило применяется также к автоматическому `let disposable`.

Основание: [defer](../docs/efen/blocks/guard.md#defer--отложенное-выполнение),
[ошибки dispose](../docs/efen/disposable.md#обработка-ошибок-в-dispose),
[try/catch/finally](../docs/efen/blocks/try-catch.md).

### Q21 · P2 · Какой контракт времени жизни и отмены обязателен для асинхронной задачи?

`async`, `await` и `spawn` показаны как extension-диалект; `AsyncDisposable`
использует их для автоматической очистки. Однако права на захваты должны быть
проверены и после преобразования диалекта.

**Задача обязана завершиться до выхода из владеющей области или может пережить
её, получив самостоятельное владение окружением?** Требуется выбрать поведение
при потере последнего handle и отмене во время `disposeAsync`: кто доводит
очистку до завершения. Общий контракт можно установить независимо от синтаксиса
и конкретного scheduler.

Основание: [extension-диалекты](../docs/efen/dialects.md#extension-диалекты-extension-dialects),
[асинхронное освобождение](../docs/efen/disposable.md#асинхронное-освобождение),
[origin захватов](../docs/efen/types/ownership.md#хранимые-и-захваченные-ссылки).

## Flow и генераторы

### Q22 · Решено 2026-09-14 · Один `flow` использует один контекст

```efen
flow {
    user <- loadUser()
    token <- findToken(user)
    return token
}
```

Предположим, первый шаг возвращает `Future<User>`, второй — `Option<Token>`.

Один `flow` требует единого вычислительного контекста. `Future` и `Option` внутри
него автоматически не смешиваются. Переход выполняется явной операцией или
явно выбранной стратегией преобразования до соответствующего шага.

Основание: [flow](../docs/efen/flow.md),
[конструкторы типов](../docs/efen/generics.md#конструкторы-типов).

### Q23 · P1 · Что означают `break` и `continue` вне цикла в `flow`?

В примерах `continue` используется прямо после единственного связывания,
но «следующая итерация» такого блока не определена. `break` допускает частичный
результат или отсутствие значения «в зависимости от контекста».

**Эти выходы доступны только контекстам с отдельной операцией пропуска/остановки
или должны быть запрещены вне явного цикла?** Если они доступны, результат
остановки и цель продолжения должны следовать из контракта контекста: обычный
`Future<T>` сам по себе не задаёт следующую итерацию или отсутствующий `T`.
Локальность `return` внутри `flow` уже решена.

Основание: [flow: catch, фильтры и прерывание](../docs/efen/flow.md).

### Q24 · Решено 2026-09-14 · Итог генератора доступен вызывающему

```efen
generator sample -> Int {
    yield "ready"
    return 42
}
```

Документ различает `yield`, значение, передаваемое обратно, и итоговый `return`,
но не даёт полной пользовательской сигнатуры для этих трёх ролей.

Финальный `return` не отбрасывается. Полный тип отдельно хранит yield, resume и
return types, а `next()` различает `yielded(value)` и `completed(result)`.
Поэтому завершение отличимо от выдачи значения даже при совпадающих типах.

Основание: [генераторы](../docs/efen/generators.md),
[flow generator](../docs/efen/flow.md#flow-генераторы).

## Стратегии, generics и интерфейсы

### Q25 · P1 · Совместимы ли значения одного generic-типа, созданные с разными strategy witnesses?

Два пакета создают `Container<Item>`, но выбирают разные допустимые стратегии
для операций над `Item`. Выбранные witnesses уже входят в ключ инстанциации.

**Это один взаимозаменяемый публичный тип с разными реализациями кода или
разные типы, между которыми нужно явное преобразование?** Проверочная ситуация
— контейнер построен в пакете A и изменяется в пакете B: нельзя потерять
предположение, на котором основаны его внутренние инварианты, например равенство
и хеширование ключей. Если witness хранится в значении либо запрещено его
переопределение для такой инстанциации, это должно быть частью языкового
контракта, а не только ключа compiler cache.

Основание: [статический выбор и пакетная область](../docs/efen/strategies.md#правила-выбора-стратегии),
[generic-зависимости](../docs/efen/generics.md#требования-к-семейству-типов).

### Q26 · P2 · На какую единицу поведения делает выбор `StrategySelector`?

Стратегия может реализовывать сразу несколько связанных методов, например
`equals` и `hash` или `save` и `load`.

**Selector выбирает целое соответствие контракту либо вправе выбирать
стратегию отдельно для каждого обращения к методу?** Во втором случае требуется
правило, которое сохраняет согласованность операций и проекций вроде `T.Item`.
Сейчас описаны возможность подменить выбор и bootstrap самого selector, но не
полный смысл запроса и длительность действия выбранного результата.

Основание: [StrategySelector](../docs/efen/strategies.md#правила-выбора-стратегии),
[проекции параметров contract](../docs/efen/generics.md#ограничения-параметров).

### Q27 · Решено 2026-09-14 · Runtime-interface явно создаётся из стратегии

```efen
let drawable: Drawable = CircleDrawing
using drawable circle.draw()
```

Такой `drawable` описан как vtable без объекта, тогда как обычное значение
interface позволяет вызывать методы уже связанного объекта.

Стратегия сама не является interface и не присваивается произвольному
interface-типу. Явная декларация `interface Drawing from CircleDrawing` создаёт
runtime-проекцию по образцу реализации, после чего
`let shape: Drawing = CircleDrawing` допустимо. Другая стратегия не принимается
структурно по совпадению методов: требуется явный общий `conforms` и проверка
всей runtime-поверхности созданного interface.

Основание: [динамические стратегии](../docs/efen/strategies.md#динамическая-стратегия),
[runtime interfaces](../docs/efen/interfaces.md).

### Q28 · P1 · Что происходит с владением при преобразовании значения в interface?

Interface скрывает конкретный runtime-тип, но потребителю всё ещё нужно знать,
владеет ли он объектом или держит borrow. Особенно показателен struct или
некопируемое значение.

**Преобразование в interface сохраняет исходный режим владения автоматически
или есть разные явно различимые owning и borrowed формы?** Нужно определить
origin borrowed-interface, допустимость упаковки временного значения и
поведение при выделении памяти с ошибкой. Вопрос не о формате vtable, а о том,
какой ресурс и какие обязанности получает вызывающая сторона.

Основание: [interfaces](../docs/efen/interfaces.md),
[полный тип и права](../docs/efen/types/ownership.md#права-как-часть-типа),
[явная проекция contract](../docs/efen/contracts.md#связь-контрактов-с-интерфейсами).

## Метапрограммирование

### Q29 · P1 · Сколько раз выполняется runtime-аргумент метафункции?

```efen
meta fn twice(value: Int) -> InlineClosure {
    return inline { value + value }
}

let result = twice(next())
```

**`next()` вычисляется один раз как обычный аргумент или повторяется при каждом
употреблении `value` в сгенерированном коде?** Нужно также определить, выполняется
ли аргумент, который генерация вовсе не использовала. Для параметра
`Expression` повторная вставка может намеренно повторять вычисление; граница
между ним и обычным runtime-параметром должна быть нормативной. От этого
зависят эффекты, порядок выполнения и возможность передать `take resource`.

Основание: [runtime-параметры метафункции](../docs/efen/compile-time/metafunctions.md#2-runtime-параметры),
[Expression и Statement](../docs/efen/compile-time/metafunctions.md#statement-placeholders).

### Q30 · P1 · Куда переходят `return`, `break` и `continue` во вставленном `Statement`?

Метафункция может получить блок пользовательского кода, вставить его в цикл
или `try`, а затем добавить собственные действия. Собственная область имён
`InlineClosure` уже заявлена, но она не определяет цели переходов внутри
переданного `Statement`.

**Переходы сохраняют лексические цели места написания, привязываются к новому
окружению вставки или запрещаются при переносе через такую границу?** Пример
проверки — обёртка транзакции получает блок с `return`: должен ли выполниться
её код после `${body}` и какие `defer` действуют. Аналогично нужно закрепить
область разрешения свободных имён и явно вставленных `Identifier`.

Основание: [Statement и InlineClosure](../docs/efen/compile-time/metafunctions.md#statement-vs-inlineclosure---критическая-разница),
[композиция placeholders](../docs/efen/compile-time/metafunctions.md#композиция-placeholders).

### Q31 · P1 · Когда результат метафункции превращается в обычное runtime-замыкание?

Начало документа запрещает хранить или вызывать `InlineClosure` в runtime.
Далее метафункция возвращает `inline (value: Int) -> Int`, а пример сохраняет
результат в `let ageValidator` и вызывает его позднее.

**Есть ли автоматическая материализация обычного closure из параметризованного
фрагмента, и чем она отличается от немедленной вставки фрагмента без параметров?**
Нужно определить тип выражения вызова метафункции, возможность вернуть
runtime-функцию без параметров и владение захваченными runtime-значениями.
Сам compile-time дескриптор при этом не обязан становиться runtime-объектом.

Основание: [граница InlineClosure](../docs/efen/compile-time/metafunctions.md),
[два режима использования](../docs/efen/compile-time/metafunctions.md#два-способа-использования-метафункций).

### Q32 · P2 · Какие внешние наблюдения compile-time кода входят в семантику сборки?

Песочница позволяет метакоду читать конфигурационный файл. Generic-код и аспекты
также могут выбирать результат по compile-time данным.

**Внешние входы обязаны проходить через API, регистрирующий зависимость сборки,
или разрешено произвольное чтение окружения с отказом от воспроизводимости?**
Проверочные случаи — изменившийся файл, текущее время и общий изменяемый объект
двух аспектов. Сохранение уже известных зависимостей в cache key не отвечает
на вопрос, какие наблюдения вообще разрешены и как они становятся известны.

Основание: [compile-time sandbox](../docs/efen/compilation-modes.md#использование-для-compile-time-кода),
[compile-time API](../docs/efen/compile-time/index.md),
[условное формирование generic](../docs/efen/generics.md#условное-соответствие-контрактам).

## Общие границы языка

### Q33 · P1 · Как соотносятся ошибки арифметики, trap и режимы компиляции?

Переполнение уже отнесено к ответственности компилятора; контейнеры не должны
дублировать проверки. Но языковому коду нужно знать результат обычного
переполнения и деления на ноль. Для `optional!` уже задан runtime trap;
общие последствия trap для выхода из области описаны недостаточно.

**Какая арифметическая политика действует по умолчанию и что разрешено менять
режиму компиляции: исключение, trap или модульную арифметику?** Проверка ответа —
одинаковы ли `throws`, выполнение `defer` и результат `nothrows` в debug и
release. Речь о семантике compiler arithmetic/access, а не о возвращении
ручных guards в реализации Array.

Основание: [числовые типы](../docs/efen/types/constants.md#ширина-числовых-типов),
[optional trap](../docs/efen/types/optional.md#5-forced-unwrapping-),
[режимы компиляции](../docs/efen/compilation-modes.md).

### Q34 · P1 · Какие гарантии обычного Efen сохраняются при включении unsafe-режима?

Документ режимов допускает глобальное отключение runtime-проверок и локальный
`unsafe`. Модель памяти одновременно требует живость, origin и корректное
владение для каждого разрешённого доступа.

**Unsafe меняет контракт всего модуля или только позволяет локально выполнить
операции с явно принятой обязанностью восстановить безопасную границу?**
Нужно определить, может ли обычный безопасный потребитель доверять публичной
сигнатуре такого модуля. Это также отделит отключение доказанно лишних проверок
от отключения обязательных условий без доказательства.

Основание: [safe/unsafe](../docs/efen/compilation-modes.md#режим-безопасной-памяти),
[модель адресов](../docs/efen/memory/addresses.md),
[граница проверки](../docs/efen/memory/viper-verification-backend.md).

### Q35 · P1 · Как инициализируются runtime-значения модулей при циклических зависимостях?

Два модуля могут ссылаться на объявления друг друга; готовность деклараций
не равна готовности runtime-значений. Например, initializer значения A читает
значение B, а initializer B вызывает функцию, читающую A.

**Инициализация eager в установленном порядке, lazy при первом обращении
или ограничена так, чтобы такие циклы были ошибкой?** Нужно определить
поведение при повторном входе и исключении initializer, а также порядок
завершения уже созданных ресурсов. Разрешённые циклы compile-time запросов
между стадиями классов этот runtime-вопрос не решают.

Основание: [модули](../docs/efen/packages.md),
[статические члены](../docs/efen/classes.md#статические-методы),
[константы и runtime-значения](../docs/efen/types/constants.md).

### Q36 · P2 · Какова область действия расширения синтаксиса и как проверяется его композиция?

Extension-диалект добавляет ключевые слова и формы через `use dialect`.
Запрещён конфликт с базовым синтаксисом, но два расширения могут независимо
добавить одну форму или изменить классификацию обычного идентификатора.

**Подключение меняет грамматику всего модуля, только последующего текста
или отдельной области, и когда конфликт двух расширений считается ошибкой?**
Нужен ответ, не зависящий от случайного порядка импортов. Для inline-диалекта
важно также однозначно отделять `name { ... }` от обычного Efen-блока до
типизации его содержимого.

Основание: [диалекты: расширение, композиция и ограничения](../docs/efen/dialects.md),
[запрет trailing closure без стрелки](../docs/efen/closure.md#оператор--для-trailing-closures).

## Что не требует повторного решения

Следующие места требуют синхронизации документации, а не новых вопросов об
уже выбранной базовой модели:

- `functions.md` показывает `test "my test" { ... }`, хотя пробельный вызов
  принимает один аргумент, а trailing closure требует `=>`.
- `types/function-type.md` показывает неинициализированный `let` с последующим
  присваиванием; принятое правило требует инициализировать `let` при объявлении.
- `generics.md` использует `AoS` и `SoA` как enum-значения, а `index.md`
  требует строчную начальную букву для значений enum.
- В разделах о функциях, замыканиях, interfaces, refinement и compile-time API
  остаются `func`, `impliments`, разные формы constructor, `catch` со скобками
  и другие несогласованные примеры. Они не доказывают наличие дополнительных
  форм языка.
- Таблица операторов не включает все конструкции, используемые в остальных
  документах: в частности, `|>` и postfix `!`. Наличие отдельного решения
  о конструкции следует отличать от полноты таблицы её приоритетов.
- Исторические разделы `DOCUMENTATION-AUDIT.md` содержат старые решения о
  `&T`, `alias`, optional и других механизмах. Их нельзя автоматически считать
  актуальнее тематических документов и последующих решений.
- Правила именованных и безымянных стратегий следует сверить между
  `strategies.md` и записью Amber от 2026-09-12 о явном `provide` для именованной
  альтернативы. В этом отчёте конфликт редакций не превращён в повторный
  вопрос о базовой активации стратегий.

Не пересматриваются: `generic` отдельно от runtime `param`; `allow strategies`;
пакетная нетранзитивность `provide`; запрет цепочек неявных coercion; локальный
`return` в `flow`; смысл `without`; разделение layout/representation;
уникальный корневой `ClassDefinition` и принятый порядок построения класса;
компиляторный вывод/доказательство условий и атомарный `replace`.

Отдельно уже отложены полная модель dependent types/`Layout<T>`, конкурентный
доступ к одному layout, неоднородные области, слабые указатели и массовый
перенос между дескрипторами. Их границы перечислены в
[addresses.md](../docs/efen/memory/addresses.md#граница-модели). Этот перечень
не означает, что для уже разобранного Chunked Array нужно заново вводить
пользовательские кванторы или ручные проверки арифметики.

## Как фиксировать ответы

Для каждого номера достаточно сначала выбрать наблюдаемое правило или явно
ограничить возможность в первой версии. После ответа нужно записать хотя бы
один разрешённый и один запрещённый/аварийный пример, затем синхронизировать
языковой документ и соответствующий контракт HIR. Детали реализации,
которые однозначно следуют из решения, не требуют новых вопросов автору.
