## Противоречия

1. Поле хранит ссылку или нет.
   - `types/parts.md:179`: «поле не хранит ссылку, поэтому общая память у двух полей бывает только там, где она объявлена».
   - `types/parts.md:472`: «Структура с `Src: Origin`, которая хранит заимствование»; `generics.md:583`: поле `let items: Access<Src> Array<T>`; `types/collections.md:556`: «поля вида `R<Src> …`»; `generators.md:262`: удержание `mut` остаётся записанным «в … поле».
2. Вызов `mut fn` через `edit` для внешнего класса.
   - `classes.md:631`: `mut fn` класса над внешним значением «вызывают и через `mut`, и через ссылку `edit`».
   - `contracts.md:281-283`: «Прямой вызов метода класса проверяется по его телу, как вызов `mut fn`» и «получатель `edit` его [`mut fn`] не принимает». У внешнего метода тела нет, и не сказано, по какому из двух правил он проверяется.
3. Обход `Iterable` и смена структуры.
   - `types/parts.md:399`: «`for item in s` не даёт менять структуру ни одной части».
   - `types/collections.md:532`, `:626-628`: при праве `mut` «тело и сам курсор меняют структуру получателя»; `for item in mut collection` допускает смену структуры.
4. Путь при `read`.
   - `types/parts.md:105`: «`read<self.x> fn` — ошибка».
   - `types/parts.md:110-111`: `Access<self.items> fn` при `Access == read` — «обычный `read fn`», то есть путь молча отбрасывается, а не ошибка; тот же вопрос в `generics.md:661`.
5. Проверка пересечения при выполнении.
   - `types/projection.md:202-204`: если не доказано, что проекции взяты из разных значений, «проверка при выполнении сравнивает адреса по полям».
   - `types/parts.md:276-278`: у метода с путём «при выполнении ничего не проверяется … недоказанное непересечение — ошибка, а не проверка адресов». Две политики для одной задачи (расхождение, а не прямое противоречие).
6. Умолчание права.
   - `generics.md:554`: «умолчания у параметра `Access` нет» и тут же «Аргумент без права значит `read`».
   - `contracts.md:385-387`: параметр без умолчания, не названный в `conforms`, — ошибка; при этом `contracts.md:406` называет ненаписанное право `read`.
7. Права среза.
   - `types/collections.md:223-224`: срез изменяемого источника «может предоставлять изменяемые элементы».
   - `types/collections.md:226`: срез даёт режим `edit` (значения менять можно, структуру нельзя). Не сказано, `edit` это или `mut` по праву элемента.
8. Кто убивает ссылку от `mut`-генератора.
   - `generators.md:258`: шаг `for` — вызов `mut` у генератора «с каким бы правом он ни держал источник».
   - `generators.md:251`: при удержании `read` или `edit` вызов `mut` «до `items` не доходит». Согласуется только через слово «доходит с правом удержания» (`:259`); разные формулировки одного правила.

## Два способа записать одно

1. Ссылка с источником: `read<self.items> Item?` (`types/parts.md:15`), `Access<Src> T?` (`generics.md:596`), `read<s.Storage.items> Item?` (`types/parts.md:350`), `read<self.inner.Storage.items>` (`types/parts.md:343`), `self.Items` для представления (`types/parts.md:167`): пять видов пути в одних скобках.
2. Удержание курсора со скобками `-> (read<self.items> Cursor)` (`types/parts.md:410`) и без скобок `-> read<self.items> Cursor` (`types/parts.md:442`): один синтаксис, два смысла (курсор, который держит часть, и ссылка на значение внутри части).
3. Право и тип в аргументе: `Iterable<Item: edit Int>` и `Iterable<Item: Int, Access: edit>` (`generics.md:619-623`); `conforms Iterable<Item: Access T, …>` (`strategies.md:408`) и `conforms Iterable<Item: T, Access: Access, …>` (`strategies.md:422`).
4. Запись изменяемой части: `mut<self.cache, edit self.items>` (`types/parts.md:87`), запись про весь объект `mut<self.cache, edit self>` (`types/parts.md:314`) и `edit fn` без пути (`types/parts.md:310`); `edit self` внутри скобок и `edit` перед `fn` — разный объём права под одним словом.
5. Одно слово `mut` в трёх ролях: право получателя (`mut fn`), право заголовка (`for x in mut v`, `types/collections.md:626`), удержание (`mut<items> generator`, `generators.md:252`).
6. Слово `take`: префикс передачи владения (`take collection`) и метод `take(n)` (`types/collections.md:757`), а также `take g.result` (`generators.md:140`).
7. Знак `_`: вывод параметра в `conforms` и «любое значение» в образце (`contracts.md:379`); запись `.{…}`: проекция и образец (`types/projection.md:151`).
8. `layout { … }`: поля `var` (`classes.md:720`), части `part` (`types/parts.md:50`), отношение `forall` (`classes.md:763`) и `shared layout` (`classes.md:768`) в одном блоке.
9. `let` в проекции: поле только читается (`types/projection.md:178`); `let` в заголовке цикла: запрещает перепривязку, но не изменение (`blocks/loops.md:136`); `let` как поле, «записываемое на время вызова» (`types/projection.md:219`).
10. Удержание генератора: пишется в типе `(edit<items> generator …)` (`generators.md:233`) и выводится из тела у генератора-метода (`generators.md:342`).
11. Удержание `own`: `(own<x> T)` и просто `T` (`generators.md:117`, `types/collections.md:533`).
12. Источник `Src`: параметр вида `Origin` (`generators.md:267`), путь `Src: self.items` (`types/parts.md:435`), «часть в `Src` пишется только в контракте» (`types/parts.md:472`).

## Случаи без правила

1. Два генератора с `edit`-удержанием одного источника одновременно (правила совместимости двух удержаний `edit` в моих документах нет):
   ```efen
   let a = active(items: list)
   let b = active(items: list)
   for x in a { for y in b { x.count = y.count } }
   ```
2. Запись в источник по значению, пока жив срез (срез даёт `edit`, но сказано только про структуру, `types/collections.md:226-229`):
   ```efen
   var arr = [1, 2, 3]
   let s = arr[0..<2]
   arr[0] = 9
   print(s[0])
   ```
3. Срез над `Vector`: правило сформулировано для массивов, а `v[] = 4` может переместить хранилище:
   ```efen
   var v: Vector<Int> = [1, 2, 3]
   let s = v[0..<2]
   v[] = 4
   print(s[0])
   ```
4. Ленивая цепочка и источник: нет правила, какое удержание и с каким правом держит `lazyResult` (`types/collections.md:808`):
   ```efen
   var numbers: Vector<Int> = [1, 2, 3]
   let lazyResult = numbers.map => item * 2
   numbers[] = 4
   for v in lazyResult { print(v) }
   ```
5. Вложенный обход `read` внутри обхода `mut` той же коллекции (`types/collections.md:626`, `blocks/loops.md:566`):
   ```efen
   for x in mut v {
       for y in v { print(x + y) }
   }
   ```
6. Анонимная проекция коллекции как значение, а не параметр: правило о структуре есть только для параметра (`types/projection.md:231`):
   ```efen
   let p = Particles.{position}
   Particles.append(Particle())
   print(p.count)
   ```
7. Генератор с удержанием `mut`, сохранённый в поле структуры, которая живёт не дольше источника (`generators.md:262`, `:473` и `types/parts.md:179` не согласованы):
   ```efen
   struct Walker { var g: (mut<items> generator yield Int) }
   ```
8. Курсор, удерживающий часть, и вызов `mut fn` без пути в теле цикла (таблица `types/parts.md:249-255` говорит о ссылках, не о курсорах):
   ```efen
   for item in s.each() {   // each -> (read<self.items> Cursor)
       s.compact()          // mut fn без пути: курсор жив или нет?
   }
   ```
9. Вызов `mut fn` внешнего класса через `edit`, когда у метода нет тела (противоречие 2):
   ```efen
   fn run(c: edit sqlite3) { c.sqlite3_step() }
   ```
10. Генератор-метод с `own`-получателем и частью: `own generator` перемещает получателя и ссылок не отдаёт (`generators.md:334`), а роль `yield read<self.items> Item` требует части:
   ```efen
   own generator drain yield read<self.items> Item { … }
   ```
