# Аудит документации Efen

Дата: 2026-09-03

Объём: все 66 Markdown-файлов в `docs/efen`

Статус: аудит, без исправления исходных документов

## Резюме

Документация содержит сильные идеи, но пока не образует единую исполнимую
спецификацию. Главная системная проблема — одновременное присутствие нескольких
версий синтаксиса и семантики языка. Наиболее заметны пары `fn`/`func`,
`Void`/`void`, `type`/`function` для функциональных алиасов,
`implements`/`conforms`/`:` для реализации абстракций и две формы `catch`.

Найдены:

- 5 критических противоречий;
- десятки проблем высокой и средней важности;
- редакционные и структурные дефекты, включая 4 битые ссылки и 3 файла с
  несбалансированными Markdown-блоками;
- незавершённые нормативные разделы с `TODO`.

Перед точечной правкой текста рекомендуется сначала утвердить короткую
каноническую грамматику и словарь терминов. Иначе локальные исправления будут
снова расходиться между документами.

## Критические проблемы

### C1. `abstraction-aspects/class.md` описывает другой язык

Файл: `docs/efen/abstraction-aspects/class.md:1-12` и далее по всему документу.

Документ называет interface «контрактом» и использует `func`, `void`, `this`,
`property`, `extends`, `implements`, `Some/None`, `::new` и точки с запятой.
Это противоречит основным `interfaces.md`, `contracts.md`, `classes.md` и
`functions.md`.

Решение: считать файл устаревшим черновиком и переписать по канонической модели
Efen либо удалить из нормативной документации.

### C2. Основной документ функций противоречит новому синтаксису вызова

Файлы: `docs/efen/functions.md:198-219`,
`docs/efen/function-call-syntax.md:26-52`.

`functions.md` разрешает вызов через пробел только как statement, тогда как
новая спецификация разрешает `func expression`, включая `echo x + 1`, без такого
ограничения.

Решение: удалить statement-only ограничение и сделать
`function-call-syntax.md` единственным нормативным источником правил вызова.

### C3. DSL-примеры нарушают правила вызова и trailing closure

Файлы: `docs/efen/functions.md:237-245`,
`docs/efen/closure.md:426-429`,
`docs/efen/function-call-syntax.md:54-84`.

`test "my test" { ... }`, `describe "feature" { ... }` и `it "..." { ... }`
визуально передают два аргумента и используют closure без `=>`, хотя оба приёма
запрещены другими разделами.

Решение: переписать вызовы со скобками и `=>` либо нормативно определить
отдельный DSL/trailing-closure синтаксис.

### C4. Несовместимые грамматики `catch`

Файлы: `docs/efen/blocks/try-catch.md:11-24`,
`docs/efen/throws.md:53-59`, `docs/efen/blocks/index.md:193-200`.

Одновременно используются `catch e: Type` и `catch (e: Type)`.

Решение: выбрать одну форму в грамматике и заменить все примеры глобально.

### C5. Раздел closure частично написан на Swift

Файл: `docs/efen/closure.md:549-567` и последующие примеры раздела.

Используются `_ request`, `@escaping`, `requests.append`, `[weak self] in`,
`func` и Swift trailing closures. Они несовместимы с синтаксисом Efen и даже с
правилами в начале того же файла.

Решение: переписать раздел на Efen или удалить до проектирования escaping и
capture semantics.

## Проблемы высокой важности

### Синтаксис и управление потоком

1. `docs/efen/flow.md:242-247`: `match` использует `case`, хотя
   `blocks/switch.md:30-54` прямо говорит, что в `match` это слово не нужно.
2. `docs/efen/flow.md:20-36`: одновременно заявлены последовательный monadic
   bind и автоматический выбор порядка компилятором. Для эффектов порядок
   наблюдаем; разрешать перестановку можно только после доказательства
   независимости.
3. `docs/efen/flow.md:87-111`: `continue` и `break` применяются вне цикла;
   «следующая итерация» и результат прерванного flow не определены.
4. `docs/efen/destructuring.md:5-23,44-47`: `let Point -> x, y` показан без
   правого значения, хотя ниже правое выражение объявлено обязательным.
5. `docs/efen/functions.md:23,330-333`: два несовместимых синтаксиса type alias:
   с `=` и без него.
6. `docs/efen/functions.md:66-69`: `fn wrap: Wrapper<T>` использует
   необъявленный `T`; требуется `fn wrap<T>` либо конкретный тип.
7. `docs/efen/functions.md:14-17`: утверждение «нет `return` — всегда `Void`»
   не согласовано с expression bodies и выражениями `if`/`match`; нужно явно
   определить implicit return.
8. `docs/efen/blocks/try-catch.md:145-174`: объявленный внутри `try` объект
   `parsed` используется после блока; показанная эквивалентность ломается при
   обычной блочной области видимости.
9. `docs/efen/blocks/try-catch.md:190-206`: одна конструкция названа
   `on Exception`, `on IoException` и `on throw`; `${e}` не имеет binding.
10. `docs/efen/disposable.md:291-314`: ошибка автоматического dispose сначала
    объявлена обязательно обработанной, затем распространяется из функции без
    `catch`; требуется согласование с throws inference.
11. `docs/efen/disposable.md:45-47,294-301`: используются `void` и bare
    `throws`, хотя канонические документы требуют `Void` и `throws Error`.

### Абстракции, модули и compile time

12. `docs/efen/superpolymorphism.md:16-102`: систематически используются `func`
    и `implements`, несовместимые с основными документами.
13. `docs/efen/interfaces.md:155-170`: fence `efenswift`, `func` и утверждение
    о работе «без участия компилятора»; последнее невозможно для проверки
    реализации и построения VTBL.
14. `docs/efen/contracts.md:8-12,147-170,190-207`: `func` смешан с `fn`, а
    `{ get set }` не определён как часть грамматики properties.
15. `docs/efen/abstraction-aspects/abstraction-aspects.md:34-52`:
    `Allocator::deallocate(Self)` передаёт тип вместо экземпляра; обращения
    `Self.refCount` должны быть `self.refCount`.
16. `docs/efen/compilation-modes.md:92-102`: проверка overflow через
    `result < value` неверна для отрицательных чисел и пропускает часть
    переполнений. Нужен checked multiply или проверка границ до операции.
17. `docs/efen/packages.md:84-94` противоречит `visibility.md:31-48`: публичный
    модуль не должен автоматически делать все internal-определения публичными.
    Также необходимо выбрать `pub` или `public`.
18. `docs/efen/context-and-effects.md:367-409`: `without` объясняется на
    неправильном scope, `fucnB` вызывается как `funcB`, упомянут отсутствующий
    `with null`, а `required EnvA` конфликтует с ранее заданным `in EnvA`.
19. `docs/efen/compile-time/metafunctions.md:2371-2383`: два семантически
    одинаковых присваивания closure объявлены соответственно корректным и
    ошибочным без различающего expected type.
20. `docs/efen/runtime/memory.md:12,18,24,40,77`: общий контракт требует
    `constructor(size)` даже у allocator, которому size не нужен, и смешивает
    `extends`/`implements` с основной моделью абстракций.
21. `docs/efen/decorators.md:137-148` обещает прямую замену AST, тогда как
    `compile-time/metafunctions.md:2029-2033` запрещает сырой generated code.
    Нужно развести два API и их модель безопасности.

### Типы, generics и память

22. `docs/efen/types/refinement-types.md:44-159`: почти весь раздел размечен
    как PHP и использует смесь PHP/Efen (`int`, `$array`, `fn f(...): T`, `;`).
23. `docs/efen/types/refinement-types.md:108-113`: `Index<T>` ссылается на
    `$array` вне scope и не связан с конкретной длиной; обещание bounds safety
    ложно без dependent type или runtime check.
24. `docs/efen/types/ownership.md:202-205`: `&T?` означает out-параметр, но
    `?` уже означает `Optional`; нельзя различить out `T` и inout `Optional<T>`.
25. `docs/efen/types/ownership.md:139-143` возвращает `T*`/`&obj`, хотя тот же
    документ запрещает возвращать ссылки, а `memory/pointer.md:187-189`
    утверждает, что указателей нет в параметрах и структурах.
26. `docs/efen/memory/pointer.md:17-34`: рекурсивное поле `next: Node` названо
    указателем, но по синтаксису это значение бесконечного размера. Нужны
    `Node?`, `Pointer<Node>` или `Box<Node>` и правило representation.
27. `docs/efen/memory.md:54-79`: обычное присваивание безусловно описано как
    retain, что противоречит unique ownership/move в `types/ownership.md`.
28. `docs/efen/memory.md:215-227`: weak без RC якобы разрешён с ослаблением
    ownership guarantees. Без control block/generation table это создаёт
    use-after-free; возможность нужно реализовать формально или запретить.
29. `docs/efen/memory.md:269-277`: RC release делает отдельные check и
    decrement; даже с `AtomicInt` возможны гонка и double destruction. Нужен
    atomic `fetch_sub` с acquire-release и уничтожение при предыдущем значении 1.
30. `docs/efen/generics.md:168-192`: `Comparable<T>` используется как constraint
    `T: Comparable`; должно быть `T: Comparable<T>`. Синтаксис реализации также
    не унифицирован.
31. `docs/efen/generics.md:275-279` обещает type erasure, тогда как
    `types/collections.md:203-205` показывает специализацию. Нужно выбрать
    monomorphization, erasure либо чётко описанный гибрид.
32. `docs/efen/types/collections.md:170-177`: compile-time contract
    `Iterable<T>` возвращает другой contract как runtime-тип. Нужен associated
    iterator type, `impl Iterator<T>` или interface existential.
33. `docs/efen/types/collections.md:170-279`: API использует `Option<T>` и
    `Some/None`, тогда как `types/optional.md:548-564` задаёт `Optional<T>` и
    `.some/.none`/`null`.
34. `docs/efen/types/function-type.md:34-40`: неизменяемый `let f` объявляется
    без значения, затем переназначается; нужен `var` либо инициализация.
35. `docs/efen/memory/allocator.md:31-40`: `init()` обращается к отсутствующему
    `data`, а `provide` ссылается на необъявленный `MyObjectAllocator`.
36. `docs/efen/memory/pointer.md:70-85`: inline union якобы меняет размер
    объекта в зависимости от runtime-варианта. Обычный tagged union имеет
    фиксированный размер; переменный требует отдельной DST/layout-модели.
37. `docs/efen/memory/pointer.md:58,74-75`: selector/tag хранится как свободное
    поле рядом с payload. Для type safety tag должен быть частью union и
    обновляться атомарно вместе с payload.

## Проблемы средней важности

1. `docs/efen/types/constants.md:148-178`: одновременно обещаны неизменяемые
   элементы const-коллекции и изменяемый объект за const-ссылкой. Нужно развести
   compile-time constant, readonly binding и deep immutability.
2. `docs/efen/types/strings.md:367-373,449-453`: family emoji назван 7 code
   units; фактически это 7 Unicode scalar values, 25 UTF-8 bytes или 11 UTF-16
   code units. Нужно определить единицу `length()` и нормализацию строк.
3. `docs/efen/types/dictionaries.md:95-108`: не определено поведение
   `dict[key]` для отсутствующего ключа и смысл `dict?[key]`.
4. `docs/efen/types/typestate.md:126-136`: сохранение исходного состояния после
   исключения невозможно без rollback/atomic transition.
5. `docs/efen/types/typestate.md:195-205`: переход через shared aliases не
   объясняет, как обновляется typestate всех aliases; модель пока unsound.
6. `docs/efen/types/type.md:1-45`: файл об алиасах внезапно вводит ownership и
   `anchored`, дублируя `type-aliases.md`; его следует разделить/переименовать.
7. `docs/efen/type-aliases.md:59-122` и
   `types/function-type.md:81-90`: функциональные алиасы используют разные
   ключевые слова `function` и `type`.
8. `docs/efen/memory/pointer.md:194-199`: observable copy/reference semantics
   нельзя выбирать по эвристике размера; ABI hidden reference обязан сохранять
   value semantics.
9. `docs/efen/memory/classes-internal.md:29-39`: `projection Raw as None`,
   `%self` и `-> Self in Self` не соответствуют публичной грамматике; пометить
   как internal IR либо переписать.
10. `docs/efen/strategies.md:233-270`: vtable «без объекта» не определяет
    receiver для `draw/resize`; нужен ABI и constraint целевого типа.
11. `docs/efen/meta/metadata.md:5-33`: упомянуты неописанные traits, а API и
    атрибуты одновременно представлены как возможность и оставлены `TODO`.
12. `docs/efen/decorators.md:103-132`: top-level `param oldConfig` не определён,
    а `this` конфликтует с каноническим `self`.
13. `docs/efen/diagnostic-groups.md:39`: «сделать все ошибки критическими» для
    `-Werror` бессмысленно; должны повышаться предупреждения. Не задан приоритет
    конфликтующих diagnostic flags.
14. `docs/efen/index.md:11-14`: обещаны «бинарные структуры» и множественное
    наследование интерфейсов, которых `interfaces.md` не определяет.
15. `docs/efen/abstractions.md:17-18`: две layout-модели показаны как свободно
    выбираемые без синтаксиса выбора и ABI-правил.
16. `docs/efen/generators.md:70-81`: таблица смешивает функции и операторы;
    `|>` отсутствует в таблице приоритетов `operators.md`.
17. `docs/efen/blocks/switch.md:238-263`: старый pattern syntax с запятыми
    визуально конфликтует с запретом запятых в бесскобочном function call;
    нужно явно отметить, что pattern — отдельный grammar context.
18. `docs/efen/is.md:54-59`: запятая используется как OR, но её приоритет и
    взаимодействие с бесскобочным вызовом не определены.
19. `docs/efen/closure.md:13-42`: одновременно используются `->` и `=>`;
    «без параметров» использует `x`, а «Сокращённая формат» содержит ошибку.
20. `docs/efen/meta/aspect.md:16-84`: кроме сломанного fence, примеры используют
    неопределённые `method`, `array` и `;` вместо канонического синтаксиса.
21. `docs/efen/сonditional_compilation.md`: имя начинается кириллической `с`,
    что создаёт невидимую файловую ловушку; документа нет в оглавлении.
22. `docs/efen/decorators-examples.md`: не сказано, являются Route/ORM/Memoize
    встроенными возможностями или условными библиотечными примерами.
23. `docs/efen/types/built-in-contracts.md:10-28`: compile-time `TypeContract`
    содержит mutable runtime-поля `name/kind/size`; нужно определить фазу и,
    вероятно, сделать их read-only associated metadata.
24. `docs/efen/memory/allocator.md:12`: allocator смешивает байты и элементы и
    не получает alignment/layout при deallocate. Нужен `Layout` либо metadata в
    `Pointer`.
25. `docs/efen/types/ownership.md:22,102-110`: тезис «без own ресурс никогда не
    освобождается автоматически» противоречит managed, RC и GC; значение `own`
    нужно ограничить конкретной моделью детерминированного владения.
26. `docs/efen/types/ownership.md:107-110`: `managed` не отслеживает
    transfer/consume, но обещает безопасное автоматическое освобождение. Без
    правил aliasing/escape это может дать double free или use-after-free.

## Язык и редактура

Повторяющиеся проблемы:

- `impliments` вместо выбранного ключевого слова: `functions.md:140`;
- «действет» → «действует»: `types/type.md:13`;
- «тольок» → «только»: `memory.md:255`;
- «монархических последовательностей» → «монадических последовательностей»:
  `flow.md:3`;
- незавершённая фраза «возвращает значение в контексте (»:
  `flow.md:30`;
- «фунции» → «функции»: `functions.md:330`;
- «Сокращённая формат» → «Сокращённая форма»: `closure.md:39`;
- систематическое «так же» в значении «также»: `functions.md:126`,
  `context-and-effects.md:89,447,470`, `classes.md:292`, `memory.md:146,230`,
  `memory/pointer.md:70`, `types/ownership.md:48,65` и другие места;
- неудачные гибриды русского и английского: «heap память», «linked list»,
  «generic sound», «compile-time проверки», «runtime overhead». Термины можно
  оставить английскими, но нужен единый словарь и одинаковое оформление;
- `docs/efen/functions.md:285-296` помечает корректные скобочные вызовы как
  «плохо», хотя пояснение рекомендует именно их;

- `docs/efen/meta/members-resolving.md:4`: требование получить именно assembler

`comments.md`, `diagnostic-groups.md`, `dialects.md`, `blocks/guard.md`. Это не
ошибка семантики, но ухудшает навигацию и автоматическое построение оглавления.

## Рекомендуемый порядок исправления

1. Создать `language-core.md` с каноническими формами объявления функции,
   вызова, closure, type alias, `catch`, реализации interface/contract и
   модификаторов видимости.
2. Явно разделить статусы документов: normative, proposal, draft и internal IR.
   Сейчас незавершённые идеи выглядят как гарантии языка.
3. Исправить пять критических конфликтов и механически унифицировать ключевые
   слова во всех примерах.
4. Утвердить модель generics: monomorphization, erasure или формальный гибрид.
5. Утвердить единую ownership/reference/allocator модель до публикации примеров

6. Определить expression grammar и precedence для пробельного вызова, `<|`,

7. После семантической правки исправить fences, ссылки, опечатки и прогнать

## Методика и ограничения

Каждый документ был отнесён к одному из трёх независимых направлений аудита:
типы/память, функции/control flow и архитектура/compile time. Дополнительно по
всему дереву выполнены проверки локальных ссылок, code fences, незавершённых
`TODO` и повторяющихся языковых ошибок.

Аудит проверяет внутреннюю согласованность документации. Реализации компилятора
в репозитории нет, поэтому утверждения о том, что конкретный пример действительно
принимается текущим компилятором, проверить невозможно. Там, где документы
расходятся, отчёт фиксирует конфликт и предлагает сначала выбрать каноническое
правило, а не угадывает поведение реализации.

## Решения после аудита

Раздел фиксирует решения, принятые при последовательном разборе отчёта.

- функции объявляются через `fn`;
- тип без возвращаемого значения называется `void`;
- interface можно реализовать через `:` в заголовке или `implements` в теле;
- contract подключается только через `conforms`;
- обработчик исключения записывается как `catch e: IOError` без скобок;
- алиас функции объявляется общим ключевым словом `type`;
- generics поддерживают monomorphization и type erasure: по умолчанию стратегию
  выбирает компилятор, программист может потребовать конкретную стратегию, а
  невозможность выполнить явное требование является ошибкой компиляции;
- interface имеет runtime-представление и динамическую диспетчеризацию, contract
  является compile-time ограничением;
- contract допустим в позиции результата; конкретный тип может быть статически
  известен либо упакован в runtime-контейнер, имя и синтаксис которого пока не
  определены; невозможность однозначно построить вызов — ошибка компиляции;
- обычная `fn` требует явного `return`, кроме результата `void`;
- однострочное closure неявно возвращает выражение и использует `=>`; `->`
  используется для типа результата;
- trailing closure разрешено только с явным `=>`;
- `match` использует ветви без `case`, а `case` относится к `switch`;
- компилятор может переставлять операции `flow`, только если анализ эффектов
  доказал сохранение поведения; `break`/`continue` в самом `flow` пока не решены;
- destructuring всегда требует исходное выражение справа;
- write-only ссылка записывается как `&out T`; `&T` означает read-only, а
  `&mut T` — read/write;
- `weak` запрещён без runtime-механизма обнаружения уничтожения объекта;
- RC/ARC по умолчанию не потокобезопасен; многопоточная стратегия описывается
  отдельным RFC;
- сырые `T*` запрещены вне будущего специального pointer-диалекта;
- физическое размещение объектов и структур выбирает компилятор;
- `String.length()` считает grapheme clusters; scalar values и UTF-8 bytes
  требуют отдельных операций;
- поведение отсутствующего ключа определяется конкретной реализацией словаря,
  а не языком;
- typestate-переходы должны описывать состояния для базовых и конкретных типов
  исключений; выбирается наиболее конкретное правило; rollback не выполняется,
  но компилятор проверяет инварианты состояния на каждом пути `throw`;
- `let` запрещает переназначение binding, `const` означает глубоко неизменяемое
  compile-time значение, а права изменения runtime-объекта задаются ссылками и
  capabilities;
- публичный optional-синтаксис — `T?`, пустое значение — `null`; формы
  `Optional<T>`, `Some`/`None` и `.some`/`.none` не используются в стандартных
  примерах;
- `Comparable` использует `Self`, поэтому constraint записывается как
  `T: Comparable`, а не `Comparable<T>`;
- metadata `TypeContract.name`, `kind` и `size` доступны только для чтения;
- `let` обязательно получает значение при объявлении; отложенная инициализация
  требует `var`;
- pipeline обозначается `|>` и является левоассоциативным; простой этап
  принимает один аргумент, а многопараметрический этап содержит ровно один `$`,
  отмечающий позицию результата предыдущего этапа:
  `data |> save(options, $)`.

Предварительный синтаксис typestate-переходов при исключениях:

```efen
fn open() -> :Closed >> Open
    throws Error >> Failed
    throws IOError >> Closed
    throws TimeoutError >> Retrying
```

Выбирается наиболее конкретный тип исключения. Синтаксис принят как рабочий, но
должен быть повторно рассмотрен при формализации грамматики `throws`.

Для union фиксируется только семантика вариантов. Физический layout (fixed
tagged union, косвенное хранение или иная оптимизация) выбирает компилятор при
обязательном сохранении наблюдаемого поведения.

`memory/classes-internal.md` описывает концептуальный внутренний IR, а не
пользовательский синтаксис. Его псевдокод не принимается обычным parser-ом и не
имеет гарантий совместимости.

## Решения по синтаксису от 2026-09-06

Раздел фиксирует решения, принятые при разборе замысла синтаксиса, и список
правок, которые из них следуют. Разбор шёл поверх этого аудита и не повторяет
его: здесь только грамматика и перегруженные знаки.

### Решения

1. **Пробельный вызов** запрещён после любого ключевого слова и после любого
   идентификатора. `return f y`, `if f y`, `throw make x` — ошибка компиляции.
   `let x = f y` и `a + f y` допустимы: перед вызовом стоит знак, а не слово.
2. **`<|` и `=>`** в таблице приоритетов стоят выше присваивания.
3. **`->`** пишется только у типа результата и в типах функций. Тело замыкания
   пишется через `=>`.
4. **Интерполяция строк** — только `${x}`. Формы `\(x)`, `$name` и `{x}` не
   существуют.
5. **`${…}` в метафункциях** остаётся. Внутри строкового литерала `${…}` —
   всегда интерполяция во время выполнения; вставка кода в строки не заходит.
   Вставка пишется только со скобками `${code}`; голое `$name` — плейсхолдер
   замыкания.
6. **Альтернатива в образце** — `|`: `if char is "a" | "e"`. Запятая в образцах
   не используется. Справа от `is` стоит образец, и `|` принадлежит ему; между
   условиями пишется `||`. Оператор `is` неассоциативен: два `is` подряд без
   скобок — ошибка компиляции.
7. **Одна конструкция сопоставления — `match`**, оператор и выражение сразу.
   Ветка — `образец: выражение` либо `образец: { блок }`. Слов `case`,
   `default` и `fallthrough` нет; умолчание — `_`. Вариант enum в образце
   пишется с точкой. `switch` из языка уходит.
8. **Генераторы**: `yield` отдаёт элемент, `return` завершает итогом. Форма
   `flow { … } yield y` заменяется на `return y` последней инструкцией блока.
   Запись `<| n <- n + 1` в генераторах не используется; `<|` — только
   применение функции.
9. **Варианты enum** объявляются фигурными скобками, поля всегда именованные:
   `failure { code: Int, message: String }`, `qrCode { code: String }`.
   Безымянных полей у вариантов нет. Создание — вызовом с метками:
   `.failure(code: 404, message: "…")`. Образец — `{ }` по имени, часть полей
   можно опустить: `.failure { message }`.
10. **Деструктуризация** — той же формой, что образец: `let Point { x, y } = p`,
    `let { x, y } = p`, `let { x, y: py } = p`. Кортеж разбирается круглыми
    скобками `let (x, _) = pair`; именованный кортеж дополнительно допускает
    `let { name, age } = person`. Форма `Type -> pattern` из языка уходит.
11. **Typestate** в сигнатуре пишется словом `state`: `fn read() -> String
    state Open`, `fn open() state Closed >> Open`. Порядок хвоста сигнатуры:
    `-> тип`, `state`, `in`, `throws | throws only | nothrows`.
12. **Правило пробелов для знаков.** Знак, отделённый слева и прижатый справа,
    — префикс (`%db`, `-x`, `&x`); отделённый с обеих сторон — бинарный
    (`a % b`); прижатый слева и отделённый справа — постфикс (`next*`,
    `next+`). Сигил `%` для контекста остаётся.
13. **Диапазоны**: закрытый диапазон — `a..b`; запись `a...b` — ошибка. Формы
    `..<`, `<..` и `<..<` остаются.
14. **`let` на структуре** замораживает всё значение: `let r = Rectangle(…)`
    запрещает и `r.color = …`, даже если поле объявлено `var`.
15. **`param` в теле функции** — все объявления подряд, до первой инструкции.
16. **Регистр имён** закреплён лексически: с заглавной буквы — типы, состояния,
    населения `set`, контексты; со строчной — значения, функции, поля,
    варианты enum.
17. **Перенос строк.** Тело замыкания после `=>` без фигурных скобок кончается
    на конце строки; многострочное тело — только в `{ }`. Строка, начинающаяся
    с `.` или с бинарного оператора, продолжает выражение предыдущей строки.
18. **Видимость модуля** пишется словом `public`; `pub` — ошибка.
19. **`with` и `use`** в их нынешних ролях остаются без изменений.

Открытым остаётся `throws!` как односимвольная семантика must-handle.
