# Миф про безопасный язык

Рассмотрим классическую структуру данных — двусвязный список. Каждый его узел
хранит два указателя: на следующего и предыдущего соседа.

```text
left <──> node <──> right
```

Вот так выглядит удаление среднего узла на C:

```c
void detach(Node *node) {
    node->prev->next = node->next;
    node->next->prev = node->prev;
    free(node);
}
```

Данная реализация не позволяет статически доказать, что программа корректна с
точки зрения управления памятью. Для такого доказательства необходимо
установить несколько фактов:

- `node`, `node.prev` и `node.next` указывают на живые объекты;
- соседи действительно связаны с `node` в обе стороны;
- после `free(node)` ни одна доступная ссылка не позволяет разыменовать `node`;
- две записи восстанавливают связность списка;
- функция не изменяет постороннюю память через алиасы.

Далее рассмотрим, как разные системы устанавливают эти факты. Типовые системы
ограничивают допустимые формы владения, runtime проверяет живость динамически, а
логические верификаторы доказывают инварианты структуры. Более поздние системы
используют те же доказательства для синтеза кода.

## Контракты Хоара

В 1969 году Тони Хоар предложил рассуждать о программе через условия до и после
её выполнения:

```text
{P} program {Q}
```

Контракт удаления узла можно записать следующим образом:

```text
requires node.prev.next == node
requires node.next.prev == node

detach(node)

ensures old(node.prev).next == old(node.next)
ensures old(node.next).prev == old(node.prev)
```

Постусловия формализуют требование к связности списка после удаления. При
модульной проверке реализацию функции сопоставляют с этим контрактом, а
вызывающий код анализируют без повторного разбора её тела. Такой подход был
предложен Тони Хоаром в работе [An Axiomatic Basis for Computer
Programming](https://doi.org/10.1145/363235.363259).

Для указателей такого контракта недостаточно. Допустим, существует ещё одна
ссылка на удаляемый узел:

```text
observer ──> node
```

Приведённый контракт эту ссылку не учитывает. Кроме того, при изменении
`left.next` необходимо зафиксировать, какая остальная память сохраняет прежнее
состояние. Для общей кучи явное перечисление таких объектов может оказаться
больше реализации функции.

Поэтому проверяющей системе нужны сведения об алиасах и правах на память: кто
может указывать на объект и кто вправе читать, изменять или освобождать его.

## Владение и регионы

Один из подходов состоит в ограничении множества программ, принимаемых системой
типов. Линейные и аффинные типы запрещают неявное копирование ресурса. Владение
передаётся явно, а ссылка не может пережить владельца.

Региональные системы применили ту же мысль к группам объектов. В Cyclone каждый
указатель был связан с регионом происхождения, а компилятор проверял, что он не
переживёт регион. Язык сохранял близкий к C контроль над представлением. Для
этого программисту приходилось указывать региональные параметры и эффекты:
[Region-Based Memory Management
in Cyclone](https://www.cs.umd.edu/projects/cyclone/papers/cyclone-regions.pdf).

Если все узлы двусвязного списка размещены в одном регионе, внутренние `prev` и
`next` остаются действительными до уничтожения региона. При этом немедленное
освобождение отдельного узла требует дополнительного механизма. Региональная
модель в первую очередь контролирует время жизни группы объектов.

## Rust: владение отдельными объектами

Rust сделал владение частью повседневной компиляции. В каждый момент допустимы
либо несколько `&T` для чтения, либо один `&mut T` для изменения. Ссылка не
должна пережить значение, из которого она получена.

Односвязный список непосредственно соответствует этой модели:

```rust
struct Node<T> {
    value: T,
    next: Option<Box<Node<T>>>,
}
```

Каждый `Box` единолично владеет хвостом. Но добавить `prev` типа `Box<Node<T>>`
нельзя: тогда два узла должны были бы владеть друг другом. Возникает цикл без
единственного корня уничтожения.

Без `unsafe` типичное решение использует сильную ссылку вперёд и слабую назад:

```rust
use std::cell::RefCell;
use std::rc::{Rc, Weak};

type Link<T> = Option<Rc<RefCell<Node<T>>>>;
type Back<T> = Option<Weak<RefCell<Node<T>>>>;

struct Node<T> {
    value: T,
    prev: Back<T>,
    next: Link<T>,
}

struct List<T> {
    head: Link<T>,
    tail: Link<T>,
}
```

`Rc` разрешает несколько владельцев, `Weak` не удерживает цель живой, а
`RefCell` переносит проверку конфликта изменяемых доступов из компилятора в
runtime. Удаление получается заметно длиннее C-версии:

```rust
impl<T> List<T> {
    fn detach(&mut self, node: &Rc<RefCell<Node<T>>>) {
        let (prev, next) = {
            let mut node = node.borrow_mut();
            let prev = node.prev.take().and_then(|p| p.upgrade());
            let next = node.next.take();
            (prev, next)
        };

        match &prev {
            Some(p) => p.borrow_mut().next = next.clone(),
            None => self.head = next.clone(),
        }

        match &next {
            Some(n) => {
                n.borrow_mut().prev = prev.as_ref().map(Rc::downgrade)
            }
            None => self.tail = prev,
        }
    }
}
```

Rust гарантирует, что безопасный код не разыменует освобождённую память. Однако
он не доказывает автоматически условие
`x.next.prev == x`. Если забыть обновить `prev`, программа останется безопасной
для памяти, но список станет логически неправильным.

Интрузивный список без `Rc` и `RefCell` тоже возможен, однако сырые указатели и
доказательство их инвариантов окажутся внутри `unsafe`. Безопасность внешнего API
тогда зависит от корректности внутренней небезопасной реализации.

Non-lexical lifetimes научили borrow checker завершать заимствование после его
последнего использования, а не только в конце блока. Polonius развивает анализ
через происхождение заимствований и отношения между ними. Его альфа-режим был
включён в nightly в августе 2026 года, но он повышает точность проверки заимствований,
а не превращает типовую систему в доказатель произвольных графовых инвариантов:
[сообщение команды Rust](https://blog.rust-lang.org/2026/08/04/enabling-polonius-alpha-on-nightly/)
и [репозиторий Polonius](https://github.com/rust-lang/polonius).

Математическое основание здесь не совпадает с реализацией компилятора. RustBelt
построил машинно проверенную модель существенной части Rust и сформулировал
условия, при которых библиотека с внутренним `unsafe` действительно образует
безопасную абстракцию: [RustBelt: Securing the Foundations of the Rust
Programming Language](https://people.mpi-sws.org/~dreyer/papers/rustbelt/paper.pdf).

## Pony: права на группы алиасов

В Pony время жизни объектов контролирует сборщик мусора,
поэтому `prev` и `next` могут быть обычными сильными ссылками. Типовая система
занята другим вопросом: кому разрешено видеть и изменять граф.

У каждой ссылки есть capability. `ref` даёт изменяемый доступ внутри актора,
`val` обозначает глубоко неизменяемый разделяемый граф, `iso` — изолированный
граф, который можно передать другому актору, `box` — доступ только для чтения,
а `tag` позволяет знать идентичность без чтения полей. Полная система включает
также переходную capability `trn`.

Внутри одного актора двусвязный список выглядит так:

```pony
class ref Node
  let value: U64
  var prev: (Node ref | None) = None
  var next: (Node ref | None) = None

  new ref create(value': U64) =>
    value = value'

class ref List
  fun ref detach(node: Node ref) =>
    match node.prev
    | let before: Node ref => before.next = node.next
    end

    match node.next
    | let after: Node ref => after.prev = node.prev
    end

    node.prev = None
    node.next = None
```

Цикл не нужно разрывать ради подсчёта ссылок. Но изменяемый граф с `ref` нельзя
просто передать другому актору: для безопасной передачи его изолируют или делают
неизменяемым. Эти правила описаны в [руководстве по reference
capabilities](https://tutorial.ponylang.io/reference-capabilities/reference-capabilities.html)
и статье [Reference Capabilities for Concurrency
Control](https://drops.dagstuhl.de/storage/00lipics/lipics-vol056-ecoop2016/LIPIcs.ECOOP.2016.5/LIPIcs.ECOOP.2016.5.pdf).

В отличие от Rust, Pony не требует единственного владельца каждого узла. Вместо
этого система ограничивает права всей группы алиасов, а время жизни обслуживает
runtime. Pony-ORCA собирает память акторов и отслеживает межакторные ссылки:
[Ownership and Reference Counting based Garbage
Collection](https://www.ponylang.io/media/papers/OGC.pdf).

Capability `ref` обеспечивает правила доступа, но не требует выполнить обе
половины переподключения списка.

## Другие единицы владения

На примере двусвязного списка видны четыре основных варианта: запретить цикл,
собирать его автоматически, проверять ссылку динамически или владеть более
крупной областью памяти.

В Mezzo основным объектом типизации стало permission. Разрешение
одновременно сообщало форму значения и право доступа к нему. Неизменяемые
permissions можно было дублировать, изменяемые обычно были аффинными. Для графов,
где контейнер должен принять множество узлов, появился механизм
`adopt`/`abandon`. Он расширял выразительность, но добавлял динамическую проверку
и сложные операции упаковки: [Programming with Permissions in
Mezzo](https://gallium.inria.fr/~fpottier/publis/pottier-protzenko-mezzo.pdf)
и ретроспектива [A Few Lessons from the Mezzo
Project](https://cambium.inria.fr/~fpottier/publis/fpottier-protzenko-lessons-mezzo.pdf).

Project Verona исследует владение целым регионом. Внутри региона может жить
свободный граф с `prev`, `next` и дополнительными указателями; граница региона
контролирует время жизни и конкурентный доступ. Это снимает пообъектную
линейность, но делает освобождение отдельного узла внутренней задачей региона.
Проект остаётся исследовательским: [описание Microsoft
Research](https://www.microsoft.com/en-us/research/project/project-verona/).

Vale исследует поколенческие ссылки. Ячейка хранит текущее поколение, ссылка —
запомненное. При освобождении поколение меняется:

```text
dereference(pointer):
    assert pointer.generation == pointer.slot.generation
    return pointer.slot.value

free(slot):
    slot.generation += 1
```

Если освободившуюся ячейку займёт новый объект, проверка отклонит старый `prev`
из-за несовпадения поколений. Эта модель допускает общие графы, но требует
метаданных и runtime-проверок при разыменовании. Проект находится в alpha, а
часть оптимизаций пока заявлена как будущая: [описание generational
references](https://vale.dev/memory-safe).

Austral использует строгую линейную модель: линейное
значение должно быть использовано ровно один раз. Это хорошо предотвращает
double-free и use-after-free, но двусвязный граф требует вынести разделяемость в
отдельную абстракцию. См. [спецификацию
Austral](https://austral-lang.org/spec/spec.html).

Hylo ограничивает роль ссылочной семантики. Его `subscript` не
возвращает долгоживущую ссылку, а временно проецирует часть значения с правом
чтения или изменения. Для локальной мутации это похоже на заимствование без
явных lifetime-параметров. Общий объектный граф при этом намеренно не является
центральной моделью языка: [введение в Hylo](https://hylo-lang.org/introduction/).

Все эти языки делают ошибки памяти менее выразимыми, но ни один типовой
квалификатор сам по себе не доказывает, что `next` и `prev` согласованы. Для
этого требуется описание формы структуры.

## Анализ формы кучи

В конце 1990-х сформировалось направление shape analysis. Анализатор приближённо
вычисляет возможную форму памяти: может ли путь быть циклическим, способны ли две
переменные указывать в один узел, бывает ли поле `NULL`. Единственный владелец
при этом не требуется.

В TVLA Сагива, Репса и Вильгельма множество конкретных куч представляется одной
трёхзначной логической структурой. Предикат получает значение «истина», «ложь»
или «неизвестно». Если анализатор не может установить, что
`node.prev.next == node` во всех состояниях, результатом будет «неизвестно».
Исследование описано в [Parametric Shape Analysis via
3-Valued Logic](https://research.cs.wisc.edu/techreports/viewreport.php?report=1383).

Такой анализ может работать почти без пользовательских контрактов. На общих
графах его точность снижается: несколько разных узлов сливаются в один
абстрактный, и часть свойств получает значение «неизвестно». Отслеживание
дополнительных отношений увеличивает стоимость анализа.

## Логика разделения

Логика разделения расширила контракты Хоара средствами для локального описания
изменяемого фрагмента без перечисления всей остальной памяти.

Формула:

```text
x ↦ Node(value, next) * list(next)
```

говорит, что ячейка `x` и память хвоста списка существуют одновременно и не
пересекаются. Оператор `*` — разделяющая конъюнкция. Благодаря frame rule
доказательство локальной операции автоматически переносится на кучу с
дополнительным независимым фрагментом.

Двусвязный список определяется рекурсивно с ожидаемым предшественником:

```text
dll(x, previous) =
    x = null ∧ emp
  ∨ exists next:
        x ↦ Node(previous, next)
      * dll(next, x)
```

Допустимое значение `prev` входит в определение `dll`. Удаление среднего узла
можно описать как преобразование:

```text
requires
    left  ↦ Node(lp, node)
  * node  ↦ Node(left, right)
  * right ↦ Node(node, rn)

ensures
    left  ↦ Node(lp, right)
  * right ↦ Node(left, rn)
```

Узел `node` отсутствует в постусловии: право на него потреблено. Обе обратные
ссылки названы явно, поэтому забытая запись не пройдёт доказательство. Основные
идеи и примеры собраны в работе Джона Рейнольдса [Separation Logic: A Logic for
Shared Mutable Data Structures](https://www.cs.cmu.edu/~jcr/seplogic.pdf).

Такой подход требует математической модели структуры наряду с её реализацией.
Для общего графа индуктивный предикат сложнее, поскольку подграфы могут
пересекаться, а `*` утверждает непересечение.

## Автоматизация доказательств

Первые системы требовали значительного объёма ручных доказательств. Последующие
инструменты использовали символическое исполнение и автоматизировали стандартные
шаги вывода.

Smallfoot ограничил язык предикатов формы, зато смог автоматически проверять
модульные операции над списками. Пользователь описывал `list` или `dll`, а
инструмент строил verification conditions и применял frame rule: [Smallfoot:
Modular Automatic Assertion Checking with Separation
Logic](https://jberdine.github.io/pub/2005_fmco.pdf).

VeriFast использует полуавтоматическую проверку C, Java и Rust. Автор задаёт
предусловия, постусловия, рекурсивные предикаты и инварианты циклов. Инструмент
проверяет каждую функцию отдельно, используя контракт вызываемой функции вместо
её тела. Двусвязный список доказуем, однако объём аннотаций может быть сопоставим
с объёмом реализации: [публикации и примеры
VeriFast](https://people.cs.kuleuven.be/~bart.jacobs/verifast/).

Bi-abduction позволяет вывести часть этих контрактов. Если для разыменования
`node.prev` не хватает гипотезы, анализ ищет недостающее предусловие; одновременно
он вычисляет frame — память, не затронутую функцией. Это позволило строить
межпроцедурный анализ снизу вверх и масштабировать идеи separation logic до
крупных кодовых баз. Подход лёг в основу Infer: [Compositional Shape Analysis by
Means of Bi-Abduction](https://www.cs.ox.ac.uk/people/hongseok.yang/paper/popl09.pdf).

Infer и полный верификатор решают разные задачи. Анализатор ищет вероятные ошибки
и может потерять точность. Верификатор требует закрыть каждое обязательство и
отказывается принимать функцию, пока контракт не доказан.

## Viper как промежуточный язык верификации

Промежуточная инфраструктура позволяет повторно использовать SMT-интеграцию,
символическое исполнение и логику разрешений. В Viper право доступа к полю
представлено как логический ресурс:

```text
acc(object.field)
```

Упрощённая проверка нашего `detach` выглядит так:

```viper
method detach(left: Ref, node: Ref, right: Ref)
  requires acc(left.next) && acc(node.prev) && acc(node.next)
  requires acc(right.prev) && acc(node.value)
  requires left.next == node && node.prev == left
  requires node.next == right && right.prev == node

  ensures acc(left.next) && acc(right.prev)
  ensures left.next == right && right.prev == left
{
  left.next := right
  right.prev := left

  exhale acc(node.prev) && acc(node.next) && acc(node.value)
}
```

Если забыть `right.prev := left`, постусловие не доказывается. Если затем
прочитать `node.value`, проверка не найдёт разрешения: операция `exhale` его
потребила. Идентичность `node` при этом ещё можно сравнивать — запрещено именно
разыменование без права.

Viper имеет backend символического исполнения Silicon и backend генерации
verification conditions Carbon. Frontend переводит конструкции исходного языка
в Viper, запускает один из решателей и возвращает ошибку в исходные координаты.
Архитектура описана в [Viper: A Verification Infrastructure for
Permission-Based
Reasoning](https://pmpub.inf.ethz.ch/publications/MuellerSchwerhoffSummers16.pdf).

Viper доказывает сгенерированную промежуточную программу. Корректность всей
проверки поэтому зависит и от frontend: ошибка при переводе поля или операции
освобождения меняет смысл доказываемой программы.

## Синтез программ из спецификаций

SuSLik принимает предусловие и постусловие в варианте separation logic и ищет
программу, преобразующую одну кучу в другую.

Для локального фрагмента двусвязного списка задача задаётся следующим
преобразованием:

```text
before: left <──> node <──> right
after:  left <────────────> right
```

Правила Synthetic Separation Logic одновременно являются правилами построения
кода. Найденная последовательность записей — это терм доказательства, поэтому
она корректна по построению. Подход реализован в SuSLik и описан в [Structuring
the Synthesis of Heap-Manipulating
Programs](https://arxiv.org/abs/1807.07022).

Низкоуровневые предикаты при этом образуют отдельный язык спецификаций. Их нужно
описывать для разных представлений данных; при большом пространстве поиска
синтезатору могут потребоваться дополнительные указания.

Pika переносит спецификацию на функциональный уровень. Автор описывает абстрактное
преобразование структуры отдельно от размещения в памяти; транслятор строит
задачу SuSLik, а тот синтезирует C-код и доказательство. Исследование опубликовано
как [Higher-Order Specifications for Deductive Synthesis of Programs with
Pointers](https://doi.org/10.4230/LIPIcs.ECOOP.2024.45).

Синтез работает в тех случаях, когда форма рекурсии, представление данных и
множество допустимых команд достаточно ограничены. Для операции над общим
графом системе необходимо знать, как найти входящие рёбра и какие
операции над ними допустимы.

## Границы отдельных подходов

Rust встроил консервативную проверку времени жизни в обычную компиляцию. Pony
допустил циклические структуры внутри графов с контролируемыми правами доступа,
а освобождение памяти оставил сборщику мусора. Региональные системы укрупнили
единицу владения. Поколенческие ссылки дополнили статические гарантии
динамической проверкой. Shape analysis приближённо вычисляет форму кучи,
separation logic позволяет задавать её явно, Viper предоставляет общую
инфраструктуру доказательства, а SuSLik и Pika синтезируют программы для
ограниченных классов спецификаций.

На двусвязном списке различимы три независимые гарантии:

1. узел ещё жив;
2. у операции есть право менять его поля;
3. `next` и `prev` согласованы.

Сборщик мусора решает первую задачу, но не третью. Borrow checker решает первую
и часть второй, но не выводит произвольный инвариант структуры. Логический
верификатор способен доказать все три, но требует модели и иногда аннотаций.
Синтезатор может построить код переподключения в рамках заданной модели памяти и
допустимого набора операций.

На практике эти механизмы можно сочетать. Типовая система проверяет локальные
правила владения, runtime выполняет необходимые динамические проверки, а
логический backend устанавливает глобальные инварианты. Выбор структуры данных
и способа поиска ссылок при этом остаётся частью алгоритма.
