# Как логика научилась проверять программы с указателями

Ошибки памяти долго считались почти неизбежной платой за ручное управление
данными. Указатель может пережить объект, два поля могут неожиданно указывать в
одно место, а одна запись способна нарушить связность целого графа. Обычной
проверки типов для этого недостаточно: компилятору требуется модель не только
значений, но и состояния памяти.

За последние полвека сложились три разных подхода. Типовые системы запрещают
опасные программы по сравнительно простым правилам. Статические анализаторы
приближённо вычисляют возможную форму памяти. Дедуктивные верификаторы переводят
программу в математические утверждения и передают их решателю. Современные
системы часто соединяют все три подхода.

## От троек Хоара к состоянию памяти

В 1969 году Тони Хоар предложил описывать программу тройкой:

```text
{P} program {Q}
```

`P` — условие до выполнения, `Q` — условие после него. Например:

```text
{x > 0}
y := x + 1
{y > 1}
```

Работа Хоара дала основу модульному доказательству программ: функцию можно
проверить отдельно, а в вызывающем коде использовать только её контракт. Это
перенесло разговор о корректности из тестовых запусков в область правил вывода
и формул. Исходная статья — [An Axiomatic Basis for Computer
Programming](https://doi.org/10.1145/363235.363259).

С числами такая схема работает естественно. С указателями возникает проблема
алиасинга. Из `x.next = y` нельзя понять, изменилась ли только структура `x`:
возможно, другая переменная `z` указывает на тот же объект. Полный контракт
пришлось бы дополнять длинным перечнем всей памяти, которая не изменилась.

## Типы владения и регионы

Один путь состоял в том, чтобы не доказывать произвольное совместное владение, а
ограничить его правилами языка. Линейные и аффинные типы разрешают использовать
владеющее значение ограниченное число раз. Borrowing временно передаёт право
доступа, не передавая сам ресурс. Регионы связывают срок жизни сразу с группой
объектов.

Характерный исследовательский язык Cyclone перенёс эти идеи на уровень,
близкий к C: указатель знал регион происхождения, а система типов проверяла, что
он не переживёт этот регион. Авторы сочетали явные аннотации, значения по
умолчанию и локальный вывод, чтобы уменьшить их количество. См. [Region-Based
Memory Management in Cyclone](https://www.cs.umd.edu/projects/cyclone/papers/cyclone-regions.pdf).

Позже владение и заимствование стали практической основой Rust. Важно различать
реализацию borrow checker и её математическое обоснование. Проект RustBelt
построил машинно проверенную модель существенной части языка и показал, какие
обязательства должны выполнять библиотеки с внутренним `unsafe`: [RustBelt:
Securing the Foundations of the Rust Programming
Language](https://people.mpi-sws.org/~dreyer/papers/rustbelt/paper.pdf).

### Rust: доказательство, встроенное в обычную компиляцию

Практический успех Rust связан с тем, что большая часть доказательства скрыта в
типизации. У значения есть владелец; `&T` разрешает совместное чтение, а `&mut T`
— исключительный доступ. Ссылка не должна пережить владельца. Программист не
пишет логические формулы, но borrow checker фактически решает ограниченную задачу
о происхождении ссылок, сроках их использования и конфликтах доступа.

```rust
let first = &node.value;
let second = &node.value;      // два читателя допустимы

let edit = &mut node.value;    // допустимо только после конца чтений
```

Non-lexical lifetimes сделали срок заимствования зависимым от фактического
использования, а не только от фигурных скобок. Следующий вариант анализа,
Polonius, формулирует borrow checking через происхождение заимствований и
отношения между ними. В августе 2026 года его альфа-режим был включён в nightly,
но это ещё не означает замену основного checker во всех режимах: [официальное
сообщение Rust](https://blog.rust-lang.org/2026/08/04/enabling-polonius-alpha-on-nighty/)
и [репозиторий Polonius](https://github.com/rust-lang/polonius).

У модели есть ясная граница. Дерево с уникальными дочерними узлами выражается
прямо, а общий изменяемый граф обычно требует индексов, `Rc`/`Arc`, внутренней
изменяемости или локального `unsafe`. Это не дефект доказательства: правило
намеренно выбирает локальную и быстро проверяемую дисциплину вместо полного
логического анализа произвольного графа. `unsafe` расширяет выразительность, но
переносит обязательство доказательства на автора абстракции; именно эту границу
формализует RustBelt.

### Pony: не владение объектом, а права каждой ссылки

Pony был создан прежде всего для безопасной конкурентности акторов. Каждая
ссылка несёт одну из шести reference capabilities:

| Capability | Смысл |
|---|---|
| `iso` | изолированный изменяемый граф, который можно передать другому актору |
| `trn` | изменяемая переходная ссылка, которую позже можно восстановить в более сильное состояние |
| `ref` | обычный изменяемый доступ внутри одного актора |
| `val` | глубоко неизменяемое значение, безопасно разделяемое между акторами |
| `box` | чтение без права записи |
| `tag` | только идентичность объекта, без чтения его полей |

Главная идея — capability описывает не только действия текущей ссылки, но и то,
какие действия возможны через её алиасы. Например, `iso` полезна потому, что
изменяемый граф снаружи изолирован; `val` можно свободно разделять, потому что
граф неизменяем. Полные правила и viewpoint adaptation описаны в [официальном
руководстве Pony](https://tutorial.ponylang.io/reference-capabilities/reference-capabilities.html)
и статье [Reference Capabilities for Concurrency
Control](https://drops.dagstuhl.de/storage/00lipics/lipics-vol056-ecoop2016/LIPIcs.ECOOP.2016.5/LIPIcs.ECOOP.2016.5.pdf).

Pony не пытается статически определить точный момент смерти каждого объекта.
Память собирается runtime; Pony-ORCA сочетает локальную сборку у акторов с
учётом межакторных ссылок: [Ownership and Reference Counting based Garbage
Collection](https://www.ponylang.io/media/papers/OGC.pdf). Поэтому циклы и много
алиасов внутри актора естественнее, чем в системе единственного владельца, но
за это платят сборщиком мусора и более сложной алгеброй capabilities.

### Экспериментальные языки: разные единицы владения

Исследовательские языки интересны тем, что каждый меняет один фундаментальный
выбор: чем именно владеет программа — объектом, разрешением, регионом или
идентичностью с поколением.

**Mezzo** сделал permissions частью статической типизации языка семейства ML.
Разрешение сообщает одновременно форму объекта и право доступа к нему;
неизменяемые разрешения можно копировать, изменяемые обычно аффинны. Для
структур, где один владелец должен временно принять много узлов, был предложен
механизм `adopt`/`abandon`. Он расширяет набор выразимых графов, но добавляет
динамическую проверку и сложные операции упаковки разрешений. См. [Programming
with Permissions in Mezzo](https://gallium.inria.fr/~fpottier/publis/pottier-protzenko-mezzo.pdf)
и ретроспективу [A Few Lessons from the Mezzo
Project](https://cambium.inria.fr/~fpottier/publis/fpottier-protzenko-lessons-mezzo.pdf).

**Project Verona** исследует владение не отдельным объектом, а целым регионом.
Внутри региона возможен свободный граф с множеством ссылок; границы региона
контролируют передачу и конкурентный доступ. Это ослабляет ограничения
пообъектной линейности, но делает регион единицей изоляции, времени жизни и
синхронизации. Microsoft прямо обозначает проект как исследовательский и не
готовый для прикладного использования: [описание
проекта](https://www.microsoft.com/en-us/research/project/project-verona/) и
[исходный код](https://github.com/microsoft/verona).

**Vale** исследует поколенческие ссылки. Объект хранит текущее поколение, ссылка
— запомненное; разыменование сверяет их. После освобождения поколение меняется,
и старая ссылка обнаруживается как недействительная. Такой подход разрешает
обратные ссылки и общие графы без доказательства единственного заимствования, но
переносит часть цены в runtime и представление ссылок. Проект находится в alpha,
а некоторые заявленные оптимизации пока описаны как будущие: [описание
поколенческих ссылок](https://vale.dev/memory-safe) и [состояние
языка](https://vale.dev/).

**Austral** выбирает более строгий путь. Линейное значение должно быть
использовано ровно один раз: его нельзя неявно скопировать или забыть. Это даёт
простое доказательство отсутствия double-free и use-after-free и позволяет
представлять права на внешние ресурсы линейными capabilities. Цена — явная
передача ресурса через функции и ограничения на циклы и ветвления. Правила
описаны в [спецификации Austral](https://austral-lang.org/spec/spec.html).

**Hylo** старается не сделать ссылки удобнее, а уменьшить их роль. Основой служит
mutable value semantics: функция получает независимый доступ к значению, а
`subscript` временно проецирует часть хранилища вместо возврата долгоживущей
ссылки. По смыслу это похоже на заимствование, но сроки жизни не появляются в
пользовательских типах. Такой дизайн хорошо скрывает локальную мутацию, однако
намеренно не делает произвольный граф ссылок центральной моделью программы:
[введение в Hylo](https://hylo-lang.org/introduction/).

Сила типовых решений — в предсказуемости и скорости проверки. Их цена —
консерватизм либо дополнительный runtime-механизм. Произвольные циклы,
интрузивные структуры и множество долгоживущих изменяемых ссылок плохо
укладываются в простое правило «один владелец — много читателей». Pony выбирает
capabilities и GC, Verona — владение регионом, Vale — динамическую проверку
поколения, а Hylo сокращает само пространство программ со ссылочной семантикой.

## Один тест для разных моделей: двусвязный список

Двусвязный список — маленький, но показательный пример. Для каждого ребра
`x.next = y` требуется обратное равенство `y.prev = x`. При удалении `x` нужно
одновременно переподключить соседей и гарантировать, что ни одна сильная ссылка
больше не разыменует удалённый узел.

В небезопасном императивном языке операция выглядит просто:

```c
void detach(Node *node) {
    if (node->prev != NULL)
        node->prev->next = node->next;
    if (node->next != NULL)
        node->next->prev = node->prev;
    free(node);
}
```

Но типы не доказывают, что `node` принадлежит именно этому списку, что других
ссылок на него нет и что вызывающий код не воспользуется старым адресом после
`free`.

### Rust: сильная ссылка вперёд, слабая назад

Без `unsafe` двусвязный список обычно строят на `Rc<RefCell<_>>`: `Rc` допускает
несколько владельцев, `RefCell` проверяет конфликт изменяемых доступов во время
исполнения, а `Weak` разрывает цикл подсчёта ссылок.

```rust
use std::cell::RefCell;
use std::rc::{Rc, Weak};

type Link<T> = Option<Rc<RefCell<Node<T>>>>;
type Back<T> = Option<Weak<RefCell<Node<T>>>>;

struct Node<T> {
    value: T,
    prev: Back<T>,
    next: Link<T>,
}

struct List<T> {
    head: Link<T>,
    tail: Link<T>,
}

impl<T> List<T> {
    fn detach(&mut self, node: &Rc<RefCell<Node<T>>>) {
        let (prev, next) = {
            let mut node = node.borrow_mut();
            let prev = node.prev.take().and_then(|p| p.upgrade());
            let next = node.next.take();
            (prev, next)
        };

        match &prev {
            Some(p) => p.borrow_mut().next = next.clone(),
            None => self.head = next.clone(),
        }

        match &next {
            Some(n) => {
                n.borrow_mut().prev = prev.as_ref().map(Rc::downgrade)
            }
            None => self.tail = prev,
        }
    }
}
```

Здесь нет висячего машинного указателя: внешний `Rc` продолжает держать
отсоединённый узел живым, а `Weak::upgrade` явно проверяет, существует ли цель.
Однако типовая система сама не доказывает инвариант `next.prev == self` — его
обеспечивает реализация `List`. Ошибка переподключения является логической
ошибкой структуры, хотя память остаётся безопасной.

Интрузивная реализация с настоящими указателями может избежать `Rc` и
`RefCell`, но тогда локализует доказательство в `unsafe`-модуле. Безопасный API
снаружи корректен только настолько, насколько верны внутренние инварианты этого
модуля.

### Pony: свободный цикл внутри актора

В Pony узлы внутри одного актора могут иметь обычные изменяемые ссылки `ref` в
обе стороны. Следующий пример показывает основную форму; управление границами
списка опущено, чтобы оставить видимым переподключение:

```pony
class ref Node
  let value: U64
  var prev: (Node ref | None) = None
  var next: (Node ref | None) = None

  new ref create(value': U64) =>
    value = value'

class ref List
  fun ref detach(node: Node ref) =>
    match node.prev
    | let before: Node ref => before.next = node.next
    end

    match node.next
    | let after: Node ref => after.prev = node.prev
    end

    node.prev = None
    node.next = None
```

Сборщик мусора отвечает за время жизни, поэтому цикл `prev`/`next` не требует
слабой стороны. Capability `ref` не позволяет свободно передать такой
изменяемый граф другому актору. Для передачи граф должен быть изолирован как
`iso` либо стать неизменяемым `val`. Как и в Rust-примере, равенство парных
ссылок является инвариантом реализации контейнера, а не автоматически
порождаемой теоремой типа `ref`.

### Логика разделения: определить список рекурсивно

В дедуктивной системе операция сопровождается предикатом формы. Упрощённое
определение сегмента двусвязного списка:

```text
dll(x, previous) =
    x = null ∧ emp
  ∨ exists next:
        x ↦ Node(previous, next)
      * dll(next, x)
```

Контракт удаления среднего узла можно записать как преобразование двух соседних
ячеек:

```text
requires
    left  ↦ Node(lp, node)
  * node  ↦ Node(left, right)
  * right ↦ Node(node, rn)

ensures
    left  ↦ Node(lp, right)
  * right ↦ Node(left, rn)
```

Отсутствие `node ↦ ...` в постусловии означает, что право на его память
потреблено. Разделяющая конъюнкция доказывает, что три записи описывают разные
ячейки. Полный контракт дополнительно связывает этот локальный фрагмент с
остатком списка через frame rule.

### Permission-based IR: доступ как расходуемый ресурс

То же доказательство в промежуточном языке с разрешениями выглядит ближе к
обычному коду:

```viper
method detach(left: Ref, node: Ref, right: Ref)
  requires acc(left.next) && acc(node.prev) && acc(node.next)
  requires acc(right.prev) && acc(node.value)
  requires left.next == node && node.prev == left
  requires node.next == right && right.prev == node

  ensures acc(left.next) && acc(right.prev)
  ensures left.next == right && right.prev == left
{
  left.next := right
  right.prev := left

  exhale acc(node.prev) && acc(node.next) && acc(node.value)
}
```

Если после вызова попытаться прочитать `node.value`, verifier не найдёт
разрешения. Если забыть `right.prev := left`, он не сможет доказать
постусловие. В реальном frontend такой технический код должен генерироваться, а
пользователь должен видеть исходный алгоритм и сообщение на его языке.

### Регион и поколение: изменить единицу гарантии

Региональная модель делает владельцем весь список или целую группу структур.
Код переподключения остаётся почти таким же, как в C, но отдельный узел обычно
не возвращается системе немедленно:

```text
region ListNodes {
    detach(node)
    retire node
}

free region ListNodes
```

Все внутренние ссылки безопасны до смерти региона. Это удобно для сложных
графов, но индивидуальное освобождение требует tombstone, свободного списка или
дополнительного доказательства.

Поколенческая модель сохраняет свободные алиасы, добавляя динамическую проверку:

```text
reference = (slot, rememberedGeneration)

dereference(reference):
    assert reference.rememberedGeneration == slot.currentGeneration
    return slot.object

free(slot):
    slot.currentGeneration += 1
```

После удаления старые `prev`, `next` или внешние ссылки не получают доступ к
новому объекту, случайно занявшему тот же слот. Зато каждое неустранённое
разыменование платит проверкой поколения, а переполнение счётчика и повторное
использование хранилища становятся частью доверенной реализации.

Сравнение показывает, почему единственного красивого ответа нет:

| Модель | Что происходит с циклом | Что доказывается автоматически | Цена |
|---|---|---|---|
| Rust `Rc`/`Weak` | цикл разрывается слабой стороной | отсутствие висячего доступа | RC, runtime borrow и ручной инвариант пары |
| Pony | цикл собирает GC | безопасное разделение между акторами | GC и capability-алгебра |
| Логика разделения | цикл или список задаётся предикатом | форма и права до/после операции | спецификации и работа решателя |
| Регион | весь граф живёт одной группой | ссылки не переживают группу | грубая гранулярность освобождения |
| Поколения | старые ссылки остаются, но не проходят проверку | временная безопасность доступа | метаданные и runtime-проверка |

## Shape analysis: вычислить форму графа

Другой путь — не требовать доказательство от программиста, а статически
приблизить все состояния кучи. Shape analysis пытается выяснить, является ли
структура списком, деревом, циклом; могут ли два пути вести к одному объекту;
может ли поле быть `null`.

В конце 1990-х Сагив, Репс и Вильгельм предложили TVLA — анализ на основе
трёхзначной логики. Абстрактная структура объединяет много конкретных объектов,
а формула получает одно из трёх значений:

- истинно во всех представленных состояниях;
- ложно во всех состояниях;
- неизвестно.

Третье значение делает анализ безопасным: когда информации недостаточно,
инструмент не придумывает доказательство. Меняя набор логических предикатов,
можно настраивать анализ под списки, деревья и структуры с разделяемыми узлами.
Исходная работа: [Parametric Shape Analysis via 3-Valued
Logic](https://research.cs.wisc.edu/techreports/viewreport.php?report=1383).

Shape analysis способен работать почти без контрактов, но платит точностью и
стоимостью вычислений. Чем свободнее граф и сложнее данные в узлах, тем чаще
результатом становится «неизвестно».

## Логика разделения

Главный поворот произошёл на рубеже 2000-х. Логика разделения дополнила логику
Хоара способом говорить о независимых частях кучи. Формула:

```text
x ↦ Node(v, next) * list(next)
```

означает не просто две истины. Оператор `*` утверждает, что ячейка `x` и память,
занятая хвостом списка, не пересекаются. Это позволяет применять frame rule:
если команда работает только с одним фрагментом памяти, остальной фрагмент
автоматически сохраняется. Больше не нужно вручную перечислять всё, чего функция
не меняет.

Рекурсивный список описывается индуктивно:

```text
list(x) =
    x = null ∧ emp
  ∨ exists y: x ↦ Node(_, y) * list(y)
```

`emp` обозначает пустую кучу. Дерево задаётся сходным образом, но с двумя
разделёнными поддеревьями. Для двусвязного списка предикату приходится
дополнительно передавать ожидаемого предшественника:

```text
dll(x, previous) =
    x = null ∧ emp
  ∨ exists y: x ↦ Node(previous, y) * dll(y, x)
```

Такое определение одновременно описывает форму, допустимые алиасы и часть
прав владения памятью. Обзор Джона Рейнольдса [Separation Logic: A Logic for
Shared Mutable Data Structures](https://www.cs.cmu.edu/~jcr/seplogic.pdf)
показывает, как эта логика применяется к выделению, освобождению и изменению
рекурсивных структур.

## От ручных доказательств к автоматическим

Следующей задачей стала автоматизация. Smallfoot проверял функции по отдельности
и автоматически работал с ограниченным языком предикатов формы. Ограничение
было сознательным: менее выразительные спецификации позволяли полностью
автоматизировать проверку списков и некоторых конкурентных программ. См.
[Smallfoot: Modular Automatic Assertion Checking with Separation
Logic](https://jberdine.github.io/pub/2005_fmco.pdf).

VeriFast продолжил полуавтоматический путь для C, Java и позднее Rust.
Программист задаёт предусловия, постусловия, инварианты циклов и рекурсивные
предикаты, после чего инструмент символически выполняет каждую функцию. При
вызове используется контракт вызываемой функции, а не её тело. Это даёт
модульность, но требует заметного объёма призрачного кода и аннотаций. Описание
инструмента и публикации собраны на [странице
VeriFast](https://people.cs.kuleuven.be/~bart.jacobs/verifast/).

В 2009 году bi-abduction показала другой компромисс. Когда анализатору не хватает
факта для разыменования или вызова, он пытается логически вывести недостающую
часть предусловия и одновременно вычислить frame — память, которую операция не
затрагивает. Так стало возможно снизу вверх строить контракты функций без
анализа всех вызывающих контекстов. Работа легла в основу промышленного
семейства анализаторов Infer: [Compositional Shape Analysis by Means of
Bi-Abduction](https://www.cs.ox.ac.uk/people/hongseok.yang/paper/popl09.pdf).

Отличие от полной верификации принципиально. Такой анализ стремится находить
реальные ошибки в больших программах и допускает потерю точности. Дедуктивный
верификатор, напротив, требует доказать заявленный контракт целиком.

## Разрешения как промежуточный язык

По мере появления новых frontend-инструментов выяснилось, что каждый раз заново
реализовывать логику кучи, SMT-взаимодействие и символическое исполнение слишком
дорого. Так возникли промежуточные языки верификации.

Viper представляет доступ к полю как отдельный логический ресурс:

```text
acc(object.field)
```

Полное разрешение позволяет читать и писать, дробное — только читать. Если
разрешение не может быть доказано, доступ к полю отклоняется. Это естественно
моделирует владение, заимствование и передачу прав между функциями.

Viper предоставляет два основных способа проверки: символическое исполнение и
генерацию verification conditions. Frontend другого языка переводит свои типы,
контракты и операции в один промежуточный язык, а инфраструктура выполняет
доказательство. Архитектура описана в статье [Viper: A Verification
Infrastructure for Permission-Based
Reasoning](https://pmpub.inf.ethz.ch/publications/MuellerSchwerhoffSummers16.pdf)
и [официальном обзоре](https://www.pm.inf.ethz.ch/research/viper.html).

Это решает инженерную, но не логическую проблему. Корректность результата всё
ещё зависит от того, сохранил ли генератор смысл исходной программы. Доказанный
промежуточный файл бесполезен, если frontend неверно перевёл удаление объекта или
забыл одно поле.

## От проверки к синтезу

Последний шаг — использовать доказательство не для проверки готового алгоритма,
а для его построения. SuSLik принимает предусловие и постусловие в варианте
логики разделения и ищет последовательность команд, превращающую одну кучу в
другую. Шаги поиска одновременно являются шагами доказательства, поэтому
полученный код корректен по построению. Система синтезировала операции над
указательными списками и деревьями: [Structuring the Synthesis of
Heap-Manipulating Programs](https://arxiv.org/abs/1807.07022).

Цена снова состоит в языке спецификаций и пространстве поиска. Низкоуровневые
индуктивные предикаты многословны, а сложный алгоритм имеет слишком много
возможных реализаций.

Pika подняла спецификацию на функциональный уровень и отделила абстрактную
операцию над структурой от её конкретного представления в памяти. Её транслятор
строит задачу для SuSLik, который затем синтезирует C-код и доказательство.
Исследование и артефакт опубликованы как [Higher-Order Specifications for
Deductive Synthesis of Programs with
Pointers](https://doi.org/10.4230/LIPIcs.ECOOP.2024.45) и [сопровождающий
артефакт](https://doi.org/10.4230/DARTS.10.2.25).

Это пока не универсальный компилятор из декларации в произвольный эффективный
алгоритм. Системы хорошо работают там, где форма рекурсии и набор допустимых
преобразований достаточно ограничены.

## Что в итоге научились доказывать

Современная система может автоматически или полуавтоматически установить, что:

- разыменовывается только живая и доступная память;
- освобождение выполняется ровно при наличии необходимого права;
- операция сохраняет не затронутую ею часть кучи;
- список или дерево остаётся связным после изменения;
- обратные ссылки соответствуют прямым;
- две параллельные операции не записывают в одну ячейку без синхронизации;
- реализация соответствует абстрактному контракту структуры данных.

Но универсального решения нет. Типы удобны, когда структуру можно подчинить
простому режиму владения. Shape analysis удобен, когда важнее автоматический
поиск ошибок, чем полнота. Логика разделения выразительнее, но требует
предикатов и инвариантов. Permission-based инфраструктура облегчает создание
новых проверяющих языков, однако не устраняет необходимость корректной
трансляции. Синтез способен построить код, но только внутри достаточно узко
заданного пространства.

Главный исторический результат состоит не в победе одного подхода. Постепенно
сложилось разделение труда: типовая система быстро доказывает простые локальные
факты, логика описывает глобальные свойства памяти, SMT-решатель закрывает
формулы, а человек выбирает структуру данных и алгоритм. Именно такая комбинация
сегодня выглядит наиболее практичной для безопасной работы со сложными графами
объектов.
