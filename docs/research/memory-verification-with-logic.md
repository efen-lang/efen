# История одного `prev`: как языки учились проверять указатели

У двусвязного списка обманчиво простая идея. Каждый узел знает следующего и
предыдущего соседа:

```text
left <──> node <──> right
```

Чтобы удалить средний узел, достаточно четырёх строк:

```c
void detach(Node *node) {
    node->prev->next = node->next;
    node->next->prev = node->prev;
    free(node);
}
```

Эта функция похожа на законченный алгоритм, но почти каждое слово в ней скрывает
вопрос.

Точно ли `prev` и `next` не равны `NULL`? Действительно ли соседи указывают на
`node`? Нет ли ещё одного владельца узла? Не сохранил ли кто-нибудь указатель на
него в другом контейнере? Можно ли после `free` обратиться к нему через старый
курсор? И даже если память безопасна, кто докажет, что после операции список
остался связным?

Историю статической проверки памяти можно рассказать как последовательность
ответов на эти вопросы. Одни языки запрещали неудобные формы графов. Другие
переносили часть работы в runtime. Третьи просили программиста описать структуру
математически. А затем появились системы, способные проверять или даже строить
код по такому описанию.

## Первый ответ: написать контракт

В 1969 году Тони Хоар предложил рассуждать о программе через условия до и после
её выполнения:

```text
{P} program {Q}
```

Для удаления узла хотелось бы написать примерно следующее:

```text
requires node.prev.next == node
requires node.next.prev == node

detach(node)

ensures old(node.prev).next == old(node.next)
ensures old(node.next).prev == old(node.prev)
```

Теперь связность — уже не комментарий, а теорема, которую должна сохранить
функция. Работа Хоара [An Axiomatic Basis for Computer
Programming](https://doi.org/10.1145/363235.363259) дала основу модульной
верификации: функцию проверяют один раз, а вызывающий код использует только её
контракт.

Но с указателями обнаружилась неприятность. Допустим, существует ещё одна
ссылка:

```text
observer ──> node
```

Контракт соседей о ней ничего не говорит. Более того, если функция меняет
`left.next`, логике нужно объяснить, почему не изменилось всё остальное. Для
чисел это почти незаметно; для общей кучи перечень неизменившейся памяти быстро
становится больше самого алгоритма.

Так появилась центральная проблема: недостаточно знать значение указателя.
Нужно знать, кто ещё может указывать туда же и кто имеет право читать, изменять
или освобождать этот объект.

## Второй ответ: сделать владение частью типа

Вместо доказательства произвольной кучи можно ограничить программы так, чтобы
опасная ситуация не типизировалась. Линейные и аффинные типы говорят: ресурс
нельзя незаметно скопировать. Владение должно передаваться явно, а ссылка не
может пережить владельца.

Региональные системы применили ту же мысль к группам объектов. В Cyclone каждый
указатель был связан с регионом происхождения, а компилятор проверял, что он не
переживёт регион. Язык сохранял близкий к C контроль над представлением, но
платил региональными параметрами и эффектами: [Region-Based Memory Management
in Cyclone](https://www.cs.umd.edu/projects/cyclone/papers/cyclone-regions.pdf).

Для двусвязного списка регион даёт простой ответ на один вопрос: все узлы можно
считать живыми до смерти списка целиком. Внутренние `prev` и `next` тогда не
висят. Но немедленно вернуть один узел аллокатору уже труднее. Регион хорошо
доказывает групповую жизнь, а не индивидуальную смерть.

## Rust: память безопасна, но список всё ещё надо придумать

Rust сделал владение частью повседневной компиляции. В каждый момент допустимы
либо несколько `&T` для чтения, либо один `&mut T` для изменения. Ссылка не
должна пережить значение, из которого она получена.

Односвязный список прекрасно совпадает с этой моделью:

```rust
struct Node<T> {
    value: T,
    next: Option<Box<Node<T>>>,
}
```

Каждый `Box` единолично владеет хвостом. Но добавить `prev` типа `Box<Node<T>>`
нельзя: тогда два узла должны были бы владеть друг другом. Простая структура
превращается в цикл владения, а у цикла нет единственного корня уничтожения.

Без `unsafe` типичное решение использует сильную ссылку вперёд и слабую назад:

```rust
use std::cell::RefCell;
use std::rc::{Rc, Weak};

type Link<T> = Option<Rc<RefCell<Node<T>>>>;
type Back<T> = Option<Weak<RefCell<Node<T>>>>;

struct Node<T> {
    value: T,
    prev: Back<T>,
    next: Link<T>,
}

struct List<T> {
    head: Link<T>,
    tail: Link<T>,
}
```

`Rc` разрешает несколько владельцев, `Weak` не удерживает цель живой, а
`RefCell` переносит проверку конфликта изменяемых доступов из компилятора в
runtime. Удаление получается заметно длиннее C-версии:

```rust
impl<T> List<T> {
    fn detach(&mut self, node: &Rc<RefCell<Node<T>>>) {
        let (prev, next) = {
            let mut node = node.borrow_mut();
            let prev = node.prev.take().and_then(|p| p.upgrade());
            let next = node.next.take();
            (prev, next)
        };

        match &prev {
            Some(p) => p.borrow_mut().next = next.clone(),
            None => self.head = next.clone(),
        }

        match &next {
            Some(n) => {
                n.borrow_mut().prev = prev.as_ref().map(Rc::downgrade)
            }
            None => self.tail = prev,
        }
    }
}
```

Это важный результат, но не магия. Rust гарантирует, что безопасный код не
разыменует освобождённую память. Он не доказывает автоматически закон
`x.next.prev == x`. Если забыть обновить `prev`, программа останется безопасной
для памяти, но список станет логически неправильным.

Интрузивный список без `Rc` и `RefCell` тоже возможен, однако сырые указатели и
доказательство их инвариантов окажутся внутри `unsafe`. Безопасность внешнего API
тогда опирается на правильность этого маленького небезопасного ядра.

Non-lexical lifetimes научили borrow checker завершать заимствование после его
последнего использования, а не только в конце блока. Polonius развивает анализ
через происхождение заимствований и отношения между ними. Его альфа-режим был
включён в nightly в августе 2026 года, но он делает точнее проверку заимствований,
а не превращает типовую систему в доказатель произвольных графовых инвариантов:
[сообщение команды Rust](https://blog.rust-lang.org/2026/08/04/enabling-polonius-alpha-on-nighty/)
и [репозиторий Polonius](https://github.com/rust-lang/polonius).

Математическое основание здесь не совпадает с реализацией компилятора. RustBelt
построил машинно проверенную модель существенной части Rust и сформулировал
условия, при которых библиотека с внутренним `unsafe` действительно образует
безопасную абстракцию: [RustBelt: Securing the Foundations of the Rust
Programming Language](https://people.mpi-sws.org/~dreyer/papers/rustbelt/paper.pdf).

## Pony: разрешить цикл, но не выпускать его куда угодно

Pony выбрал другой компромисс. Время жизни объектов контролирует сборщик мусора,
поэтому `prev` и `next` могут быть обычными сильными ссылками. Типовая система
занята другим вопросом: кому разрешено видеть и изменять граф.

У каждой ссылки есть capability. `ref` даёт изменяемый доступ внутри актора,
`val` обозначает глубоко неизменяемый разделяемый граф, `iso` — изолированный
граф, который можно передать другому актору, `box` — доступ только для чтения,
а `tag` позволяет знать идентичность без чтения полей. Полная система включает
также переходную capability `trn`.

Внутри одного актора двусвязный список выглядит почти буквально:

```pony
class ref Node
  let value: U64
  var prev: (Node ref | None) = None
  var next: (Node ref | None) = None

  new ref create(value': U64) =>
    value = value'

class ref List
  fun ref detach(node: Node ref) =>
    match node.prev
    | let before: Node ref => before.next = node.next
    end

    match node.next
    | let after: Node ref => after.prev = node.prev
    end

    node.prev = None
    node.next = None
```

Цикл не нужно разрывать ради подсчёта ссылок. Но изменяемый граф с `ref` нельзя
просто передать другому актору: для безопасной передачи его изолируют или делают
неизменяемым. Эти правила описаны в [руководстве по reference
capabilities](https://tutorial.ponylang.io/reference-capabilities/reference-capabilities.html)
и статье [Reference Capabilities for Concurrency
Control](https://drops.dagstuhl.de/storage/00lipics/lipics-vol056-ecoop2016/LIPIcs.ECOOP.2016.5/LIPIcs.ECOOP.2016.5.pdf).

Pony отвечает на проблему многих указателей иначе, чем Rust: не требует
единственного владельца каждого узла, а ограничивает права всей группы алиасов.
За свободу топологии платит runtime. Pony-ORCA собирает память акторов и
отслеживает межакторные ссылки: [Ownership and Reference Counting based Garbage
Collection](https://www.ponylang.io/media/papers/OGC.pdf).

И снова безопасность памяти не равна корректности списка. Capability `ref` не
заставляет автора выполнить обе половины переподключения.

## Другие языки меняли единицу владения

Двусвязный список обнажает выбор, который обязан сделать любой безопасный язык:
запретить цикл, собрать его автоматически, проверять ссылку динамически или
владеть более крупной областью памяти.

Mezzo попробовал считать основным объектом типизации permission. Разрешение
одновременно сообщало форму значения и право доступа к нему. Неизменяемые
permissions можно было дублировать, изменяемые обычно были аффинными. Для графов,
где контейнер должен принять множество узлов, появился механизм
`adopt`/`abandon`. Он расширял выразительность, но добавлял динамическую проверку
и сложные операции упаковки: [Programming with Permissions in
Mezzo](https://gallium.inria.fr/~fpottier/publis/pottier-protzenko-mezzo.pdf)
и честная ретроспектива [A Few Lessons from the Mezzo
Project](https://cambium.inria.fr/~fpottier/publis/fpottier-protzenko-lessons-mezzo.pdf).

Project Verona исследует владение целым регионом. Внутри региона может жить
свободный граф с `prev`, `next` и дополнительными указателями; граница региона
контролирует время жизни и конкурентный доступ. Это снимает пообъектную
линейность, но делает освобождение отдельного узла внутренней задачей региона.
Проект остаётся исследовательским: [описание Microsoft
Research](https://www.microsoft.com/en-us/research/project/project-verona/).

Vale исследует поколенческие ссылки. Ячейка хранит текущее поколение, ссылка —
запомненное. При освобождении поколение меняется:

```text
dereference(pointer):
    assert pointer.generation == pointer.slot.generation
    return pointer.slot.value

free(slot):
    slot.generation += 1
```

Старый `prev` больше не откроет новый объект, случайно занявший тот же адрес.
Общие графы становятся естественными, но неустранённое разыменование платит
runtime-проверкой и метаданными. Сам проект находится в alpha, а часть
оптимизаций пока заявлена как будущая: [описание generational
references](https://vale.dev/memory-safe).

Austral, напротив, доводит линейность до простой строгой модели: линейное
значение должно быть использовано ровно один раз. Это хорошо предотвращает
double-free и use-after-free, но двусвязный граф требует вынести разделяемость в
отдельную абстракцию. См. [спецификацию
Austral](https://austral-lang.org/spec/spec.html).

Hylo пытается уменьшить саму роль ссылочной семантики. Его `subscript` не
возвращает долгоживущую ссылку, а временно проецирует часть значения с правом
чтения или изменения. Для локальной мутации это похоже на заимствование без
явных lifetime-параметров. Общий объектный граф при этом намеренно не является
центральной моделью языка: [введение в Hylo](https://hylo-lang.org/introduction/).

Все эти языки делают ошибки памяти менее выразимыми, но ни один типовой
квалификатор сам по себе не доказывает, что `next` и `prev` согласованы. Для
этого требуется описание формы структуры.

## Третий ответ: анализировать форму кучи

В конце 1990-х появился shape analysis. Вместо требования выбрать одного
владельца анализатор приближённо вычисляет возможную форму памяти: может ли путь
быть циклическим, способны ли две переменные указывать в один узел, бывает ли
поле `NULL`.

В TVLA Сагива, Репса и Вильгельма множество конкретных куч представляется одной
трёхзначной логической структурой. Предикат получает значение «истина», «ложь»
или «неизвестно». Последний результат принципиален: если анализатор не может
доказать, что `node.prev.next == node` во всех состояниях, он не делает вид, что
условие выполнено. Исследование описано в [Parametric Shape Analysis via
3-Valued Logic](https://research.cs.wisc.edu/techreports/viewreport.php?report=1383).

Такой анализ может работать почти без пользовательских контрактов. Но общий
граф быстро теряет точность: несколько разных узлов сливаются в один абстрактный,
и ответы превращаются в «неизвестно». Чем больше отношений хочется помнить, тем
дороже анализ.

## Четвёртый ответ: разделить кучу логически

Логика разделения решила старую проблему контрактов Хоара: как говорить о
маленьком изменяемом фрагменте, не перечисляя всю остальную память.

Формула:

```text
x ↦ Node(value, next) * list(next)
```

говорит, что ячейка `x` и память хвоста списка существуют одновременно и не
пересекаются. Оператор `*` — разделяющая конъюнкция. Благодаря frame rule
доказательство локальной операции автоматически переносится на кучу с
дополнительным независимым фрагментом.

Двусвязный список определяется рекурсивно с ожидаемым предшественником:

```text
dll(x, previous) =
    x = null ∧ emp
  ∨ exists next:
        x ↦ Node(previous, next)
      * dll(next, x)
```

Теперь `prev` — не просто поле. Его правильное значение входит в смысл
`dll`. Удаление среднего узла можно описать как преобразование:

```text
requires
    left  ↦ Node(lp, node)
  * node  ↦ Node(left, right)
  * right ↦ Node(node, rn)

ensures
    left  ↦ Node(lp, right)
  * right ↦ Node(left, rn)
```

Узел `node` отсутствует в постусловии: право на него потреблено. Обе обратные
ссылки названы явно, поэтому забытая запись не пройдёт доказательство. Основные
идеи и примеры собраны в работе Джона Рейнольдса [Separation Logic: A Logic for
Shared Mutable Data Structures](https://www.cs.cmu.edu/~jcr/seplogic.pdf).

Цена выразительности видна сразу. Программист пишет уже не только список, но и
его математическую модель. Для общего графа индуктивный предикат сложнее, потому
что подграфы могут пересекаться, а `*` как раз утверждает непересечение.

## Когда доказательство поручили отдельным программам

Ранние доказательства были во многом ручными. Затем появились инструменты,
которые символически исполняли программу и автоматически закрывали стандартные
шаги.

Smallfoot ограничил язык предикатов формы, зато смог автоматически проверять
модульные операции над списками. Пользователь описывал `list` или `dll`, а
инструмент строил verification conditions и применял frame rule: [Smallfoot:
Modular Automatic Assertion Checking with Separation
Logic](https://jberdine.github.io/pub/2005_fmco.pdf).

VeriFast пошёл по полуавтоматическому пути для C, Java и Rust. Автор задаёт
предусловия, постусловия, рекурсивные предикаты и инварианты циклов. Инструмент
проверяет каждую функцию отдельно, используя контракт вызываемой функции вместо
её тела. Двусвязный список доказуем, но аннотации становятся полноценной второй
программой рядом с первой: [публикации и примеры
VeriFast](https://people.cs.kuleuven.be/~bart.jacobs/verifast/).

Bi-abduction попыталась часть этих контрактов вывести. Если для разыменования
`node.prev` не хватает гипотезы, анализ ищет недостающее предусловие; одновременно
он вычисляет frame — память, не затронутую функцией. Это позволило строить
межпроцедурный анализ снизу вверх и масштабировать идеи separation logic до
крупных кодовых баз. Подход лёг в основу Infer: [Compositional Shape Analysis by
Means of Bi-Abduction](https://www.cs.ox.ac.uk/people/hongseok.yang/paper/popl09.pdf).

Infer и полный верификатор решают разные задачи. Анализатор ищет вероятные ошибки
и может потерять точность. Верификатор требует закрыть каждое обязательство и
отказывается принимать функцию, пока контракт не доказан.

## Viper: не новый язык приложения, а общий язык доказательства

Создателю нового проверяющего frontend не хочется заново писать SMT-интеграцию,
символическое исполнение и логику разрешений. Viper предлагает промежуточный
язык, где право доступа к полю является логическим ресурсом:

```text
acc(object.field)
```

Упрощённая проверка нашего `detach` выглядит так:

```viper
method detach(left: Ref, node: Ref, right: Ref)
  requires acc(left.next) && acc(node.prev) && acc(node.next)
  requires acc(right.prev) && acc(node.value)
  requires left.next == node && node.prev == left
  requires node.next == right && right.prev == node

  ensures acc(left.next) && acc(right.prev)
  ensures left.next == right && right.prev == left
{
  left.next := right
  right.prev := left

  exhale acc(node.prev) && acc(node.next) && acc(node.value)
}
```

Если забыть `right.prev := left`, постусловие не доказывается. Если затем
прочитать `node.value`, проверка не найдёт разрешения: операция `exhale` его
потребила. Идентичность `node` при этом ещё можно сравнивать — запрещено именно
разыменование без права.

Viper имеет backend символического исполнения Silicon и backend генерации
verification conditions Carbon. Frontend переводит конструкции исходного языка
в Viper, запускает один из решателей и возвращает ошибку в исходные координаты.
Архитектура описана в [Viper: A Verification Infrastructure for
Permission-Based
Reasoning](https://pmpub.inf.ethz.ch/publications/MuellerSchwerhoffSummers16.pdf).

Это сильное инженерное решение, но у него есть собственная доверенная граница.
Viper доказывает сгенерированную программу. Если frontend забыл перевести одно
поле или неверно смоделировал освобождение, доказана будет не та программа,
которую написал человек.

## Последний поворот: можно ли построить `detach` из доказательства

До сих пор человек писал алгоритм, а машина его проверяла. SuSLik поменял роли:
на вход подаются предусловие и постусловие в варианте separation logic, а система
ищет программу, преобразующую одну кучу в другую.

Для локального фрагмента двусвязного списка задача выглядит почти как наш
контракт:

```text
before: left <──> node <──> right
after:  left <────────────> right
```

Правила Synthetic Separation Logic одновременно являются правилами построения
кода. Найденная последовательность записей — это терм доказательства, поэтому
она корректна по построению. Подход реализован в SuSLik и описан в [Structuring
the Synthesis of Heap-Manipulating
Programs](https://arxiv.org/abs/1807.07022).

Но низкоуровневые предикаты сами стали новым языком программирования. Их нужно
писать, дублировать для разных представлений и направлять дополнительными
подсказками, когда пространство поиска велико.

Pika подняла спецификацию на функциональный уровень. Автор описывает абстрактное
преобразование структуры отдельно от размещения в памяти; транслятор строит
задачу SuSLik, а тот синтезирует C-код и доказательство. Исследование опубликовано
как [Higher-Order Specifications for Deductive Synthesis of Programs with
Pointers](https://doi.org/10.4230/LIPIcs.ECOOP.2024.45).

Это впечатляющий результат, но пока не универсальный компилятор намерений.
Синтез хорошо работает, когда форма рекурсии, представление данных и множество
допустимых команд достаточно ограничены. По одной фразе «удали узел из любого
графа» эффективный алгоритм не возникает: системе всё равно нужно знать, как
найти входящие рёбра и какой ценой их разрешено хранить.

## Где закончилась эта история

Она не закончилась победой одного языка.

Rust встроил быстрое консервативное доказательство времени жизни в обычную
компиляцию. Pony разрешил свободнее строить циклы внутри изолированных графов и
передал смерть объектов GC. Регионы укрупнили единицу владения. Поколенческие
ссылки обменяли часть статического доказательства на динамическую проверку.
Shape analysis научился угадывать форму кучи, separation logic — точно её
описывать, Viper — служить общим механизмом доказательства, а SuSLik и Pika —
строить код из некоторых доказательств.

Двусвязный список остался хорошим тестом именно потому, что он слишком мал для
оправданий. В нём видны сразу три разные гарантии:

1. узел ещё жив;
2. у операции есть право менять его поля;
3. `next` и `prev` согласованы.

Сборщик мусора решает первую задачу, но не третью. Borrow checker решает первую
и часть второй, но не выводит произвольный инвариант структуры. Логический
верификатор способен доказать все три, но требует модели и иногда аннотаций.
Синтезатор может сам написать переподключение, но лишь внутри заранее описанного
мира.

Поэтому наиболее практичное направление сегодня — не искать одно магическое
правило указателей, а соединять уровни. Типовая система закрывает частые
локальные ошибки. Runtime страхует случаи, где статическое ограничение слишком
жёстко. Логический backend проверяет редкие глобальные инварианты. А человек
по-прежнему выбирает структуру данных и объясняет, где находятся все ссылки,
которые операция обязана изменить.
