# Система доказательств Bend и её применимость к Efen

Дата: 2026-09-18. Основание: сайт bend-lang.com, репозиторий `bendlang/bend`
(`README.md`, `guide/GUIDE.md`, исходник статьи BendTT в
`bend2/docs/BendTT/main.typ`, заголовок `bend2/bend.lean`, демо с
`LAWS.bend`/`PROOF.bend`), документы Efen `types/refinement-types.md`,
`types/ownership.md`, `context-and-effects.md`,
`memory/viper-verification-backend.md` и решение Q15 из
`dev/language-design-questions.md`. Чекер Bend не запускался; утверждения о
нём — по коду и статье.

Это записка исследования, а не нормативный документ. Принятое решение одно:
доказательственное подмножество не покрывает весь язык. Остальное — материал
для будущих решений.

## Вывод

Систему доказательств Bend целиком в Efen перенести нельзя: её согласованность
держится на том, что весь исполняемый код чист, аффинен и завершается, а Efen —
язык с мутацией, исключениями, эффектами и `managed`-слотами. Переносимы три
части устройства: рабочий цикл «закон → доказательство → ворота сборки», стена
между стёртым кодом спецификаций и живым кодом программы, и синтаксическая
проверка спуска для тотального подмножества. Подмножество, на которое эти
части ложатся, из Efen извлекается там, где владение единственное или выражено
через `layout`, а эффекты выведены.

## Устройство системы доказательств Bend

Система доказательств Bend — это его тайп-чекер `bend2/bend.ts` (3,7 тыс.
строк TypeScript), а не отдельный прувер. Теория, которую он реализует,
называется BendTT и держится на пяти решениях.

1. **Одна вселенная, `Type : Type`, без проверки позитивности.** Известные
   парадоксы — Жирара, Хёркенса, Карри — копируют функцию, поэтому
   согласованность куплена аффинностью: переменная используется не более
   одного раза, если вид её типа (`Data`) не разрешает большего. Функция
   никогда не `Data`; тип данных зарабатывает `Data` на каждом конструкторе,
   если ни одно поле не хранит аффинного значения.
2. **Стена «живое / мёртвое».** Типы, стёртые аргументы, уравнения и мотивы
   переписывания проверяются на нулевом спросе: они могут расходиться,
   населять `Empty` и стираются перед рантаймом. Живой код обязан завершаться
   и не имеет замкнутого терма типа `Empty`. Утверждать можно что угодно;
   ограничения касаются только того, что выполняется.
3. **Завершение — один синтаксический тест спуска.** Аргументы рекурсивного
   вызова сравниваются с колонками образца слева направо; первый
   изменившийся обязан быть строгим подтермом. Взаимная рекурсия и `match` на
   вычисленном значении запрещены.
4. **Доказательство — обычный `def`.** `match` и есть элиминатор,
   рекурсивный вызов — гипотеза индукции, `{==}` — рефлексивность по
   нормализации обеих сторон, `%e : P` — аксиома J с явно выписанным
   мотивом. Тактик, унификации и вывода типов нет; отсюда скорость чекера и
   многословность доказательств.
5. **Цикл работы.** `LAWS.bend` пишет человек, `PROOF.bend` и код — ИИ,
   `bend PROOF.bend` — ворота: сборка красная, пока хоть один закон открыт.

Цена по демо из репозитория: игра на 194 строки, доказательство двух законов —
484 строки; в Pong лемма о четырёх флагах — перебор шестнадцати случаев
вручную.

## Математический статус доказательств

Доказательство внутри Bend — терм заданного типа, проверенный машиной по
правилам исчисления; в этом смысле оно равноценно доказательству в Lean или
Agda. Исчисление механизировано в Lean 4: `bend2/bend.lean`, 20 981 строка,
без `sorry` и без объявлений `axiom`; доказаны конфлюэнтность, сохранение типа
при слабой редукции, прогресс, слабая нормализация и согласованность живого
фрагмента. Согласованность относительна: она верна при условии согласованности
самого Lean, как и у остальных пруверов.

Lean при этом в Bend не используется ни при компиляции, ни при проверке:
`bend.lean` — доказательство о теории, сделанное авторами один раз, а не часть
чекера. Отсюда четыре оговорки, которые авторы называют сами.

1. Теоремы — про исчисление, не про чекер. Заголовок `bend.lean` говорит, что
   модель не полностью совпадает с `bend.ts` и баги реализации могут дать
   несогласованность; README добавляет, что компилятор на 99 % написан ИИ и
   полного аудита не прошёл.
2. Стёртая часть ничего не гарантирует. Закон, опирающийся на `F32`,
   недоказуем, потому что `F32.add` — аксиома без тела; закон, опирающийся на
   эффект из C или JS, доверяет чужому коду.
3. `@unsafe` и `?TODO` выводят книгу из-под теорем; чекер печатает это в
   вердикте, и гарантия действует только для чистого вердикта.
4. Сравнение типов — полурешающая процедура: на мёртвом коде оно может
   зависнуть, и зависание означает «неизвестно», а не «принято».

Доказательство покрывает соответствие кода закону, а не соответствие закона
намерению: закон «выиграть невозможно» — это `is_won(replay(start, moves)) ==
False`, и при неверной `is_won` он доказуем и бесполезен. Для Efen это та же
граница, что у Viper: спецификация остаётся в доверенной базе.

## Соответствия в Efen

- **Аффинность.** `own` в `types/ownership.md` — передача права уничтожить,
  после которой прежнее имя владеть не может; это бендовский счётчик «не
  более одного раза». Деление Bend на `Type` (ресурс с одним владельцем) и
  `Data` (копируемое) совпадает с делением Efen на владеемый ресурс и тип с
  копирующей стратегией.
- **Предикаты.** По Q15 `refine()` явный, неявной runtime-проверки нет, а
  предикаты — материал для системы доказательств. Закон Bend — тот же
  предикат, вынесенный из типа в отдельную декларацию.
- **Compile-time-слой.** Метафункции и обход HIR — место для стёртого кода:
  законы и доказательства живут там и в бинарь не попадают.
- **Verification boundary.** Генератор Efen → Viper уже спроектирован для
  памяти, населений и `layout`.

## Препятствия переносу целиком

- Согласованность BendTT требует, чтобы весь живой код был чистым, аффинным и
  завершающимся; стену можно провести только вокруг подмножества.
- Доказательство в Bend — нормализация самой программы на открытых термах,
  где заклинивший `match` сворачивается обратно к вызову. Compile-time-
  интерпретатор Efen считает на конкретных значениях; символьное вычисление —
  новая машина.
- Индукция в Bend идёт по `Nat` с образцом `1n+p`. Машинные `Int`/`UInt64`
  структуры не имеют, поэтому законы об арифметике — территория SMT/Viper.
  Bend этого не решает: его `U32` вычислим только на замкнутых термах.
- Замыкания в Bend аффинны — вызов не более одного раза. Для общего кода Efen
  это неприемлемо и допустимо только внутри доказательственного диалекта.

## Сведение кода Efen к чистой аффинной форме

Сведение делается ради проверки, а не исполнения; так поступают Dafny, Prusti
и генератор Efen → Viper. Чистота достигается, если известна сигнатура
эффектов, и именно её Efen уже выводит: `in`, `throws` и права на параметры.

| В Efen | В чистой форме |
|---|---|
| `in Context`, `%db` | запись контекста — ещё один параметр |
| `throws E` | результат `Result<T, E>`, `try/catch` — `match` |
| `effect` | параметр-словарь функций либо значение-описание команды, как `IO` в Bend |
| `var` и присваивание | SSA: новое имя на каждое присваивание |
| `for`/`while` | рекурсия; условие выхода — образец, а не вычисленное значение |
| `flow`, генераторы | конечный автомат: состояние и функция шага |
| классы, виртуальный вызов | данные и таблица функций |

Аффинность переводится по выведенным правам параметра:

- `own` аффинен и переводится как есть;
- `&read T` — копия, если `T` копируемый, иначе «одолжи и верни»: функция
  возвращает значение рядом с результатом, как `a[5]` в Bend отдаёт массив и
  элемент;
- `&T`, `&out T` — «взять, изменить, вернуть»: значение протягивается через
  вызов как параметр и как результат;
- мутация через ссылки на кучу переводится там, где `layout` и населения уже
  свели указатель к паре (хранилище, индекс): хранилище — одно владеемое
  значение, ссылка — индекс, то есть данные. Код над сырыми указателями не
  переводится.

Не сводятся три вещи:

1. `shared` и одновременный доступ из потоков — разделяемая запись
   противоречит единственному владельцу по определению; Bend пускает
   разделяемые массивы с атомиками только под `@unsafe`.
2. `managed`-слоты (ARC, GC) с циклами — граф с общими узлами не аффинен,
   пока не выражен как `layout` и индексы.
3. Циклы без верхней оценки — сервер, событийный цикл. Выход тот же, что в
   Bend: счётчик топлива как явный аргумент либо метка вне гарантий.

Две оговорки к переводу. Доказательство получается о переведённой программе,
поэтому переводчику нужна обратная карта, иначе ошибка прувера приходит в
терминах SSA-имён и протянутых состояний. Права стоит выводить по полям, а не
по объекту: параметр с `write` на весь объект после перевода тянет объект
целиком через каждый вызов.

## Как применить: три слоя

1. **Декларация `law` рядом с `test`.** Файл законов пишет автор, файл
   доказательств может писать ИИ. Compiler публикует статус доказательства, но
   `not proven` не является ни ошибкой, ни предупреждением и сам по себе не
   останавливает обычную сборку. Обязательство проверяется одним из трёх
   способов по форме закона:
   замкнутые равенства — вычислением на compile-time, которое уже есть;
   индуктивные законы о чистых рекурсивных функциях над `variant`/`enum` —
   Bend-подобным чекером над HIR; арифметика, границы, инварианты циклов и
   памяти — Viper/SMT.
2. **Доказательственный диалект.** Функции без эффектов и `throws`, без
   `managed`, с рекурсией вместо циклов, `match` только по параметру и
   проверкой спуска по образцу BendTT. `isolated` по глоссарию не означает
   `pure`; пригодность конкретной функции для доказательства выводит compiler
   из её тела, сводки и зависимостей. Внутри диалекта — пропозициональное
   равенство, `{==}` и переписывание с мотивом. Типы,
   параметризованные compile-time значениями, уже предоставляет обычная
   generic-модель; отдельная система типов для этого не требуется.
3. **Ядро чекера.** Проверяющая часть `bend.ts` без вывода типов и унификации
   даёт оценку стоимости собственного чекера над Amber HIR; переносить стоит
   спецификацию из части I `bend.lean`, а не код `bend.ts`. Механизация
   переносу не подлежит.

Развилка: два прувера (Viper и термовый чекер) — две доверенные базы и два
языка ошибок. Дешёвый путь — начать со слоя 1 только с Viper и compile-time-
вычислением, а Bend-подобный чекер добавить вместе с диалектом.

## Принятое решение

Доказательственное подмножество не покрывает весь язык (2026-09-18). Граница:
владение единственное или выражено через `layout`, эффекты выведены; снаружи
остаются разделяемая запись, `managed`-графы без `layout` и циклы без верхней
оценки.

Отдельная source-метка тотальности не вводится. Когда функцию используют в
доказательстве, compiler автоматически определяет применимость выбранного
proof-механизма. Если доказательство не найдено, он публикует отдельный статус
`not proven`/`unknown`; это не diagnostic severity, обычная компиляция
продолжается. Недоказанный результат нельзя использовать как установленный факт
в другом доказательстве. Проект или CI может отдельно потребовать `proven` для
выбранных законов, но это политика сборки, а не семантика языка.

Не разобраны: перевод `defer`/`disposable` (явное возвращение ресурса на
каждом пути, включая путь исключения), замыкания, захватывающие `var`,
расхождения модели и чекера по пунктам a–e заголовка `bend.lean`,
интенсиональность равенства.
