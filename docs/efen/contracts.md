# Контракты

[Документация](README.md) · [Словарь](glossary.md) · [Interfaces](interfaces.md) · [Стратегии](strategies.md)

> Контакт -- высшая языковая абстракция времени компиляции, которая описывает правила формирования других абстракций.

Контракт устанавливает какие свойства и методы должны быть определены в абстракции.

Примеры контрактов:
```efen
contract MyContract {
    var myProperty: Int { get set }
    fn myMethod
}
```

## ⚠️ Contract vs Interface: Ключевое различие

**Это фундаментальная концепция Efen, которую необходимо понимать:**

### Contract — compile-time абстракция
- ✅ Существует **только** во время компиляции
- ✅ После компиляции **полностью исчезает** из бинарника
- ✅ Используется компилятором для проверки корректности кода
- ✅ Сам по себе не требует runtime-дескриптора или VTBL
- ✅ Позволяет статическую диспетчеризацию, когда конкретная реализация известна

Contract не является типом значения. Его нельзя использовать как тип свойства
или локальной переменной. Generic-функция сначала объявляет конкретный тип через
`generic T: Contract`, а затем использует `T` как тип runtime-параметра.
`opaque Contract` в позиции результата ограничивает скрытый конкретный тип.
Неизвестное конкретное значение с runtime-полиморфизмом выражается интерфейсом.
`opaque Contract` остаётся статической формой и не создаёт runtime-interface.

### Interface — runtime абстракция
- ✅ Существует в **runtime** как **VTBL** (виртуальная таблица)
- ✅ Присутствует в скомпилированном бинарнике
- ✅ Позволяет полиморфизм во время выполнения
- ✅ Имеет runtime overhead (косвенный вызов через VTBL)
- ✅ Динамическая диспетчеризация (dynamic dispatch)

### Практический пример

```efen
// CONTRACT: только compile-time
contract Drawable {
    fn draw
}

// INTERFACE: runtime VTBL
interface Shape {
    fn area -> Float
}

// Класс соответствует контракту и реализует интерфейс
class Circle {
    conforms Drawable      // Compile-time проверка
    implements Shape       // Runtime VTBL

    var radius: Float

    fn draw {
        // Реализация требования контракта
        print("Рисую круг")
    }

    fn area -> Float {
        // Реализация метода интерфейса
        return 3.14 * radius * radius
    }
}
```

### Что происходит после компиляции?

```efen
// Compile-time: компилятор проверяет что draw() есть
fn renderStatic<T: Drawable>(object: T) {
    object.draw()  // STATIC DISPATCH - прямой вызов
}

// Runtime: используется VTBL для полиморфизма
fn calculateArea(shape: Shape) -> Float {
    return shape.area()  // DYNAMIC DISPATCH - вызов через VTBL
}
```

**После компиляции:**
- `Drawable` контракт **исчез** — вызов `draw()` скомпилирован напрямую
- `Shape` интерфейс **присутствует** как VTBL в бинарнике
- `calculateArea` может принимать **любой** объект реализующий Shape

Исчезновение contract не означает, что любой использующий его код бесплатен.
Например, скрытый structural union нескольких реализаций выполняет switch по
runtime-тегу.
Эта стоимость принадлежит выбранному представлению и dispatch, а не самому
contract; обычная известная реализация по-прежнему допускает прямой вызов.

### Когда использовать что?

**Используйте Contract когда:**
- ✅ Нужны generic constraints (ограничения на типы)
- ✅ Не нужен обязательный runtime-interface или VTBL
- ✅ Тип известен во время компиляции
- ✅ Хотите максимальную оптимизацию компилятора

**Используйте Interface когда:**
- ✅ Нужен runtime полиморфизм
- ✅ Тип неизвестен во время компиляции
- ✅ Хотите binary compatibility (совместимость бинарников)
- ✅ Реализуете plugin system или динамическую загрузку

### Комбинация Contract + Interface

Можно использовать оба одновременно для максимальной гибкости:

```efen
// Контракт для compile-time проверок
contract Serializable {
    fn serialize -> String
}

// Интерфейс для runtime полиморфизма
interface Storable {
    fn save(path: String)
}

class Document {
    conforms Serializable  // Compile-time гарантия
    implements Storable    // Runtime возможность

    fn serialize -> String {
        return "..."
    }

    fn save(path: String) {
        let data = serialize()  // Статический вызов
        writeToFile(path, data)
    }
}

// Generic с контрактом - нулевой overhead
fn sendOver<T: Serializable>(object: T) {
    let data = object.serialize()  // STATIC - оптимально
    network.send(data)
}

// Полиморфный с интерфейсом - runtime гибкость
fn saveAll(objects: [Storable]) {
    for obj in objects {
        obj.save("/tmp/file")  // DYNAMIC - через VTBL
    }
}
```

См. также: [interfaces.md](interfaces.md) для подробного описания интерфейсов.

## Контракты копирования и перемещения

`Movable`, `Copyable` и `ImplicitlyCopyable` являются независимыми
compile-time контрактами возможностей значения, кроме одной явной связи:
`ImplicitlyCopyable` наследует `Copyable`.

```efen
contract Movable {
}

contract Copyable {
    fn copy -> Self
}
```

Уточнение одного контракта другим пишется через `:`:

```efen
contract ImplicitlyCopyable : Copyable {
}
```

`ImplicitlyCopyable` уточняет `Copyable`: тип, соответствующий первому,
обязан соответствовать и второму.

`Movable` разрешает передать существующее значение через `take`. `Copyable`
разрешает создать независимое значение оператором `copy`. Ни один из этих
контрактов не подразумевает другой: перемещаемый ресурс может запрещать копию,
а закреплённое значение может разрешать построение копии, не разрешая перенос
существующего экземпляра.

`ImplicitlyDestroyable` — встроенный пустой контракт, как `Movable`: компилятор может уничтожить значение такого типа
в точке, которую программа не называет (конец области, `removeAll`, перезапись). Соответствие вычисляется, а не
пишется: ему не соответствуют класс, у которого все роли деструктора `explicit`, и всё, что содержит значение такого
класса. Что тогда обязан сделать код — [Disposable](disposable.md#implicitlydestroyable).

### Оператор `copy`

Копия записывается префиксным оператором `copy x`, как перенос — `take x`. Оператор
вызывает метод `copy()` контракта `Copyable` типа `x`; сам метод объявляет и
реализует тип, а вызывается он только оператором.
Три способа отдать значение читаются одинаково, действие стоит первым словом:

```efen
send(take message)     // отдаёт владение
send(copy message)     // отдаёт независимую копию
send(message)          // одалживает
```

Копия стоит памяти и времени, поэтому она видна в начале выражения, а не в конце
цепочки. `copy x` для типа без `Copyable` — ошибка компиляции. Оператор связывает
слабее `.`: `copy a.b` копирует `a.b`.

`copy` — глубокая копия: у результата свои экземпляры всех данных в куче, которыми владеет
источник, поэтому `copy` строки, `indirect`-variant или класса с одним владельцем выделяет память и может бросить
`AllocationError`. Копия, которая провалилась на середине, разрушает уже построенное, как любой конструктор. `copy` значения `immutable T` даёт изменяемое `own T` ([неизменяемость](immutability.md#точки-заморозки)).

### Оператор `clone`

`clone x` копирует только верхний уровень значения: данные в куче остаются общими у источника и копии. Без счётчика ссылок общий блок освободили бы дважды, поэтому `clone`
допустим у типа со счётчиком ссылок, где он увеличивает счётчик, и у типа, чей layout содержит код с
доказательствами владения общими данными. В остальных случаях `clone x` — ошибка компиляции.

```efen
let tree2 = copy tree      // своё дерево: каждый блок выделен заново
let shared = clone handle  // тот же объект, счётчик ссылок + 1
let wrong = clone tree     // ошибка: у `tree` нет счётчика ссылок
```

Тип разрешает `clone` контрактом `lang::Cloneable` с функцией `fn clone -> Self`, как `copy` разрешает
`lang::Copyable`. Класс со строкой `conforms ArcClass` получает его от аспекта подсчёта ссылок
([поля, которые требует контракт](#поля-которые-требует-контракт)); тип, чей layout доказывает общее владение,
реализует его сам;
generic-код пишет `T: Cloneable`. Прямой вызов `x.clone()` получает ту же диагностику, что `x.copy()`: пишется
`clone x`.

Префиксные операторы связывают сильнее `as`, поэтому `copy a as B` — это
`(copy a) as B`.

`copy` — контекстное слово, как `take` и `capture`. Оператором оно является, только
когда за ним через пробел идёт начало операнда: имя, литерал, `(`, `[`, `%`, `take`
или `copy`. Знаки `+ - ! ~ ++ --` операнд не начинают: `copy + 1`, `copy - n` и
`copy !flag` читаются как выражения над переменной `copy`. После `.` и перед `=`,
`:`, `.` или `(` это обычное имя, поэтому `let copy = twin`, `copy.second`, функция
`copy(from:to:)` и метод `fn copy -> Self` остаются допустимыми, как и метод
`numbers.take(3)`. Прямой вызов `x.copy()` метода `Copyable` получает диагностику
стиля с исправлением на `copy x`; другие члены с именем `copy` не затрагиваются. Как
значение функции копия пишется замыканием: `items.map((x) => copy x)`.

`ImplicitlyCopyable` говорит о передаче параметров: значение такого типа выгодно передавать в функцию копией, а
не по ссылке, как `Int` в регистре. Компилятор по нему решает, копировать ли аргумент. Он же
решает, что делает `let x = y`: значение типа `ImplicitlyCopyable` `let` копирует, значение другого типа получает
второе имя ([связывание существующего значения](types/ownership.md#связывание-существующего-значения)).

```efen
fn area(p: Point) -> Int { … }
area(point)          // Point — ImplicitlyCopyable: передаётся копией
evaluate(expression) // indirect variant: передаётся по ссылке
```

Копирование `ImplicitlyCopyable` не меняет исходное значение, не производит
наблюдаемых изменений состояния или ввода-вывода и не выделяет память: тип, копия которого выделяет память, не
бывает `ImplicitlyCopyable`, передавать его копией невыгодно. Изменение скрытого счётчика
ссылок допустимо. Явная копия такого типа пишется, как у любого `Copyable`, `copy x`.

Стоимость копирования остаётся ответственностью автора типа. Generic-код,
который пишет `copy x` явно, требует `Copyable`, а не
`ImplicitlyCopyable`.

### `ThreadBound`

`ThreadBound` — встроенный пустой контракт, как `Movable`: значение такого типа привязано к потоку. По умолчанию тип
свободен. Строку `conforms ThreadBound` пишет тип, который привязан к потоку сам по себе; любой тип может её написать.
Тип, у которого поле, элемент, захват замыкания или поле `layout` имеет тип `ThreadBound`, соответствует ему без
строки: соответствие вычисляется, как у `ImplicitlyDestroyable`. Значение `ThreadBound` не попадает в многопоточную
корутину, в тело `offload`, в поле `shared` и в объект `shared layout`; обобщённый код, который отправляет туда
значение параметра типа, проверяется при инстанциации
([общая память](shared.md#привязка-к-потоку-threadbound)).

```efen
contract ThreadBound {
}

@abi(c) class sqlite3 {
    conforms ThreadBound          // соединение sqlite в режиме NOMUTEX
    …
}
```

## Доступ метода к self

Метод контракта пишет, меняет ли он `self`, тем же правом, что и параметр.
`own fn` забирает `self`: владение переходит к методу, как аргумент параметра
`own`, и после вызова переменной-получателя больше нет. Получателя отдают явно,
формой `(take x).m()`, как у замыкания `(take task)()`; `take x.m()` забирает
результат вызова, а не `x`. `mut fn` может менять
`self` целиком, включая структуру: добавить элемент, убрать его, записать `self`
заново. `edit fn` не перемещает и не уничтожает существующие слоты `self`: он
меняет значения в них и может создать новые слоты, как `append` связного списка.
`read fn` только читает `self`. Метод без
пометки тоже только читает: пометка `read` записывает умолчание явно, как у
параметров.

```efen
contract Stack<T> {
    mut fn push(item: T)
    mut fn pop -> T?
    fn peek -> T?          // то же, что read fn peek -> T?
    own fn drain -> [T]    // забирает стек, после вызова его нет
}

let items = (take stack).drain()   // забор пишут явно
let items = stack.drain()          // ошибка: own fn требует take у получателя

contract Cursors<T> {
    edit fn next(cursor: mut Cursor) -> edit T?
}
```

`edit fn` нужен методу, который отдаёт место `edit` в `self`
([место в результате функции](types/ownership.md#место-в-результате-функции)):
вызов `mut fn` может перестроить `self`, поэтому место из прошлого вызова
умирает, а после вызова `edit fn` оно живёт. Два курсора через контракт
работают только так:

```efen
fn pair(items: edit Cursors<Item>, a: mut Cursor, b: mut Cursor) {
    if let x = items.next(cursor: a) {
        if let y = items.next(cursor: b) {   // x жив: next не меняет структуру items
            x.count = y.count
        }
    }
}
```

Метод `edit fn` вызывается у
получателя `edit` и `mut`, но не у получателя без права записи, так же, как параметр `edit` принимает только
место с правом записи.
Так проверяется вызов через контракт или интерфейс, где видна одна пометка.
Прямой вызов метода класса проверяется по его телу, как вызов `mut fn`: `edit fn`,
который ничего не меняет, можно вызвать и у получателя без права записи. Вызов
`mut fn` через интерфейс может перестроить `self`, поэтому получатель `edit` его
не принимает.

Если тело `mut fn` не перемещает и не уничтожает ни одного существующего слота
`self` и не делает перехода состояния, компилятор выдаёт предупреждение
`W.access.edit-suffices` и предлагает пометку `edit fn`. Предупреждения нет у `open fn` и `override`, у реализации метода контракта или interface и у функции, которую кладут в тип функции с параметром `mut`.:

```efen
class Chain {
    var nodes: own LinkedList<Int>

    mut fn add(value: Int) {      // warning[W.access.edit-suffices]: mark it `edit fn`
        self.nodes.append(value)  // новый узел; старые узлы не двигаются
    }
}
```

Компилятор не смотрит в реализации, когда проверяет вызов через контракт:
вызывающий читает только пометку. Реализация проверяется по пометке там, где
она написана. Тело `peek`, которое меняет поле `self`, — ошибка в этом теле, а
не у вызывающего; так же ошибка — тело `edit fn`, которое перемещает или
уничтожает существующие слоты `self`. Реализация может быть уже пометки, но не шире: метод `mut fn`
реализуют `mut fn`, `edit fn` или `read fn`, метод `edit fn` — `edit fn` или
`read fn`. Метод `own fn` реализует только `own fn`: вызывающий уже отдал
объект, и реализация обязана его уничтожить или передать дальше. Пометка бывает
параметром типа `Access`, и тогда одно объявление покрывает несколько прав
([право доступа как параметр](generics.md#право-доступа-как-параметр)).

Контракт остаётся такой границей и при сборке всей программы: его реализуют
типы, которые автор контракта не видит. Методы классов при сборке всей
программы пометки не требуют, см. [«Классы»](classes.md#доступ-метода-к-self).

## Параметры контракта

Контракт объявляет compile-time параметры через `generic`. Параметр со
значением типа записывается как `generic Name: Type`:

```efen
contract ValueIterator<Item> {
    mut fn next -> Item?
}
```

Параметры связываются при `conforms`. Позиционная и именованная формы
равноправны:

```efen
class StringIterator {
    conforms ValueIterator<String>
}

class AnotherStringIterator {
    conforms ValueIterator<Item: String>
}
```

Параметр принимает тип вместе с правом, если объявление пишет шаблон `Access T`
([право доступа как параметр](generics.md#право-доступа-как-параметр)).

Параметр может требовать, чтобы переданный тип соответствовал другому
контракту:

```efen
contract Producer<Item, Cursor: ValueIterator<Item>> {   // пример, не контракт lang
    fn iterator -> Cursor
}
```

`Cursor` здесь является конкретным типом результата. `ValueIterator<Item>` остаётся
compile-time ограничением и не используется как тип значения. Параметр может
иметь значение по умолчанию: `generic Name: Type = DefaultType`. Кроме типов,
`generic` принимает любое compile-time значение с указанным типом, включая
значение enum, число, строку, origin, экземпляр атрибута, contract, interface,
strategy, функцию или другую compile-time декларацию. Переданный contract
остаётся объектом compile-time и не становится типом runtime-значения.

Параметр contract можно не указывать при `conforms`, если его значение
однозначно выводится из реализованных требований:

```efen
class IntList {
    conforms Iterable<Item: Int>

    fn iterator -> IntListIterator
}
```

Здесь сопоставление с `fn iterator -> Cursor` выводит
`Cursor = IntListIterator`. Компилятор затем проверяет
`IntListIterator conforms ValueIterator<Item: Int>`. Неоднозначный вывод является
ошибкой и требует явного именованного аргумента.

Generic-тип может объявить соответствие условно внутри `#if`. Ложное условие
убирает соответствие и его условные члены из конкретной инстанциации, но не
запрещает создать сам тип:

```efen
class Box<T> {
    #if T conforms Copyable
        conforms Copyable
    #endif
}
```

`generic` является полной формой параметра объявления. Список в угловых скобках
остаётся допустимой короткой формой там, где она предусмотрена объявлением.

## Наследование контрактов

`:` у contract уточняет всех перечисленных parents. Соответствующий тип обязан
удовлетворять транзитивному объединению их требований:

```efen
contract Seekable : Readable, Writable {
    fn seek(position: Int)
}
```

Повтор одного ancestor с теми же resolved generic arguments дедуплицируется.
Members с одним именем допустимы лишь при идентичной нормализованной
requirement-signature: parameters, result, state, contexts, `throws` и rights.
Иначе declaration самого contract ошибочна. `use`/`as` не применяются: они
разрешают runtime member conflicts interface, а contract задаёт compile-time
requirements.

## Связь контрактов с интерфейсами

Runtime-interface из contract создаётся только явной декларацией:

```efen
contract DrawableContract {
    fn draw
}

interface DrawableInterface from DrawableContract
```

`DrawableInterface` сохраняет compile-time identity исходного
`DrawableContract` и проверяется как соответствующий ему (`conforms`). В
runtime-поверхность переносятся только вызываемые методы. Associated types,
требования к representation и другие compile-time ограничения проверяются при
создании и реализации interface, но автоматически не материализуются в runtime
metadata. Каждая runtime-сигнатура должна быть полностью замкнута: несвязанный
associated type или `Self` и неудовлетворённое representation-требование
являются ошибкой, а не молча стираются. Нужную runtime metadata может отдельно
породить метакод.

Без `interface ... from ...` contract остаётся только compile-time абстракцией
и сам по себе не создаёт VTBL.

Интерфейс может **соответствовать** (`conforms`) одному или нескольким контрактам. Это означает, что
компилятор проверит на этапе компиляции, что интерфейс удовлетворяет всем требованиям контракта.

Базовый пример:
```efen
interface MyInterface {
    conforms MyContract

    var anotherProperty: String { get set }
}
```

Интерфейс может наследовать один или несколько interface. Это расширяет
runtime-протокол, не добавляя storage:
```efen
interface ParentInterface {
    var parentProperty: Bool { get set }
    fn parentMethod
}

interface MyInterface : ParentInterface {
    conforms MyContract

    var anotherProperty: String { get set }
}
```

Множественные контракты в conforms уже определены Q46:
```efen
contract SecondContract {
    fn additionalMethod
}

interface MyInterface : ParentInterface {
    conforms MyContract, SecondContract

    var anotherProperty: String { get set }
}
```

Множественное наследование интерфейсов с контрактами допустимо:
```efen
interface AnotherParentInterface {
    var anotherParentProperty: Float { get set }
}

interface MyInterface : ParentInterface, AnotherParentInterface {
    conforms MyContract, SecondContract

    var anotherProperty: String { get set }
}
```

## Классы в контракте

Контракт может потребовать класс, как требует функцию. Класс в контракте задаёт то, что видит код снаружи: имя, базовый
класс, `open` и `final`, `conforms`, конструкторы и подписи методов с эффектами. Тел у методов нет, полей нет. Поля и
тела даёт реализация контракта:

```efen
// lang/exceptions.efen
contract Exceptions {
    open class Exception {
        conforms Throwable, Constructible, OpenClass
        @constructor fn init -> Self
        open fn reason -> Reason nofail
    }
}

// рантайм
implementation Exceptions {
    class Exception {
        var message: String
        @constructor fn init -> Self { … }
        fn reason -> Reason nofail { return .program }
    }
}

// программа
class ParseError: Exception { }
try { parse(text) } catch e: Exception { log(e.message) }
```

- **Класс в контракте — всегда требование.** Контракт не определяет классы сам; класс с телами пишут рядом с
  контрактом, в том же файле. Поэтому отдельного слова для требования нет: класс без тел методов читается как `fn` без
  тела.
- **Только в контракте, который реализуют через `implementation`.** Класс в контракте, который соблюдают через
  `conforms` или называют в `generic T: Contract`, — ошибка компиляции: такой контракт не для классов. Тип, который
  выбирает соблюдающий, задают параметром контракта (`Iterable<Item>`).
- **Имя принадлежит модулю контракта.** Программа пишет `Exception` или `lang::Exception`, а не
  `Exceptions.Exception`: контракт не пространство имён. Объявление с тем же именем в том же модуле — ошибка. Класс
  внутри `implementation` не вводит нового имени: это тот же тип.
- **Реализация повторяет подписи и добавляет своё.** Она не меняет базовый класс, `open`, `conforms` и подписи из
  контракта, даёт тело каждому методу и может добавить поля и члены. Открытые члены, которые она добавила, программа
  видит (`e.message` выше), и тогда программа зависит от этой реализации.
- **Одна реализация в программе.** Реализацию выбирает конфигурация сборки, как для контракта `@unique`
  ([связывание](context-and-effects.md)). Раскладка класса зависит от реализации, поэтому другой выбор пересобирает
  пакеты, которые наследуют такой класс или читают его поля.
- **В любом пакете.** Первое применение — корни исключений в `lang::`, но объявлять классы в контракте может любой
  пакет.

- **Выбор по имени пакета.** У блока `implementation` нет своего имени, поэтому строка `provide` называет
  пакет: `Exceptions: runtime`. Пакет даёт не больше одной реализации каждого контракта.
- **Наследование — соединение без противоречий.** Контракт с классами наследуют через `:`, как любой контракт:
  его реализация даёт классы всех предков. Противоречие — ошибка компиляции: если в сборку попадают две
  реализации, которые дают один и тот же класс, сборка не собирается.

```efen
contract WebExceptions : Exceptions { class Redirect: Exception { … } }

provide {
    Exceptions: runtime
    WebExceptions: web    // ошибка: `web` тоже даёт `Exception`, а его уже дал `runtime`
}
```

## Поля, которые требует контракт

Контракт описывает функции, полей storage он не объявляет (поля `layout` контракта —
[ниже](#layout-и-модель-в-контракте): в байтах их нет). Поле, которое нужно его
функциям, в тип добавляет аспект — [реализация извне](#реализация-извне): интерфейс storage не владеет
([интерфейсы](interfaces.md)). Например, класс со счётчиком пишет пустой контракт `ArcClass`, а поле `refCount` и
функции над ним даёт аспект из runtime:

```efen
contract ArcClass {             // пишет класс: conforms ArcClass
    allow implementations from runtime, std
}

contract ArcOperations {        // реализует аспект; вызовы расставляет компилятор
    mut fn retain
    mut fn release
}

@default
aspect ArcCounter {
    implements ArcClass
    conforms ClassDefinitionHandler, ArcOperations

    private var refCount: UInt
}
```

Требований у `ArcClass` нет, поэтому класс ему соответствует без своих методов. `retain` и `release` (контракт
`ArcOperations`) даёт аспект, а вызовы расставляет компилятор; программа их не пишет и не вызывает. Соответствие
`Cloneable` классу тоже даёт аспект: `clone x` увеличивает счётчик ([подсчёт ссылок](memory.md#подсчет-ссылок)).

## Реализация извне

Контракт может разрешить, чтобы реализацию тому, кто его соблюдает и не реализовал его сам, дали извне: пакет std,
другой пакет, конфигурация сборки. Разрешение — строка `allow implementations` в теле контракта. Без неё
реализацию для соблюдающего типа извне дать нельзя: аспект, который пишет `implements` такого контракта, — ошибка
компиляции. Реализация самого контракта блоком `implementation` ([классы в контракте](#классы-в-контракте),
`@unique` контракты) — отдельный механизм, эта строка его не касается.

```efen
contract ArcClass {
    allow implementations from runtime, std
}

contract Tracing {
    allow implementations from trace, program default trace::Console
    fn note(event: Event)
    fn flush
}
```

- **`from` — кто может дать реализацию.** Пакеты (`from std, runtime`), модуль со всем, что внутри
  (`from Memory::*`), пакет самой программы (`from program`). Без `from` реализацию может дать любой пакет
  сборки. Список ограничивает каждый способ выбора ниже: `use` в классе, `provide`, `default` контракта, `@default`.
  Аспект из пакета вне списка — ошибка сборки: «`ArcClass` не разрешает реализации из `mylib`».
- **Реализация извне — аспект.** Он пишет `implements Контракт` (у аспекта это слово значит «реализует контракт для
  соблюдающих», у класса — «реализует интерфейс») и добавляет в класс код и скрытые структуры: поле счётчика,
  описатель, служебное слово. Компилятор сам в класс ничего не добавляет ([аспекты](aspects/aspect.md)). Строка
  `allow implementations` даёт аспекту право ровно на это: требования контракта, приватные поля и соответствия,
  которые аспект перечисляет в `conforms`. Методы служебных контрактов вроде `ArcOperations` вызывает только
  компилятор. В построении класса аспект участвует как `ClassDefinitionHandler`
  ([построение класса](aspects/compile-time/class.md#план-построения)) один раз, у корня иерархии, поэтому он не
  спорит с определением корня.
- **Аспект полон.** Аспект с `implements C` реализует каждое требование `C`; неполный аспект — ошибка в месте его
  объявления, а не у класса, к которому его применили.
- **Всё или ничего.** Класс либо реализует все требования контракта сам, и тогда извне ничего не накладывается,
  либо не реализует ни одного. Часть требований своя, часть чужая — ошибка компиляции. Контракт без требований с
  `allow implementations` (`ArcClass`) всегда реализуется извне:

```text
error[E....]: `Config` implements part of `Tracing`
  --> app.efen:4:5
   |
 4 |     fn note(event: Event) { … }
   |     ^^^^^^^^^^^^^^^^^^^^^ `note` is written here, `flush` is not
   |
   = help: write every requirement of `Tracing`, or none and let an implementation be chosen
```

- **Выбор реализации**, от сильного к слабому:
  1. `use Аспект` в корне иерархии — выбор окончательный для этой иерархии;
  2. запись `provide` программы, затем рабочего пространства, затем глобальной конфигурации; ключ такой записи —
     контракт с `allow implementations`, значение — аспект: `provide { ArcClass: runtime::ArcCounter }`
     ([конфигурация сборки](build-config.md)). Это не связывание эффекта: функции, в которых компилятор вызывает
     методы аспекта, эффекта не получают. Библиотека, секции пакетов и `provides` слоя такую запись не пишут;
  3. `default Аспект` в строке `allow implementations` контракта;
  4. `@default` на аспекте ([умолчание](context-and-effects.md#умолчание)); два `@default` на параллельных ветках
     зависимостей — ошибка, как у реализаций эффектов.
- **Нет реализации — ошибка.** Класс соблюдает контракт, сам его не реализовал, и ни одно правило не выбрало
  аспект: «`Config` conforms to `ArcClass`, and no implementation is chosen».
- **Раскладка класса.** Аспект, который добавляет поля, меняет раскладку класса. Поэтому выбор по `provide` один на
  контракт в программе (`use` у корня его перекрывает для своей иерархии), а другой выбор пересобирает пакеты,
  которые наследуют класс или читают его поля, как у [класса в контракте](#классы-в-контракте). Пакет, который
  приходит только в бинарном виде и собран с другим выбором, — ошибка сборки. Поля двух аспектов одного класса
  лежат в порядке контрактов в строке `conforms`; два аспекта, которые дают классу одно и то же соответствие
  (`Cloneable`), — ошибка, называющая оба.

Ранняя форма шаблона структуры внутри контракта (`requires struct: struct<T>`,
`@base struct <T> { … }`) в язык не входит: поля даёт аспект.

## `layout` и модель в контракте

Контракт может объявить `layout { var … }` и [модели](conditions.md#модель-model) у методов. Поля такого `layout` — не
поля storage: их нет в байтах, их пишут только модели и читает только FLOW
([`layout` в теле класса](memory/addresses.md#layout-в-теле-класса)). Обобщённый код над контрактом берёт модель
метода как сводку вызова; каждая реализация проверяется там, где написан `conforms`, как пометки `edit fn`. `layout`
и модели входят в объявление контракта. При выполнении они ничего не стоят: вызов остаётся статическим, таблицы
методов нет.

```efen
contract Sink {                                  // хранит буферы между write и flush
    layout { var kept: [read [UInt8]] }
    mut fn write(data: read [UInt8])
    model { self.kept.append(data) }
    mut fn flush
    model { self.kept.clear() }
}

fn dump<S: Sink>(out: mut S, lines: read [String]) {
    for line in lines {
        let buf = line.utf8()
        out.write(data: buf)
        out.flush()                              // без него ошибка: buf умирает, пока out его держит
    }
}

public class File {
    conforms Sink
    representation Raw<Descriptor>
    mut fn write(data: read [UInt8]) { … }       // копирует: удержаний нет, модель Sink уточнена
    mut fn flush { }
}
```

**Реализация сравнивается с моделью по удержаниям, а не по полям.** Удержание определяют метод, который его положил,
путь параметра и право; имена полей — учёт каждого объявления. После каждого метода удержания реализации входят в
удержания модели: реализация не кладёт ничего сверх модели, не берёт более широкого права и не держит того, что
модель снимает. Реализация, которая копирует, не держит ничего и уточняет любую модель.

`shared layout` реализации ([общая память](shared.md#shared-layout)) уточняет только `shared layout` контракта.
Реализация без `shared` под объявлением `shared layout` обещает меньше объявления, и это допустимо.

```efen
contract AsyncSink {                             // ядро читает буферы, когда захочет
    shared layout { var kept: [read [UInt8]] }
    mut fn write(data: read [UInt8])
    model { self.kept.append(data) }
    mut fn drain
    model { self.kept.clear() }
}

class Ring {
    conforms AsyncSink
    representation Raw<Descriptor>
    shared layout { var inflight: [read [UInt8]] }   // своё имя поля: сравниваются удержания
    mut fn write(data: read [UInt8])
    model { self.inflight.append(data) }       // то же удержание, что у AsyncSink.write
    {
        …
    }
    mut fn drain
    model { self.inflight.clear() }
    {
        …
    }
}
```

Контракт, у которого `write` всегда копирует, `layout` и моделей не объявляет: это другой контракт.
