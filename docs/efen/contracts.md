# Контракты

[Документация](README.md) · [Словарь](glossary.md) · [Интерфейсы](interfaces.md) · [Стратегии](strategies.md)

Контракт задаёт правила, которым должны соответствовать код и его поведение.
Компилятор использует эти правила, чтобы проверить реализацию и код,
который с ней работает.

Требования могут описывать доступные операции и свойства, права чтения
и изменения, передачу владения, состояния, условия выполнения и заимствование
чужой памяти. Список методов и свойств — лишь одна из форм таких требований.
Например, `edit fn` обещает сохранять существующие слоты в памяти, а модель
метода описывает, какие переданные значения он может заимствовать после вызова.

В простейшем случае контракт требует свойство и метод:

```efen
contract MyContract {
    var myProperty: Int { get set }
    fn myMethod
}
```

## Чистый контракт и его реализация

Чистый контракт задаёт только требования. Само объявление не предоставляет
тела методов, хранимые поля или готовую реализацию. Здесь «чистый» описывает
отделение требований от реализации; это не обещание отсутствия побочных
эффектов у методов и не отдельная пометка `pure`.

```efen
contract Named {
    fn name -> String
}

class Document {
    conforms Named
    var title: String
    fn name -> String { return title }
}
```

`Named` остаётся чистым контрактом, хотя `Document` содержит реализацию его
требования. `conforms Named` требует проверить соответствие; эта строка сама
по себе не добавляет метод `name`.

Контракт может не требовать ни одного члена. Отсутствие методов само по себе
ничего не говорит о необходимости внешней реализации: это определяется
правилами контракта и способом его использования.

### Кто предоставляет реализацию

| Способ | Что требуется |
|---|---|
| `conforms C` у типа | Тип выполняет требования `C`; общий код использует их через ограничение параметра типа |
| `implementation C` с блоком в фигурных скобках | Отдельный блок предоставляет объявления и тела, требуемые контрактом; так можно потребовать в том числе классы |
| `allow implementations` в контракте | Аспекту разрешено предоставить реализацию для соблюдающего типа по правилам [реализации извне](#реализация-извне) |

Например, контракт может требовать функцию, которую предоставляет отдельная реализация:

```efen
contract Clock {
    fn now -> Int
}

implementation Clock {
    fn now -> Int { return 0 }   // фиксированное время для теста
}
```

Объявление задаёт требование, блок `implementation` — исполняемый код.
Когда контракт используется как эффект, реализацию выбирают по правилам
[статического связывания](context-and-effects.md#статическое-связывание-эффектов).
Требования классов и выбор их реализации описаны [ниже](#классы-в-контракте).
`allow implementations` относится к реализации для соблюдающего типа и не
является разрешением на блок `implementation`.

Специальные контракты, функции и типы, которые доступны в языке всегда,
собраны в разделе [Runtime языка Efen](runtime/README.md). Их связь с
операторами и действиями компилятора определяется языком; пользовательский
контракт с похожим именем такой связи не получает.

## Контракт и интерфейс

Контракт задаёт требования, проверяемые при компиляции. Интерфейс позволяет
выбирать реализацию при выполнении программы.

<a id="contract--compile-time-абстракция"></a>

### Контракт: проверка при компиляции

Сам по себе контракт не является типом значения и не требует таблицы
виртуальных методов. Когда конкретная реализация известна, вызов может быть
прямым. Проверки и модели контракта используются компилятором; необходимый
код реализации при этом остаётся в программе.

Контракт нельзя использовать как тип поля или локальной переменной.
Обобщённая функция объявляет конкретный тип через `generic T: Contract`,
а затем использует `T` как тип параметра. Запись `opaque Contract` в результате
задаёт требования к скрытому конкретному типу и сама по себе не создаёт
интерфейс времени выполнения.

<a id="interface--runtime-абстракция"></a>

### Интерфейс: выбор реализации при выполнении

Значение интерфейса позволяет работать с разными реализациями через общий
набор операций. Вызов направляется к нужной реализации через таблицу
виртуальных методов (VTBL). Это динамическая диспетчеризация; она требует
соответствующего представления и косвенного вызова.

### Практический пример

```efen
// CONTRACT: только compile-time
contract Drawable {
    fn draw
}

// INTERFACE: runtime VTBL
interface Shape {
    fn area -> Float
}

// Класс соответствует контракту и реализует интерфейс
class Circle {
    conforms Drawable      // Compile-time проверка
    implements Shape       // Runtime VTBL

    var radius: Float

    fn draw {
        // Реализация требования контракта
        print("Рисую круг")
    }

    fn area -> Float {
        // Реализация метода интерфейса
        return 3.14 * radius * radius
    }
}
```

### Что происходит после компиляции?

```efen
// Compile-time: компилятор проверяет что draw() есть
fn renderStatic<T: Drawable>(object: T) {
    object.draw()  // STATIC DISPATCH - прямой вызов
}

// Runtime: используется VTBL для полиморфизма
fn calculateArea(shape: Shape) -> Float {
    return shape.area()  // DYNAMIC DISPATCH - вызов через VTBL
}
```

**После компиляции:**
- Требования `Drawable` проверены компилятором; при известной реализации `draw()` может вызываться напрямую
- `Shape` интерфейс **присутствует** как VTBL в бинарнике
- `calculateArea` может принимать **любой** объект реализующий Shape

Проверка контракта при компиляции не гарантирует отсутствие затрат при
выполнении. Например, скрытое структурное объединение нескольких реализаций
выбирает нужную операцию по метке активного типа. Эти затраты определяются
представлением и способом вызова; известная конкретная реализация
по-прежнему допускает прямой вызов.

<a id="когда-использовать-что"></a>

### Выбор механизма

Используйте контракт, когда общий код должен проверяться для конкретных типов:
например, алгоритм требует сравнение, копирование или определённые права доступа.
Используйте интерфейс, когда значения разных реализаций должны передаваться
через общий тип, а выбор реализации происходит при выполнении.

Бинарная совместимость требует сохранения ABI и соглашений о вызовах.
Производительность зависит от конкретной реализации и оптимизации;
само слово `contract` или `interface` её не определяет.

<a id="комбинация-contract--interface"></a>

### Совместное использование контракта и интерфейса

Один класс может соответствовать контракту и реализовывать интерфейс:

```efen
// Требования, проверяемые при компиляции
contract Serializable {
    fn serialize -> String
}

// Общий тип для выбора реализации при выполнении
interface Storable {
    fn save(path: String)
}

class Document {
    conforms Serializable  // Соответствие проверяется при компиляции
    implements Storable    // Доступ через интерфейс

    fn serialize -> String {
        return "..."
    }

    fn save(path: String) {
        let data = serialize()  // Статический вызов
        writeToFile(path, data)
    }
}

// Общий код с требованием Serializable
fn sendOver<T: Serializable>(object: T) {
    let data = object.serialize()  // При известной реализации возможен прямой вызов
    network.send(data)
}

// Общий тип для разных реализаций Storable
fn saveAll(objects: [Storable]) {
    for obj in objects {
        obj.save("/tmp/file")  // DYNAMIC - через VTBL
    }
}
```

Подробнее — в статье [об интерфейсах](interfaces.md).

## Доступ метода к self

Метод контракта пишет, меняет ли он `self`, тем же правом, что и параметр.
`own fn` забирает `self`: владение переходит к методу, как аргумент параметра
`own`, и после вызова переменной-получателя больше нет. Получателя отдают явно,
формой `(take x).m()`, как у замыкания `(take task)()`; `take x.m()` забирает
результат вызова, а не `x`. `mut fn` может менять
`self` целиком, включая структуру: добавить элемент, убрать его, записать `self`
заново. `edit fn` не перемещает и не уничтожает существующие слоты `self`: он
меняет значения в них и может создать новые слоты, как `append` связного списка.
`read fn` только читает `self`. Метод без
пометки тоже только читает: пометка `read` записывает умолчание явно, как у
параметров.

```efen
contract Stack<T> {
    mut fn push(item: T)
    mut fn pop -> T?
    fn peek -> T?          // то же, что read fn peek -> T?
    own fn drain -> [T]    // забирает стек, после вызова его нет
}

let items = (take stack).drain()   // забор пишут явно
let items = stack.drain()          // ошибка: own fn требует take у получателя

contract Cursors<T> {
    edit fn next(cursor: mut Cursor) -> edit T?
}
```

`edit fn` нужен методу, который отдаёт ссылку `edit` в `self`
([ссылка в результате функции](types/ownership.md#место-в-результате-функции)):
вызов `mut fn` может перестроить `self`, поэтому ссылка из прошлого вызова
умирает, а после вызова `edit fn` она живёт. Два курсора через контракт
работают только так:

```efen
fn pair(items: edit Cursors<Item>, a: mut Cursor, b: mut Cursor) {
    if let x = items.next(cursor: a) {
        if let y = items.next(cursor: b) {   // x жив: next не меняет структуру items
            x.count = y.count
        }
    }
}
```

Метод `edit fn` вызывается у
получателя `edit` и `mut`, но не у получателя без права записи, так же, как параметр `edit` принимает только
ссылку с правом записи.
Так проверяется вызов через контракт или интерфейс, где видна одна пометка.
Прямой вызов метода класса проверяется по его телу, как вызов `mut fn`: `edit fn`,
который ничего не меняет, можно вызвать и у получателя без права записи. Вызов
`mut fn` через интерфейс может перестроить `self`, поэтому получатель `edit` его
не принимает. Исключение — класс над внешним значением: там право получателя относится к слоту с сырым значением,
а пометка метода — к внешнему объекту ([класс над внешним значением](classes.md#класс-над-внешним-значением)).

Если тело `mut fn` не перемещает и не уничтожает ни одного существующего слота
`self` и не делает перехода состояния, компилятор выдаёт предупреждение
`W.access.edit-suffices` и предлагает пометку `edit fn`. Предупреждения нет у `open fn` и `override`, у реализации метода контракта или интерфейса и у функции, которую кладут в тип функции с параметром `mut`:

```efen
class Chain {
    var nodes: own LinkedList<Int>

    mut fn add(value: Int) {      // warning[W.access.edit-suffices]: mark it `edit fn`
        self.nodes.append(value)  // новый узел; старые узлы не двигаются
    }
}
```

Компилятор не смотрит в реализации, когда проверяет вызов через контракт:
вызывающий читает только пометку. Реализация проверяется по пометке там, где
она написана. Тело `peek`, которое меняет поле `self`, — ошибка в этом теле, а
не у вызывающего; так же ошибка — тело `edit fn`, которое перемещает или
уничтожает существующие слоты `self`. Реализация может быть уже пометки, но не шире: метод `mut fn`
реализуют `mut fn`, `edit fn` или `read fn`, метод `edit fn` — `edit fn` или
`read fn`. Метод `own fn` реализует только `own fn`: вызывающий уже отдал
объект, и реализация обязана его уничтожить или передать дальше. Пометка бывает
параметром типа `Access`, и тогда одно объявление покрывает несколько прав
([право доступа как параметр](generics.md#право-доступа-как-параметр)).

Пометка может назвать часть объекта, структуру которой метод меняет: `mut<self.cache> fn clearCache`. Части контракт
объявляет строкой `layout { part items, cache }`, а реализация привязывает их к своим полям. После вызова такого
метода ссылки в остальные части действуют ([части объекта](types/parts.md)).

Контракт остаётся такой границей и при сборке всей программы: его реализуют
типы, которые автор контракта не видит. Права методов класса также задаются объявлением; отсутствие пометки означает
`read`. Сборка всей программы может уточнять сводки действий, но не отменяет
это правило ([классы](classes.md#доступ-метода-к-self)).

## Параметры контракта

Контракт объявляет параметры времени компиляции через `generic`. Параметр со
значением типа записывается как `generic Name: Type`:

```efen
contract ValueIterator<Item> {
    mut fn next -> Item?
}
```

Параметры связываются при `conforms`. Позиционная и именованная формы
равноправны:

```efen
class StringIterator {
    conforms ValueIterator<String>
}

class AnotherStringIterator {
    conforms ValueIterator<Item: String>
}
```

Параметр принимает тип вместе с правом, если объявление пишет право перед его именем, `Access T`
([право доступа как параметр](generics.md#право-доступа-как-параметр)).

Параметр может требовать, чтобы переданный тип соответствовал другому
контракту:

```efen
contract Producer<Item, Cursor: ValueIterator<Item>> {   // пример, не контракт lang
    fn iterator -> Cursor
}
```

`Cursor` здесь является конкретным типом результата. `ValueIterator<Item>` остаётся
ограничением времени компиляции и не используется как тип значения. Параметр может
иметь значение по умолчанию: `generic Name: Type = DefaultType`. Кроме типов,
`generic` принимает любое значение времени компиляции с указанным типом, включая
элемент перечисления, число, строку, источник (`origin`), экземпляр атрибута,
контракт, интерфейс, стратегию, функцию или другое объявление времени компиляции.
Переданный контракт остаётся объектом времени компиляции и не становится
типом значения времени выполнения.

Значение параметра при `conforms` можно не писать, а вывести из реализованных требований. Вывод просят явно, знаком
`_` на месте значения:

```efen
class IntList {
    conforms Iterable<Item: Int, Cursor: _>

    fn iterator -> IntListIterator
}
```

Здесь сопоставление с требованием `iterator` выводит `Cursor = IntListIterator`. Компилятор затем проверяет инвариант
контракта: `IntListIterator` соблюдает `Iterator<Access Item, Src: self>` или `ValueIterator<Item>`
([контракты обхода](types/collections.md#контракты-обхода)). Неоднозначный вывод — ошибка и требует явного значения.
Знак `_` здесь просит вывести значение; в образце тот же знак означает «любое значение, оно не нужно».

- `Cursor: _` выводит названный параметр. Голый `_` в конце списка выводит все оставшиеся параметры:
  `conforms Iterable<Item: Int, _>`, а `conforms Iterable<_>` выводит все. Голый `_` в списке один и стоит последним.
- Запись с именем строже: параметр, добавленный в контракт позже, даёт ошибку, пока его не назовут. Голый `_`
  такой параметр выведет.
- Параметр без значения по умолчанию, который в `conforms` не назван и не отмечен `_`, — ошибка:
  `conforms Iterable<Item: Int>` не говорит, чему равен `Cursor`. Пропуск означает только умолчание, объявленное в
  контракте (`generic Name: Type = DefaultType`), как пропущенный аргумент функции.
- Правило относится к `conforms`. Ограничение `T: Iterable<Item: Int>` ничего не выводит: оно требует только то, что
  называет, а остальные параметры у подходящего типа любые. По тому же правилу читается `conforms` внутри
  `invariants`: `Cursor conforms Iterator<Access Item, Src: self>` требует названное.
- Когда остался один параметр, пишут его имя: `Cursor: _`. Голый `_` — для нескольких оставшихся параметров.

**Правило.** Параметр выводится в два шага. Сначала требования контракта сопоставляются с объявлениями типа. Затем
инвариант вида `P conforms K<Q>` при известном `P` определяет `Q`, если `P` соблюдает `K` ровно одним способом; в
инварианте с `||` выполнимой должна быть ровно одна ветвь. Так `conforms Iterable<_>` выводит `Item` из типа курсора.

| Случай | Что происходит |
|---|---|
| два требования дают параметру разные значения | ошибка-конфликт; сообщение называет оба требования |
| значение не определяют ни требования, ни инварианты | для голого `_` берётся умолчание контракта; без умолчания — ошибка, которая называет параметр |
| параметр с умолчанием, значение определено | берётся выведенное значение, а не умолчание; `Name: _` умолчания не берёт никогда |
| требованию подходят несколько перегрузок | сначала их отсеивают уже известные параметры; больше одной оставшейся — ошибка |
| параметр-число или источник | выводится только сопоставлением записи: `N + 1` с `8` не решается, это ошибка |
| выведен приватный тип в публичном соответствии | та же ошибка видимости, что при явной записи |

- `_` выводит и право: `conforms Iterable<_>` рядом с `edit fn iterator` даёт `Access = edit`. Право, которое не
  написано и не покрыто знаком `_`, по-прежнему значит `read`: `conforms Iterable<Item: Int, Cursor: _>` — это
  `Access = read`.
- Параметр, сопоставленный с результатом в скобках `(R<путь> X)`, выводится как тип курсора, в котором путь
  заимствования заменён параметром источника: для `-> ArrayIterator<Access T, Src: self>` это `ArrayIterator<Access T, Src>`.
  Каждый вызов подставляет в `Src` своего получателя, поэтому `C.Cursor` — тип, и приватное поле из `Src: self.data`
  в аргумент контракта не попадает. Явная запись того же: `Cursor: ArrayIterator<Access T, Src>`.
- `_` пишется только там, где то же объявление даёт объявления для сопоставления: в `conforms` класса, структуры,
  стратегии и интерфейса с собственными членами, в `implements` аспекта (вывод идёт для каждого класса отдельно). В
  `interface X from C<_>`, в `#if T conforms C<_>`, в псевдониме и в ограничении `_` — ошибка: выводить не из чего.

Параметризованный тип может объявить соответствие условно внутри `#if`. Ложное условие
убирает соответствие и его условные члены из конкретной инстанциации, но не
запрещает создать сам тип:

```efen
class Box<T> {
    #if T conforms Copyable
        conforms Copyable
    #endif
}
```

`generic` является полной формой параметра объявления. Список в угловых скобках
остаётся допустимой короткой формой там, где она предусмотрена объявлением.

## Наследование контрактов

Двоеточие после имени контракта перечисляет контракты-предки.
Реализация должна выполнять требования всех предков, в том числе унаследованные:

```efen
contract Seekable : Readable, Writable {
    fn seek(position: Int)
}
```

Повтор одного предка с теми же аргументами учитывается один раз.
Одноимённые требования совместимы только при совпадении нормализованных
сигнатур: параметров, результата, состояний, контекстов, исключений и прав.
Иначе возникает ошибка в объявлении контракта.

`use` и `as` для разрешения таких конфликтов не применяются. Они выбирают
наследуемые члены интерфейса, а контракт объединяет требования, которые
не должны противоречить друг другу.

## Связь контрактов с интерфейсами

Интерфейс по контракту создаётся только явным объявлением:

```efen
contract DrawableContract {
    fn draw
}

interface DrawableInterface from DrawableContract
```

`DrawableInterface` сохраняет связь с исходным `DrawableContract` и проверяется
на соответствие ему. Через интерфейс доступны методы, вызываемые при выполнении.
Связанные типы, требования к представлению данных и другие статические
ограничения проверяются при создании и реализации интерфейса.

Типы в каждой вызываемой сигнатуре должны быть определены полностью.
Несвязанный параметр типа, `Self` без конкретной привязки или невыполненное
требование к представлению приводят к ошибке: компилятор не может просто
стереть их из сигнатуры. Если при выполнении нужны метаданные, их отдельно
создаёт метакод. Сам контракт таблицы виртуальных методов не порождает.

Интерфейс может **соответствовать** (`conforms`) одному или нескольким контрактам. Это означает, что
компилятор проверит на этапе компиляции, что интерфейс удовлетворяет всем требованиям контракта.

Базовый пример:
```efen
interface MyInterface {
    conforms MyContract

    var anotherProperty: String { get set }
}
```

Интерфейс может наследовать один или несколько интерфейсов. Это расширяет
протокол вызовов, не добавляя память для полей:
```efen
interface ParentInterface {
    var parentProperty: Bool { get set }
    fn parentMethod
}

interface MyInterface : ParentInterface {
    conforms MyContract

    var anotherProperty: String { get set }
}
```

В одной строке `conforms` можно перечислить несколько контрактов:
```efen
contract SecondContract {
    fn additionalMethod
}

interface MyInterface : ParentInterface {
    conforms MyContract, SecondContract

    var anotherProperty: String { get set }
}
```

Множественное наследование интерфейсов с контрактами допустимо:
```efen
interface AnotherParentInterface {
    var anotherParentProperty: Float { get set }
}

interface MyInterface : ParentInterface, AnotherParentInterface {
    conforms MyContract, SecondContract

    var anotherProperty: String { get set }
}
```

## Классы в контракте

Контракт может потребовать класс, как требует функцию. Класс в контракте задаёт то, что видит код снаружи: имя, базовый
класс, `open` и `final`, `conforms`, конструкторы и сигнатуры методов с эффектами. Тел у методов нет, полей нет. Поля и
тела даёт реализация контракта:

```efen
// Объявление требований в пакете storage-api
contract Records {
    class Record {
        fn label -> String
    }
}

// Реализация в пакете storage
implementation Records {
    class Record {
        var text: String
        fn label -> String { return text }
    }
}

// Код, использующий объявленный класс
fn describe(record: Record) -> String { return record.label() }
```

- **Класс в контракте — всегда требование.** Контракт не определяет классы сам; класс с телами пишут рядом с
  контрактом, в том же файле. Поэтому отдельного слова для требования нет: класс без тел методов читается как `fn` без
  тела.
- **Только в контракте, который реализуют через `implementation`.** Класс в контракте, который соблюдают через
  `conforms` или называют в `generic T: Contract`, — ошибка компиляции: такой контракт не для классов. Тип, который
  выбирает соблюдающий, задают параметром контракта (`Iterable<Item>`).
- **Имя принадлежит модулю контракта.** Программа пишет `Record` с квалификацией его модуля, а не
  `Records.Record`: контракт не пространство имён. Объявление с тем же именем в том же модуле — ошибка. Класс
  внутри `implementation` не вводит нового имени: это тот же тип.
- **Реализация повторяет сигнатуры и добавляет своё.** Она не меняет базовый класс, `open`, `conforms` и сигнатуры из
  контракта, даёт тело каждому методу и может добавить поля и члены. Открытые члены, которые она добавила, программа
  видит (`text` выше), и тогда программа зависит от этой реализации.
- **Одна реализация в программе.** Реализацию выбирает конфигурация сборки, как для контракта `@unique`
  ([связывание](context-and-effects.md)). Раскладка класса зависит от реализации, поэтому другой выбор пересобирает
  пакеты, которые наследуют такой класс или читают его поля.
- **В любом пакете.** Объявлять классы в контракте может любой пакет. Применение к
  корням исключений описано в [разделе Runtime](runtime/lang-roles.md#исключения-языка).

- **Выбор по имени пакета.** У блока `implementation` нет своего имени, поэтому строка `provide` называет
  пакет: `Records: storage`. Пакет даёт не больше одной реализации каждого контракта.
- **Наследование — соединение без противоречий.** Контракт с классами наследуют через `:`, как любой контракт:
  его реализация даёт классы всех предков. Противоречие — ошибка компиляции: если в сборку попадают две
  реализации, которые дают один и тот же класс, сборка не собирается.

```efen
contract ExtendedRecords : Records { class Metadata { fn size -> Int } }

provide {
    Records: storage
    ExtendedRecords: cache    // ошибка: оба пакета дают класс Record
}
```

## Поля, которые требует контракт

Требование свойства описывает доступ к нему, но не задаёт физическое поле объекта.
Поля `layout` контракта нужны для проверки моделей и в байтах объекта не хранятся.
Реальные поля и тела методов даёт реализация. При реализации извне поля может
добавить аспект, если контракт это разрешает.

Применение этого механизма к счётчику ссылок описано в разделе
[Runtime языка Efen](runtime/object-support.md).

## Реализация извне

Контракт может разрешить, чтобы реализацию тому, кто его соблюдает и не реализовал его сам, дали извне: пакет std,
другой пакет, конфигурация сборки. Разрешение — строка `allow implementations` в теле контракта. Без неё
реализацию для соблюдающего типа извне дать нельзя: аспект, который пишет `implements` такого контракта, — ошибка
компиляции. Реализация самого контракта блоком `implementation` ([классы в контракте](#классы-в-контракте),
`@unique` контракты) — отдельный механизм, эта строка его не касается.

```efen
contract Tracing {
    allow implementations from trace, program default trace::Console
    fn note(event: Event)
    fn flush
}
```

- **`from` — кто может дать реализацию.** Пакеты (`from std, runtime`), модуль со всем, что внутри
  (`from Memory::*`), пакет самой программы (`from program`). Без `from` реализацию может дать любой пакет
  сборки. Список ограничивает каждый способ выбора ниже: `use` в классе, `provide`, `default` контракта, `@default`.
  Аспект из пакета вне списка — ошибка сборки: «`Tracing` не разрешает реализации из `mylib`».
- **Реализация извне — аспект.** Он пишет `implements Контракт` (у аспекта это слово значит «реализует контракт для
  соблюдающих», у класса — «реализует интерфейс») и добавляет в класс код и скрытые структуры: поле счётчика,
  описатель, служебное слово. Компилятор сам в класс ничего не добавляет ([аспекты](aspects/aspect.md)). Строка
  `allow implementations` даёт аспекту право ровно на это: требования контракта, приватные поля и соответствия,
  которые аспект перечисляет в `conforms`. В построении класса аспект участвует как `ClassDefinitionHandler`
  ([построение класса](aspects/compile-time/class.md#план-построения)) один раз, у корня иерархии, поэтому он не
  спорит с определением корня.
- **Аспект полон.** Аспект с `implements C` реализует каждое требование `C`; неполный аспект — ошибка в месте его
  объявления, а не у класса, к которому его применили.
- **Всё или ничего.** Класс либо реализует все требования контракта сам, и тогда извне ничего не накладывается,
  либо не реализует ни одного. Часть требований своя, часть чужая — ошибка компиляции. Контракт без требований с
  `allow implementations` всегда реализуется извне.

При частичной реализации диагностика указывает на уже написанное требование:

```text
error[E....]: `Config` implements part of `Tracing`
  --> app.efen:4:5
   |
 4 |     fn note(event: Event) { … }
   |     ^^^^^^^^^^^^^^^^^^^^^ `note` is written here, `flush` is not
   |
   = help: write every requirement of `Tracing`, or none and let an implementation be chosen
```

- **Выбор реализации**, от сильного к слабому:
  1. `use Аспект` в корне иерархии — выбор окончательный для этой иерархии;
  2. запись `provide` программы, затем рабочего пространства, затем глобальной конфигурации; ключ такой записи —
     контракт с `allow implementations`, значение — аспект: `provide { Tracing: trace::Console }`
     ([конфигурация сборки](build-config.md)). Особенности служебных вызовов компилятора описаны в
     [поддержке объектов](runtime/object-support.md). Библиотека, секции пакетов и `provides` слоя такую запись не пишут;
  3. `default Аспект` в строке `allow implementations` контракта;
  4. `@default` на аспекте ([умолчание](context-and-effects.md#умолчание)); два `@default` на параллельных ветках
     зависимостей — ошибка, как у реализаций эффектов.
- **Нет реализации — ошибка.** Класс соблюдает контракт, сам его не реализовал, и ни одно правило не выбрало
  аспект: «`Config` conforms to `Tracing`, and no implementation is chosen».
- **Раскладка класса.** Аспект, который добавляет поля, меняет раскладку класса. Поэтому выбор по `provide` один на
  контракт в программе (`use` у корня его перекрывает для своей иерархии), а другой выбор пересобирает пакеты,
  которые наследуют класс или читают его поля, как у [класса в контракте](#классы-в-контракте). Пакет, который
  приходит только в бинарном виде и собран с другим выбором, — ошибка сборки. Поля двух аспектов одного класса
  лежат в порядке контрактов в строке `conforms`; два аспекта, которые дают классу одно и то же соответствие
  другому контракту, — ошибка, называющая оба.

Ранняя форма шаблона структуры внутри контракта (`requires struct: struct<T>`,
`@base struct <T>`) в язык не входит: поля даёт аспект.
