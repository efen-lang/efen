# Условия функций и циклов

[Документация](README.md) · [Словарь](glossary.md) · [Функции](functions.md) · [Операторы](operators.md)

Функция объявляет, что она требует от вызывающего (`requires`) и что гарантирует после возврата (`ensures`).
Цикл объявляет, что верно на каждом шаге (`invariant`) и почему он кончится (`decreases`). Компилятор
доказывает условия; что он может вывести из кода сам, писать не нужно.

Форма `requires`/`ensures` после сигнатуры, по образцу
[проекта проверяемого диалекта](memory/viper-verification-backend.md#синтаксис-контрактов-проверяемого-диалекта);
`previous(x)` вместо `old(x)`; условия функции не пишутся в `{}` у параметров и результата, кроме тех, что
являются частью типа; недоказанное условие — заметка, а безопасность, которая держалась бы на нём, проверяется при выполнении; переполнение в
условии — ошибка, когда оно видно точно, иначе заметка и проверка ([арифметика](#арифметика-и-частичные-операции)).

## Форма

```efen
fn withdraw(account: mut Account, amount: Int) -> Int
    requires amount > 0
    requires account.balance >= amount
    ensures account.balance == previous(account.balance) - amount
    ensures result == account.balance
{
    account.balance = account.balance - amount
    return account.balance
}
```

- Условия идут после сигнатуры, каждое с новой строки, с отступом на один уровень. Порядок хвоста сигнатуры: `state`, `in`, `throws`, `where` — каждый, если есть;
  затем все `requires`, затем все `ensures`, затем `decreases`, затем [`model`](#модель-model).
- Если у функции есть условия, `{` тела стоит на отдельной строке без отступа. Без условий `{` пишется как
  обычно, в конце сигнатуры; строка `throws` при этом может стоять отдельно, как в
  [условном владении](types/ownership.md#владение-которое-функция-забирает-не-всегда).
- Условия видят все параметры, и те, что объявлены `param` и `generic` в начале тела:

```efen
fn tryExtendInPlace -> Bool
    requires oldSize >= 0 && newSize >= 0
    requires p >= 0 && p <= arena.limit && newSize <= arena.limit - p
    ensures result ==> arena.bump == p + newSize
{
    param arena: mut Arena
    param p: Int
    param oldSize: Int
    param newSize: Int

    // тело
}
```

  У объявления без тела (`contract`, `interface`, `@abi(c)`) места для `param` нет, поэтому правило
  [`S.function-parameter-layout`](diagnostic-groups.md#style-diagnostics-s) на него не действует.
- Условие кончается переводом строки вне скобок. Длинное условие пишется блоком:

```efen
fn relinkBlock(pool: mut Pool, index: Int, block: mut SlotBlock)
    requires {
        index >= 0 && index < CLASSES
        block.used > 0
        !block.linked
    }
    ensures block.linked
{
    // тело
}
```

  Это блок условий, как у [условий свойства](memory/addresses.md#декларативные-условия): каждая строка —
  отдельное условие, строки соединяются `&&`, `if` внутри означает импликацию. Это не выражение-блок: его
  значение — не последняя строка.
- Условие продолжается на следующей строке, если та начинается с бинарного оператора (`==>`, `&&`, `||`) или
  перенос стоит внутри скобок. Это правило одно для строки `requires`/`ensures` и для строки блока.
- Несколько `requires` соединяются `&&`, несколько `ensures` — тоже.
- `requires`, `ensures`, `invariant`, `decreases`, `forall` и `previous` — контекстные слова: особые
  только в условиях. Особое имя `result` в условиях — результат; параметр с именем `result` у функции с
  `ensures` — ошибка.
- В методе имена в условиях разрешаются так же, как в теле: поле получателя пишется без `self`, если тело так
  может.

## Смысл

- **`requires`** доказывает вызывающий код в каждой точке вызова. Внутри функции это известный факт, даже если
  у какого-то вызывающего он не доказан: тогда его проверяет точка вызова
  ([ниже](#обычная-сборка-и-диагностики)).
- **`ensures`** доказывает функция на каждом выходе: обычном возврате и, если у исключения нет своих условий,
  на выходе исключением ([ниже](#выход-по-исключению-и-halt)). После вызова это известный факт.
- **`result`** — результат функции: в `ensures` и в посылке [условного владения](#условия-в--только-часть-типа);
  на выходе исключением его нет, и строки с `result` там не действуют.
- Имя параметра `mut` в `ensures` значит его значение на выходе: его видит вызывающий. Значение на входе —
  `previous(x)`. Так и для `x: mut Int`, и для поля: `account.balance` — баланс на выходе.
- Имя любого другого параметра на входе и на выходе значит одно и то же: функция его не меняет. Параметр `own`,
  который функция забирает, в `ensures` пишется только под `previous`, и с безусловным `take`, и с условным
  `{ … ==> take }`; без `previous` — ошибка.
- Условие не имеет побочных эффектов. Вызвать в условии можно функцию, которую компилятор признал чистой и
  завершающейся: обычную функцию с телом, без записи, без `halt()`, без признака «может провалить `assert`» ([тесты](tests/tests.md#assert)) и без исключений, в том числе неявных
  (все операции её тела доказаны определёнными), рекурсивную — только с доказанным `decreases`. Отдельного вида «функции только для условий» нет: функция без тела с `ensures` была бы аксиомой,
  а две несовместные аксиомы доказывают что угодно.
  Вызов функции, которая не чистая, — ошибка `efen.condition-call` у строки условия; она называет первую причину:
  `ratio` может бросить `DivisionByZeroError`, потому что FLOW не доказал `b != 0`; функция вызывает сама себя;
  вызывает `halt()`; пишет вне своих переменных; объявляет `throws` или параметр не `read`. Чаще всего у такой
  функции не хватает `requires`: с `requires b != 0` деление в `ratio` доказано, и функция чистая.

### `previous(x)`

`previous(x)` — значение выражения `x` на входе в функцию. Это то же слово, что у
[условия поля](shared.md#роли) `{ value >= previous }`: там голое `previous` — значение поля до записи, здесь
`previous(x)` — значение `x` до вызова.

- Всё выражение в скобках считается на входе: в `previous(cache.blocks[cache.count - 1])` и `blocks`,
  и `count` — входные. Имена, введённые в самом условии (переменная `forall`, `let` блока), сохраняют своё
  значение: в `forall i in 0 ..< n: a[i] == previous(a[i])` номер `i` тот же.
- Вложенный `previous`, `previous` в `requires` и `result` внутри `previous` — ошибки.
- У параметра `own`, который функция забрала, `previous(memory)` — значение, пришедшее на вход.
- В условии цикла `previous(x)` — тоже вход в функцию, а не в цикл. Значение на входе в цикл запоминается
  `let` перед циклом.
- Имя `previous` у локальной переменной не мешает: в условии `previous(` всегда означает вход.

### `let`, `forall` и импликация

- В блоке условия можно назвать значение:

```efen
    ensures {
        let before = previous(arena.bump)

        if before + size <= previous(arena.limit) {
            result != null
            arena.bump == before + size
        }
    }
```

- `forall i in 0 ..< n: …` — квантор по диапазону; `forall x in collection: …` — по элементам коллекции
  ([отношения в `layout`](#отношения-в-layout-класса)); `forall k: …` без `in` остаётся для отношений
  вроде `reachable`. Тело квантора тянется до конца условия.
- `a ==> b` — импликация «если `a`, то `b`». Приоритет у неё самый низкий в выражении условия:
  `a && b ==> c` значит `(a && b) ==> c`, `a ==> b && c` значит `a ==> (b && c)`, а
  `result != null || throws CopyError ==> take` — `(result != null || throws CopyError) ==> take`, как
  [условное владение](types/ownership.md#владение-которое-функция-забирает-не-всегда) и писалось. Цепочка
  `a ==> b ==> c` — ошибка. `==>` бывает только в условиях.

### Арифметика и частичные операции

Условие считается в тех же машинных типах, что и код: `Int` в условии — то же 64-битное `Int`. Компилятор обязан доказать, что каждая операция условия определена: не переполняется, не делит на
ноль, индекс в границах, `!` не от `null`. Что из этого не доказано, решается так:

- нарушение видно точно (`a / 0`, `Int.MAX + 1`, индекс за известной границей) — ошибка компиляции;
- FLOW не смог исключить нарушение — заметка в группе `Proof`, а условие проверяется при выполнении вместе с
  этой операцией: переполнение, деление на ноль или выход за границу во время проверки останавливает
  программу, как нарушенное условие ([ниже](#обычная-сборка-и-диагностики)). Сборка с решателем доказывает
  остальное; `-Werror Proof` делает такую заметку ошибкой.

У `assert` своё правило: неопределённая операция его условия при выполнении — провал этого `assert`, а не
остановка ([тесты](tests/tests.md#assert)).

Как это доказывается:

- слева направо и с коротким вычислением: правая часть `&&` — при истинной левой, `||` — при ложной, `==>` и
  `if` в блоке — при истинной посылке;
- из всех `requires` и строк выше в том же блоке;
- для `ensures` — ещё из фактов пути до возврата: если тело уже посчитало `balance + amount` без
  переполнения, то и `previous(account.balance) + amount` в `ensures` определено.

Поэтому порядок строк важен: `requires b != 0` должна стоять выше `requires a / b > 1`. Пример, где нужна
граница:

```efen
fn calloc(count: Int, size: Int) -> own Pointer?
    requires count >= 0 && size >= 0
    requires size == 0 || count <= MAX_RUN / size
    ensures result == null || result.size >= count * size
{
    // тело
}
```

Без второго `requires` произведение `count * size` в `ensures` могло бы переполниться: FLOW выдаст заметку
`Proof` и поставит проверку на возврате.

## Выход по исключению и `halt()`

Исключение — особый канал выполнения, и у него могут быть свои условия выхода.

- Без своих условий выход исключением обязан выполнить те же `ensures`, что и обычный возврат. Строки, которые
  называют `result`, к нему не относятся: результата нет.
- Свои условия для исключения `E` пишутся посылкой `ensures throws E ==> …`, как у
  [условного владения](types/ownership.md#владение-которое-функция-забирает-не-всегда). Если у `E` есть свои
  строки, на выходе исключением `E` действуют только они, а обычные `ensures` — нет.
- Своя строка исключения — та, у которой посылка верхнего уровня состоит только из членов `throws`:
  `throws E ==> …` или `(throws E || throws F) ==> …` — строка и для `E`, и для `F`. Посылка, где `throws`
  смешан с другим условием (`result != null || throws E ==> …`), — ошибка.
- Строка для класса действует и на его подклассы. Если подходят строки нескольких классов, действуют строки
  самого близкого из них, как выбирается `catch`.
- `E` — исключение из объявленного или выведенного списка `throws` функции, в том числе неявное
  (`OverflowError`).

```efen
fn deposit(account: mut Account, amount: Int)
    requires amount > 0
    ensures account.balance == previous(account.balance) + amount
    ensures throws OverflowError ==> account.balance == previous(account.balance)
{
    account.balance = account.balance + amount
}
```

Без последней строки `deposit` не доказать: на выходе `OverflowError` баланс прежний, а обычное `ensures`
требует, чтобы он вырос. Компилятор выдаст заметку `Proof`, и автор либо напишет условие для исключения, либо
увидит, что функция ведёт себя не так, как он думал.

```efen
fn transfer(from: mut Account, to: mut Account, amount: Int)
    requires amount > 0
    requires from.balance <= Account.LIMIT && to.balance <= Account.LIMIT
    ensures from.balance + to.balance == previous(from.balance + to.balance)
    ensures throws LimitError ==> from.balance == previous(from.balance) && to.balance == previous(to.balance)
{
    // тело
}
```

Второе `requires` нужно для суммы в `ensures`: без границ `from.balance + to.balance` могло бы переполниться,
а это ошибка ([выше](#арифметика-и-частичные-операции)); `Account.LIMIT` — такая константа, что `2 * LIMIT`
помещается в `Int`. Здесь у `LimitError` свои условия (ничего не изменилось), а для остальных исключений действует обычное
`ensures`: сумма на двух счетах сохраняется при любом выходе.

- Условия, которые их документ требует восстановить перед `throw`
  ([условия вида](memory/pointer.md#условия-вида), [инвариант](shared.md#инвариант)), действуют на любом выходе
  сверх этого.
- Путь через `halt()` в доказанное не входит: программа остановлена. Отчёт доказательства называет такие пути.
- На выходе по `AssertionError` `ensures` и строки с `result` не доказываются и не проверяются: в выпускной
  сборке этого пути нет. Остальные проверки выхода делаются и для него, в том числе для `AssertionError` из
  вызова; где не проходят, провал в этой точке останавливает программу, как `halt()`, и отчёт доказательства
  называет такие точки ([тесты](tests/tests.md#assert)).

## Генераторы

У генератора есть посылки `ensures yield ==>` (условие каждого отданного значения) и `requires resume ==>` (условие
значения, которое передаёт `next`), а в условиях — история `yielded` и `resumed`
([генераторы](generators.md#условия-генератора)).

## Функции без тела, контракты и интерфейсы

У метода `contract` или `interface` условия — обязательство реализации. Реализация может написать свои
условия, но её `requires` не сильнее, а `ensures` не слабее объявленных; без своих условий она получает условия
объявления. Вызывающий через интерфейс видит только условия интерфейса. Нарушение этого правила — ошибка, не
заметка; если компилятор не доказал, что `requires` реализации не сильнее, а `ensures` не слабее, это тоже
ошибка, даже когда так и есть: реализация пишет условия, для которых это видно, или не пишет своих.

```efen
contract System {
    const PAGE: Int

    fn map(bytes: Int, aligned: Int) -> own Pointer.Zeroed?
        requires PAGE > 0 && bytes % PAGE == 0
        ensures result == null || (result.size == bytes && result.alignment == aligned)

    fn unmap(memory: own Pointer, bytes: Int)
}
```

Без доказательства, на веру, компилятор принимает `ensures` только у `@abi(c)` без тела, у вставок `@asm` и у встроенных функций платформы
`@intrinsic` ([векторы std](types/simd.md#встроенные-функции-платформы)):
их кода он не читает ([system](memory/system.md#условия-результата--единственная-точка-доверия)). Писать их может
любой пакет ([кому доступно доверие](memory/system.md#кому-доступно-доверие)). Каждое такое
условие попадает в список доверия, который печатает сборка с доказательством.

## Рекурсия

Рекурсивная функция, которую нужно доказать завершающейся (например, её зовут из условия), пишет меру
`decreases` так же, как цикл. Недоказанная мера — заметка `Proof`, но такую функцию нельзя звать из
условия.

```efen
fn depth(node: Node?, fuel: Int) -> Int
    requires fuel >= 0
    decreases fuel
{
    // тело
}
```

## Циклы

Условия цикла стоят после заголовка, `{` тела — на своей строке.

```efen
var count = 0

while let block = take pool.firstFreeBlock
    invariant count <= pool.blocks
    decreases pool.blocks - count
{
    pool.firstFreeBlock = take block.next
    System.unmap(memory: block as Pointer, bytes: BLOCK)
    count = count + 1
}
```

- **`invariant`** верен перед каждой проверкой условия цикла (у `while let` — до `take`) и после выхода из
  цикла. У `repeat { } while c` условия стоят после `repeat`, и инвариант верен перед каждым проходом тела.
  У инварианта цикла нет имени: имя есть у объявления `invariant name { }` в `shared struct`, а условие цикла
  стоит только между заголовком и `{`.
- **`decreases`** — мера: целое неотрицательное, строго убывает за шаг. Без неё завершение не доказывается;
  безопасность проверяется независимо.
- У `for` по конечной коллекции, диапазону или конечной цепочке (`chained`) завершение компилятор выводит сам.
- Инварианты из условий вида и из границ компилятор выводит сам; руками пишется только остаток.

## Модель `model`

Модель — абстрактный код после сигнатуры функции: `model { … }`. Её не компилируют; FLOW читает её как сводку того,
что функция кладёт в поля `layout` и что с них снимает. Сами поля и всё остальное о памяти объявляет `layout` типа
([`layout` в теле класса](memory/addresses.md#layout-в-теле-класса)); модель только пишет в них.

```efen
mut fn sqlite3_bind_text(index: Int32, text: read CString, length: Int32,
                         destructor: sqlite3_destructor_type) -> Int32
model { if destructor == SQLITE_STATIC { self.bound[index] = text } else { self.bound.remove(index) } }
```

- **Место.** После хвоста сигнатуры и после `requires`/`ensures`, перед телом, если оно есть. Модель бывает у
  внешних функций и методов (`@abi(c)`, `@asm`, `@intrinsic`, функции бинарного пакета), у методов контрактов и
  интерфейсов и у любой функции с телом. У литерала замыкания, типа функции и генератора модели нет.
- **Содержимое — закрытый список.** Параметры, `self`, `result` (состояние после вызова), поля `layout` и настоящие
  поля `self` и параметров; `if`, `if let`, `match` по параметру или `result`; `==` и `!=` с константой или `null`;
  `=` в поле `layout`; `take` параметра `own` в поле; на абстрактных коллекциях `[k] = v`, `remove(k)`, `clear()`,
  `append(v)`, `remove(v)`. Проекции (`name.cString`, путь по полям, `.values`, `[k]` у настоящей коллекции) вызовами
  не считаются. Других вызовов, циклов и арифметики в модели нет.
- **Проверка модели.** Права: удержание не шире права параметра. Владение: параметр забирается ровно на путях его
  посылки, безусловный `own` — на каждом пути. Живость: в поле кладут параметр или путь через него, никогда
  временное значение. Сравнение с константой решается, только когда аргумент — эта константа; макрос C без
  параметров переносится как `const` типа указателя ([библиотеки на C](foreign.md#что-amber-переносит-сам)).
- **Модель и тело.** Тело держит не больше модели: ничего сверх неё, не дольше, не с более широким правом, и не
  снимает того, что модель держит. Модель уже тела — ошибка; модель шире тела — предупреждение с названием лишнего
  удержания.
- **Умолчания.** Функция без модели и без тела после вызова ничего не держит. У функции с телом и без модели сводку
  выводит компилятор и кладёт в заголовки пакета. Чего модель не называет, то не меняется: удержания остаются.
  Снятие пишется явно, под тем условием, при котором внешняя сторона действительно отпускает.
- **Исключение.** Внешняя функция исключений не бросает. Модель функции Efen описывает обычный возврат; при
  `throws E` новых удержаний нет, если посылка параметра не называет `throws E ==> take`.

Модели функции без тела компилятор верит, как её `ensures`: она попадает в список доверия
([кому доступно доверие](memory/system.md#кому-доступно-доверие)), а проверочная сборка сверяет с ней поведение
внешней стороны, когда может. Модель метода контракта или интерфейса — сводка каждого вызова через него; каждая
реализация проверяется там, где написана ([контракты](contracts.md#layout-и-модель-в-контракте)).

### Удержания

Удержание — то, что модель записала в поле `layout`: слот аргумента, сведённый к корню и пути (`name.cString` держит
`name`; `row` цикла `for row in rows` держит `rows[i]` с корнем `rows`), зависимость от внешнего объекта за аргументом
класса над внешним значением или значение `own`. Удержание живёт, пока его не снимут (перезапись, `remove`,
`clear`, `null`), или пока объект не уничтожен. Использование удержанного не моделируется.

- **Синхронный режим** — по умолчанию: внешняя сторона трогает удержанное только во время вызовов с объектом.
  Пока объект держит слот `read` или `edit`, владелец слота читает его и пишет значения, но не меняет структуру,
  не перемещает, не уничтожает и не отдаёт — как при ссылке внутри функции
  ([что ссылке можно и нельзя](types/ownership.md#что-ссылке-можно-и-нельзя)). При зависимости `mut U` или
  `read U` владелец `U` вызывает всё, кроме уничтожения и передачи.
- **Параллельный режим.** Держатель, который попал в тело многопоточной корутины (`capture … = take` или
  заимствованное имя), в тело `offload`, в поле `shared` или в объект `shared layout`, везёт туда удержания: каждое
  становится областью доступа этого режима с правом удержания (`read`, `edit`; `mut U` — вызовы с `U`), и до конца
  режима или снятия удержания действует таблица многопоточного вида
  ([корутины `spawn`](types/access-regions.md#корутины-spawn), [общая память](shared.md#пометка-shared)).
- **Ссылки умирают.** Вызов с правом `mut` убивает каждую ссылку с источником в объекте и в каждом объекте,
  достижимом через поля `layout` с правом `mut`: `read<db.errmsg>` умирает на `s.sqlite3_step()`, потому что `s.db` —
  `mut sqlite3`. Вызов `read` не убивает ничего.
- **Сильное и слабое обновление.** `obj.field = v` у параметра и `self` заменяет прежнее удержание. У абстрактного
  словаря запись сильная при ключе, равном константе при сборке, иначе слабая: прежнее удержание остаётся.
  `remove(k)` с неизвестным `k` ничего не снимает, `clear()` снимает всё. `null` в элемент неoptional-типа — ошибка.
- **Живость.** Слот, область которого кончается, пока его держит живой объект, — ошибка с именем держателя и вызова,
  который положил удержание. Удержания едут с объектом: `take`, `capture … = take`, запись в поле или контейнер,
  передача в функцию.
- **Держатель.** Удержание лежит только на объекте, слот которого видит FLOW: локальная переменная, параметр, поле
  `own` или элемент, достижимые из них через обычные слоты. Держатель в `managed`-слоте (поле класса со счётчиком,
  элемент коллекции внутри него) при записи и на каждом выходе метода этого класса держит только внешние объекты,
  названные отношением `layout` класса; удержаний слотов Efen на нём нет. Сам `managed`-слот удержать нельзя.
- **Настоящие поля.** Модель, которая называет настоящее поле параметра или `self` (`pool.items.append(take s)`,
  `self.cache[sql].bound[1] = name.cString`), переносит удержание на этот объект. Удержание из параметра в `self`
  допустимо: это сводка метода, и вызывающий отвечает за то, чтобы слот жил не меньше `self`.
- **Контейнер держателей** с одним владельцем держит объединение удержаний своих элементов. Удаление элемента
  снимает их слабо; `removeAll()`, уничтожение контейнера и доказанный факт `count == 0` (из `ensures` коллекции,
  например `removeLast`) — сильно.
- **Результат-держатель.** `-> own sqlite3_stmt?` с `model { if let r = result { r.bound[1] = name.cString } }`
  держит `name`; голое `result.bound` у возможно пустого результата — ошибка.
- **Значение-функция.** Функция или замыкание, модель или сводка которой кладёт удержание между параметрами или из
  параметра в результат, не подходит ни к одному типу функции
  ([тип функции](types/function-type.md#ссылка-в-результате-типа-функции)).

```efen
class Pool { var items: Vector<own sqlite3_stmt> }

fn park(pool: mut Pool, s: own sqlite3_stmt)
model { pool.items.append(take s) }              // удержания s переходят к pool
{
    pool.items.append(take s)
}
```

### Отношения в `layout` класса

Строка условия в `layout` класса связывает его настоящие поля с полями `layout` элементов:
`forall s in cache.values: s.db == db`. Отношение пишет любой класс с настоящими полями. У класса со счётчиком
строк `var` в `layout` нет, но отношение есть: держатель в его `managed`-слоте держит только внешние объекты, которые
отношение называет ([удержания](#удержания)). Отношение проверяется на каждой записи любого поля, которое оно называет,
настоящего или поля `layout`, по любому пути от `self`, включая записи, которые делает модель вызванной функции:

- вставка в `cache` доказывает `s.db == db` по происхождению элемента: его `db` записала модель
  `sqlite3_prepare_v2` из того же `db`;
- модель, которая пишет `e.multi` у элемента, достижимого через `easies`, обязана заново доказать отношение;
- заменить, забрать `take` или отдать `db`, пока не доказано, что `cache` пуст, — ошибка;
- порядок уничтожения полей следует из отношения: `cache` раньше `db`
  ([порядок уничтожения](memory/addresses.md#layout-в-теле-класса)).

Связанное поле можно передать функции (`mut self.cache`), если её модель или сводка не добавляет элемент и не пишет
связанное поле `layout`; иначе ошибка называет отношение. Это правило условия поля
([ниже](#условия-в--только-часть-типа)) для отношений.

```efen
class Connection {
    var db: own sqlite3
    var cache: Dictionary<String, own sqlite3_stmt>
    layout { forall s in cache.values: s.db == db }

    mut fn evict(sql: read String) { cache.remove(sql) }   // удаление сохраняет forall
    mut fn reopen(path: read CString) {
        cache.removeAll()                                  // сильное обновление: cache пуст
        var fresh: sqlite3? = null
        let rc = sqlite3.sqlite3_open(filename: path, self: fresh)
        guard let d = fresh, rc == SQLITE_OK else { return }
        db = take d                                        // можно: cache доказанно пуст
    }
}
```

## Условия в `{}`: только часть типа

Условия функции пишутся только `requires` и `ensures`. Блок `{}` у параметра или результата остаётся там, где это часть типа:

- **условное владение** `own T? { посылка ==> take }`: функция забирает значение тогда и только тогда, когда
  посылка верна ([владение](types/ownership.md#владение-которое-функция-забирает-не-всегда)). В `ensures` это
  стало бы импликацией, и реализация интерфейса, которая забирает значение всегда, стала бы законной;
- **уточнение типа элемента** в типе коллекции: `[Int { value > 0 }]` — массив положительных чисел, как
  [уточняющий тип](types/refinement-types.md) без имени;
- **условие случая варианта** у результата: `-> MapResult { mapped: memory.size == bytes }`
  ([system](memory/system.md)) — условие на данные случая, которые в `ensures` назвать нечем;
- **условная запись выходного слота** `self { посылка ==> out }` и `p: out T { посылка ==> out }`: внешняя функция
  пишет слот ровно на путях посылки, на остальных он не записан; и проверяемый слот `self?`, который функция
  пишет на каждом возврате ([конструкторы внешнего объекта](classes.md#конструкторы-внешнего-объекта));
- **условное владение получателем** `own fn m(self { посылка ==> take })`.

Признак один: `{}` прямо за типом параметра или результата функции — ошибка с исправлением на
`requires`/`ensures`, кроме форм выше (`==> take` и `==> out` в посылке, `{}` внутри `[ ]`, `случай:` у варианта).

| Было | Стало |
|---|---|
| `index: Int { value >= 0 && value < CLASSES }` | `requires index >= 0 && index < CLASSES` |
| `block: mut SlotBlock { used > 0 }` | `requires block.used > 0` |
| `-> own Pointer? { size >= size }` | `ensures result == null \|\| result.size >= size` |
| `data: read [T] { count == n }` | `requires data.count == n` |
| `memory: own Pointer? { result != null ==> take }` | без изменений |

`{}` после типа данных — свойство самого типа, как и было: `type Nat: Int { value >= 0 }`, условие поля
`var length: Size = 0 { value == Items.count }`, условия вида после `struct`.

**Условие поля держит каждая запись.** Компилятор доказывает условие поля в каждой записи: в присваивании, в
конструкторе, в значении по умолчанию. Поле можно отдать функции на чтение. Параметром `mut` его можно отдать только
функции, которая обещает то же условие в `ensures`: тогда его доказывают её выходы. Пишущую ссылку `&` на такое
поле взять нельзя: запись через неё никто не проверит. Остальное — ошибка:

```efen
struct Pool {
    var blocks: Int = 0 { value >= 0 }
}

fn setTo(value: mut Int) { value = -5 }

fn setWithin(value: mut Int)
    ensures value >= 0
{
    value = 5
}

fn lend(pool: mut Pool) {
    setTo(value: pool.blocks)      // ошибка: setTo не обещает value >= 0
    setWithin(value: pool.blocks)  // можно
}
```

**Состояние типа.** `requires x is State` по оси [typestate](types/typestate.md) — требование состояния, его
проверяет typestate, и нарушение — всегда ошибка, не заметка:

```efen
fn release(pool: mut Pool, connection: own Connection)
    requires pool.mutex is Mutex.Free
{
    // тело
}
```

Стиль: свойство одного значения, которое нужно многим функциям, — тип
(`type Slot: Int { value >= 0 && value < CAPACITY }`); связь параметров и выход — `requires`/`ensures`.
`ensures`, который пересказывает тело, не пишется: компилятор выведет его сам.

## Что выводится само

Писать не нужно:

- что функция читает и меняет. Слова `reads`, `modifies`, `creates`, `removes` и `opens` проекта Viper в язык
  не входят;
- учёт взятых и возвращённых мест: Δ`used` и `taken` ([pointer](memory/pointer.md#учёт-на-выходе-функции));
- условия вида и инварианты, которые их документы требуют восстановить;
- инварианты циклов из условий вида и границ;
- для не публичной и не рекурсивной функции без `ensures` — её сводку из тела. Явное `ensures` главнее
  выведенного: правка тела не меняет доказательство у вызывающих, пока `ensures` верно. Отчёт
  `amber prove --explain` печатает выведенные сводки и тела, от которых зависит каждое доказательство.
  У публичной функции сводка не выводится: вызывающий из другого пакета видит только её условия.
- для закрытой функции — не публичной, вызываемой только прямо, не значением и не из `spawn` — факты на входе
  о её целых параметрах из всех мест вызова, как в Goose: на входе верно то, что доказал каждый вызов (Amber S95). Эти факты только снимают проверки при выполнении; принята ли программа, решается без них.
  Контракт открытой или экспортируемой функции — по-прежнему её `requires`.

  ```efen
  const SIZES: [Int] = [16, 32, 64, 128]

  fn sizeOf(index: Int) -> Int {
      return SIZES[index]  // оба вызова передают 0 и 3: проверки индекса нет
  }

  fn smallest -> Int {
      return sizeOf(0)
  }

  fn largest -> Int {
      return sizeOf(3)
  }
  ```

## `assume`: факт без доказательства

Иногда условие верно по причине, которой компилятор не видит. Счётчик блоков растёт на один с каждым блоком, который
выдала система, а адресов меньше 2⁴⁸ блоков по 64 КБ, поэтому `blocks + 1` не переполнится. FLOW этой связи не знает
и оставляет у сложения выход по `OverflowError`. Строка `assume` говорит компилятору принять условие без
доказательства:

```efen
const MAX_BLOCKS = 1 << 48

fn growPool(pool: mut Pool) -> Bool {
    guard let memory = System.map(bytes: REGION_BLOCKS * BLOCK, aligned: BLOCK) else {
        return false
    }

    let region: Blocks.Area { value.count == REGION_BLOCKS } = memory as Blocks.Area
    for element in take region {
        pool.firstFreeBlock = newFreeBlock(memory: take element, next: take pool.firstFreeBlock)
        assume pool.blocks < MAX_BLOCKS && pool.pooled < MAX_BLOCKS
        pool.blocks = pool.blocks + 1      // доказано: переполнения нет
        pool.pooled = pool.pooled + 1
    }
    return true
}
```

- `assume` — инструкция тела функции, как `guard`. После неё условие — факт, пока не изменится место, которое оно
  читает: `pool.blocks = pool.blocks + 1` меняет `pool.blocks`, и дальше факт о нём держится только тот, что FLOW
  выведет сам (`pool.blocks <= MAX_BLOCKS`).
- Компилятор условие не проверяет и не вычисляет: в программе на его месте нет ни одной инструкции. Ложное
  условие ломает то, что на нём доказано: проверка, которую оно сняло, не стоит, и сложение, переполнения которого
  «нет», заворачивается молча.
- Строка `assume` — точка доверия, как `@asm`: пакет с ней становится рискованным, `efen proofs` показывает её
  строкой `trust` ([кому доступно доверие](memory/system.md#кому-доступно-доверие)).
- Факт ставят точечно, рядом с операцией, которой он нужен. Условие поля в `layout` или `requires` с `assume` не
  пишут: такое условие действовало бы на каждую запись поля во всей программе, и ошибку в любой из них компилятор
  принял бы молча.
- Условие — сравнения, `&&`, `||` и `!` над параметрами, полями, локальными значениями и константами. Арифметика в
  нём — ошибка компиляции: условие не вычисляется, и у `a + b` в нём не было бы ни машинного смысла с переполнением,
  ни проверки. Границу пишут константой: `1 << 48` — значение `MAX_BLOCKS`, а не выражение в строке.

## Обычная сборка и диагностики

- FLOW доказывает `requires` в точке вызова и `ensures` на возврате, где может. Остальное доказывает сборка с
  решателем (Amber S87).
- Недоказанное условие не останавливает сборку: компилятор выдаёт заметку в группе `Proof`. Отчёт доказательства отмечает каждый вывод, который держится на недоказанном условии.
- Недоказанное условие не считается фактом для безопасности. Как именно:
  - проверку ставит та сторона, которая должна доказательство. Недоказанный `requires` проверяется целиком в
    точке вызова, недоказанный `ensures` — на возврате. Вызываемая функция всегда полагается на свой
    `requires`, вызывающий — на `ensures`: при раздельной сборке функция не знает, доказали ли условие все,
    кто её вызывает;
  - функцию `@abi(c)` с телом вызывает C, который ничего не доказывает, поэтому её `requires` проверяется на входе,
    до тела, в каждой сборке, а заметка `Proof` стоит у самой функции;
  - при выполнении проверяемы: сравнения и арифметика над параметрами, полями и `result`; `forall i in a ..< b`;
    вызовы чистых функций; `previous(x)`, где `x` — значение или поле: компилятор снимает его на входе, как у
    [проверочной сборки C](foreign.md). Строка `ensures throws E ==> …` проверяется в точке выхода
    исключением;
  - остальное (`forall k:` без `in`, `reachable`, `chained`, `previous` от составного значения) не проверяется
    при выполнении. Такое условие остаётся заметкой `efen.unchecked` группы `Proof` с причиной, а проверка,
    которую оно сняло бы, не снимается: `SIZES[index]` проверяет границу, как без условия. `efen proofs` пишет
    такую строку итогом `unchecked`, один раз у самой строки условия. Строку с `==>` программа проверяет как
    `!a || b`: заключение читается, только когда посылка верна. Вызов функции в строке, с метками аргументов или
    без, проверка делает так же, как строка: функция чистая, поэтому вызов ничего не меняет и не бросает;
  - нарушение останавливает программу, как `halt()`, с сообщением, какое условие и где нарушено: это ошибка
    программы, а не исключение, которое ловят.
  Условие, которое доказано, проверок не порождает. Требование состояния `requires x is State` сюда не
  относится: его проверяет typestate, и недоказанное — ошибка ([выше](#условия-в--только-часть-типа)).
- `efen proofs` перечисляет проверки по файлам и функциям. У каждой — место, вид, итог и способ: `proved` с видами
  рассуждения, без которых доказательство пропадает (`FLOW::linear`, `Z3::<алгоритм>`), или `checked` — программа
  проверяет это при выполнении. Под доказанной проверкой — строки `assume`, на которых она держится, и строки
  `requires` вызванной функции, которые FLOW не доказал у какого-то её вызова: у такой строки пишется
  `unproved at 12:20` — вызов, где она проверяется при выполнении. Так же — строки `ensures`, которые функция
  не доказала на выходе: выход их проверяет, и вызывающий берёт их фактом о результате. У такой строки
  `unproved at` — этот выход. Пока FLOW берёт такой факт, только когда результат привязан к `let`. Под
  недоказанной — чего условия программы не называют о величинах этой проверки. Это факты о программе, а не совет,
  что дописать. Место факта — справа:

  ```text
  main.efen
    fn ratio    line 1
       3:18  overflow  proved    FLOW::linear
       3:18  zero      proved    FLOW::linear
    fn sum      line 8
      12:23  overflow  checked   run-time check
                       `total` changes in the loop                11:5
                       `i` changes in the loop                    11:5
      13:15  overflow  proved    FLOW::linear
    fn main     line 18
      19:31  overflow  checked   run-time check
                       `ratio()` states nothing about its result  1:1
                       `sum()` states nothing about its result    8:1
  5 checks: 3 proved (FLOW::linear 3), 2 checked
  ```

  Видов фактов пять: параметр, которого не называет ни одна строка `requires` его функции; результат вызова, о
  котором функция не говорит в `ensures`; поле без условия; значение функции, которой сборка верит (`@asm`,
  функция C); переменная, которую меняет цикл вокруг проверки. Величина прослеживается через арифметику и `let` до
  одного из этих источников. `--unproved` оставляет только `checked` и места доверия, `--flat` пишет строку на
  проверку (`main.efen:13:15 overflow proved FLOW::linear`), `--json` — тот же список одним объектом: `version`,
  `files` → `functions` → `checks` с полями `at`, `kind`, `result`, `by`, `kept`, `rests`, `facts`, и `summary`;
  каждое место в нём — `at: {file, line, column}`, у строки `requires` в `rests` — ещё `unproved`, список таких мест.

  Ошибка FLOW не прячет список. Функция, на которой сборка остановилась, стоит строкой `not built` с первой
  ошибкой, и её проверки не перечислены. Ошибка об условии без проверки при выполнении (условие вида, приведение,
  заём, состояние) — отдельная строка `error`. Остальные функции перечислены как обычно. Недоказанное `requires`,
  `ensures` или условие поля, поднятое до ошибки (`-Werror Proof`), — тоже `error`. Ошибка читателя или плагина
  оставляет только диагностики.
- Заметку группы `Proof` поднимают до предупреждения или ошибки флагами
  [групп диагностик](diagnostic-groups.md#управление-через-флаги) или в конфигурации сборки.
- Условие, которое решатель опроверг, — ошибка с контрпримером: значения параметров, на которых оно ложно.
- Неопределённая операция в условии (переполнение, деление на ноль, индекс вне границ) — ошибка, только когда
  нарушение видно точно; если FLOW не смог её исключить — заметка `Proof` и проверка при выполнении ([Арифметика](#арифметика-и-частичные-операции)).
- У `assert` эти два пункта свои: в обычном коде ошибка — только `assert`, ложный или неопределённый на каждом пути
  ([тесты](tests/tests.md#assert)).

## Граница

`requires`/`ensures` описывают один вызов в одном потоке. Структура, которую меняют два потока без блокировки
(кольцо писателя и читателя), описывается [ролями и инвариантами](shared.md#роли), а не условиями функции.
Замыкания в условиях и условия у параметра-функции в первой версии не поддерживаются.
