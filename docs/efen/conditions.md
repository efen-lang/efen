# Условия функций и циклов

[Документация](README.md) · [Словарь](glossary.md) · [Функции](functions.md) · [Операторы](operators.md)

Функция объявляет, что она требует от вызывающего (`requires`) и что гарантирует после возврата (`ensures`).
Цикл объявляет, что верно на каждом шаге (`invariant`) и почему он кончится (`decreases`). Компилятор
доказывает условия; что он может вывести из кода сам, писать не нужно.

Форма `requires`/`ensures` после сигнатуры;
`previous(x)` вместо `old(x)`; у функции нет ни одного `{}`, кроме тела: её условия — только `requires` и
`ensures`; недоказанное условие — заметка, а безопасность, которая держалась бы на нём, проверяется при выполнении; переполнение в
условии — ошибка, когда оно видно точно, иначе заметка и проверка ([арифметика](#арифметика-и-частичные-операции)).

## Форма

```efen
fn withdraw(account: mut Account, amount: Int) -> Int
    requires amount > 0
    requires account.balance >= amount
    ensures account.balance == previous(account.balance) - amount
    ensures result == account.balance
{
    account.balance = account.balance - amount
    return account.balance
}
```

- Условия идут после сигнатуры, каждое с новой строки, с отступом на один уровень. Порядок хвоста сигнатуры: `state`, `in`, `throws` — каждый, если есть;
  затем все `requires`, затем все `ensures`, затем `decreases`, затем [`model`](models.md#модель-model).
- Если у функции есть условия, `{` тела стоит на отдельной строке без отступа. Без условий `{` пишется как
  обычно, в конце сигнатуры; строка `throws` при этом может стоять отдельно.
- Условия видят все параметры, и те, что объявлены `param` и `generic` в начале тела: обе формы — одна модель
  параметров ([функции](functions.md)), и строка `param` — часть сигнатуры, записанная в теле:

```efen
fn tryExtendInPlace -> Bool
    requires oldSize >= 0 && newSize >= 0
    requires p >= 0 && p <= arena.limit && newSize <= arena.limit - p
    ensures result ==> arena.bump == p + newSize
{
    param arena: mut Arena
    param p: Int
    param oldSize: Int
    param newSize: Int

    // тело
}
```

  У объявления без тела (`contract`, `interface`, `@abi(c)`) места для `param` нет, поэтому правило
  [`S.function-parameter-layout`](diagnostic-groups.md#style-diagnostics-s) на него не действует.
- Условие кончается переводом строки вне скобок. Длинное условие пишется блоком:

```efen
fn relinkBlock(pool: mut Pool, index: Int, block: mut SlotBlock)
    requires {
        index >= 0 && index < CLASSES
        block.used > 0
        !block.linked
    }
    ensures block.linked
{
    // тело
}
```

  Это блок условий, как [`invariants`](#условия-значений-и-invariants) у типа: каждая строка — отдельное
  условие, строки соединяются `&&`, `if` внутри означает импликацию. Это не выражение-блок: его
  значение — не последняя строка.
- Условие продолжается на следующей строке, если та начинается с бинарного оператора (`==>`, `&&`, `||`) или
  перенос стоит внутри скобок. Это правило одно для строки `requires`/`ensures` и для строки блока.
- Несколько `requires` соединяются `&&`, несколько `ensures` — тоже.
- `requires`, `ensures`, `invariant`, `invariants`, `decreases`, `forall`, `previous`, `taken` и `written` —
  контекстные слова: особые
  только в условиях. Особое имя `result` в условиях — результат; параметр с именем `result` у функции с
  `ensures` — ошибка.
- В методе имена в условиях разрешаются так же, как в теле: поле получателя пишется без `self`, если тело так
  может.

## Смысл

- **`requires`** доказывает вызывающий код в каждой точке вызова. Внутри функции это известный факт, даже если
  у какого-то вызывающего он не доказан: тогда его проверяет точка вызова
  ([ниже](#обычная-сборка-и-диагностики)).
- **`ensures`** доказывает функция на каждом выходе: обычном возврате и, если у исключения нет своих условий,
  на выходе исключением ([ниже](#выход-по-исключению-и-halt)). После вызова это известный факт.
- **`result`** — результат функции, в `ensures`; на выходе исключением его нет, и строки с `result` там не действуют.
- Имя параметра `mut` в `ensures` значит его значение на выходе: его видит вызывающий. Значение на входе —
  `previous(x)`. Так и для `x: mut Int`, и для поля: `account.balance` — баланс на выходе.
- Имя любого другого параметра на входе и на выходе значит одно и то же: функция его не меняет. Параметр `own`,
  который функция забирает, всегда или по строке `ensures taken(x) == (…)`, в `ensures` пишется только под
  `previous` или в `taken(x)`; иначе — ошибка.
- Условие не имеет побочных эффектов. Вызвать в условии можно функцию, чистую [по виду кода](#вызов-функции-в-условии).

### Вызов функции в условии

Чистота решается по виду кода, а не по тому, что доказал FLOW: программа, которая собирается сегодня, не перестаёт
собираться, когда FLOW докажет меньше. Чистая функция:

- обычная функция с телом: функция без тела с `ensures` была бы аксиомой, а две несовместные аксиомы доказывают
  что угодно, поэтому отдельного вида «функции только для условий» нет;
- не пишет вне своих переменных, все параметры `read`;
- без `halt()`, инструкции `throw`, объявленного `throws` и признака «может провалить `assert`»
  ([тесты](tests/tests.md#assert));
- рекурсивная — только с `decreases`.

Вызов функции, которая не чистая, — ошибка `efen.condition-call` у строки условия; она называет первую причину:
функция вызывает сама себя без `decreases`, вызывает `halt()`, пишет вне своих переменных, содержит `throw`,
объявляет `throws` или параметр не `read`. Неявное исключение операции (`OverflowError` у сложения, которое FLOW не
доказал) причиной не бывает: от силы FLOW ответ не зависит.

Функция, которую вызывает условие значения `{ }` или [уточняющий тип](types/refinement-types.md), сверх этого читает
только свои параметры и константы: такое условие проверяется только на записи значения, и чтение `static var`
сделало бы его ложным без единой записи.

Операция тела, которая может быть не определена (деление, сложение), чистоту не отменяет: её охраняет `requires`
вызванной функции. Вызов в условии доказывает этот `requires`, как любой вызов:

```efen
fn ratio(a: Int, b: Int) -> Int
    requires b != 0
{
    return a / b
}

fn pick(x: Int, y: Int) -> Int
    requires y != 0
    requires ratio(a: x, b: y) > 1
{
    // тело
}
```

- Строка `requires y != 0` стоит выше и доказывает `requires b != 0` у вызова `ratio`.
- Без неё компилятор выдаёт заметку `Proof` у вызова, а проверка строки `pick` при выполнении сначала проверяет
  `b != 0`: нарушение кончается так же, как нарушение строки, ради которой идёт проверка. Сам компилятор недостающую строку в условия
  `pick` не добавляет: требования функции пишет её автор.
- `requires` вызванной функции доказывают строки, проверенные раньше этой: у строки `requires` — строки `requires`
  выше неё; у строки `ensures` — строки `requires`, которые не называют ни параметр `mut`, `edit` или `own`, ни
  `self`, который функция меняет, и строки `ensures` выше неё, которые проверяются на тех же выходах.
- Операция тела, которую `requires` вызванной функции не охраняет, — тоже заметка `Proof` и проверка при выполнении,
  как такая же операция в самом условии ([арифметика](#арифметика-и-частичные-операции)): исключение такой операции
  останавливает программу, а в записи — место и текст строки условия и слова `a function it calls threw`.
- Чтобы доказать строку, FLOW читает вызванную функцию: подставляет её тело на один уровень или берёт её `ensures`.

### `previous(x)`

`previous(x)` — значение выражения `x` до проверяемого шага. Шаг задаёт условие:

- у `ensures` шаг — весь вызов: `previous(x)` — значение на входе в функцию;
- у условия значения `{ }` шаг — одна запись: `var head: AtomicInt = AtomicInt(0) { value >= previous(value) }` —
  значение `head` до этой записи. У первой записи (при создании) прошлого значения нет, и строка с `previous` тогда
  не проверяется;
- в `invariants` шаг — от входа открытого метода до точки восстановления: `previous(x)` — значение на входе в метод.
  Строка с `previous` на входе метода фактом не считается и при создании значения не проверяется;
- в условии цикла шаг — итерация: `previous(x)` — значение до этой итерации, то есть на прошлой проверке условия.

Голого `previous` без скобок нет.

- Всё выражение в скобках считается до шага: в `previous(cache.blocks[cache.count - 1])` у `ensures` и `blocks`,
  и `count` — входные. Имена, введённые в самом условии (переменная `forall`, `let` блока), сохраняют своё
  значение: в `forall i in 0 ..< n: a[i] == previous(a[i])` номер `i` тот же.
- Вложенный `previous`, `previous` в `requires` и `result` внутри `previous` — ошибки.
- У параметра `own`, который функция забрала, `previous(memory)` — значение, пришедшее на вход.
- Значение на входе в функцию или в цикл, нужное в условии цикла, запоминается `let` перед циклом:

```efen
let start = total
var i = 0
while i < items.count
    invariant total == start + (sum j in 0 ..< i: items[j].price)
    invariant total >= previous(total)          // не уменьшается за итерацию
{
    total += items[i].price
    i += 1
}
```
- Имя `previous` у локальной переменной не мешает: в условии `previous(` всегда означает значение до шага.

### `let`, `forall` и импликация

- В блоке условия можно назвать значение:

```efen
    ensures {
        let before = previous(arena.bump)

        if before + size <= previous(arena.limit) {
            result != null
            arena.bump == before + size
        }
    }
```

- `forall i in 0 ..< n: …` — квантор по диапазону; `forall x in collection: …` — по элементам коллекции
  ([отношения класса](models.md#отношения-в-invariants-класса)). Домен всегда конечный: `forall k: …` без `in` — ошибка.
  Тело квантора тянется до конца условия.
- `a ==> b` — импликация «если `a`, то `b`». Приоритет у неё самый низкий в выражении условия:
  `a && b ==> c` значит `(a && b) ==> c`, `a ==> b && c` значит `a ==> (b && c)`, а
  `result != null || throws CopyError ==> …` — `(result != null || throws CopyError) ==> …`. Цепочка
  `a ==> b ==> c` — ошибка. `==>` бывает только в условиях. Внутри операнда `==>` условный оператор, `=>` и `|>`
пишутся только в скобках: `a ==> (b ? c : d)`.
- `sum i in D: e` и `product i in D: e` — сумма и произведение выражения `e` по домену `D`; домен и тело — как у
  `forall`. Пустой домен даёт 0 и 1. Считаются в типе тела, как любая операция условия: переполнение доказывается
  ([ниже](#арифметика-и-частичные-операции)). Часть элементов — через `if` в теле:
  `sum i in items.indices: if items[i].paid { items[i].price } else { 0 }`.

### Арифметика и частичные операции

Условие считается в тех же машинных типах, что и код: `Int` в условии — то же 64-битное `Int`. Компилятор обязан доказать, что каждая операция условия определена: не переполняется, не делит на
ноль, индекс в границах, `!` не от `null`. Что из этого не доказано, решается так:

- нарушение видно точно (`a / 0`, `Int.MAX + 1`, индекс за известной границей) — ошибка компиляции;
- FLOW не смог исключить нарушение — заметка в группе `Proof`, а условие проверяется при выполнении вместе с
  этой операцией: переполнение, деление на ноль или выход за границу во время проверки останавливает
  программу, как нарушенное условие ([ниже](#обычная-сборка-и-диагностики)). Сборка с решателем доказывает
  остальное; `-Werror Proof` делает такую заметку ошибкой.

У `assert` своё правило: неопределённая операция его условия при выполнении — провал этого `assert`, а не
остановка ([тесты](tests/tests.md#assert)).

Как это доказывается:

- слева направо и с коротким вычислением: правая часть `&&` — при истинной левой, `||` — при ложной, `==>` и
  `if` в блоке — при истинной посылке;
- из всех `requires` и строк выше в том же блоке;
- для `ensures` — ещё из фактов пути до возврата: если тело уже посчитало `balance + amount` без
  переполнения, то и `previous(account.balance) + amount` в `ensures` определено.

Поэтому порядок строк важен: `requires b != 0` должна стоять выше `requires a / b > 1`. Пример, где нужна
граница:

```efen
fn calloc(count: Int, size: Int) -> own Pointer?
    requires count >= 0 && size >= 0
    requires size == 0 || count <= MAX_RUN / size
    ensures result == null || result.size >= count * size
{
    // тело
}
```

Без второго `requires` произведение `count * size` в `ensures` могло бы переполниться: FLOW выдаст заметку
`Proof` и поставит проверку на возврате.

## Выход по исключению и `halt()`

Исключение — особый канал выполнения, и у него могут быть свои условия выхода.

- Без своих условий выход исключением обязан выполнить те же `ensures`, что и обычный возврат. Строки, которые
  называют `result`, к нему не относятся: результата нет.
- Свои условия для исключения `E` пишутся посылкой `ensures throws E ==> …`. Если у `E` есть свои
  строки, на выходе исключением `E` действуют только они, а обычные `ensures` — нет.
- Своя строка исключения — та, у которой посылка верхнего уровня состоит только из членов `throws`:
  `throws E ==> …` или `(throws E || throws F) ==> …` — строка и для `E`, и для `F`. Посылка, где `throws`
  смешан с другим условием (`result != null || throws E ==> …`), — ошибка.
- Строка для класса действует и на его подклассы. Если подходят строки нескольких классов, действуют строки
  самого близкого из них, как выбирается `catch`.
- `E` — исключение из объявленного или выведенного списка `throws` функции, в том числе неявное
  (`OverflowError`).

```efen
fn deposit(account: mut Account, amount: Int)
    requires amount > 0
    ensures account.balance == previous(account.balance) + amount
    ensures throws OverflowError ==> account.balance == previous(account.balance)
{
    account.balance = account.balance + amount
}
```

Без последней строки `deposit` не доказать: на выходе `OverflowError` баланс прежний, а обычное `ensures`
требует, чтобы он вырос. Компилятор выдаст заметку `Proof`, и автор либо напишет условие для исключения, либо
увидит, что функция ведёт себя не так, как он думал.

```efen
fn transfer(from: mut Account, to: mut Account, amount: Int)
    requires amount > 0
    requires from.balance <= Account.LIMIT && to.balance <= Account.LIMIT
    ensures from.balance + to.balance == previous(from.balance + to.balance)
    ensures throws LimitError ==> from.balance == previous(from.balance) && to.balance == previous(to.balance)
{
    // тело
}
```

Второе `requires` нужно для суммы в `ensures`: без границ `from.balance + to.balance` могло бы переполниться,
а это ошибка ([выше](#арифметика-и-частичные-операции)); `Account.LIMIT` — такая константа, что `2 * LIMIT`
помещается в `Int`. Здесь у `LimitError` свои условия (ничего не изменилось), а для остальных исключений действует обычное
`ensures`: сумма на двух счетах сохраняется при любом выходе.

- Строка `taken(x)` или `written(x)` говорит только об обычном возврате: на выходе исключением значение остаётся у
  вызывающего, а слот не записан, если строка `ensures throws E ==> taken(x)` не говорит иного
  ([владение и запись](#условия-функции-только-requires-и-ensures)).
- Строки `invariants`, которые выход обязан восстановить ([точки восстановления](#когда-условие-проверяется)),
  действуют на любом выходе сверх этого.
- Путь через `halt()` в доказанное не входит: программа остановлена. Отчёт доказательства называет такие пути.
- На выходе по `AssertionError` `ensures` и строки с `result` не доказываются и не проверяются: в выпускной
  сборке этого пути нет. Остальные проверки выхода делаются и для него, в том числе для `AssertionError` из
  вызова; где не проходят, провал в этой точке останавливает программу, как `halt()`, и отчёт доказательства
  называет такие точки ([тесты](tests/tests.md#assert)).

## Генераторы

У генератора есть посылки `ensures yield ==>` (условие каждого отданного значения) и `requires resume ==>` (условие
значения, которое передаёт `next`), а в условиях — история `yielded` и `resumed`
([генераторы](generators.md#условия-генератора)).

## Функции без тела, контракты и интерфейсы

У метода `contract` или `interface` условия — обязательство реализации. Реализация может написать свои
условия, но её `requires` не сильнее, а `ensures` не слабее объявленных; без своих условий она получает условия
объявления. Вызывающий через интерфейс видит только условия интерфейса. Нарушение этого правила — ошибка, не
заметка; если компилятор не доказал, что `requires` реализации не сильнее, а `ensures` не слабее, это тоже
ошибка, даже когда так и есть: реализация пишет условия, для которых это видно, или не пишет своих.

```efen
contract System {
    const PAGE: Int

    fn map(bytes: Int, aligned: Int) -> own Pointer.Zeroed?
        requires PAGE > 0 && bytes % PAGE == 0
        ensures result == null || (result.size == bytes && result.alignment == aligned)

    fn unmap(memory: own Pointer, bytes: Int)
}
```

Без доказательства, на веру, компилятор принимает `ensures` только у `@abi(c)` без тела, у вставок `@asm` и у встроенных функций платформы
`@intrinsic` ([векторы std](types/simd.md#встроенные-функции-платформы)):
их кода он не читает ([system](memory/system.md#условия-результата--единственная-точка-доверия)). Писать их может
любой пакет ([кому доступно доверие](memory/system.md#кому-доступно-доверие)). Каждое такое
условие попадает в список доверия, который печатает сборка с доказательством.

## Рекурсия

Рекурсивная функция, которую нужно доказать завершающейся (например, её зовут из условия), пишет меру
`decreases` так же, как цикл. Недоказанная мера — заметка `Proof`; звать такую функцию из условия можно:
чистота решается по виду кода ([вызов функции в условии](#вызов-функции-в-условии)).

```efen
fn depth(node: Node?, fuel: Int) -> Int
    requires fuel >= 0
    decreases fuel
{
    // тело
}
```

## Циклы

Условия цикла стоят после заголовка, `{` тела — на своей строке.

```efen
var count = 0

while let block = take pool.firstFreeBlock
    invariant count <= pool.blocks
    decreases pool.blocks - count
{
    pool.firstFreeBlock = take block.next
    System.unmap(memory: block as Pointer, bytes: BLOCK)
    count = count + 1
}
```

- **`invariant`** верен перед каждой проверкой условия цикла (у `while let` — до `take`) и после выхода из
  цикла. У `repeat { } while c` условия стоят после `repeat`, и инвариант верен перед каждым проходом тела.
  У инварианта цикла нет имени. Слово `invariant` бывает только у цикла; условия типа пишутся блоком
  [`invariants`](#условия-значений-и-invariants) в его теле.
- **`decreases`** — мера: целое неотрицательное, строго убывает за шаг. Без неё завершение не доказывается;
  безопасность проверяется независимо.
- У `for` по конечной коллекции или диапазону завершение компилятор выводит сам.
- Инварианты из условий вида и из границ компилятор выводит сам; руками пишется только остаток.

## Модель `model`

## Условия значений и `invariants`

**Условие на одно значение — блок `{ }` в конце его строки-объявления; он читает только собственную память `value`
и константы.
Условие, которое читает несколько значений, — строка в блоке `invariants { }` внутри тела типа. У функции условия —
только строки `requires` и `ensures`.**

```efen
var classes: own Classes.Area? = null { value == null || value.count == CLASSES }
var head: AtomicInt = AtomicInt(0) { value >= previous(value) }
generic Lanes: Int { value > 0 }
```

- Порядок частей строки один: `пометки слово имя: право Тип = значение { условие }`; `{ }` всегда последний.
  У строки `param` блока нет: условие параметра пишется строкой `requires`.
- `{ }` у строки — условие этой переменной или поля: только то, что касается её собственной памяти, и проверяется
  оно на каждой её записи ([ниже](#условие-поля-и-состояние-типа)). При копировании (`let h = ring.head`) условие не
  переходит: у `h` своя строка. `{ }` внутри типа — уточнение типа: `[Int { value > 0 }]`,
  `type Nat: Int { value >= 0 }` ([уточняющие типы](types/refinement-types.md)).
- Собственная память значения — сами биты переменной или поля, у значения-структуры — её поля. То, что лежит за
  ссылкой (`own`, `read`, `!`, поле другого узла, элемент призрачной последовательности), — чужое состояние: его
  пишут без записи в эту переменную. `{ value.count == CLASSES }` у `own Classes.Area?` законно: длина области —
  часть её значения; `{ value.next == null }` у `own Node?` — нет.
- `{ }` у строки, который читает что-то кроме собственной памяти `value` и констант, — ошибка с подсказкой
  перенести строку в `invariants`.
- `invariants` бывает в теле типа один раз: у `struct`, `class`, `projection`, `context`, `strategy`, `contract`,
  случая `variant`. Строки в
  нём соединяются `&&`, `if` внутри — импликация. Имени у строки нет: диагностика называет её текстом и номером.
- Строка `invariants`, которая читает только собственную память одного имени со своей строкой-объявлением в этом
  же теле, — ошибка с подсказкой перенести её к этой строке. У поля встроенной структуры (`Header.kind` в
  `SlotBlock`) и у права, объявленного перед именем параметра (`Access` из `<Access T>`), своей строки в этом теле нет, и
  их условия законно стоят в `invariants`. Строка, которая через одно имя читает чужое состояние
  (`forall k in freeSlots: !slots.taken.contains(k)`), тоже стоит в `invariants`.
- Условий после тела (`struct S { … } { … }`), `invariant имя { }`, `state invariant`, строк условий в
  `layout { }` и `where` нет: всё это строки `invariants`.

```efen
shared struct Ring {
    let capacity: Int { value > 0 }
    var head: AtomicInt = AtomicInt(0) { value >= previous(value) }
    var tail: AtomicInt = AtomicInt(0) { value >= previous(value) }
    var slots: [Job?]

    invariants {
        slots.count == capacity
        head <= tail
        tail <= head + capacity
    }
}
```

`head <= tail` и `tail <= head + capacity` читают два атомарных поля, которые пишут разные роли, и только
доказываются: из монотонности `head` и `tail` и из того, что каждое поле пишет своя роль.

### Когда условие проверяется

Время следует из того, что читает строка:

| Строка | Проверяется |
|---|---|
| читает только параметры generic | при сборке, у каждой подстановки |
| `{ }` у строки-объявления | на каждой записи этого значения |
| `invariants`, несколько значений | в точках восстановления |
| `invariants` у `shared struct` | в конце создания, при отпускании блокировки и после каждой прямой записи там, где корутин нет ([роли](shared.md#роли)) |
| строка про состояние, которое пишут разные роли без общей блокировки (два атомарных поля) | только доказывается: прочесть его порознь при выполнении — гонка; недоказанная — `unchecked` |
| строка с `previous` в `invariants` | в точках восстановления; на входе метода фактом не считается, при создании не проверяется |
| `ensures` | на выходе из вызова |
| условие цикла | перед каждой итерацией и на выходе из цикла |

Точка восстановления — момент, в который строки `invariants` значения обязаны быть верны:

- `return` и `throw` открытого (не `private`) метода или функции, которые значение меняли;
- вызов любого открытого метода этого же значения с любым правом, и `read` тоже: открытый метод опирается на
  `invariants` на входе;
- передача самого значения наружу с любым правом (`onChange(self)`, `save(pool)`).

Вызов закрытого метода того же типа точкой восстановления не бывает; закрытый метод и деструктор на `invariants` на
входе не опираются. Передача отдельного поля (`tasks.append(…)` у `self.tasks`) — тоже не она: наружу уходит поле, а
не само значение. Внутри метода строку `invariants` можно временно
нарушить: к точке восстановления она обязана снова стать верной. Закрытый помощник того же типа получает нарушенное
состояние и на `invariants` не опирается: что ему нужно, он пишет в `requires`, что оставляет — в `ensures`.

```efen
class TaskQueue {
    var tasks: Vector<Task>
    var count: Int = 0
    invariants { count == tasks.count }

    mut fn add(task: own Task) {
        tasks.append(take task)    // строка временно нарушена
        log()                      // закрытый метод: не точка восстановления
        count += 1                 // к выходу снова верна
    }

    private mut fn log() { … }
}
```

Уничтожение — не точка восстановления. Арену можно освободить целиком, а потом выбросить список сырых адресов в
неё (`nodes.removeAll()` — передача поля), не читая их. Безопасность здесь — дело FLOW: после уничтожения значения
адреса, которые по `invariants` ему равны, висячие, и чтение через висячий адрес — ошибка. Порядок уничтожения
полей следует из строк `invariants`: поле, которое называет адрес другого поля, уничтожается раньше.

### Условия функции: только `requires` и `ensures`

У функции нет ни одного `{ }`, кроме тела. `{ }` прямо за типом параметра или результата — ошибка с исправлением на
`requires`/`ensures`; `{ }` внутри типа (`[Int { value > 0 }]`) — уточнение типа, его можно.

| Было | Стало |
|---|---|
| `index: Int { value >= 0 && value < CLASSES }` | `requires index >= 0 && index < CLASSES` |
| `block: mut SlotBlock { used > 0 }` | `requires block.used > 0` |
| `-> own Pointer? { size >= size }` | `ensures result == null \|\| result.size >= size` |
| `memory: own Pointer? { result != null ==> take }` | `ensures taken(memory) == (result != null)` |
| `handle: out Int { result == 0 ==> out }` | `ensures written(handle) == (result == 0)` |
| `-> MapResult { mapped: memory.size == bytes }` | `ensures match result { … }` |

Владение и запись слота по условию — призрачные функции `taken(x)` и `written(x)` в `ensures`: они есть только при
доказательстве, в машинном коде их нет. Пишутся они через `==`, а не
`==>`: `==>` не говорит, что при ложном условии значение осталось у вызывающего, и реализация интерфейса, которая
забирает значение всегда, стала бы законной.

```efen
fn adopt(memory: own Pointer?) -> Handle?
    ensures taken(memory) == (result != null)

fn open(path: String, handle: out Int) -> Int
    ensures written(handle) == (result == 0)
```

- Строка с `taken` или `written` обязана быть доказана: недоказанная — ошибка, при выполнении владение не проверить.
- Она говорит об обычном возврате. На выходе исключением значение остаётся у вызывающего, а слот не записан;
  функция, которая забирает значение или пишет слот и на этом выходе, пишет строку `ensures throws E ==> taken(x)`
  или `ensures throws E ==> written(x)` ([выход по исключению](#выход-по-исключению-и-halt)). Такая строка своей
  строкой исключения `E` не считается: обычные `ensures` на этом выходе действуют, как без неё.
- Без строки `taken` параметр `own` функция забирает всегда, параметр `out` пишет на каждом возврате.

Случай результата — `match` в `ensures`:

```efen
fn mapX86(bytes: Int) -> MapResult
    ensures match result {
        .mapped.{ let memory }: memory.size == bytes
        .failed: true
    }
```

### Условие поля и состояние типа

**Условие поля держит каждая запись.** Компилятор доказывает условие поля в каждой записи: в присваивании, в
конструкторе, в значении по умолчанию. Поле можно отдать функции на чтение. Параметром `mut` его можно отдать только
функции, которая обещает то же условие в `ensures`: тогда его доказывают её выходы. Пишущую ссылку `&` на такое
поле взять нельзя: запись через неё никто не проверит. Остальное — ошибка:

```efen
struct Pool {
    var blocks: Int = 0 { value >= 0 }
}

fn setTo(value: mut Int) { value = -5 }

fn setWithin(value: mut Int)
    ensures value >= 0
{
    value = 5
}

fn lend(pool: mut Pool) {
    setTo(value: pool.blocks)      // ошибка: setTo не обещает value >= 0
    setWithin(value: pool.blocks)  // можно
}
```

**Состояние типа.** `requires x is State` по оси [typestate](types/typestate.md) — требование состояния, его
проверяет typestate, и нарушение — всегда ошибка, не заметка. Так же доказывается строка `invariants` про состояние
(`mutex is Mutex.Held`):

```efen
fn release(pool: mut Pool, connection: own Connection)
    requires pool.mutex is Mutex.Free
{
    // тело
}
```

Стиль: свойство одного значения, которое нужно многим функциям, — тип
(`type Slot: Int { value >= 0 && value < CAPACITY }`); связь параметров и выход — `requires`/`ensures`.
`ensures`, который пересказывает тело, не пишется: компилятор выведет его сам.

## Призрачные поля и цепочки

Призрачное значение есть только при доказательстве: в памяти и в машинном коде его нет, размер значения оно не
меняет. Читают его только условия (`invariants`, `requires`, `ensures`, `assume`) и правая часть призрачного
присваивания; обычный код, который его читает, — ошибка. Призрачное поле пишется, только когда компилятор не может
вывести состояние сам: цепочку по ссылкам он ведёт сам, поле по формуле вычисляет сам.

### Цепочка

`A.chain(from: H, by: T.L, until: END)` — узлы, которые достигаются от головы `H` по полю-ссылке `L` узла `T` до
конца `END` (константа или `null`); каждый из них лежит в области или наборе `A`. Узел — номер слота в области
(`Int`) или элемент набора. Цепочка пишется только в `invariants`; `let` даёт ей имя. Какие узлы на цепочке после
каждой записи `H` и `L`, компилятор знает сам: снятие головы, вставка, вырезание из середины. Программист пишет
только законы.

| Что | Запись |
|---|---|
| каждый узел | `forall k in c: P(k)` |
| число узлов | `c.count` |
| первый, последний | `c.first`, `c.last` — `T?`; `null` у пустой цепочки и только у неё |
| входит ли | `c.contains(x)` |
| пуста ли | `c.isEmpty` |

Порядка цепочка не хранит: `c[i]`, `c[a ..< b]` и `c.indexOf(x)` — ошибка. В точке восстановления цепочка доходит
до `END`, без повторов и петли, и ни одна ссылка не ведёт за `A`; это компилятор проверяет сам, как законы
`invariants`. Внутри метода цепочку можно разорвать, как любой закон. Присвоить имени цепочки ничего нельзя.

```efen
struct SlotBlock {
    Header                                  // used, frontier, firstFreeSlot, kind
    @align(LINE) area slots: Slot

    invariants {
        kind == SLOTS
        used == slots.taken.count
        frontier <= slots.count
        forall k in frontier ..< slots.count: !slots.taken.contains(k)

        let freeSlots = slots.chain(from: firstFreeSlot, by: Slot.next, until: NONE)
        forall k in freeSlots: 0 <= k && k < frontier && !slots.taken.contains(k)
        freeSlots.count == frontier - slots.taken.count
    }
}

fn returnSlot(block: mut SlotBlock, slot: Int)
    requires slot >= 0 && slot < block.frontier
    requires block.slots.taken.contains(slot)
{
    …                                        // slot уходит из slots.taken
    block.used -= 1
    block.slots[slot].next = UInt16(block.firstFreeSlot)
    block.firstFreeSlot = slot               // slot встал в голову freeSlots
}
```

Последние две строки компилятор читает как вставку `slot` в голову `freeSlots`: ссылка нового узла — старая голова,
голова — новый узел. Отсюда он выводит, что `freeSlots` выросла на один узел, и проверяет законы у `slot`. Цепочка
не из области — список с хвостом над набором `Items` ([законы и цепочки](memory/layout.md#законы-и-цепочки)):
`let nodes = Items.chain(from: head, by: Item.next, until: null)`, законы `forall n in Items: nodes.contains(n)` и
`tail == nodes.last`.

Голова может зависеть от переменной `forall`, тогда цепочка пишется без имени: «запись лежит в своей корзине» —
`forall e in Entries: Entries.chain(from: buckets[e.home], by: Entry.next, until: null).contains(e)`.

Порядок — номер элемента, вставка и удаление по номеру — цепочка не даёт; такая структура (список как
представление `Array`) хранит его в `ghost var` с `Sequence`.

### Поля по формуле и хранимые поля

**Заданное формулой `ghost let x: T = выражение`** вычисляется из обычных полей и не присваивается. Выражение
читает обычные поля своего значения и `ghost let` значений, которыми оно владеет (`own`); `ghost let` своего же
значения оно не читает, поэтому циклов нет, а рекурсия идёт вниз по владению и конечна. Решатель разворачивает
формулу на один-два уровня; глубже не доказывает, и это печатается в `efen proofs`. `ghost let` в теле функции —
призрачная локальная переменная, снимок значения в этой строке. Дерево пишется полями по формуле, и каждый закон
местный — узел и его дети:

```efen
struct Node {
    let key: Int
    var left: own Node? = null
    var right: own Node? = null
    ghost let size: Int = 1 + (left?.size ?? 0) + (right?.size ?? 0)
    ghost let lowestKey: Int = left?.lowestKey ?? key
    ghost let highestKey: Int = right?.highestKey ?? key

    invariants {
        left == null || left!.highestKey < key
        right == null || right!.lowestKey > key
    }
}
```

**Хранимое `ghost var`** — для состояния, которое не даёт ни цепочка, ни формула: номер элемента в списке,
перестройка в цикле. Оно меняется только призрачным присваиванием — строкой `ghost x = выражение` в
коде. Компилятор значение не ищет: он проверяет, что строки `invariants` верны в точке восстановления, и при
нарушении называет строку. Присваивание требует права записи на путь, читает обычные и призрачные значения, зовёт
только чистые функции и обычное состояние не пишет. Призрачное значение ничего не перемещает: `Sequence(item)` с
`own item` держит сам элемент (его адрес), и `==` у таких элементов — сравнение адресов.

`Sequence<T>` — конечная последовательность, которая бывает только у призрачных значений:

| Что | Запись |
|---|---|
| пустая, из элементов | `Sequence()`, `Sequence(x)`, `Sequence(x, y)` |
| длина, элемент | `s.count`, `s[i]` |
| первый, последний | `s.first`, `s.last` — `T?`, у пустой `null` |
| отрезок | `s[a ..< b]`, определён при `0 <= a <= b <= s.count` |
| склейка | `s + t` |
| входит ли, где | `s.contains(x)`, `s.indexOf(x)` — `Int?` |

Значение из сырой памяти (`memory as SlotBlock`) условий не несёт ([pointer](memory/pointer.md)): поле
`ghost var` получает свой инициализатор, а поля код пишет до первой точки восстановления.

Строка, которая читает призрачное значение, при выполнении не вычисляется: недоказанная, она получает заметку
`efen.unchecked`, а проверки, которые сняла бы, остаются в программе
([обычная сборка](#обычная-сборка-и-диагностики)).

## Что выводится само

Писать не нужно:

- что функция читает и меняет. Слова `reads`, `modifies`, `creates`, `removes` и `opens` в язык
  не входят;
- учёт взятых и возвращённых слотов: Δ`used` и `taken` ([pointer](memory/pointer.md#учёт-на-выходе-функции));
- условия вида и инварианты, которые их документы требуют восстановить;
- инварианты циклов из условий вида и границ;
- для не публичной и не рекурсивной функции — её сводку из тела. Сводка добавляется к написанным `ensures`, а не
  заменяет их, и в отчёте её строки помечены выведенными. Написанное `ensures` доказывается как прежде; тело, которое
  ему противоречит, — ошибка сборки. Правка тела меняет у вызывающих только выведенную часть сводки: что должно
  пережить правку, пишется в `ensures`.
  У публичной функции дополнительные функциональные постусловия из тела не выводятся: вызывающий из другого пакета
  видит её объявленные условия. Это не относится к обязательной сводке безопасности памяти `layout`: источники,
  права, выдачи и возвраты, уничтожение и эффекты наблюдения выводятся и проверяются также для публичных функций,
  затем экспортируются в интерфейс пакета ([алгоритм FLOW](memory/layout-algorithm.md#сохранение-законов-и-сводки-вызовов)).
  Это требование проектируемой модели `layout`, не утверждение о текущей реализации компилятора.
- для закрытой функции — не публичной, вызываемой только прямо, не значением и не из `spawn` — факты на входе
  о её целых параметрах из всех вызовов, как в Goose: на входе верно то, что доказал каждый вызов. Эти факты только снимают проверки при выполнении; принята ли программа, решается без них.
  Контракт открытой или экспортируемой функции — по-прежнему её `requires`.

  ```efen
  const SIZES: [Int] = [16, 32, 64, 128]

  fn sizeOf(index: Int) -> Int {
      return SIZES[index]  // оба вызова передают 0 и 3: проверки индекса нет
  }

  fn smallest -> Int {
      return sizeOf(0)
  }

  fn largest -> Int {
      return sizeOf(3)
  }
  ```

## `assume`: факт без доказательства

Иногда условие верно по причине, которой компилятор не видит. Счётчик блоков растёт на один с каждым блоком, который
выдала система, а адресов меньше 2⁴⁸ блоков по 64 КБ, поэтому `blocks + 1` не переполнится. FLOW этой связи не знает
и оставляет у сложения выход по `OverflowError`. Строка `assume` говорит компилятору принять условие без
доказательства:

```efen
const MAX_BLOCKS = 1 << 48

fn growPool(pool: mut Pool) -> Bool {
    guard let memory = System.map(bytes: REGION_BLOCKS * BLOCK, aligned: BLOCK) else {
        return false
    }

    let region: Blocks.Area = memory as Blocks.Area { value.count == REGION_BLOCKS }
    for element in take region {
        pool.firstFreeBlock = newFreeBlock(memory: take element, next: take pool.firstFreeBlock)
        assume pool.blocks < MAX_BLOCKS && pool.pooled < MAX_BLOCKS
        pool.blocks = pool.blocks + 1      // доказано: переполнения нет
        pool.pooled = pool.pooled + 1
    }
    return true
}
```

- `assume` — инструкция тела функции, как `guard`. После неё условие — факт, пока не изменится слот, который он
  читает: `pool.blocks = pool.blocks + 1` меняет `pool.blocks`, и дальше факт о нём держится только тот, что FLOW
  выведет сам (`pool.blocks <= MAX_BLOCKS`).
- Компилятор условие не проверяет и не вычисляет: в программе на его месте нет ни одной инструкции. Ложное
  условие ломает то, что на нём доказано: проверка, которую оно сняло, не стоит, и сложение, переполнения которого
  «нет», заворачивается молча.
- Строка `assume` — точка доверия, как `@asm`: пакет с ней становится рискованным, `efen proofs` показывает её
  строкой `trust` ([кому доступно доверие](memory/system.md#кому-доступно-доверие)).
- Факт ставят точечно, рядом с операцией, которой он нужен. Условие значения, строку `invariants` или `requires` с
  `assume` не пишут: такое условие действовало бы на каждую запись поля во всей программе, и ошибку в любой из них компилятор
  принял бы молча.
- Условие — сравнения, `&&`, `||` и `!` над параметрами, полями, локальными значениями и константами. Арифметика в
  нём — ошибка компиляции: условие не вычисляется, и у `a + b` в нём не было бы ни машинного смысла с переполнением,
  ни проверки. Границу пишут константой: `1 << 48` — значение `MAX_BLOCKS`, а не выражение в строке.

## Обычная сборка и диагностики

- FLOW доказывает `requires` в точке вызова и `ensures` на возврате, где может. Остальное доказывает сборка с
  решателем.
- Недоказанное условие не останавливает сборку: компилятор выдаёт заметку в группе `Proof`. Отчёт доказательства отмечает каждый вывод, который держится на недоказанном условии.
- Недоказанное условие не считается фактом для безопасности. Как именно:
  - проверку ставит та сторона, которая должна доказательство. Недоказанный `requires` проверяется целиком в
    точке вызова, недоказанный `ensures` — на возврате. Вызываемая функция всегда полагается на свой
    `requires`, вызывающий — на `ensures`: при раздельной сборке функция не знает, доказали ли условие все,
    кто её вызывает;
  - функцию `@abi(c)` с телом вызывает C, который ничего не доказывает, поэтому её `requires` проверяется на входе,
    до тела, в каждой сборке, а заметка `Proof` стоит у самой функции;
  - при выполнении проверяемы: сравнения и арифметика над параметрами, полями и `result`; `forall i in a ..< b`;
    вызовы чистых функций; `previous(x)`, где `x` — значение или поле: у `ensures` компилятор снимает его на входе,
    как у [проверочной сборки C](foreign.md), у условия значения `{ }` — перед каждой записью, а у атомарного
    значения прежнее значение даёт сама атомарная операция записи. Строка `ensures throws E ==> …` проверяется в точке выхода
    исключением;
  - остальное (строка, которая читает призрачное поле — поле, которое есть только при доказательстве, — и
    `previous` от составного значения) не проверяется
    при выполнении. Такое условие остаётся заметкой `efen.unchecked` группы `Proof` с причиной, а проверка,
    которую оно сняло бы, не снимается: `SIZES[index]` проверяет границу, как без условия. `efen proofs` пишет
    такую строку итогом `unchecked`, один раз у самой строки условия. Строку с `==>` программа проверяет как
    `!a || b`: заключение читается, только когда посылка верна. Вызов функции в строке, с метками аргументов или
    без, проверка делает так же, как строка: функция чистая, поэтому вызов ничего не меняет и не бросает;
  - нарушение по умолчанию останавливает программу, как `halt()`, и пишет в стандартный поток ошибок, какое условие
    и где нарушено (`stopped: main.efen:3: result > 10`): это ошибка программы, а не исключение, которое ловят.
    Файл и строка — там, где идёт проверка: у `requires` — вызов, у `ensures` — выход, на котором строка нарушена,
    у уточняющего типа — `.refine()`, у условия значения — запись; текст — сама строка условия. Сборка может выбрать для вида строки другой исход
    ([`proofs`](build-config.md#доказательства)): `fault` — нарушение бросает `ConditionError`, сбой с текстом
    строки, местом и функцией, которая её проверила; сервер ловит его на уровне запроса и работает дальше.
    Исход решает пакет, в коде которого стоит проверка: для `requires` — вызывающий, для `ensures` — сама
    функция, для вида `values` (условие значения `{ }`, строка `invariants`, `.refine()`) — код, который пишет
    значение или зовёт `.refine()`. В функции `nofail`, в деструкторе и в предикате нарушение всё равно останавливает программу, как и
    строка `ensures yield`, строка выхода исключением и `ensures` конструктора. `observe` (только для `ensures`)
    — нарушение пишется в стандартный поток ошибок через `Trap.observe` (`observed: main.efen:3: result > 10`), и
    программа работает дальше, как будто строка выполнена; следующие строки того же выхода не проверяются.
    Строка остаётся фактом для FLOW при любом исходе. При `stop` и `fault` код после нарушенной строки не
    выполняется; при `observe` выполняется, поэтому каждая проверка, доказательство которой опирается на
    наблюдаемую строку, в такой сборке остаётся и при нарушении останавливает программу, как проверка,
    оставленная `keep`; `efen proofs` пишет её `proved … kept`.
  Условие, которое доказано, проверок не порождает. Требование состояния `requires x is State` сюда не
  относится: его проверяет typestate, и недоказанное — ошибка ([выше](#условие-поля-и-состояние-типа)).
- `efen proofs` перечисляет проверки по файлам и функциям. У каждой — место, вид, итог и способ: `proved` с видами
  рассуждения, без которых доказательство пропадает (`FLOW::linear`, `Z3::<алгоритм>`), или `checked` — программа
  проверяет это при выполнении. Под доказанной проверкой — строки `assume`, на которых она держится, и строки
  `requires` вызванной функции, которые FLOW не доказал у какого-то её вызова: у такой строки пишется
  `unproved at 12:20` — вызов, где она проверяется при выполнении. Так же — строки `ensures`, которые функция
  не доказала на выходе: выход их проверяет, и вызывающий берёт их фактом о результате. У такой строки
  `unproved at` — этот выход. Под
  недоказанной — чего условия программы не называют о величинах этой проверки. Это факты о программе, а не совет,
  что дописать. Место факта — справа:

  ```text
  main.efen
    fn ratio    line 1
       3:18  overflow  proved    FLOW::linear
       3:18  zero      proved    FLOW::linear
    fn sum      line 8
      12:23  overflow  checked   run-time check
                       `total` changes in the loop                11:5
                       `i` changes in the loop                    11:5
      13:15  overflow  proved    FLOW::linear
    fn main     line 18
      19:31  overflow  checked   run-time check
                       `ratio()` states nothing about its result  1:1
                       `sum()` states nothing about its result    8:1
  5 checks: 3 proved (FLOW::linear 3), 2 checked
  ```

  Видов фактов пять: параметр, которого не называет ни одна строка `requires` его функции; результат вызова, о
  котором функция не говорит в `ensures`; поле без условия; значение функции, которой сборка верит (`@asm`,
  функция C); переменная, которую меняет цикл вокруг проверки. Величина прослеживается через арифметику и `let` до
  одного из этих источников. `--unproved` оставляет только `checked` и места доверия, `--flat` пишет строку на
  проверку (`main.efen:13:15 overflow proved FLOW::linear`), `--json` — тот же список одним объектом: `version`,
  `files` → `functions` → `checks` с полями `at`, `kind`, `result`, `by`, `kept`, `rests`, `facts`, и `summary`;
  каждое место в нём — `at: {file, line, column}`, у строки `requires` в `rests` — ещё `unproved`, список таких мест.

  Почти каждая проверка при выполнении — одно сравнение. Проверка `requires` или `ensures`, строки которой вызывают
  функции, пишет их имена в той же строке: ``checked   run-time check, calls `sorted` ``, в JSON — поле
  `cost: {"calls": ["sorted"]}`. Такая проверка может стоить прохода по данным при каждом вызове, и
  `efen proofs | grep calls` перечисляет все такие места. Называются только функции, которые вызывает сама строка;
  оценки вроде O(n) нет, потому что число шагов функции зависит от данных. У доказанной проверки цены нет.

  Ошибка FLOW не прячет список. Функция, на которой сборка остановилась, стоит строкой `not built` с первой
  ошибкой, и её проверки не перечислены. Ошибка об условии без проверки при выполнении (условие вида, приведение,
  заём, состояние) — отдельная строка `error`. Остальные функции перечислены как обычно. Недоказанное `requires`,
  `ensures` или условие поля, поднятое до ошибки (`-Werror Proof`), — тоже `error`. Ошибка читателя или плагина
  оставляет только диагностики.
- Заметку группы `Proof` поднимают до предупреждения или ошибки флагами
  [групп диагностик](diagnostic-groups.md#управление-через-флаги) или в конфигурации сборки.
- Условие, которое решатель опроверг, — ошибка с контрпримером: значения параметров, на которых оно ложно.
- Неопределённая операция в условии (переполнение, деление на ноль, индекс вне границ) — ошибка, только когда
  нарушение видно точно; если FLOW не смог её исключить — заметка `Proof` и проверка при выполнении ([Арифметика](#арифметика-и-частичные-операции)).
- У `assert` эти два пункта свои: в обычном коде ошибка — только `assert`, ложный или неопределённый на каждом пути
  ([тесты](tests/tests.md#assert)).

## Граница

`requires`/`ensures` описывают один вызов в одном потоке. Структура, которую меняют два потока без блокировки
(кольцо писателя и читателя), описывается [ролями и инвариантами](shared.md#роли), а не условиями функции.
Замыкания в условиях и условия у параметра-функции в первой версии не поддерживаются.
