Пакет на Efen вызывает библиотеку на C через модуль, который Amber создаёт по её заголовку программой clang. Всё, что
заголовок описывает полностью, Amber переносит сам: константы, перечисления, структуры, функции без указателей. Что
значит указатель, заголовок не говорит: одно значение или массив, можно ли `NULL`, забирает ли C владение, хранит
ли адрес после вызова. Такие места человек заполняет в модуле. Объявлению компилятор верит; проверочная сборка
ловит ошибки в нём, когда может.

## Подключение

C вызывает любой пакет, и только через сгенерированный модуль:

```efen
use Sqlite
```

Прямого подключения заголовка нет. Замер clang на заголовках Linux 2026-10-28 показал, что функций с указателями
почти везде большинство: `stdio.h` — 80 из 84, `string.h` — 42 из 42, `sqlite3.h` — 270 из 291; даже в `math.h`
их 34 из 479 (`frexp`, `modf`). Модуль нужен почти всегда, поэтому путь один.

Одна библиотека C — один пакет с её модулями, например `Sqlite` над `sqlite3.h`; остальные пакеты подключают его.
Модули для заголовков libc даёт стандартная библиотека. Тип C один на всю программу и узнаётся по имени C
(`FILE`, `struct tm`), а не по файлу, где он объявлен: `FILE` в glibc лежит в `bits/types/FILE.h`, в macOS — в
`_stdio.h`. Типы libc модуль берёт из модулей стандартной библиотеки, свои — объявляет сам.

Библиотека, в которой лежат функции (`sqlite3.h` → `libsqlite3`), пути к заголовкам, макросы `-D` и цель сборки для
clang записаны в настройках сборки пакета, а не в коде. В модулях платформы стандартной библиотеки
по-прежнему действует `@library` у функции ([системные вызовы](memory/system.md#внешние-функции-abic)).

## Что Amber переносит сам

Amber переносит то, что заголовок описывает полностью:

| В C | В Efen |
|---|---|
| макрос без параметров, значение которого — целое, дробное или строковое константное выражение | `const` с типом выражения |
| макрос — целое, приведённое к указателю (`MAP_FAILED`, `SQLITE_TRANSIENT`, `SIG_IGN`) | `const` с типом C; его можно только передать в C и сравнить |
| `enum` | тип-синоним его целого типа и `const` на каждое значение |
| `struct` из полей, которые Amber переносит сам | `@abi(c) struct` с размещением C цели сборки |
| `union` из чисел (`in6_addr`) | `@abi(c) variant`, все случаи читаются |
| `struct` без определения (`typedef struct sqlite3 sqlite3`) | `@abi(c) class` без полей: объект — указатель `sqlite3*` ([класс над внешним значением](classes.md#класс-над-внешним-значением)) |
| `typedef` | синоним типа |
| функция, параметры и результат которой — числа и такие структуры по значению | `@abi(c) fn` без тела |
| такая функция с атрибутом `noreturn` | то же, с результатом `-> Never` |

`enum` C становится целым, а не `enum` Efen: значения C складывают как флаги (`O_CREAT | O_RDWR`), и полный `match`
по ним был бы ложью.

Числа берутся по ABI цели. Типы фиксированной ширины сводятся раньше базовых: `uint64_t` — `UInt64`, хотя в glibc это
`unsigned long`.

| C | Efen |
|---|---|
| от `int8_t` до `int64_t`, от `uint8_t` до `uint64_t` | от `Int8` до `Int64`, от `UInt8` до `UInt64` |
| `signed char`, `short`, `int`, `long long` и `unsigned`-пары | `Int8`, `Int16`, `Int32`, `Int64`, от `UInt8` до `UInt64` |
| `char` | `CChar`: знак зависит от цели |
| `long`, `unsigned long` | `CLong`, `CULong`: отдельные типы, 4 байта на Windows, 8 на Linux и macOS |
| `size_t`, `uintptr_t` | `UInt`: ширина указателя цели ([ширина чисел](types/constants.md#ширина-числовых-типов)) |
| `ptrdiff_t`, `intptr_t` | `Int` |
| `__int128`, `unsigned __int128` | `Int128`, `UInt128` |
| `float`, `double` | `Float32`, `Float` |
| `long double` | `CLongDouble`: отдельный тип, не синоним, иначе код с `Float` собирался бы на Windows и ломался на Linux; формат по цели — x87 80 бит на x86-64 Linux и macOS, binary128 на AArch64 Linux и Android x86-64, binary64 на Windows и macOS AArch64; Amber берёт его из `__LDBL_MANT_DIG__` цели, а не из таблицы |
| `_Float128` | `Float128`: IEEE 754 binary128 |
| `float _Complex`, `double _Complex`, `_Float128 _Complex` | `Complex<Float32>`, `Complex<Float>`, `Complex<Float128>`: два числа подряд, как в C |
| `bool` | `Bool` |

### Массивы

У `Array` три параметра: тип элемента, укладка (`aos` — элементы целиком подряд, `soa` — поле столбцом) и
косвенность (`direct` — значение в ячейке, `indirect` — указатель на отдельно лежащее значение). Умолчание: `aos`; `direct` у структуры, `indirect` у класса. `[T]` — массив с умолчаниями; в записи
называют только то, что отличается, и по имени параметра, потому что второй позиционный параметр `Array` уже
занят формой ([generics](generics.md)): `Array<Row, indirection: indirect>`.

```efen
var events: [epoll_event] = []              // aos, direct: как struct epoll_event * в C
var rows: Array<Row, indirection: indirect> = []   // как struct Row ** в C
var shapes: [Shape] = []                    // класс: indirect по умолчанию
var particles: Array<Particle, soa> = []    // в C не передаётся
```

Пока запрещены: `soa` вместе с `indirect` и `direct` у класса (объект потомка не помещается в ячейку базового
класса). В функцию `@abi(c)` массив уходит, только если его элементы лежат одной непрерывной областью (форма `aos`,
а не `soa` или блоки `Chunked` из [блочного `Array`](memory/layout-examples/chunked-array.md)): `direct` — как `T*`, `indirect` — только `read`,
как `T* const*`. Иначе C переставил бы указатели (сортировка `Row**`), и ссылка `&rows[0]`, которую компилятор
держит адресом ячейки, увидела бы другой элемент. Умолчание для `T` в generic-функции и для `variant` и
`interface` не решено.

### Структура `packed`

`__attribute__((packed))` и `#pragma pack(n)` переносятся как `@abi(c)`-структура с `@packed` или `@packed(n)`: поля идут без выравнивания или с выравниванием не больше `n`.

```efen
@abi(c) @packed
struct Header {
    var kind: UInt8
    var length: UInt32              // смещение 1, не 4
}
```

Поле такой структуры читается и пишется значением: компилятор делает невыровненную загрузку. Ссылки на поле нет: его
нельзя передать параметром с правом `edit` или `mut` и нельзя вернуть ссылкой, потому что адрес невыровненного
`UInt32` нельзя отдать коду, который ждёт выровненный. Поле-владелец (`[Byte]`, класс) в `packed`-структуре —
ошибка: его нельзя ни скопировать значением, ни взять ссылкой. Поле типа структуры без `inline` в структуре
`@abi(c)` или `@packed` — тоже ошибка: раскладку C держит только встроенное поле
([вложенность](memory/layout/declaration.md#вложенность)).

Упакованность бывает только на части целей: `struct epoll_event` в glibc упакован на x86-64 и не упакован на AArch64.
Поэтому код, который пользуется модулем, проверяется против каждой цели, общей для программы и модуля (с учётом
`@platform` у самого вызывающего кода), а не только против цели сборки: иначе `edit`-параметр на поле собрался бы на AArch64 и стал бы ошибкой на x86-64.

### Битовые поля

Битовое поле переносится с шириной в битах. Как и у поля `packed`-структуры, оно читается и пишется
значением, сдвигом и маской, и ссылки на него нет. Расположение битов у компиляторов разное (GCC и MSVC кладут их
по-своему: у `struct { unsigned char a:4; unsigned short b:4; }` GCC даёт размер 2, MSVC — 4), поэтому Amber
пишет у каждого поля смещение в битах, взятое у clang для цели, и при различии пишет структуру под `@platform`.
Запись проверяется по ширине: `h.doff = value` требует доказанного `value < 16`. Безымянные поля (`int :3`,
`int :0`) Amber пишет явно, как `@bits(3, at: 5) _: Int32`.

```efen
@abi(c)
struct tcphdr {
    var source: UInt16
    var dest: UInt16
    var seq: UInt32
    var ack_seq: UInt32
    @bits(4, at: 96) var res1: UInt16
    @bits(4, at: 100) var doff: UInt16
    @bits(1, at: 104) var fin: UInt16
    @bits(1, at: 105) var syn: UInt16
    @bits(1, at: 106) var rst: UInt16
    @bits(1, at: 107) var psh: UInt16
    @bits(1, at: 108) var ack: UInt16
    @bits(1, at: 109) var urg: UInt16
    @bits(2, at: 110) var res2: UInt16
    var window: UInt16
    var check: UInt16
    var urg_ptr: UInt16
}
```

Смещения битов в дереве `-ast-dump=json` нет; их даёт `-fdump-record-layouts` или libclang (предположение, не
проверено).

### `union`

`union` C становится `variant` с `@abi(c)`: все случаи лежат с нулевого смещения, размер и выравнивание — по
самому большому, байтов метки нет. Так же `@abi(c)` на `struct` значит раскладку `struct` C.

```efen
@abi(c)
variant epoll_data_t {
    ptr { let ptr: @fill void* }
    fd { let fd: Int32 }
    u32 { let u32: UInt32 }
    u64 { let u64: UInt64 }
}
```

У `@abi(c) variant` метка — не часть значения, как в [`variant`](types/variant.md): `match` и `==` по нему без
доказательства живого случая — ошибка. Поле случая читается через имя случая: `data.u64`. Метки в байтах нет,
поэтому живой случай компилятор узнаёт одним из трёх путей:

1. Условие на внешней структуре, которая держит и метку, и `union`. Условие — любое выражение по полям, как
   диапазон у [`MapResult`](memory/system.md#вариант-в-одно-слово). Это заполняет человек:

   ```c
   struct Value {
       int kind;
       union { int number; char *text; } value;
   };
   ```

   ```efen
   @abi(c)
   struct Value {
       var kind: Int32
       var value: Value_value { kind == 1 ==> value is .number, kind == 2 ==> value is .text }
   }
   ```

   Запись в `kind` меняет структуру значения и разрешена только вместе с записью нового случая в `value`. Метка, которую
   условие не называет (новая версия библиотеки добавила `kind == 3`), не даёт читать ни один случай; `match` по
   такому значению обязан иметь ветку для неназванных меток. Шаблон общего начала (`SDL_Event`, где `type` лежит в
   каждом случае и жив всегда) записывается так же, но `type` остаётся в каждом случае: вынос общего поля сдвинул
   бы смещения остальных полей при другом выравнивании.

2. typestate: значение записал Efen, и компилятор помнит, какой случай записан.
3. Контракт функций, которые пишут и читают значение. Живой случай пишут в объявлениях вместо
   `@fill`: какой случай функция кладёт, такой другая возвращает. У `epoll` это `u64`, номер записи, а не указатель
   ([ниже](#пример-epoll)):

   ```efen
   @abi(c) fn epoll_ctl(epfd: Int32, op: Int32, fd: Int32, event: read epoll_event?) -> Int32
       requires event == null || event.data is .u64

   @abi(c) fn epoll_wait(epfd: Int32, events: out [epoll_event], max: Int32, timeout: Int32) -> Int32
       requires max > 0 && events.count >= Int(max)
       ensures result <= max
       ensures forall i in 0 ..< Int(result): events[i].data is .u64
   ```

   `epoll_wait` пишет только первые `result` элементов, остальные не инициализированы.

Если ни один путь не применим, читаются только случаи, где допустимы любые байты: целые и дробные числа, без `Bool`.
Случай с указателем можно только передать в C; прочитать его без доказательства — ошибка.

Поле-указатель структуры остаётся с `@fill`. Ядру или библиотеке, которые возвращают переданное значение позже,
указатель на память Efen не отдают: после `fork` или передачи дескриптора через `SCM_RIGHTS` то же значение придёт
в другой процесс. Отдают номер записи в таблице, которой владеет Efen, как в `epoll` ниже.

#### Пример: epoll

Первый вариант держал в ядре адрес элемента и помечал элемент состоянием `Registered`. Критик нашёл в
нём шесть дыр: состояние не привязано к конкретному `epoll`, его нельзя проследить для заранее неизвестного числа
соединений, освобождение области его не проверяет. Принятый вариант
обходится владением: соединениями владеет сам `Epoll`.

```efen
interface Pollable {
    var descriptor: Descriptor { get }      // Descriptor — тип только для чтения: edit не закроет и не заменит его
}

var epoll = Epoll<Connection>()             // обычное значение: может быть полем сервера или корутины

let key = epoll.add(take conn, events: EPOLLIN)      // Key?; при отказе ядра conn остаётся у вызывающего

for event in epoll.wait(timeout: 100) {
    serve(event.item)                       // mut-доступ к Connection, которым владеет epoll

    if closed {
        let back = event.remove()           // own Connection: настоящая передача владения
        drop(back)
    }
}

let other = epoll.remove(key)               // own Connection?: null, если ключ уже снят
```

Как это устроено. `Epoll` пишется на Efen в модуле платформы Linux поверх сырых `epoll_ctl` и `epoll_wait`:

- Владеет таблицей записей, которая не перемещается. Запись — соединение (`own T`), номер дескриптора, записанный при
  `add`, и поколение. `remove` снимает по записанному номеру, а не по текущему полю соединения.
- Ядро получает в `data.u64` номер записи и поколение, указателя оно не видит. `wait` находит запись по номеру и
  пропускает событие, если поколение старее записи: эту запись сняли в той же пачке. Номер вне таблицы или поколение
  новее записи — ошибка программы: проверочная сборка останавливается, обычная пропускает событие.
- Поколение не переполняется: запись, поколение которой дошло до максимума, больше не выдаётся.
- `Key` хранит номер, поколение и номер экземпляра `Epoll`. Ключ другого `Epoll` не подходит, и `remove` вернёт `null`.
- `add` объявлен как `fn add(item: own T? { result != null ==> take }, events: UInt32) -> Key?`. Если ядро
  отказало (`EPERM`, `EEXIST`, `ENOSPC`), владение не переходит; код ошибки ядра доступен отдельно.
- `remove` всегда возвращает владение. Если ядро не сняло запись (кроме `ENOENT`, когда записи там и так нет), запись
  остаётся в ядре без владельца; поколение уже сменилось, поэтому её события пропускаются. Проверочная сборка
  сообщает о таком случае.
- `event.item` — ссылка `mut` с источником-путём `<self.entries[slot].item>`: таблица не перемещается, поэтому ссылка
  не мешает курсору. `epoll.add` и `epoll.remove(key)` во время обхода меняют структуру `epoll` и поэтому запрещены,
  пока жив курсор ([источник-путь](types/ownership.md)).
- `wait`, `add` и `remove` берут `mut epoll`; `Epoll` не бывает `shared`.
- После `fork` дочерний процесс `Epoll` родителя не использует: таблица скопирована, и номера записей совпадут с
  чужими. `wait` в дочернем процессе — ошибка программы.
- При уничтожении `Epoll` сначала закрывает свой дескриптор ядра (ядро забывает все записи), потом освобождает
  соединения.
- Цена: одна загрузка и одно сравнение поколения на событие, рядом с системным вызовом на каждый `wait`. На каждое
  соединение и каждый байт ничего не добавляется. Не измерено.

Первый шаг: только срабатывание по уровню (`EPOLLET` и `EPOLLONESHOT` не поддерживаются). `add`, `wait`,
`event.item`, `event.remove()`, `remove(key)`, `item(key)` и обход всех соединений (для таймаутов и остановки).

### Что не переносится

Amber называет пропущенное в отчёте `amber foreign-report`:

- функции с атрибутом `returns_twice` (`setjmp`, `vfork`) — никогда: после второго возврата всё, что FLOW доказал о
  стеке и владении, ложно;
- функции с `...` (`printf`): типы аргументов не проверить; предложение — объявлять конкретные формы вызова.

Позже, по плану S79 (не решено):

- массив без длины в конце структуры (`struct { int n; char data[]; }`) — на поле `inline x: Area<T>` в конце структуры layout;
- `static inline`-функции и макросы с параметрами (`deflateInit`): символов в библиотеке нет; Amber пишет файл C,
  где каждая обёрнута обычной функцией, и собирает его тем же clang;
- глобальные переменные (`stdout`, `optarg`) — через `@fill` с правом и `shared`.

## Сгенерированный модуль и пометка `@fill`

Модуль создаёт команда `amber import-c`. В нём весь интерфейс библиотеки на Efen: константы,
структуры, типы и все функции. Обычная сборка читает только этот файл и clang не запускает.
Человек заполняет в нём места с пометкой `@fill`; после пометки стоит тип C как в заголовке, с `const`.

У каждой функции генератор оставляет её прототип C (`@c`): по нему компилятор выбирает, как передать аргумент, по
значению или указателем, а сверка сравнивает его с заголовком. Право Efen этого не говорит: `read Point` — это
`struct Point` или `const struct Point*`, смотря что записано в `@c`. Имя символа, если оно отличается от имени
функции (`stat` → `stat64` в glibc при `_FILE_OFFSET_BITS=64`), стоит в `@symbol` под `@platform` цели.

```efen
module {
    foreign: c
    header: "sqlite3.h"
}

const SQLITE_OK = 0
const SQLITE_ROW = 100

@abi(c) fn sqlite3_libversion_number -> Int32

@c("int sqlite3_open(const char *filename, sqlite3 **ppDb)")
@abi(c) fn sqlite3_open(filename: @fill const char*, db: @fill sqlite3**) -> Int32

@c("int sqlite3_close(sqlite3 *)")
@abi(c) fn sqlite3_close(db: @fill sqlite3*) -> Int32

@c("int sqlite3_step(sqlite3_stmt *)")
@abi(c) fn sqlite3_step(statement: @fill sqlite3_stmt*) -> Int32

@c("const unsigned char *sqlite3_column_text(sqlite3_stmt *, int iCol)")
@abi(c) fn sqlite3_column_text(statement: @fill sqlite3_stmt*, column: Int32) -> @fill const unsigned char*
```

Заполненный модуль. Непрозрачный тип C становится [классом над внешним значением](classes.md#класс-над-внешним-значением)
`@abi(c) class`, функции, которые берут его хендлер, — его методами. Прототип `@c` у каждого метода остаётся, как у
функции; в примерах он опущен.

```efen
module {
    foreign: c
    header: "sqlite3.h"
}

const SQLITE_OK = 0
const SQLITE_ROW = 100
const SQLITE_STATIC: sqlite3_destructor_type = null // макрос ((sqlite3_destructor_type)0): константа типа C

@abi(c) class sqlite3 {                             // сырое значение — sqlite3*, пустое значение — NULL
    conforms Constructible, Destructible
    layout { var errmsg: CString }                  // строка, которую sqlite держит у себя
    nocontext {
        @constructor fn sqlite3_open(filename: read CString, self?) -> Int32
        @destructor own fn sqlite3_close_v2 -> Int32                                     // неявный деструктор
        @destructor own fn sqlite3_close(self { result == SQLITE_OK ==> take }) -> Int32  // никогда не неявный
        private read fn sqlite3_errmsg -> read<self.errmsg> CString
    }
    public fn errorMessage -> own String { return String(copy sqlite3_errmsg()) }
}

@abi(c) class sqlite3_stmt {                        // сырое значение — sqlite3_stmt*
    conforms Constructible, Destructible
    layout {
        var db: mut sqlite3                         // запрос держит соединение
        var bound: [Int32: read CString]            // строки после SQLITE_STATIC
    }
    nocontext {
        @constructor fn sqlite3_prepare_v2(db: mut sqlite3, sql: read CString, length: Int32, self?,
                                           tail: out read<sql> CString? = null) -> Int32
        model { if let s = self { s.db = db } }

        mut fn sqlite3_bind_text(index: Int32, text: read CString, length: Int32,
                                 destructor: sqlite3_destructor_type) -> Int32
        model { if destructor == SQLITE_STATIC { self.bound[index] = text } else { self.bound.remove(index) } }

        mut fn sqlite3_clear_bindings -> Int32
        model { self.bound.clear() }

        mut fn sqlite3_step -> Int32
        mut fn sqlite3_reset -> Int32
        read fn sqlite3_column_text(column: Int32) -> read CString?    // источник — self
        @destructor own fn sqlite3_finalize -> Int32
    }
}
```

- Функция, у которой осталась пометка, не вызывается: вызов — ошибка, она показывает на пометку. Модуль с пометками
  компилируется.
- `@abi(c) class sqlite3` без `@c` — непрозрачная структура C, сырое значение — указатель `sqlite3*`. `self` метода
  стоит на позиции C: без записи первым, иначе там, где его написали (`mut fn fputs(text: read CString, self)`).
  `@c("pthread_t")` у класса называет typedef: сырое значение — `pthread_t`, и пустого значения у него нет.
- Деструкторы — `@destructor` у методов ([внешние деструкторы](disposable.md#внешние-деструкторы)). Неявный —
  единственный безусловный, не `explicit`: его вызывает компилятор, когда владеющий хендлер выходит из области, в
  том числе при исключении. `sqlite3_close` забирает хендлер только при `SQLITE_OK`: при `SQLITE_BUSY` соединение
  живо. Это условное владение получателем; неявным такой деструктор не бывает, его вызывают на слоте:
  `db.sqlite3_close()`.
- `self?` — C кладёт новый хендлер в слот вызывающего на каждом возврате, при отказе — `NULL`; вызывающий проверяет
  слот. Так же устроен `posix_memalign` в
  [владении](types/ownership.md#владение-которое-функция-забирает-не-всегда). C прежнее значение не освобождает,
  поэтому слот перед вызовом пуст: передать живой хендлер — ошибка компиляции, иначе хендлер потерялся бы. Если
  при отказе C оставляет в слоте мусор (`pthread_create`), пишут `self { result == 0 ==> out }`
  ([конструкторы внешнего объекта](classes.md#конструкторы-внешнего-объекта)).
- Строка из `sqlite3_column_text` — ссылка в память C с источником `self`
  ([ссылка в результате](types/ownership.md#место-в-результате-функции)). `sqlite3_step` — `mut fn`, поэтому по
  общему правилу его вызов гасит ссылки от того же хендлера, и чтение строки после `step` — ошибка компиляции:

```efen
let text = st.sqlite3_column_text(column: 0)
st.sqlite3_step()
echo text                       // ошибка: text погашен вызовом sqlite3_step с правом mut
```

Метод, который может испортить ссылки от хендлера, — `mut fn`, остальные — `read fn`. Решает человек по
документации библиотеки; генератор права хендлера не предлагает.

Ссылку от другого хендлера гасит зависимость в `layout`. `sqlite3_errmsg(db)` отдаёт строку `db.errmsg`, а портит
её `sqlite3_step(statement)`, который `db` не берёт. Поле `layout` запроса `db: mut sqlite3` связывает их: вызов
`mut` с объектом гасит ссылки и от объектов, достижимых через его поля `layout` с правом `mut`, поэтому
`read<db.errmsg>` умирает на `s.sqlite3_step()`. Остаётся дыра внутри модуля: `sqlite3_column_text` — `read fn` и
ничего не гасит, хотя при нехватке памяти sqlite переписывает `errmsg`. Пометить его `mut fn` нельзя: тогда второй
столбец гасил бы первый. Поэтому `sqlite3_errmsg` — `private`, а публичный `errorMessage` отдаёт копию. Ошибку в
самом модуле статически не поймать; на Linux её ловит проверочная сборка, у которой тогда `malloc` sqlite.

Что пишут вместо пометки:

| Вид указателя в C | Запись в Efen |
|---|---|
| `T*` непрозрачного `T` | `self` метода `@abi(c) class T`; у другого параметра — `own T`, `own T? { result == 0 ==> take }`, `read T`, `mut T` |
| `T*` на одну структуру или число | `read T`, `edit T`, `mut T`; в результате — `read<x> T`, `edit<x> T` |
| `T*` на массив | `read [T]`, `edit [T]` и `requires x.count == n` ([условия функций](conditions.md)) |
| `T**` на массив структур | `read Array<T, indirection: indirect>` и `requires x.count == n` |
| `const char*`, строка с нулём в конце | `read CString`; в результате — `read<x> CString?`. `String` Efen хранит нуль после последнего байта, поэтому `name.cString` отдаёт C тот же буфер без копии; срез строки нуля не имеет и копируется |
| `T**` для результата | `self?` или `p: mut T?`, пустой перед вызовом и записанный на каждом возврате; `self { посылка ==> out }` или `p: out T { посылка ==> out }`, записанный ровно на путях посылки. То же для выходного слота любого сырого типа (`pid: out Pid { result == 0 ==> out }`) |
| `T**` на массив, куда C пишет объекты (`int fds[2]` у `pipe2`) | `fds: mut [T?]` с неинициализированными элементами или `fds: out [T] { посылка ==> out }`, и `requires fds.count == n`; функция — `@constructor` |
| `const char**`, куда C пишет указатель внутрь другого параметра (`pzTail`) | `tail: out read<sql> CString? = null`: вызывающий получает ссылку на слот аргумента `sql`, а не значение ([ниже](#что-c-держит-после-вызова)) |
| `T**` или `void*`, которые модуль не передаёт (`retval` у `pthread_join`) | `p: mut Pointer? = null` или `p: out Pointer? = null`; аргумент не передаётся, C получает `NULL` ([сырая память](memory/pointer.md#память-пришедшая-из-c)) |

Поле-указатель структуры остаётся с `@fill`: ссылку на поле держать нельзя
([где ссылки в результате нет](types/ownership.md#где-места-в-результате-нет)), а у `struct tm` поле `tm_zone` —
`const char*`. Такую структуру можно передавать, но не читать её указательные поля. Генератор подсказывает частые пары в комментарии, не снимая
пометку: `void* buf, size_t n` → `buf: read [Byte]` и `requires buf.count == n`.

Обновление библиотеки — `amber import-c --update`. Заполненное, у которого прототип `@c` совпадает с заголовком,
остаётся. Изменённое в заголовке снова получает `@fill`, прежняя запись остаётся рядом комментарием. Функция, которой больше нет, — ошибка
со списком мест вызова.

### Что C держит после вызова

Что функция C хранит после возврата, модуль пишет [моделью](models.md#модель-model) в поля `layout` класса:
`sqlite3_bind_text` с `SQLITE_STATIC` кладёт строку в `self.bound[index]`, и пока запрос жив и строка не снята,
владелец строки её не меняет и не уничтожает. Снимают заимствование перезапись, `sqlite3_clear_bindings`, уничтожение
запроса. Модели без тела компилятор верит, как `ensures`.

```efen
fn bindName(st: mut sqlite3_stmt) {
    var who = readName()
    st.sqlite3_bind_text(index: 1, text: who.cString, length: -1, destructor: SQLITE_STATIC)   // st держит read who
}                                               // ошибка: who умирает, пока st его держит
                                                // (sqlite3_clear_bindings или SQLITE_TRANSIENT это исправляют)
```

Выходной параметр-ссылка `tail: out read<sql> CString? = null` пишет в слот вызывающего ссылку на слот аргумента
`sql`. Аргумент — незаписанная переменная `var rest: CString?`; после вызова это ссылка, как `var`, которую
инициализировал вызов, возвращающий ссылку, и она живёт по правилам
[«Пока результат жив»](types/ownership.md#пока-результат-жив) против аргумента `sql`. Право ссылки не шире права
`sql`. Сам выходной слот источником не бывает. `= null` позволяет не передавать аргумент: C получает `NULL`.

```efen
public fn prepareFirst(db: mut sqlite3, script: read String, next: out Int) -> own sqlite3_stmt? throws SqliteError {
    var s: sqlite3_stmt? = null
    var rest: CString?                          // незаписанная: вызов делает её ссылкой на script
    let rc = sqlite3_stmt.sqlite3_prepare_v2(db: db, sql: script.cString, length: -1, self: s, tail: rest)
    guard rc == SQLITE_OK else { throw SqliteError() }
    next = script.count - (rest?.count ?? 0)    // смещение неразобранного остатка
    return take s
}                                               // rest ничем не владела
```

Поток, который создала библиотека, трогает заимствованное в любой момент. Такой объект объявляет `shared layout`
([общая память](shared.md#пометка-shared)), а деструктор, без которого нельзя, — `explicit`
([внешние деструкторы](disposable.md#внешние-деструкторы)):

```efen
@c("pthread_t") @abi(c) class Thread {          // сырое значение — pthread_t: пустого значения нет, Thread? с тегом
    conforms Constructible, Destructible
    shared layout { var start: own (() own -> Pointer?)? }
    nocontext {
        @constructor fn pthread_create(self { result == 0 ==> out },
                                       attr: read pthread_attr_t?,
                                       start: own (() own -> Pointer?)? { result == 0 ==> take }) -> Int32
        model { if result == 0 { self.start = take start } }
        @destructor(explicit) own fn pthread_join(value: mut Pointer? = null) -> Int32
        own fn pthread_detach -> Int32
    }
}

fn runJob(job: edit Job) throws ThreadError {
    var t: Thread                               // незаписанный выходной слот
    let rc = Thread.pthread_create(self: t, attr: null, start: () -> Pointer? { job.run(); return null })
    if rc != 0 { throw ThreadError() }          // t не записан
    // print(job.count)                         // ошибка: t держит edit job в другом потоке
    (take t).pthread_join()                     // обязателен на этом пути; заимствования кончились
    print(job.count)                            // можно
}
```

- Замыкание, которое модель кладёт в поле `layout`, проверяется как тело корутины: его заимствования на время вызова, выведенные в
  точке вызова, становятся заимствованиями, которые живут в объекте, с тем правом, которое нужно телу
  ([сохранение замыкания](closure.md#сохранение-замыкания-после-вызова)).
- Замыкание, которое держит объект `shared layout`, выполняет чужой поток, и оно проверяется как тело `offload`:
  отдельный поток, асинхронного контекста вызывающего нет (`spawn` внутри требует своего `with`), ссылок из
  контекста потока вызывающего нет, `Blocking` можно ([эффекты ожидания](shared.md#эффекты-ожидания)).
- `pthread_detach` забирает объект, но деструктором не является: он допустим, только если объект не держит ни одного
  слота Efen; значения `own` уходят с объектом.
- Объект, который нельзя трогать из другого потока (sqlite в режиме `NOMUTEX`, контекст GL), объявляет
  `conforms ThreadBound` ([контракты](runtime/built-in-contracts.md#threadbound)). Модуль std для sqlite пишет его, когда не может
  доказать последовательный режим библиотеки.

### Память, которую функция отдаёт до следующего вызова

`strerror`, `getenv`, `localtime`, `dlerror` отдают память, которая живёт до следующего вызова той же или
связанной функции, и хендлера у неё нет. Это состояние библиотеки. Модуль описывает его
[контекстом процесса или потока](context-and-effects.md#контексты-процесса-и-потока) с полями `foreign`: у такого
поля нет памяти и значения, это только имя пути для прав. Читать его, передавать, `copy` и `take` — ошибка.

```efen
public thread context LibcThread {      // у каждого потока свой буфер
    public foreign strerror
    public foreign tmbuf                // localtime, gmtime, ctime пишут в один struct tm
    public foreign dlerror
}

public process context LibcProcess {    // одно на процесс
    public foreign env
    public shared foreign tz            // библиотека сама защищает его блокировкой
}

@abi(c) fn strerror(errnum: Int32) -> read<LibcThread.strerror> CString in mut LibcThread.strerror
@abi(c) fn getenv(name: read CString) -> read<LibcProcess.env> CString? in read LibcProcess.env
@abi(c) fn setenv(name: read CString, value: read CString, overwrite: Int32) -> Int32 in mut LibcProcess.env
@abi(c) fn localtime(time: read CTime) -> read<LibcThread.tmbuf> tm? in mut LibcThread.tmbuf, mut LibcProcess.tz
@abi(c) fn gmtime(time: read CTime) -> read<LibcThread.tmbuf> tm? in mut LibcThread.tmbuf
@abi(c) fn strlen(s: read CString) -> UInt nocontext
```

Вызов с `mut` на путь убивает ссылки из этого пути, ссылки из других путей живут:

```efen
let a = strerror(errnum: 2)
let home = getenv(name: "HOME")
let b = strerror(errnum: 13)      // a умирает
print(home)                       // можно: env не тронут
setenv(name: "HOME", value: "/tmp", overwrite: 1)
print(home)                       // ошибка: setenv поменял LibcProcess.env
```

- Буфер, который делят несколько функций, — одно поле. Кто что делит, модуль берёт из руководства библиотеки (у
  glibc это пометки `race:tmbuf`, `env`, `locale`), для каждой платформы своё, под `@platform`: в musl у
  `localtime` и `gmtime` разные буферы.
- На поле `foreign` бывает только `read` и `mut`; `edit` — ошибка. Буфер, который C перезаписывает, не переселяя,
  по общему правилу был бы записью значения, и старая ссылка молча показывала бы новый текст. Поэтому перезапись
  буфера внешним кодом считается изменением структуры: она обесценивает прежнюю ссылку и требует `mut`.
- У функции C тела нет, поэтому `in` у неё обязателен; функция, которая контекстов не трогает, пишет `nocontext`
  после сигнатуры. Функция без того и другого — ошибка компиляции. `in` у функции C говорит только о контекстах:
  ждёт ли она, решает обещание `without Waiting` ([ниже](#блок-объявлений-c)). `in LibcThread` без права у функции C
  значит `read LibcThread`, как любое право без пометки; функция, которая пишет контекст, пишет `in mut LibcThread`.
- `amber import-c` ставит `@fill` вместо `in` у каждой функции каждого модуля. Много функций сразу закрывает
  [блок объявлений](#блок-объявлений-c). `--update` оставляет заполненный `in`, пока не изменились контексты,
  которые он называет, и прототип `@c`.
- Ссылка из контекста потока умирает в каждой точке ожидания, в том числе на выводе в терминал
  ([контекст потока](context-and-effects.md#ссылка-из-контекста-потока)): `print(copy strerror(errnum: e))`.
  Стандартная библиотека даёт в первую очередь повторно входимые формы (`strerror_r`, `localtime_r`,
  `getpwnam_r`): они пишут в буфер `out` и контекстов не трогают. Пути `foreign` — для того, у чего такой формы нет
  (`getenv`, `setlocale`, `dlerror`, чужие библиотеки).
- Пути `foreign` контекста процесса проверяет таблица многопоточных корутин: `mut` против `mut` или `read` из
  двух потоков — ошибка; тело `offload` считается отдельным потоком. У `shared foreign` два вызова с `mut` из
  двух потоков допустимы, но корутина, которая держит ссылку из этого пути, считается читающей его, пока ссылка
  жива. Потоки, которые создал сам C, проверке не видны.

### Блок объявлений C

Функция C по умолчанию `Blocking`. Функция, которая не ждёт, пишет после сигнатуры `without Waiting`: у функции без
тела это обещание модуля, компилятор ему верит. Тот же заголовок для многих функций сразу пишут блоком:

```efen
nocontext without Waiting {
    @abi(c) fn strlen(s: read CString) -> UInt
    @platform(os: "linux") @abi(c) fn memcpy(to: edit [Byte], from: read [Byte], count: UInt)
}

in mut LibcThread.tmbuf {
    @abi(c) fn gmtime(time: read CTime) -> read<LibcThread.tmbuf> tm?
    @abi(c) fn localtime(time: read CTime) -> read<LibcThread.tmbuf> tm? in mut LibcProcess.tz
}
```

- Каждая функция внутри читается так, будто заголовок написан после её сигнатуры. Блок — не область видимости и не
  пространство имён: имена, видимость, `@platform`, `@c`, `@symbol` и `@fill` у параметров пишутся у самой функции.
  `public`, `private`, `internal` или атрибут перед заголовком — ошибка.
- Блок стоит на верхнем уровне модуля или в теле класса над внешним значением вокруг его внешних методов, `{` — на
  строке заголовка. Внутри — только функции `@abi(c)` без тела, с `model` после сигнатуры или без:
  функция с телом, `struct`, `const`, `type`, `context`, вложенный блок — ошибка у этого объявления со строкой блока.
  У функции с телом те же слова значат проверку тела, а не обещание. Пустой блок — предупреждение.
- Заголовок: `nocontext` или `in` с контекстами и путями с правами, и `without Waiting`; в любом порядке, каждое не
  больше раза, хотя бы одно. Другого в заголовке нет: ни `throws`, ни `isolated`, ни пачки, ни `without` контекста,
  ни `without Suspending` или `without Blocking`.
- `in` заголовка и `in` функции складываются в один список по обычным правилам: один путь дважды с разными правами —
  ошибка, точный повтор — предупреждение. `nocontext` в заголовке и `in` у функции — ошибка; `without Waiting` в
  заголовке и `in Blocking` или `in Suspending` у функции — ошибка. Переопределить заголовок нельзя: функция, которой
  нужно другое, стоит вне блока. Источник результата сверяется со сложенным списком.
- Правило «`in` или `nocontext` обязателен» заголовок выполняет. Блок без `nocontext` и `in` по-прежнему требует их у
  каждой функции. `@fill` вместо `in` внутри блока с заголовком контекстов — ошибка.
- Обещание для функции C без тела даёт только она сама или блок. `in` или `without Waiting` строкой у модуля, пакета
  или класса на функции C без тела не действует: если такая строка их накрывает, ошибка у этой строки называет блок.
- Объявления одной функции для разных целей могут стоять в разных блоках или вне их. Вызов получает объединение
  эффектов и контекстов по всем целям, для которых собирается вызывающий, с учётом его `@platform`, как у полей
  `packed`.
- `amber import-c` блоков не пишет. Если при `--update` прототип `@c` функции изменился, она остаётся на месте, вместо
  её `in`, `nocontext` и `without Waiting` встаёт `@fill`, прежние слова — рядом комментарием: обещание о старой
  версии на новую не переносится. Функции сопоставляются по имени символа C; новые встают вне блоков.
- Сообщение, причина которого в заголовке, называет строку блока и помечает «(на веру)». `amber foreign-report`
  перечисляет функции с обещанием и строку блока или объявления. Подсказка к «`f` может ждать под мьютексом»
  предлагает `offload`, а не обещание.

### Колбэки

Указатель на функцию C — функция Efen `@abi(c)` без захватов: C получает её адрес. Замыкание с захватами C
вызвать само не может: код замыкания ждёт адрес своего окружения скрытым аргументом, а C его не передаёт.

Если функция C принимает вместе с указателем на функцию `void*` с данными колбэка, модуль по заголовку
принимает обычное замыкание Efen. Компилятор строит вход `@abi(c)`, который берёт окружение из `void*`, и
передаёт адрес окружения в этот аргумент:

```efen
sqlite3_exec(db: db, sql: "SELECT name FROM users", callback: (columns) => names.append(columns[0]))
```

Замыкание живёт только на время вызова (параметр без `own`) и может трогать локальные данные. Если C хранит
колбэк дольше вызова (`pthread_create`, регистрация обработчика), модуль пишет у параметра `own`, и действуют
правила [сохранённых замыканий](closure.md#сохранение-замыкания-после-вызова). Если модель кладёт колбэк в поле
`layout`, его заимствования становятся заимствованиями, которые живут в объекте ([что C держит после
вызова](#что-c-держит-после-вызова)). Функция C без такого `void*`
(`qsort`) получает только функцию `@abi(c)` без захватов: замыкание с захватами там — ошибка компиляции.

## Сверка с заголовком

Цели сборки видят заголовок по-разному: `O_CREAT` на Linux равен 64, на macOS 512; `struct tm` в glibc несёт
`tm_gmtoff`, на Windows этого поля нет. Такие объявления Amber пишет в модуль по одному на цель, с `@platform`;
одинаковые пишет один раз:

```efen
@platform(os: "linux", arch: "x86_64")
const O_DIRECTORY = 65536

@platform(os: "linux", arch: "aarch64")
const O_DIRECTORY = 16384
```

`@platform` называет и ОС, и архитектуру: на Linux x86-64 и AArch64 значения флагов `open` и раскладка
`struct stat` разные.

`amber import-c` проходит заголовок clang для каждой цели из настроек пакета. Модуль перечисляет свои цели, и для
каждой хранит отпечаток: хэш флагов clang и содержимого всех файлов, которые заголовок включил, с их путями. Сборка
под цель, которой нет в списке, — ошибка с советом добавить цель и перегенерировать.

```efen
module {
    foreign: c
    header: "sqlite3.h"
    targets: ["x86_64-linux", "aarch64-linux", "x86_64-windows"]
}
```

Сборка хэширует файлы из отпечатка цели без clang. clang она запускает, только когда хэш изменился, и тогда сверяет
модуль с заголовком. Если сборка заголовка не находит (кросс-сборка), она берёт модуль как есть и
предупреждает:

```text
warning: sqlite.efen is not checked against sqlite3.h: the header is not found for target x86_64-windows
```

Сверка снимает с объявления права и условия Efen и сравнивает остальное с заголовком:

- тип каждого параметра, поля и результата, включая указатель это или значение;
- `const`: у `const T*` нет `edit` и `mut`, ни у параметра, ни у результата, ни у поля;
- размер, выравнивание и смещения структур, значения констант;
- имя символа для цели: glibc при `_FILE_OFFSET_BITS=64` связывает `stat` с `stat64`, macOS x86-64 — с
  `stat$INODE64`; Amber берёт имя из дерева clang;
- соглашение о вызове.

Расхождение в объявлении, которое программа вызывает или читает, — ошибка; в остальных — предупреждение. Иначе
пакет `Sqlite`, созданный по sqlite 3.46, не собрался бы у того, у кого стоит 3.37 без нескольких новых функций.

```text
error: `sqlite3_column_count` differs from sqlite3.h
  --> Sqlite.efen:40:56
   |
40 | @abi(c) fn sqlite3_column_count(statement: read sqlite3_stmt) -> Int64
   |                                                                   ^^^^^ declared `Int64`
   = note: sqlite3.h declares `int sqlite3_column_count(sqlite3_stmt *pStmt)`, which is `Int32`
```

Если один символ C объявлен в двух модулях по-разному, это ошибка: при сборке целиком программа видит оба. То же
для одного типа C с разными деструкторами.

Amber запускает clang отдельной программой, как уже запускает его для генерации кода: `clang -fsyntax-only
-Xclang -ast-dump=json` с целью и флагами пакета. Макросов в этом дереве нет; их список даёт `clang -E -dM`, а
значение — clang на маленькой единице трансляции (предположение, не проверено).

## Доверие и проверочная сборка

Объявление функции C пишет человек, и проверить его нечем: тело на C. Компилятор ему верит, как условиям `@asm`, и
доказывает вызывающий код от него. В обычной сборке это ничего не стоит. Память C читается и пишется
на месте, без копий.

Ошибка в объявлении может испортить память: функция отдаёт 16 байт, а человек написал `ensures result.count == 64`. FLOW
доказывает, что `buffer[40]` в границах, и проверки не ставит.

Сырой `Pointer` с условиями размера, выравнивания и состояния остаётся стандартной библиотеке
([системные вызовы](memory/system.md#кому-доступно-доверие)). `Pointer.trusted` нет нигде.

Проверочная сборка ([checking-build](memory/checking-build.md)) проверяет на каждом возврате из C:

- `null` там, где объявление его не допускает (`-> read<s> CString` без `?`);
- каждое `ensures` (`result.count == n`, `result <= 4096`); условие с `previous(x)` — по снимку `x`, сделанному
  перед вызовом;
- кусок `[p, p + count * size)` по таблице слотов;
- сырое значение в результате и в выходном слоте: `null` или внутри уточнения (`Descriptor` вне диапазона —
  остановка со строкой объявления); слот с посылкой записан только на путях посылки;
- результат `Packed` лежит в одном из объявленных диапазонов.

Модели функции C проверочная сборка верит так же, как обычная; поведение C против модели она сверяет там, где это
видно по таблицам ниже.

Запись таблицы хранит, кто держит слот (Efen или C) и сколько байт запросили. По ней:

- кусок, который налезает на живой слот Efen, — остановка с именем функции и строкой объявления; кроме куска
  внутри своего источника, если его право не шире права источника (`strchr` по строке Efen);
- кусок внутри слота, который C взял у `malloc` проверочной сборки, не длиннее запрошенного;
- куска нет в таблице (стек C, статические буферы, память от ОС, нарезка самой библиотеки) — проверки нет.

Второй пункт работает, только если `malloc` библиотеки C — проверочной сборки. На Linux это даёт подмена символов
ELF; на macOS и Windows библиотека берёт `malloc` своей системы, и пункт не действует.

Ссылку из C с источником проверочная сборка записывает как заём у источника: `free` этой памяти, пока ссылка жива, —
остановка.

Адреса, которые функции C отдают из путей `foreign`, записываются тоже: по последнему адресу на путь (на путь и
поток у контекста потока). Два разных пути, которые отдали один и тот же записываемый адрес (не из сегмента
только для чтения), — остановка с именами обоих объявлений: так ловятся `localtime` и `gmtime`, разведённые по двум
полям там, где у библиотеки буфер один.

Хендлеры записываются тоже. Любой хендлер, пришедший из C (результатом, через `self?`, `self { result == 0 ==> out }` или
массив) или принятый `Self(raw:)`, — «выдан» с типом и строкой объявления. Выдать значение, которое уже выдано, —
остановка: так ловится второй `File.adopt(raw: 1)`. «Вернулся» — только на пути, где деструктор или параметр его
забрал: у `own fn sqlite3_close(self { result == SQLITE_OK ==> take })` — при `SQLITE_OK`. Передача вернувшегося хендлера в любой параметр останавливает программу (двойной `sqlite3_close`, `sqlite3_step` после
`finalize`). Хендлеры, живые в конце программы, попадают в отчёт.

Эффекты функции C — по умолчанию из [общей памяти](shared.md): `Blocking`, пока модуль не написал `without Waiting`
у неё или у [блока](#блок-объявлений-c). Модули libc стандартной библиотеки так помечают `strlen`, `memcpy` и
подобные. Исключения Efen функция C не
бросает.

## Команды

- `amber import-c <header> --module <name>` создаёт модуль `<name>.efen` по заголовку.
- `amber import-c --update <name>.efen` сверяет модуль с новым заголовком и обновляет его.
- `amber foreign-report` выводит анализ: какие пакеты верят C, через какие модули, сколько объявлений пакет заполнил
  сам и сколько взял у чужого пакета, что из заголовков пропущено. Сборка об этом молчит.

Менеджер пакетов сможет показать этот анализ при подключении пакета; менеджера пакетов в
спецификации пока нет.

## Не решено

- Заимствования через поля структуры, которые пишет Efen (`next_in` у `z_stream`): такое поле остаётся с `@fill`.
- Состояние без значения (`glBegin`/`glEnd`).
- Глобальные хендлеры: `stdout`, дескрипторы 0–2 как объекты, которые никогда не уничтожаются.
- Как забрать значение обратно из поля `layout`.
- Циклы в модели (массивы `iovec`).
- Более узкое гашение ссылок, чем «вызов `mut` гасит всё, что достижимо через поля `layout` с правом `mut`».
- Роли `@copy` у класса над внешним значением.
- Форма чтения сырого значения вне модуля класса.
- Форма типа функции для заимствования между параметрами.
- Результат `Thread<T>` в std поверх сырого `Thread`.
- Функции, которые ломают рантайм, хотя указателей у них нет (`fork` в многопоточной программе): по заголовку их не
  узнать; модули libc стандартной библиотеки их не дают, у других библиотек — пока ничего.
- Диапазон версий заголовка, с которыми совместим пакет.
- `errno`: это число, которое читают после вызова, а не ссылка; его, видимо, забирает заглушка вызова.
- Повторный вход из колбэка.
- `strtok`: результат указывает в строку из прошлого вызова; остаётся `@fill`.
- Обработчик сигнала: функция `@abi(c)` без захватов; ограничение её эффектов (безопасность в обработчике сигнала —
  не то же, что `without Waiting`: распределитель памяти неждущий) и вызов функции с `mut` на пути `foreign`.
  `shared layout` обработчики сигналов не покрывает.
- `tm_zone` в своём `struct tm` после смены часового пояса.
- Совместная работа с ASan на стороне C.
- Исключение на границе динамической библиотеки: что делает экспортируемая функция `@abi(c)`, из которой вышло
  исключение, и чей обработчик непойманных и чья нумерация тегов открытых enum ([расширение](types/enum.md#расширение))
  у потока, который создала сама библиотека.
- Формат настроек сборки пакета.
- Как записать отличие структуры между целями: вся структура дважды под `@platform` или отличие по полям.
- `static inline`-функции и макросы с параметрами через переходник, собранный тем же clang.
- Заголовки C++ и Objective-C.
- `epoll`: срабатывание по фронту (`EPOLLET`) и `EPOLLONESHOT` с повторным взводом (`EPOLL_CTL_MOD`); добавление и
  снятие чужой записи во время обхода; соединения, которые живут в области пользователя, а не в таблице `Epoll`;
  `wait` и `remove` из разных корутин ([общая память](shared.md)); как записать запрет `Epoll` в дочернем процессе.

## Придумано

Нет в спецификации, предложено в этом черновике:

- опции модуля `foreign: c` и `header: "x.h"` ([опции модуля](packages.md#опции-модуля)) и `.efen`-модуль, созданный по заголовку;
- `@platform` на объявлении, а не только на `implementation`;
- `@c("прототип")`, `@symbol("имя")`, опция модуля `targets` и отпечаток цели;
- `mut T?` для `T**`, пустая перед вызовом;
- `@abi(c) class` и `@c("имя")` у класса, `representation Raw<I>`, `representation Packed<I>`, объявление
  `type Option<T> { representation Raw<I>; null: c }`;
- `self` в списке параметров и с регистром (`@in(rdi) self`), `self?`, `self { посылка ==> out }`,
  `p: out T { посылка ==> out }`, `own fn m(self { посылка ==> take })`, метка `self:` у вызова конструктора;
- массивы `mut [T?]` и `out [T] { посылка ==> out }` у конструктора, `tail: out read<sql> CString? = null`,
  `= null` у параметра `mut Pointer?` и `out Pointer?` функции без тела;
- блок объявлений в теле класса, блок `layout` в теле класса, интерфейса и контракта, блок `model`, `forall x in
  collection:`, `shared layout`;
- `Self(raw:)`, `@destructor(explicit)`, несколько ролей `@destructor` у класса, контракты `ImplicitlyDestroyable` и
  `ThreadBound`;
- `@fill` и тип C после него;
- `CString`, `CChar`, `CLong`, `CULong`;
- `@abi(c)` на `variant` и `struct` как раскладка C; `{ data is .ptr(read T) }` — условие на случай поля;
  `{ kind == 1 ==> as is .number }` на внешней структуре; `requires event.data is .u64` у параметра и `ensures forall i in 0 ..< result: events[i].data is .u64` у
  элементов, которые функция записала ([условия функций](conditions.md));
- в примере `epoll`: `Pollable`, `Descriptor` как тип только для чтения, `Epoll<T>`, `Key`, `event.item`,
  `event.remove()`, `epoll.item(key)`;
- `@packed`, `@packed(n)`, `@bits(n, at: k)` у поля; тип `Float80` и `CLongDouble` как отдельный тип;
- параметр `Array` `indirection: direct | indirect` (имена утвердил координатор) и умолчания форм `Array`;
- типы `Int128`, `UInt128`, `Float128`, `Complex<T>` (имена предложены, их утверждает координатор);
- `read [T]` и `edit [T]` с `requires x.count == n` у параметра функции `@abi(c)`;
- `@abi(c)` без тела вне модуля платформы, результат функции C как второй вход адресов из C, библиотека в
  настройках сборки, а не в `@library`;
- проверки проверочной сборки на возврате из C и на выходных слотах, запись держателя и запрошенного размера,
  таблица хендлеров с принятыми значениями;
- команды `amber import-c`, `amber import-c --update`, `amber foreign-report`.
