# Сертификация

[Документация](README.md) · [Плагины и метакод](compile-time/plugins.md) · [Конфигурация сборки](build-config.md) · [Пакеты](packages.md)

Большую часть кода, который порождают плагины, компилятор проверяет сам: этот код проходит ядро (FLOW,
эффекты, условия) как написанный человеком. Проверить нельзя лишь немногое: плагин языка со скрытыми
параметрами, свою цель генерации кода (например, GPU) и проход после запечатывания. Такие плагины компилятор
принимает на веру, и сертификация определяет, кто за них ручается.

Программист должен иметь возможность сказать: «моя программа доказана везде, кроме записей реестра,
помеченных „на вере“, и у каждой такой записи указано, кто за неё ручается». `amber trust` начинает отчёт с
этого итога:

```
412 доказано, 3 на вере (target gpu-sm90 2.1, ручаются acme, me), 0 без сертификата
```

Проект и обоснование — amber dev/plans/S90.md §13. Систему сертификации с несколькими центрами предложил
Edmond 2026-10-29: «предлагаю идею сертификации», «нужно продумать несколько центров сертификации», «чтобы
нельзя было монополизировать систему». Решения агента отмечены «(агент)».

## Доказательство и сертификат

Это два разных слова:

- **доказательство** проверяет сам компилятор: FLOW, Z3, доказательство в формате LRAT или Alethe;
- **сертификат** подписывает человек или центр сертификации.

Записи, которую проверил компилятор, сертификат не нужен.

## Сначала сужается то, во что надо верить

Сертифицируется только то, что нельзя проверить (агент):

| Что | Как выходит из доверия | Что остаётся на вере |
|---|---|---|
| Решатель | возвращает доказательство в проверяемом формате; его проверяет ядро | шаги формата, которым доверяют; они перечислены в записи |
| Проход после запечатывания (оптимизация MLIR) | даёт свидетельство, которое валидатор проверяет при каждой сборке, где это по силам | валидатор и его предел |
| Своя цель | обычно никак | весь плагин |
| Плагин языка | никак | весь плагин |

В первой версии ответ решателя без доказательства не принимается.

Проходы после запечатывания и свои цели появятся вместе с плагинами компилятора (amber S90 §12); сегодня
[плагины и метакод](compile-time/plugins.md) знают на вере только плагин языка.

## Что утверждает сертификат

Сертификат — подписанное утверждение, которое любой может перепроверить по приложенным материалам проверки.
Это утверждение, а не разрешение: плагин без сертификата собирается в режимах, где доверие не требуется.

| Поле | Смысл и что проверяет сборка |
|---|---|
| субъект | хеш на 256 бит от исходников плагина, всех загружаемых им библиотек и метакода, а также схемы его секции; сборка сравнивает его с загруженным плагином |
| настройки | значения секции плагина или правило над ними, для которых верно утверждение; с другими значениями плагин вне сертификата |
| входы | все доверенные точки входа плагина (проход, цель, плагин языка); вход, которого нет в сертификате, — без сертификата |
| свойство | что утверждается, в терминах ядра: «сохраняет смысл запечатанного HIR на x86_64 при модели памяти v3» |
| допущения | версия семантики, шаги доказательства на веру, внешние программы по хешу; хеш каждой программы сверяется при каждом запуске |
| возможности | импорты песочницы, которые плагин использует; это потолок, и разрешение сверх него делает все записи реестра, которые опираются на плагин, «без сертификата» |
| API | диапазон версий ядра и семантики; версия компилятора сверяется с диапазоном, поэтому новый выпуск компилятора не отменяет все сертификаты |
| уровень | ниже |
| критерии и материалы проверки | опубликованные критерии с версией; хеши корпуса, журналов, доказательств, заметок проверки; `amber certify --recheck` перезапускает их |
| дата выпуска, срок, кто выдал | — |

Сертификаты лежат в пакете плагина или по адресу, который центр называет в конфигурации (поле `address`).
Общего хранилища нет.

## Уровни

| Уровень | Слово в конфигурации | Материалы проверки |
|---|---|---|
| L0 | `own` | только подпись |
| L1 | `reviewed` | исходник проверен по опубликованным критериям |
| L2 | `validated` | L1 и проверка перевода или сравнительное тестирование на опубликованном корпусе с названным пределом |
| L3 | `proved` | машинное доказательство против формальной семантики Efen; проверяющая программа названа, доверенная часть перечислена |

Уровень — это то, что заявил центр. Сколько из заявленного принять, решает конфигурация: у каждого центра
есть потолок (`upTo`), поэтому собственная подпись проекта не выдаёт себя за внешнюю проверку. Правил по
умолчанию у компилятора нет: доверенный вход без правила отклоняется во всех режимах, где доверие требуется.

## Центры сертификации

Центр — это ключ и область: какие входы и пространства имён плагинов он вправе заверять. Без `scope` центр
заверяет всё. Примеры: центр проекта Efen; фирма, которая заверяет только цели для автомобильных
контроллеров; университетская группа, которая заверяет только валидаторы; служба безопасности компании; сам
пользователь. Пока нет двух настоящих центров, центр — это один ключ; наборы ключей с порогом внутри центра,
смена ключей и делегирование приходят позже.

Центры задаются в секции `trust` конфигурации сборки (Edmond, 2026-10-29: «центр сертификации должен
настраиваться в конфиге»). Секция может стоять на любом уровне конфигурации самой сборки: в глобальном
`config.efen` (центры машины или организации), в `workspace.efen`, в `project.efen`. Уровни сливаются, как
остальные поля: побеждает ближний ([конфигурация сборки](build-config.md)). Глобальный файл, который
ставится вместе с компилятором, секции `trust` не содержит. Конфигурация зависимости не добавляет ни центра,
ни правила, ни разрешения.

```efen
config server {
    trust {
        centres {
            efen {
                key: path("keys/efen.pub")
                upTo: validated
            }

            acme {
                key: path("keys/acme.pub")
                scope: [target]
                upTo: validated
                address: "https://certs.acme.example"
            }

            me {
                key: path("keys/me.pub")
                upTo: own
            }
        }

        require {
            target {
                count: 2
                of: [efen, acme, me]
                level: validated
            }

            language {
                count: 1
                of: [me]
                level: own
                modes: [debug, testing]
            }
        }
    }
}
```

- `count` считает разные центры, а не ключи. Делегат центра считается тем же центром.
- Сертификат за пределами области выдавшего центра не засчитывается, и сборка сообщает об этом.
- Свой ключ пользователь может внести в список всегда. Засчитывается он только там, где указан, и не выше
  своего потолка.

## Почему систему нельзя монополизировать

- **Нет встроенного корня и встроенных правил.** Компилятор не знает ни одного центра. `amber trust init`
  перечисляет известные центры наравне и записывает выбор пользователя в конфигурацию.
- **Центр проекта Efen — один из многих** (Edmond, 2026-10-29): особого места в списке у него нет. Список
  известных центров — опубликованный файл. Попадают в него по открытым критериям, и попадание ничего не даёт:
  доверие задаёт только конфигурация проекта.
- **Центр отзывает только свои сертификаты.** Чужой сертификат снимается только опровержением, которое любой
  может воспроизвести: входом, на котором результат плагина не проходит проверку.
- **Две подписи под одним именем.** Если доверенный центр подписал два разных субъекта под одним именем и
  версией, доверие теряет этот центр, а не имя. Запись в открытый журнал не может отнять плагин у остальных.
- **Материалы проверки открыты.** Критерии опубликованы и имеют версии, материалы можно перезапустить.
  Поэтому сертификат — проверяемое утверждение, а не разрешение.

## Режимы

Режим может объявить `trust: required` или `trust: warn`; без объявления — `required`, так что режим
`production` не окажется молча слабее (агент). Правило из `require` может назвать свои режимы (`modes`). В
режиме `warn` плагин на вере без нужного сертификата собирается, а записи реестра, которые на него
опираются, помечаются «на вере, без сертификата».

## Проверка в сборке

- `amber lock` работает с сетью. Он получает сертификаты из пакета плагина или по адресу центра и проверяет
  подписи, области, уровни и сроки. Затем закрепляет каждый сертификат по хешу в `efen.lock` и запоминает
  старшую принятую версию каждого плагина. Lock-файл, откаченный к старой версии, отклоняется.
- `amber build` работает без сети и без часов. Он сверяет субъект, настройки, входы, хеши внешних
  программ, подписи, области, уровни, пороги и диапазон API. Идентичность сборки содержит хеши плагинов и
  вердикт политики, но не хеши сертификатов. Сертификаты записываются в протокол проверки рядом со сборкой,
  поэтому продление сертификата ничего не пересобирает (агент).
- Смена ключа после компрометации — правка конфигурации. Заявления, подписанного одним старым ключом, для
  неё недостаточно.

## Сертификат не даёт прав

Разрешения песочницы задаются только в секции плагина ([плагины](compile-time/plugins.md#чтение-мира-и-внешние-программы)).
Если плагин использует больше, чем указано в сертификате, плагин работает, но записи реестра, которые на
него опираются, помечаются «на вере, без сертификата».

## Реестр свойств и `amber trust`

Компилятор ведёт для каждой функции реестр свойств. Запись реестра — одно свойство в одной точке:
`requires`, `ensures`, инвариант, `assert`, предложение или требование плагина, проверка при выполнении,
которую генератор может убрать. Статусы записи:

- доказано FLOW;
- доказано проверенным доказательством;
- на вере, ручаются…;
- на вере, без сертификата;
- неизвестно, проверяется при выполнении;
- нарушено.

Поле `on` записи называет сертификаты, на которые она опирается. Проход после запечатывания ничего не
доказывает: он — допущение под всеми записями функций, которых коснулся.

```
parse  ensures result.count <= input.count
  доказано FLOW, записи 3, 4
  на вере: код цели gpu-sm90 2.1 (blake3-256:9f…)
    ручается acme (validated) «сохраняет смысл запечатанного HIR, sm_90»; сертификат 4c1e…
    ручается me (own); сертификат 77aa…
    правило target: нужно 2 из [efen, acme, me] уровня validated: acme — да; me не выше own — нет
```

`amber trust --why-not <плагин>` печатает ту же таблицу и отмечает невыполненное правило.

## Версии

- **v0, без криптографии:** поле `on` в реестре; каждая запись на вере называет плагин по хешу;
  `trust { allow: [<хеш плагина>] }` в конфигурации проекта, где подписью служит сам репозиторий; режимы
  с `trust`; `amber trust` и `--why-not`.
- **v1, когда появится первый доверенный плагин:** хеш на 256 бит, подпись ed25519, `amber key new`,
  `amber certify` уровней `own` и `reviewed`, центры из одного ключа и области, правила `require`,
  закрепление в `efen.lock` со старшей версией, сроки при `amber lock`. Первый проход или цель приходит
  вместе со сравнительным тестированием уровня `validated` или ждёт его: иначе есть только `own`, и
  проверка превращается в формальность.
- **v2:** подписанные списки отзыва, `amber audit` в CI (отозванный сертификат — ошибка, истёкший —
  предупреждение, чтобы все проекты не упали в один день), опровержения, недоверие с даты, наборы ключей и
  их смена, делегирование, журналы прозрачности (по желанию, несколько, ни один не обязателен).
