# Алгоритм работы layout

[Layout](layout.md) · [Доказательство структур](layout-proofs.md) · [Каталог структур](layout-catalogue.md) ·
[Владение](../types/ownership.md)

Статус: модель на бумаге (2026-11-09). Компилятор строит из неё пока только часть: что именно, сказано в
[`layout.md`](layout.md#состояние-в-компиляторе).

`layout` описывает, как лежат в памяти связанные данные: списки, деревья, графы. Компилятор по этому описанию и по
коду функций доказывает, что программа не обращается к мёртвой памяти, не освобождает её дважды и не теряет.
Доказательство строится по одной функции за раз и не требует от программиста ничего, кроме законов структуры.

## Центральные законы

Компилятор доказывает восемь законов для любой программы на `layout`. Первые четыре — безопасность памяти, которую
получает программист; остальные — то, на чём держится доказательство.

1. **Нет висячих указателей.** После события, которое уничтожает значение, переносит его в другую память или меняет
   его вид, ни один указатель на него не ведёт в мёртвую или чужую память.
2. **Один владелец.** У значения в каждый момент ровно один владелец: `own`, `anchor` или множество, если значение —
   его член. Поэтому значение уничтожается ровно один раз.
3. **Указатель знает своё множество.** Тип `Items.Item` говорит, из какого множества указатель. Указатель на элемент
   другого множества в этот тип не попадёт; это доказывает проверка типов.
4. **Элементы не пересекаются.** Разные элементы не делят ни байта памяти: места раздаёт множество.
5. **Время жизни выводится из кода.** Его задают события: `take`, уничтожение, вызовы функций, которые уничтожают
   значение или отдают владение. Руками время жизни не пишется. Указатель не живёт дольше того, на что указывает.
6. **Ничего не теряется.** Всё выданное возвращается или передаёт владельца дальше; иначе — ошибка «утечка».
   Исключение — член множества: он умирает при `free` или вместе с множеством.
7. **Доказательство локально.** Каждая функция проверяется сама по себе, по прототипам вызванных функций, а каждое
   событие — по своей окрестности. Законы структуры пишет программист, условия функций компилятор выводит сам.
8. **Граница `layout` закрыта.** Структуру меняют только функции `layout`. Снаружи структура видна только в
   состояниях, где все её законы верны.

## Что описывает layout

| Понятие | Что это |
|---|---|
| множество `set Items: Item` | элементы одной формы; расположение в памяти не обещано |
| `Items.Item` | указатель на элемент множества `Items` |
| `own` | исключительное владение: других указателей на значение нет |
| `anchor` | владение, при котором на значение могут смотреть имена; точка его уничтожения |
| имя | указатель без владения (`prev`, `parent`, ребро графа) |
| член множества | элемент, которого не держит ни `own`, ни `anchor`; им владеет множество |
| закон | условие формы структуры в `invariants`, пишется руками |

Выделение и освобождение памяти — переход элемента между множествами: память ОС — тоже множество
([подробнее](layout.md#выделение-и-освобождение--переход-между-множествами)).

## Односвязный список

```efen
layout {
    set Items: Item

    struct Item {
        var next: own Items.Item? = null
    }

    fn new() -> own Items.Item { … }

    fn setNext(self: mut Items.Item, next: own Items.Item) {
        self.next = take next
    }
}
```

Каждый элемент владеет следующим через `own`, и никто другой этим элементом не владеет.

**Почему `setNext` безопасен.** Параметр `own` значит, что вызывающий отдал функции единственное владение `next`. Был
бы `next` в списке, его владелец сидел бы в слоте списка, и отдать его вызывающий смог бы только после `take` оттуда.
Значит, элемент под `own` по построению не лежит в структуре, и отдельного слова для этого не нужно.

Остаются две опасности, и обе закрывают предусловия, которые компилятор выводит из тела сам:

| Предусловие | Без него |
|---|---|
| `self.next == null` | запись `self.next = take next` теряет старый хвост `self` — утечка |
| `next.next == null` | в хвосте `next` может лежать `self`, и запись замыкает цикл, который никто не уничтожит |

Предусловия попадают в прототип `setNext`, и их доказывает вызывающий.

## Двусвязный список

```efen
layout {
    set Items: Item

    struct Item {
        var next: anchor Items.Item? = null
        var prev: Items.Item? = null
        invariants { next == null || next!.prev == self }
    }

    struct List {
        var head: anchor Items.Item? = null
        invariants { head == null || head!.prev == null }
    }

    fn insertAfter(self: mut Items.Item, node: anchor Items.Item) {
        node.prev = self
        node.next = take self.next
        if let old = node.next { old.prev = node }   // старый сосед смотрит назад на node
        self.next = take node
    }
}
```

`next` — якорь: он определяет, где элемент уничтожат, а имя `prev` на элемент при этом допустимо. Закон стоит на
слоте якоря: элемент в `next` смотрит назад на того, кто его держит. Поэтому имя на элемент одно и лежит в известном
месте: `n.next!.prev`.

Без строки `old.prev = node` старый сосед смотрел бы назад на `self`, хотя лежит уже после `node`: закон нарушен, и
компилятор отвергает функцию. Предусловие `node.next == null` выводится, как в односвязном списке.

**Удаление.** Перед уничтожением элемента компилятор спрашивает закон, где имена на него, и проверяет, что каждое
переписано:

```efen
fn remove(n: mut Items.Item) {
    guard let p = n.prev else { return }
    guard let node = take p.next else { return }   // якорь n лежит в слоте узла n.prev
    p.next = take node.next
    if let b = p.next { b.prev = p }               // единственное имя на n переписано
    destroy(take node)
}
```

Закон обратной ссылки руками не пишется (`prev!.next == self` не нужен): он сломал бы каждую передачу оторванного
элемента через вызов. Обратная ссылка элемента, вынутого в функцию, — имя, которое функция ведёт сама
([правило](layout-proofs.md#правила-доказательства)).

## Как компилятор это доказывает

Структура доказывается индукцией по событиям.

| Шаг | Что доказывается |
|---|---|
| закон | форма структуры, пишет программист |
| база | закон верен в начальном состоянии: пустой список, только что рождённый элемент |
| шаг | каждое событие, меняющее структуру, сохраняет закон |
| крайнее состояние | уничтожение, перенос и смена вида не оставляют висячих указателей |

Остальные состояния получаются из начального цепочкой событий и отдельно не доказываются.

**Окрестность события.** Закон проверяется только на элементах, которых событие касается, и на местах, куда указывает
сам закон. В `insertAfter` это `self`, `node` и `old`: остальные элементы событие не тронуло, и закон для них верен без
проверки. Так работают natural proofs (Dryad, PLDI 2013): решатель Z3 получает короткую формулу без рекурсии.

**Где лежит доказательство отсутствия висячих указателей.** Закон говорит, где имена на значение могут лежать; код
события показывает, что каждое мертво или переписано. Чем точнее закон, тем больше работы при каждой вставке и тем
меньше при удалении.

| Доказательство | Закон говорит | Удаление делает | Пример |
|---|---|---|---|
| в структуре | имён нет | ничего | односвязный список |
| смешанное | имя одно, в известном месте | переписывает его | двусвязный список, дерево с родителем |
| в коде | имена где угодно | проходит всех держателей | [свободный граф](#свободный-граф) |

Разбор каждой структуры: [доказательство структур](layout-proofs.md).

## Граница layout

Внутри функции закон может быть нарушен: `insertAfter` между строками держит структуру сломанной. Снаружи это не видно
никому, потому что границу защищают четыре правила.

1. **Структуру меняют только функции `layout`.** Писать в поля элементов может только функция, объявленная внутри
   `layout`. Внешний код читает и вызывает функции. Иначе запись `n.prev = x` в любом месте программы обходила бы
   закон, и доказательство пришлось бы вести по всей программе.
2. **Закон верен на входе и выходе каждой публичной функции и при каждом вызове наружу.** Пока закон нарушен, вызов
   внешнего кода — ошибка: внешний код мог бы войти обратно и застать структуру сломанной.

   ```efen
   fn remove(n: mut Items.Item, onRemove: fn(Items.Item)) {
       guard let p = n.prev else { return }
       guard let node = take p.next else { return }
       p.next = take node.next      // закон нарушен: следующий ещё смотрит на n
       onRemove(node)               // ошибка: внешний код вызван при нарушенном законе
       …
   }
   ```

3. **Прототип публичной функции говорит только о видимом снаружи.** Если выведенное условие касается внутреннего
   состояния, которое вызывающий проверить не может, оно становится законом `layout`, верным на границе всегда, или
   функция отвергается.
4. **Указатель, отданный наружу, подчиняется правилам хранения** из следующего раздела. Результат `anchor` или `own` —
   пометка «отдаёт»: вызывающий получает обязанность уничтожить значение.

## Указатели за пределами layout

Передать указатель в функцию просто: имя параметра умирает при её возврате. Трудно его сохранить. Указатель на
элемент `e` из одного `layout` лежит в поле держателя `h` вне его — в другом `layout` или в обычной структуре.
Освобождает `e` код своего `layout`, и про `h` этот код ничего не знает. Поэтому доказывается не время жизни
держателя само по себе, а его отношение к времени жизни `e`: держатель умирает или переписывает указатель раньше,
чем `e` освободят.

| Способ | Почему держатель не переживёт элемент | Цена | Пример |
|---|---|---|---|
| вложенность | держатель лежит внутри `e` или внутри множества, вложенного в `e`, и умирает вместе с ним | нет | индекс внутри страницы |
| заём | держатель держит заём `layout` элемента: пока он жив, элемент освобождается только функцией, которая получает и держатель | `layout` заморожен для освобождения | курсор, итератор |
| объявленная связь | `layout` элемента объявляет поле держателя держателем своих имён, и функция освобождения обязана его переписать | оба `layout` доказываются вместе | индекс над таблицей, LRU над хеш-таблицей |

Если ни один способ не доказан — ошибка в месте, где указатель кладут: «время жизни держателя не связано с `e`».
Заём вне `layout` записывается [структурой над источником](layout.md#открытые-вопросы) (вопрос 2).

Остальной код вне `layout`:

| Держатель | Правило |
|---|---|
| параметр функции | имя умирает при возврате |
| замыкание, сопрограмма | захват держит заём (S102) |
| коллекция имён (`Vector<Items.Item>`) | держатель: умирает целиком, если может содержать освобождённый элемент |
| код C | точка доверия: условие результата и код `model` |
| другой поток | `shared anchor`, не продумано |

Слабой ссылки с проверкой при выполнении (поколение при месте, как в `slotmap`) в модели нет: это проверка, а не
доказательство.

## Свободный граф

В графе узлы ссылаются друг на друга с любыми циклами и петлями, и простыми правилами владения это не выразить.
Доказательством корректности здесь служит сам код, который отвечает на вопрос «может ли остаться висячая ссылка».

Самый простой граф: у каждого узла есть список узлов, на которые он ссылается.

```
 граф: A→B, A→C, B→C, C→A, C→C (петля)

 множество Vertices — память всех узлов держит оно
 ┌──────────────┐   ┌──────────────┐   ┌──────────────┐
 │ A            │   │ B            │   │ C            │
 │ neighbors:   │   │ neighbors:   │   │ neighbors:   │
 │   B, C       │   │   C          │   │   A, C       │
 └──────────────┘   └──────────────┘   └──────────────┘
   каждый элемент neighbors — имя: ссылка без владения
```

```efen
layout {
    set Vertices: Vertex

    struct Vertex {
        var label: Int
        var neighbors: Vector<Vertices.Item>    // узлы, на которые ссылается этот
    }

    fn addVertex(label: Int) -> Vertices.Item {
        return Vertices.new(Vertex(label: label, neighbors: []))
    }

    fn addEdge(from: Vertices.Item, to: Vertices.Item) {
        from.neighbors.append(to)               // to == from — петля
    }

    fn removeEdge(from: Vertices.Item, to: Vertices.Item) {
        from.neighbors.removeAll(where: { $0 == to })
    }

    fn removeVertex(v: Vertices.Item) {
        for w in Vertices {                     // каждый узел множества
            w.neighbors.removeAll(where: { $0 == v })
        }
        Vertices.free(v)                        // конец жизни v
    }
}
```

Записи `Vertices.new`, `Vertices.free` и перебор множества — наброски.

**Кто чем владеет.** Узлы — члены множества `Vertices`: их память держит множество, а не другие узлы. Ссылки в
`neighbors` — имена, поэтому циклы и петли владения не создают. Владелец узла — функция, которая его освобождает:
точка вызова `removeVertex` — конец жизни узла, а её тело — доказательство.

**Что доказывает компилятор в `removeVertex`.** Имена на `v` могут лежать только в `neighbors` узлов множества: других
полей типа `Vertices.Item` в `layout` нет. Проход по всем узлам убирает из каждого списка все ссылки на `v`, и
компилятор выводит инвариант прохода «в пройденных узлах ссылок на `v` нет». Проход кончился — пройдены все узлы, и
`Vertices.free(v)` не оставляет висячих ссылок. Список самого `v` умирает вместе с ним, поэтому петлю `v → v` отдельно
убирать не нужно. Без прохода или с проходом, который останавливается раньше, — ошибка.

Остальные функции доказываются сразу: `addEdge` и `removeEdge` только добавляют и убирают имена, а `addVertex`
рождает узел без ссылок на него.

Условия, при которых это работает:

1. все держатели имён известны: поля типа `Vertices.Item` и коллекции таких имён в `layout` (`neighbors`), переменные,
   захваты;
2. сводка `removeVertex` говорит «освобождает `v`», и у вызывающего умирают имена, которые могут быть равны `v`;
3. пока жив перебор `Vertices`, вызов, освобождающий его элементы, — ошибка, кроме освобождения через курсор: внутри
   прохода `removeVertex` узлы не освобождаются, освобождение идёт после;
4. освобождённое место не путается с новым: адрес не устаревает, а индекс безопасен только вместе с условием 2.

**Цена.** Удаление узла проходит все узлы и все их списки.

### Граф с обратными ссылками

Если удалять нужно быстро, у каждого узла держат ещё и список тех, кто ссылается на него.

```
 граф: A→B, A→C, B→C, C→A, C→C (петля)

 ┌──────────────┐   ┌──────────────┐   ┌──────────────┐
 │ A            │   │ B            │   │ C            │
 │ neighbors:   │   │ neighbors:   │   │ neighbors:   │
 │   B, C       │   │   C          │   │   A, C       │
 │ referrers:   │   │ referrers:   │   │ referrers:   │
 │   C          │   │   A          │   │   A, B, C    │
 └──────────────┘   └──────────────┘   └──────────────┘
```

```efen
layout {
    set Vertices: Vertex

    struct Vertex {
        var label: Int
        var neighbors: Vector<Vertices.Item>    // на кого ссылается этот узел
        var referrers: Vector<Vertices.Item>    // кто ссылается на этот узел
        invariants {
            forall w in neighbors: w.referrers.contains(self)
            forall w in referrers: w.neighbors.contains(self)
        }
    }

    fn addEdge(from: Vertices.Item, to: Vertices.Item) {
        from.neighbors.append(to)
        to.referrers.append(from)
    }

    fn removeVertex(v: Vertices.Item) {
        for w in v.referrers { w.neighbors.removeAll(where: { $0 == v }) }
        for w in v.neighbors { w.referrers.removeAll(where: { $0 == v }) }
        Vertices.free(v)
    }
}
```

Законы здесь пишутся в обе стороны, и это не обратный закон, который ломает передачу через вызов: оба поля — имена,
а не якоря, узлы никто не отрывает от структуры. Граф без кратных рёбер; кратные рёбра требуют закона о числе
вхождений (`count`) вместо `contains`.

**Что доказывает компилятор в `removeVertex`.** Если `v` лежит в `u.neighbors`, то по закону узла `u` в
`v.referrers` лежит `u`; если `v` лежит в `u.referrers`, то `u` лежит в `v.neighbors`. Значит, все имена на `v` —
в узлах двух списков самого `v`, и два прохода по ним убирают каждое. Доказательство смешанное: закон сузил поиск до
двух списков, код проходит их. Закон после удаления проверяется только на узлах, которых проходы коснулись.

**Цена.** Удаление смотрит только на соседей `v`, зато каждая вставка ребра пишет в два места, а у каждого узла два
списка. Подробный разбор той же формы на цепочках рёбер — в [разборе](layout-proofs.md#граф-со-входящими-рёбрами).

## Где модель не работает

**Владение по рёбрам произвольного графа.** Если узлы держатся якорями-рёбрами, цикл якорей ничей с момента, когда
замкнулся. Доказать, что запись `t.f = take r` цикла не замыкает, значит доказать, что `t` не лежит в дереве `r`, а это
достижимость по пути любой длины. По окрестности события её не проверить. Компилятор принимает такую запись в трёх
случаях, где ответ виден из кода (`r` только что оторван, `r` пришёл без детей-якорей, `t` сам только что взят как
корень), иначе выводит предусловие или сообщает ошибку. Граф строится из имён с владельцем-функцией.

**Кольцо произвольной длины.** Через узел события проходит цепочка каждого узла кольца, поэтому закон кольца — тоже
достижимость. Кольцо остаётся открытым вопросом.

**Жизнь множества целиком.** Когда умирает множество верхнего уровня, не определено, а от этого зависит, когда
умирает забытый член множества ([открытый вопрос 1](layout.md#открытые-вопросы)).
