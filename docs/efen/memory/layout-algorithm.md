# Алгоритм работы layout

[Layout](layout.md) · [Доказательство структур](layout-proofs.md) · [Каталог структур](layout-catalogue.md) ·
[Владение](../types/ownership.md)

Статус: модель на бумаге (2026-11-09). Компилятор строит из неё пока только часть: что именно, сказано в
[`layout.md`](layout.md#состояние-в-компиляторе).

`layout` описывает, как лежат в памяти связанные данные: списки, деревья, графы. Компилятор по этому описанию и по
коду функций доказывает, что программа не обращается к мёртвой памяти, не освобождает её дважды и не теряет.
Доказательство строится по одной функции за раз и не требует от программиста ничего, кроме законов структуры.

## Центральные гарантии

Компилятор доказывает восемь гарантий для любой программы на `layout`. Первые четыре — безопасность памяти, которую
получает программист; остальные — то, на чём держится доказательство. Законом дальше называется только строка
`invariants`, которую пишет программист.

1. **Нет висячих указателей.** После события, которое уничтожает значение, переносит его в другую память или меняет
   его вид, ни один указатель на него не ведёт в мёртвую или чужую память.
2. **Один владелец, одно уничтожение.** У значения в каждый момент ровно один владелец: `own`, `anchor` или
   множество, если значение лежит под ним. После уничтожения все указатели на значение недействительны, поэтому
   второе уничтожение — ошибка.
3. **Указатель знает своё множество и его экземпляр.** `Items.Item` хранит, из какого множества и из какого
   экземпляра `layout` пришёл указатель ([производные типы дескриптора](addresses.md#производные-типы-дескриптора)).
   Указатель на элемент другого множества или другого экземпляра — ошибка.
4. **Элементы не пересекаются.** Разные элементы не делят ни байта памяти: места раздаёт множество.
5. **Время жизни выводится из кода.** Его задают события: `take`, уничтожение, вызовы функций, которые уничтожают
   значение или отдают владение. Руками время жизни не пишется. Указатель не живёт дольше того, на что указывает.
6. **Память берётся явно и возвращается явно.** Каждый выданный элемент на каждом пути возвращается или передаёт
   владельца дальше. Элемент под множеством возвращает функция освобождения или код, который уничтожает источник его
   памяти; источник умирает только без выданных элементов, а элементы под множеством умирают вместе с ним. Возврат при выходе процесса не считается: у глобального `layout` есть явная
   функция завершения. Иначе — ошибка «утечка».
7. **Доказательство локально.** Каждая функция проверяется сама по себе, по прототипам вызванных функций, а каждое
   событие — по своим проверяемым элементам. Законы структуры пишет программист, условия функций компилятор выводит сам.
8. **Граница `layout` закрыта.** Структуру меняют только функции `layout`. Снаружи структура видна только в
   состояниях, где все её законы верны.

## Что описывает layout

| Понятие | Что это |
|---|---|
| множество `set Items: Item` | элементы одной формы; расположение в памяти не обещано |
| `Items.Item` | указатель на элемент множества `Items` |
| `own` | исключительное владение: других указателей на значение нет |
| `anchor` | владение, при котором на значение могут смотреть указатели; точка его уничтожения |
| невладеющий указатель | указатель без владения: `prev`, `parent`, ребро графа |
| элемент под множеством | элемент, которого не держит ни `own`, ни `anchor`; им владеет множество |
| закон | условие формы структуры в `invariants`, пишется руками |

Указатель сам по себе только читает. Запись в поле через указатель требует права `mut` на область, в которой лежит
цель: на сам элемент (`self: mut Items.Item`) или на весь объект (`self: mut Self`)
([права в типе указателя](../types/ownership.md)). Первое годится, когда записываемые элементы различны по
построению (список, дерево); второе — когда два параметра могут указывать на один элемент (петля в графе).

**Создание и освобождение.** Создание элемента возвращает `own`: на новый элемент ещё никто не указывает, и все его
поля задаются сразу. Освобождение `free` принимает только `own`. Память по указателю `anchor` или `mut` (в том числе на
элемент под множеством) сначала переводится в `own`, и это единственная точка проверки висячих указателей. Компилятор
доказывает две вещи:

1. владеющее поле отпущено в этой функции: якорь или поле `own`, которое держало элемент, взято через `take`, или
   элемент лежит под множеством и владеющего поля у него нет;
2. по всем законам `layout` на память больше не ссылается ни один невладеющий указатель: функция нашла их и обнулила
   или переписала.

Указатели вызывающего на эту память становятся недействительными в точке вызова по сводке функции («освобождает `x`»).
Без этого перехода компилятор не даёт ничего делать; после него с `own` можно делать что угодно. При освобождении
поля `own` освобождаются вместе с элементом, а поля-якоря обязаны быть пусты, и это требование распространяется на
всё поддерево `own`: ни у одного значения, которое `free` освобождает неявно, поле-якорь не должно держать элемент.
Создание называется `Items.new`; это то же, что `Items.allocate` в [адресах](addresses.md#производные-типы-дескриптора).

Указатель внешнего мира на элемент внутри `layout` — невладеющий; `own` вне `layout` бывает только у оторванного
элемента.

**Уничтожение источника памяти.** Код, который возвращает источник памяти, — `System.unmap` области, завершение
экземпляра `layout`, — событие карты, как `free`: он одним шагом кончает жизнь всех элементов под множествами,
память которых держит источник. Его обязательства: (1) каждый выданный из этих множеств элемент (`own`, `anchor`,
`lend`) вернулся — источник умирает без выданных элементов; (2) нет живого заимствования экземпляра; (3) каждый
хранимый указатель на элемент этих множеств лежит в элементе, который умирает на этом же шаге, или у держателя
объявленной связи, которого событие очищает функцией его `layout` до шага; (4) сводка события — «освобождает все
элементы множеств S₁…Sₙ этого экземпляра», и указатели вызывающего на них недействительны в точке вызова. Указатели
между элементами освобождаемых множеств не висячие: их после шага никто не читает. Прохода по каждому элементу и
перехода каждого в `own` нет.

```efen
let n = Items.new(Item(label: 1))       // n: own Items.Item, на него никто не указывает
free(take n)                            // own без полей-якорей освобождается без проверок
```

**Перенос** — создание элемента на новом месте и освобождение старого. Перед освобождением старого все указатели на
него переписаны на новый, по тому же правилу. Голый адрес элемента, который `layout` может перенести, вне `layout` не
хранится: внешний мир обращается к нему через функции `layout`.

Выделение и освобождение памяти — переход элемента между множествами: память ОС — тоже множество
([подробнее](layout.md#выделение-и-освобождение--переход-между-множествами)).

## Односвязный список

```efen
layout {
    set Items: Item

    struct Item {
        var next: own Items.Item? = null
    }

    fn new() -> own Items.Item { … }

    fn setNext(self: mut Self, item: Items.Item, next: own Items.Item) {
        item.next = take next
    }
}
```

Каждый элемент владеет следующим через `own`, и никто другой этим элементом не владеет.

**Почему `setNext` безопасен.** Параметр `own` значит, что вызывающий отдал функции единственное владение `next`. Был
бы `next` в списке, его владелец сидел бы в слоте списка, и отдать его вызывающий смог бы только после `take` оттуда.
Значит, элемент под `own` по построению не лежит в структуре, и отдельного слова для этого не нужно.

Остаётся одна опасность, и её закрывает предусловие, которое компилятор выводит из тела сам: `item.next == null`.
Без него запись `item.next = take next` теряет старый хвост `item` — утечка. Цикл здесь невозможен: чтобы отдать
`next` как `own`, вызывающий отказывается от всех указателей внутрь его хвоста, поэтому `item` в этом хвосте лежать не
может. Это верно и для указателя, который вызывающий получил из `layout` наружу: `own` внешнего мира в параметр
`own` функции `layout` не подходит (граница миров). У варианта с `anchor` (`push` в [разборе](layout-proofs.md#односвязный-список)) указатели на хвост допустимы, и там
нужно второе предусловие, `next.next == null`.

Предусловие попадает в прототип `setNext`, и его доказывает вызывающий.

## Двусвязный список

```efen
layout {
    set Items: Item

    struct Item {
        var next: anchor Items.Item? = null
        var prev: Items.Item? = null
        invariants { next == null || next!.prev == self }
    }

    struct List {
        var head: anchor Items.Item? = null
        invariants { head == null || head!.prev == null }
    }

    fn insertAfter(self: mut Self, a: Items.Item, node: anchor Items.Item) {
        node.prev = a
        node.next = take a.next
        if let old = node.next { old.prev = node }   // старый сосед смотрит назад на node
        a.next = take node
    }
}
```

`next` — якорь: он определяет, где элемент уничтожат, а указатель `prev` на элемент при этом допустим. Закон стоит на
поле-якорь: элемент в `next` смотрит назад на того, кто его держит. Поэтому указатель на элемент один и лежит в известном
месте: `n.next!.prev`.

Без строки `old.prev = node` старый сосед смотрел бы назад на `a`, хотя лежит уже после `node`: закон нарушен, и
компилятор отвергает функцию. Предусловие `node.next == null` выводится, как в односвязном списке.

**Удаление из середины.** Удаляем `N` из `A ⇄ N ⇄ B`:

```
до:     A ⇄ N ⇄ B
шаг 1:  вынуть N из A.next          — якорь N теперь у функции
шаг 2:  A.next = B                  — A смотрит мимо N
шаг 3:  B.prev = A                  — B смотрит назад мимо N
шаг 4:  на N никто не указывает     — anchor → own
шаг 5:  free(N)
после:  A ⇄ B
```

```efen
fn remove(self: mut Self, n: Items.Item) {
    let a = n.prev!                         // сосед слева; голову удаляет removeFirst
    let node = take a.next!                 // шаг 1
    a.next = take node.next                 // шаг 2
    if let b = a.next { b.prev = a }        // шаг 3
    let alone: own Items.Item = take node   // шаг 4: компилятор доказывает, что указателей на N нет
    free(take alone)                        // шаг 5
}
```

На шаге 4 компилятор спрашивает закон, где могут лежать указатели на `N`. Закон на якоре отвечает: только в
`N.next!.prev`, то есть в `B.prev`, и он переписан на шаге 3. Собственное поле `N.prev` освобождается вместе с `N`.
Что `take a.next!` вынимает именно `N`, тоже следует из закона: якорь `N` лежит в поле того узла, на который
указывает `N.prev`. Предусловие «`N` в списке и не первый» компилятор выводит сам.

Закон на обратном указателе руками не пишется (`prev!.next == self` не нужен): он сломал бы каждую передачу оторванного
элемента через вызов. Обратный указатель элемента, вынутого в функцию, — указатель, который функция ведёт сама
([правило](layout-proofs.md#правила-доказательства)).

## Как компилятор это доказывает

Структура доказывается индукцией по событиям.

| Шаг | Что доказывается |
|---|---|
| закон | форма структуры, пишет программист |
| база | закон верен в начальном состоянии: пустой список, только что рождённый элемент |
| шаг | каждое событие, меняющее структуру, сохраняет закон |
| крайнее состояние | уничтожение, перенос и смена вида не оставляют висячих указателей |

Остальные состояния получаются из начального цепочкой событий и отдельно не доказываются.

**Окрестность события.** Закон проверяется только на элементах, которых событие касается, и на местах, куда указывает
сам закон. В `insertAfter` это `a`, `node` и `old`: остальные элементы событие не тронуло, и закон для них верен без
проверки. Так работают natural proofs (Dryad, PLDI 2013): решатель Z3 получает короткую формулу без рекурсии.

**Где лежит доказательство отсутствия висячих указателей.** Закон говорит, где указатели на значение могут лежать; код
события показывает, что каждое мертво или переписано. Чем точнее закон, тем больше работы при каждой вставке и тем
меньше при удалении.

| Доказательство | Закон говорит | Удаление делает | Пример |
|---|---|---|---|
| в структуре | указателей нет | ничего | односвязный список |
| смешанное | указатель один, в известном месте | переписывает его | двусвязный список, дерево с родителем |
| в коде | указатели где угодно | проходит всех держателей | [свободный граф](#свободный-граф) |

Разбор каждой структуры: [доказательство структур](layout-proofs.md).

## Граница layout

Внутри функции закон может быть нарушен: `insertAfter` между строками держит структуру сломанной. Снаружи это не видно
никому, потому что границу защищают четыре правила.

0. **Ворота — функции `public`.** Функции `layout`, как все функции efen, по умолчанию `internal`
   ([видимость](../visibility.md)): их вызывает код этого `layout`. Внешний мир вызывает только функции, объявленные
   `public`, — ворота `layout`. Правила ниже о «публичной функции» говорят о них.
1. **Структуру меняют только функции `layout`.** Писать в поля элементов может только функция, объявленная внутри
   `layout`. Внешний код читает и вызывает функции. Иначе запись `n.prev = x` в любом месте программы обходила бы
   закон, и доказательство пришлось бы вести по всей программе.
2. **Закон верен на входе и выходе каждой публичной функции и перед каждым вызовом, который может войти обратно.**
   Пока закон нарушен, запрещён вызов, сводка которого может читать поля этого `layout` или вызывать его функции:
   неизвестная функция, замыкание, обратный вызов, деструктор с пользовательским кодом. Операции контейнера над
   указателями (`append`, `removeAll` с условием из одного сравнения) этого не делают и разрешены.

   ```efen
   fn remove(self: mut Self, n: Items.Item, onRemove: fn(Items.Item)) {
       guard let p = n.prev else { return }
       guard let node = take p.next else { return }
       p.next = take node.next      // закон нарушен: следующий ещё смотрит на n
       onRemove(node)               // ошибка: замыкание может войти обратно в layout
       …
   }
   ```

3. **Прототип публичной функции говорит только о видимом снаружи.** Выведенное условие должно выражаться через поля,
   которые вызывающий может прочитать (`n.prev!.next == n` — «`n` в списке»). Если это невозможно, функция
   отвергается с подсказкой: условие о внутреннем состоянии записать законом `layout`. Сам компилятор законов не
   добавляет.
4. **Граница миров.** Что внешний мир получает от ворот, говорит тип результата; вариантов три.

   | Тип результата | Что это | Как кончается |
   |---|---|---|
   | `own self.slots.Item` (`own` с источником) | **выдача во внешнее владение**: снаружи настоящий `own`, внешний держатель один; память остаётся в `self.slots`, место помечено выданным, и внутренний код его поля не читает и не пишет | вернуть можно только на своё место функцией `layout` (`pool.release(slot: take s)`); полнота карты требует возврата |
   | `mut Items.Item?`, `edit …`, `read …` (место в результате) | **частичный доступ**: элемент остаётся во владении `layout`, вызывающий получает доступ с этим правом; пока доступ жив, источник (`self`) занят, и второго доступа к элементу внешний мир не получит | доступ кончается вместе со ссылкой; к `free` и параметру `own` не подходит ([место в результате](../types/ownership.md#место-в-результате-функции)) |
   | `own Items.Item` (`own` без источника) | **оторванный элемент**: функция вынула его из структуры и доказала переход в `own`; `layout` о нём ничего не держит, обратные указатели пусты | вызывающий освобождает его `free` или передаёт дальше |

   Указатель на элемент без права и без `own` (`-> Items.Item`) снаружи только читает и становится недействительным
   при любом вызове, сводка которого может освободить или перенести элемент; хранится в поле только одним из трёх
   способов следующего раздела.

## Указатели за пределами layout

Передать указатель в функцию просто: указатель в параметре недействителен после её возврата. Трудно его сохранить. Указатель на
элемент `e` из одного `layout` лежит в поле держателя `h` вне его — в другом `layout` или в обычной структуре.
Освобождает `e` код своего `layout`, и про `h` этот код ничего не знает. Поэтому доказывается не время жизни
держателя само по себе, а его отношение к времени жизни `e`: держатель умирает или переписывает указатель раньше,
чем `e` освободят.

| Способ | Почему держатель не переживёт элемент | Цена | Пример |
|---|---|---|---|
| вложенность | держатель лежит внутри `e` или внутри множества, вложенного в `e`, и умирает вместе с ним | если `e` переносится (`area`, `set area`), указатели внутри него переписываются; иначе нет | индекс внутри страницы |
| заимствование | держатель держит заимствование `layout` элемента: пока он жив, элемент освобождается только функцией, которая получает и держатель; на `free(e)` его поле переписано или недействительно, как `Cursor.current` внутри `layout` | `layout` заморожен для освобождения | курсор, итератор |
| объявленная связь | `layout` элемента держит обратный указатель на держателя под двусторонним законом, как граф с обратными указателями; функция освобождения находит держателя по нему и очищает его вызовом функции `layout` держателя | сводка вызванной функции обязана говорить «переписывает все указатели на `e`» и «не вызывает функций `layout` элемента», иначе вызов при нарушенном законе запрещён | индекс над таблицей, LRU над хеш-таблицей |

Если ни один способ не доказан — ошибка в месте, где указатель кладут: «время жизни держателя не связано с `e`».
Каждый `layout` доказывается сам, по сводкам функций другого, а не вместе с ним. Заимствование вне `layout`
записывается структурой с параметром источника (`ListCursor<Src: Origin>` в
[`layout.md`](layout.md#открытые-вопросы)).

Остальной код вне `layout`:

| Держатель | Правило |
|---|---|
| параметр функции | указатель недействителен после возврата |
| замыкание, корутина | захват держит заимствование (S102) |
| локальная переменная или временное значение любого типа (`Vector<Items.Item>`, структура) | недействительно целиком, если может содержать освобождённый элемент |
| поле структуры, коллекция в поле | только одним из трёх способов выше |
| код C | точка доверия: условие результата и код `model` |
| другой поток | `shared anchor`, не продумано |

Слабой ссылки с проверкой при выполнении (поколение при месте, как в `slotmap`) в модели нет: это проверка, а не
доказательство.

## Свободный граф

В графе узлы ссылаются друг на друга с любыми циклами и петлями, и простыми правилами владения это не выразить.
Доказательством корректности здесь служит сам код, который отвечает на вопрос «может ли остаться висячий указатель».

Самый простой граф: у каждого узла есть список узлов, на которые он ссылается.

```
 граф: A→B, A→C, B→C, C→A, C→C (петля)

 множество Vertices — память всех узлов держит оно
 ┌──────────────┐   ┌──────────────┐   ┌──────────────┐
 │ A            │   │ B            │   │ C            │
 │ neighbors:   │   │ neighbors:   │   │ neighbors:   │
 │   B, C       │   │   C          │   │   A, C       │
 └──────────────┘   └──────────────┘   └──────────────┘
   каждый элемент neighbors — указатель: ссылка без владения
```

```efen
layout {
    set Vertices: Vertex                        // у каждого объекта графа своё множество узлов

    struct Vertex {
        var label: Int
        var neighbors: Vector<Vertices.Item>    // невладеющие указатели; вектор — поле узла
    }

    struct Self {
        var count: Int = 0
    }

    fn addVertex(self: mut Self, label: Int) -> Vertices.Item {
        self.count += 1
        return Vertices.new(Vertex(label: label, neighbors: []))
    }

    fn addEdge(self: mut Self, from: Vertices.Item, to: Vertices.Item) {
        from.neighbors.append(to)               // to == from — петля
    }

    fn removeEdge(self: mut Self, from: Vertices.Item, to: Vertices.Item) {
        from.neighbors.removeAll(where: { $0 == to })
    }

    fn removeVertex(self: mut Self, v: mut Vertices.Item) {
        for w in Vertices {                     // каждый узел этого графа
            w.neighbors.removeAll(where: { $0 == v })
        }
        let alone: own Vertices.Item = take v   // под множеством → own: указателей на v нет
        free(take alone)
        self.count -= 1
    }
}
```

`new`, `free` и перебор множества — наброски.

**Чей указатель и кто пишет.** `set Vertices` в начале `layout` — множество каждого объекта графа, а `struct Self`
— поля самого объекта. `Vertices.Item` хранит, из какого объекта графа узел, поэтому узел другого графа сюда не
передать. Право записи даёт `self: mut Self`, а не указатель: указатель без `mut` только читает
([права в типе указателя](../types/ownership.md)). Поэтому `addEdge(from: a, to: a)` — петля — допустима: два
указателя только для чтения на один узел не конфликтуют.

**Кто чем владеет.** Узлы — элементы под множеством `Vertices`: их память держит множество, а не другие узлы. Ссылки в
`neighbors` — указатели, поэтому циклы и петли владения не создают. Владелец узла — функция, которая его освобождает:
точка вызова `removeVertex` — конец жизни узла, а её тело — доказательство.

**Что доказывает компилятор в `removeVertex`.** Указатели на `v` могут лежать только в `neighbors` узлов множества: других
полей типа `Vertices.Item` в `layout` нет. Проход по всем узлам убирает из каждого списка все ссылки на `v`, и
компилятор выводит инвариант прохода «в пройденных узлах ссылок на `v` нет». Проход кончился — пройдены все узлы, и
переход `take v` в `own` доказан, и `free` не оставляет висячих указателей. Список самого `v` умирает вместе с ним, поэтому петлю `v → v` отдельно
убирать не нужно. Без прохода или с проходом, который останавливается раньше, — ошибка.

Остальные функции доказываются сразу: `addEdge` и `removeEdge` только добавляют и убирают указатели, а `addVertex`
рождает узел без ссылок на него.

Условия, при которых это работает:

1. все держатели указателей известны: поля типа `Vertices.Item` и коллекции таких указателей в `layout` (`neighbors`), переменные,
   захваты;
2. сводка `removeVertex` говорит «освобождает `v`», и у вызывающего умирают указатели, которые могут быть равны `v`;
3. пока жив перебор `Vertices`, вызов, освобождающий его элементы, — ошибка, кроме освобождения через курсор: внутри
   прохода `removeVertex` узлы не освобождаются, освобождение идёт после;
4. освобождённое место не путается с новым: адрес не устаревает, а индекс безопасен только вместе с условием 2.

**Цена.** Удаление узла проходит все узлы и все их списки.

### Граф с обратными указателями

Если удалять нужно быстро, у каждого узла держат ещё и список тех, кто ссылается на него.

```
 граф: A→B, A→C, B→C, C→A, C→C (петля)

 ┌──────────────┐   ┌──────────────┐   ┌──────────────┐
 │ A            │   │ B            │   │ C            │
 │ neighbors:   │   │ neighbors:   │   │ neighbors:   │
 │   B, C       │   │   C          │   │   A, C       │
 │ referrers:   │   │ referrers:   │   │ referrers:   │
 │   C          │   │   A          │   │   A, B, C    │
 └──────────────┘   └──────────────┘   └──────────────┘
```

```efen
layout {
    set Vertices: Vertex

    struct Vertex {
        var label: Int
        var neighbors: Vector<Vertices.Item>    // на кого ссылается этот узел
        var referrers: Vector<Vertices.Item>    // кто ссылается на этот узел
        invariants {
            forall w in neighbors: w.referrers.contains(self)
            forall w in referrers: w.neighbors.contains(self)
            neighbors.isUnique && referrers.isUnique       // без кратных рёбер
        }
    }

    fn addEdge(self: mut Self, from: Vertices.Item, to: Vertices.Item) {
        from.neighbors.append(to)
        to.referrers.append(from)
    }

    fn removeEdge(self: mut Self, from: Vertices.Item, to: Vertices.Item) {
        from.neighbors.removeAll(where: { $0 == to })
        to.referrers.removeAll(where: { $0 == from })
    }

    fn removeVertex(self: mut Self, v: mut Vertices.Item) {
        for w in v.referrers { w.neighbors.removeAll(where: { $0 == v }) }
        for w in v.neighbors { w.referrers.removeAll(where: { $0 == v }) }
        let alone: own Vertices.Item = take v   // указателей на v нет
        free(take alone)
    }
}
```

Законы здесь пишутся в обе стороны, и это не обратный закон, который ломает передачу через вызов: оба поля — указатели,
а не якоря, узлы никто не отрывает от структуры. Закон `isUnique` запрещает кратные рёбра, и `addEdge` получает
выведенное предусловие `!from.neighbors.contains(to)`. Для безопасности памяти хватило бы `contains`: `removeAll`
находит каждое вхождение; запрет нужен `removeEdge`, чтобы она убирала ребро с обеих сторон одинаково. Между двумя
строками `addEdge` закон нарушен, но `append` — операция контейнера и обратно в `layout` не входит.

**Что доказывает компилятор в `removeVertex`.** Если `v` лежит в `u.neighbors`, то по закону узла `u` в
`v.referrers` лежит `u`; если `v` лежит в `u.referrers`, то `u` лежит в `v.neighbors`. Значит, все указатели на `v` —
в узлах двух списков самого `v`, и два прохода по ним убирают каждое. Доказательство смешанное: закон сузил поиск до
двух списков, код проходит их. Закон после удаления проверяется только на узлах, которых проходы коснулись.

**Цена.** Удаление смотрит только на соседей `v`, зато каждая вставка ребра пишет в два места, а у каждого узла два
списка. Подробный разбор той же формы на цепочках рёбер — в [разборе](layout-proofs.md#граф-со-входящими-рёбрами).

## Что модель запрещает и что доказывает

**Запрещено: цикл якорей.** Если узлы держатся якорями-рёбрами, цикл якорей ничей с момента, когда замкнулся.
Запись якоря `t.f = take r` компилятор принимает, если `t != r` и по источнику видно, что `t` не лежит в дереве `r`:
`t` — корень, который держит сама функция, или дерево `r` состоит из `r` и поддеревьев, оторванных в этой функции.
Иначе он выводит предусловие, если его можно выразить через читаемые поля, а если нельзя — ошибка
([правило](layout-proofs.md#правила-доказательства)). Граф с циклами строится из невладеющих указателей, а конец жизни узла задаёт
функция освобождения.

**Доказывается выводом по цепочке — частично.** Цикл по одному полю, которое он не пишет, при законе, который
связывает соседей равенством или порядком, получает инвариант «отношение верно между началом и текущим элементом»;
обход по кругу до начала — «пройден весь цикл» ([правило](layout-proofs.md#правила-доказательства)). Отношение
текущего элемента с концом пути (сжатие пути в union-find) этим не выводится: это достижимость. Что граф после обхода стал прежним, компилятор не доказывает: он доказывает
только законы на выходе функции, а идентичность — правильность алгоритма.

**Не доказывается: правильность алгоритма.** Что `find` вернул представителя, а остов минимален, — вне модели.
