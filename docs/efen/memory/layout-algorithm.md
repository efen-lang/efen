Решения от 2026-11-10 отменяют три механизма первой редакции: `external own` с кодом возврата и порядком
источников (вместо них выдача места вложенной области), факт `AllAnchored` (владелец элементов множества виден
из объявлений: [владеющее поле или строка `public own`](layout-reference.md#владелец-множества)) и связь
между двумя `layout`. Решение от 2026-11-12 убрало множество без владельца: множество, у которого нет ни владеющего
поля, ни строки `public own`, вызывает ошибку. В разделе [механика FLOW](#механика-flow) и в таблицах [проверки](#проверка-алгоритмов) эти слова
ещё встречаются; там они читаются с этой поправкой, пока механика не переписана по плану Amber.

`layout` описывает, как лежат в памяти связанные данные: списки, деревья, графы. Компилятор по этому описанию и по
коду функций доказывает, что программа не обращается к мёртвой памяти, не освобождает её дважды и не теряет.
Целевой режим — доказательство по одной функции, с инвариантами структуры от программиста и выведенными условиями
функций и циклов. Вывод неполон: безопасная функция, для которой FLOW не нашёл доказательства, отвергается.
Ниже описан проект проверяющего алгоритма, а не отчёт о реализованном FLOW. Проверка охватывает также примеры из
`layout-proofs.md`, `layout-catalogue.md` и `layout-examples`; её результаты приведены в
[разборе алгоритмов](#проверка-алгоритмов). FLOW здесь — анализатор компилятора, не конструкция языка `flow`.

## Центральные гарантии

Модель требует от компилятора доказать восемь гарантий для каждой принятой программы на `layout`. Первые четыре —
безопасность памяти, которую получает программист; остальные — то, на чём держится доказательство. Инвариантом дальше
называется только строка `invariants`, которую пишет программист.

1. **Нет висячих указателей.** После события, которое уничтожает значение, переносит его в другую память или меняет
   его вид, ни один сохранившийся допустимый доступ не ведёт в мёртвую или чужую память. Биты уже недействительного
   указателя могут оставаться в локальной переменной, но читать цель через него запрещено.
2. **Один владелец, одно уничтожение.** Время жизни элементов множества задаёт его владелец: поле `own` или
   `anchor` либо строка `public own Nodes`, один способ на множество. У элемента в каждый момент ровно один владелец. После
   уничтожения все указатели на значение недействительны, поэтому второе уничтожение — ошибка.
3. **Указатель знает своё множество.** Множество одно на программу; `Items.Item` хранит, из какого множества
   пришёл указатель. Указатель на элемент другого множества — ошибка. Какой структуре элемент принадлежит сейчас,
   видно из владения.
4. **Элементы не пересекаются.** Разные элементы не делят ни байта памяти: слоты раздаёт множество.
5. **Время жизни выводится из кода.** Его задают события: `take`, `tie`, уничтожение, вызовы функций, которые уничтожают
   значение или отдают владение. Руками время жизни не пишется. Указатель не живёт дольше того, на что указывает.
6. **Память берётся явно и возвращается явно.** Каждый выданный элемент на каждом пути возвращается или передаёт
   владельца дальше. Память элемента возвращает функция, которая им владеет. Память родителя возвращается, только
   когда выданное из неё не хранится вне её ([выдача и возврат слота](layout-reference.md#выдача-и-возврат),
   правило 8). Возврат при выходе процесса не считается: у `layout` с `one` есть явная
   функция завершения. Иначе — ошибка «утечка».
7. **Доказательство локально.** Каждая функция проверяется сама по себе, по прототипам вызванных функций, а каждое
   событие — по своим проверяемым элементам. Инварианты структуры пишет программист, условия функций компилятор выводит сам.
8. **Граница `layout` закрыта.** Структуру меняет только код модуля или пакета, названного модификатором `layout`. Снаружи структура видна только в
   состояниях, где все её инварианты верны. Структуру в каждый момент трогает один поток или только читатели.

## Что описывает layout

| Понятие | Что это |
|---|---|
| множество `set Items: Item` | элементы одной формы; расположение в памяти не обещано |
| `Items.Item` | указатель на элемент множества `Items` |
| `own` | право уничтожения значения и исключительность: других действующих доступов к передаваемой памяти нет; локальные заимствования завершаются до уничтожения или передачи |
| `anchor` | владение, при котором на значение могут смотреть указатели; точка его уничтожения |
| невладеющий указатель | указатель без владения: `prev`, `parent`, ребро графа |
| инвариант | условие формы структуры в `invariants`, пишется руками |

Указатель сам по себе только читает. Запись в поле через указатель требует права на элемент: `edit` для записи
значения, невладеющего указателя и перестановки внутри структуры, `mut` для изменения структуры
([`edit` и `mut` в `layout`](layout-reference.md#edit-и-mut-в-layout)). Два пишущих параметра одного множества по
правилу `apart` не пересекаются; случай «оба параметра — один элемент» (петля в графе) функция разбирает отдельно.
`layout` — логическое пространство без экземпляров: параметра `self: mut Self` у его функций нет.

**Вход памяти и освобождение.** Операции «создать элемент» нет: память входит в множество приведением `Pointer`
(`mm.allocate(bytes: sizeOf(Item)) as Item`) или выдачей из другого множества и возвращается тем же путём
([создание элемента](layout-reference.md#выделение-и-освобождение--переход-между-множествами)). Возврат принимает только `own`. Память под
`anchor`, вынутым из поля, сначала переводится в `own` приведением
[`as own`](layout-reference.md#переход-к-владению-as-own). Невладеющий указатель владения не даёт, с любым правом.
В этой точке компилятор доказывает:

1. функция владеет элементом: якорь взят в этой функции через `tie` либо значение пришло параметром `anchor`
   ([удаление элемента](layout-reference.md#переход-к-владению-as-own), правило 2);
2. по всем инвариантам и учтённым классам держателей на память больше нет действующих невладеющих доступов: функция
   обнулила или переписала хранимые указатели, завершила заимствования, а локальные имена инвалидированы;
3. слоты вложенных областей элемента, выданные наружу, вернулись.

Указатели вызывающего на эту память становятся недействительными в точке вызова по сводке функции («освобождает `x`»).
К стиранию и к `as own` владеющие поля элемента, `own` и якоря, равны `null`: то, чем они владели, явный код
освободил раньше ([удаление элемента](layout-reference.md#переход-к-владению-as-own), правило 3).

**Освобождения всех элементов одним шагом нет.** Каждый элемент освобождает его владелец: к точке `as own` владеющие
поля элемента равны `null`, а указатели на него переписаны. Память родителя возвращается по правилу 8 раздела
[«Выдача и возврат слота»](layout-reference.md#выдача-и-возврат): вместе с родителем уходит только слот, все
владельцы и указатели которого находятся в памяти самого родителя. Память, которой элементы владеют вне родителя
(область `Vector`), возвращается отдельно, явным кодом.

```efen
let n = mm.allocate(bytes: sizeOf(Item)) as Item   // n: own Items.Item, на него никто не указывает
mm.free(n as Pointer)                              // исключительность уже известна; память возвращается туда, откуда взята
```

**Перенос** — явный код, а не действие компилятора: создание элемента на новом месте, копирование и явное
освобождение старого. Копировать может отдельная функция, которая переносит сырые байты; компилятор доказывает, что
это эквивалентно переносу значения. Перед освобождением старого все сохраняемые
доступы переписаны на новый или доказанно завершены, по тому же правилу. Голый адрес элемента, который `layout` может перенести, вне `layout` не
хранится: внешний мир обращается к нему через функции `layout`.

Выделение и освобождение памяти — переход элемента между множествами: память ОС — тоже множество
([подробнее](layout-reference.md#выделение-и-освобождение--переход-между-множествами)).

## Односвязный список

```efen
layout {
    set Items: Item

    struct Item {
        var next: own Items.Item? = null
    }
}

fn setNext(item: edit Items.Item, next: own Items.Item) {
    item.next = take next
}
```

Каждый элемент владеет следующим через `own`, и никто другой этим элементом не владеет.

**Почему `setNext` безопасен.** Параметр `own` значит, что вызывающий отдал функции единственное владение `next`. Был
бы `next` в списке, его владельцем был бы слот списка, и отдать его вызывающий смог бы только после `take` оттуда.
Значит, элемент под `own` по построению не входит в структуру, и отдельного слова для этого не нужно.

Остаётся одна опасность, и её закрывает предусловие, которое компилятор выводит из тела сам: `item.next == null`.
Без него запись `item.next = take next` теряет старый хвост `item` — утечка. Цикл здесь невозможен: чтобы отдать
`next` как `own`, вызывающий отказывается от всех указателей внутрь его хвоста, поэтому `item` в этом хвосте лежать не
может. Место, выданное наружу через `lend` (`own Block.data.Item`), в параметр `own Items.Item` не подходит: это
другой тип. У варианта с `anchor` (`push` в
[разборе](layout-proofs.md#односвязный-список)) указатели на хвост допустимы, и там
нужно второе предусловие, `next.next == null`.

Предусловие попадает в прототип `setNext`, и его доказывает вызывающий.

## Двусвязный список

```efen
layout {
    set Items: Item

    struct Item {
        var next: anchor Items.Item? = null
        var prev: Items.Item? = null
        invariants { next == null || next!.prev == self }
    }

    struct List {
        var head: anchor Items.Item? = null
        invariants { head == null || head!.prev == null }
    }
}

fn insertAfter(a: edit Items.Item, node: anchor Items.Item) {
    node.prev = a
    node.next = tie a.next
    if let old = node.next { old.prev = node }   // старый сосед указывает назад на node
    a.next = tie node
}
```

`next` — якорь: он определяет, где элемент уничтожат, а указатель `prev` на элемент при этом допустим. Инвариант стоит на
поле-якорь: элемент в `next` указывает назад на своего владельца. В `layout` есть поля `anchor` на `Items.Item`, поэтому время
жизни каждого узла задаёт поле-владелец: узлом владеет `next`, `List.head` или локальная переменная функции. Узла без
владельца в этом множестве нет, и хранимый `prev` на `n` находится только в `n.next!.prev`.

Без строки `old.prev = node` старый сосед указывал бы назад на `a`, хотя стоит уже после `node`: инвариант нарушен, и
компилятор отвергает функцию. Нужны `node.next == null` и `a != node`. Первый факт исключает потерю старого хвоста,
оба вместе с деревом якорей исключают цикл. Один `anchor` не запрещает передать указатель `a` на тот же узел. Параметр `a` служит
указателем без источника в типе, и для него ни один факт правила 5 раздела
[«Перенос владения»](layout-reference.md#64-перенос-владения) не доказан. Поэтому оба условия FLOW выводит
предусловием функции.

**Удаление из середины.** Удаляем `N` из `A ⇄ N ⇄ B`:

```
до:     A ⇄ N ⇄ B
шаг 1:  вынуть N из A.next          — якорь N теперь у функции
шаг 2:  A.next = B                  — A указывает на B
шаг 3:  B.prev = A                  — B указывает назад на A
шаг 4:  на N никто не указывает     — anchor → own
шаг 5:  вернуть память N в mm
после:  A ⇄ B
```

```efen
fn remove(list: mut List, n: read<list> Items.Item) {   // освобождает узел: нужен mut на список
    let a = n.prev!                         // сосед слева; голову удаляет removeFirst
    let node = tie a.next!                 // шаг 1
    a.next = tie node.next                 // шаг 2
    if let b = a.next { b.prev = a }        // шаг 3
    mm.free(node as own Pointer)            // шаги 4 и 5: доказано, что указателей на N нет
}
```

На шаге 4 компилятор спрашивает инвариант, где могут лежать указатели на `N`. Для узлов этой структуры инвариант вместе с
полным учётом якорей даёт `B.prev` — поле входного `N.next`, переписанное на шаге 3. Указатели в отдельно хранимых
узлах и локальных переменных учитываются дополнительно по [правилам держателей](#владение-лесом-и-поиск-всех-держателей).
Собственное поле `N.prev` освобождается вместе с `N`.
Что `tie a.next!` забирает именно `N`, из инварианта не следует: для этого нужно `n.prev!.next == n`. Это условие
FLOW выводит как предусловие функции («`N` в списке и не первый»), и его доказывает вызывающий
([перенос владения](layout-reference.md#64-перенос-владения), правило 5). Параметр `list: mut List` даёт право
освободить узел ([право на элемент](layout-reference.md#82-право-на-элемент), правило 5).

Инвариант на обратном указателе руками не пишется (`prev!.next == self` не нужен): он сломал бы каждую передачу оторванного
элемента через вызов. Обратный указатель элемента, вынутого в функцию, — указатель, который функция ведёт сама
([правило](layout-proofs.md#правила-доказательства)).

## Как компилятор это доказывает

Структура доказывается индукцией по событиям.

| Шаг | Что доказывается |
|---|---|
| инвариант | форма структуры, пишет программист |
| база | инвариант верен в начальном состоянии: пустой список, только что рождённый элемент |
| шаг | каждое событие, меняющее структуру, сохраняет инвариант |
| крайнее состояние | уничтожение, перенос и смена вида не оставляют висячих указателей |

Остальные состояния получаются из начального цепочкой событий и отдельно не доказываются.

**Окрестность события.** Проверять нужно инварианты всех элементов, чьи зависимости затронуты записью, даже если сами
элементы не менялись. В `insertAfter` это `a`, `node` и `old`; полноту этого набора дают инварианты и единственность
якоря. Для остальных элементов требуется доказать, что память, которую читают их инварианты, не изменилась.

Например, при инварианте `next == null || key == next!.key` запись `q.key` может нарушить инвариант `p`, у которого
`p.next == q`, хотя `p` не изменён и из `q` не виден. Нужен доказанный способ найти таких держателей: обратные связи,
обход множества или другое достаточное условие; иначе операция не доказана. Отсутствие записи в сам узел не является
доказательством сохранения его инварианта. Natural proofs (Dryad, PLDI 2013) дают направление для такого механизма,
но требуют формальных правил сохранения незатронутой памяти; вывод условий и инвариантов циклов — отдельная задача.

**Где лежит доказательство отсутствия висячих указателей.** Инвариант говорит, где указатели на значение могут лежать; код
события показывает, что каждое мертво или переписано. Чем точнее инвариант, тем больше работы при каждой вставке и тем
меньше при удалении.

| Доказательство | Инвариант говорит | Удаление делает | Пример |
|---|---|---|---|
| в структуре | указателей нет | ничего | односвязный список |
| смешанное | указатель один, в известном слоте | переписывает его | двусвязный список, дерево с родителем |
| в коде | указатели в любых элементах той же публичной структуры | проходит все её элементы | [свободный граф](#свободный-граф) |

Разбор каждой структуры: [доказательство структур](layout-proofs.md).

## Механика FLOW

### Область доказательства и доверенные операции

Первый вариант проверяет последовательный код одного `layout`. Вызовы проверяются по сводкам, внешний код — по
обычным правилам типов и линейной передачи прав; его внутренние структуры для доказательства `layout` не раскрываются.
Межпоточная передача — модель раздела [«Многопоточность»](layout-reference.md#многопоточность) в `layout-reference.md`. Остановка процесса не считается
доказательством освобождения, а для бесконечного выполнения не обещается, что каждый ресурс когда-нибудь вернётся.
Доказывается отсутствие потерянного владельца и невыполненных обязательств на завершённых путях.

Нижний уровень — проверенные реализации операций над множествами и областями: выделение непересекающихся слотов, запись
в неинициализированный слот, `take` слота и освобождение. Их сводка задаёт нормальные и исключительные исходы, изменения
памяти и владельцев. Системное выделение и C — явно названные точки доверия. Из написанного `set` само по себе не
следует, что распределитель правильно раздаёт память. Разные слоты одного уровня не пересекаются; вложенный слот может
лежать в памяти родителя, но передача доступа к нему учитывается отдельно.

`replace` и другие обещанные атомарные операции должны иметь реализацию prepare/commit/cleanup: подготовка может
завершиться ошибкой, изменение опубликованного состояния не бросает и не вызывает наблюдателя, очистка реально
исполняется. Записи в доказательстве не заменяют этот код. Это логическая атомарность, не машинная атомарная инструкция.

### Состояние в каждой точке функции

FLOW строит граф управления с обычными, исключительными и cleanup-рёбрами. Состояние на его ребре — символическое
описание всех возможных конкретных состояний, а не один угаданный пример:

| Часть | Что хранится |
|---|---|
| Память `H` | Значения полей, отношения равенства и возможного совпадения адресов, инициализированные компоненты и диапазоны. Запись получает новую версию памяти. |
| Идентичность | Источник, экземпляр, слот и рождение значения. Новое значение в повторно использованном слоте имеет другую идентичность. Это факт доказательства, не обязательный счётчик в runtime. |
| Живость | Какие значения и источники живы; какие указатели и компоненты более нельзя читать. |
| Владение | Единственный владелец каждого ресурса: слот `own` или слот `anchor`; пустые и перемещённые слоты. |
| Области и доступ | Какие байты покрывает право, какие области различны, какие права временно переданы заимствованию. Вложенный доступ из параметра `mut` не создаёт второго независимого права записи. |
| Выданные слоты | Какие слоты вложенных областей выданы наружу и из какого родителя; родитель не возвращается, пока слот выдан. |
| Факты | Условия ветвей, арифметика, отношения множеств, сводки цепочек и леса владельцев, доказанные условия вызовов. |
| Инварианты | Закрытые инварианты, открытые обязательства восстановления и память, от которой зависит каждый инвариант. |

`H₀` обозначает память на входе, `Hᵢ` — после события. Факт `H₀[B].prev == N` не превращается в факт о `Hᵢ` без
проверки записей между ними. Номер рождения не позволяет использовать старый указатель только потому, что его
машинный адрес снова занят. Превращение произвольного `Int` в указатель не восстанавливает такую идентичность.

При слиянии ветвей сохраняются только факты, верные на всех путях, либо условные факты с их условиями. Если на одной
ветви ресурс освобождён, а на другой жив, FLOW не объявляет его безусловно живым. Владелец и обязанность возврата
должны быть учтены на каждой ветви. Потеря точности допустима; выдуманный факт — нет.

### Порядок проверки функции

```text
проверить типы, источники и доверенные контракты примитивов
построить CFG, включая исключения, закрытие выдач и очистку частичных значений
обработать граф вызовов по рекурсивным группам:
    предложить конечный набор кандидатов сводок и инвариантов циклов
    для каждого кандидата:
        создать входное состояние из параметров, требований и закрытых инвариантов
        пройти CFG, применяя переходы и объединяя состояния
        на цикле проверить базу J, шаг J ∧ guard → J' и каждый выход
        на доступе проверить живость, инициализацию, границы и права
        на вызове проверить контракт и применить эффекты соответствующего исхода
        на уничтожении проверить всех держателей и потребить ресурсы
        на выходах проверить инварианты и баланс ресурсов
    принять группу только если все обязательства одного набора доказаны
    иначе уточнить кандидаты в пределах бюджета или отвергнуть
экспортировать проверенные сводки, не сами предположения поиска
```

Поиск кандидатов и проверка их достаточности разделены. Из недоказанного обязательства можно получить новое
предусловие, но новый кандидат заново проверяется целиком, а каждый вызов доказывает это предусловие. Разворачивание
циклов до фиксированного числа итераций не является заменой индукции. Ограничение времени или числа кандидатов
заканчивается отказом, а не признанием свойства верным.

### Переходы и обязательства

Проверка разыменования выполняется **до чтения**, даже когда инварианты структуры временно открыты: доказаны живость
источника и цели, происхождение, инициализация компонента, границы, выравнивание и право доступа. Обещание восстановить
инвариант к `return` не разрешает временный доступ к освобождённой памяти.

| Операция | Проверка и новое состояние |
|---|---|
| Вход памяти: `mm.allocate(bytes: sizeOf(Item)) as Item(value: 0)` | Новый живой идентификатор и непересекающаяся память под владельцем `own`. Поля, названные в приведении, записаны, поля со значением по умолчанию получили его, остальные не инициализированы до записи. При ошибке результата нет, и уже созданные ресурсы освобождены. |
| Запись нового элемента во владеющее поле | Потребляется `own`, и владельцем становится поле; только после этого допустим невладеющий указатель на элемент в результате. Нельзя просто забыть `own` при смене типа результата. |
| Чтение владеющего поля | Создаётся невладеющий доступ; владелец не переносится. |
| `take` или `tie` владеющего слота | Право и обязательства переходят получателю, и прежний слот значением больше не владеет: после `take` он пуст, а локальное имя после `tie` остаётся невладеющим указателем ([перенос владения](layout-reference.md#64-перенос-владения), правило 1). Для `Items.Item` переходит владение, а узел остаётся на своём адресе. Физический перенос inline-значения, если он нужен, дополнительно проверяется как перенос памяти. |
| Запись указателя | Цель жива и принадлежит допустимому источнику; новый держатель включён в учёт. Проверяются время жизни и зависимости инвариантов. |
| Запись владельца | Старый владелец в назначении отсутствует либо его ресурс отдельно возвращён; потребляется право из источника. Для якоря дополнительно проверяется отсутствие цикла. |
| Запись в неинициализированный слот области | Слот не инициализирован; после записи он инициализирован и получает переданный ресурс. |
| `take` слота; перенос: `take` из старого слота и запись в новый | Слот-источник инициализирован, слот назначения не инициализирован; маска инициализации меняется точно. Доступы к прежнему значению слота-источника недействительны со строки `take`. Операции переноса нет: перенос пишет код. После `take` поля уничтожать его повторно нельзя. |
| Переход `anchor` в `own` | Владеющий слот уже вынут; доказана исключительность передаваемой области, учтены внешние выдачи. Один невладеющий указатель не создаёт право владения. |
| `free` / смена вида / физический перенос | Определяется вся затронутая область, доказывается допустимость каждого сохранившегося доступа и ресурсной очистки; старые идентичности и зависящие от них указатели инвалидируются. |

Неизвестное совпадение указателей нельзя считать различием. При записи через `a` факт о `b` сохраняется лишь после
доказательства `a != b` либо при доказанно разных полях. Иначе FLOW рассматривает обе возможности или ослабляет факт.

Арифметика считается в машинном типе. Для `length + 1`, `2 * capacity`, `% capacity` нужны доказанные границы и
ненулевой делитель. Проверка при выполнении допустима только там, где она определена языком и стоит до опасного
доступа или необратимого изменения; её исключительный выход тоже проверяется. Проверка границы не заменяет
доказательство живости указателя. `unknown`, тайм-аут решателя и неподдержанный инвариант не разрешают операцию с памятью.

### Владение лесом и поиск всех держателей

Единственный входящий владелец ещё не означает лес: `A.next = B; B.next = A` даёт по одному владельцу, но цикл без
внешнего корня. FLOW хранит доказанный лес владельцев и отдельно проверяет каждую вставку якоря.

После `tie p.child` получен корень отделённого поддерева: прежнее дерево и отделённая часть не пересекаются.
Когда запись якоря `t.child = tie r` принимается, определяет правило 5 раздела
[«Перенос владения»](layout-reference.md#64-перенос-владения). Для него FLOW хранит лес владельцев и пересчитывает
факты отделения после каждой записи. Произвольный `graft(x: mut Items.Item, s: anchor Items.Item)` от передачи
`anchor` доказанным не становится: для указателя-параметра без источника ни один факт правила не доказан, и
предусловия в полях, которые читает вызывающий, нет.

Для уничтожаемой области `D` требуется охватить **всех** держателей: поля всех видов этого `layout`, вложенные
контейнеры, курсоры, локальные значения, захваты, внешние выдачи и объявленные связи. Варианты доказательства:

1. Исключительное владение уже исключает внешние действующие доступы к `D`.
2. Инвариант и правила владельцев дают полный перечень держателей: например, обратные ссылки детей и отдельно
   хранимых узлов дерева. Каждый из них проверяется по текущей памяти.
3. Перебор охватывает всё множество возможных держателей и доказывает, что ссылки на `D` удалены.

Держателей обобщённого контейнера и непрозрачного типа FLOW находит по типу, отдельной сводки хранения нет:

1. Значение может держать `Items.Item`, только если его тип называет `Items.Item` или тип, который его называет, в своих
   аргументах (`Vector<Vertices.Item>`, `Map<Key, Vertices.Item>`). Где именно внутри лежит указатель, не важно:
   держателем считается всё значение. Тип без `Items.Item` в аргументах его не держит: положить туда указатель
   нельзя, потому что вне `layout` поле `Items.Item` бывает только у структуры с параметром источника.
2. Сохраняемое замыкание захватывает `Items.Item`, только когда его тип называет заимствование структуры, из которой
   указатель прочитан: `read<list> () -> Void`
   ([указатель вне layout](layout-reference.md#указатели-вне-layout), «Запрещено»). Корутина `spawn` или
   `background` такой указатель не захватывает ([структура и поток](layout-reference.md#структура-и-поток),
   «Запрещено»). Несохраняемое замыкание захватывает указатель на время вызова и видно в сводке вызова.
3. Что в контейнере не осталось указателя на `D`, доказывает условие результата его метода, написанное и
   доказанное в теле контейнера: `removeAll(where:)` с `ensures forall x in self: !predicate(x)`. Метод без такого
   условия держателя не очищает, и обход через него неполон: ошибка в строке освобождения.

Полноту учёта владельцев задаёт владелец множества, и читается он из объявлений. Поле `own` или `anchor` на
`Nodes.Item` где-либо в `layout` значит, что каждый хранимый элемент `Nodes` находится под владеющим полем. Множество без
такого поля выдано целиком строкой `public own Nodes`, и `layout` указателей на его элементы не хранит. Множество без
поля и без строки вызывает ошибку. Отдельного факта и предусловия для этого нет. Внутри функции
вынутый узел учитывается отдельно до укладки назад, возврата или уничтожения; ссылки из таких узлов не исчезают
из учёта.

Указатель элемента на самого себя переходу `as own Pointer` не мешает: он расположен в уходящей памяти и уходит
вместе с элементом.
Неявного уничтожения владеющих полей нет: к стиранию и к `as own` поля `own` и якоря элемента равны `null`
([удаление элемента](layout-reference.md#переход-к-владению-as-own), правило 3). Область `D` поэтому состоит из
памяти элементов, которые функция освобождает явно.

У вызывающего сводка инвалидирует все указатели, которые могут попасть в `D`. Для частично известной коллекции
можно консервативно запретить чтение её содержимого целиком, но нельзя потерять владение её собственным буфером:
очистка без разыменования недействительных целей остаётся необходимой. Выданный слот вложенной области
(`own Block.data.Item`) так выбросить нельзя: его возвращают туда, откуда он выдан.

### Сохранение инвариантов и сводки вызовов

Пусть `W` — изменённые слоты, а `reads(I, x, H)` — память, которую читает инвариант `I` для элемента `x`. FLOW доказывает
инвариант для произвольного элемента из его области действия после события. Разбор: новый элемент; изменённые
зависимости; оставшийся элемент, для которого доказано сохранение прочитанной памяти. Изменение самого множества,
его мощности или границ квантора тоже является зависимостью. Разворачивание инварианта лишь на перечисленных в коде
узлах допустимо только с доказательством полноты этого набора. Иначе нужен общий символический элемент или обход.

Пока инвариант открыт, его нельзя заново принять как факт о текущей памяти. Сохраняются входные факты и точные эффекты
записей. Закрываются инварианты на нормальном и исключительном выходе публичной функции и перед возможным наблюдением,
обратным входом или приостановкой. Внутренний помощник получает явно выведенные требования к текущему состоянию;
он не вправе молча предположить все инварианты закрытыми. Вызовы контейнера разрешены по их сводкам, включая возможный
callback и исключение, а не по одному имени `append`.

Сводка функции содержит:

```text
требования: источники, права, живость, нужные инварианты и условия аргументов
нормальный / исключительные исходы:
    изменённая память и восстановленные инварианты
    созданные, уничтоженные и переданные ресурсы
    источник результата и судьба внешних выдач
наблюдение: callback, повторный вход, приостановка
```

Например, освобождённые рёбра задаются как `{e из Edges₀ | H₀[e].from == v || H₀[e].to == v}`. Вызывающий проверяет
свой `e0` по входному снимку, не читает поля уже освобождённого ребра. Запись в область эффекта забывает прежние
факты о ней; факты вне области сохраняются только по правилу зависимостей.

Кандидаты предусловий получаются из невыполненных обязательств тела. Их проверяют заново как предположения на входе,
а вызывающий обязан их обеспечить. Кандидат нельзя считать доказанным только потому, что он позволяет закончить
анализ. Публичный контракт не требует раскрыть приватные поля: источники, владение и внешние выдачи представлены
типовыми фактами; остальные условия должны быть доступны вызывающему либо следовать из инвариантов `layout`.

Для рекурсивной группы сначала предлагается конечный набор сводок, затем проверяется тело каждой функции при этих
контрактах вызовов. Это правило индукции по конечному выполнению, а не разрешение предположить произвольный результат
самого тела. Завершение доказывается отдельно убывающей мерой; у `freeTree` — размером отделяемого поддерева леса.
Неполученная сводка или неподтверждённая индукционная гипотеза означает отказ в доказательстве.

### Циклы: вывод кандидата и проверка индукции

FLOW ищет инвариант в конечном наборе шаблонов по форме цикла, инвариантам и эффектам тела. Для любого кандидата `J`
нужно доказать базу, сохранение одной итерацией и достаточность на **каждом** выходе. `break`, исключение и ранний
`return` не получают постусловие полного обхода. При расширении или объединении состояния можно терять факты,
но нельзя терять ресурсные обязанности. Поиск ограничен; отсутствие подходящего шаблона — результат «не доказано».

| Шаблон | Кандидат и обязательство сохранения |
|---|---|
| Счётчик `0 ..< N` | `0 <= i <= N` и `forall k < i: P(k)`. Итерация устанавливает `P(i)` и сохраняет `P` прежних слотов; предел и все прочитанные `P` поля стабильны либо их изменения доказанно сохраняют `P`. |
| Обход цепочки структуры | Встроенного перебора множества нет: обходится цепочка, которую ведёт структура. Узлы цепочки на входе `S₀ = Done ⊎ Remaining`; обработанные элементы удовлетворяют `P`. При обычном обходе состав цепочки стабилен; удаление через курсор потребляет текущий элемент и сохраняет точный набор ещё не обработанных. |
| Цепочка до `null` | Последовательность разложена на пройденную и оставшуюся части; указатель стоит на начале оставшейся. Нужны доказанные полнота цепочки и отсутствие повторов; одной записи `p = p.next` недостаточно. |
| Отношение вдоль пути | Отношение начала и текущего узла следует из транзитивности. Должны сохраняться не только `next`, но и данные отношения либо факт о снимке. Для строгого порядка нулевая длина пути — отдельный случай. |
| Цикл по кольцу | Взаимно обратные `next/prev`, конечность, стабильность связей и хотя бы один шаг до сравнения с началом. Обойдён один компонент-кольцо, не все кольца множества. |
| Сдвиг массива | В области есть одна «дырка», неинициализированный слот. Код переносит в неё соседнее значение (`take` из соседнего слота и запись) и этим сдвигает дырку. Маска точнее, чем `length`, пока операция открыта. |
| Двухпроходное сжатие пути | Первый проход фиксирует стабильную последовательность пути до корня; второй идёт по сохранённому прежнему преемнику и меняет только пройденные `parent`. Дополнительный шаблон разобран ниже. |
| Растущая очередь копирования | Просканированная часть закрыта, непросканированная часть ещё содержит старые ссылки; новые элементы добавляются только через единственную таблицу пересылки. Это отдельный шаблон, не цикл с постоянным `N`. |

Если цель — только безопасность обращений внутри цикла, достаточно более слабого инварианта живости, типов,
инициализации и сохранения владельцев. Он может сохраняться и при повторном посещении узлов. Из него нельзя
получать ни завершение, ни отсутствие ссылок во всём множестве после обхода. Эти более сильные выводы требуют
именно соответствующего шаблона покрытия и доказанной меры.

Для графа с полным проходом `P(w)` — отсутствие `v` в `w.neighbors`. Нужна сводка
`removeAll(eq(v)): result = old(sequence)` без всех вхождений `v`, с сохранением остальных элементов и без callback.
Она относится к конкретному контейнеру; другая итерация не должна вернуть `v` в уже обработанный список.
После `Remaining = ∅` получено отсутствие ссылок во всех держателях данного класса. Если есть ещё `Cursor.current`,
одного прохода по `neighbors` недостаточно.

### Почему эти проверки дают безопасность

Доказательство корректности самого FLOW должно связывать его символическое состояние с конкретной памятью.
Обязательства для реализации проверяющего:

1. Начальное состояние соответствует реальному созданию и доверенным контрактам распределителя.
2. Каждый примитивный переход сохраняет соответствие и не выполняет недопустимого доступа.
3. Объединение путей и обобщение цикла покрывают все исходные состояния, а не отбрасывают неудобные пути.
4. Подстановка сводки сохраняет источники, область эффекта и линейные ресурсы; правило кадра не теряет зависимых инвариантов.
5. Выход закрывает инварианты и учитывает все ресурсы и возвраты; cleanup присутствует в исполняемом коде.

Тогда индукция по конечному префиксу выполнения даёт отсутствие чтения мёртвой/неинициализированной памяти и
двойного освобождения; учёт владельцев — отсутствие потери ресурса на завершённом пути. Сохранение инвариантов
обеспечивается в точках наблюдения. Это план доказательства soundness, а не выполненная механизация: тестирование
примеров не заменяет доказательство этих пяти свойств реализации FLOW. «Короткая формула для Z3» сама по себе
не доказывает ни полноту охвата памяти, ни корректность генератора обязательств, ни линейное время анализа.

## Вывод времени жизни

Время жизни не объявляется: FLOW выводит его из кода по точкам уничтожения. Правила, которые он при этом
проверяет, перечисляет [справочник](layout-reference.md#время-жизни); здесь описан порядок вывода.

**Алгоритм.** FLOW строит граф указателей и для каждой точки программы проверяет его рёбра.

| Вершина | Что это |
|---|---|
| значение | элемент множества, слот области, область, память ОС |
| слот с указателем | поле, переменная, параметр, результат, захват замыкания |

| Ребро | Откуда известно |
|---|---|
| владеет (`own`, `anchor`) | тип поля или параметра; в каждый момент одно на значение |
| расположен внутри | вложенность `layout`: поле-область, вид элемента, выдача из родителя |
| указывает (указатель) | запись указателя; источник — по коду: из какого множества пришло значение |
| заимствует | структура, которая заимствует, ссылка внутри функции |

Шаги:

1. **Источник.** У каждого указателя FLOW отслеживает, из какого множества или источника он пришёл: из поля
   с объявленным типом `Items.Item`, из выдачи, из результата функции по её сводке. Указатель без доказанного
   источника — ошибка, кроме точек доверия.
2. **Операции над значением.** Создание, передача якоря и уничтожение каждого значения — по телу и по пометкам в сводках вызванных функций.
3. **Проверка ребра «указывает».** В каждой точке, где значение уничтожается, каждый слот с указателем на него уничтожен, переписан или не используется дальше. Где находятся такие слоты, FLOW знает из инварианта, из объявленного множества указателя или из заимствования; слот, которого он найти не может, — ошибка в месте, где указатель записан.
4. **Проверка ребра «заимствует».** В точке, где структура источника меняется или источник уничтожается, структура, которая заимствует, уже уничтожена или не используется дальше; если она используется дальше — ошибка, и компилятор показывает её в строке этой операции.
5. **Проверка ребра «расположен внутри».** Родитель не уничтожается, пока внутри него что-то существует.
6. **Сводка.** Что функция делает с источником и временем жизни своих параметров и результата, FLOW записывает в её
   прототип; вызывающий проверяется по прототипу.

**Направления, по которым принцип проверен.**

| Направление | Как доказывается | Состояние |
|---|---|---|
| локальная переменная | ссылка внутри функции; операции тела | есть в FLOW |
| параметр и результат | сводка: источник и пометки уничтожения | частично |
| поле внутри `layout` | инвариант или объявленное множество указателя | модель |
| поле вне `layout` | структура, которая заимствует `Src: Origin` | есть в FLOW (S109) |
| захват замыкания | заимствование замыкания (S102) | есть в FLOW |
| вложенные множества | ребро «расположен внутри», `lend`/`take` | есть в FLOW |
| память ОС и функции C | точка доверия: условие результата, код `model` | частично |
| цикл, произвольный граф | указатели под инвариантом; вершинами владеет структура, а функция освобождения доказывает, что указателей на вершину не осталось | модель |
| потоки | структура считается одним целым; изменения структуры «корень ушёл в другой поток» и «блокировка отпущена» | модель |

**Отсутствие висячих указателей.** Операция, которая уничтожает значение, физически переносит его в другую память или меняет его вид, требует доказательства: каждый указатель на значение недействителен или переписан. Передача якоря через `tie` к таким операциям не относится: указатели при ней верны. Инвариант структуры говорит, где указатели могут храниться, и его доказывает код, меняющий структуру, при каждой такой операции; внутри тела инвариант бывает нарушен, поэтому слоты с указателями FLOW считает по состоянию на входе в функцию и записям тела до операции. Код операции показывает, что каждый указатель недействителен или переписан; при переносе и смене вида указатель может остаться верным, если
переведён на новое место или вид. Доказательство бывает целиком в структуре (`own`: указателей нет), целиком в
коде (проход по всем слотам с указателями) или смешанным (инвариант сужает поиск, код проходит оставшиеся слоты). Чем точнее инвариант, тем
больше работы в коде, который строит структуру, и тем меньше в коде такой операции.

**Порядок вывода.**

1. Поле, параметр или переменная с `own` или `anchor` — владелец значения.
2. FLOW находит, где владелец уничтожает значение: в теле функции или через вызов функции, которая, как видно по её
   сводке, значение уничтожает или отдаёт наружу.
3. Эта точка — конец времени жизни значения и всех указателей, привязанных к нему: указателей, ссылок внутри функции,
   элементов множеств, расположенных внутри него.
4. Так FLOW собирает жизненный цикл каждой структуры данных и каждого указателя — от создания через вызовы функций до
   точки уничтожения — и проверяет, что цикл не нарушает правил: ни один указатель не используется после своей точки,
   ни одно значение не уничтожается дважды и не остаётся без владельца.

Конец времени жизни связывает с вызовом функции FLOW, а не программист: он видит, что функция уничтожает память,
и связывает с её вызовом конец времени жизни всего, что от этой памяти зависит.

### Диагностика времени жизни

FLOW не только доказывает, но и объясняет. Ошибка времени жизни называет конфликт: где значение уничтожено, где его указатель использован после этого и путь между ними.

```
error[flow.slot-left]: указатель `node` использован после конца времени жизни узла
  --> list.efen:12:11   print(node!.key)
note: узел уничтожен вызовом release (сводка: уничтожает node)
  --> list.efen:11:5    release(pool: pool, node: tie list.head)
note: указатель взят здесь
  --> list.efen:10:16   let node = list.head
```

В режиме подробной печати FLOW выдаёт жизненный цикл значения целиком в виде графа: создание, передачи якоря, вызовы
с их пометками из сводок, точку уничтожения и каждый указатель с местом, где он становится недействительным. По графу видно, на каком пути
цикл нарушен.

Отдельный режим печатает граф времени жизни всех объектов одного `layout`: каждое множество и область, их
вложенность, якоря и владельцев, функции, которые создают, передают и уничтожают элементы, с их пометками из сводок, и
все указатели между множествами. Это карта времени жизни элементов (раздел [время жизни](layout-reference.md#время-жизни)) целиком, а не для одного
значения: по ней видно, как устроена память структуры данных и где у элемента нет пути к уничтожению.

Указатели ключей или команд для этих режимов задаёт реализация.

## Граница layout

Внутри функции инвариант может быть нарушен: `insertAfter` между строками держит структуру сломанной. Снаружи это не видно
никому, потому что границу защищают четыре правила.

0. **Круг пишущего кода задаёт модификатор `layout`.** `private layout` — поля пишут функции модуля; без
   модификатора (`internal`) — функции пакета; код другого пакета только читает и вызывает
   ([кто пишет поля](layout-reference.md#пространство-layout)). Публичная функция структуры — функция этого круга
   без `private`.
1. **Структуру меняет только код этого круга.** Иначе запись `n.prev = x` в любом месте программы меняла бы
   память, от которой зависят инварианты, а автор `layout` не мог бы изменить инвариант, не сломав чужие пакеты. FLOW
   проверяет каждую функцию круга: инвариант принят на входе и доказан на выходе.
2. **Инвариант верен на входе и выходе каждой публичной функции и перед каждым вызовом, которому он нужен закрытым.**
   Пока инвариант нарушен, запрещены неизвестный наблюдатель, обратный вход и вызов, полагающийся на закрытые инварианты:
   неизвестная функция, замыкание или деструктор без подходящей сводки. Проверенный внутренний помощник может читать
   и менять открытую структуру по своему явному контракту текущего состояния. Операции контейнера над указателями
   (`append`, `removeAll` с условием из одного сравнения) допустимы, если их эффекты, включая исключения и отсутствие
   обратного входа, доказаны. Одного имени операции для этого недостаточно.

   ```efen
   fn remove(list: mut List, n: read<list> Items.Item, onRemove: (Items.Item) -> Void) {
       let p = n.prev ?? return
       let node = tie p.next ?? return
       p.next = tie node.next      // инвариант нарушен: следующий ещё указывает на n
       onRemove(node)               // ошибка: замыкание может войти обратно в layout
       // дальше функция переписала бы prev следующего узла и освободила node
   }
   ```

3. **Прототип публичной функции говорит только о доступных вызывающему фактах.** Выведенное условие выражается через
   доступные поля (`n.prev!.next == n` — «`n` в списке») либо сведения о правах и источниках из типов и сводок.
   Приватные поля ради доказательства раскрывать не требуется. Если нужное условие так выразить невозможно, функция
   отвергается с подсказкой: условие о внутреннем состоянии записать инвариантом `layout`. Сам компилятор инвариантов не
   добавляет.
4. **Граница миров.** Что внешний мир получает от публичной функции, говорит тип результата; вариантов три.

   | Тип результата | Что это | Как кончается |
   |---|---|---|
   | `own Block.data.Item` | **выданный слот**: `lend` слота вложенной области; поля элемента остаются у `layout`, внешний код владеет байтами области | слот возвращается туда, откуда выдан, функцией `layout`; привести к `Pointer` и освободить нельзя ([выдача наружу](layout-reference.md#выдача-наружу)) |
   | `mut Items.Item?`, `edit Items.Item?`, `read Items.Item?` (ссылка в результате) | **частичный доступ**: элемент остаётся во владении `layout`, вызывающий получает доступ с этим правом; источник — структура, из которой взят элемент; доступ живёт, пока она не изменила структуру | доступ кончается вместе со ссылкой; к `free` и параметру `own` не подходит ([место в результате](../types/ownership.md#место-в-результате-функции)) |
   | `own Items.Item` | **передача самого владения**: функция доказала исключительность и сняла обязательства перед прежним владельцем; обратные указатели в прежнюю структуру очищены | вызывающий возвращает элемент функции обратного пути, которая принимает `own Items.Item` и освобождает его или оставляет в структуре, либо передаёт элемент дальше ([проверка строк](layout-reference.md#87-проверка-строк-public-own-и-public-lend), проверка 4) |

   Указатель на элемент без права и без `own` (`-> Items.Item`) сам права записи не даёт: вызывающий пишет через
   него с тем правом, которое у него есть на структуру-источник
   ([право на элемент](layout-reference.md#82-право-на-элемент), правило 2). Указатель становится недействительным
   при вызове, сводка которого может освободить или перенести элемент. Вне `layout` он хранится только
   заимствованием ([раздел о хранимых указателях](#указатели-за-пределами-layout)).

## Указатели за пределами layout

Вне `layout` указатель на элемент хранит только значение, которое заимствует: структура с параметром источника
(`ListCursor<Src: Origin>`) или коллекция с источником в типе элемента (`Vector<read<g> Vertices.Item>`).
Такое значение хранит заимствование своего источника `Src` и проверяется правилами заимствований: изменение структуры
источника делает его указатели недействительными. Правило и пример —
в [`layout-reference.md`](layout-reference.md#указатели-вне-layout). Выдача памяти наружу владением — `lend` слота вложенной области
([выдача наружу](layout-reference.md#выдача-наружу)): после каждого вызова FLOW доказывает, что указатель у внешнего кода
актуален, и недоказанный случай — ошибка.

Остальной код вне `layout`:

| Держатель | Правило |
|---|---|
| параметр функции | указатель недействителен после возврата |
| замыкание, которое не сохраняется | захват хранит заимствование на время вызова (S102) |
| сохраняемое замыкание | не захватывает `Items.Item`, если его тип не называет заимствование структуры: `read<list> () -> Void` ([указатель вне layout](layout-reference.md#указатели-вне-layout)) |
| локальная переменная или временное значение с источником в типе (`Vector<read<g> Items.Item>`, структура с `Src`) | указатели в нём недействительны, если могут быть равны освобождённому элементу; ошибку вызывает чтение такого указателя |
| поле структуры, коллекция в поле | только значение, которое заимствует: структура с параметром источника или коллекция с источником в типе элемента |
| код C | точка доверия: условие результата и код `model` |
| корутина, другой поток | `Items.Item` не захватывает ([структура и поток](layout-reference.md#структура-и-поток)); структура переходит в другой поток целиком |

Слабой ссылки с проверкой при выполнении (поколение при слоте, как в `slotmap`) в модели нет: это проверка, а не
доказательство.

## Свободный граф

В графе вершины указывают друг на друга с любыми циклами и петлями. Владение по рёбрам такой граф не описывает:
цикл якорей не имеет владельца. Поэтому вершинами владеет структура `Graph` через отдельную цепочку якорей, а рёбра
записаны невладеющими указателями. Доказательством служит код функции удаления: её тело показывает, что указателей
на удаляемую вершину не осталось.

Самый простой граф: у каждой вершины есть вектор вершин, на которые она указывает.

```
 граф: A→B, A→C, B→C, C→A, C→C (петля)

 Graph.first ─▶ A ─ nextAll ─▶ B ─ nextAll ─▶ C       цепочка якорей владеет вершинами
 ┌──────────────┐   ┌──────────────┐   ┌──────────────┐
 │ A            │   │ B            │   │ C            │
 │ neighbors:   │   │ neighbors:   │   │ neighbors:   │
 │   B, C       │   │   C          │   │   A, C       │
 └──────────────┘   └──────────────┘   └──────────────┘
   каждый элемент neighbors: невладеющий указатель на вершину того же графа
```

```efen
layout {
    set Vertices: Vertex

    struct Vertex {
        var label: Int
        var neighbors: Vector<Vertices.Item>         // невладеющие указатели на вершины того же графа
        var nextAll: anchor Vertices.Item? = null    // цепочка всех вершин графа: владеет следующей
    }

    public struct Graph {                            // внешний код хранит граф значением
        var first: anchor Vertices.Item? = null      // владеет цепочкой вершин
        invariants {
            let all = Vertices.chain(from: first, by: Vertex.nextAll, until: null)
            forall v in Vertices: all.contains(v)
        }
    }
}

public fn addVertex(graph: edit Graph, label: Int) -> Vertices.Item {
    let v = mm.allocate(bytes: sizeOf(Vertex)) as Vertex(label: label, neighbors: Vector<Vertices.Item>())
    v.nextAll = tie graph.first             // прежняя первая вершина теперь под v
    graph.first = tie v                     // вершина принадлежит графу
    return graph.first!                     // указатель без владения, источник: graph
}

public fn addEdge(graph: mut Graph, from: read<graph> Vertices.Item, to: read<graph> Vertices.Item) {
    from.neighbors.append(to)               // to == from даёт петлю; mut: рост вектора переносит его слоты
}

public fn removeEdge(graph: mut Graph, from: read<graph> Vertices.Item, to: read<graph> Vertices.Item) {
    from.neighbors.removeAll(where: { $0 == to })
}

public fn removeVertex(graph: mut Graph, v: read<graph> Vertices.Item) {
    var w = graph.first
    while let x = w {                       // цепочка графа называет каждую его вершину
        x.neighbors.removeAll(where: { $0 == v })
        w = x.nextAll
    }
    let cut = unlinkVertex(graph, v)        // anchor Vertices.Item: вершина вырезана из цепочки графа
    let neighbors = take cut.neighbors      // вектор забран из вершины
    mm.free(cut as own Pointer)             // доказано: указателей на вершину нет, владеющие поля равны null
}                                           // конец области: dispose вектора neighbors возвращает его область
```

Встроенного перебора множества нет: обход идёт по цепочке графа, и инвариант «каждая вершина графа входит в
цепочку» даёт его полноту. Право `mut` на граф разрешает писать в каждую его вершину
([право на элемент](layout-reference.md#82-право-на-элемент)). Параметр
`v: read<graph> Vertices.Item` требует вершину именно этого графа ([запись и тип](layout-reference.md#ссылки),
правило 4). Вызывающий проверяется по сводке: `removeVertex` сжимает `neighbors` каждой вершины, поэтому её вызов в
теле обхода `for n in w.neighbors` вызывает ошибку, если обход после вызова продолжается.

**Кто чем владеет.** Вершинами владеет граф: цепочка якорей идёт от `Graph.first` по `Vertex.nextAll`. Внешний код
хранит `Graph` значением, и граф составляет публичную структуру. Указатели в `neighbors` владения не дают, поэтому
циклы и петли владельца вершины не меняют. Вершина нечиста: её `neighbors` указывают на другие вершины того же
графа. Все вершины вместе составляют чистый `Graph`
([чистая структура](layout-reference.md#структура-источник-чистота)).

**Чей указатель и кто пишет.** Множество `Vertices` одно на программу, а графов сколько угодно. Указатель, который
вернула `addVertex`, имеет источником граф. Писать значения в вершину разрешает право `edit` на её граф, менять
структуру разрешает `mut`; указатель без права только читает ([права в типе указателя](../types/ownership.md)).
Вызов `addEdge(graph, from: a, to: a)` даёт петлю и допустим: оба параметра-указателя только называют вершины.

**Что доказывает компилятор в `removeVertex`.** По правилу чистоты указатель на `v` хранится только внутри того же
графа: в `neighbors` его вершин, в `nextAll` и в `Graph.first`. Других полей типа `Vertices.Item` в `layout` нет.
Проход по цепочке убирает из каждого вектора все указатели на `v`, и компилятор выводит инвариант прохода
«в пройденных вершинах указателей на `v` нет». `unlinkVertex` вырезает вершину из цепочки и возвращает якорь. После
этого переход `cut as own Pointer` доказан. Между `unlinkVertex` и `mm.free` вершина под локальным якорем нечиста:
её `neighbors` ещё указывают на вершины графа. Это допустимо, потому что нового владельца вершина не получает и
функция её освобождает ([правило чистоты](layout-reference.md#структура-источник-чистота), раздел 4.3,
правило 5). Петля `v → v` удалена тем же проходом при `x == v`. Без прохода или с
проходом, который останавливается раньше `null`, функция вызывает ошибку.

Остальные функции доказываются сразу: `addEdge` и `removeEdge` только добавляют и убирают указатели, а `addVertex`
вводит вершину, на которую ещё ничто не указывает.

Условия, при которых это работает:

1. все места, где хранится указатель на вершину, известны: поля типа `Vertices.Item` и коллекции таких указателей
   в `layout` (`neighbors`), переменные, захваты;
2. сводка `removeVertex` говорит «освобождает `v`», и у вызывающего становятся недействительными указатели с
   источником в этом графе, которые могут быть равны `v`;
3. пока идёт обход цепочки, вызов, который освобождает вершины, вызывает ошибку: внутри прохода `removeVertex`
   вершины не освобождаются, освобождение идёт после;
4. освобождённый слот не путается с новым: адрес не устаревает, а индекс безопасен только вместе с условием 2.

**Цена.** Удаление вершины проходит все вершины графа и все их векторы. Цепочка `nextAll` занимает одно слово в
каждой вершине.

### Граф с обратными указателями

Если удалять нужно быстро, каждая вершина хранит ещё и вектор вершин, которые на неё указывают. Вершинами
по-прежнему владеет цепочка от `Graph.first` по полю `nextAll`.

```
 граф: A→B, A→C, B→C, C→A, C→C (петля)

 ┌──────────────┐   ┌──────────────┐   ┌──────────────┐
 │ A            │   │ B            │   │ C            │
 │ neighbors:   │   │ neighbors:   │   │ neighbors:   │
 │   B, C       │   │   C          │   │   A, C       │
 │ referrers:   │   │ referrers:   │   │ referrers:   │
 │   C          │   │   A          │   │   A, B, C    │
 └──────────────┘   └──────────────┘   └──────────────┘
```

```efen
layout {
    set Vertices: Vertex

    struct Vertex {
        var label: Int
        var neighbors: Vector<Vertices.Item>    // на кого ссылается этот узел
        var referrers: Vector<Vertices.Item>    // кто ссылается на этот узел
        var nextAll: anchor Vertices.Item? = null    // цепочка всех вершин графа: владеет следующей
        invariants {
            forall w in neighbors: w.referrers.contains(self)
            forall w in referrers: w.neighbors.contains(self)
            neighbors.isUnique && referrers.isUnique       // без кратных рёбер
        }
    }

    public struct Graph { var first: anchor Vertices.Item? = null }   // владеет цепочкой вершин, инвариант как выше
}

public fn addEdge(graph: mut Graph, from: read<graph> Vertices.Item, to: read<graph> Vertices.Item) {
    from.neighbors.append(to)
    to.referrers.append(from)
}

public fn removeEdge(graph: mut Graph, from: read<graph> Vertices.Item, to: read<graph> Vertices.Item) {
    from.neighbors.removeAll(where: { $0 == to })
    to.referrers.removeAll(where: { $0 == from })
}

public fn removeVertex(graph: mut Graph, v: read<graph> Vertices.Item) {
    for w in v.referrers { w.neighbors.removeAll(where: { $0 == v }) }
    for w in v.neighbors { w.referrers.removeAll(where: { $0 == v }) }
    v.referrers.removeAll(where: { $0 == v }) // собственная обратная петля; для перехода в own необязательно
    let cut = unlinkVertex(graph, v)        // anchor Vertices.Item: вершина вырезана из цепочки графа
    let neighbors = take cut.neighbors      // оба вектора забраны из вершины
    let referrers = take cut.referrers
    mm.free(cut as own Pointer)             // доказано: указателей на вершину нет
}                                           // конец области: dispose возвращает области обоих векторов
```

Инварианты здесь пишутся в обе стороны, и это не обратный инвариант, который ломает передачу через вызов: оба поля — указатели,
а не якоря, узлы никто не отрывает от структуры. Инвариант `isUnique` запрещает кратные рёбра, и `addEdge` получает
выведенное предусловие `!from.neighbors.contains(to)`. Для безопасности памяти хватило бы `contains`: `removeAll`
находит каждое вхождение, а удаление всех вхождений с обеих сторон не требует `isUnique`. Запрет кратных рёбер задаёт
именно модель простого графа. Между двумя строками `addEdge` инвариант нарушен. Показанный код допустим лишь при доказанно
небросающих вставках без обратного входа; иначе нужно заранее подготовить ёмкость обоих списков или откатить первую
вставку при неуспехе второй. Само имя операции контейнера этой гарантии не даёт.

**Что доказывает компилятор в `removeVertex`.** Если `v` лежит в `u.neighbors`, то по инварианту узла `u` в
`v.referrers` лежит `u`; если `v` лежит в `u.referrers`, то `u` лежит в `v.neighbors`. Значит, все указатели на `v` —
в узлах двух списков самого `v`. Два прохода убирают ссылки из остальных узлов; отдельная строка очищает собственный
`v.referrers`, где могла остаться петля после изменения `v.neighbors` первым проходом. Доказательство смешанное: инвариант сузил поиск до
двух списков, код проходит их. Инвариант после удаления проверяется только на узлах, которых проходы коснулись.

**Цена.** Удаление смотрит только на соседей `v`, зато каждая вставка ребра пишет в два места, а у каждого узла два
списка. При `Vector.removeAll` каждый такой список просматривается: цена определяется суммой их длин, а не только
числом рёбер самой `v`. Подробный разбор той же формы на цепочках рёбер — в [разборе](layout-proofs.md#граф-со-входящими-рёбрами).
Вырезание вершины из односвязной цепочки `nextAll` проходит цепочку; с обратным указателем в вершине оно обходится
без прохода.

## Что модель запрещает и что доказывает

**Запрещено: цикл якорей.** Цикл якорей не имеет владельца с момента, когда замкнулся. Какую запись якоря
`t.f = tie r` компилятор принимает, определяет правило 5 раздела
[«Перенос владения»](layout-reference.md#64-перенос-владения). Граф с циклами строится из невладеющих указателей. Вершинами владеет
структура, а функция освобождения доказывает, что указателей на удаляемую вершину не осталось.

**Доказывается выводом по цепочке — частично.** Цикл по одному полю, которое он не пишет, при инварианте, который
связывает соседей равенством или порядком, получает инвариант «отношение верно между началом и текущим элементом»;
обход по кругу до начала — «пройден весь цикл» ([правило](layout-proofs.md#правила-доказательства)). Отношение
текущего элемента с концом пути (сжатие пути в union-find) этим простым шаблоном не выводится; ниже предложен отдельный
[шаблон двух проходов](#сжатие-пути-и-union). Что граф после обхода стал прежним, компилятор не доказывает: он доказывает
только инварианты на выходе функции, а идентичность — правильность алгоритма.

**Не доказывается: правильность алгоритма.** Что `find` вернул представителя, а остов минимален, — вне модели.

## Проверка алгоритмов

Проверены тела и описания в этой статье, [доказательствах структур](layout-proofs.md),
[каталоге](layout-catalogue.md), пяти [проверочных файлах](layout-examples/checks/README.md) и шести
[представлениях массива](layout-examples/README.md). Код Amber в этом репозитории отсутствует; запустить на нём эти
примеры и подтвердить работу реализации FLOW невозможно. Старые пометки «да», «есть» и «нужен только Z3» в соседних
статьях не являются результатом такой проверки.

В таблицах **вывод** означает обоснование перечисленными здесь переходами и индукционными схемами при указанных
предпосылках. **Исправить** означает, что написанного кода или инвариантов недостаточно. **Нет тела** — проверена только
идея, полного доказательства конкретной функции нет. Ни один из этих статусов не означает машинно проверенную
корректность реализации FLOW. Синтаксические эскизы также нужно привести к актуальным правилам языка.

### Списки, деревья и графы

| Алгоритм | Результат и существенные обязательства |
|---|---|
| Вход памяти (`as`), освобождение (`as own`), создание группы | Вывод через свежесть, маску инициализации и единственного владельца. Взаимно ссылающиеся новые узлы создаются как закрытая группа: сначала резервируются слоты, затем инициализируются поля, затем проверяются инварианты и разрешается наблюдение. При ошибке очищаются только созданные компоненты. Отдельный `own` каждого узла со ссылками из другого не получается автоматически. |
| `setNext` с `own` | Вывод: `item.next == null`, совместимое происхождение, право записи; исключительность передаваемого хвоста исключает действующий `item` внутри него. |
| `push` с якорем и `pop` | Вывод: для вставки новый узел — отдельно хранимый корень без старого хвоста; для извлечения голова передаётся, а её `next` обнуляется через `tie`. При наличии `length` изменение равно изменению длины цепочки; арифметика выполняется до открытия инварианта либо доказывается небросающей. |
| Двусвязный `insertAfter` | Вывод при `node.next == null`, `a != node` и раздельном владении. Обрабатываются `a`, `node`, старый сосед; после передачи владельцев проверяются обе изменённые связи. |
| Двусвязный `remove` | Вывод для множества под владеющим полем, при `a = n.prev != null` и `a.next == n`. Последний факт нельзя получить только из ненулевого `prev` оторванного узла. До `free` переписаны `B.prev`, все другие хранимые держатели, если они объявлены, и учтены внешние выдачи. Без полного учёта владельцев показанный набор инвариантов недостаточен. |
| `rotateLeft` | Вывод для параметра-якоря `x`, вынутого из прежнего владельца. После `y = tie x.right` деревья `x` и `y` раздельны; `y.left` передаётся `x.right`, затем `x` под `y`. При чтении `x.parent` требуется его допустимость. Результат имеет прежний `x.parent`; вызывающий восстанавливает свой слот и инвариант. Вариант с одним `mut x` не даёт владения для `tie x`. |
| `freeTree` | Вывод по размеру леса для множества под владеющим полем и при полном перечне указателей на дерево: каждый ребёнок вынут, рекурсивно уничтожен, оба якоря пусты перед освобождением корня. Сводка уничтожает **всё входное поддерево**, не только корень. Отдельно хранимые узлы вызывающего сохраняют владельцев, но их ссылки на умерших родителей становятся недействительными. |
| `makePair`, `dropPeer` | Для `makePair` нужно учесть прежних партнёров: достаточное предусловие — оба `peer == null`. Иначе прежний партнёр может сохранить нарушенный инвариант. Для `dropPeer` нужны подходящие права и `a.peer == b`; из симметричного инварианта следует полный охват входящего `peer`. |
| Кольцо по `next/prev` | Вывод локальных вставок и удалений после разбора совпадений соседей, включая кольца размера 1 и 2. Полный обход требует хотя бы одного шага и стабильных связей. Инвариант допускает несколько колец; одной связности он не доказывает. |
| Граф, полный проход по цепочке вершин (от `graph.first` по `nextAll`) | Вывод шаблоном `Done/Remaining`, если все хранимые держатели служат проверенными полями вершин цепочки. Временные и внешние держатели проверяются отдельно. Досрочный выход не даёт отсутствия ссылок во всём графе. |
| Граф с `neighbors/referrers` | Удаление выводится из эквивалентности членства и двух проходов; петля допустима. Для вставки нужны отсутствие ребра при `isUnique` и безопасные исключительные исходы обеих вставок. Два последовательных потенциально бросающих `append` сами по себе не доказаны. |
| Граф с отдельным множеством `Edges` | Вывод через курсор: обработанные рёбра либо удалены, либо не касаются `v`; необработанные не пропущены. Любой `Cursor` или другой держатель указателя на удаляемое ребро тоже должен быть учтён. |
| Граф с исходящей и входящей цепочками | Вывод требует полного членства каждого хранимого ребра в обеих цепочках, принадлежности одному графу, однородности `to` во входящей цепочке и конечности. Самого факта «ребро найдено в цепочке» недостаточно для рамки остальных рёбер; используются разложение цепочек и правило произвольного элемента. |
| LRU | В каталоге нет тела удаления и полного набора инвариантов — готового доказательства нет. В одном `layout` решается одним владельцем записи, двусторонними `older/newer`, инвариантами концов и учётом всех корзин, хвостов и курсоров; удаление очищает оба индекса до `free`. |

Для `remove` полезен точный след. На входе `H₀[A].next = N`, `H₀[N].next = B`, `H₀[B].prev = N` (если `B` есть).
После `tie A.next` владельцем `N` стала локальная переменная, но факт о входящем `B.prev` не исчез.
После переноса `N.next` в `A.next` у `N.next` уже `null`; это не доказывает отсутствия входящих ссылок.
Только запись `B.prev = A` закрывает прежний держатель. Затем проверяются прочие классы держателей, пустота якорей
`N`, выдачи, и переход к уничтожению разрешён. Переставить `free` перед записью `B.prev` нельзя.

В графе с обратными списками первая петля может обработать `w == v`: она удаляет `v` из `v.neighbors`, а перебирает
`v.referrers` — другой контейнер. После неё во втором переборе `v.neighbors` уже нет `v`, поэтому запись в
`w.referrers` не меняет перебираемый контейнер. Это требует модели отдельных буферов `Vector` и сводки `removeAll`,
а не предположения, что `w != v` всегда. На выходе для произвольной оставшейся вершины `u` оба вида ссылок на `v`
исключены входным двусторонним инвариантом и эффектами проходов.

Во всех старых `.efen`-эскизах массива условия полей, читающие соседние поля, нужно перенести в `invariants`
с правильными точками восстановления. В списковых эскизах `nodes.count - 1` также неопределён при пустой
последовательности с беззнаковым размером. Безопасная запись связи соседей:
`forall i in 0 ..< nodes.count: i == 0 || nodes[i - 1].next == nodes[i]`.
Она не вычисляет `i - 1` при `i == 0`; для обратной связи используется такая же защита. Это исправления базы
доказательства, а не замечания к оформлению. Готовые схемы операций из таблицы относятся к исправленным инвариантам.

**Пул.** Достаточное усиление инварианта для вместимости `C`:

```text
0 <= frontier <= C
Taken ⊎ Free = [0, frontier)
Free — конечная цепочка без повторов
used = |Taken|
```

При выдаче из свободной цепочки её голова переносится из `Free` в `Taken`; при выдаче у границы в `Taken` добавляется
старый `frontier`, затем граница увеличивается. При возврате происходит обратный переход. Из разбиения следуют
неповторность выдачи и отсутствие потерянных доступных слотов. Контрпример старым инвариантам: `C=1`, `frontier=0`,
`Taken={0}`, `Free=∅`, `used=1`. Все перечисленные в каталоге равенства верны, но ветка выдачи у границы выбирает
уже выданный слот. Сама операция `lend` должна отвергнуть это состояние; для принятия `acquire` нужно усилить инвариант.

**Сдвиг массива.** Пусть до вставки инициализирован `[0, n)`, а ёмкость не меньше `n+1`. На голове цикла с `cursor=c`
маска — `[0, c) ∪ [c+1, n+1)`: слот `c` не инициализирован. Перенос `c-1 → c` законен и уменьшает `c`. На выходе не инициализирован именно
`index`, его заполняет запись нового значения. При удалении после `take` слота `index` маска `[0,c) ∪ [c+1,n)`, а перенос `c+1 → c`
увеличивает `c`; на выходе пусто `n-1`. Так ни одна запись не теряет владельца, ни одно чтение не берётся из дырки.
На любой ошибке необходим cleanup по **этой маске**, а не по старому `length`; удобный вариант — исключить ошибки
внутри сдвига проверенной подготовкой. Частично извлечённый `Item` освобождается без повторного уничтожения `Target`.

**Блоки.** Для размера блока `K > 0`, общего размера `N` и `m` выделенных блоков достаточно:

```text
m >= ceil(N / K)
для каждого j < m:
    Chunk[j].length = min(K, max(0, N - j*K))
    initialized(Chunk[j]) = [0, Chunk[j].length)
```

Формула — математическая; вычисления индексов в программе отдельно проверяются на переполнение. Тогда из `i < N`
следуют существование блока `i / K` и инициализация смещения `i % K`. Лишние выделенные блоки пусты. Старые условия
допускают `K=2`, длины блоков `[0,1]`, `N=1`: общий счёт верен, но `itemAt(0)` читает пустой первый блок.
Во время сдвига маска может иметь дырку в любом блоке; публикуемые `Chunk.length` восстанавливаются к выходу.

**Пять файлов `checks/*.efen`.** Это исторические пробы, не набор уже принятых программ. Для пула заменить потерю
источника через `Pointer` и произвольный `k=0` на передачу идентичности слота. Для списка вывести пустоту `node.next`,
проверить арифметику и запретить использование имени после передачи/уничтожения. В `peekPast` кольца возможен
индекс вне области; при `head=63,count=1` он равен 64. В хеш-таблице `Bucket.head` объявлен невладеющим, хотя код
передаёт в него владельца: сначала исправить тип, затем проверять корзину и знак остатка. В дереве согласовать
владельцев с обратными указателями и проверять очистку/инвалидацию `parent` после отделения. Пустые `drop` также
не доказывают освобождения ресурса, если lowering не вставляет проверенное уничтожение.

### Сжатие пути и union

Простой шаблон отношения «начало — текущий узел» недостаточен, но показанный `find` допускает следующий специальный
кандидат без пользовательского инварианта цикла. FLOW распознаёт два прохода и вводит призрачную последовательность
`P` реально пройденных узлов; это не предположение о произвольной достижимости.

Первый проход читает стабильные `parent` и `rank`. Инвариант: `P[0] = x`, последний элемент — `root`, соседние
элементы связаны входным `parent`, ранги строго растут, повторов нет. При переходе к следующему узлу все свойства
сохраняются инвариантом `parent == self || parent.rank > rank` и транзитивностью. Мера завершения — число ещё не
добавленных элементов конечного входного множества. На выходе `root.parent == root`, и ранг последнего элемента
больше ранга любого предыдущего.

Во втором проходе `y = P[k]`. Для пройденного префикса `parent` уже равен `root`, для оставшегося суффикса сохранён
прежний `parent`; ранги не менялись. Ветка `y.parent != root` может выполняться только для не-корня. Сохранённый
`next` равен следующему элементу `P`, запись `y.parent = root` сохраняет инвариант ранга, а `y = next` увеличивает `k`.
Ранний выход при непосредственном ребёнке корня безопасен: его родитель уже нужный. Ни один прежний корень не меняет
родителя. Это последнее свойство входит в сводку `find` и сохраняет результат первого вызова после второго в `union`.

В `union` при разных рангах новый родитель имеет больший ранг. При равных рангах повышение ранга корня сохраняет
инварианты его прежних детей монотонностью, но выражение `ra.rank + 1` может бросить. Его нужно вычислить **до** записи
`rb.parent = ra`, затем выполнить обе записи без отказа. Иначе максимальный машинный ранг даёт исключительный выход
с уже ложным инвариантом. Два корня сначала сравниваются: при `ra == rb` функция ничего не меняет.

Этот вывод требует именно описанных стабильности и формы проходов. Если первый проход вызывает изменяющий `rank`
код или второй следует по уже переписанному `parent` без сохранённого `next`, шаблон неприменим. Без инварианта ранга
можно отдельно доказать безопасность обращений, но нельзя обещать завершение поиска на произвольном цикле.

### DCEL, Шорр — Уэйт и копирование графа

**DCEL.** Инварианты действительно ограничивают держателей указателей на полуребро `h`: парное, два соседа, поле
вершины и поле грани. Это доказывает полноту поиска входящих ссылок, но ещё не корректность перестройки.
Пример, удовлетворяющий указанным инвариантам (у всех одна грань; `prev` обратен `next`):

```text
twin:   0↔1, 2↔3
next:   0→2→0, 1→3→1
origin: [A, B, B, A]
```

Если удалить пару `0,1`, просто обойдя её в циклах, останутся `2.next=2` и `3.next=3`. Инвариант обратных соседей верен,
но `2.twin.origin=A`, а `2.next.origin=B`: инвариант концов ребра нарушен. Поэтому утверждение «удаление пары доказано
локально» нужно читать как возможность конечной проверки, не как доказательство произвольного удаления. Нужны
конкретная операция и её предусловия, например с корректным слиянием вершин/граней и обновлением их держателей.
Без тела такой операции результат — «не доказано». Удаление грани обходом одного кольца также не охватывает дырки;
достаточный вариант — проход по всем `HalfEdges` с проверенным исправлением `face` и зависимых инвариантов.

**Шорр — Уэйт.** В статье нет тела алгоритма, поэтому полное доказательство конкретного обхода отсутствует.
Для варианта только с инвариантом рёбер записи указателей на живые узлы сохраняют этот инвариант. Но отдельно нужны
проверки всех чтений, `null`, инициализации и прав. Если заданы двусторонние инварианты, их восстановление требует
инварианта развёрнутого пути; схема «проверить тронутые узлы на выходе» сама этот инвариант не создаёт. В первом
варианте FLOW такой код отвергается, пока не найден и не проверен подходящий шаблон. Восстановление исходного графа
и посещение всех достижимых вершин остаются отдельными функциональными свойствами.

**Копирующий сборщик.** Немедленное освобождение каждого старого объекта после копирования небезопасно при циклах.
Для `A→B→A` после копирования и освобождения старого `A` обработка старой ссылки из `B` уже не может читать
`A.forward`. Исправленный алгоритм сохраняет всю старую область до завершения перенаправления.

Достаточная схема доказательства копирования с очередью:

1. Зафиксировать конечное множество старых объектов `Old`, учесть все корни, внешние выдачи и источники. Живое
   заимствование перемещаемой памяти должно быть завершено кодом возврата либо корректно обновлено проверенным
   протоколом; обычный внешний адрес нельзя незаметно оставить у вызывающего.
2. `forward` — частичное взаимно однозначное отображение старых объектов в новые. Первый перенос создаёт новый
   слот, повторный возвращает уже записанное. До публикации нового объекта все читаемые компоненты инициализированы;
   для циклов запись пересылки предшествует обработке его ссылок. Указатель на строящийся объект не разрешает читать
   ещё неинициализированные поля.
3. Корни перенаправлены; новая область разбита на просканированную и очередь. В просканированных объектах ссылки
   ведут в новую область, в очереди ещё разрешены старые ссылки. Старая область и её записи пересылки живы.
4. Обработка одного объекта перенаправляет все его поля-указатели и переносит границу сканирования. Добавление в
   очередь происходит только при новом значении `forward`; мера — лексикографическая пара
   `(|Old| - |domain(forward)|, число непросканированных новых объектов)`.
5. При пустой очереди у всех корней и новых объектов нет указателей в `Old`. Проверяются остальные классы
   держателей, завершённость выдач и ресурсная очистка; только затем освобождается старая область целиком.

Поля с ресурсами нельзя просто побитово скопировать и получить двух владельцев. Нужно передать каждый ресурс один
раз либо ограничить допустимые типы объектов. Ошибка выделения в середине требует сохранённого старого состояния
и отката владельцев/пересылок; достаточный первый вариант — заранее выделенная новая область нужного размера и
небросающий этап переноса. В исходном тексте тела сборщика нет: эта схема задаёт обязательства для будущей реализации,
а не подтверждает любой алгоритм, названный копирующим сборщиком.

| Сдвиги массива с маской инициализации | Все позиции при длине 0–8: 81 случай |

| `find` и исправленный `union` | Все родительские функции и ранги `0 ..< n`, удовлетворяющие инварианту, при `n=1..4`: 13 919 поисков, 55 343 объединения |
| Перехеширование | Все наборы из 0–5 записей с ключами `0..3`, переход с 2 на 4 корзины: 1 365 случаев; владельцы не дублируются и старые корзины пустеют |
| Отрицательные примеры | 15 свидетелей: зависимость чужого инварианта, цикл владельцев, повторная выдача, дырка в блоках, прежний партнёр, overflow в `union`, раннее освобождение пересылки, нестабильные данные пути, удаление пары DCEL, собственная петля перед `own`, устаревшее условие возврата, перемещение захваченного источника, underflow в инварианте пустого списка, неохваченный `prev` узла под множеством, изменяемое чужое состояние в коде возврата |

Успех такого перебора — проверка ошибок в рассуждении на конечной модели. Он не заменяет доказательство базы, шага,
рамки и выхода, не подтверждает cleanup и ABI и не является результатом запуска существующего FLOW.

## Что ещё нужно определить

Для первого варианта решения заданы: состояния памяти и владельцев, правила событий, проверка зависимостей,
сводки нормальных и исключительных исходов, конечные шаблоны циклов. Заимствование не вводит особого списка разрешённых действий: разрешено то, для чего эти правила дали
доказательство. Неподдержанный случай отвергается, даже если он фактически безопасен.

Осталась реализация и проверка soundness переходов самого FLOW, проверка операций над памятью при выполнении и
порождение кода очистки.
Параллельный `shared` — модель раздела [«Многопоточность»](layout-reference.md#многопоточность) в `layout-reference.md`. У схем без тела — DCEL, Шорр — Уэйт, mm, открытая адресация — нельзя
объявить доказанной конкретную функцию до появления её кода и получения перечисленных обязательств.
