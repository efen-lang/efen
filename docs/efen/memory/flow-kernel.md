# Малое проверяемое ядро FLOW

[Алгоритм layout](layout-algorithm.md) · [Исходный код проверяющего](layout-examples/checks/flow-kernel/kernel.py) ·
[Проверяемые функции](layout-examples/checks/flow-kernel/verify.py)

Статус: отдельный эксперимент на Python и Z3, не реализация FLOW Amber. Здесь зафиксированы переходы небольшой
IR и воспроизводимые обязательства их проверки. Это следующий шаг после конечных моделей: формулы содержат
произвольные идентичности, значения и размер кучи, а не перебор до выбранного числа объектов.

## Что входит в ядро

Один `layout`, последовательное выполнение, отдельные выделения со скалярным содержимым. Значение имеет владельца:
текущую функцию, множество источника или внешнего получателя. Есть `own`, публикация под множеством, получение
обратно в `own`, чтения через локальные заимствования и `external own` с **фиксированным** продолжением возврата.
Публичный результат может передавать обычное владение навсегда или переносить обязательство внешнего заимствования.

Поддержаны конечные графы управления: последовательность, ветвление, выделение с независимыми исходами успеха и
ошибки, `return`, `throw`. Очистка — явные инструкции на соответствующем пути. Проверяющий её не дорисовывает.
Источник передаётся функции как существующий домен с правом выполнять его операции; ядро не создаёт локальные
экземпляры `Self` со скрытым временем жизни. Все структурные операции принадлежат этому единственному `layout`.

В ядре **нет** полей-указателей, якорей, пользовательских структурных законов, вложенных областей, физического
перемещения, циклов CFG, рекурсии, произвольных вызовов и продолжений, callback, приостановки, потоков и деструкторов
полезной нагрузки. Это не доказательство списка, дерева, пула или GC. Поддержка этих конструкций не подразумевается
успехом проверки маленького ядра; неподдержанные инструкции отвергаются.

Скалярное содержимое моделируется математическим `Int`, но IR только записывает входное значение/константу и читает
его: арифметики полезной нагрузки нет. Поэтому этот эксперимент ничего не доказывает о машинном overflow. Операнды
не могут быть произвольными SMT-формулами с чтением скрытой памяти. Условия веток — входные булевы значения/константы;
исход каждой операции выделения проверяющий создаёт отдельной свежей булевой переменной.

## Конкретное состояние и его символическое представление

Идентичность объекта — натуральный номер рождения `i > 0`. `epoch` — наибольший когда-либо выданный номер.
При новом выделении получается `epoch + 1`; после освобождения номер не используется повторно. Это призрачная
идентичность, а не требование бесконечного счётчика в runtime. Связь этой модели с повторным использованием
физического адреса предстоит доказать при реализации lowering.

Состояние кучи `H` содержит `epoch`, флаг жизни источника `source` и пять отображений по идентичностям:

| Отображение | Значение |
|---|---|
| `live[i]` | память объекта жива |
| `init[i]` | скаляр инициализирован |
| `owner[i]` | `DEAD`, `SOURCE`, `LOCAL` или `OUT` |
| `lent[i]` | существует внешнее заимствование объекта |
| `value[i]` | содержимое; читать можно только при доказанных правах, живости и инициализации |

`OUT` означает владение вне текущей функции, а не отсутствие владельца. Все выделения имеют независимое backing
storage: обычный владелец может пережить источник. Для части общей страницы такой вывод неприменим.

В символическом состоянии это массивы SMT; запись — `Store`, чтение — `Select`. Неизвестное совпадение идентичностей
не считается различием. Начальные состояния `incoming` задаются произвольными масками занятости, внешнего владения,
инициализации и займов на диапазоне `1..epoch`. Размер `epoch` не ограничен. Маски представляют любой корректный
фон при заявленном контракте: источник жив, локальные владельцы — только переданные параметры, остальные объекты
принадлежат источнику или внешнему коду. Отдельный вход `empty` задаёт пустой источник.

Конструктивное представление начальной кучи нужно для решаемости проверок. Вместо предположения сложной
кванторной аксиомы правильность этого представления проверяется на произвольной идентичности при входе. Фон не
объявляется пустым: неизвестные посторонние объекты и внешние займы сохраняются.

## Инвариант кучи и линейный учёт

`WF(H)` — следующая формула для **каждого** целого `i`:

```text
epoch >= 0
owner[i] ∈ {DEAD, SOURCE, LOCAL, OUT}
live[i] ⇔ owner[i] != DEAD
live[i] ⇒ 0 < i <= epoch
init[i] ⇒ live[i]
owner[i] == SOURCE ⇒ source && init[i]
lent[i] ⇒ source && owner[i] == SOURCE
```

Одного `WF` недостаточно. Он ничего не говорит о забытом локальном владельце или результате, указывающем на
мёртвый объект. Поэтому отдельно ведётся среда линейных токенов и невладеющих чтений. Токен содержит вид `own`/`loan`,
идентичность объекта и идентичность права. `move` переносит токен, чтение его не копирует.

На входе, после каждой инструкции и на выходе проверяются:

1. `owner[i] == LOCAL` тогда и только тогда, когда в среде ровно один владелец `own` для `i`.
2. `lent[i]` тогда и только тогда, когда это заём внешнего контекста, токен `loan` текущей функции или явно
   переданный результат-заём. Эти классы не дублируют друг друга.
3. Активные линейные токены имеют различные права и объекты. Локальное чтение ссылается на существующий токен
   именно того же объекта. Перед передачей/погашением токена все чтения от него завершены.
4. Результаты-владельцы живы, инициализированы и имеют `owner == OUT`; результаты-займы сохраняют своё обязательство.
5. На `return` и `throw` локальная среда пуста: ресурсы возвращены, опубликованы под источником или явно переданы
   результатом. На `throw` результатов нет. Память живого входного источника остаётся у источника, а не теряется.

Посторонние внешние займы представлены неизменяемой маской `ambient_loans`. Функция не может погасить их без
соответствующего входного токена. У входного параметра `loan` его объект исключается из фоновой маски и учитывается
в локальной среде. Новую выдачу нельзя скрыть в этой маске.

Имена исходных объектов в `ids` — сведения об идентичности, **не права чтения**. Даже если имя осталось после
освобождения, операция над ним должна заново доказать нужное состояние. Новое выделение не оживляет старую
идентичность. Обычные хранимые невладеющие указатели на объекты источника в эту IR не входят.

## Точные переходы

Неуказанные компоненты состояния сохраняются. Все локальные передачи дополнительно требуют завершённых чтений
от передаваемого токена; эта проверка относится к среде, а не к таблице кучи.

| Переход | Предусловие | Изменение |
|---|---|---|
| Успех выделения | доверенный распределитель предоставляет новое отдельное место | `i=epoch+1`, `epoch=i`, `live[i]=true`, `init[i]=false`, `owner[i]=LOCAL`, `lent[i]=false`; создать `own` |
| Ошибка выделения | отдельный возможный исход | куча и владельцы не меняются; исполняется написанная ветка ошибки |
| `init` | локальный владелец, место не инициализировано | записать скаляр, установить `init` |
| `publish` | локальный владелец, скаляр инициализирован, источник жив | потребить `own`, установить `owner=SOURCE` |
| `reclaim` | живой объект источника без внешнего займа | `owner=LOCAL`, создать `own` |
| `lend` | живой инициализированный объект источника без займа | `lent=true`, создать линейную пару указателя и фиксированного возврата |
| `release` | именно токен живого займа этого источника | `lent=false`, потребить токен |
| `free` | локальный владелец без займа | `live=false`, `init=false`, `owner=DEAD`, потребить владельца |
| Обычный результат `own` | локальный владелец и инициализированное значение | `owner=OUT`, передать владельца в результат |
| Результат `external own` | токен займа без производных чтений | перенести токен в результат, `lent` остаётся истинным |
| `write_source` | объект принадлежит живому источнику, займа нет | заменить скаляр |
| Чтение | живой корневой токен `own` или `loan`, соответствующее локальное чтение, `live && init` | память не меняется |
| `close_source` | источник жив и не владеет ни одним объектом | `source=false`; независимые `LOCAL`/`OUT` не уничтожаются |

`free` может вернуть неинициализированное место, поскольку полезная нагрузка здесь — скаляр без ресурсов и
деструктора. Этот переход нельзя переносить без уточнений на произвольный тип `T`. `write_source` во время займа
консервативно запрещён этим ядром; это не новое ограничение общей модели, где более точное доказательство может
разрешить запись. Закрытие источника не означает скрытый проход освобождения: его множество уже должно быть пусто.

## Проверяемое продолжение возврата

Для ядра код возврата фиксирован: операция `release(i)` с погашением данного линейного токена. У него нет
пользовательских захватов, исключений, вызовов и приостановки. Поэтому

```text
ReturnReady(i, H) = source && live[i] && init[i] && owner[i] == SOURCE && lent[i]
```

`lend` устанавливает этот факт. Для каждого примитива проверяется сохранение `ReturnReady` уже существующих займов;
`release(i)` исключает ровно погашаемый заём. Закрытие источника с займом не проходит предусловие. Перед выполнением
возврата проверяющий дополнительно требует завершения всех производных чтений. Фиксированный возврат состоит
из одного перехода, поэтому завершается; здесь нет предположения о завершении произвольного продолжения.

`acquire` передаёт обязательство наружу. Отдельно проверенное тело `release` принимает его как входной линейный
параметр и погашает. Внешний код должен соблюдать эти права. Реальное представление пары в ABI и трансляция
вызова продолжения не реализованы этим экспериментом.

## Как генерируется доказательство

Для обязательства `P ⇒ Q` скрипт спрашивает Z3 о выполнимости `P && !Q`. Только `unsat` означает успех.
`sat` даёт контрпример, `unknown` и тайм-аут означают отказ. Невыполнимый входной контракт отвергается отдельно,
чтобы ошибочная функция не получила зелёный результат из противоречивых предположений.

Для каждого примитива на произвольных `H`, цели `i` и наблюдаемом объекте `q` проверяются:

```text
WF(H, q) && WF(H, i) && pre(op) ⇒ WF(step(op, H), q)
q != i ⇒ все пять отображений кучи в q сохраняются
ReturnReady(q, H) ⇒ ReturnReady(q, step(op, H))    // кроме погашаемого займа
```

Для выделения `i=epoch+1`; отдельно проверяется свежесть. Для закрытия источника предусловие квантифицировано по
всей куче, а все отображения неизменны. Также проверяются база пустого состояния, недопустимость повторного
освобождения и возврата, живость и инициализация при чтении. Получается 42 обязательства. Произвольный `q` —
символическая переменная, а не один выбранный пример: невыполнимость отрицания проверяет все её значения.

Проверяющий тела функций идёт по конечному CFG, сохраняя обе ветки вместе с их условиями. Он не объединяет их с
потерей информации. Пропустить ветку можно только после ответа `unsat` на её достижимость; `unknown` не позволяет
пропуск. На каждом переходе проверяются предусловие и полный линейный учёт. Уже доказанный факт разрешается
добавить к состоянию; непроверенного `assume` в IR нет. Для каждой функции проверяются все достижимые выходы.

На бумаге из этих правил получается следующая условная теорема: если вход соответствует `WF` и линейной среде,
примитивы исполняют указанную семантику и все обязательства конечного тела выполнены, каждый его доступ допустим,
а завершение не теряет локальные ресурсы и займы. Аргумент — индукция по переходам и структуре CFG:
свежесть даёт базу нового владельца; передача меняет ровно одного владельца; чтения ограничивают погашение права;
заём сохраняет источник и возврат; каждая ветка ошибки явно погашает оставшиеся обязательства; выход проверяет
баланс и передаваемые результаты. Правило кадра сохраняет посторонние объекты, включая неизвестное число займов.

Это **не механизированное доказательство метатеоремы** о Python-проверяющем. Z3 проверяет сформированные формулы;
соответствие формул семантике IR, корректность обхода CFG и представления прав остаются частью доверенной реализации.
Для дальнейшей формализации нужны отдельная операционная семантика, отношение представления и машинная проверка
этой индукции. Корректность распределителя, runtime и lowering efen из неё также не следует автоматически.

## Полные функции и отрицательные проверки

Тела находятся в `positive_programs()` файла `verify.py`, а не генерируются из текста efen.

| Функция | Проверяемое поведение |
|---|---|
| `create_pair` | две аллокации, инициализация, проверка входного флага; четыре пути, включая ошибку каждой аллокации и отказ после обеих; очистка всего уже выделенного на ошибке, два живых владельца на успехе |
| `with_loan` | выдача, производное чтение, завершение чтения и возврат займа как на успехе, так и при ошибке |
| `loan_allocation_cleanup` | временное выделение при живом займе; при отказе распределителя заём всё равно возвращается |
| `acquire` | передача наружу того же живого займа вместе с обязательством возврата |
| `release` | погашение входного займа без изменения скаляра и посторонних займов |
| `detach` | перевод объекта источника в обычный `own` и окончательная передача наружу |
| `move_owner` | перенос токена, чтение через него, завершение чтения и передача результата |
| `update_after_return` | запись в объект после возврата займа; в результате новое содержимое и нет займа |
| `detach_and_close` | отделение объекта, закрытие пустого источника, передача живого владельца наружу; ошибка выделения также закрывает источник |

Всего 9 тел и 15 конечных путей. Контракты `incoming` допускают произвольный корректный фон; `create_pair` и
`detach_and_close` начинают с явно пустого источника. Дополнительные постусловия проверяют значения, очистку,
возврат займа и жизнь окончательно переданного объекта после закрытия источника.
На каждом выходе также проверяется рамка всей функции: ни одно отображение для прежней идентичности вне входного
набора затронутых объектов не изменилось. Новые идентичности находятся выше входного `epoch`.
На Z3 4.13.4 проверены 42 обязательства переходов и 131 обязательство положительных тел; отвергнуты все 23
отрицательных случая. Тайм-аут в отрицательном примере не засчитывается как найденный контрпример.

Отрицательные случаи включают чтение до инициализации, double-free, активное чтение при уничтожении/возврате,
потерю владельца или займа на одном выходе, вторую выдачу, уничтожение источника с займом, использование
перемещённого владельца, дублирование результата/входного владельца, запись при займе, ложный входной контракт,
неподдержанный цикл, скрытое чтение памяти в SMT-операнде, неинициализированный результат и старую идентичность
после нового выделения. Ещё две проверки намеренно портят переходы: `release` не снимает `lent`, а `export`
освобождает результат. Инвариант кучи сам по себе их не исключает — нарушения обнаруживает линейный учёт.
Отдельно проверяется отказ при `unknown`. Ни один отрицательный пример не должен быть принят.

## Воспроизведение

Из корня репозитория, Python 3.10 или новее:

```sh
python3 -m venv /tmp/efen-flow-kernel
/tmp/efen-flow-kernel/bin/pip install -r docs/efen/memory/layout-examples/checks/flow-kernel/requirements.txt
/tmp/efen-flow-kernel/bin/python docs/efen/memory/layout-examples/checks/flow-kernel/verify.py --emit-vcs /tmp/efen-flow-vcs
```

`--emit-vcs` необязателен. Он сохраняет обязательства в SMT-LIB и `report.json` с результатом каждого запроса,
перечнем функций и диагностик. В каталоге будут и намеренно опровергаемые обязательства отрицательных примеров:
для них ожидается `sat`, а не `unsat`. Ошибки линейной среды могут обнаруживаться до обращения к решателю.
Для нового отчёта следует использовать новый пустой каталог, чтобы не смешать файлы разных запусков.

Следующее расширение — одно поле-якорь и его перенос с доказательством отсутствия цикла, затем один цикл с явно
заданным инвариантом. Автоматический вывод инвариантов, обобщённые контракты функций и произвольный код возврата
нужно добавлять и проверять отдельно. Проверяющий не должен объявлять их поддержанными по аналогии с этим ядром.
