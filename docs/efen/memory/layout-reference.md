## 1. Что такое layout

**Правило.** `layout` объявляет память структуры данных: множества элементов, владение ими, указатели между ними и
то, что получает внешний код. Всё, чего `layout` не объявил, запрещено.

**Пример.** Двусвязный список. Узлы составляют множество `Items`, поле `next` владеет следующим узлом, поле `prev`
только указывает на предыдущий.

```efen
layout {
    set Items: Item

    struct Item {
        var value: Int
        var next: anchor Items.Item? = null      // владеет следующим узлом
        var prev: Items.Item? = null             // указывает на предыдущий, не владеет
    }
}
```

**Запрещено.** У каждого множества есть владелец: владеющее поле или строка владения (`public own S`,
`public lend T.поле`). Множество, у которого нет ни поля, ни строки, вызывает ошибку (раздел 3.4). Хранимый
невладеющий указатель указывает только внутрь своей публичной структуры (разделы 3.3 и 4.3). Внешний код получает
во владение только то, что `layout` назвал. Указатель, использованный после уничтожения его цели, вызывает ошибку
компиляции: компилятор показывает её в строке изменения структуры и отдельно показывает строку использования.

**Почему.** Два поля или два параметра указывают на одну память, только если это объявлено явно
([поля не делят память](../types/ownership.md#поля-не-делят-память)). Способов объявить два. Первый способ:
право с источником, `право<поле или параметр>`. Так пишутся поле-псевдоним `current: read<self.children> Node?`,
поле `items: read<Src> Array<T>` и параметр `src: read<dst?> T`. Второй способ: `layout`. По объявлениям `layout`
компилятор доказывает два свойства. Ни один указатель не используется после уничтожения цели. Каждый слот, выданный
внешнему коду, возвращается, а каждый элемент, которым владеет поле или переменная, уничтожается явным кодом.

Доказывает эти свойства FLOW, анализатор потока в компиляторе. Условия, которые FLOW не доказывает сам, он
передаёт решателю Z3. Место, где компилятор принимает факт без доказательства, называется точкой доверия. Точка
доверия бывает только объявленной. В `layout` встречаются пять видов: строка `assume`; условие результата у вставки
`@asm`; объявление без тела, которому компилятор верит по записи (функция C с правами из `@fill`, код `model`);
приведение адреса из C к элементу множества (раздел 4.5); объявление функции `@abi(c)` с телом, о которой
компилятор принимает, что C вызывает её в одном потоке (раздел 9.1, правило 5). Все точки доверия пакета печатает
`efen proofs`. Полный список мест, которые компилятор принимает на веру, приведён в статье о
[системных вызовах](system.md#кому-доступно-доверие).

Экземпляров у `layout` нет. `layout` стоит на уровне модуля и только описывает память. Значения создают его
структуры (раздел 2.3).

<a id="layout-в-теле-класса"></a>

Слово `layout` в теле класса, интерфейса или контракта означает другое. Там оно описывает не байты, а то, что
заимствует внешний код, и физических объявлений (`set`, `area`, `one`, `struct`) не содержит. Его правила стоят в
статье о классах: [`layout` в теле класса](../classes.md#layout-в-теле-класса).

## 2. Объявление

`layout` объявляет множества и области, структуры их элементов и то, какой код пишет поля. Остальные разделы
опираются только на эти объявления.

Три примера ниже используются во всех разделах.

```efen
// Пример A: двусвязный список
layout {
    set Items: Item

    struct Item {
        var value: Int
        var next: anchor Items.Item? = null
        var prev: Items.Item? = null
        invariants { next == null || next!.prev == self }
    }

    public struct List {
        var head: anchor Items.Item? = null
        var tail: Items.Item? = null
        var length: Int = 0 { value >= 0 }
    }
}

// Пример B: пул, который выдаёт память внешнему коду
layout {
    set area Blocks: Block

    public lend Block.data

    struct Block {
        var next: anchor Blocks.Item? = null
        var prev: Blocks.Item? = null
        area data: Byte
        invariants { next == null || next!.prev == self }
    }

    public struct Pool { var busy: anchor Blocks.Item? = null }
}

// Пример C: граф, вершинами которого владеет структура Graph
layout {
    set Vertices: Vertex
    set Edges: Edge

    struct Vertex {
        var label: Int
        var neighbors: Vector<Vertices.Item>         // соседи: вершины того же графа
        var firstEdge: anchor Edges.Item? = null
        var nextAll: anchor Vertices.Item? = null    // цепочка всех вершин графа: владеет следующей
    }

    struct Edge {
        var to: Vertices.Item                        // вершина того же графа
        var next: anchor Edges.Item? = null
    }

    public struct Graph {                            // внешний код хранит граф значением
        var first: anchor Vertices.Item? = null      // владеет цепочкой вершин
        invariants {                                 // цепочку описывает раздел 5.2
            let all = Vertices.chain(from: first, by: Vertex.nextAll, until: null)
            forall v in Vertices: all.contains(v)
        }
    }
}
```

<a id="множества-и-области"></a>

### 2.1 Множества и области

**Правило.** Каждый элемент памяти `layout` принадлежит множеству или области, объявленным одной из четырёх строк.

| Строка | Что объявляет |
|---|---|
| `set X: T` | множество элементов структуры `T` без обещания непрерывности: узлы списков, деревьев, графов |
| `area X: T` | область: непрерывные слоты одной структуры, доступные по индексу `0 ..< count` |
| `set area X: T` | множество независимых областей (участки менеджера памяти); каждый байт принадлежит элементу |
| `one X` | один экземпляр структуры `X` на программу, как `static`; на его единственность FLOW опирается |

Дополнительные правила:

1. Множество одно на программу. `set Items: Item` называет все узлы этой структуры во всей программе, а списков
   `List` сколько угодно. Поэтому узел, вынутый из одного списка, вставляется в другой обычной операцией.
2. Своей памяти у множества нет, оно не создаётся и не уничтожается. Множество даёт имя типу указателя:
   `Items.Item` значит «элемент из `Items`». Время жизни есть у памяти элементов. Она взята из исходной памяти
   (у ОС, из области родителя) и возвращается туда явным кодом. Возврат при выходе процесса не считается.
3. Число слотов области задаёт её владелец условием у поля (`value.count == capacity`) или строка `invariants`
   вида (`slots.count == PAYLOAD / SIZES[sizeClass]`).
4. Слот области хранит значение: `table[i].size = 16` пишет поле слота `i`. Индекс доказан в границах или
   проверяется при выполнении.
5. Строки `set`, `area` и `one` принято писать в начале. Порядок объявлений на разрешение имён не влияет: у одного
   `layout` одна общая область видимости.
6. Строка множества может нести условие в фигурных скобках, как поле: `set area Boxes: Box { … }`. Условие верно
   для каждого элемента множества, имя `value` в нём называет элемент (раздел 5.3).

**Пример.** В примере B `Blocks` объявлено как `set area`: участки не обязаны идти подряд, а каждый состоит из
непрерывных байтов. Область с известным числом слотов:

```efen
layout {
    area Classes: Class                       // 32 класса размеров подряд

    struct Sizes {
        var classes: own Classes.Area? { value == null || value.count == CLASSES }
    }
}
```

**Запрещено.** Элементы `set area` не индексируются. Набор раздаётся целиком циклом
[`for element in take region`](pointer.md#раздача-набора-for-element-in-take-region): цикл передаёт телу каждый
элемент по одному (раздел 6.6). Встроенного перебора всех элементов множества нет.

**Почему.** Тип указателя называет множество, поэтому по объявлениям видно, какие поля могут хранить указатель на
элемент. На этом держится поиск всех указателей перед уничтожением элемента.

Куда дальше: как одна область лежит в байтах другого элемента, говорит раздел 2.2.

<a id="вложенность"></a>

### 2.2 Вложенность

**Правило.** Область, объявленная полем структуры, занимает байты элемента этой структуры и существует, пока
элемент сохраняет этот вид.

**Пример.**

```efen
@align(BLOCK)
struct SlotBlock {
    Header                            // общее первое поле видов (раздел 2.3)
    @align(LINE) area slots: Slot     // слоты занимают байты элемента SlotBlock
    invariants {
        sizeOf(slots.Item) == SIZES[sizeClass]
        slots.count == PAYLOAD / SIZES[sizeClass]
    }
}

struct Slot {
    var next: Int = NONE
    var key: Int = SLOT_KEY
    area rest: Byte                   // хвост слота занимает байты слота
}
```

Память элемента `SlotBlock` выдана из множества `Blocks`. Область `slots` занимает его байты, область `rest`
занимает байты слота.

**Запрещено.** Вложенность объявляется только полем `area`. Два `layout` друг в друга не вкладываются.

**Почему.** Из вложенности следуют два правила времени жизни. Слот не существует дольше элемента, в котором
расположен (раздел 7.1). Родителя нельзя вернуть, пока его слот выдан и хранится вне его памяти (раздел 6.6).

Куда дальше: структуры элементов и их виды описывает раздел 2.3.

<a id="виды-и-приведение-as"></a>

### 2.3 Структуры из layout и виды элемента

**Правило.** Структура, объявленная в `layout`, описывает байты элемента или служит корнем коллекции. Все операции
над ней явные.

Дополнительные правила:

1. Коллекция (`Vector`, `List`, `Map`) объявляется обычным `struct` внутри `layout`. Программа хранит её значением
   в переменной или в поле класса: `var v = Vector<Int>()`.
2. У структуры из `layout` нет написанных программистом инициализатора и деструктора. Этим она отличается от
   класса: память выделяет и возвращает явный код (разделы 6.2 и 7.4).
3. Одни и те же байты в разное время описывают разные структуры. Структура, которой байты элемента описаны сейчас,
   называется видом элемента. Виды одного множества начинаются с общего первого поля (`Header`), и у каждого вида
   свои строки `invariants`.
4. Строка в `invariants` вида уточняет поле для этого вида. `next: SlotBlock?` значит, что цель имеет вид
   `SlotBlock`. `next: own FreeBlock?` значит, что в виде `FreeBlock` поле владеет, а в остальных видах только
   указывает.
5. Читать поля может код, которому их показывает видимость полей. Кто их пишет, определяет раздел 2.5.

**Пример.** Участок менеджера памяти бывает видами `PoolBlock`, `FreeBlock`, `SlotBlock`, `LargeBlock`. Список из
примера A хранится значением:

```efen
var list = List()                 // значение, как Int
```

**Запрещено.** Экземпляров у `layout` нет: `layout` не тип. Физические объявления (`set`, `area`, `one`, `struct`
с полями-областями) пишет только `layout` уровня модуля.

**Почему.** Структура описывает память на уровне байтов. Неявная операция над ней изменила бы память без строки
кода, которую можно проверить.

Куда дальше: обобщённые объявления описывает раздел 2.4.

### 2.4 Параметры

**Правило.** Параметры пишутся сразу после слова `layout`, и для каждого набора аргументов множества свои.

Дополнительные правила:

1. Параметры: типы и значения времени компиляции. `Items` при `T == Int` и `Items` при `T == String` составляют
   два разных множества. Экземпляров у `layout` с параметрами тоже нет.
2. Снаружи имена пишутся с аргументами: `Vector<Int>`, `Items<Int>.Item`. При `area Items: T` имя `Items.Item`
   называет слот, а результат `-> own T?` у `Vector<T>` отдаёт значение `T`.
3. Ограничение пишется у параметра, как у обобщённой структуры: `layout<T: Movable>`. Оно действует на все
   объявления этого `layout` и на стратегии его структур, повторять его у стратегии не нужно.
4. Аргумент типа становится частью `layout`. Значение `T` в слоте области принадлежит структуре, которая владеет
   этой областью, и проверяется теми же правилами, что её поля. Элемент или область, которыми значение `T`
   владеет, входят в цепочку владения этой структуры (раздел 3.3). Указатель в значении `T` подчиняется правилу
   чистоты (раздел 4.3), а значение `T` с источником в типе хранит заимствование (раздел 4.5).

**Пример.**

```efen
private layout<T: Movable> {
    area Items: T

    public struct Vector {
        private var items: own Items.Area? = null { value == null || value.count == capacity }
        private var capacity: Int = 0 { value >= 0 }
        public  var count: Int = 0 { value >= 0 && value <= capacity }
    }
}
```

**Запрещено.** Аргумент типа правил структуры не отменяет. Тип с аргументом проверяется там, где он написан
(раздел 8.7, проверка 7). `Vector<Vertices.Item>` как отдельное значение у внешнего кода хранил бы указатели за
пределы своей публичной структуры и вызывает ошибку (раздел 4.4, правило 6).

**Почему.** Множество с разными аргументами хранит элементы разного размера, поэтому указатели таких множеств
несовместимы. Значение `T` хранится в памяти структуры, переходит к другому владельцу и уничтожается вместе с ней.
Поэтому отдельных правил для него нет: действуют правила структуры.

Куда дальше: какой код пишет поля, определяет раздел 2.5.

### 2.5 Кто пишет поля

**Правило.** Поля структур из `layout` пишет только код, которому это разрешает модификатор видимости `layout`.

| Объявление | Поля пишут | Остальной код |
|---|---|---|
| `private layout { … }` | функции этого модуля | читает поля и вызывает функции |
| `layout { … }` (по умолчанию `internal`) | функции пакета | читает поля и вызывает функции |

Из правила следуют четыре определения:

1. **Код `layout`.** Функции, которым модификатор разрешает писать поля: модуль у `private layout`, пакет у
   `layout`.
2. **Внешний код.** Весь остальной код: другой пакет, а у `private layout` ещё и другие модули пакета.
3. **Публичная функция структуры.** Функция без `private`, которая пишет поля структуры из `layout`. Инварианты
   структуры верны на её входе и выходе (раздел 5.1).
4. **Вспомогательная функция.** Функция `private`, которая пишет поля. Она получает структуру, инвариант которой
   может быть временно нарушен. Что она сделала, сообщает её сводка. Сводка функции: то, что FLOW выводит из тела
   функции и записывает в её прототип.

Функции в `layout` не входят. `layout` содержит только описание памяти: множества, структуры, инварианты и строки
`public own` и `public lend` (раздел 3.5). Функции стоят рядом, в модуле или пакете.

**Пример.**

```efen
private fn setPrev(a: Items.Item, b: edit Items.Item) {      // вспомогательная функция
    b.prev = a
}

strategy for List {
    public mut fn removeFirst { … }                           // публичная функция структуры
}
```

**Запрещено.** Запись поля из внешнего кода вызывает ошибку.

**Почему.** FLOW проверяет каждую функцию, которая пишет поля, поэтому место функции для доказательства не важно.
Модификатор ограничивает количество кода, который автор обязан согласовать с инвариантами.

Куда дальше: кто владеет элементами, описывает раздел 3.

## 3. Владение

У каждого элемента в каждый момент один владелец, и он виден из объявлений. Раздел опирается на множества, поля и
границу между кодом `layout` и внешним кодом из раздела 2.

<a id="якорь-anchor"></a>

### 3.1 own и якорь

**Правило.** Владение бывает исключительным (`own`) и неисключительным (`anchor`, якорь). У значения ровно один
владелец, и он определяет, где значение уничтожается. Владение переносят операции `take` и `tie` (раздел 6.4),
якорь превращает в `own` приведение `as own` (раздел 6.5).

| | `own`: исключительное владение | `anchor`: якорь, неисключительное владение |
|---|---|---|
| смысл | единственный путь к значению | конец времени жизни значения; на значение указывают хранимые указатели |
| перенос | `take`; других указателей нет | `tie`; указатели множества на значение остаются действительными |
| уничтожение | безопасно всегда | после него ни один указатель не используется |
| факт на входе функции | «ничего не заимствовано» | такого факта нет |
| пример | `var pending: own Job?`; слот, выданный внешнему коду | узел дерева с `parent`; элемент `Block` в цепочке пула |

Дополнительные правила:

1. `own` равен якорю, на значение которого не указывает ни один указатель. Поэтому значение `own` записывается в
   поле `anchor` без отдельного шага. Обратно, от якоря к `own`, ведёт только `as own` (раздел 6.5).
2. Владеющее поле стоит в элементе того же множества (узел дерева владеет поддеревом), в слоте области другого
   множества (корзина хеш-таблицы владеет первой записью цепочки) или в корне коллекции (`List.head`).
3. Владение считается отдельно в каждом множестве. Область целиком принадлежит своему владельцу, а её слот может
   быть якорем элемента другого множества. Это два разных владения.
4. Пока из множества что-то выдано или его слоты хранят якоря существующих элементов, область нельзя уничтожить, а
   слот нельзя перезаписать целиком.

**Пример.** В примере A `Item.next` и `List.head` объявлены якорями, потому что на узел указывает `prev` соседа.

```efen
struct Node {
    var left: anchor Nodes.Item? = null      // владеет левым поддеревом
    var right: anchor Nodes.Item? = null
    var parent: Nodes.Item? = null           // невладеющий указатель
}
```

**Запрещено.** Два поля `anchor` на одно значение вызывают ошибку. `anchor` вместе с `own` на одно значение тоже
ошибка.

**Почему.** У значения одна точка уничтожения. Два вида владения дают FLOW разные проверки: под `own` указателей
нет и проверять нечего, под якорем перед уничтожением надо найти каждый указатель.

Куда дальше: владелец бывает не только полем, это описывает раздел 3.2.

### 3.2 Владелец вне поля

**Правило.** Владельцем бывают параметр, результат и локальная переменная с `own` или `anchor`. Функция с
параметром `anchor` отвечает за уничтожение значения.

**Пример.**

```efen
fn destroyBlock(pool: mut Pool, node: anchor Blocks.Item) {
    unlink(pool, node)                       // указатели на node в цепочках пула сняты
    mm.free(node as own Pointer)             // якорь стал own, память вернулась менеджеру памяти
}

fn pop(list: mut List) -> anchor Items.Item? {
    guard let first = tie list.head else { return null }
    list.head = tie first.next               // first.next теперь равен null
    if let h = list.head { h.prev = null } else { list.tail = null }
    list.length -= 1                         // инварианты List восстановлены: функция публичная
    return first                             // якорь переходит к вызывающему
}
```

Имя `mm.free` здесь и далее обозначает функцию внешнего менеджера памяти, которая принимает `own Pointer`.

До выхода функция с параметром `anchor` уничтожает значение или передаёт якорь дальше. Пока она этого не сделала,
указатели на значение у остального кода действительны.

**Запрещено.** Якорь переходит только между функциями кода `layout`. Локальный владелец неявно не уничтожается
(раздел 7.4).

**Почему.** Между снятием элемента с одного поля и записью в другое им кто-то владеет. Если бы владельцем считалось
только поле, такой промежуток был бы утечкой.

Куда дальше: цепочка владельцев элемента определяет его структуру, раздел 3.3.

### 3.3 Структура элемента

**Правило.** Структурой элемента называется корень цепочки его владения.

Цепочка идёт от элемента вверх по `anchor`, по `own`, по вложенности в область и по полю, которое хранит значение
структуры из `layout`. Она кончается на первом владельце вне значения `layout`: локальной переменной, параметре,
поле обычного типа, `one`.

<a id="публичная-структура"></a>

Публичной называется структура, которую внешний код хранит значением или получает по строке владения
(раздел 3.5): значение структуры из `layout` вместе со всеми элементами под ним, элемент `own S.Item`, выданный
слот. Внутренней структурой называется часть публичной: элемент вместе со всем, чем он владеет, или значение
структуры из `layout` в поле элемента. `one X` со всем, чем владеют его поля, составляет одну структуру всей
программы. Хранимые указатели под `one X` указывают внутрь этой структуры (раздел 4.3), и она никуда не переходит
(раздел 9.5).

**Пример.** Хеш-таблица вместе с областью корзин составляет одну структуру. Два `List` в полях одного объекта
составляют две структуры, и обе публичные. Вершина из примера C принадлежит цепочке от `Graph.first`, поэтому её
структурой служит граф. Сама вершина со своими рёбрами и вектором `neighbors` составляет внутреннюю структуру этого
графа.

**Запрещено.** Элемент не принадлежит двум структурам сразу. Он переходит из структуры в структуру только
владением, одной операцией (раздел 6.4).

**Почему.** По структуре элемента решается, какие указатели затрагивает операция. Цена определения: внутри одной
структуры её цепочки не различаются. Вызов, который освобождает элементы структуры, делает недействительным каждый
указатель в ней, который может быть равен освобождённому.

Куда дальше: кто владеет элементами множества, определяет раздел 3.4.

<a id="время-жизни-по-полю-и-по-функциям"></a>

### 3.4 Два способа владеть элементами множества

**Правило.** У каждого множества есть владелец, и он виден из объявлений: владеющее поле (`own` или `anchor` с типом
`S.Item`, у области `own S.Area`) либо строка владения, `public own S` или `public lend T.поле` (раздел 3.5). Способ
владения элементами множества один.

| Поле `own` или `anchor` с типом `S.Item` | Строка `public own S` | Способ | Кто владеет элементом `S` |
|---|---|---|---|
| есть | нет или есть | по полю | владеющее поле или функция кода `layout`; при строке `public own S` ещё и внешний код, получивший `own S.Item` |
| нет | есть | множество выдано целиком | только внешний код, через `own S.Item`; `layout` указателей на элемент не хранит |

Дополнительные правила:

1. Элемент под `own` у внешнего кода составляет отдельную публичную структуру. Её корень находится в переменной
   или параметре, которые хранят элемент. Элемент в слоте обобщённого контейнера (`Vector<own Nodes.Item>`)
   принадлежит структуре контейнера (раздел 2.4, правило 4).
2. Участок менеджера памяти с выданными слотами остаётся под владеющим полем. Им владеет цепочка якорей пула:
   `Pool.busy` в примере B, список участков класса размеров у менеджера памяти
   ([иерархия владения](pointer.md#иерархия-владения)). Получатель слота владеет слотом и участком не владеет
   (раздел 3.5). Участок считает выданные из него слоты в поле `used`. Пока `used > 0`, участок нельзя вернуть
   или освободить; после возврата последнего слота код вырезает его из цепочки и получает `own`
   (раздел 6.6, правило 5).
3. Коллекции, которой нужны оба способа для разных элементов, нужны два множества.
4. Область, объявленная полем структуры (раздел 2.2), принадлежит элементу, в байтах которого расположена.

**Пример.** В примере C оба множества относятся к способу «по полю». Вершинами владеет граф: цепочка идёт от
`Graph.first` по `Vertex.nextAll`. Рёбрами владеет вершина через `firstEdge`. Перед освобождением вершины её
владеющие поля равны `null`: функция сначала вырезает вершину из цепочки графа и освобождает рёбра.

**Запрещено.**

- Множество, у которого нет ни владеющего поля, ни строки владения, вызывает ошибку у своего объявления: у его
  элементов не было бы владельца.
- Потерянный владелец у множества «по полю» вызывает ошибку.
- У множества, выданного целиком, хранимое поле типа `S.Item` вызывает ошибку: `own` значит, что на элемент ничто
  не указывает.

**Почему.** Владелец даёт компилятору место, от которого он ищет указатели на элемент. При владении по полю каждый
хранимый указатель на элемент находится в той же публичной структуре, что и владелец (раздел 4.3). На элемент
множества, выданного целиком, не указывает ничто. Доказательство, что указателей на элемент не осталось, пишет
функция, которая его освобождает (раздел 6.5).

Куда дальше: что из этого получает внешний код, перечисляет раздел 3.5.

<a id="выдача-наружу"></a>
<a id="схема-владения"></a>

### 3.5 Что уходит наружу

**Правило.** Внешний код получает память `layout` пятью способами. Два из них передают владение частью памяти, и
их `layout` объявляет строкой владения: `public own S` или `public lend T.поле`, где `T` называет структуру, а
`поле` её поле-область.

| Что получает внешний код | Запись | Строка |
|---|---|---|
| значение структуры из `layout` (`List`, `Graph`, `Vector<Int>`) вместе со всеми элементами под ним | тип структуры | не нужна: владение значением выражает его тип |
| элемент целиком | `own S.Item` | `public own S` |
| слот или диапазон слотов области | `own Block.data.Item` | `public lend Block.data` |
| заимствование | результат с правом `read`, `edit` или `mut` | не нужна: владение не переходит |
| указатель без права записи | `S.Item` | не нужна |

Передача слота области во владение получателю называется выдачей слота. Её пишет операция `lend` (раздел 6.6).
Байты при выдаче остаются на месте, а `layout` запоминает только то, что слот занят.

Какой способ выбрать, зависит от того, что `layout` делает с памятью, пока она у внешнего кода:

| Что делает `layout` | Способ |
|---|---|
| не читает и не пишет содержимое | выдача слота: `lend block.slots[k]` |
| хранит в элементе свои поля (`next`, `prev`, счётчики), а отдаёт остальное | поля остаются у `layout`, выдаётся вложенная область: `lend block.data[0]` |
| продолжает читать или писать те же байты | заимствование: результат с правом |

Правила строк:

1. Строка `lend` называет область так же, как тип выданного слота: структура и её поле-область. `lend Block.data`
   относится к слотам типа `own Block.data.Item` и `own block.data.Item`, выданным по одному или диапазоном.
2. Тип выданного слота называет область, из которой слот выдан. Когда родитель передан параметром, тип пишется
   через него: `own block.data.Item`. В результате функции, где родитель вызывающему не виден, тип пишется через
   структуру: `own Block.data.Item`.
3. На одно множество и на одну область строка одна.
4. Видимость строки равна самой широкой видимости функций, которым она разрешает отдавать и принимать владение.
   `public own S` покрывает функции `public` и `internal`. `internal own S` покрывает только `internal`.
5. Строка шире модификатора `layout`: у `layout` с видимостью пакета имеет смысл только `public`, у
   `private layout` допустимы `internal` и `public`.
6. Строка `public` стоит в модуле `public module`, и структура множества (`Item`) тоже `public`
   ([видимость](../visibility.md)).
7. Между функциями кода `layout` владение элементом переходит без строки.

Где внешний код хранит полученное:

1. Элемент `own S.Item` и выданный слот внешний код хранит в локальной переменной, параметре и результате.
2. Дольше одного вызова значение хранится в обобщённом контейнере из `layout` (`Vector<own Nodes.Item>`), который
   стоит в локальной переменной или в поле класса. Деструктор класса вынимает элементы и возвращает каждый функции
   кода `layout`.
3. Множество, которое строка не называет, наружу владением не уходит. Его элементы внешний код читает и правит
   через структуру, которая ими владеет. Граф описывается структурой с цепочкой якорей (пример C), и наружу
   уходит значение этой структуры.

**Пример.** Пример B объявляет `public lend Block.data`. Его функции:

```efen
public fn acquire(pool: mut Pool) -> own Block.data.Item? {
    guard let block = takeFree(pool) else { return null }
    let data = lend block.data[0]            // выдан слот из block.data
    linkBusy(pool, tie block)                // участок привязан к Pool.busy и остаётся у пула
    return data
}

public fn release(pool: mut Pool, data: own Block.data.Item) {
    let block = blockOf(pool, data)          // участок, из которого выдан data: его находит код layout
    block.data[0] = take data                // слот вернулся туда, откуда выдан
}

public fn destroy(pool: own Pool) { … }      // освобождает участки пула
```

Внешний код получает только слот, участка у него нет. Поэтому `release` принимает пул и слот, а участок находит
вспомогательная функция `blockOf` по адресу слота (раздел 6.6, правило 9).

Элемент целиком:

```efen
private layout {
    set Nodes: Node
    public own Nodes                          // узел уходит наружу целиком: на него ничто не указывает

    public struct Node  { var next: own Nodes.Item? = null; public var value: Int }
    public struct Queue { var head: own Nodes.Item? = null }
}

public fn newNode(value: Int) -> own Nodes.Item { … }
public fn freeNode(node: own Nodes.Item) { … }
public fn push(queue: edit Queue, node: own Nodes.Item) { … }
public fn pop(queue: mut Queue) -> own Nodes.Item? { … }
public fn clear(queue: mut Queue) { … }
```

**Запрещено.**

- Якорь внешнему коду не выдаётся. `anchor S.Item` в сигнатуре функции, видимой внешнему коду, вызывает ошибку
  при любой строке. Строки `anchor` нет.
- Строка без слова видимости вызывает ошибку. Строка не шире модификатора `layout` тоже ошибка: ей нечего
  разрешать.
- Функция `public`, которая отдаёт `own S.Item` при строке `internal own S`, вызывает ошибку.
- Поле `own S.Item` или `own Block.data.Item` в классе или в обычной структуре вызывает ошибку.
- Сохраняемое замыкание `own S.Item` не захватывает: уничтожить его неявно нельзя. Корутина захватывает его
  владением, как параметр `own` (раздел 9.2).
- Приведения элемента во внешнем коде (`as Pointer`, `as own`, смена вида) вызывают ошибку.
- Выданный слот нельзя привести к `Pointer` и отдать менеджеру памяти: слот возвращается туда, откуда выдан.

**Почему.** Владение, которое получил внешний код, `layout` больше не видит. Строка делает такой выход частью
объявления, и компилятор сверяет с ней каждую функцию (раздел 8.7). Якорь не выдаётся, потому что якорь обещает
найти все указатели на значение, а внешний код этого доказать не может.

Куда дальше: указатели, которые владения не дают, описывает раздел 4.

<a id="структура-источник-чистота"></a>

## 4. Невладеющие указатели

Невладеющий указатель называет множество и имеет источник. Хранимый указатель указывает только внутрь своей
публичной структуры. Раздел опирается на структуру элемента и публичную структуру (3.3) и на способы владения (3.4).

<a id="ссылки"></a>

### 4.1 Запись и тип

**Правило.** Невладеющим указателем называется поле, переменная, параметр или результат типа `S.Item` без `own`
и `anchor`. Он ничем не владеет и по умолчанию только читает.

| Запись | Что это |
|---|---|
| `var prev: Items.Item?` | указатель на элемент множества `Items` |
| `var key: Keys.Item` | указатель на слот области `Keys` того же `layout` |
| `var next: Int` с концом `NONE` | слот своей области по индексу (цепочка свободных слотов) |

Дополнительные правила:

1. Тип указателя называет множество, а не экземпляр коллекции. Источник в типе поля `layout` не пишется: его
   выводит FLOW.
2. Указатель из одного множества в другое особо объявлять не нужно: FLOW видит каждую его запись.
3. Указатель может существовать дольше цели. После уничтожения цели он недействителен, и ошибку вызывает только
   его использование.
4. Параметр, которому нужен узел определённого графа, пишет источник обычным способом:
   `from: read<g> Nodes.Item`.

**Пример.** В примере A `Item.prev` и `List.tail` объявлены невладеющими указателями на элементы `Items`.

**Запрещено.**

- Указатель на обычное поле (`next`, `used`) не существует. Тип указателя есть только у того, что объявлено
  строкой `set` или `area`.
- Обратные указатели (`prev`, `parent`) разрешены только внутри `layout`.
- Запись вида `g.Nodes.Node`, которая называет экземпляр, не существует.

**Почему.** Один тип на множество позволяет переносить элемент между коллекциями без смены типа. К какой
коллекции элемент относится сейчас, говорит не тип, а владение.

Куда дальше: откуда указатель прочитан, определяет раздел 4.2.

<a id="источник-указателя"></a>

### 4.2 Источник ссылки

**Правило.** Источником ссылки или указателя на элемент служит структура элемента, из которой он прочитан. Источник
называет структуру целиком, а не путь внутри неё.

Дополнительные правила:

1. Указатель, прочитанный через любое поле элемента, имеет тот же источник, что и указатель на этот элемент.
2. Источник указателя в результате функции с телом выводится. У объявления без тела он пишется (раздел 8.5).

**Пример.**

```efen
let p = a.first()                   // Items.Item, источник: список a
let q = p.next                      // источник тот же: a
```

**Запрещено.** Указатель элемента не копируется из одной структуры в другую. Элемент меняет структуру только
владением (раздел 3.3).

**Почему.** По источнику решается, какие операции делают указатель недействительным: только те, что меняют
структуру его источника (раздел 7.1). Два списка общей памяти не объявляли, поэтому операция над `b` не затрагивает
указатель с источником `a`.

Куда дальше: куда хранимый указатель может указывать, ограничивает раздел 4.3.

### 4.3 Правило чистоты

**Правило.** Каждый хранимый невладеющий указатель указывает на элемент своей публичной структуры: той, в которую
входит поле с этим указателем.

Дополнительные правила:

1. Правило относится к указателям в элементах и в самом корне (`List.tail`).
2. Внутренняя структура может хранить указатель за свои пределы, но только внутрь своей публичной структуры
   (раздел 4.4). Указатель из одной публичной структуры в другую не хранится нигде.
3. Внутри тела функции правило может быть нарушено. Оно доказывается на каждом выходе публичной функции
   структуры, обычном и через исключение, и перед вызовом или приостановкой, которым нужны выполненные инварианты.
4. Элемент под локальным якорем составляет отдельную структуру: её корень находится в этой переменной.
5. Переход элемента между структурами тоже доказывает правило. В прежней структуре не остаётся указателя на
   уходящее поддерево, а в поддереве не остаётся указателя за его пределы.
6. Слоты с указателями FLOW находит по инварианту или обходом.
7. Под `one X` хранимый указатель указывает внутрь структуры этого `one` (раздел 3.3).
8. Правило относится к указателям без источника в типе. Значение с источником в типе (`read<g> Vertices.Item`,
   поле структуры с `Src: Origin`) хранит заимствование. Оно указывает в структуру своего источника и проверяется
   правилами заимствований (раздел 4.5).

**Пример.** В примере A `prev` каждого узла указывает на узел того же списка. В примере C `Edge.to` и `neighbors`
указывают на вершины того же графа: вершины двух графов не смешиваются.

**Запрещено.**

- Указатель за пределы публичной структуры вызывает ошибку. Компилятор показывает её у записи, которая создала
  такой указатель.
- Поле, которое не находит ни один инвариант и ни один обход, делает переход элемента ошибкой.

**Почему.** Благодаря правилу операция над одной публичной структурой не может оставить висячий указатель в другой.
Поэтому доказательство остаётся в пределах одной структуры и её кода, а публичная структура переходит к другому
владельцу целиком.

Куда дальше: какая структура чиста и как отделяется нечистая, определяет раздел 4.4.

### 4.4 Чистая структура

**Правило.** Структура чиста, если каждый её хранимый невладеющий указатель указывает внутрь неё. Публичная
структура чиста всегда: этого требует правило чистоты (4.3). Внутренняя структура может быть нечистой: её указатели
выходят за её пределы, но остаются внутри её публичной структуры.

Дополнительные правила:

1. Чистота внутренней структуры считается относительно её публичной структуры. Вершина из примера C нечиста, а
   все вершины графа вместе составляют чистый `Graph`.
2. Внешний код нечистую внутреннюю структуру от её публичной структуры не отделяет: он не получает её ни
   значением, ни владением и не передаёт в другой поток.
3. Отделяет её только код `layout`. Функция, которая выводит часть из публичной структуры, переписывает указатели
   и доказывает, что часть чиста: в прежней структуре не осталось указателя на неё, а в ней не осталось указателя
   за её пределы (раздел 4.3, правило 5).
4. Внешнему коду отделённая часть уходит только через функцию, которой это разрешает строка владения (раздел 8.7).
   У внешнего кода она становится отдельной публичной структурой.
5. Аргумент типа считается так же, как поле (раздел 2.4, правило 4). Значение `Vector<Vertices.Item>` в поле
   вершины хранит указатели внутрь графа и входит в граф внутренней структурой.
6. Внешний код хранит набор указателей на элементы публичной структуры заимствованием. Путь по графу, найденный
   обходом в ширину, записывается вектором с источником в типе элемента: `Vector<read<g> Vertices.Item>`. Такой
   вектор заимствует граф `g` с правом `read` (раздел 4.5). Вектор без источника, `Vector<Vertices.Item>`, у
   внешнего кода был бы публичной структурой с указателями за её пределы, и запись такого указателя вызывает
   ошибку.

**Пример.** `List` из примера A и `Graph` из примера C чисты. Узел `Item` из примера A нечист: `prev` указывает на
соседний узел того же списка. `Vertex` из примера C нечист: `neighbors` и `Edge.to` указывают на другие вершины
графа. `removeVertex` (раздел 6.5) отделяет вершину от графа: переписывает указатели на неё во всём графе и после
этого освобождает.

**Запрещено.**

- Функция, которая отдаёт внешнему коду часть публичной структуры и не доказала, что часть чиста, вызывает
  ошибку.
- В поле `shared` помещается только публичная структура, целиком
  ([пометка `shared`](../shared.md#пометка-shared)).

**Почему.** Публичная структура не зависит от памяти вне себя, поэтому её можно целиком передать другому владельцу,
в другой поток или закрыть одной блокировкой (раздел 9). Нечистая внутренняя структура зависит от соседних частей
своей публичной структуры. Отделённая без переписывания указателей, она хранила бы адреса памяти, которую меняет и
освобождает другой код. Все поля с такими указателями знает только код `layout`, поэтому отделяет её он.

Куда дальше: указатель на элемент вне `layout` описывает раздел 4.5.

<a id="указатели-вне-layout"></a>

### 4.5 Указатель вне layout

**Правило.** Вне `layout` указатель на элемент хранит только значение, которое заимствует: структура с параметром
источника `Src: Origin` или коллекция, в типе элемента которой записан источник (`Vector<read<g> Vertices.Item>`).

**Пример.**

```efen
struct ListCursor<Src: Origin> {
    var list: read<Src> List
    var current: read<Src> Items.Item? = null
}

let cursor = ListCursor<Src: list>(list: list)
```

Поле `current` хранит заимствование: курсор заимствует `list` с правом `read`, и указатель в поле имеет
источником `list`. Действует общее правило заимствований
([что делает ссылку недействительной](memory-rules.md#что-делает-ссылку-недействительной)):

1. После вызова `edit` у списка (вставка, перестановка узлов) курсор действителен.
2. Перед вызовом, который освобождает узлы или забирает их из списка, курсор, не используемый дальше,
   уничтожается. Курсор, используемый дальше, вызывает ошибку.
3. Исключение: функция, которая принимает сам курсор и переставляет его `current`.
4. Курсор по вершинам графа из примера C пишется так же. Структура
   `struct VertexCursor<Src: Origin> { var current: read<Src> Vertices.Item? }` создаётся как
   `VertexCursor<Src: graph>`, и источником её указателя служит граф. Вызов `removeVertex(graph, …)` меняет для
   такого курсора структуру источника.

Набор указателей, который внешний код собрал при обходе, тоже записывается заимствованием. Путь по графу из
примера C:

```efen
fn findPath(g: read Graph, from: read<g> Vertices.Item, to: read<g> Vertices.Item)
    -> Vector<read<g> Vertices.Item> { … }                // обход в ширину; источник указателей: g

var path = findPath(graph, from: a, to: b)                // a и b: вершины graph; вектор заимствует graph
print(path.count)
addVertex(graph, label: 7)                                // edit: path действителен
print(path.count)
path.release()                                            // область вектора возвращена
removeVertex(graph, a)                                    // меняет структуру источника: path больше не используется
```

Вектор `path` заимствует `graph`, как курсор. Вызов `edit` у графа его не затрагивает. Вызов, который освобождает
вершины, делает его недействительным целиком, и использование вектора после такого вызова вызывает ошибку. Значения
в слотах вектора проверяются теми же правилами, что поле с источником (раздел 2.4, правило 4).

Внутри `layout` курсор пишется проще. Структура `Cursor`, объявленная в том же `layout`, хранит
`var current: Items.Item?` без указателя на список: поле связано инвариантом или объявленным множеством, и FLOW
проверяет его как любой хранимый указатель.

Указатель на элемент из адреса без множества получается только через точку доверия:

```efen
let block = (address(m) & ~(BLOCK - 1)) as Blocks.Item       // элемент, которому принадлежит адрес из C
```

Маску в такой строке компилятор сверяет с `@align(BLOCK)` и вложенностью области и ничего не подставляет сам. Если
сверку доказать не удалось, перед строкой пишется `assume`. То, что адрес из C указывает в элемент множества,
компилятор принимает без доказательства. Поэтому строка остаётся точкой доверия и при доказанной сверке, и её
перечисляет `efen proofs`.

**Запрещено.**

- Поле типа `S.Item` без источника в структуре или классе вне `layout` вызывает ошибку, с любым правом.
- Приведение адреса, сверка которого не доказана, без `assume` вызывает ошибку.
- Хранимые указатели на узлы без заимствования всей коллекции (таблица LRU указывает на узлы его списка, индекс
  указывает на строки таблицы) существуют только внутри одного `layout`. Обе структуры объявляет один `layout`,
  либо производный `layout` добавляет свои множества и структуры с указателями в множества базового. Обычная
  структура вне `layout` таких указателей не хранит, и два независимых `layout` взаимных указателей не описывают.

**Почему.** Вне `layout` у хранимого указателя нет инварианта, по которому его можно найти перед уничтожением
цели. Заимствование с источником даёт компилятору ту же связь другим способом: по типу.

Куда дальше: как объявляется связь между указателями и владельцами, описывает раздел 5.

## 5. Инварианты

Инвариантом называется строка `invariants`. Она говорит, где хранятся указатели и что верно о полях, и доказывается
везде, где структуру видит другой код. Раздел опирается на роли функций (2.5) и на указатели (4).

### 5.1 Инвариант и места, где он верен

**Правило.** Инвариант структуры верен на входе публичной функции структуры без доказательства и доказывается в
каждом месте, где структуру видит другой код.

Такие места:

1. `return` публичной функции структуры, включая выход её параметра `mut`;
2. `throw`;
3. приостановка (`yield`, точка ожидания);
4. вызов кода, способного обратиться к изменяемой структуре: публичной функции или функции без тела, которой
   структура передана аргументом;
5. запись значения структуры в поле другого значения и публикация указателя на неё.

Дополнительные правила:

1. Между этими местами соседние шаги, которые не бросают исключений, могут временно нарушить инвариант.
2. От каких слотов зависит инвариант, FLOW выводит из прочитанных им слотов.
3. Вспомогательная функция получает структуру, инвариант которой может быть нарушен, и в сводке сообщает
   вызывающему, что она с инвариантом сделала.
4. Условие у поля (`var length: Int = 0 { value >= 0 }`) задаёт инвариант одного поля.
5. Несколько выражений в одних `invariants` соединяются логическим `&&`.

Исключение составляет курсор обхода. Курсор, который объявил, какие части источника он заимствует, может оставить
инвариант нарушенным на этих частях между шагами обхода. Тело цикла обратиться к этим частям мимо курсора не
может, а `exit` восстанавливает инвариант на любом выходе из цикла
([области доступа](../types/access-regions.md#итератор-как-структура)). Приостановка внутри такого обхода
допустима, только если ни одна корутина и ни один генератор, которые возобновятся позже, не хранят пути к
источнику.

**Пример.** Инвариант из примера A записан у поля, которое владеет следующим узлом:

```efen
invariants { next == null || next!.prev == self }
```

Функция удаления переставляет `next` и `prev` соседей, и компилятор проверяет, что инвариант снова выполняется.
Поэтому `prev` не может по-прежнему указывать на удалённый узел, а проверка обходится двумя соседями без обхода
списка.

**Запрещено.** Публичная функция структуры, которая пишет `prev` и не может доказать инвариант к своему выходу,
вызывает ошибку. Вспомогательной функции `setPrev` из раздела 2.5 это разрешено: инвариант восстановит и докажет
публичная функция, которая её вызвала.

**Почему.** Инвариант сообщает компилятору, где может храниться указатель на элемент. Перед уничтожением элемента
компилятор проверяет только эти места, а не всю память программы.

Куда дальше: форму «узлы, достижимые от головы» даёт цепочка, раздел 5.2.

### 5.2 Цепочка

**Правило.** Цепочка `A.chain(from: H, by: T.L, until: END)` называет узлы, достижимые от головы `H` по полю `L`
до конца `END`. Программист пишет инварианты о её узлах, а состав цепочки после каждой записи FLOW отслеживает
сам.

Дополнительные правила:

1. Ключевого слова под каждую структуру данных нет. Список, очередь, стек и дерево описываются одной формой
   цепочки и инвариантами.
2. Повторов в цепочке нет: каждый узел входит в неё ровно один раз.
3. Цепочка может связывать часть множества (свободные элементы, свободные слоты области). Тогда инвариант говорит,
   какие элементы в неё входят.
4. Над областью вида то же пишется номерами слотов ([сырая память](pointer.md#цепочка-свободных-мест)).
5. Коллекция, которой нужно обойти свои элементы, ведёт их цепочку через поле элемента и инвариант «каждый элемент
   входит в цепочку».
6. В инвариантах структуры запись `forall n in S` перебирает элементы `S`, которые принадлежат этой структуре
   (раздел 3.3). Функция опирается на такой инвариант только для структур, к которым у неё есть доступ: иначе один
   поток полагался бы на инвариант, который в другом потоке сейчас нарушен.

**Пример.** Список с хвостом:

```efen
public struct List {
    var head: anchor Items.Item? = null
    var tail: Items.Item? = null
    var length: Int = 0 { value >= 0 }

    invariants {
        let nodes = Items.chain(from: head, by: Item.next, until: null)
        forall n in Items: nodes.contains(n)
        tail == nodes.last
        length == nodes.count
    }
}
```

Строки читаются так: `nodes` называет узлы от `head` по `next` до `null`; каждый элемент `Items` этого списка
входит в цепочку; хвост равен последнему узлу; длина равна числу узлов. `(head == null) == (tail == null)` следует
из того, что `last` равен `null` только у цепочки без узлов.

У списка строка с `forall` следует из владения: списку принадлежат именно узлы под `head` по `next`. У `Graph` из
примера C она так же следует из цепочки от `first` по `nextAll`. Требованием строка становится у цепочки, которая
не владеет своими узлами.

Цепочка части множества. Ячейками `Cells` владеет цепочка от `all` по полю `Cell.nextAll`. Свободные ячейки связаны
второй цепочкой, по полю `Cell.next`, и она ими не владеет:

```efen
struct CellPool {
    var all: anchor Cells.Item? = null
    var firstFree: Cells.Item? = null
    invariants {
        let freeCells = Cells.chain(from: firstFree, by: Cell.next, until: null)
        forall c in Cells: (c.kind == FREE) == freeCells.contains(c)
    }
}
```

Цепочка свободных слотов области:

```efen
invariants {
    used == slots.taken.count
    frontier <= slots.count
    forall k in frontier ..< slots.count: !slots.taken.contains(k)
    let freeSlots = slots.chain(from: firstFreeSlot, by: Slot.next, until: NONE)
    forall k in freeSlots: 0 <= k && k < frontier && !slots.taken.contains(k)
}
```

**Запрещено.** Вспомогательных строк, которые описывают состав цепочки после операции, программист не пишет:
снятие головы, вставку и вырезание из середины FLOW учитывает по записям головы и поля-ссылки.

**Почему.** Встроенного перебора множества нет (раздел 2.1), и его заменяет цепочка: инвариант «каждый элемент
входит в цепочку» даёт и обход, и место, где хранится указатель на каждый элемент.

Куда дальше: условия на вид элемента описывает раздел 5.3. Подробно о цепочке:
[условия](../conditions.md#цепочка).

### 5.3 Условие вида

**Правило.** Условие множества может назвать вид элемента: `value is V` значит, что у элемента верны все
инварианты вида `V`.

Дополнительные правила:

1. Вид `V` встраивает тип элемента первым полем.
2. Имя элемента инвариантов вида не несёт. После проверки `box.kind == STACKED` они верны, и `box` можно передать
   как `Stack`.
3. Функция, которая меняет то, что читают инварианты `Stack` (поля, `taken`), доказывает их у элементов, которые
   меняет.

**Пример.**

```efen
set area Boxes: Box {
    value.kind == STACKED ==> value is Stack
}
```

**Запрещено.** `x is V` с видом справа допустимо только в условиях.

**Почему.** Вид элемента меняется при выполнении, а тип указателя вида не называет. Условие множества связывает
вид со значением поля, поэтому после проверки поля компилятор знает инварианты вида.

Куда дальше: границы того, что задают инварианты, называет раздел 5.4.

### 5.4 Чего инварианты не задают

**Правило.** Время жизни задают владение, вложенность и указатели. Инварианты о числах
(`used == slots.taken.count`), порядок элементов и представление в памяти на время жизни не влияют.

Инварианты о числах и порядке доказываются отдельно от времени жизни. Как эта работа делится между FLOW и Z3,
описывает [доказательство структур](layout-proofs.md#локальное-доказательство-инвариантов).

**Пример.** `length == nodes.count` говорит о числе, «ключ левого поддерева меньше ключа правого» говорит о
порядке. Ни одна из этих строк не сообщает, где хранится указатель, поэтому в доказательстве времени жизни они не
участвуют.

**Запрещено.** Недоказанный инвариант вызывает ошибку компиляции. Проверкой при выполнении заменяются только
граница индекса и пересечение аргументов (раздел 6.1).

**Почему.** Доказательство времени жизни не зависит от решателя: ему достаточно владения, вложенности и
указателей.

Куда дальше: операции, которые нарушают и восстанавливают инварианты, описывает раздел 6.

## 6. Изменение памяти

Каждая операция над памятью `layout` относится к одному из двух классов. Запись значения не переносит и не
уничтожает ни один элемент и требует `edit`. Изменение структуры уничтожает элемент, выводит его из структуры,
меняет его вид или лишает слот значения и требует `mut`. Раздел опирается на владение (3), источник (4.2) и
инварианты (5): к выходу публичной функции они восстановлены.

<a id="edit-и-mut-в-layout"></a>

### 6.1 edit и mut

**Правило.** `edit` гарантирует, что ни один существующий элемент или слот не перенесён и не уничтожен. `mut`
разрешает всё, что `edit`, и этой гарантии не даёт ([права](memory-rules.md#права)).

Права внутри `layout` те же, что в языке ([владение](../types/ownership.md)): `own` и `anchor` дают владение,
`edit` и `mut` заимствуют с правом записи, указатель без права записи только читает.

| Операция | Класс | Право |
|---|---|---|
| чтение поля | чтение | не нужно |
| запись поля-значения, которое ничем не владеет (`length`, `key`, `state`) | запись значения | `edit` |
| запись невладеющего указателя (`prev`, `parent`, `tail`) | запись значения | `edit` |
| запись в неинициализированный слот области вместе с полями-счётчиками из инварианта (`count`) | запись значения | `edit` |
| новый элемент во владеющее поле, равное `null` (`list.head = tie node`) | запись значения | `edit` |
| `tie` якоря, когда к выходу функции элемент снова принадлежит той же структуре (вставка в начало, вращение дерева, обращение списка) | запись значения | `edit` |
| элемент пришёл в структуру владением (`if let n = pop(a) { pushFirst(b, tie n) }`) | запись значения | `edit` на структуру, в которую он пришёл |
| `tie` якоря, после которого элемент ушёл из структуры: в результат, в другую структуру, в уничтожение | изменение структуры | `mut` на структуру, из которой он ушёл |
| `take` значения `own` из поля, `take` слота области | изменение структуры | `mut` |
| `lend` вместе с полями-счётчиками (`used`, `frontier`, `firstFree`) | изменение структуры | `mut` на родителя: слот ушёл из его структуры владением |
| возврат выданного слота (`block.slots[k] = take slot`) | изменение структуры | `mut` на родителя |
| `as own`, освобождение (`mm.free`) | изменение структуры | владение элементом: `as own` применяется к значению под `anchor` (раздел 6.5); `mut` на структуру, из которой элемент вырезан |
| смена вида `as` | изменение структуры | `mut` |
| перевыделение или замена области: сначала `let old = take table.buckets`, затем `table.buckets = take fresh` | изменение структуры | `mut` на владельца |

Дополнительные правила:

1. Право читается по итогу функции, а не по тексту. Функция с параметром `edit` к каждому своему выходу оставляет
   каждый элемент, который до неё принадлежал структуре этого параметра, в той же структуре, на том же адресе и в
   том же виде. Выход через исключение тоже выход.
2. Между `tie` из структуры и `tie` обратно функция `edit` не вызывает ничего, что может бросить исключение или
   приостановиться.
3. Право на элемент действует и на элементы, достижимые от него по указателям `layout`.
4. Достижимость даёт право писать, но в проверку непересечения не входит. Эта проверка одна и называется `apart`:
   пишущий аргумент (`edit`, `mut`, `out`, `own`) не пересекается ни с одним другим аргументом вызова
   ([два доступа сразу](memory-rules.md#два-доступа-сразу)). Два пишущих параметра одного множества сравниваются
   как два названных элемента. Пару, непересечение которой не доказано, программа сравнивает по адресам при
   вызове, и при совпадении вызов бросает сбой `OverlapError`. Такая пара помечается «проверено при выполнении».
5. Реализация вправе делать меньше, чем разрешает право. Таблица с открытой адресацией удаляет запись строкой
   `state = DELETED`. Для компилятора это запись значения, а право `mut` у её `remove` задаёт контракт коллекции.

**Пример.**

```efen
fn rotateRootLeft(tree: edit Tree) {          // edit: все узлы остались в дереве, ни один не перенесён
    guard let top = tie tree.root else { return }
    guard let pivot = tie top.right else { tree.root = tie top; return }
    top.right = tie pivot.left
    if let l = top.right { l.parent = top }
    top.parent = pivot
    pivot.parent = null
    pivot.left = tie top
    tree.root = tie pivot                     // к выходу каждый узел снова в tree
}
```

**Запрещено.**

- Операция без права, которое называет таблица, вызывает ошибку в своей строке (раздел 8.3).
- Функция, которой нужен случай «оба параметра называют один элемент», разбирает его отдельной веткой: передать
  один элемент в два пишущих параметра нельзя.

**Почему.** Гарантия `edit` позволяет вызывающему сохранить все ссылки и указатели в структуру. Поэтому вставка в
список, вращение дерева и `get` у LRU не делают недействительной ни одну ссылку.

Куда дальше: как память становится элементом, описывает раздел 6.2.

<a id="выделение-и-освобождение--переход-между-множествами"></a>

### 6.2 Создание элемента

**Правило.** Операции «создать элемент» нет. Память входит в множество преобразованием указателя и возвращается
тем же путём, каким пришла.

Путей два:

1. Из другого `layout`: менеджер памяти отдаёт `own Pointer`, и приведение `as` делает из него элемент.
2. Из другого множества этого же `layout`: участок, взятый у ОС, делится на элементы выдачей слота `lend` или
   раздачей `for element in take region` (раздел 6.6).

Правила приведения:

1. Приведение сохраняет право указателя: из `own Pointer` получается владеющий указатель на элемент. Приведение
   `Pointer` к виду поглощает `Pointer`.
2. Компилятор доказывает, что размер памяти не меньше вида и выравнивание не меньше `@align` вида.
3. Приведение с аргументами (`as Item(value: 0)`) записывает названные поля, как вызов `Item(…)`. Поле со
   значением по умолчанию (`var next: … = null`) получает его.
4. Поле не инициализировано, если оно не имеет значения по умолчанию, не записано в приведении и не записано
   кодом после приведения. «Не инициализировано» и `null` различаются: `null` считается значением.
5. Инициализатор `_` пишется только явно, у имени поля в строке приведения. На поле-числе (целом или с плавающей
   точкой) он оставляет прежние байты и при выполнении ничего не делает. На опциональном поле (`S.Item?`,
   `own …?`, `anchor …?`) он записывает `null`.
6. Запись во владеющее поле требует доказательства, что поле равно `null`.
7. Элемент, обязательные указатели которого связывают его с другим новым элементом (пара встречных полурёбер),
   вводится одной операцией вместе с ним.
8. Когда памяти нет, `mm.allocate` бросает `AllocationError`, и ничего не меняется ([аллокатор](allocator.md)).
   Имена `mm.allocate` и `mm.free` в примерах обозначают функции внешнего менеджера памяти.

Выделение и освобождение особыми операциями не считаются: память переходит из одного множества в другое, и только
направление делает переход выделением или освобождением. Память ОС тоже множество; его описывает контракт `System`
([системные вызовы](system.md#память-ос-как-множество)).

**Пример.**

```efen
fn newNode -> own Items.Item {
    return mm.allocate(…) as Item           // own Pointer стал own Items.Item
}

fn addVertex(graph: edit Graph, label: Int) -> Vertices.Item {
    let v = mm.allocate(…) as Vertex(label: label, neighbors: Vector<Vertices.Item>())
    v.nextAll = tie graph.first             // поле пусто по умолчанию; прежняя первая вершина теперь под v
    graph.first = tie v                     // вершина принадлежит графу
    return graph.first!                     // указатель без владения, источник: graph
}

// m1, m2, m3: три разных значения own Pointer; каждое приведение поглощает своё
let a = m1 as Item(value: 0)                    // value записан в приведении, next и prev равны null по умолчанию
let b = m2 as Item(value: _)                    // value сохраняет прежние байты, это написано явно

let c = m3 as Item                              // value не инициализирован
print(c.value)                                  // ошибка: value не инициализирован
c.value = 0
print(c.value)                                  // можно
```

**Запрещено.**

- Чтение неинициализированного поля вызывает ошибку компиляции.
- Перезапись владеющего поля со значением вызывает ошибку.
- `_` на неопциональном указателе, поле `own` или `anchor`, логическом поле, варианте и поле типа-параметра `T`
  вызывает ошибку: такое поле записывается явно. Записи «остальные поля оставить как есть» нет.
- Возврат нового элемента через результат без права (`-> Items.Item`), пока элемент не записан во владеющее поле,
  вызывает ошибку «владелец потерян».

**Почему.** У структуры из `layout` все операции явные. Память, которая вошла приведением, имеет известные размер и
происхождение, поэтому FLOW может проследить её до возврата. Обычный путь состоит в записи полей в приведении или
кодом после него. `_` нужен для поля, байты которого программе не важны или уже верны по устройству памяти.

Куда дальше: слоты области, которые ещё не получили значения, описывает раздел 6.3.

<a id="частичная-инициализация-и-очистка"></a>

### 6.3 Слоты области

**Правило.** Какие слоты области инициализированы, говорит инвариант владельца (`0 ..< count` у вектора), а не
сама область.

Дополнительные правила:

1. Указатель `Items.Area` не хранит ни числа занятых слотов, ни таблицы инициализации.
2. `take` слота области ничего не делает с памятью. Он объявляет, что значения по этому адресу больше нет, и
   требует `mut`. После `take` слот не инициализирован: запись в него его инициализирует.
3. `take` слота меняет структуру. Хранимые указатели `layout` на слот переписаны до `take`.
4. К выходу публичной функции неинициализированный слот по инварианту владельца не входит в занятые.
5. Переноса как отдельной операции нет. Значение переносит код: `take` из старого слота и запись в новый.
6. Код, который заполняет область по одному слоту, записывает поля владельца (`items`, `capacity`, `count = 0`) до
   первой операции, способной бросить исключение, и увеличивает `count` после каждой записи.
7. Если очередная запись бросила исключение, выполняется очистка: код на пути исключения, который порождает
   компилятор. Очистка освобождает ровно инициализированный префикс `0 ..< count`. Каждый занятый слот
   уничтожается один раз, неинициализированные остаются как есть, затем возвращается память области. Слот,
   значение которого код уже забрал `take`, в префикс не входит.
8. У коллекции из нескольких областей ([массив из участков](layout-examples/chunked-array.md)) каждый участок
   хранит свою область и свой `count`. Уничтожение сначала освобождает префикс каждого участка, затем каталог.

**Пример.**

```efen
strategy<T> for Vector<T> {
    public mut fn removeLast -> own T? {
        guard count > 0 else { return null }
        count -= 1
        return take items![count]        // слот вне 0 ..< count: не инициализирован
    }
}
```

**Запрещено.** Чтение неинициализированного слота вызывает ошибку. Использование ссылки или указателя на слот
после его `take` вызывает ошибку.

**Почему.** Область не хранит сведений о своих слотах, поэтому единственным источником этих сведений остаётся
инвариант. Очистку писать руками не обязательно, но инвариант «слоты вне `0 ..< count` не инициализированы»
доказан только вместе с ней.

Куда дальше: перенос владения существующим элементом описывает раздел 6.4.

### 6.4 Перенос владения

**Правило.** Якорь переносит `tie`, значение `own` переносит `take`. В каждый момент у значения один владелец.

Дополнительные правила:

1. При `tie` получатель привязывает значение к себе, а в прежнем слоте значения больше нет.
2. Внутри одной структуры указатели на значение при `tie` остаются действительными: меняется только точка
   уничтожения. При уходе в другую структуру действует раздел 7.1.
3. Во владеющее поле `own` значение записывается через `take`, в поле `anchor` через `tie`. Значение `own` через
   `tie` записывается в поле `anchor` и становится якорем: на него ещё ничто не указывает.
4. `take` берёт значение из опционального поля или из слота области.
5. Запись якоря `t.f = tie r` принимается, только если доказано, что `t` не входит в дерево `r`. Достаточно одного
   из трёх фактов: `r` только что отделён от своего владельца; `r` пришёл параметром без дочерних якорей; `t` сам
   только что взят как корень. Во всех трёх случаях `t != r`. Иначе FLOW выводит предусловие.
6. Элемент переходит между структурами одной операцией: `mut` для структуры, из которой он уходит, `edit` для
   структуры, в которую приходит.

**Пример.**

```efen
fn pushFirst(list: edit List, node: anchor Items.Item) requires node.next == null {
    node.next = tie list.head                // поле пусто по requires; прежний первый узел теперь под node.next
    if let second = node.next { second.prev = node }
    list.head = tie node                     // якорь записан в поле: узел принадлежит списку
    if list.tail == null { list.tail = list.head }
    list.length += 1
}
```

**Запрещено.**

- `take` слота под якорем вызывает ошибку.
- `tie` из поля, якоря которого у функции нет, вызывает ошибку. Из параметра `top: edit Nodes.Item` нельзя
  написать `pivot.left = tie top`: якорь `top` находится у вызывающего.
- Запись якоря без доказательства из правила 5 и без выведенного предусловия вызывает ошибку.
- `tie` и `take` невладеющего указателя владения не дают.

**Почему.** Цикл якорей не имеет владельца с момента замыкания, и в общем случае его отсутствие требует
достижимости, которую локально не доказать. Поэтому цикл строится из указателей под инвариантом, а не из якорей
([доказательство структур](layout-proofs.md#произвольный-граф-узел-освобождает-функция)).

Куда дальше: уничтожение элемента описывает раздел 6.5.

<a id="переход-к-владению-as-own"></a>

### 6.5 Удаление элемента

**Правило.** Память, на которую указывают несколько указателей, освобождается только после перехода к `own`:
`v as own Pointer`. К этой точке код уже нашёл все указатели на элемент и переписал или уничтожил их.

Дополнительные правила:

1. Компилятор проверяет это по инвариантам и объявлениям `layout` и выдаёт право `own`.
2. `as own` применяется к значению под `anchor`: параметру, локальной переменной или значению, которое функция
   забрала из поля. Невладеющий указатель владения не даёт, с любым правом.
3. К точке `as own` владеющие поля элемента (`own` и якоря) равны `null`: их освобождает явный код раньше.
4. Функция, которая владеет элементом через `own` или `anchor`, может забрать `take` его поля-значения перед
   освобождением (`let value = take node.value`). После этого элемент только освобождается.
5. Стирание вида `x as Pointer` даёт `own Pointer` той же памяти: вида больше нет, память существует и передаётся
   дальше. Размер, с которым память брали, FLOW помнит как факт о значении.

**Пример.**

```efen
fn removeVertex(graph: mut Graph, v: read<graph> Vertices.Item) {
    var w = graph.first
    while let x = w {                       // цепочка графа называет каждую его вершину
        x.neighbors.removeAll(where: { $0 == v })
        removeEdges(from: x, to: v)         // рёбра x с to == v вынуты из цепочки и освобождены
        w = x.nextAll
    }
    let cut = unlinkVertex(graph, v)        // anchor Vertices.Item: вершина вырезана из цепочки графа
    freeEdges(cut)                          // владеющее поле firstEdge равно null
    cut.neighbors.release()                 // область вектора возвращена
    mm.free(cut as own Pointer)             // доказано: указателей на вершину нет, владеющие поля равны null
}
```

Полноту обхода дают два факта. По инварианту `Graph` из примера C каждая вершина графа входит в цепочку от
`graph.first`. По правилу чистоты (раздел 4.3) указатель на вершину хранится только внутри того же графа. Запись
`read<graph>` у параметра `v` требует вершину именно этого графа (раздел 4.1, правило 4).

**Запрещено.**

- `as own` без доказательства вызывает ошибку.
- `as own` невладеющего указателя вызывает ошибку: указатель `mut` владения не даёт. Элемент, которым владеет
  внешний код, освобождает только функция, принявшая его как `own S.Item`.
- Приведения элемента (`as own`, `as Pointer`, смена вида) пишет только код `layout`.

**Почему.** Якорь превращается в исключительное владение только в `as own`. Поэтому доказательство того, что
указателей на элемент нет, требуется в одном месте: в функции, которая элемент освобождает.

Куда дальше: выдачу и возврат слотов описывает раздел 6.6.

<a id="выдача-и-возврат"></a>

### 6.6 Выдача и возврат слота

**Правило.** `lend` выдаёт слот во владение получателю, `take` в тот же слот возвращает его. Пока слот выдан,
родителя нельзя вернуть; исключение даёт правило 8.

Правила:

1. `lend block.slots[k]` выдаёт слот `k`: получатель владеет значением `own block.slots.Item`. Байты не
   переносятся, `k` входит в `slots.taken`.
2. `block.slots[k] = take slot` возвращает слот, `k` выходит из `slots.taken`.
3. Поля выданного слота через родителя не читаются и не пишутся: памятью владеет получатель.
4. На каждом выходе функции изменение `used` равно числу выдач минус число возвратов.
5. Первый `lend` понижает право на родителя с `own` до `mut`. Право `own` восстанавливается, когда вернулись все
   слоты (`used == 0`) или когда каждый невозвращённый слот подпадает под правило 8. Родитель с выданными слотами
   остаётся у своего владельца. Если к выходу функции слот не возвращён, родитель записан в цепочку якорей
   (`linkBusy(pool, tie block)` в разделе 3.5). Функция, которая вернула последний слот, вырезает родителя из
   цепочки и приводит якорь к `own` (раздел 6.5): `used == 0`, указатели на родителя в цепочке переписаны.
6. Диапазон выдаётся так же: `lend block.bytes[a ..< b]`, и возвращается тем же диапазоном.
7. Раздача `for element in take region` передаёт каждый элемент телу цикла, и тело передаёт его дальше.
8. Возврат родителя меняет структуру так же, как возврат элемента, только уходит вся его память. Слот, у
   которого все владельцы и указатели находятся в памяти самого родителя, уходит вместе с ним.
9. Родителя для возврата находит код. Основная форма: родителя передаёт вызывающий, и тип связывает его со слотом
   (`releaseSlot(block: mut SlotBlock, slot: own block.slots.Item)`). Внешний код родителя не получает, поэтому
   функция, которая принимает слот от него, вычисляет родителя по адресу слота (`release` в разделе 3.5). Такое
   вычисление пишется строкой кода с приведением адреса (раздел 4.5).

**Пример.**

```efen
fn reuse(block: own SlotBlock) {
    let a = lend block.slots[0]         // block теперь mut SlotBlock
    let b = lend block.slots[1]
    block.slots[0] = take a             // слот 0 вернулся
    freeBlock(take block)               // ошибка: слот 1 выдан, own SlotBlock не восстановлен
}
```

**Запрещено.**

- Выдать выданный слот нельзя. Вернуть слот можно только в свой слот.
- `break`, `continue` и `return` в теле раздачи вызывают ошибку. Элемент, оставленный телом, считается утечкой.
- Вернуть или освободить родителя, пока его слот выдан, нельзя. Исключение составляет слот из правила 8.

**Почему.** Выданный слот и родитель не пересекаются по байтам, поэтому получатель владеет слотом исключительно,
а `layout` продолжает работать со своими полями. Счёт `used` связывает их время жизни.

Куда дальше: смену вида и замену области описывает раздел 6.7. Подробно о выдаче:
[иерархия владения](pointer.md#иерархия-владения).

### 6.7 Смена вида и замена области

**Правило.** Смена вида пишется приведением `as` и требует `mut`. Замена области пишется записью нового значения
в поле владельца и требует `mut` на владельца.

**Пример.**

```efen
let spare = block as SlotBlock(slots: Slot(size: SIZES[index]))     // тот же участок памяти в другом виде

fn grow(table: mut Table) {
    var fresh = newBuckets(count: 2 * BUCKETS)
    // записи переходят из старых корзин в новые операцией tie
    freeBuckets(take table.buckets)          // все слоты старой области равны null
    table.buckets = take fresh
}
```

Правила инициализации полей нового вида те же, что при создании (раздел 6.2). После смены вида ни одно поле не
сохраняет значение неявно, в том числе поля общего первого поля видов (`Header`): каждое поле нового вида записано
в приведении, кодом после него или инициализатором `_`. Аргумент `slots: Slot(size: …)`
задаёт раскладку области: особый параметр `size` называет полный размер одного слота, а число слотов компилятор
выводит из размера памяти ([сырая память](pointer.md#поле-area-и-параметр-size)).

**Запрещено.** Освободить область, пока её слоты хранят якоря существующих элементов, нельзя (раздел 3.1).

**Почему.** Смена вида меняет то, какие поля есть у элемента и какие инварианты о нём верны. Указатель прежнего
вида после неё описывал бы память неверно.

Куда дальше: что каждая из этих операций делает с указателями, описывает раздел 7.

<a id="общий-принцип"></a>

## 7. Время жизни

Время жизни не объявляется: FLOW выводит его из кода. Указатель или ссылка становится недействительной в точке
изменения структуры, которое могло затронуть цель, а ошибку вызывает только использование после этой точки.
Раздел опирается на классы операций (6.1) и на источник (4.2).

Указатель допустим везде, где его разрешает раздел 4, если компилятор доказал два факта: из какого множества
указатель получен и что он не используется дольше, чем существует его цель. Все правила раздела следуют из этого
принципа. Аннотаций времени жизни в сигнатурах нет. Источник пишется только у объявления без тела
(раздел 8.5) и в типе значения, которое заимствует: у структуры с `Src: Origin` и в аргументе типа коллекции
(раздел 4.5).

<a id="диагностика-времени-жизни"></a>

Как FLOW строит доказательство и как печатает ошибки времени жизни, описывает
[алгоритм работы layout](layout-algorithm.md#вывод-времени-жизни).

### 7.1 Что делает указатель недействительным

**Правило.** Изменение структуры элемента X делает недействительными в любом коде каждый указатель и каждую ссылку
с источником в структуре X, которые могут быть равны X, тому, чем X владеет, или тому, что в нём расположено.
Запись значения не делает недействительным ничего.

| Изменение структуры | Что становится недействительным |
|---|---|
| `tie` якоря, после которого элемент ушёл из структуры | указатели и ссылки с источником в этой структуре на элемент и на всё, чем он владеет |
| `take` значения `own` из поля, `take` слота области | ссылки и указатели на прежнее содержимое, со строки `take` |
| `lend` | ссылки, срезы и курсоры, которые могут пересекаться с выданным слотом; остальные действительны |
| возврат выданного слота | каждый указатель на слот, в том числе хранимый в поле другой структуры |
| `as own`, освобождение | все указатели и ссылки на элемент |
| смена вида `as` | указатели прежнего вида, кроме переведённых на новый вид |
| перевыделение или замена области | ссылки и указатели внутрь прежней области |
| корень структуры ушёл из своего слота: `take` в существующий слот, `swap`, `replace`, передача `own`, возврат | все указатели и ссылки с этим источником |

Дополнительные правила:

1. `take` целой локальной переменной в новую переменную ничего не делает недействительным: источником становится
   новая переменная.
2. Слот не существует дольше элемента, в котором расположен. Элемент не существует дольше памяти, из которой
   взят.
3. Указатель на значение под якорем действителен не дольше якоря. В точке, где якорь уничтожает значение или
   отдаёт его из структуры, указатели недействительны. Хранимый указатель к выходу функции указывает на
   существующий элемент.
4. Указатель с источником «множество» становится недействительным при любой операции, которая освобождает или
   переносит элемент этого множества.
5. Операция, которая уничтожает значение, переносит его в другую память или меняет его вид, требует
   доказательства: каждый указатель на значение недействителен или переписан. При переносе и смене вида указатель
   остаётся действительным, если переведён на новое место или вид. `tie` внутри структуры такого доказательства не
   требует.
6. Недействительный указатель, который дальше не используется, операции не мешает. Значение, которое хранит такой
   указатель (курсор) и дальше не используется, уничтожается перед операцией.

**Пример.**

```efen
let p = a.first()                   // Items.Item, источник: a
freeAll(b)                          // освобождает узлы b; a и b общей памяти не объявляли
print(p.value)                      // допустимо
moveFirst(a, b)                     // mut для a: узел ушёл из a
print(p.value)                      // ошибка: p недействителен со строки moveFirst
```

```efen
fn shrink(table: mut Table, n: mut Nodes.Item) {
    let k = n.key
    table.keys = take smallerKeys()        // ошибка: k используется ниже и указывает в прежнюю область
    print(k)
}
```

**Запрещено.** Использование недействительного указателя или ссылки вызывает ошибку. Компилятор показывает её в
строке изменения структуры и отдельно показывает строку использования.

**Почему.** Источник делит указатели программы по структурам, поэтому изменение одной структуры не затрагивает
указатели в другую. Внутри структуры компилятор считает затронутым каждый указатель, который может быть равен
изменённому элементу.

Куда дальше: когда время жизни элемента начинается и кончается, описывает раздел 7.2.

### 7.2 Начало и конец времени жизни, смена источника

**Правило.** Время жизни элемента начинается, когда память входит в множество, и кончается, когда она из него
выходит. Переход элемента в другую структуру внутри `layout` время жизни не кончает.

Дополнительные правила:

1. Для вложенной области FLOW учитывает четыре операции: память родителя создана (приведение `Pointer` к виду,
   `System.map`); число слотов известно из условия владельца или вида; слот выдан (`lend`, раздача); слот вернулся
   через `own`.
2. Владение выданным слотом начинается при выдаче и кончается при возврате в свой слот. До выдачи и после
   возврата слот хранит значение в памяти родителя.
3. У множества верхнего уровня (`Blocks`) родителя нет. Время жизни его элемента начинается при приведении памяти
   к виду и кончается при стирании `as Pointer` или возврате памяти системе.
4. Элемент, перешедший владением в другую структуру, существует. Указатели множества на него внутри новой
   структуры допустимы. Указатели и ссылки с источником в прежней структуре становятся недействительными в любом
   коде.
5. Исключение из правила 4 одно. В функции, которая сама передала элемент, её локальный указатель получает
   источником новую структуру, если она известна в этой функции: по `tie` в её теле или по сводке вызова, которая
   называет параметр, в структуру которого элемент записан.
6. После вызова без тела и после вызова, сводка которого сообщает только о возможной передаче, указатель
   недействителен.
7. Получатель элемента не считает, что на элемент ничто не указывает: на него могут указывать другие указатели
   множества.

**Пример.**

```efen
fn move(pool: mut Pool, block: anchor Blocks.Item) {
    let name = block
    keep(pool, tie block)                  // block перешёл в pool; источник name теперь pool
    print(name.kind)                       // допустимо
}
```

**Запрещено.** Использование указателя на слот после его возврата вызывает ошибку. Компилятор показывает её в
строке возврата и отдельно показывает строку использования.

**Почему.** Элемент существует, пока его память принадлежит множеству, а кому он принадлежит внутри `layout`,
может меняться. Поэтому время жизни элемента и действительность указателя различаются: первое зависит от
множества, вторая от источника.

Куда дальше: те же правила для указателей у внешнего кода описывает раздел 7.3.

### 7.3 Пока память у внешнего кода

**Правило.** После каждого вызова FLOW доказывает, что указатель, оставшийся у внешнего кода, действителен.
Недоказанный случай вызывает ошибку.

Дополнительные правила:

1. Вызов, который пишет только другие байты, разрешён. Пример: перестановка `next` и `prev` в цепочке пула, пока
   область `data` элемента выдана.
2. Заимствование с правом (`mut`, `edit`, `read` в результате) подчиняется общему правилу
   ([что делает ссылку недействительной](memory-rules.md#что-делает-ссылку-недействительной)). После вызова `edit` оно
   действительно. Вызов, который меняет структуру источника, делает его недействительным.

**Пример.**

```efen
fn example(list: mut List) {
    let node = list.first()             // указатель на узел, источник: list
    list.insertFirst(value: 7)          // допустимо: edit, узлы на своих адресах
    print(node.value)
    list.removeFirst()                  // ошибка: узел освобождён, а node используется ниже
    print(node.value)
}
```

**Запрещено.** Вызов, сводка которого освобождает или переносит память под указателем, используемым дальше,
вызывает ошибку. Компилятор показывает её в строке вызова и отдельно показывает строку использования. Вернуть или
освободить родителя, пока его слот выдан, нельзя (раздел 6.6).

**Почему.** Внешний код не видит полей и не может сам проверить, что его указатель действителен. За него это
делает сводка вызванной функции.

Куда дальше: обязанность довести каждое владение до конца описывает раздел 7.4.

### 7.4 Ничего не теряется

**Правило.** Владение не кончается неявно: на каждом выходе, обычном и через исключение, каждое значение под
владельцем из `layout` записано в структуру, возвращено или освобождено явным кодом.

Локальный владелец:

1. Локальная переменная `anchor` или `own` с элементом `layout` неявно не уничтожается.
2. Вызов, который может бросить исключение, пока такая переменная хранит значение, вызывает ошибку, если на этом
   пути нет обработчика, который значение освобождает.
3. То же относится к элементу `own S.Item` и выданному слоту у внешнего кода: на каждом выходе значение
   возвращено функции кода `layout` или передано дальше.

Значение структуры из `layout`:

1. Память структуры освобождает явный код: публичная функция структуры (`v.release()`), сводка которой оставляет
   все владеющие поля равными `null`.
2. Публичная функция с получателем `own` (`own fn release`) забирает структуру целиком и освобождает в том числе
   поля `let`.
3. Выход из области видимости со структурой, у которой владеющее поле может быть не `null`, вызывает ошибку
   компиляции. Выход через исключение тоже выход. Правило выполняет `defer v.release()`: это явный код на каждом
   пути.
4. Структура, которая прямо или через поля содержит владеющее поле `layout`, не `ImplicitlyDestroyable`
   ([деструкторы](../disposable.md)).
5. Класс, который хранит такую структуру в поле, освобождает её в своём деструкторе. `shared struct` с таким
   полем освобождает его явной функцией под своей блокировкой.
6. Публичные функции, которые уничтожают элементы типа `T`, требуют `T conforms ImplicitlyDestroyable`. Для
   остальных `T` структура отдаёт элементы вызывающему, и он уничтожает их сам.

Жизненный цикл элемента. По телам функций FLOW строит путь каждого вида элемента: создание, повторная выдача,
смена вида (`SlotBlock`, затем `FreeBlock`, затем снова `SlotBlock`), возврат памяти. О каждом пути он доказывает
четыре свойства:

1. Каждый выданный слот и каждый элемент с владельцем на каждом пути возвращается или передаёт владельца дальше.
   Память берётся явно и возвращается явно: у глобального `layout` есть явная функция завершения.
2. Ничто не возвращается дважды и не возвращается в чужой слот.
3. Исходная память множества уничтожается, только когда ничто выданное из неё не хранится вне её. Области,
   вложенные в неё, уничтожаются вместе с ней ([уничтожение источника](layout-algorithm.md#что-описывает-layout)).
4. Элемент покидает множество только операциями раздела 6 или через точку доверия.

Сырая память линейна: владеющий корень передаёт её дальше на каждом выходе.

**Пример.**

```efen
fn countCopied(values: read Array<Int>) -> Int throws {
    var v = Vector<Int>()
    defer v.release()                   // явный код на каждом пути, включая исключение
    for x in values { v.append(x) }
    return v.count
}
```

**Запрещено.**

- Потерянный локальный владелец вызывает ошибку в конце функции.
- Класс без деструктора с полем, которое хранит структуру с владеющим полем `layout`, вызывает ошибку.
- Оставленная сырая память вызывает ошибку компиляции с кодом `flow.leak`.

**Почему.** У структуры из `layout` нет деструктора, поэтому неявного места, где память могла бы вернуться, не
существует. Ошибка на выходе из области видимости заменяет деструктор проверкой.

Куда дальше: как эти правила проходят через вызов функции, описывает раздел 8.

## 8. Функции

Вызывающий код проверяется по сводке функции, когда тело видно, и по написанному праву и типу, когда тела нет.
Раздел опирается на инварианты (5), на операции и время жизни (6 и 7), которые записаны в сводке, и на строки
`public own` и `public lend` (3.5).

### 8.1 Публичная функция структуры и вспомогательная функция

**Правило.** Право параметра проверяется у публичной функции структуры по её телу и по сводкам всех
вспомогательных функций, которые она вызывает.

Дополнительные правила:

1. Инварианты структуры верны на входе и выходе публичной функции структуры (раздел 5.1).
2. Вспомогательная функция работает по своей сводке. Сводка («узел ушёл из `list` в результат») передаётся
   вызывающему.
3. Функции `private` и функции, не видимые внешнему коду, строкам `public own` и `public lend` не подчиняются.
   Проверяется функция, через которую владение выходит наружу.

**Пример.** `removeFirst` объявлена `mut`, потому что вспомогательная функция, которую она вызывает, выводит узел
из списка. `pushFirst` объявлена `edit`: ни она, ни вызванные ею функции не выводят и не переносят узлы.

**Запрещено.** Публичная функция с параметром `edit`, сводка которой выводит элемент из структуры этого
параметра, вызывает ошибку.

**Почему.** Граница доказательства проходит по публичным функциям: внутри неё инварианты могут быть нарушены, на
ней они верны. Вспомогательные функции позволяют делить код, не размножая эту границу.

Куда дальше: откуда функция берёт право на элемент, описывает раздел 8.2.

### 8.2 Право на элемент

**Правило.** Указатель получает право значения, через которое он прочитан.

Дополнительные правила:

1. Указатель, прочитанный через параметр `mut`, передаётся в параметр `mut S.Item`; прочитанный через `edit`
   передаётся в `edit S.Item`.
2. У результата функции то право, которое в нём записано: `-> mut Items.Item?`.
3. Право на изменение структуры (уход элемента из структуры, освобождение) даёт право на саму структуру, которую
   называет источник указателя. Функция получает её параметром с этим правом.

**Пример.**

```efen
fn bump(list: edit List) {
    if let first = list.head { first.value += 1 }        // first прочитан через поле параметра edit: право edit
}
```

**Запрещено.** Указатель, полученный с `edit`, не даёт `mut`, даже если структура у функции есть.

**Почему.** Право на элемент выводится из права на его структуру. Если бы указатель нёс право сам, его можно было бы
вынести из функции и изменить структуру без её владельца.

Куда дальше: соответствие тела написанному праву описывает раздел 8.3.

### 8.3 Тело и право параметра

**Правило.** Тело функции не делает больше, чем разрешает право её параметра.

Дополнительные правила:

1. Что функция делает с `one X`, параметром не записывается: это её эффект. У функции с телом эффект выводится и
   попадает в прототип. У функции без тела он пишется как право на контекст: `in edit Registry` или
   `in mut Registry` ([контекст и эффекты](../context-and-effects.md)).
2. Вызывающий проверяется по сводке. Вызов, который через `one` меняет структуру памяти, на которую указывают
   ссылки и заимствования вызывающего, делает их недействительными, как любое изменение структуры.

**Пример.** Функция `register` записывает новый элемент через `one Registry`. Её прототип получает эффект
`in edit Registry`.

```efen
layout {
    set Names: Name
    one Registry

    struct Name     { var id: Int; var next: anchor Names.Item? = null }
    struct Registry { var first: anchor Names.Item? = null }      // один экземпляр: строка one Registry
}

fn register(id: Int) {
    let name = mm.allocate(…) as Name(id: id)
    name.next = tie Registry.first
    Registry.first = tie name                // запись через one: эффект in edit Registry
}
```

**Запрещено.** Запись или освобождение через параметр `S.Item` без права записи вызывает ошибку в строке записи.

**Почему.** Вызывающий полагается на право как на верхнюю границу того, что с его памятью сделают.

Куда дальше: что именно записано в сводке, перечисляет раздел 8.4.

<a id="как-flow-вычисляет-время-жизни"></a>

### 8.4 Сводка функции

**Правило.** FLOW по телу функции определяет, что она делает с каждым владением, и записывает это пометкой в
сводке. Руками пометки не пишут.

| Пометка | Что функция делает со значением | Указатели вызывающего на значение после вызова |
|---|---|---|
| уничтожает | освобождает его | недействительны |
| отдаёт | передаёт вызывающему результатом или параметром `out` | недействительны |
| оставляет | записывает в поле того же множества; пометка называет параметр, в структуру которого элемент записан | действительны |

Дополнительные правила:

1. Пометка бывает «на всех путях» и «на некоторых». Функция, которая уничтожает значение только на одном пути,
   помечается «может уничтожить», и указатели после её вызова недействительны.
2. Пометка относится не только к параметру `anchor`. Функция, которая через параметр `mut` уничтожает элемент,
   достижимый из него (`pool.head`), помечается так же, с путём от параметра.
3. Пометка «уничтожает» через параметр `mut` относится к элементам под полями структуры этого параметра
   (`clear(queue: mut Queue)`). Элемент, которым владеет внешний код, из неё недостижим: на элемент под `own`
   ничто не указывает.
4. Условия о памяти, которых программист не написал (что не инициализировано, что выдано, кто владеет), FLOW
   выводит из тела и добавляет в прототип. У `acquireSlot` это «результат выдан из `block.slots`»,
   у `releaseSlot` это «`slot` выдан из `block.slots`».
5. Программист вправе написать `requires` и `ensures` сам. FLOW добавляет только недостающее.
6. Источник указателя в результате функции с телом тоже выводится и записывается в сводку.

**Пример.** Сводки функций из раздела 3.2: `destroyBlock` уничтожает `node` на всех путях; `pop` отдаёт первый узел
`list` результатом. После `pop(list)` указатели вызывающего на первый узел недействительны.

**Запрещено.** Вызов уничтожающей или отдающей функции, после которого указатель на значение используется,
вызывает ошибку (раздел 7.1).

**Почему.** Сводка переносит время жизни через вызов: FLOW связывает с вызовом функции конец времени жизни всего,
что зависит от памяти, которую она уничтожает. Поэтому в сигнатурах нет аннотаций времени жизни.

Куда дальше: что заменяет сводку, когда тела нет, описывает раздел 8.5.

### 8.5 Функция без тела

**Правило.** У объявления без тела (интерфейс, контракт, функция C, тип функции) решают написанные право и тип.
Источник указателя в результате пишется явно.

Дополнительные правила:

1. `-> read<list> Items.Item?` называет источником структуру параметра `list`. Результат без записанного
   источника имеет источником множество.
2. Запись `read<list>` значит «где-то внутри `list`». Ссылку точно на один слот пишет `read<&path>`:
   `-> read<&doc.title> T` ([ссылка в результате](../types/ownership.md#ссылки-только-внутри-функции)).
3. Вызов без тела с параметром `mut S.Item` или с правом `mut` на структуру делает недействительными указатели с
   источником в структуре аргумента.
4. Указатель с источником «множество» становится недействительным при любом вызове `mut` без тела над значением
   того же `layout`.
5. Условия функции без тела выводятся из кода её [модели](../models.md#модель-model).

**Пример.**

```efen
// два объявления без тела
fn first(list: read List) -> read<list> Items.Item?      // источник результата записан
fn clear(list: mut List)                                 // после вызова указатели с источником list недействительны
```

**Запрещено.** Использование указателя с источником в структуре аргумента после вызова `mut` без тела вызывает
ошибку.

**Почему.** Без тела компилятор не знает, что функция делает, и принимает худший случай, который разрешает право.

Куда дальше: как функции структуры объявляются для вызова через точку, описывает раздел 8.6.

### 8.6 Стратегии

**Правило.** Функции структуры из `layout` даёт [стратегия](../strategies.md) из того же модуля или пакета:
`public mut fn append` в `strategy<T> for Vector<T>` вызывается как `v.append(1)`.

Дополнительные правила:

1. Функции стратегии объявлены вне структуры: собственных методов у структуры нет. Правила разделов 8.1–8.5
   действуют на них без изменений.
2. Ограничение параметра `layout` действует и на стратегию. Стратегия может добавить своё ограничение сверх него:
   `strategy<T: Copyable> for Vector<T>` даёт функции только для копируемых `T`.

**Пример.** `removeLast` в разделе 6.3 объявлена в `strategy<T> for Vector<T>`.

**Запрещено.** Стратегия из внешнего кода поля не пишет: она подчиняется разделу 2.5, как любая функция.

**Почему.** Структура остаётся описанием памяти, а запись через точку не требует, чтобы функции стояли внутри
объявления типа.

Куда дальше: проверку функций по строкам `public own` и `public lend` описывает раздел 8.7.

### 8.7 Проверка строк public own и public lend

**Правило.** FLOW проверяет каждую функцию кода `layout`, видимую внешнему коду: типы её сигнатуры сверяются со
строками, а действия с владением берутся из сводки.

Проверки:

1. **Позиции.** Владение элементом или слотом ищется в типе каждой позиции: параметр, параметр `out`, результат,
   а также внутри опционала, кортежа, варианта, аргумента обобщённого типа (`-> Vector<own Nodes.Item>`) и типа
   функции (`-> () -> own Nodes.Item?`). Позиция с `own S.Item` требует строки `own S`. Позиция со слотом требует
   строки `lend` его области. Видимость строки не уже видимости функции.
2. **Якорь.** `anchor S.Item` в любой позиции такой функции вызывает ошибку. Принятый `own S.Item` код `layout`
   записывает в поле `anchor` без отдельного шага, а обратно к выдаче ведёт только `as own`.
3. **Уничтожение.** Элемент, которым владеет внешний код, уничтожает только функция, принявшая его как
   `own S.Item`.
4. **Обратный путь.** У строки `видимость own S` есть функция той же видимости, сводка которой принимает
   `own S.Item` и уничтожает его или оставляет в структуре (`freeNode`, `push`). У строки
   `видимость lend Block.data` есть функция той же видимости, которая возвращает слот в его область (`release`).
5. **Лишняя строка.** Строка, по которой ни одна функция ничего не отдаёт, вызывает ошибку.
6. **Значение структуры.** У структуры с владеющим полем, видимой внешнему коду, есть функция той же видимости,
   которая оставляет все её владеющие поля равными `null`.
7. **Обобщённый код.** Тип с аргументом `own S.Item` (`Vector<own Nodes.Item>`) проверяется там, где он написан.
   Назвать его может код `layout` множества `S` и внешний код, которому видна строка `own S`. Тот же предел
   действует на любую запись типа `own S.Item` и типа слота во внешнем коде.

Печать. По запросу компилятор печатает для каждого `layout` пакета его множества, строки и функции выдачи и
возврата, вместе с точками доверия в `efen proofs` и в документации пакета. Печать выводится из объявлений и
сводок, поэтому всегда совпадает с кодом. Структуру, которую получает внешний код, печать помечает словом
«публичная» (раздел 3.3): такая структура чиста всегда. Внутреннюю структуру печать называет, когда она нечиста
(раздел 4.4), и сообщает, в какой публичной структуре она находится и на какое множество указывают её хранимые
указатели: «внутренняя в `Graph`; нечистая: указывает на `Vertices`».

Печать для `private layout` из раздела 3.5 и для примеров B и C:

```
private layout, модуль queue

Nodes       по полю, с выдачей: Queue.head, Node.next (own)
            public own: отдают newNode, pop; принимают push, freeNode
Queue       значение; освобождает clear(queue:); публичная

layout, пакет pool

Blocks      по полю: Pool.busy, Block.next (anchor); наружу не уходит
Block.data  public lend: выдаёт acquire; возвращает release
Pool        значение; освобождает destroy(pool:); публичная
Block       внутренняя в Pool; нечистая: указывает на Blocks

layout, пакет graph

Vertices    по полю: Graph.first, Vertex.nextAll (anchor); наружу не уходит
Edges       по полю: Vertex.firstEdge, Edge.next (anchor); наружу не уходит
Graph       значение; освобождает destroy(graph:); публичная
Vertex      внутренняя в Graph; нечистая: указывает на Vertices
Edge        внутренняя в Graph; нечистая: указывает на Vertices
```

Совместимость. Строки `public` и напечатанные функции выдачи и возврата входят в публичный интерфейс пакета.
Убрать строку, сузить её видимость или убрать последнюю функцию обратного пути значит сделать несовместимое
изменение. Добавить строку значит сделать совместимое.

**Пример.** В разделе 3.5 строке `public own Nodes` соответствуют `newNode` и `pop` (отдают), `push` и `freeNode`
(принимают). Без `freeNode` и `push` строка вызвала бы ошибку проверки 4.

**Запрещено.**

- Позиция без нужной строки вызывает ошибку у позиции. Сообщение называет недостающую строку.
- Строка без функции обратного пути вызывает ошибку у строки: внешний код получил бы владение, от которого не
  может избавиться.
- Структура без освобождающей функции вызывает ошибку у объявления структуры, а не в каждой точке, где внешний
  код выходит из области видимости.
- Расхождение объявленных строк с тем, что делает код, вызывает ошибку компиляции.

**Почему.** Строки и сводки вместе дают полный список того, что `layout` отдаёт и принимает. Автор пакета видит
этот список в одном месте, а пользователь пакета получает гарантию, что от любого полученного владения можно
избавиться.

Куда дальше: те же правила при нескольких потоках описывает раздел 9.

<a id="многопоточность"></a>

## 9. Потоки

В другой поток переходит только публичная структура, целиком, а делится между потоками она только под
блокировкой. Оба случая относятся к изменениям структуры из раздела 7.1, нового синтаксиса для них нет. Раздел
опирается на структуру элемента и публичную структуру (3.3), чистую структуру (4.4), места проверки инвариантов
(5.1) и печать из раздела 8.7.

Потоком здесь называется поток выполнения (корутина, тело `offload`, замыкание `shared layout`), а не поток ОС:
корутина может сменить поток ОС ([области доступа](../types/access-regions.md#корутины-spawn)).

<a id="структура-и-поток"></a>

### 9.1 Структура и поток

**Правило.** При проверке доступа из нескольких потоков структура считается одним целым: корень вместе с каждым
элементом под ним. Право, которым пользуются через любой указатель с этим источником, считается доступом ко всей
структуре с этим правом.

Дополнительные правила:

1. Указатель, ссылка или заимствование, действительные на любом участке работы многопоточной корутины, считаются
   чтением (`read`) своего источника на всё это время ([два доступа сразу](memory-rules.md#два-доступа-сразу)).
2. Указатель, источник которого находится в контексте потока, становится недействительным в каждой точке, где
   поток может смениться, как ссылка из контекста
   ([ссылка из контекста потока](../context-and-effects.md#ссылка-из-контекста-потока)).
3. В однопоточном контексте новых правил нет. В точке ожидания действуют сводки незавершённых корутин, как при
   вызове: их изменения структуры делают указатели недействительными, а инварианты выполнены до приостановки.
4. Доступ через указатель с источником «множество» (раздел 8.5) считается доступом к каждой структуре с элементами
   этого множества: которой из них принадлежит цель, неизвестно.
5. Функцию `@abi(c)` с телом вызывает C. Её тело проверяется как код однопоточного контекста: компилятор
   принимает, что C вызывает её в одном потоке. Вызов из другого потока происходит на стороне C, и компилятор его
   не видит, поэтому объявление такой функции служит точкой доверия (раздел 1). Функция, которую C вызывает из
   нескольких потоков, объявляет это, и её тело проверяется как код многопоточного контекста. Запись такого
   объявления не выбрана (раздел 10.1).

**Пример.**

```efen
fn work(list: own List) {
    defer list.release()                       // явный код на каждом пути (раздел 7.4)
    let p = list.first()                       // Items.Item, источник: list
    with makeTaskGroup() {
        let h = spawn { countItems(list) }     // корутина читает list, всю структуру
        print(p.value)                         // можно: чтение против чтения
        list.insertFirst(value: 7)             // ошибка: запись против чтения корутины
        await(take h)
    }
}
```

**Запрещено.**

- Корутина, которая пишет в источник или меняет его структуру, пока действует чужое чтение, вызывает ошибку
  компиляции. Компилятор показывает строку `spawn` и отдельно строку последующего использования.
- Корутина не захватывает невладеющий указатель `S.Item` ([замыкания](../closure.md#что-корутина-может-взять)).
  Она называет структуру и читает указатели внутри неё.

**Почему.** Указатель действителен только в потоке, у которого есть доступ к его источнику. Поэтому указатель,
действительный в двух потоках без блокировки, не возникает.

Куда дальше: передачу структуры другому потоку описывает раздел 9.2.

<a id="переход-между-потоками"></a>

### 9.2 Переход между потоками

**Правило.** Поток меняет только публичная структура, и только целиком, владением корня: `capture x = take x`,
параметр `own`, результат корутины, `take` в поле `shared` и из него.

Дополнительные правила:

1. Переход относится к изменению структуры «корень ушёл из своего слота» (раздел 7.1). В отправителе становится
   недействительным каждый указатель и каждая ссылка с этим источником.
2. Значение, которое хранит такой указатель и дальше не используется, уничтожается до перехода.
3. При переходе структура передаётся дальше, поэтому инварианты и правило чистоты доказываются в этой точке.
4. Выданный слот (`own block.data.Item`) составляет отдельное значение `own` и может находиться в другом потоке,
   чем родитель: их байты не пересекаются (раздел 6.6, правило 3). Вернуть слот можно только с `mut` на родителя.
   Пока слот выдан, родителя нельзя уничтожить.
5. Что внешний код может передать в другой поток, читается из печати раздела 8.7. Значение с пометкой
   «публичная» уходит целиком, владением. Элемент `own S.Item` уходит параметром `own`, результатом корутины или
   захватом `capture var n = take node`. Выданный слот уходит отдельно от родителя.
6. Корутина, которая захватила `own S.Item`, владеет им, как функция параметром `own`: на каждом выходе, обычном и
   через исключение, она возвращает элемент функции кода `layout` или передаёт его дальше (раздел 7.4).
7. Внутренняя структура отдельно от своей публичной в другой поток не переходит: вершину графа из примера C
   передаёт только `Graph` целиком. Отделяет её код `layout` по правилам раздела 4.4.

**Пример.**

```efen
fn work(list: own List) {
    let p = list.first()
    with makeTaskGroup() {
        background { capture var l = take list; l.removeFirst(); l.release() }   // корень ушёл из слота
        print(p.value)                         // ошибка: p недействителен после take list
    }
}
```

**Запрещено.** Значение с указателем в переданную структуру, используемое после перехода, вызывает ошибку.

**Почему.** Вместе с корнем уходят все элементы под ним. Публичная структура чиста, поэтому ни один её указатель
не указывает на память, которая осталась у отправителя, а правило чистоты гарантирует, что в отправителе не
осталось хранимых указателей на ушедшие элементы.

Куда дальше: общий доступ нескольких потоков описывает раздел 9.3.

<a id="структура-под-блокировкой"></a>

### 9.3 Структура под блокировкой

**Правило.** Отпускание блокировки меняет структуру каждого охраняемого поля: каждый указатель,
ссылка и заимствование с источником в таком поле становится недействительным на `exit`.

Дополнительные правила:

1. Под охраной поля проекция даёт на корень `mut`, если поле `var`, и `read`, если `let`.
2. Пока блокировка захвачена, `edit` и `mut` работают, как в одном потоке.
3. Значение, которое хранит указатель, ссылку или заимствование в охраняемое поле и дальше не используется,
   уничтожается до `exit`, даже если это переменная верхнего уровня тела `with`
   ([проекция](../shared.md#доступ-через-projection)).
4. Инварианты и правило чистоты охраняемых структур принимаются верными после захвата и доказываются при каждом
   отпускании: на обычном выходе, при исключении и в конце каждого вызова замыкания `waitFor`, вместе с
   `invariants` самой общей структуры ([инвариант](../shared.md#инвариант)).
5. Элемент, взятый под локальным `anchor`, может выйти за пределы блокировки: правило чистоты на `exit`
   доказывает, что внутри на него ничто не указывает. Особого вида якоря для этого не нужно.
6. Поток, который ждёт завершения другого (`await`, конец `with`), опирается на обычный конец доступов корутины.

**Пример.**

```efen
shared struct Jobs {
    var mutex: Mutex
    var queue: List                            // публичная структура
}
projection JobsEditor for Jobs { var queue; invariants { mutex is Mutex.Held } }

fn peek(jobs: mut Jobs) -> Int requires jobs.mutex is Mutex.Free {
    var node: Items.Item? = null
    with jobs.mutex {
        let editor = jobs as JobsEditor
        node = editor.queue.first()            // источник: jobs.queue
        editor.queue.insertFirst(value: 7)     // запись значения: node действителен
    }                                          // exit: node недействителен
    return node!.value                         // ошибка: использован после отпускания блокировки
}
```

**Запрещено.** В поле `shared`-структуры помещают только публичную структуру, целиком. Указатель в охраняемое
поле, используемый после `exit`, вызывает ошибку.

**Почему.** После отпускания блокировки структуру может изменить другой поток, и компилятор этого изменения не
видит. Поэтому он считает худший случай: структура изменена целиком.

Куда дальше: деление одной структуры между потоками без блокировки описывает раздел 9.4.

<a id="роли"></a>

### 9.4 Роли

**Правило.** Роль делит между потоками целые поля или диапазоны индексов области, у которой тип слота и всё, чем
слот владеет, не хранят невладеющего `S.Item` ([роли](../shared.md#роли)).

**Пример.** Кольцевой буфер [`Ring`](../shared.md#роли) делит поле `slots` между двумя ролями: писатель получает
свободные ячейки, читатель получает заполненные. Как проекция называет диапазон области, которая стоит в поле
структуры из `layout`, не решено (раздел 10.1).

**Запрещено.** Элементы `set` роль не делит: такая структура целиком принадлежит одной роли.

**Почему.** Слоты области без указателей не зависят друг от друга. Элементы множества связаны указателями, и
граница роли прошла бы через них.

Куда дальше: структуру, которая принадлежит всей программе, описывает раздел 9.5.

<a id="one-и-поток"></a>

### 9.5 one и поток

**Правило.** `one X` вместе со всем, чем владеют его поля, составляет одну структуру, которая принадлежит всей
программе. При проверке потоков она считается одним целым и в другой поток не переходит.

Дополнительные правила:

1. Эффект `in read|edit|mut X` считается доступом к этому целому с названным правом. Так же считается доступ через
   указатель с источником в `X`. Эти доступы проверяются по всей программе.
2. У вызова без тела эффект на `one X` записан в объявлении (раздел 8.3).

**Пример.** `Registry` и `register` объявлены в разделе 8.3. Функция `isRegistered` читает цепочку от
`Registry.first`, её эффект `in read Registry`.

```efen
with makeTaskGroup() {
    background { register(id: 2) }             // эффект in edit Registry
    print(isRegistered(id: 1))                 // ошибка: чтение Registry против записи корутины
}
```

**Запрещено.** `one` под блокировку не помещают и в другой поток не передают. Общее состояние под блокировкой
записывают публичной структурой в поле `shared struct`: `Graph` из примера C помещается туда целиком.

**Почему.** `one X` не хранится значением ни в одном слоте, поэтому его нельзя передать владением или поставить в
поле `shared`. Его память считается общей памятью всех потоков.

Куда дальше: что остаётся за пределами этих правил, перечисляет раздел 9.6.

<a id="чего-layout-не-описывает"></a>

### 9.6 За пределами layout

**Правило.** Три вида памяти `layout` не описывает. Их дают примитивы стандартной библиотеки и отдельные решения.

1. Структуры без блокировок, где слоты делят больше двух потоков. Это примитивы стандартной библиотеки, доказанные
   один раз. Указатель, действительный в нескольких потоках без блокировки, требует механизма времени выполнения,
   который откладывает освобождение цели, пока указатель используется. Доказательство FLOW такой механизм не
   заменяет.
2. Освобождение памяти менеджера памяти из другого потока. Слот, выданный кучей потока A и освобождаемый в потоке
   B, возвращается в кучу потока A. Как это делается, не решено ([сырая память](pointer.md#не-решено)). Выданный
   слот в любом потоке доказывает, что его родитель существует (раздел 6.6).
3. Объекты со счётчиком (`conforms ArcClass`). FLOW их не анализирует: для них действует отдельный алгоритм
   ([управление памятью](../classes.md#управление-памятью)). `shared class` со счётчиком ждёт решения об атомарном
   счётчике.

**Запрещено.** Указатель, действительный в двух потоках без блокировки, обычным `layout` не выражается
(раздел 9.1).

**Почему.** Доказательство FLOW опирается на то, что в каждый момент у структуры один поток с правом записи. Там,
где это неверно, нужна проверка при выполнении.

Куда дальше: нерешённые вопросы перечисляет раздел 10.

<a id="открытые-вопросы"></a>

## 10. Что не решено

### 10.1 Нерешённые вопросы

1. Исходная память множества как отдельное понятие в записи `layout`.
2. Область со слотами разного размера. Она нужна, запись для неё не разработана. Размер слота уже задаётся при
   приведении: структура, которая кончается полем `area`, получает его параметром `size`
   ([сырая память](pointer.md#поле-area-и-параметр-size)), и все слоты одной области имеют этот размер. Не хватает
   слотов разного размера внутри одной области.
3. Инвариант с головой цепочки, которая зависит от переменной: «запись входит в цепочку своей корзины»
   (`forall e in entries: entries.chain(from: buckets[e.home].head, …).contains(e)`). Способ доказательства
   известен ([доказательство структур](layout-proofs.md#локальное-доказательство-инвариантов)), но FLOW сегодня
   отслеживает цепочку только с одной постоянной головой.
4. Производный `layout`. Он добавляет свои множества и структуры с указателями в множества базового `layout`
   (раздел 4.5). Не решены его запись и два вопроса о производном `layout` из другого пакета: пишет ли он поля
   базового (круг кода `layout`, раздел 2.5) и как меняется состав публичного интерфейса (раздел 8.7). До решения
   структуры со взаимными указателями объявляет один `layout`.
5. Роль над диапазоном области, которая стоит в поле структуры из `layout`: как проекция называет такую область
   (раздел 9.4).
6. Запись, которой функция `@abi(c)` с телом объявляет, что C вызывает её из нескольких потоков (раздел 9.1,
   правило 5).

Слабых указателей и поколений элементов в `layout` нет: они относятся только к объектам со счётчиком (раздел 9.6).
Операции «перенести все элементы множества» тоже нет: память переносит обычная функция, и её действие
доказывается, как у любой другой (раздел 6.3, правило 5).

Доказательства надёжности у правил нет. Что ещё находится вне правил, перечисляет
[таблица правил](memory-rules.md#чего-таблица-не-обещает). Проверочные структуры для этих вопросов:
[layout-examples/checks](layout-examples/checks/README.md).

<a id="состояние-в-компиляторе"></a>

### 10.2 Что компилятор проверяет сегодня

Amber ещё не читает синтаксис этой редакции: модификатор видимости у `layout` и запрет записи из другого пакета,
`anchor`, переход `as own`, тип слота через структуру (`own Block.data.Item`), строки `public own S` и
`public lend T.поле` и их печать.

На 2026-11-08 Amber проверяет:

- `area`, `set area` и структуру с полем `area` и `invariants`; указатель на элемент `X.Item`;
- выдачу и возврат слота: `lend`, `take` в свой слот, `slots.taken`, счёт `used` на выходе, раздачу
  `for element in take region`;
- приведение `as`, `@align`, `Pointer`;
- строки `invariants`: поле против константы, число слотов, `sizeOf` и таблицу размеров,
  `used == x.taken.count`, одну цепочку свободных слотов;
- то, что указатель, полученный приведением, становится недействительным при вызове, который может сменить вид.

Amber ещё не проверяет:

- запись `take` элемента под владением в поле, которое только указывает (`head = take entry` теряет владельца,
  ошибка не выдаётся);
- результат функции с правом `own` на элемент множества (`-> own Nodes.Item?`), и поэтому списки, деревья и
  хеш-таблицы с узлами, которые передаются владением
  ([проверочные структуры](layout-examples/checks/README.md));
- `one`, `set X` с инвариантами над множеством (`forall n in Items: …`), `layout<T>` с параметрами и структуры со
  стратегиями;
- недействительность хранимых указателей после возврата элемента, жизненный цикл элемента и его четыре свойства
  (раздел 7.4), выведенные условия о выданных слотах в прототипе;
- поле `S.Item` в обычной структуре вне `layout`: Amber принимает его без ошибки, это расхождение с разделом 4.5;
- возврат родителя, у которого все указатели на выданные слоты находятся в его же памяти (раздел 6.6, правило 8):
  Amber требует вернуть все слоты;
- очистку инициализированного префикса при исключении (раздел 6.3): она не порождается;
- правила раздела 9 и `layout` в теле класса с кодом `model`.

Инварианты цепочек целиком доказывает Z3 в тестовом режиме. Обычная сборка видит из цепочки только правило
свободных слотов. Локальное доказательство инвариантов (раздел 5.4) проверено на бумаге и в компиляторе не
реализовано.
