# Контракты аллокатора памяти

Память в Efen выдают контракты двух уровней из слоя `memory` ([слой `memory`](../runtime/memory.md)).
`memory::Allocator` — общий контракт над сырой памятью: его вызывает низкоуровневый код, который сам берёт и
возвращает память (коллекция, строка, менеджер памяти). Над ним стоит `memory::AllocatorType<Type>` — стратегия,
которая даёт память значениям одного типа: объекту класса и элементу множества `layout`. Её вызывает компилятор, когда
создаёт значение формой с полями (`Box(value: 10)`, `Node<T>(value: take value)`), и когда значение кончается. У
типа со стандартным аллокатором программа выделение и освобождение не пишет; тип с нестандартным аллокатором может
потребовать ручного выделения ([ручное выделение](#ручное-выделение)). Области `Area<T>` аллокатора нет
([область не берёт памяти](#область-не-берёт-памяти)).

## Общий контракт `memory::Allocator`

```efen
contract Allocator {
    // Выделяет блок не меньше size байт с выравниванием не меньше aligned; без памяти бросает AllocationError.
    static fn allocate(size: Int, aligned: Int = alignOf(Int)) -> own Pointer throws only AllocationError
        ensures result.size >= size && result.alignment >= aligned

    // То же, но без памяти возвращает null.
    static fn tryAllocate(size: Int, aligned: Int = alignOf(Int)) -> own Pointer? nofail
        ensures result == null || (result.size >= size && result.alignment >= aligned)

    // Расширяет блок на месте или переносит в новый и возвращает его; без памяти бросает AllocationError,
    // старый блок остаётся у вызывающего.
    static fn reallocate(ptr: own Pointer, size: Int) -> own Pointer throws only AllocationError

    // То же, но без памяти возвращает null, старый блок остаётся у вызывающего.
    static fn tryReallocate(ptr: own Pointer?, size: Int) -> own Pointer? nofail
        ensures taken(ptr) == (result != null)

    // Возвращает блок; его размер реализация находит сама.
    static fn deallocate(ptr: own Pointer) nofail
}
```

Функции статические: значения аллокатора нет, реализацию называет тип, а не объект. Размер — один тип, `Int`.
Выравнивание по умолчанию — `alignOf(Int)`, выравнивание машинного слова. `deallocate` размера не принимает: размер
блока реализация находит сама, как `mm` находит его по адресу ([менеджер памяти `mm`](#менеджер-памяти-mm)).

При неудаче ничего не меняется: блок, переданный `reallocate` или `tryReallocate`, остаётся у вызывающего.
`tryAllocate` и `tryReallocate` служат коду, которому вместо исключения нужен `null`: формы создания, которая даёт
`null`, нет ([создание элемента](layout/operations.md#62-создание-элемента), правило 2). `Pointer` не обобщённый
([сырая память](pointer.md)): аллокатор выдаёт байты, вид им даёт приведение `as`.

Для правил областей доступа ([рост без перемещения](../types/access-regions.md#рост-без-перемещения)) у операций одно
событие на все реализации: `allocate` — создание (новая память, старая не двигается), `reallocate` — создание,
перенос и уничтожение (может переместить), `deallocate` — уничтожение. На Linux с overcommit нехватку физической
памяти после успешного выделения видит ОС, а не программа.

## Рост на месте: `memory::ExtendableAllocator`

Рост блока без переноса — отдельный небольшой контракт рядом с общим.

```efen
contract ExtendableAllocator : Allocator {
    // Расширяет блок на месте; никогда не перемещает; если на месте нельзя, бросает AllocationError.
    static fn extend(ptr: mut Pointer, size: Int) throws only AllocationError

    // То же, но если на месте нельзя, возвращает false.
    static fn tryExtend(ptr: mut Pointer, size: Int) -> Bool nofail
}
```

`extend` — создание: новая память, старая не двигается. `extend` расширяет блок сырой памяти на месте. Области
`layout` это не касается: формы роста области на месте нет. Коллекция растёт заменой области, и после роста ссылки и
указатели внутрь прежней области недействительны, каким бы методом аллокатора рост ни был выполнен
([смена вида и замена области](layout/operations.md#67-смена-вида-и-замена-области)).

Контракт один, реализации на платформах разные, и различаются они только тем, когда операция отказывает:

- Linux с overcommit: выделение почти всегда успешно, нехватку физической памяти видит ОС при первой
  записи и завершает процесс; программа об этом не узнаёт.
- Windows: выделение и `extend` внутри резерва (`MEM_COMMIT`) честно отказывают при нехватке памяти.
- wasm32 и платформы без MMU: независимого резерва адресов нет, `extend` удаётся только у последнего
  блока линейной памяти, поэтому `tryExtend` чаще возвращает `false`, а коллекции с резервом
  выделяют всю ёмкость сразу или объявляют предел.

## Аллокатор одного типа `memory::AllocatorType<Type>`

`AllocatorType<Type>` — стратегия, которая даёт память значениям одного типа. Это отдельный контракт со своим
списком функций и строкой `for Type`, а не наследник `Allocator`: типизированная стратегия обещает размеры только
своего типа (пул слотов одного типа), поэтому там, где ждут общий `Allocator`, она не стоит. Общий уровень служит
типизированному через стратегию по умолчанию `Heap<Type>`, которая передаёт каждую операцию общему контракту `mm`
с выравниванием `alignOf(Type)`.

```efen
contract AllocatorType<Type: Allocatable>
{
    for Type

    // Выделяет блок не меньше size байт с выравниванием alignOf(Type); без памяти бросает AllocationError.
    static fn allocate(size: Int) -> own Pointer throws only AllocationError
        requires Type is FixedSize ==> size == sizeOf(Type)
        ensures result.size >= size && result.alignment == alignOf(Type)

    // То же, но без памяти возвращает null.
    static fn tryAllocate(size: Int) -> own Pointer? nofail
        requires Type is FixedSize ==> size == sizeOf(Type)
        ensures result == null || (result.size >= size && result.alignment == alignOf(Type))

    // Возвращает блок; его размер стратегия находит сама.
    static fn deallocate(ptr: own Pointer) nofail
}
```

Функции статические: значения типа до вызова ещё нет. Ограничение `Type: Allocatable` пропускает только типы,
значения которых получают память от аллокатора: классы и структуры строк `set` уровня `layout`
([`Allocatable`](../runtime/built-in-contracts.md#allocatable)). Для множества `layout` компилятор спрашивает
стратегию `AllocatorType<X.Item>`, для класса — `AllocatorType<Класс>`. У множества ключом служит `X.Item`, а не
структура: несколько видов описывают одни байты в разное время
([смена вида](layout/operations.md#67-смена-вида-и-замена-области)), и память, взятая под одним видом, возвращается
под любым другим. Структура, которая задаёт свой размер сама
([область с разным шагом](layout/declaration.md#область-с-разным-шагом)), получает память только по ключу `X.Item`.

Размер элемента множества — размер структуры, объявленной в строке `set` (`set Nodes: Node`). Смена вида заново
толкует байты уже выданного слота и памяти не берёт, а вид больше слота отвергает приведение
([приведение `as`](pointer.md#приведение-as), правило 1).

Строка `requires` связывает размер с типом. У типа `FixedSize` все значения одного размера, и `size` равен
`sizeOf(Type)` ([`FixedSize`](../runtime/built-in-contracts.md#fixedsize)). Тип динамического размера объявляет
статический метод `sizeOf` над полями, которые задают размер, например `static fn sizeOf(length: Int) -> Int` у
`Record`; FLOW доказывает, что метод согласован с инвариантом размера типа. Пул слотов одного размера объявляет
параметр `<T: Allocatable & FixedSize>`: слот вмещает блок, только когда размер у типа один.

Для элемента компилятор вызывает `allocate(size:)` до вычисления аргументов формы. Размер даёт тип: `sizeOf(Type)` у
типа `FixedSize`, у типа динамического размера — его метод `sizeOf` по полям размера формы
(`Record.sizeOf(length: n)`). Выравнивание — `alignOf(Type)`, его обещает `ensures`. Затем компилятор приводит память
к виду; условие `ensures` доказывает, что память вмещает вид. Когда значение `own` кончается, он вызывает
`deallocate(ptr:)` той же стратегии ([создание элемента](layout/operations.md#62-создание-элемента)). `tryAllocate`
служит коду, который работает с сырой памятью элемента сам; такой код передаёт тот же размер: `sizeOf(Type)` или
результат метода `sizeOf` типа. При неудаче ничего не меняется, как у общего контракта. Функций роста у контракта нет.

<a id="область-не-берёт-памяти"></a>

## Область не берёт памяти

У области `Area<T>` аллокатора нет. Область описывает память, в которой подряд лежат значения `T`, и никогда её не
берёт. `Area<T>` не соответствует `Allocatable`, поэтому `AllocatorType<Area<T>>` — ошибка компиляции по обычному
правилу ограничения параметра. Конструктора, который выделяет область, нет.

Область существует в двух видах. Первый — вид сырой памяти: код владельца берёт память у общего аллокатора и
приводит её к области, а когда значения из слотов забраны или уничтожены, стирает вид и возвращает память тому же
аллокатору:

```efen
let memory = A.allocate(size: n * sizeOf(T), aligned: alignOf(T))
let fresh: Area<T> = memory as Area<T> { value.count == n }
// слоты заполняются и забираются кодом владельца
A.deallocate(ptr: fresh as Pointer)
```

Второй — поле `inline`: область лежит в памяти элемента, который её содержит, и возвращается вместе с ним
([вложенность](layout/declaration.md#вложенность)).

## Коллекция и её аллокатор

Коллекция берёт и возвращает память своей области в собственном коде, через контракт `memory::Allocator`. Аллокатор
она получает параметром типа с ограничением `Allocator`; по умолчанию это `mm`:

```efen
private layout<T: Movable, A: Allocator = mm> {
    public struct Vector {
        var items: own Area<T>? = null { (value == null) == (capacity == 0) && (value == null || value.count == capacity) }
        var capacity: Int = 0 { value >= 0 }
        var count: Int = 0 { value >= 0 && value <= capacity }
        invariants { items == null || items!.initialized == count }
        set Elements: items[_]
    }
}
```

`Vector<Int>` и `Vector<Int, FrameArena>` — два разных типа: аргумент `A` входит в тождество типа, как любой
аргумент. Код, который только читает элементы, берёт срез `Slice<T>` или контракт индексирования (`Indexable`) и
аллокатора не называет. Полный пример — [динамический массив](layout-examples/dynamic-array.md).

Код коллекции знает контракт: сигнатуры и условия функций `Allocator`, но не реализацию. Поэтому FLOW доказывает
коллекцию против контракта один раз, а каждую реализацию против того же контракта отдельно, и аллокатор меняется без
переписывания кода коллекции.

## Менеджер памяти `mm`

`mm` — пакет, который управляет памятью программы: тот, который называет поле `allocator:` её конфигурации
([конфигурация сборки](../build-config.md)). Куча одна на исполняемый файл, и выбирает её программа, а не
библиотека. `mm` реализует `memory::Allocator` и `memory::ExtendableAllocator`: у его функций те же сигнатуры и
условия, что у функций контрактов. Размер блока для `deallocate` он находит по адресу: служебную запись хранит сам
блок. Код пишет `mm` аргументом типа коллекции или для сырой памяти `own Pointer`; значения типов получают память
через `AllocatorType<Type>`.

Стратегия по умолчанию передаёт каждую операцию в `mm`. Её даёт пакет `allocator:`; она действует для типа, для
которого не выбрана другая стратегия. При `allocator: none` форма, которой нужна память, вызывает ошибку сборки.

```efen
public strategy Heap<Type> {
    conforms AllocatorType<Type>

    static fn allocate(size: Int) -> own Pointer throws only AllocationError {
        return mm.allocate(size: size, aligned: alignOf(Type))
    }

    static fn tryAllocate(size: Int) -> own Pointer? nofail {
        return mm.tryAllocate(size: size, aligned: alignOf(Type))
    }

    static fn deallocate(ptr: own Pointer) nofail {
        mm.deallocate(ptr: take ptr)
    }
}
```

Строка `conforms AllocatorType<Type>` проверяется у каждой инстанциации, поэтому `Heap<Area<Int>>` — ошибка
компиляции: ограничение `Type: Allocatable` контракта ложно.

## К каким типам прилипает стратегия

Ограничение параметра стратегии задаёт, к каким типам она применима. `ThreadHeap` ниже служит только типам,
привязанным к одному потоку, и берёт память из кучи потока без блокировки:

```efen
public strategy ThreadHeap<Type: ThreadBound> {
    conforms AllocatorType<Type>

    static fn allocate(size: Int) -> own Pointer throws only AllocationError {
        return threadheap::take(size: size, aligned: alignOf(Type))
    }

    static fn deallocate(ptr: own Pointer) nofail {
        threadheap::give(ptr: take ptr)
    }

    // tryAllocate написан так же
}
```

Стратегию для типа выбирают обычные правила ([выбор стратегии](../strategies.md#правила-выбора-стратегии)):
`provide` в пакете типа, запись программы, правило `Resolve<AllocatorType<let T>>`; стратегия по умолчанию —
последний шаг, а не кандидат наравне с другими. Внешний пакет и программа меняют аллокатор типа только там, где тип
пишет `allow strategies` ([право применить стратегию](../strategies.md#право-применить-стратегию)).

<a id="один-аллокатор-на-множество"></a>

## Один аллокатор на множество

Компилятор выбирает стратегию `AllocatorType<X.Item>` один раз на множество, а не на вызов: каждое создание и каждое
освобождение элемента `X` идёт через неё. Каждая строка `set` и `set area` считается
ограничением своего `layout`, поэтому выбранная стратегия входит в тождество его типов
([идентичность](../strategies.md#тело-обобщённого-объявления)). Два пакета с разным выбором получают разные типы, и
передать значение из одного в другой — ошибка компиляции:

```text
error: expected List<Int> [AllocatorType = mm::Heap], found List<Int> [AllocatorType = pools::NodePool]
```

Так аллокатор подменяется в разных контекстах: по типу и при компиляции. Память элемента возвращается аллокатору,
который её выдал, потому что другого у его множества нет. Память области коллекции возвращается аллокатору `A`,
который назван аргументом её типа ([коллекция и её аллокатор](#коллекция-и-её-аллокатор)).

Класс получает память так же: `MyObject(data: 1)` вызывает `allocate` стратегии, выбранной для `MyObject`.

```efen
class MyObject {
    conforms Constructible, ThreadBound
    var data: Int

    @constructor fn init(data: Int) -> Self {
        self.data = data
    }
}

provide ThreadHeap for MyObject                 // MyObject привязан к потоку: ThreadHeap к нему применим
```

Стратегию иерархии классов выбирает её корень: `provide … for Корень` или другой выбор `AllocatorType<Корень>`.
Объекты наследников берут память у той же стратегии, и выбор другой стратегии для наследника вызывает ошибку
компиляции, как строки `ArcClass` и `OpenClass` у наследника ([классы](../classes.md#определение-класса)). Иерархия
открытого класса не `FixedSize`: объекты её классов разного размера, поэтому пул слотов с ограничением `FixedSize` к
ней не применим.

<a id="ручное-выделение"></a>

## Ручное выделение

Правило выделения одно для каждого типа. Тип со стандартным аллокатором работает, как описано выше: память
выделяет и освобождает компилятор. Тип с нестандартным аллокатором через API времени компиляции может потребовать,
чтобы аллокатор и явный конструктор вызывались вручную, или назвать другой аллокатор. Тип в ручном режиме
освобождает память явным вызовом статической `deallocate(ptr:)` своей стратегии.

## Отказ при освобождении

`deallocate` объявлен `nofail` на обоих уровнях, и реализация повторяет это слово. Он не ждёт
([эффекты ожидания](../shared.md#эффекты-ожидания)) и памяти у менеджера не просит: служебную запись хранит сам блок.
Его вызывают на каждом выходе, в том числе во время раскрутки: `deallocate` стратегии типа — компилятор, `deallocate`
общего контракта — код владельца памяти. Сообщать об отказе некому.

Отказ, после которого инварианты кучи верны, реализация поглощает: блок остаётся у аллокатора или теряется.
Нарушение инвариантов (адрес не выдан этим аллокатором или уже возвращён, заголовок блока испорчен) останавливает
программу вызовом `halt()` в каждой сборке: при раскрутке каждый кадр вернул бы свои значения в ту же кучу.

Возврат старого блока в `reallocate` и `tryReallocate` — то же освобождение: `reallocate` бросает только
`AllocationError` и только до переноса.
