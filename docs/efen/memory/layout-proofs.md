# Доказательство структур на `layout`

[Layout](layout/README.md#справочник-правил) · [Каталог структур](layout-catalogue.md) · [Условия](../conditions.md) · [Чужой опыт](prior-art.md)

Статус: статья не нормативна. Она содержит разбор на бумаге (2026-11-08). 2026-11-12 примеры приведены к правилам
[справочника](layout/README.md#справочник-правил): у каждого множества есть владелец, а хранимый указатель остаётся внутри своей
публичной структуры. Сами доказательства после этого не пересматривались. FLOW этих доказательств ещё не строит;
чего ему для этого не хватает, названо в каждом разделе и сведено в [итоге](#итог).

Структура на `layout` доказывается индукцией по событиям: инвариант верен в начальном состоянии, каждое событие его
сохраняет, а уничтожение, перемещение и смена вида не оставляют висячих указателей. Остальные состояния выводятся из
начального цепочкой событий и отдельно не доказываются. Так доказывается и произвольный граф: вершинами владеет
структура графа через цепочку якорей, рёбра записаны указателями внутри того же графа, а отсутствие указателей на
вершину доказывает функция, которая её освобождает. Не доказывается локально
только владение, которое зависит от достижимости по графу: цикл якорей, который держится одними указателями.

## Правила доказательства

Доказательство структуры складывается из четырёх частей.

| Часть | Что доказывается | Кто пишет |
|---|---|---|
| инвариант | форма структуры: где лежат якоря и указатели | программист, в `layout` |
| база | инвариант верен в начальном состоянии: пустая структура, только что рождённый элемент | FLOW |
| шаг | каждое событие, меняющее структуру, сохраняет инвариант | FLOW |
| крайнее состояние | уничтожение, перемещение, смена вида не оставляют [висячих указателей](layout/lifetime.md#общий-принцип) | FLOW |

**Шаг проверяется на проверяемых элементах события.** Это элементы, названные в коде, и слоты, куда из них указывает
инвариант (`next!.prev`); в литературе — *footprint*. Инвариант раскрывается только на них. Для остальной части структуры инвариант верен,
потому что событие её не тронуло. Так устроены natural proofs (Qiu, Garg, Ştefănescu, Madhusudan, PLDI 2013, логика
Dryad): рекурсивное определение раскрывается на следе кода, и Z3 получает формулу без рекурсии. По пересказу авторов,
так автоматически доказаны списки, деревья поиска, AVL и красно-чёрные деревья, кучи и функции glib; статья здесь не
перепроверялась.

**Инвариант на якоре.** Dryad получает обратное направление даром: рекурсивное определение
списка в логике разделения делает предшественника единственным. Инвариант первого порядка над множеством этого не даёт:
`next!.prev == self` говорит, что следующий указывает назад, но не говорит, где ещё может храниться `prev == p`. Слоты с
указателями FLOW находит по инварианту или обходом ([правило чистоты](layout/pointers.md#43-правило-чистоты),
правило 6). Поле, которое не находит ни один инвариант и ни один обход, делает ошибкой переход элемента, а не
объявление `layout`. Один из способов поиска состоит из трёх частей:

1. каждый узел принадлежит ровно одному якорю;
2. поле-якорь `anchor Nodes.Item?` может нести инвариант об обратном указателе узла под ним: `next!.prev == self`,
   `left!.parent == self`, `head!.prev == null`. Тогда поле с обратным указателем FLOW находит по этому инварианту.
   Требованием к объявлению это не служит: поле-якорь без такого инварианта (`nextAll` у графа) допустимо, и
   указатели на его узлы FLOW находит обходом;
3. узел под якорем функции (параметр, локальная, результат) вне структуры. Его обратный указатель функция ведёт как
   локальный: он записан при `tie` из старого поля-якоря (`x.parent == p`), становится недействительным при вызове,
   сводка которого уничтожает элементы множества, требуется действительным или `null` выведенным предусловием
   функции, которая его читает, и переписывается при укладке в новое поле-якорь.

Тогда указатели на `p` хранятся в обратных указателях узлов в его полях-якорях или в обратных указателях узлов под
якорями функций, а за них отвечает сама функция. Инвариант на обратном указателе (`prev!.next == self`) руками не
пишется: он сломал бы каждую передачу
оторванного узла через вызов.

**Права записи и границы в примерах.** Все функции примеров — функции своего `layout`; где пример стоит после
закрывающей скобки `layout`, он сокращён. Какое право нужно операции, называет таблица
[`edit` и `mut`](layout/operations.md#edit-и-mut-в-layout), а откуда функция берёт право на элемент, определяет раздел
[«Право на элемент»](layout/functions.md#82-право-на-элемент). Экземпляров у `layout` нет, множество одно на программу
([множества и области](layout/declaration.md#множества-и-области), правило 1).

**Освобождение принимает только `own`.** Переход к владению пишется `let dead = node as own Nodes.Item`, где `node` —
значение под `anchor`; с концом `dead` память уходит туда, откуда пришла. Кроме невладеющих указателей компилятор проверяет, что функция владеет элементом:
якорь взят в этой функции через `tie` (значение `own` через `take`) либо пришёл параметром `anchor`
([удаление элемента](layout/operations.md#переход-к-владению-as-own), правило 2). Указатели вызывающего на элемент недействительны по сводке.
На этом переходе компилятор по всем инвариантам `layout` проверяет, что на память больше никто не ссылается; без
доказательства переход отвергается. К этой точке владеющие поля элемента, `own` и якоря, равны `null`
([удаление элемента](layout/operations.md#переход-к-владению-as-own), правило 3).

**Освобождения всех элементов одним шагом нет.** Каждый элемент освобождает его владелец, а память родителя
возвращается по правилу 8 раздела [«Выдача и возврат слота»](layout/operations.md#выдача-и-возврат).

**Держатели указателей считаются от входа в функцию.** Внутри тела инвариант бывает нарушен, его проверяют в точках передачи.
Поэтому на событии уничтожения FLOW ищет указатели не по инварианту в этой точке, а по состоянию на входе в функцию и записям
тела до события. Пример: в `A→B→C` после `n.next = tie old.next` у `C` осталось `C.prev == B`; инвариант в этой точке
нарушен и о нём не говорит, но запись тела видна, и `old as own Nodes.Item` до починки `C.prev` — ошибка.

**Отсутствие висячих указателей делится между структурой и кодом.** Инвариант говорит, где указатели на значение могут лежать;
код события показывает, что каждое из них мертво, переписано или верно. Чем точнее инвариант, тем больше работы в шагах,
которые его поддерживают, и тем меньше в событии.

| Где доказательство | Инвариант говорит | Код события делает | Раздел |
|---|---|---|---|
| в структуре | указателей нет | ничего | [односвязный](#односвязный-список) |
| смешанное | указатель один, в известном слоте, или указатели — в одной цепочке узла | переписывает этот указатель или опустошает цепочку | [двусвязный](#двусвязный-список), [дерево](#дерево-с-родителем), [пара](#пара-и-кольцо), [граф со входящими](#граф-со-входящими-рёбрами) |
| в коде | указатели в любых элементах той же публичной структуры | проходит все её элементы | [граф с исходящими](#граф-только-с-исходящими-рёбрами), [произвольный граф](#произвольный-граф-вершинами-владеет-структура) |

**Что выводится.** Инварианты пишутся. Пометки сводок (уничтожает, отдаёт, оставляет), условия функций и инварианты типовых
циклов FLOW выводит сам. Типовой цикл — проход по цепочке до `null` или по счётчику; инвариант необычного цикла не
выводится, и такой цикл — ошибка с подсказкой.

**Вывод по цепочке.** Цикл, который идёт по цепочке через одно поле (`h = h.next`), получает выведенный инвариант,
если выполнены все условия:

- инвариант связывает соседей по этому полю отношением, которое склеивается по шагам: равенство поля
  (`next.face == face`) или порядок по одному полю (`<`, `<=`, `>`, `>=`), с учётом нулевого числа шагов;
- поле, по которому идёт цикл, в цикле не пишется, и инвариант для него верен на входе в цикл;
- инвариант связывает **начало прохода и текущий элемент**, и только их.

Для обхода по кругу, который кончается на исходном элементе, выводится ещё «пройден весь цикл», если в цикле нет
раннего выхода и инвариант делает `next` взаимно однозначным (`next.prev == self && prev.next == self`). Отношение между
текущим элементом и **концом** пути (`root.rank > y.rank` при сжатии пути) этим правилом не выводится: для него нужно
«`y` лежит между началом и концом», а это достижимость.

**Граница локальности.** Обязательство события должно зависеть только от его проверяемых элементов: от узлов,
названных в коде, и от слотов, указанных инвариантом. Если ответ зависит от путей произвольной длины через произвольные узлы, локально
он не доказывается ([раздел](#произвольный-граф-вершинами-владеет-структура)).

Такое обязательство есть у каждой записи якоря `t.f = tie r`: `t` не входит в дерево якорей `r`, иначе цикл замкнётся
и его никто не уничтожит. Когда компилятор принимает запись, определяет правило 5 раздела
[«Перенос владения»](layout/operations.md#64-перенос-владения): поле `t.f` равно `null`, и один из трёх фактов правила
доказывает, что `t` принадлежит другой структуре, чем дерево `r`. Записи в примерах этой статьи принимаются так:

| Запись | Факт правила 5 |
|---|---|
| `n.next = tie list.head` в `push`, `n.next = tie a.next` в `insertAfter` | «а»: `n` пришёл параметром `anchor` и владеет собой |
| `list.head = tie n` в `push` | «в»: `head` служит полем корня `list`, а отделение корень не затрагивает |
| `a.next = tie n` в `insertAfter` | ни один: `a` служит указателем-параметром без источника в типе; FLOW выводит предусловие `a != n && n.next == null` |
| `p.next = tie node.next` в `remove` | «в»: узел `node` отделён от поля `p.next`, а отделение сам элемент `p` не затрагивает |
| `x.right = tie y.left`, `y.left = tie x` в `rotateLeft` | «а»: `x` пришёл параметром `anchor`, `y` служит локальным владельцем |
| `e.next = tie fresh![b].head` в `grow` | «а»: `e` служит локальным владельцем |
| `fresh![b].head = tie e` в `grow` | «в»: слот принадлежит локальному владельцу `fresh`, а хвост записи `e` отделён от этого же слота |

Когда ни один факт не доказан и предусловие через поля, которые читает вызывающий, не записывается, запись вызывает
ошибку. Так `fn graft(x: mut Nodes.Item, s: anchor Nodes.Item) { x.left = tie s }` отвергается: условие «`x` не
входит в дерево `s`» через поля не выражается.

## Односвязный список

```efen
layout {
    set Nodes: Node

    struct Node {
        var next: anchor Nodes.Item? = null
    }

    struct List {
        var head: anchor Nodes.Item? = null
    }
}
```

**Инвариант.** Владение — цепочка от `head` по `next`. Указателей на узлы нет, потому что в `layout` нет ни одного поля типа
`Nodes.Item`; это проверяемое условие, а не следствие якоря: `anchor` хранимые указатели допускает.

**База.** `head == null`.

**Шаги.**

```efen
fn push(list: edit List, n: anchor Nodes.Item) {
    n.next = tie list.head      // n пришёл якорем: он не в цепочке, цикла нет
    list.head = tie n
}

fn pop(list: mut List) -> anchor Nodes.Item? {
    let first = tie list.head ?? return null
    list.head = tie first.next  // после tie поле first.next равно null
    return first
}
```

В `push` два обязательства. `n` не лежит в цепочке, иначе `n.next = tie list.head` замкнёт цикл; это даёт
источник: `n` пришёл параметром `anchor`, его якорь был у вызывающего. И `n.next == null`: иначе запись
перепишет якорь собственного хвоста `n`, а если в этом хвосте лежит узел списка, цикл замкнётся с другой стороны.
Второе обязательство FLOW выводит в предусловие `push`.

**Крайнее состояние.** `let dead = first as own Nodes.Item` после `pop`: указателей на узел нет, висячих указателей нет. Доказательство целиком в
структуре.

## Двусвязный список

```efen
layout {
    set Nodes: Node

    struct Node {
        var next: anchor Nodes.Item? = null
        var prev: Nodes.Item? = null                    // невладеющий указатель
        invariants { next == null || next!.prev == self }
    }

    struct List {
        var head: anchor Nodes.Item? = null
        invariants { head == null || head!.prev == null }
    }
}
```

**Инвариант.** Указатель на узел один: `prev` его следующего соседа. Инвариант на якоре говорит, где он лежит: `n.next!.prev`. Узел,
вынутый из списка, сохраняет `prev` на бывшего соседа, но он под якорем функции, и этот указатель ведёт она
([правило](#правила-доказательства)).

**База.** Пустой список; узел, только что вставленный в голову, с `prev == null`.

**Шаг: вставка после узла `a`.** Предусловие `n.next == null` выводится, как в `push`, а вместе с ним `a != n`
([правила](#правила-доказательства)).

```efen
fn insertAfter(a: edit Nodes.Item, n: anchor Nodes.Item) {
    n.prev = a
    n.next = tie a.next
    if let b = n.next { b.prev = n }
    a.next = tie n
}
```

Окрестность события — `a`, `n` и бывший сосед `b`. Инвариант проверяется на трёх узлах: `a.next!.prev == a`,
`n.next!.prev == n`, у `b` он не меняется. Остальные узлы событие не тронуло.

**Крайнее состояние: удаление из середины.**

```efen
fn remove(list: mut List, n: read<list> Nodes.Item) {
    let p = n.prev ?? return                   // голову удаляет removeHead
    let node = tie p.next ?? return            // якорь n: n в списке, его поле-якорь находится у n.prev
    p.next = tie node.next
    if let b = p.next { b.prev = p }           // единственный указатель на n переписан
    let dead = node as own Nodes.Item
}
```

На `free` FLOW спрашивает, где указатели на `n`. Инвариант отвечает: только в `n.next!.prev`, то есть в `b.prev`. Он
переписан на `p`. Собственное поле `n.prev` уничтожается вместе с `n`. То, что `tie p.next` забирает именно `n`, из
инварианта на якоре не следует: для этого нужно `n.prev!.next == n`. Это условие FLOW выводит как предусловие
`remove` («`n` в списке и не первый»), и его доказывает вызывающий. Право освободить узел даёт параметр
`list: mut List`. Доказательство смешанное, но проверяемых элементов три.

## Дерево с родителем

```efen
layout {
    set Nodes: Node

    struct Node {
        var left: anchor Nodes.Item? = null
        var right: anchor Nodes.Item? = null
        var parent: Nodes.Item? = null
        invariants {
            left == null || left!.parent == self
            right == null || right!.parent == self
        }
    }

    struct Tree {
        var root: anchor Nodes.Item? = null
        invariants { root == null || root!.parent == null }
    }
}
```

**Инвариант.** Указатель на узел один: `parent` каждого его ребёнка. Владение — дерево по `left`, `right` и `Tree.root`; у
каждого поля-якоря свой инвариант на якоре.

**База.** Пустое дерево; лист с `parent`, указывающим на узел, в который его вставили.

**Шаг: левый поворот.**

```efen
fn rotateLeft(x: anchor Nodes.Item) -> anchor Nodes.Item {
    let y = tie x.right ?? return x
    x.right = tie y.left
    if let b = x.right { b.parent = x }
    y.parent = x.parent
    x.parent = y
    y.left = tie x          // y вынут из x.right: в поддереве x его нет, цикла нет
    return y
}
```

Окрестность — `x`, `y`, `b`. Инвариант на трёх узлах: `x.right!.parent == x`, `y.left!.parent == y`; у `y` новый
родитель тот же, что был у `x`. FLOW выводит условие результата `result.parent == old(x.parent)`. По нему вызывающий
доказывает инвариант в узле, куда кладёт `y` вместо `x`. Цикла нет по записи спуска: `y` взят из `x.right`, значит,
оторван от поддерева `x`.

**Крайнее состояние: уничтожение поддерева.**

```efen
fn freeTree(t: anchor Nodes.Item) {
    if let l = tie t.left { freeTree(t: tie l) }
    if let r = tie t.right { freeTree(t: tie r) }
    let dead = t as own Nodes.Item
}
```

Указатели на `t` по инварианту лежат только в `parent` его детей, а дети уже уничтожены. Если вызывающий раньше вынул
узел `x` из поддерева (`let x = tie p.left`), у `x` осталось `x.parent == p`; этот указатель ведёт вызывающий, и после
`freeTree` он недействителен: первое чтение `x.parent` или вызов `rotateLeft(x: tie x)`, которому он нужен действительным, — ошибка. Указатель на `t` из его родителя — это
якорь, его забрал вызывающий. Висячих ссылок нет. Рекурсия конечна: идёт по якорям, а якоря образуют дерево.

## Пара и кольцо

**Пара.** Цикл двух узлов строится из указателей, а узлами владеет цепочка якорей структуры `Pairs`.

```efen
layout {
    set Nodes: Node

    struct Node {
        var peer: Nodes.Item? = null
        var nextAll: anchor Nodes.Item? = null       // цепочка всех узлов: владеет следующим
        invariants { peer == null || peer!.peer == self }
    }

    public struct Pairs {
        var all: anchor Nodes.Item? = null           // владеет цепочкой узлов
    }
}

fn makePair(pairs: edit Pairs, a: read<pairs> Nodes.Item, b: read<pairs> Nodes.Item) {
    a.peer = b
    b.peer = a               // база инварианта пары
}

fn dropPeer(pairs: mut Pairs, a: read<pairs> Nodes.Item, b: read<pairs> Nodes.Item) {
    a.peer = null                       // по инварианту указатель peer на b хранит только a
    let cut = unlinkNode(pairs, b)      // anchor Nodes.Item: узел вырезан из цепочки pairs
    let dead = cut as own Nodes.Item    // b.peer уничтожается вместе с b
}
```

Право писать в узлы и освободить `b` даёт параметр `pairs: mut Pairs`; параметры `a` и `b` только называют узлы этой
структуры. FLOW выводит предусловие `dropPeer`: `a.peer == b`. Без него `a.peer = null` нарушило бы инвариант у
настоящего соседа `a`. Время жизни `b` кончается в точке вызова `dropPeer`.

**Кольцо.** Узлы кольца держит реестр (цепочка якорей), связи кольца — указатели `next` под инвариантом «цепочка по `next` от
узла возвращается в него». Шаг «вставить после `a`» меняет два указателя, но инвариант касается каждого узла кольца: цепочка
любого узла проходит через `a`. Довод корзин хеш-таблицы («произвольная цепочка, два случая») здесь не работает: у корзин есть
нетронутые цепочки, а в кольце через `a` проходит цепочка каждого узла. Обязательство — достижимость по пути любой
длины, а это за границей локальности. Поэтому инвариант кольца пишется локально: `next.prev == self && prev.next == self`. В конечном множестве он
делает каждый узел частью цикла, и вставка и удаление проверяются на двух соседях. Что кольцо одно, а не несколько, —
правильность алгоритма, вне модели. Поиск предыдущего звена обходом по кругу до исходного узла покрывает
[вывод по цепочке](#правила-доказательства).

## Граф только с исходящими рёбрами

```
══▶  якорь              to┆X  указатель: ребро ведёт в узел X

 Graph.first
     ║
     ▼
  ┌─────┐ nextInGraph ┌─────┐ nextInGraph ┌─────┐
  │  A  │════════════▶│  B  │════════════▶│  C  │════▶ null
  └─────┘             └─────┘             └─────┘
     ║ out               ║ out               ║ out
     ▼                   ▼                   ▼
  ┌─────┐ nextOut ┌─────┐┌─────┐          ┌─────┐ nextOut ┌─────┐
  │ e1  │════════▶│ e2  ││ e3  │          │ e4  │════════▶│ e5  │
  └─────┘         └─────┘└─────┘          └─────┘         └─────┘
   to┆B            to┆C   to┆C             to┆A            to┆C   ← петля
```

```efen
layout {
    set Vertices: Vertex
    set Edges: Edge

    struct Vertex {
        var nextInGraph: anchor Vertices.Item? = null
        var out: anchor Edges.Item? = null
    }

    struct Edge {
        var to: Vertices.Item
        var nextOut: anchor Edges.Item? = null
    }

    struct Graph {
        var first: anchor Vertices.Item? = null
        invariants {
            let all = Vertices.chain(from: first, by: Vertex.nextInGraph, until: null)
            forall e in Edges: all.contains(e.to)        // ребро графа ведёт в вершину его цепочки
        }
    }
}
```

**Инвариант.** Владение — дерево глубины два: реестр узлов и цепочка рёбер каждого узла. Циклы графа идут только по
указателям `to`. Инвариант рёбер: каждое ребро графа ведёт в узел цепочки этого же графа. В каких рёбрах хранятся
указатели на узел, инвариант не говорит.

**Шаги.** Добавить узел и добавить ребро — `tie` в голову цепочки; инвариант верен, потому что функция получает `to`
параметром с источником `read<g>`. Удалить ребро — рёбер стало меньше.

**Крайнее состояние: удаление узла.**

```efen
fn removeVertex(g: mut Graph, v: read<g> Vertices.Item) {
    var u = g.first
    while let w = u {
        removeEdgesTo(g, from: w, target: v)   // все рёбра w с to == v
        u = w.nextInGraph
    }
    freeOwnEdges(g, v: v)
    let dead = unlinkVertex(g: g, v: v) as own Vertices.Item
}
```

Инвариант не сужает поиск, поэтому доказательство целиком в коде. Запись `forall e in Edges` в инварианте `Graph`
перебирает рёбра этого графа ([цепочка](layout/invariants.md#52-цепочка), правило 6), а по правилу чистоты ребро другого
графа на `v` не указывает. Параметр `v: read<g> Vertices.Item` требует вершину именно графа `g`, поэтому проход по
реестру `g` проходит каждое ребро, которое может хранить указатель на `v`. Инвариант прохода «в пройденной части реестра
рёбер в `v` нет» FLOW выводит как для типового цикла. Проход кончается на `null`, значит, пройден весь реестр, и на
`free` верно `forall e in Edges: e.to != v`. Без прохода или с проходом, который останавливается раньше `null`, —
ошибка. Цена — обход всех рёбер графа на каждом удалении узла.

## Граф со входящими рёбрами

```efen
layout {
    set Vertices: Vertex
    set Edges: Edge

    struct Vertex {
        var nextInGraph: anchor Vertices.Item? = null
        var out: anchor Edges.Item? = null
        var inbound: Edges.Item? = null
    }

    struct Edge {
        var from: Vertices.Item
        var to: Vertices.Item
        var nextOut: anchor Edges.Item? = null
        var nextIn: Edges.Item? = null
    }

    struct Graph {
        var first: anchor Vertices.Item? = null
        invariants {
            forall e in Edges:
                Edges.chain(from: e.from.out, by: Edge.nextOut, until: null).contains(e) &&
                Edges.chain(from: e.to.inbound, by: Edge.nextIn, until: null).contains(e)
        }
    }
}
```

**Инвариант.** Каждое ребро лежит в двух цепочках: исходящих своего источника и входящих своей цели. Этого мало:
`nextIn` — указатель, и две цепочки входящих могут сойтись в общий хвост или образовать петлю (`e1.nextIn = e1`), не нарушая
инварианта. Тогда удаление ребра из чужой цепочки оставит висячий указатель в цепочке `v`. Поэтому к инварианту добавляются
однородность цепочки и её конечность:

```efen
struct Vertex { invariants { inbound == null || inbound!.to == self } }
struct Edge   { invariants { nextIn == null || nextIn!.to == to } }
```

Конечность здесь — свойство самой записи `chain(from: e.to.inbound, by: Edge.nextIn, until: null)`: цепочка обязана дойти до `null`. С этими инвариантами
указатели на узел `v` лежат только в рёбрах двух его цепочек.

**Шаги.** Добавление ребра вставляет его в голову двух цепочек; проверяемые элементы — `from`, `to` и само ребро. Удаление ребра
вынимает его из двух цепочек, а в односвязной цепочке для этого нужен проход до предыдущего звена, так что проверяемые
элементы удаления — вся цепочка. Инвариант проверяется для произвольного ребра в три случая: ребро события, другое ребро той же
цепочки и ребро чужой цепочки, которой событие не коснулось.

Новое ребро в локальной переменной инвариант не нарушает: запись `forall e in Edges` перебирает рёбра, которые
принадлежат этому графу ([цепочка](layout/invariants.md#52-цепочка), правило 6).

**Крайнее состояние: удаление узла.**

```efen
fn removeVertex(g: mut Graph, v: read<g> Vertices.Item) {
    while let e = v.inbound { removeEdge(g, e) }      // removeEdge(g: mut Graph, e: read<g> Edges.Item)
    while let e = v.out { removeEdge(g, e) }
    let dead = unlinkVertex(g: g, v: v) as own Vertices.Item
}
```

Инвариант сузил поиск до двух цепочек самого `v`. Когда обе пусты, рёбер с указателем на `v` нет. Доказательство смешанное:
цену платит каждая вставка и каждое удаление ребра, которые поддерживают инвариант.

Нужно FLOW: `forall` по множеству и цепочка с головой, зависящей от ребра (`e.from.out`). Сегодня FLOW отслеживает
цепочку только с одной постоянной головой
([что компилятор проверяет сегодня](layout/open-questions.md#состояние-в-компиляторе)).

## Произвольный граф: вершинами владеет структура

Граф с любыми циклами и петлями доказывается без якорных рёбер. Вершинами и рёбрами владеет структура `Graph` через
две цепочки якорей, а концы рёбер записаны невладеющими указателями. Вершину освобождает функция: точка её вызова
кончает время жизни вершины, а её тело доказывает, что указателей на вершину не осталось.

```efen
layout {
    set Vertices: Vertex
    set Edges: Edge

    struct Vertex {
        var label: Int
        var nextAll: anchor Vertices.Item? = null    // цепочка всех вершин графа: владеет следующей
    }

    struct Edge {
        var from: Vertices.Item
        var to: Vertices.Item                        // to == from даёт петлю
        var nextEdge: anchor Edges.Item? = null      // цепочка всех рёбер графа: владеет следующим
    }

    public struct Graph {                            // внешний код хранит граф значением
        var first: anchor Vertices.Item? = null
        var firstEdge: anchor Edges.Item? = null
        invariants {
            let vertices = Vertices.chain(from: first, by: Vertex.nextAll, until: null)
            forall v in Vertices: vertices.contains(v)     // каждая вершина графа входит в цепочку
            let edges = Edges.chain(from: firstEdge, by: Edge.nextEdge, until: null)
            forall e in Edges: edges.contains(e)           // каждое ребро графа входит в цепочку
        }
    }
}

fn removeVertex(g: mut Graph, v: read<g> Vertices.Item) {
    dropEdgesOf(g: g, v: v)                     // проход по цепочке рёбер до null: рёбра с from == v или to == v вынуты и освобождены
    let cut = unlinkVertex(g: g, v: v)          // anchor Vertices.Item: вершина вырезана из цепочки графа
    let dead = cut as own Vertices.Item         // доказано: указателей на v нет
}
```

Множества `Vertices` и `Edges` одни на всю программу, а графов сколько угодно: каждому графу принадлежат вершины и
рёбра его цепочек. Право записи функции даёт параметр `mut` на граф. Параметр `v: read<g> Vertices.Item` требует
вершину этого графа. Встроенного перебора множества нет
([обход множества](layout/declaration.md#множества-и-области)), поэтому граф ведёт обе цепочки сам, и инвариант говорит,
что в цепочку входит каждый его элемент. `dropEdgesOf` показана наброском: проход по цепочке рёбер до `null`, который
вынимает (`tie`) и освобождает каждое ребро с концом в `v`.

**Проверка по свойствам.**

| Свойство | Почему выполняется |
|---|---|
| нет обращения к освобождённой вершине | проход убрал все рёбра с указателем на `v`; по правилу чистоты хранимых указателей на `v` вне графа нет; у вызывающего указатели с источником `g`, которые могут быть равны `v`, недействительны с точки вызова |
| нет двойного освобождения | после `cut as own Vertices.Item` якоря у функции нет, а указатель `v` недействителен; второй вызов вызывает ошибку |
| вершины не пересекаются | каждая вершина занимает свою память, полученную от менеджера памяти |
| память не теряется | вершина без рёбер остаётся в цепочке графа; функция, которая уничтожает граф, проходит обе цепочки и освобождает каждый элемент |

Ребро нечисто: `from` и `to` указывают на вершины того же графа. `Graph` целиком чист, и внешний код получает только
его ([чистая структура](layout/pointers.md#структура-источник-чистота)). Память берётся и возвращается явно
([гарантия 6](layout-algorithm.md#центральные-гарантии)).

**Цена цепочек.** Одно слово на ребро (поле `nextEdge`), одно слово на вершину (поле `nextAll`) и два слова на
головы. Проход по цепочке рёбер стоит O(рёбер), вырезание вершины из односвязной цепочки стоит O(вершин). Это
оценка, не замер. Скрытого учёта элементов у множества нет: цепочку ведёт структура, которая владеет элементами.

**Условия.** Каждое нарушение вызывает ошибку FLOW в названном месте.

1. **Все места, где хранится указатель, известны.** Указатель на `Vertices.Item` или `Edges.Item` хранится в полях
   этого типа внутри `layout` (`Edge.from`, `Edge.to`, `Cursor.current`), в переменных функций, в коллекциях
   (`Vector<Vertices.Item>` в поле структуры графа, `Vector<read<g> Vertices.Item>` вне его) и в захватах замыканий
   того же вызова. Корутина указатель `Vertices.Item` не захватывает
   ([структура и поток](layout/threads.md#структура-и-поток)). Полей конечное число. Хранимые указатели
   в структурах того же графа функция освобождения обходит сама. Переменные вызывающего проверяются у вызывающего
   по условию 2. Если функция учла только `Edge.to`, а граф хранит в своём поле структуру `Cursor` с полем `current`,
   компилятор выдаёт ошибку «поле `Cursor.current` может указывать на `v`». Требование относится и к рёбрам:
   `removeVertex` освобождает их тоже.
2. **Сводка называет освобождённые элементы, и у вызывающего становятся недействительными указатели, которые могут
   быть им равны.** Сводка `removeVertex`: «освобождает `v` и рёбра графа `g` с `from == v || to == v`». Указатель `b`
   после `removeVertex(g: g, v: a)` действителен, только если доказано `b != a`. Указатель на ребро `e0` действителен,
   только если доказано `e0.from != a` и `e0.to != a`. Проверка при выполнении (`if b != a`) даёт этот факт. Коллекция
   указателей с источником `g` (`Vector<read<g> Vertices.Item>`) после вызова существует: `count` допустим, `dispose`
   в конце области видимости забирает слоты `take`, а это использованием указателя не считается
   ([время жизни](layout/lifetime.md#71-что-делает-указатель-недействительным), правило 5), а чтение слота, который
   может хранить `a`, вызывает ошибку ([указатель вне layout](layout/pointers.md#указатели-вне-layout)). Поэтому
   удаление нескольких вершин пишется отдельной функцией (`removeVertices(g, doomed)`): она получает коллекцию и
   освобождает всё за один вызов.
3. **Пока идёт проход по цепочке, вызов, который освобождает её элементы, вызывает ошибку.** Исключение одно:
   текущее звено вынимает сам проход. Проход по цепочке рёбер, который для ребра с `e.to.label < 0` вызывает
   `removeVertex(g: g, v: e.to)`, отвергается: `removeVertex` освобождает рёбра, по которым идёт внешний проход
   ([время жизни](layout/lifetime.md#время-жизни)).
4. **Освобождённый слот не путается с новым.** Элемент множества сам не переносится: перенос пишет явный код,
   поэтому адрес при росте не устаревает. Если указателем служит индекс, слот после освобождения может занять новый
   элемент, и устаревший индекс укажет на него без ошибки. Индекс безопасен только вместе с условием 2.

Нужно FLOW: `forall` по элементам структуры и инвариант полноты цепочки, вывод инварианта прохода «в пройденной
части рёбер с указателем на `v` нет», перечень полей с указателями из объявлений, сводки с освобождёнными
элементами по условию.

**Почему не годится владение по рёбрам.** Если бы узлы держались якорями-рёбрами, у каждого узла было бы не больше
одного входящего якоря. Цикл якорей тогда не может иметь внешнего якоря: он дал бы одному из узлов второй. Значит,
цикл якорей ничей с момента, когда замкнулся, и утечка случается на замыкающей записи. Указатели в этой модели ничего не
держат: их запись утечки не даёт. Вопрос в другом: доказать, что запись `t.f = tie r` не замыкает цикл, значит
доказать, что `t` не лежит в дереве `r`, а для произвольного графа владения это достижимость по пути любой длины.
Локально FLOW доказывает её только фактами правила 5 раздела
[«Перенос владения»](layout/operations.md#64-перенос-владения), остальные записи вызывают ошибку.

Достижимость не выражается инвариантом первого порядка, но у неё есть разрешимые кодировки для решателя: отношение
«между» в эффективно пропозициональной логике (Itzhaky и соавторы, CAV 2013 и POPL 2014), достижимость при изменении
указателей (Lahiri и Qadeer, POPL 2008). Это уже не проверка по проверяемым элементам события, а отдельный механизм, и FLOW его
не применяет. Шорр — Уэйт доказан в Isabelle и в Dafny с Z3 (Leino, 2010) с инвариантами, написанными руками.
Ссылки приведены по памяти и здесь не перепроверялись.

## Сложные графы из литературы

Четыре структуры, которые в литературе служат проверочными примерами для доказательства программ с графами. Система
непересекающихся множеств и поколенческий сборщик мусора доказаны в Coq (Wang, Cao, Mohan, Hobor, OOPSLA 2019,
[статья](https://2019.splashcon.org/details/splash-2019-oopsla/54/Certifying-Graph-Manipulating-C-Programs-via-Localizations-within-Data-Structures),
вместе с разметкой графа и остовным деревом); разметка с переворотом указателей (Шорр — Уэйт) — в Isabelle (Mehta и
Nipkow) и в Dafny (Leino), по памяти;
список полурёбер (DCEL) — основная структура вычислительной геометрии
([описание](https://www.ics.uci.edu/~goodrich/teach/geom/notes/DCEL.pdf)). Доказательства в Coq строит человек; здесь
проверяется, что из них даёт модель `layout` автоматически.

**Граница модели.** `layout` доказывает безопасность памяти: нет висячих указателей, двойного освобождения, потерь и
пересечений, инварианты формы сохраняются. Правильность алгоритма — что `find` возвращает представителя, что разметка
отметила все достижимые узлы, что остов минимален — модель не доказывает.

### Система непересекающихся множеств

```efen
layout {
    set Elements: Element

    struct Element {
        var parent: Elements.Item               // self у корня
        var rank: Int
        var nextAll: anchor Elements.Item? = null    // цепочка всех элементов: владеет следующим
        invariants { parent == self || parent.rank > rank }
    }

    public struct Partition {                   // владеет элементами
        var first: anchor Elements.Item? = null
        invariants {
            let all = Elements.chain(from: first, by: Element.nextAll, until: null)
            forall e in Elements: all.contains(e)
        }
    }
}

fn find(sets: edit Partition, x: read<sets> Elements.Item) -> Elements.Item {
    var root = x
    while root.parent != root { root = root.parent }
    var y = x
    while y.parent != root {                    // сжатие пути
        let next = y.parent
        y.parent = root
        y = next
    }
    return root
}

fn union(sets: edit Partition, a: read<sets> Elements.Item, b: read<sets> Elements.Item) {
    let ra = find(sets, x: a)
    let rb = find(sets, x: b)
    if ra == rb { return }
    if ra.rank < rb.rank { ra.parent = rb }
    else if ra.rank > rb.rank { rb.parent = ra }
    else { rb.parent = ra; ra.rank += 1 }
}
```

- **Память.** Элементами владеет структура `Partition`: цепочка якорей идёт от `first` по полю `nextAll`. Поле
  `parent` хранит невладеющий указатель на элемент той же `Partition`. Пока структура существует, элементы не
  удаляются, поэтому каждое `parent` указывает на существующий элемент. Функция, которая уничтожает `Partition`,
  проходит цепочку и освобождает каждый элемент. Писать `parent` и `rank` разрешает право `edit` на `Partition`, а
  параметры `read<sets>` называют элементы именно этой структуры. Результат `find` записан без слова права, и
  `union` пишет через него своим правом `edit` на `sets`
  ([право на элемент](layout/functions.md#82-право-на-элемент), правило 2).
- **Инвариант в `union`** проверяется на двух корнях: после `rb.parent = ra; ra.rank += 1` у `rb` верно
  `ra.rank > rb.rank`, а у элементов с `parent == ra` ранг родителя только вырос. Но это верно, только если `ra`
  остался корнем после второго вызова `find(sets, x: b)`, а он пишет `parent` на пути `b`. Сводка «`find` пишет только
  не-корни на пути» требует того же инварианта цепочки, что и сжатие пути.
- **Инвариант при сжатии пути** требует `root.rank > y.rank` для каждого `y` на пути. Это транзитивность по цепочке
  `parent` любой длины: инвариант второго цикла «ранг корня больше рангов на пройденном пути» не типовой, и FLOW его
  не выведет. Без инварианта о ранге сжатие пути доказывается сразу: указатели переписываются на живой элемент.
- **Итог:** безопасность памяти — да; инвариант ранга — нет: [вывод по цепочке](#правила-доказательства) даёт отношение
  начала и текущего элемента, а сжатию пути нужно отношение текущего и конца, и второй цикл пишет поле, по которому
  идёт.

### Список полурёбер (DCEL)

Каждое ребро плоского графа — два полуребра в противоположные стороны; у полуребра есть парное, следующее и
предыдущее по своей грани, начальная вершина и грань.

```efen
layout {
    set Vertices: Vertex
    set HalfEdges: HalfEdge
    set Faces: Face

    struct Vertex {
        var incident: HalfEdges.Item?
        var nextAll: anchor Vertices.Item? = null     // цепочка всех вершин: владеет следующей
        invariants { incident == null || incident!.origin == self }
    }

    struct Face {
        var edge: HalfEdges.Item?
        var nextAll: anchor Faces.Item? = null        // цепочка всех граней
        invariants { edge == null || edge!.face == self }
    }

    struct HalfEdge {
        var twin: HalfEdges.Item
        var next: HalfEdges.Item
        var prev: HalfEdges.Item
        var origin: Vertices.Item
        var face: Faces.Item
        var nextAll: anchor HalfEdges.Item? = null    // цепочка всех полурёбер
        invariants {
            twin.twin == self && twin != self
            next.prev == self && prev.next == self
            next.face == face
            twin.origin == next.origin
        }
    }

    public struct Mesh {                              // владеет тремя цепочками
        var vertices: anchor Vertices.Item? = null
        var halfEdges: anchor HalfEdges.Item? = null
        var faces: anchor Faces.Item? = null
    }
}
```

- **Владение.** Вершинами, полурёбрами и гранями владеет структура `Mesh`: три цепочки якорей идут от её полей по
  полям `nextAll`. Инвариант «каждый элемент входит в свою цепочку» пишется, как у `Graph`
  ([пример C](layout/declaration.md#пространство-layout)). Остальные поля хранят невладеющие указатели внутрь той же
  `Mesh`.

- **Указатели на полуребро `h`.** Инварианты фиксируют каждый: `twin` — только у `h.twin` (из `g.twin.twin == g`),
  `next` — только у `h.prev`, `prev` — только у `h.next`, `incident` — только у `h.origin`, `edge` — только у
  `h.face`. Все держатели — среди проверяемых элементов `h`, поэтому удаление пары полурёбер доказывается локально.
- **Указатели на вершину и грань инварианты не ограничивают.** На вершину указывает `origin` каждого исходящего полуребра,
  на грань — `face` каждого её полуребра, и ни один инвариант не говорит, сколько их и где они. У грани с дыркой два цикла
  границы, и проход по циклу `next` от `face.edge` обходит только один. Освобождение вершины или грани поэтому —
  проход по всему множеству полурёбер, или нужен инвариант, который связывает грань со всеми её циклами.
- **Полурёбра вводятся только парой.** Поля `twin`, `next`, `prev`, `face` обязательны, а инвариант
  `twin.twin == self` требует пары. Одно новое полуребро инварианту не удовлетворяет, поэтому пару полурёбер вводит
  одна операция, вместе с циклом их грани
  ([создание элемента](layout/operations.md#выделение-и-освобождение--переход-между-множествами), правило 7).
- **Слияние граней** — проход по циклу `next` до исходного полуребра; [вывод по цепочке](#правила-доказательства)
  даёт «пройден весь цикл», но цикл пишет `face`, и инвариант `next.face == face` в середине прохода ложен. Нужен инвариант
  «в пройденной части `face` новый», а `next` не меняется. Освободить грань после обхода можно, только если инвариант
  говорит, что каждое полуребро с `face == f` лежит на цикле от `f.edge`; без него — у грани с дыркой — проход по
  множеству.
- **Итог:** удаление полурёбер локально; освобождение грани — обходом её цикла при инварианте «все полурёбра грани на
  этом цикле», иначе проходом по множеству; пару полурёбер вводит одна операция, которая привязывает оба (`tie`)
  к цепочке структуры `Mesh`.

### Разметка с переворотом указателей (Шорр — Уэйт)

Обход графа без стека: спускаясь в соседа, алгоритм разворачивает указатель назад, а поднимаясь, восстанавливает его.
Пока обход идёт, граф испорчен: часть указателей указывает не на свои цели.

- **Память.** Ничего не освобождается, все указатели во время обхода ведут в существующие элементы графа. Безопасность
  памяти доказывается сразу: это записи указателей на живые элементы.
- **Инварианты.** Компилятор не доказывает, что после обхода граф стал прежним: это правильность алгоритма, другая
  задача. Он доказывает то же, что для любой функции: на выходе инварианты `layout` верны. С одним инвариантом рёбер
  («ребро ведёт в живой узел») это верно сразу: каждая запись пишет указатель на живой узел. С двусторонними инвариантами
  (как в [графе с обратными указателями](layout-algorithm.md#граф-с-обратными-указателями)) компилятор проверяет инвариант
  на каждом узле, который функция трогала; не доказал — ошибка на выходе с названием инварианта.
- **Граница `layout`.** Пока инварианты нарушены, обход не вызывает внешний код, и это проверяется
  [правилом границы](layout-algorithm.md#граница-layout).
- **Итог:** доказывается сохранение инвариантов на выходе; идентичность графа вне модели.

### Копирующий сборщик мусора

Сборщик переносит живые объекты в новую область.

- **Перенос — создание и освобождение.** Каждый объект создаётся в новом слоте, а старый освобождается. К
  освобождению старого слота применяется то же правило, что к удалению: он переводится в `own`, а для этого все
  указатели на него переписаны на новый слот. Особого вида «пересылка» в модели нет: если сборщик хранит адрес
  пересылки в старом слоте, это его внутреннее дело, и доказывается оно тем же правилом.
- **Что переносится.** Элемент переносится, только когда код `layout` создаёт его в новом слоте и освобождает
  старый; множество само ничего не переносит. Неявного переноса нет: замену области тоже пишет явный код
  ([смена вида и замена области](layout/operations.md#67-смена-вида-и-замена-области)), и она делает
  недействительными все указатели в прежнюю область. Функция, тело которой
  может перенести или освободить элементы множества, несёт это в выведенной сводке.
- **Указатели снаружи.** Внешний мир не держит указатель в множество, которое сборщик может перенести, через
  сборку: такой указатель недействителен после любого вызова, сводка которого может перенести или освободить
  элементы этого множества. В `let a = heap.alloc(); let b = heap.alloc()` использовать `a` после второго
  вызова — ошибка, и это верно. Корень, который переживает сборку, — элемент множества, которое сборщик не переносит
  (`set Roots: Root`, `var target: Objects.Item`). Корни принадлежат структуре кучи: ими владеет её цепочка якорей.
  Внешний код хранит заимствование `read<heap> Roots.Item` и обращается к объекту через функции
  `layout`. Тогда каждый держатель `Objects.Item` — поле `layout` (поля объектов и `Roots.target`), проход переноса знает
  их все и переписывает, как в графе с обратными указателями.
- **Корни на стеке и в регистрах** внутри функций сборщика — его локальные переменные: переписаны переносом или
  недействительны после него. Локальные переменные вызывающего не переписываются — они недействительны по сводке.
- **Итог:** сводится к правилу удаления; нужен проход, который дописывает в новую область во время перебора, как
  типовой цикл.

### Сводка

| Структура | Безопасность памяти | Инварианты формы | Чего не хватает |
|---|---|---|---|
| непересекающиеся множества | да | `union` — да; сжатие пути — нет | отношение текущего элемента и конца пути |
| DCEL | да | удаление полурёбер — да; грань — обходом цикла при инварианте о её цикле, иначе проходом | рождение пары одной операцией |
| Шорр — Уэйт | да | инварианты на выходе — проверяются; идентичность вне модели | — |
| копирующий сборщик | да, правилом удаления, корни — множество `layout` | — | проход с растущей границей как типовой цикл |

Общий пробел у трёх структур из четырёх — цикл или инвариант над цепочкой любой длины: путь `parent`, цикл `next` по
грани, развёрнутый путь обхода. [Вывод по цепочке](#правила-доказательства) закрывает его частично: обход по
кругу до начала и отношение начала с текущим элементом. Отношение текущего элемента с концом пути (сжатие пути)
остаётся достижимостью. Восстановление графа после
Шорра — Уэйта доказывать не нужно: компилятор проверяет только инварианты на выходе.

## Локальное доказательство инвариантов

Статус: гипотеза, проверена на бумаге на менеджере памяти и проверочных структурах; в компиляторе не реализована.

Инвариант, верный на входе функции, на выходе нужно доказать только для того, что функция изменила. FLOW
доказывает его сам, своей линейной арифметикой, за число шагов, равное числу операций в теле; Z3 для этого не нужен.

**Какие инварианты локальны.** Инвариант `forall k in c: P(k)` или `forall k in a ..< b: P(k)` локален, если `P` читает только:

1. поля самого узла `k` и, для двусвязной формы, поля его соседа по ссылке (`k.next.prev == k`);
2. поля вида, которые функция меняет только в сторону, сохраняющую `P` (`k < frontier` при росте `frontier`);
3. принадлежность `k` множеству, которое отслеживает FLOW (`slots.taken.contains(k)`).

Инвариант о числе узлов (`freeSlots.count == frontier - slots.taken.count`, `length == nodes.count`) локален, если обе
стороны меняются на известные величины: вставка даёт `+1`, снятие — `-1`.

**Алгоритм.** На входе инвариант принят. FLOW проходит тело и для каждой операции записывает обязательство:

| Операция | Обязательство на выходе |
|---|---|
| вставка узла `k` в цепочку | `P(k)` |
| снятие головы, вырезание узла | нет: остальные узлы те же, повторов нет |
| запись поля узла `k`, которое читает `P` | `P(k)`, если `k` на цепочке, и `P` соседа для двусвязной формы |
| запись поля вида, которое читает `P` | новое значение сдвинуто в сохраняющую сторону; иначе инвариант не локален |
| выдача слота `m` (`m` входит в `taken`) | `m` не на цепочке: снят с неё или взят у границы |
| возврат слота `m` (`m` выходит из `taken`) | нет: условие `!taken.contains(k)` только усиливается |
| сдвиг границы диапазона (`frontier + 1`) | `P` у узлов, вошедших в диапазон; вышедшие свободны от инварианта |

Внутри тела инвариант может быть нарушен: обязательства проверяются на выходе по итоговым значениям. Каждое обязательство —
линейное неравенство над полями узла и вида, и его доказывает тот же доказатель, что и границы индексов.

**Проверка на структурах.**

| Структура | Инвариант | Локален |
|---|---|---|
| `SlotBlock` менеджера памяти, `Region` менеджера памяти, пул объектов | `forall k in freeSlots: 0 <= k && k < frontier && !slots.taken.contains(k)` | да: `frontier` только растёт, выдача — после снятия или у границы |
| те же | `forall k in frontier ..< slots.count: !slots.taken.contains(k)` | да: выданный у границы слот выходит из диапазона тем же сдвигом |
| односвязный список | `length == nodes.count` | да: `+1` при вставке, `-1` при снятии |
| двусвязный список | `k.next == null \|\| k.next.prev == k` | да, с соседом |
| хеш-таблица | каждая запись в цепочке своей корзины | да, если FLOW отслеживает цепочку каждой корзины отдельно: вставка в корзину `b` требует `e.home == b` |
| дерево поиска | ключ левого меньше ключа правого по всему поддереву | нет: связывает узел со всем поддеревом — Z3 |

**Цикл со счётчиком.** Цикл, где переменная `i` начинается с 0, растёт на 1 за итерацию и кончается на `N`, а тело
делает `P(i)` верным и не меняет других слотов, даёт инвариант цикла `forall k in 0 ..< i: P(k)`: перед циклом диапазон пуст,
итерация добавляет в него ровно слот `i`, после цикла `i == N`. Это тот же сдвиг границы в сохраняющую сторону, что
и рост `frontier`. Раздача `for element in take region` даёт то же без счётчика: тело получает каждый слот ровно
один раз.

**Пример: рост хеш-таблицы.** Записи переходят из старых корзин `A` в новые `B`; освободить `A` можно, только если
пусты все её слоты.

```efen
layout {
    set Entries: Entry

    struct Entry {
        var key: Int
        var home: Int
        var next: anchor Entries.Item? = null       // якорь следующей записи цепочки
    }

    area Buckets: Bucket

    struct Bucket {
        var head: anchor Entries.Item? = null       // якорь первой записи корзины
    }

    struct Table {
        var size: Int = BUCKETS { value > 0 }
        var buckets: own Buckets.Area? = null { value == null || value.count == size }
    }
}

fn grow(table: mut Table) requires table.size == BUCKETS {
    var fresh = Buckets.Area(count: 2 * BUCKETS)
    var i = 0
    while i < BUCKETS {
        while let e = tie table.buckets![i].head {      // снять первую запись старой корзины i
            table.buckets![i].head = tie e.next
            let b = hash(e.key) % (2 * BUCKETS)
            e.home = b
            e.next = tie fresh![b].head                 // вставить в голову новой корзины b
            fresh![b].head = tie e
        }
        i = i + 1                                        // инвариант цикла: корзины 0 ..< i пусты
    }
    let dead = take table.buckets                        // все слоты A пусты: область освобождается с концом dead
    table.size = 2 * BUCKETS                             // поле из условия области пишется вместе с её заменой
    table.buckets = take fresh
}
```

Каждая запись в любой момент под одним якорем, в `A` или в `B`; переход — `tie`, указатели на записи действительны: таблица вместе с областью корзин — одна
[структура](layout/pointers.md#структура-источник-чистота). Инвариант «запись
в цепочке своей корзины» внутри функции нарушен и восстановлен на выходе.

**Где нужен Z3.** Нелинейные выражения (`slots.count == PAYLOAD / SIZES[sizeClass]`), порядок по всей структуре, сумма
или перестановка узлов, инвариант, связывающий две цепочки, и поле вида, сдвинутое в несохраняющую сторону.

**Инвариант с головой, зависящей от переменной.** «Запись входит в цепочку своей корзины»
(`forall e in entries: entries.chain(from: buckets[e.home].head, by: Entry.next, until: null).contains(e)`) доказывается для произвольной
корзины `i` в два случая. При `i == b` это корзина, которую операция изменила: вставка `e` требует
`e.home == b`. При `i != b` цепочка корзины не изменена. Корзина произвольная, поэтому инвариант верен для всех.
FLOW сегодня отслеживает цепочку только с одной постоянной головой
([нерешённые вопросы](layout/open-questions.md#открытые-вопросы)).

## Итог

| Структура | Где доказательство | Окрестность события | Что нужно FLOW |
|---|---|---|---|
| односвязный список | в структуре | голова и узел | есть |
| двусвязный список | смешанное, один указатель | три узла | инвариант `next!.prev` на событии |
| дерево с родителем | смешанное, один указатель | три узла | условие результата поворота, рекурсия по якорям |
| пара | смешанное, один указатель | два узла | вывод предусловия |
| кольцо | смешанное | два соседа | — |
| граф с исходящими | в коде | весь реестр, типовой проход | привязка рёбер к графу, инвариант прохода |
| граф со входящими | смешанное | две цепочки узла | однородность цепочек, цепочка с параметром |
| произвольный граф, узел освобождает функция | в коде | весь реестр рёбер | инвариант полноты реестра и `forall` по множеству, инвариант прохода, перечень держателей |
| граф с владением по рёбрам | только факты правила 5 о записи якоря | путь любой длины | — |
