# Сырая память: `Pointer` и приведение `as`

[Управление памятью](index.md) · [Layout](layout-reference.md) ·
[Allocator](allocator.md) · [Структуры](../structs.md)

Статус: нормативная модель. Amber реализует её по частям
(S74): пул блоков, области и таблицы, системные вызовы. Полный пример — аллокатор блоков
и классов размеров, записанный в этой модели. Системные вызовы описаны в
[отдельном файле](system.md).

Нетипизированную память в Efen называет тип `Pointer`. Методов у него нет. Его отдаёт и принимает контракт
[аллокатора](allocator.md) и контракт `System`, а типизированный доступ к памяти даёт только приведение `as`.
Остальные операции над `Pointer`: выдача диапазона `lend`, чтение адреса `address` и проверка `isAligned`
([ниже](#выдача-частей-памяти-lend)). Приведение утверждает, что память эквивалентна типу `T`, и это утверждение
доказывает компилятор. Если доказать нельзя, программа не компилируется. Какие поля приведение записывает, определяет
справочник ([создание элемента](layout-reference.md#выделение-и-освобождение--переход-между-множествами), правила 3–5).

## `Pointer`

`Pointer` — владеющий адрес памяти без типа. Его нельзя скопировать. Компилятор
знает о каждом `Pointer` размер памяти, её выравнивание и происхождение: из какого
системного вызова или из какого слота она взята. В памяти `Pointer` занимает одно
машинное слово.

`Pointer` не дженерик: `Pointer<T>` нет. Типизированный доступ к памяти даёт
только приведение к структуре.

Память выделяют и освобождают системные вызовы, например отображение страниц ОС.
Внутри `layout` других источников `Pointer` нет, кроме стирания элемента: `slot as Pointer`;
такой `Pointer` помнит слот, из которого взят.

## Приведение `as`

`p as T` утверждает: память `p` эквивалентна `T`. Компилятор проверяет:

1. размер памяти не меньше `sizeOf(T)`; памяти больше — можно, меньше — ошибка
   компиляции;
2. выравнивание памяти не меньше `alignOf(T)`;
3. у этой памяти нет другого живого вида.

После `let b = a as T` имя `a` больше не используется: одну память не описывают
два несовместимых типа.

Приведение записывает поля, названные в его аргументах, и поля со значением по умолчанию. Остальные поля нового вида
не инициализированы, и чтение такого поля до записи вызывает ошибку компиляции
([создание элемента](layout-reference.md#выделение-и-освобождение--переход-между-множествами), правила 3 и 4).

```efen
let block = memory as Block        // память эквивалентна Block; поля без значения по умолчанию не записаны
block.Header = Header(kind: .free) // поля пишет программа
```

Формы приведения различаются только источником доказательства:

| Форма | Доказательство |
|---|---|
| `memory as Block` из `Pointer` | размер, выравнивание и происхождение `memory` |
| `spare as LargeBlock` из `FreeBlock` | оба встраивают `Block` первым полем; владеющие поля старого вида пусты |
| `spare as SlotBlock(slots: Slot(size: s))` | эквивалентность разметки, леммы ниже |
| `slot as Pointer` | стирание: элемент принадлежит тому, кто приводит |
| `(address(m) & ~(BLOCK - 1)) as read<pool> Blocks.Item` | маску компилятор сверяет с `@align(BLOCK)` и вложенностью области, а недоказанная сверка требует `assume`; что адрес указывает в элемент множества и что элемент принадлежит структуре `pool`, принимается без доказательства: точка доверия ([указатель вне layout](layout-reference.md#указатели-вне-layout)) |

Сужения приведением нет. После проверки поля, которое называет вид (`block.kind == .large`), инварианты вида верны по
условию множества, и значение передаётся как `LargeBlock` без приведения
([условие вида](layout-reference.md#53-условие-вида), правило 2).

Слова «блок становится большим» к `as` не относятся. Память остаётся той же; меняется
тип, которым программа её описывает.

## Выравнивание `@align`

`@align(N)` на структуре задаёт её выравнивание, на поле — смещение поля, кратное
`N`.

```efen
@align(BLOCK)
struct Block {
    Header
    @align(LINE) area bytes: Byte
}
```

`p.alignment == N` в условии значит: адрес `p` кратен `N`. Память, выровненная сильнее, этому условию тоже
удовлетворяет: `System.map(bytes:aligned:)` с `aligned: PAGE` может вернуть адрес, кратный `BLOCK`.

```efen
fn smallSlot(pool: mut Pool, size: Int) -> own Pointer?
    ensures result == null || (result.size >= size && result.alignment == 16)
```

Шаг структуры, которая кончается полем `area`, равен её `@align`, как в C.

## Встраивание первым полем — наследование по началу

Голое имя структуры первым полем — наследование по началу: память наследника
начинается с памяти предка, поэтому приведение наследника к предку и одного
наследника к другому доказывается устройством структур.

```efen
struct FreeBlock {
    Block
    invariants { kind == .free }
}

struct LargeBlock {
    Block
    invariants {
        kind == .large
        offset >= LINE
    }
}
```

`FreeBlock` и `LargeBlock` описывают одни и те же байты: тот же `Header`, та же
область. Различаются они условиями. Встраивающий вид наследует условия встроенного: строки `invariants` у `Block`
верны и у `FreeBlock`, и повторить такую строку у наследника — ошибка. Методов и таблицы виртуальных функций у
структур нет, так что наследование по началу касается только памяти.

## Условия вида

Строки [`invariants`](../conditions.md#условия-значений-и-invariants) структуры — условия, которые выполняются у
каждого её значения. Условие на поле заголовка связывает вид с этим полем:

- в `LargeBlock` всегда `kind == .large`, поэтому у `Block` с `kind == .large` другого вида быть не может. После
  проверки `block.kind == .large` значение передаётся как `LargeBlock` без приведения: инварианты вида даёт строка
  `value.kind == .large ==> value is LargeBlock` в условии множества
  ([условие вида](layout-reference.md#53-условие-вида), правило 2);
- поле, которое называет вид (здесь `kind`), пишут только функции смены вида;
  через `Block` и другие виды оно только читается. Иначе одно имя давало бы два
  вида.

Условие вида над областью `x` называет, кроме полей:

- `x.count` — число слотов области;
- `x.size`: размер области в байтах; то же число даёт `sizeOf(x)`;
- `sizeOf(x.Item)` — размер одного слота в байтах;
- `extent` — размер памяти, из которой значение приведено (`size` исходного `Pointer`), в байтах от начала вида;
  у всех видов одних байтов он один;
- `x.taken` — множество номеров слотов, выданных сейчас ([иерархия владения](#что-значит-own-блока)):
  `x.taken.count`, `x.taken.isEmpty`, `x.taken.contains(k)`. `x.taken.count` считает слоты: диапазон из `n` слотов
  добавляет `n`;
- цепочки и призрачные поля вида — например, цепочка свободных слотов ([ниже](#цепочка-свободных-мест)).

Строка может быть `forall k in a ..< b: P` и `if c { P }` (импликация), как в
[инвариантах `layout`](layout-reference.md#инварианты). Строку с `forall` показывает
[цепочка свободных слотов](#цепочка-свободных-мест). Условие с одним неравенством:

```efen
struct Arena {
    var top: Int = 0 { value >= 0 }
    @align(16) area bytes: Byte

    invariants { top <= bytes.count }
}
```

Байты арены до `top` отданы кусками, следующий кусок начинается с `top` ([арена](#арена)).

Условия вида приносят: параметр `own V` и `mut V` на входе функции и значение, взятое из владеющего поля (`take
shelf.pool`). Значение, только что приведённое из памяти (`memory as V`), условий не несёт: у него пусто `x.taken`,
известны поля, записанные после приведения, и число слотов, которое даёт размер памяти. Имя (`Blocks.Item`, поле без
`own`) условий тоже не несёт; их даёт строка `value is V` множества после проверки метки
([инварианты и цепочки](layout-reference.md#инварианты)).

Каждое значение вида, которое функция получила или создала приведением и не отдала, снова удовлетворяет условиям
вида в каждой [точке восстановления](../conditions.md#когда-условие-проверяется): вызванная функция и вызывающий
полагаются на них.

**Поле раскладки** — поле, через которое строка условия задаёт число слотов или размер слота: `x.count == E` или
`sizeOf(x.Item) == E`, где поле входит в `E`. Его пишут, только пока `x.taken` пуст: иначе номера выданных слотов
начали бы означать другие байты. После записи область разложена заново, и строка верна с новым значением.
Неравенство (`top <= bytes.count`) полем раскладки поле не делает.

Память вида вмещает его области: смещение области плюс `x.count · sizeOf(x.Item)` не больше `extent`.

## Поле `area` и параметр `size`

`area x: T` последним полем структуры — область элементов `T`. Её длина в
объявлении неизвестна; её задаёт приведение особым параметром `size` — полным
размером структуры. Область получает остаток, отсчитанный от смещения своего поля.

```efen
struct Slot {
    var next: UInt16 = NONE
    var key: UInt = SLOT_KEY
    area rest: Byte
}

struct SlotBlock {
    Header
    @align(LINE) area slots: Slot
}

let block = spare as SlotBlock(slots: Slot(size: s))
```

Здесь `s` — полный размер одного слота: `rest` получает `s - 16` байт. Число слотов
компилятор выводит: сколько слотов по `s` байт помещается в память блока. Без
`size` область получает всю память до конца исходного `Pointer`.

Выражение `block.slots[i]` компилятор понимает так же, как индекс массива: адрес
слота равен `LINE + i·s`, граница — число слотов.

Структура слота может задать свой размер сама: её инвариант связывает число слотов её последней области с её
же полем (`text.count == length`). Область таких слотов называется областью с разным шагом. Параметр `size` в
приведении и инвариант `sizeOf(x.Item) == E` для неё вызывают ошибку. Номером слота служит смещение его начала
в байтах, поэтому адрес `x[k]` равен адресу области плюс `k`, и о каждом `k` доказано, что с него начинается
слот. Условия называют ещё три имени: `sizeOf(x[k])`, размер слота `k`; `x.extent`, число байтов области,
занятых слотами; `x.starts`, начала слотов. Число `x.count` у такой области находит обход. Имя `x.extent` относится
к области, а `extent` без области по-прежнему называет размер памяти вида ([условия вида](#условия-вида)). Память
вида вмещает такую область: смещение области плюс `x.size` не больше `extent`, а `x.extent` не больше `x.size`.
Правила перечисляет
[справочник `layout`](layout-reference.md#область-с-разным-шагом).

## Цепочка свободных слотов

Свободные слоты блока связаны номерами: поле вида хранит номер первого, поле элемента — номер следующего. Условие
вида называет эту [цепочку](../conditions.md#цепочка) и пишет инварианты о её слотах:

```efen
struct SlotBlock {
    Header                                  // used, frontier, firstFreeSlot, kind
    @align(LINE) area slots: Slot

    invariants {
        frontier <= slots.count
        forall k in frontier ..< slots.count: !slots.taken.contains(k)

        let freeSlots = slots.chain(from: firstFreeSlot, by: Slot.next, until: NONE)
        forall k in freeSlots: 0 <= k && k < frontier && !slots.taken.contains(k)
        freeSlots.count == frontier - slots.taken.count
    }
}
```

Строки по порядку: выше границы слоты ещё не выдавались; `freeSlots` — слоты от `firstFreeSlot` по `next` до `NONE`;
каждый из них свободен и ниже границы; их столько же, сколько всех невыданных ниже границы. Повторов в цепочке нет,
значит, невыданные слоты ниже границы `frontier` — ровно слоты цепочки. Призрачных строк в коде нет: снятие головы
и возврат в голову компилятор видит по записям `firstFreeSlot` и `next` и сам знает, какие слоты теперь на цепочке.

`firstFreeSlot` и `frontier` — целые `var` вида, `Slot.next` — поле элемента. Вне смены вида граница только растёт на
единицу, а начало цепочки меняется только снятием (`firstFreeSlot = slots[k].next` при `k == firstFreeSlot`) и
возвратом (`slots[k].next = firstFreeSlot`, затем `firstFreeSlot = k`).

Строки с `freeSlots` при выполнении не вычисляются. Недоказанная строка вызывает ошибку компиляции
([чего инварианты не задают](layout-reference.md#54-чего-инварианты-не-задают)), а проверка границы у `lend`
остаётся в программе.

## Эквивалентность разной разметки одних байтов

`SlotBlock` не встраивает `Block`, но размечает те же байты. Приведение `FreeBlock`
к `SlotBlock` законно, только если компилятор докажет леммы:

| № | Утверждение |
|---|---|
| Э1 | область слотов начинается там же, где область байтов (`LINE`) |
| Э2 | слот вмещает свои поля: `s >= offsetOf(Slot.rest)` |
| Э3 | `slots.count · s <= bytes.count` |
| Э4 | слот `i` занимает ровно `bytes[i·s ..< (i+1)·s]` |
| Э5 | слоты не пересекаются |
| Э6 | каждый слот выровнен на `alignOf(Slot)` |
| Э7 | хвост `bytes[slots.count·s ..< bytes.count]` не теряется: вид помнит размер исходной памяти и при следующем приведении отдаёт её целиком |

Если `s` берётся из постоянной таблицы, Э2 и Э3 проверяются перебором её значений.

## Смена вида — отдельная функция

Смена вида блока записывается функцией: на входе один вид, на выходе другой. Внутри
— приведение и запись полей, которые называют новый вид; условия нового вида
компилятор доказывает к `return`.

```efen
fn toLargeBlock(spare: own PoolBlock, offset: Int) -> own LargeBlock {
    let block = spare as LargeBlock
    block.Header = Header(kind: .large, offset: offset)
    return block
}
```

Старый вид пришёл как `own` и дальше не используется. Сменить вид нельзя, пока из
областей вида выдан элемент; у `own` такого не бывает (правило `own` ниже). Владеющие
указатели старого вида, которых новый не держит, должны быть пусты в точке приведения:
взяты `take` или проверены `== null`. Через вызов это не передаётся: `own FreeBlock`
говорит, что указатель пуст либо занят, поэтому смена вида берёт `own PoolBlock`, вид
блока пула без указателей (`struct PoolBlock { Block } { bytes.count == PAYLOAD }`), а
функция, которая забрала указатель, сама приводит блок к `PoolBlock`.

## Вид и имя элемента

Вид блока отдаёт имя своего элемента множества: значение вида можно записать в поле типа
`Blocks.Item?`, и тогда записывается только адрес, а вид не поглощается. Владеющее поле хранит само `own`, а не
адрес. Поле объявлено с типом множества, а вид его цели называет строка `invariants`
([виды элемента](layout-reference.md#виды-и-приведение-as), правило 4):

```efen
struct Pool {
    var classes: own Classes.Area? = null { value == null || value.count == CLASSES }
    var firstFreeBlock: own Blocks.Item? = null
    invariants { firstFreeBlock: FreeBlock? }      // цель поля имеет вид FreeBlock
}

pool.firstFreeBlock = toFreeBlock(block, next: take pool.firstFreeBlock)
let spare = take pool.firstFreeBlock!  // приведения нет: поле уточнено до FreeBlock
```

## Возврат памяти

Особой инструкции возврата нет. Элемент возвращается в свой слот через `take`
(раздел ниже); блок — функцией, которая берёт его параметром `own` и кладёт во владеющее
поле:

```efen
fn releaseBlock(pool: mut Pool, block: own PoolBlock) {
    pool.firstFreeBlock = toFreeBlock(block, next: take pool.firstFreeBlock)
}
```

## Иерархия владения

`layout` описывает отношения между множествами зон памяти, и владение следует этим отношениям. Уровней три:

1. байтами блока от отображения ОС до его возврата владеет владеющее поле: цепочка пула или цепочка класса
   размеров. Множество `Blocks` только называет тип указателя;
2. блок: значение `own FreeBlock`, `own SlotBlock` и т. п. даёт право читать и писать блок через вид и менять вид.
   Оно хранится в переменной, параметре или владеющем поле (`firstFreeBlock`);
3. элемент области блока: значение `own block.slots.Item`. Оно принадлежит тому, кому элемент выдан.

Правило одно для всех уровней: родитель с выданным элементом остаётся у своего владельца, но вернуть или
освободить родителя нельзя, пока элемент не возвращён. Блоком с выданными слотами владеет цепочка якорей его
класса размеров. Ниже правило записано через типы и `take`.

### Что значит `own` блока

`own V` означает: из областей `V` не выдан ни один элемент, и владеющие поля, уточнённые видом,
пусты либо заняты своим значением. Для каждой области `x` компилятор ведёт `x.taken`:
множество номеров выданных слотов. Это призрачное значение, как число занятых слотов у владельца области ([множества и области](layout-reference.md#множества-и-области)); при
выполнении его нет. Поле учёта связывается с ним условием вида явно:

```efen
struct SlotBlock {
    Header
    @align(LINE) area slots: Slot

    invariants {
        kind == .slots
        used == slots.taken.count          // связь поля учёта с выданными слотами
        linked ==> used > 0                // в списке класса — только блоки с выданными слотами
        next: anchor SlotBlock?            // цепочка класса владеет следующим блоком
        prev == null || prev! is SlotBlock // невладеющий указатель на предыдущий блок цепочки
    }
}
```

Блок с выданными слотами всегда записан в одну из двух цепочек якорей своего класса. Список класса (`linked`)
связывает блоки, в которых есть свободные слоты. Цепочка заполненных блоков связывает блоки без свободных слотов.
Обе цепочки идут по полю `next` и владеют своими блоками; поле `prev` только указывает.

Отсюда `own SlotBlock ⇒ used == 0`. Поле учёта пишут только разностью (`used + 1`, `used - 1`)
и только через вид, который его связал; абсолютная запись допустима в функции смены вида.
Через `Block`, `Blocks.Item` и другие виды поле читается.

### Выдача: `lend` элемента

`lend block.slots[k]` даёт `own block.slots.Item` — владеющий типизированный адрес слота `k`.
Байты не переносятся: структура, кончающаяся `area`, размера в объявлении не имеет, значением
быть не может и `Movable` не является, поэтому слот отдаёт единственное, что у него есть, —
адрес. Слот `k` входит в `slots.taken`. Условия:

- слот `k` ещё не выдан. Доказательством служит условие вида (`k` снят с цепочки свободных или
  `k == frontier`), а в отладочной сборке ещё и проверка метки слота;
- источник — `own` блока либо имя с условием `used > 0`.

Первая выдача из `own` делает владение неисключительным: дальше значение имеет тип `anchor SlotBlock`, так же как
права любого имени сужаются после передачи `own` ([владение](../types/ownership.md), «уточнение типа в точке
программы»). Владелец у блока остаётся, и переносит блок теперь `tie`. До выхода функция записывает блок в цепочку
якорей класса, и блок принадлежит пулу, пока не вернётся последний слот. Построить `own` блока с выданным элементом
нельзя: обратно к `own` ведёт приведение `as own` при `used == 0`
([выдача и возврат слота](layout-reference.md#выдача-и-возврат), правило 5).

```efen
fn acquireSlot(entry: mut Classes.Item, block: mut SlotBlock) -> own Pointer
    requires block.used > 0
{
    var k: Int
    if block.firstFreeSlot != NONE {
        k = Int(block.firstFreeSlot)
        block.firstFreeSlot = Int(block.slots[k].next)   // k снят с цепочки: не выдан
    } else {
        k = Int(block.frontier)                // k >= frontier: не выдан
        block.frontier = block.frontier + 1
    }
    let slot = lend block.slots[k]         // k входит в slots.taken
    block.used = block.used + 1            // Δused == +1 == число выдач
    if block.firstFreeSlot == NONE && Int(block.frontier) == block.slots.count { unlinkBlock(entry, block) }
    return slot as Pointer                 // стирание; Pointer помнит происхождение
}
```

`unlinkBlock` переносит блок без свободных слотов из списка класса в цепочку заполненных блоков того же класса
(`tie` из одной цепочки в другую). `relinkBlock` переносит блок обратно, когда в нём появился свободный слот.

<a id="возврат-take-на-своё-место"></a>

### Возврат: `take` в свой слот

Номер слота элемента даёт compiler-known `area.index(element)`; формула (адрес минус начало
области, делённое на шаг) принадлежит компилятору, доказывать её не нужно. После
`block.slots[k] = take slot` слот `k` выходит из `slots.taken`, и его поля снова доступны.

```efen
fn releaseSlot(pool: mut Pool, entry: read<pool> Classes.Item, block: read<pool> SlotBlock,
               slot: own block.slots.Item)
    requires block.used > 0
    requires block.slots.taken.contains(block.slots.index(slot))
{
    let k = block.slots.index(slot)
    block.slots[k] = take slot             // байтов не копирует: slot и есть слот k
    block.slots[k].next = UInt16(block.firstFreeSlot)
    block.firstFreeSlot = k                // k встал в голову freeSlots
    block.used = block.used - 1            // Δused == −1 == число возвратов
    if block.used > 0 {
        if !block.linked { relinkBlock(entry, block) }
        return
    }
    let cut = detachBlock(pool, entry: entry, block: block)   // anchor SlotBlock: блок вырезан из своей цепочки класса
    let spare = cut as own SlotBlock       // used == 0, указателей на блок в цепочке нет
    if entry.reserve == null { entry.reserve = take spare; return }
    releaseBlock(pool, block: toPoolBlock(take spare))        // смена вида: releaseBlock принимает own PoolBlock
}
```

Вырезать блок из цепочки класса и вернуть его пулу значит вывести элемент из структуры. Поэтому функция получает
пул параметром `mut`, а класс и блок называет параметрами с источником `read<pool>`: право писать в них она берёт
из права на `pool` ([право на элемент](layout-reference.md#82-право-на-элемент), правило 5). `detachBlock` получает
`pool` по той же причине: блок уходит из структуры пула. Перед возвратом пулу блок меняет вид: `toPoolBlock`
приводит `own SlotBlock` к `PoolBlock`, виду без указателей
([смена вида](#смена-вида--отдельная-функция)).

### Блок после возврата последнего слота

Функция, которая вернула последний слот (`used` стало 0), вырезает блок из цепочки класса и получает якорь:
`detachBlock` переписывает `next` и `prev` соседей и возвращает `anchor SlotBlock`. Приведение `as own` превращает
якорь в `own`. Компилятор доказывает в этой точке два факта: выданных слотов нет (`used == 0`) и указателей на блок
в цепочке не осталось ([удаление элемента](layout-reference.md#переход-к-владению-as-own)). Блок с `used == 0` на
входе функции (запас класса, блок пула) в цепочках класса не состоит. Им владеет поле
(`entry.reserve`, `firstFreeBlock`), и получить его можно только через `take` поля. Что в
цепочках класса нет блока без выданных слотов, говорит инвариант `Class`; в Amber это отладочная проверка.

### Учёт на выходе функции

На каждом выходе Δ`used` равно числу выданных слотов минус число возвращённых в этой функции.
Функция, которая меняет `used`, сама выдаёт или принимает элементы; «посчитать за другого»
нельзя. Цикл с `take` требует инварианта по `taken`; пока такой цикл не нужен — см. «Не решено».

<a id="поля-взятого-элемента"></a>

### Поля выданного элемента

`block.slots[j].next` через имя допустимо для `j`, доказанно не входящего в `slots.taken` в этой точке: `j` снят с
цепочки в этой функции, только что возвращён или лежит там, где условие вида говорит, что слоты не выданы. Иначе
ошибка компиляции: памятью владеет получатель элемента.

### Один элемент: большой блок и отображение

У `LargeBlock` и `RunBlock` элемент один: хвост области. Его выдаёт
`let payload = lend block.bytes[offset - LINE ..< block.bytes.count]`. Учёт ведёт то же поле:
`used <= 1; (used == 0) == bytes.taken.isEmpty`. Выдача делает владение блоком неисключительным, и блок остаётся у
своего владельца. Возврат пишется тем же диапазоном: `block.bytes[a ..< b] = take payload`, где
`a == block.bytes.index(payload)`.

### Выдача и возврат диапазона

Слоты области выдаются и диапазоном. `lend block.bytes[a ..< b]` даёт значение типа `own block.bytes.Item` на слоты
`a ..< b` и добавляет их все в `bytes.taken`; ни один из них до этого не выдан. В результате функции, где родитель
вызывающему не виден, тип пишется через структуру: `own Block.bytes.Item`. Возврат пишется тем же диапазоном:
`block.bytes[a ..< b] = take p`, где `a == block.bytes.index(p)`, а `b - a` равно числу слотов `p`. Все слоты
диапазона выданы, и после возврата они выходят из `bytes.taken`. Возврат забывает значения полей слотов: получатель
мог записать в них что угодно. `Pointer` из выданного диапазона не получается, поэтому до функции освобождения
менеджера памяти диапазон не доходит. Правила [выдачи частей памяти](#выдача-частей-памяти-lend) (выдачи группы
идут подряд, последняя поглощает владельца) относятся к `lend` у `Pointer`, не к выдаче слотов области.

### Тип элемента

`block.slots.Item` — сокращение origin-формы `own<block> SlotBlock.slots.Item`, той же, что у
других типов с origin. `block` — параметр или `let`-имя той же функции; аргумент в
этой позиции — имя. Это условие происхождения на пару значений, а не generic по runtime-значению
([типы со значением-параметром](../types/value-parameterized-types.md) допускают origin именно для этого). Два разных параметра — два
разных типа; `var` или временное выражение в этой позиции — ошибка.

### Стирание и восстановление

`slot as Pointer` стирает тип; `Pointer` помнит происхождение. Стирание выданного слота и обратное приведение пишет
только код `layout`. Обратное приведение `memory as block.slots.Item` называет родителя и служит точкой доверия: что
память составляет слот, выданный из этого родителя, компилятор принимает без доказательства
([указатель вне layout](layout-reference.md#указатели-вне-layout)). Проверочная сборка проверяет три факта: адрес
указывает в блок кучи, на начало слота, и слот выдан. Это относится к каждому возврату через контракт `Allocator`,
в том числе из Efen: `deallocate(memory: own Pointer)` происхождения параметра не знает.

### Владеющие указатели вида

`FreeBlock` уточняет `Header.next` до `own FreeBlock?`. Запись в такое поле подчиняется общим правилам владеющих
полей. Перед записью поле равно `null`
([создание элемента](layout-reference.md#выделение-и-освобождение--переход-между-множествами), правило 6). Право
называет таблица [`edit` и `mut`](layout-reference.md#edit-и-mut-в-layout): новый элемент в поле, равное `null`,
требует `edit`. Запись якоря принимается по доказательству, что цикла не возникает, или по выведенному предусловию
([перенос владения](layout-reference.md#64-перенос-владения), правило 5). Смена вида требует, чтобы владеющие поля
прежнего вида были равны `null`: иначе `as` вызывает ошибку, и остаток пула не теряется. Поле, которое добавляет
новый вид, после приведения не инициализировано.

### Арена

Арена в этом примере состоит из одного блока: структуры `Arena` из раздела [«Условия вида»](#условия-вида). Кусок
арены отдаётся заимствованием с источником `arena`, а не выдачей `lend`:

```efen
fn carve(arena: edit Arena, size: Int) -> edit<arena> [Byte]?
    requires size > 0
{
    guard size <= arena.bytes.count - arena.top else {
        return null
    }

    let piece = &arena.bytes[arena.top ..< arena.top + size]
    arena.top = arena.top + size
    return piece
}
```

`resetArena` начинает выдачу кусков заново: она пишет `arena.top = 0`, и байты прежних кусков после неё достаются
новым. Для компилятора это запись значения. Когда тело `resetArena` видно, её вызов ни один прежний кусок
недействительным не делает: что вызов меняет, решает сводка тела, а не слово в сигнатуре
([что делает ссылку недействительной](memory-rules.md#что-делает-ссылку-недействительной)). Прежний и новый кусок
тогда составляют два заимствования одного источника `arena` над одними байтами. Язык это допускает
([два доступа сразу](memory-rules.md#два-доступа-сразу)).

Арена, которая обещает, что после сброса прежние куски не используются, объявляет сброс в контракте без тела:
`mut fn reset`. Вызов через такой контракт проверяется по слову `mut`, и использование прежнего куска после него
вызывает ошибку ([функция без тела](layout-reference.md#85-функция-без-тела), правило 3).

```efen
let first = carve(arena, size: 8) ?? return
resetArena(arena)                         // тело видно: запись значения, first действителен
let second = carve(arena, size: 8) ?? return
first[0] = 1                              // допустимо: first и second заимствуют arena, байты у них общие
```

Из блока арены ничего не выдано `lend`: кусок служит заимствованием, а не выданным слотом.

## Обнулённая память: состояние `Pointer.Zeroed`

Обнулённость памяти — явное свойство, компилятор её отслеживает. Правила проверки ниже — Amber S74.6i, в спецификации
typestate их нет (список в конце раздела).

У `Pointer` одна ось состояний:

```efen
state Content {
    initial Raw
    Zeroed
    Initialized
}
```

- `Raw` — о содержимом ничего не известно; голый `Pointer` означает `Pointer.Raw`;
- `Zeroed` — вся память нулевая;
- `Initialized` — пометка, что в память уже записано что-то полезное; компилятор её не проверяет и ничего из неё не
  выводит.

Состояние пишется в типе параметра или результата функции, короткой формой `Pointer.Zeroed` (у типа одна ось) или
полной `Pointer.Content.Zeroed`:

```efen
fn map(bytes: Int, aligned: Int) -> own Pointer.Zeroed?
    requires bytes % PAGE == 0
    ensures result == null || (result.size == bytes && result.alignment == aligned)

fn fill(memory: own Pointer.Zeroed, bytes: Int)
    requires memory.size == bytes && memory.alignment == 4096

fn keep(some: own Pointer.Zeroed?)
```

Компилятор доказывает и выдаёт только `Zeroed`:

1. Результат `Pointer.Zeroed` доказывается на каждом `return`; вызывающий получает нулевую память. У такого результата
   обязательны условия `size` и `alignment` в `ensures` ([условия функций](../conditions.md)).
2. Параметр `Pointer.Zeroed` считается нулевым при входе и доказывается на каждом вызове. Аргумент `null`
   необязательного параметра подходит; привязка `guard let m = take some` получает состояние `some`.
3. Параметр `Pointer`, `Pointer.Raw` или `Pointer.Initialized` принимает любую память, нулевую тоже. Результат
   `Pointer.Initialized` может вернуть нулевую память, но вызывающий нулей не получает.
4. Нули дают `@asm`-функция (`memory is Pointer.Zeroed` в условии её результата, см. [системные вызовы](system.md)),
   результат или параметр `Pointer.Zeroed`, проверка `isAligned` и выдача у нулевого владельца.
5. Имя, которому в теле функции присваивается другое значение, нулей не несёт; параметр после присваивания теряет и
   размер.
6. Состояние не выводится через сигнатуру: голый `Pointer` в сигнатуре не обещает нулей, даже если тело их доказывает.
7. Переопределение метода и реализация `@platform` указывают те же состояния, что исходная функция и контракт.

Состояние пишется только в типе параметра (`own` или только чтение) и результата функции. Поле layout, тип переменной,
цель `as`, поле `variant`, элемент массива, параметр `mut` или `edit` — ошибка компиляции. Проверка `m is
Pointer.Zeroed` в коде тоже ошибка: при выполнении нули не проверяются.

Приведение допустимо при любом состоянии памяти и от состояния не зависит. Поле без значения по умолчанию после
приведения не инициализировано, и чтение до записи вызывает ошибку
([создание элемента](layout-reference.md#выделение-и-освобождение--переход-между-множествами)). Вид, приведённый из
нулевой памяти, тоже записывает каждое поле до первого чтения или называет его инициализатором `_`: так проверка не
зависит от того, откуда пришла память.

Нет в [typestate](../types/typestate.md), добавить при утверждении:

- состояние в типе параметра и результата (там есть только `state` у получателя метода);
- состояние встроенного типа и сама ось `Pointer.Content`;
- `is State` как условие результата `@asm`-функции;
- упорядоченные состояния вместо взаимоисключающих: `Zeroed` подходит туда, где ждут `Raw` или `Initialized`;
- запрет вывода состояния `Pointer` через сигнатуру.

## Область layout: `area` и `set area`, число элементов у переменной

Статус: строки `area` и `set area` описаны в [множествах и областях](layout-reference.md#множества-и-области). Строка
объявляет только тип элемента, а число элементов указывает переменная, которая хранит область. Правила приведения и
раздачи ниже относятся к Amber S74.8c и S74.6g.

Строка области в `layout` объявляет только тип элемента:

```efen
layout {
    set area Blocks: Block {
        value.kind == .slots ==> value is SlotBlock      // условие множества: после проверки метки верны инварианты вида
        value.kind == .large ==> value is LargeBlock
    }
    area Classes: Class

    struct Class {
        var size: Int = 0
        var firstAvailable: anchor Blocks.Item? = null    // список класса: блоки со свободными слотами
        var firstFull: anchor Blocks.Item? = null         // цепочка заполненных блоков
        var reserve: own Blocks.Item? = null              // запас класса: блок без выданных слотов

        invariants {
            let available = Blocks.chain(from: firstAvailable, by: Header.next, until: null)
            let full = Blocks.chain(from: firstFull, by: Header.next, until: null)
            forall b in available: b.linked && b.used > 0
            forall b in full: !b.linked && b.used > 0
        }
    }

    struct Pool {
        var classes: own Classes.Area? = null { value == null || value.count == CLASSES }
        var firstFreeBlock: own Blocks.Item? = null
        invariants { firstFreeBlock: FreeBlock? }
    }
}
```

Инварианты `Class` называют обе владеющие цепочки. В каждой состоят только блоки с выданными слотами, а поле
`linked` говорит, в какой из двух цепочек блок находится. Вторая владеющая цепочка новых полей не требует: обе идут
по `next` и `prev` заголовка.

`Classes.Area` — чистый указатель на начало области, одно машинное слово; ёмкость он не хранит
([области](layout-reference.md#множества-и-области)). Число элементов — уточнение переменной, сразу после её
типа, по форме [уточнённых типов](../types/refinement-types.md):

```efen
let table: Classes.Area = memory as Classes.Area { value.count == CLASSES }
```

- у необязательного поля — `{ value == null || value.count == N }`, у остальных — `{ value.count == N }`;
- `N` — число, имя константы или неизменяемое имя функции (`let`, параметр); у поля — другое поле той же
  структуры (`value.count == capacity`), и тогда запись этого поля без замены области — ошибка. Две переменные с
  одним значением числа держат область одного типа, с разными — разных типов;
- приведение к области бывает только начальным значением такой переменной и только из `Pointer`;
- переменная без записанного типа берёт тип начального значения: `if let table = take pool.classes`;
- область без числа — тип параметра, результата, поля или переменной — ошибка компиляции.

Шаг элемента — `sizeOf(Class)`. Приведение `memory as Classes.Area` поглощает `Pointer`. Компилятор доказывает:

1. размер памяти не меньше `count · sizeOf(E)` для `area` и равен ему для `set area`: в нём каждый байт принадлежит
   элементу;
2. выравнивание не меньше `alignOf(E)`;
3. элементы не читаются до записи.

Элементы `area` — значения. `table[i].size = 16` пишет поле элемента `i`, `table[i] = Class(size: 16)` — элемент целиком.
Индекс доказан в границах `0 ..< count` или проверяется при выполнении. Поля элемента — любые типы, в том числе параметр `T` у `layout`, `own`-область и якоря
элементов других множеств ([владение по множествам](layout-reference.md#множества-и-области)); владеть частью той же области
элемент не может. Пока якорь слота не пуст, слот нельзя перезаписать целиком, а область — освободить.

Стирание `table as Pointer` возвращает память без вида; размер, с которым её брали, FLOW помнит как факт о
значении, и `unmap` доказывает по нему своё условие `memory.size == bytes`.

Элементы `set area` не индексируются: множество областей раздаётся целиком циклом ниже.

## Поле-область: доступ на месте `!`

Статус: правило справочника ([множества и области](layout-reference.md#множества-и-области),
[слоты области](layout-reference.md#частичная-инициализация-и-очистка)); в Amber сделано шагом S74.8c1b.

Владеющее поле `var classes: own Classes.Area? = null { value == null || value.count == CLASSES }` хранит область. `pool.classes![i].size` читает и пишет элемент на
месте: поле не забирается, `!` утверждает, что оно не пусто. Пустое поле останавливает программу при выполнении.

```efen
fn countUse(pool: mut Pool, index: Int) {
    if index >= 0 && index < CLASSES {
        pool.classes![index].used = pool.classes![index].used + 1
    }
}
```

`!` после поля пишется только перед `[`. В индексе и в правой части такой записи вызова нет: вызов мог бы забрать
поле, пока доступ к нему открыт.

## Раздача набора: `for element in take region`

Статус: правило справочника ([выдача и возврат слота](layout-reference.md#выдача-и-возврат), правило 7); в Amber
сделано шагом S74.8c3. Форма повторяет `for x in take v` у коллекций.

```efen
fn growPool(pool: mut Pool) -> Bool {
    let memory = System.map(bytes: REGION_BLOCKS * BLOCK, aligned: BLOCK) ?? return false

    let region: Blocks.Area = memory as Blocks.Area { value.count == REGION_BLOCKS }
    for element in take region {
        pool.firstFreeBlock = newFreeBlock(memory: take element, next: take pool.firstFreeBlock)
    }
    return true
}
```

Цикл поглощает набор и выдаёт его элементы по одному. Каждый `element` — `own Pointer` размером в шаг элемента,
выровненный по `alignOf(Block)`; тело обязано передать его дальше: привести, отдать владеющему параметру или полю.
Элемент, который тело оставило, — утечка, ошибка компиляции.

Выйти из такого цикла раньше нельзя: `break`, `continue` и `return` в его теле, в том числе во вложенном цикле, —
ошибки компиляции, а исключение из тела — утечка. Иначе элементы после точки выхода не достались бы никому.

## Выдача частей памяти: `lend`

Обрезка в `lend memory[a ..< b]` — как `map_aligned` в limelight-lang/model; `address` и `isAligned` — Amber S74.19b3.

Выдача делит память владельца на части без копирования:

```efen
let skip = (aligned - address(memory) % aligned) % aligned
let head = lend memory[0 ..< skip]
let block = lend memory[skip ..< skip + bytes]
let tail = lend memory[skip + bytes ..< total]
System.unmap(memory: take head, bytes: skip)
System.unmap(memory: take tail, bytes: total - skip - bytes)
guard block.isAligned(to: aligned) else {
    System.unmap(memory: take block, bytes: bytes)
    return null
}
return take block
```

- Выдачи одной группы идут подряд, и их границы после выдачи не меняются. Последняя кончается на размере владельца и
  поглощает его.
- Выданную часть код отдаёт системе (`System.unmap`; длина проверяется при выполнении, а ноль байт обходится без
  системного вызова), читает её `address` и проверяет `isAligned`. Один `take` выданной части делает её владельцем.
- `address(memory)` читает адрес как `Int` и `Pointer` не поглощает.
- `guard x.isAligned(to: k) else { return null }` проверяет выравнивание при выполнении; после него компилятор знает,
  что `x` выровнен по `k`.

Выдача слота области, `lend block.slots[k]`, описана в разделе «Иерархия владения».

## Память, пришедшая из C

Голый адрес из C входит в Efen двумя путями. Первый: параметр `Pointer?` функции с пометкой `@abi(c)` и телом.
Второй: результат `-> own Pointer?` в объявлении функции C без тела; так объявлены функции ОС, например
`VirtualAlloc` ([системные вызовы](system.md#внешние-функции-abic)). Такое объявление служит точкой доверия, а
размер и выравнивание памяти называет его `ensures`. Остальные функции библиотек C отдают то, что записано в их
объявлении: объект класса над внешним значением, `CString`, ссылку с источником-хендлером
([библиотеки на C](../foreign.md#доверие-и-проверочная-сборка)). Функцию `@abi(c)` с телом вызывает
только C; компилятор экспортирует её под своим именем. Из адреса блок находится маской по выравниванию блока, и это
единственное приведение целого к элементу множества:

```efen
@abi(c)
fn smallFree(memory: own Pointer?) {
    let found = take memory ?? return

    guard let pool = take Heap.pool else {
        halt()
    }

    let block = (address(found) & ~(BLOCK - 1)) as read<pool> Blocks.Item   // точка доверия: блок кучи pool
    guard block.kind == .slots else {                                        // дальше верны инварианты SlotBlock
        halt()
    }

    let slot = (take found) as block.slots.Item                             // точка доверия: слот выдан из block
    releaseSlot(pool, entry: pool.classes![block.sizeClass], block: block, slot: take slot)
    Heap.pool = take pool
}
```

После проверки `block.kind == .slots` инварианты вида `SlotBlock` верны по условию множества `Blocks`, и приведения вида
функции не нужно. Приведение адреса и восстановление слота пишет только код `layout`, поэтому функция стоит в
пакете `layout` менеджера памяти.

Функция записана для программы с одним потоком. Компилятор принимает, что C вызывает её в потоке этого контекста и
не одновременно с остальным его кодом ([структура и поток](layout-reference.md#структура-и-поток), правило 4). Тогда
`take Heap.pool` берёт кучу, из которой слот выдан, и приведение называет её верно. При куче на поток и вызове `free` из другого потока функция не выражается: блок
принадлежит куче потока, который выдал слот, а `take Heap.pool` берёт кучу вызывающего потока. Приведение назвало бы
не ту структуру, и возврат слота изменил бы цепочки чужой кучи. Как слот возвращается в кучу своего потока, не решено
([за пределами layout](layout-reference.md#чего-layout-не-описывает)).

- `@abi(c)` с телом пишет любой пакет. Её `Pointer` — голый `Pointer?`: без размера, выравнивания
  и состояния. Вызов из Efen и значение такой функции — ошибка.
- Внешняя функция без тела объявляет параметр `p: mut Pointer? = null` или `p: out Pointer? = null` только с этим
  умолчанием. Аргумент передать нельзя: C получает `NULL`, и ничего не записывается. Так объявлен лишний параметр
  деструктора `pthread_join(value: mut Pointer? = null)`
  ([внешние деструкторы](../disposable.md#внешние-деструкторы)). Результат `-> own Pointer?` такая функция
  объявляет свободно: это объявление без тела, которому компилятор верит по записи.
- Приведение `(address(m) & ~(BLOCK - 1)) as read<pool> Blocks.Item` пишет код `layout` множества `Blocks`. `BLOCK`
  называет выравнивание элемента этого множества, `m` называет значение, адрес которого функция читает, `pool`
  называет структуру, которой принадлежит элемент
  ([указатель вне layout](layout-reference.md#указатели-вне-layout)). Маску компилятор сверяет с `@align`; сверка,
  которую доказать не удалось, требует `assume`. Право на блок функция берёт из своего права на `pool`.
- Обратное приведение `(take found) as block.slots.Item` восстанавливает тип слота. Оно тоже принимается на веру
  ([стирание и восстановление](#стирание-и-восстановление)).
- Между вызовами C куча хранится в поле потока `thread var pool: own Pool? = null` класса (пишет любой пакет): у
  каждого потока своя куча. `Pool` не `ImplicitlyDestroyable`, поэтому такое поле служит точкой доверия:
  компилятор не доказывает, что к завершению потока куча освобождена. Деструктор класса её не освобождает: он
  выполняется для объекта, а не для потока
  ([ничего не теряется](layout-reference.md#74-ничего-не-теряется), правило 5). Функция `@abi(c)`
  берёт её (`take Heap.pool`) и кладёт обратно (`Heap.pool = take pool`) до выхода; другие функции её не называют.
- Обычная сборка проверяет заголовок найденного блока: вид, класс, `used > 0`, начало слота (`index`) и слот ниже
  границы нарезки. Двойное освобождение она не ловит, как и модель ред. 6.
- Отладочная сборка проверяет каждый адрес на входе, до чтения заголовка: это начало слота, выданного и ещё не
  возвращённого. Двойное освобождение, адрес внутри слота и чужой адрес дают отчёт с именем функции и узла.
- Не проверяется ни одной сборкой: повторное освобождение после того, как слот выдали снова.
- Сброс кучи, в которой остались блоки с выданными слотами, не описан. Блок с `used > 0` освободить нельзя, а
  без владельца он оставаться не может (см. «Не решено»).

## Порядок байтов

Если структура читает готовые байты, порядок которых не совпадает с порядком байтов
цели сборки, это ошибка компиляции.

## Не решено

Эти места модели пока описаны эскизом; синтаксис для них не утверждён:

- как отображение ОС, взятое не регионом, входит в множество блоков и выходит из него;
- условная компиляция отладочных проверок (`#if debug()` в спецификации нет);
- `own<block>` — origin-форма, у ссылок она есть, для `own` не записана;
- `x.index(element)` как имя, известное компилятору;
- цикл, который берёт несколько элементов: нужен инвариант по `taken`;
- происхождение `Pointer` через границу контракта (`tryAllocate -> own Pointer?`);
- одна куча на процесс: поле `static` бывает только `shared`-типа или неизменяемым, поэтому общая куча — `shared`-тип,
  который сам охраняет свои данные; его вид не записан. Общая куча — `shared`-тип с блокировкой и чистым `Pool`
  ([многопоточность](layout-reference.md#многопоточность)). Блок, освобождённый не тем потоком, который его выдал, пока
  не описан: `smallFree` выше верна только при вызове в потоке своего контекста;
- конец потока или сброс кучи, в которой остались блоки с выданными слотами: у такого блока нет владельца после
  конца потока, а освободить его нельзя;
- проверка адресов из C в отладочной сборке сделана в компиляторе, а в спецификации не описана;
- как отображение покидает множество блоков при `unmap`.

В список не входят правила, которые справочник уже описывает: уточнение поля видом, `next: own FreeBlock?`
([виды элемента](layout-reference.md#виды-и-приведение-as), правило 4), источник в приведении адреса
([указатель вне layout](layout-reference.md#указатели-вне-layout)), функция `@abi(c)` с телом
([структура и поток](layout-reference.md#структура-и-поток), правило 4) и точка доверия `thread var x: own T`
([ничего не теряется](layout-reference.md#74-ничего-не-теряется), правило 5). Что из них Amber уже проверяет, говорит
раздел [11.2](layout-reference.md#112-что-компилятор-проверяет-сегодня).
