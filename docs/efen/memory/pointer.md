# Сырая память: `Pointer` и приведение `as`

[Управление памятью](index.md) · [Компоновка и дескрипторы](addresses.md) ·
[Allocator](allocator.md) · [Структуры](../structs.md)

Статус: нормативная модель, решения Edmond от 2026-10-23. Amber реализует её по частям
(S74): пул блоков, области и таблицы, системные вызовы. Полный пример — аллокатор блоков
и классов размеров, записанный в этой модели. Системные вызовы описаны в
[отдельном файле](system.md).

Нетипизированная память в Efen — тип `Pointer`. Он живёт только внутри `layout`, у
него нет методов, и единственная операция над ним — приведение `as`. Приведение
ничего не пишет и не меняет при выполнении: это утверждение «эта память
эквивалентна типу `T`», которое доказывает компилятор. Если доказать нельзя,
программа не компилируется.

## `Pointer`

`Pointer` — владеющий адрес памяти без типа. Его нельзя скопировать. Компилятор
знает о каждом `Pointer` размер памяти, её выравнивание и происхождение: из какого
системного вызова или из какого места она взята. В памяти `Pointer` занимает одно
машинное слово.

`Pointer` не дженерик: `Pointer<T>` нет. Типизированный доступ к памяти даёт
только приведение к структуре.

Память выделяют и освобождают системные вызовы, например отображение страниц ОС.
Внутри `layout` других источников `Pointer` нет, кроме стирания элемента: `slot as Pointer`;
такой `Pointer` помнит место, из которого взят.

## Приведение `as`

`p as T` утверждает: память `p` эквивалентна `T`. Компилятор проверяет:

1. размер памяти не меньше `sizeOf(T)`; памяти больше — можно, меньше — ошибка
   компиляции;
2. выравнивание памяти не меньше `alignOf(T)`;
3. у этой памяти нет другого живого вида.

После `let b = a as T` имя `a` больше не используется: на одну память не смотрят
два несовместимых типа.

Приведение не записывает полей. Поле нового вида, которое программа ещё не
записала, читать нельзя: чтение до записи — ошибка компиляции.

```efen
let block = memory as Block        // память эквивалентна Block; ничего не записано
block.Header = Header(kind: .free) // поля пишет программа
```

Формы приведения различаются только источником доказательства:

| Форма | Доказательство |
|---|---|
| `memory as Block` из `Pointer` | размер, выравнивание и происхождение `memory` |
| `spare as LargeBlock` из `FreeBlock` | оба встраивают `Block` первым полем; владеющие поля старого вида пусты |
| `block as LargeBlock` из `Block` | условие вида: `kind == .large` (сужение) |
| `spare as SlotBlock(slots: Slot(size: s))` | эквивалентность разметки, леммы ниже |
| `slot as Pointer` | стирание: элемент принадлежит тому, кто приводит |
| `memory as block.slots.Item` | только в `@trusted`: на веру в обычной сборке, проверка в отладочной |

Слова «блок становится большим» к `as` не относятся. Память остаётся той же; меняется
тип, через который на неё смотрит программа.

## Выравнивание `@align`

`@align(N)` на структуре задаёт её выравнивание, на поле — смещение поля, кратное
`N`.

```efen
@align(BLOCK)
struct Block {
    Header
    @align(LINE) area bytes: Byte
}
```

Шаг структуры, которая кончается полем `area`, равен её `@align`, как в C.

## Встраивание первым полем — наследование по началу

Голое имя структуры первым полем — наследование по началу: память наследника
начинается с памяти предка, поэтому приведение наследника к предку и одного
наследника к другому доказывается устройством структур.

```efen
struct FreeBlock {
    Block
} {
    kind == .free
}

struct LargeBlock {
    Block
} {
    kind == .large
    offset >= LINE
}
```

`FreeBlock` и `LargeBlock` описывают одни и те же байты: тот же `Header`, та же
область. Различаются они условиями. Методов и таблицы виртуальных функций у
структур нет, так что наследование по началу касается только памяти.

## Условия вида

Блок `{}` после структуры задаёт условия, которые выполняются у каждого её значения.
Условие на поле заголовка связывает вид с этим полем:

- в `LargeBlock` всегда `kind == .large`, поэтому у `Block` с `kind == .large`
  другого вида быть не может, и `block as LargeBlock` доказано;
- поле, которое называет вид (здесь `kind`), пишут только функции смены вида;
  через `Block` и другие виды оно только читается. Иначе одно имя давало бы два
  вида.

Условия проверяются там, где значение создаётся или меняется: на `return` функции
смены вида и на выходе каждой публичной операции `layout`.

## Поле `area` и параметр `size`

`area x: T` последним полем структуры — область элементов `T`. Её длина в
объявлении неизвестна; её задаёт приведение особым параметром `size` — полным
размером структуры. Область получает остаток, отсчитанный от смещения своего поля.

```efen
struct Slot {
    var next: UInt16 = NONE
    var key: UInt = SLOT_KEY
    area rest: Byte
}

struct SlotBlock {
    Header
    @align(LINE) area slots: Slot
}

let block = spare as SlotBlock(slots: Slot(size: s))
```

Здесь `s` — полный размер одного слота: `rest` получает `s - 16` байт. Число слотов
компилятор выводит: сколько слотов по `s` байт помещается в память блока. Без
`size` область получает всю память до конца исходного `Pointer`.

Выражение `block.slots[i]` компилятор понимает так же, как индекс массива: адрес
слота равен `LINE + i·s`, граница — число слотов.

## Эквивалентность разной разметки одних байтов

`SlotBlock` не встраивает `Block`, но размечает те же байты. Приведение `FreeBlock`
к `SlotBlock` законно, только если компилятор докажет леммы:

| № | Утверждение |
|---|---|
| Э1 | область слотов начинается там же, где область байтов (`LINE`) |
| Э2 | слот вмещает свои поля: `s >= offsetOf(Slot.rest)` |
| Э3 | `slots.count · s <= bytes.count` |
| Э4 | слот `i` занимает ровно `bytes[i·s ..< (i+1)·s]` |
| Э5 | слоты не пересекаются |
| Э6 | каждый слот выровнен на `alignOf(Slot)` |
| Э7 | хвост `bytes[slots.count·s ..< bytes.count]` не теряется: вид помнит размер исходной памяти и при следующем приведении отдаёт её целиком |

Если `s` берётся из постоянной таблицы, Э2 и Э3 проверяются перебором её значений.

## Смена вида — отдельная функция

Смена вида блока записывается функцией: на входе один вид, на выходе другой. Внутри
— приведение и запись полей, которые называют новый вид; условия нового вида
компилятор доказывает к `return`.

```efen
fn toLargeBlock(spare: own PoolBlock, offset: Int) -> own LargeBlock {
    let block = spare as LargeBlock
    block.Header = Header(kind: .large, offset: offset)
    return block
}
```

Старый вид пришёл как `own` и дальше не используется. Сменить вид нельзя, пока из
областей вида взят элемент; у `own` такого не бывает (правило `own` ниже). Владеющие
ссылки старого вида, которых новый не держит, должны быть пусты в точке приведения:
взяты `take` или проверены `== null`. Через вызов это не передаётся: `own FreeBlock`
говорит, что ссылка пуста либо занята, поэтому смена вида берёт `own PoolBlock`, вид
блока пула без ссылок (`struct PoolBlock { Block } { bytes.count == PAYLOAD }`), а
функция, которая забрала ссылку, сама приводит блок к `PoolBlock`.

## Вид и имя элемента

Вид блока отдаёт имя своего элемента множества: значение вида можно записать в поле типа
`Blocks.Item?`, и тогда записывается только адрес, а вид не поглощается. Владеющее поле
(`firstFreeBlock: own FreeBlock?`) хранит само `own`, а не адрес:

```efen
var firstFreeBlock: own FreeBlock? = null

self.firstFreeBlock = toFreeBlock(block, next: take self.firstFreeBlock)
let spare = take self.firstFreeBlock!  // приведения нет: тип поля уже FreeBlock
```

## Возврат памяти

Особой инструкции возврата нет. Элемент возвращается на своё место через `take`
(раздел ниже); блок — функцией, которая берёт его параметром `own` и кладёт во владеющее
поле:

```efen
fn releaseBlock(block: own PoolBlock) {
    self.firstFreeBlock = toFreeBlock(block, next: take self.firstFreeBlock)
}
```

## Иерархия владения

Решение Edmond от 2026-10-24, уточнено после разбора и одобрено в тот же день.
`layout` описывает отношения между множествами зон памяти, и владение следует этим отношениям. Уровней три:

1. множество `Blocks` владеет байтами всегда, от отображения ОС до его возврата;
2. блок: значение `own FreeBlock`, `own SlotBlock` и т. п. — право смотреть на блок через вид
   и менять вид; его держит переменная, параметр или владеющее поле (`firstFreeBlock: own FreeBlock?`);
3. элемент области блока: значение `own block.slots.Item`; его держит тот, кому элемент выдан.

Правило одно для всех уровней: у родителя с выданным элементом владельца нет. Ниже оно
записано через типы и `take`.

### Что значит `own` блока

`own V` означает: из областей `V` не взят ни один элемент, и владеющие поля, уточнённые видом,
пусты либо заняты своим значением. Для каждой области `x` компилятор ведёт `x.taken` —
множество номеров взятых мест. Это ghost-значение, как `Items.count` в [компоновке](addresses.md); при
выполнении его нет. Поле учёта связывается с ним условием вида явно:

```efen
struct SlotBlock {
    Header
    @align(LINE) area slots: Slot
} {
    kind == .slots
    used == slots.taken.count          // связь поля учёта с взятыми местами
    linked ==> used > 0                // в списке класса — только блоки с выданными слотами
    next: SlotBlock?                   // имена, не владельцы
    prev: SlotBlock?
}
```

Отсюда `own SlotBlock ⇒ used == 0`. Поле учёта пишут только разностью (`used + 1`, `used - 1`)
и только через вид, который его связал; абсолютная запись допустима в функции смены вида.
Через `Block`, `Blocks.Item` и другие виды поле читается.

### Выдача: `take` элемента

`take block.slots[k]` даёт `own block.slots.Item` — владеющий типизированный адрес места `k`.
Байты не переносятся: структура, кончающаяся `area`, размера в объявлении не имеет, значением
быть не может и `Movable` не является, поэтому место отдаёт единственное, что у него есть, —
адрес. Место `k` входит в `slots.taken`. Условия:

- место `k` ещё не взято; доказательство — условие вида (`k` снят с цепочки свободных или
  `k == bump`), класс L; в отладочной сборке — проверка метки слота;
- источник — `own` блока либо имя с условием `used > 0`.

Первый `take` из `own` поглощает `own`: дальше имя — `mut SlotBlock`, так же как права любого
имени сужаются после передачи `own` ([владение](../types/ownership.md), «уточнение типа в точке программы»). Так блок
переходит из «есть владелец» в «выдан, владельца нет», и `own` с выданным элементом построить
нельзя.

```efen
fn acquireSlot(entry: mut Classes.Item, block: mut SlotBlock { used > 0 }) -> own Pointer {
    var k: Int
    if block.free != NONE {
        k = Int(block.free)
        block.free = block.slots[k].next   // k снят с цепочки: не взят
    } else {
        k = Int(block.bump)                // k >= bump: не взят
        block.bump = block.bump + 1
    }
    let slot = take block.slots[k]         // k входит в slots.taken
    block.used = block.used + 1            // Δused == +1 == число take
    if block.free == NONE && Int(block.bump) == block.slots.count { unlinkBlock(entry, block) }
    return slot as Pointer                 // стирание; Pointer помнит происхождение
}
```

### Возврат: `take` на своё место

Номер места элемента даёт compiler-known `area.index(element)`; формула (адрес минус начало
области, делённое на шаг) принадлежит компилятору, доказывать её не нужно. После
`block.slots[k] = take slot` место `k` выходит из `slots.taken`, и его поля снова доступны.

```efen
fn releaseSlot(entry: mut Classes.Item, block: mut SlotBlock { used > 0 },
               slot: own block.slots.Item) {
    let k = block.slots.index(slot)
    block.slots[k] = take slot             // байтов не копирует: slot и есть место k
    block.slots[k].next = block.free
    block.free = UInt16(k)
    block.used = block.used - 1            // Δused == −1 == число возвратов
    if block.used > 0 {
        if !block.linked { relinkBlock(entry, block) }
        return
    }
    if block.linked { unlinkBlock(entry, block) }
    let spare = take block                 // used: > 0 на входе, 0 здесь — имя стало владельцем
    if entry.reserve == null { entry.reserve = spare; return }
    releaseBlock(spare)
}
```

### Имя становится владельцем

`take block` у имени допустим при двух условиях: имя пришло с условием `used > 0`, и в этой
функции `used` стало 0 возвратом элементов. Единственность следует из правила `own`: у блока
с `used > 0` владельца не было, значит после последнего возврата владелец один — это имя.
Имя с `used == 0` на входе (запас класса, блок пула, блок арены) владельцем стать не может:
его владелец — поле (`entry.reserve`, `firstFreeBlock`, `arena.currentBlock`), и путь к нему —
`take` поля. Прочие имена того же блока (список класса) остаются именами; что в списке нет
блока без выданных слотов — условие `layout` (У7), класс L; в Amber — отладочная проверка.

### Учёт на выходе функции

На каждом выходе Δ`used` равно числу `take` элементов минус число возвратов в этой функции.
Функция, которая меняет `used`, сама выдаёт или принимает элементы; «посчитать за другого»
нельзя. Цикл с `take` требует инварианта по `taken`; пока такой цикл не нужен — см. «Не решено».

### Поля взятого элемента

`block.slots[j].next` через имя допустимо для `j`, доказанно не взятого в этой точке: `j`
снят с цепочки в этой функции или только что возвращён. Иначе ошибка компиляции: память
держит получатель элемента.

### Один элемент: большой блок и отображение

У `LargeBlock` и `RunBlock` элемент — хвост области: `take block.bytes[offset - LINE...]`.
Учёт — то же поле: `used <= 1; (used == 0) == bytes.taken.isEmpty`. Выдача поглощает `own`;
возврат — `block.bytes[from...] = take payload` с `from = block.bytes.index(payload)`, затем
`take block`.

### Тип элемента

`block.slots.Item` — сокращение origin-формы `own<block> SlotBlock.slots.Item`, той же, что у
ссылок (`&read<values> Int`). `block` — параметр или `let`-имя той же функции; аргумент в
этой позиции — имя. Это условие происхождения на пару значений, а не generic по runtime-значению
([типы со значением-параметром](../types/value-parameterized-types.md) допускают origin именно для этого). Два разных параметра — два
разных типа; `var` или временное выражение в этой позиции — ошибка.

### Стирание и восстановление

`slot as Pointer` стирает тип; `Pointer` помнит происхождение. Обратное приведение
`memory as block.slots.Item` допустимо только в коде `@trusted`: в обычной сборке на веру (Д3),
в отладочной — проверка (Р1–Р4: блок кучи, начало места, место выдано). Это касается каждого
возврата через контракт `Allocator`, в том числе из Efen: `deallocate(memory: own Pointer)`
происхождения параметра не знает.

### Владеющие ссылки вида

`FreeBlock` уточняет `Header.next` до `own FreeBlock?`. Такое поле пишется только переносом
(`spare.next = take next`) через владельца вида: `own`-параметр или переменную, которая ещё
владеет видом. Через `mut`-параметр ссылку можно только сравнить с `null`: вызывающий мог
передать имя блока из середины цепочки, и `last.next = take first` замкнул бы её. Через
`Blocks.Item` и другие виды поле читается как имя, записать его нельзя. Смена вида
требует, чтобы владеющие ссылки старого вида были `null`; иначе `as` отказывает, и
остаток пула не теряется молча. Ссылка, которую добавляет новый вид, после приведения не
записана: байты держат старое имя, а не владельца.

Владеющее поле пишется только через владельца: через `own`-значение или путь от него, который
держит заём владельца. Через имя, полученное чтением владеющего места, — нельзя: имя переживает
`take` владельца, и запись через него замкнула бы цепочку саму на себя (`second.next = take head`
после `let head = take self.firstFreeBlock!`). Исключение — множество со структурным условием
(`chained`, `tree`): там запись через имя разрешена, а компилятор доказывает сохранение условия,
как `append` через `tail` в [примерах компоновки](layout-examples/singly-linked-array.md).

### Арена

Блоки арены держит цепочка `arena.currentBlock: own ArenaBlock?` → `next: own ArenaBlock?`.
Заём `&block.bytes[a..<b]` имеет origin `self`; `resetArena` берёт владеющее поле и меняет вид,
то есть меняет структуру `self`, и по сводке функции ([владение](../types/ownership.md)) все займы умирают при
вызове. Имя блока арены никогда не приходит с `used > 0`, поэтому владельцем стать не может.

## Обнулённая память `zeroed`

Статус: свойство потребовал Edmond 2026-10-24 («обнулённость памяти — явное свойство, компилятор её отслеживает»);
слово `zeroed` и правила ниже предложены в Amber S74.8c2 и не утверждены.

`zeroed` — условие результата типа `Pointer` рядом с `size` и `alignment`: вся память нулевая. Функция обещает его в
своей сигнатуре и доказывает на каждом `return`; вызывающий получает его вместе с памятью:

```efen
fn map(bytes: Int { value % PAGE == 0 }, aligned: Int) -> own Pointer? { size == bytes && alignment == aligned && zeroed }
```

Компилятор помнит `zeroed` у имени, которое держит память. Его дают условие результата функции или `@asm`
(`memory.zeroed`, см. [системные вызовы](system.md)), проверка `isAligned` и заём у нулевого владельца. Имя, которому
в теле функции присваивается другое значение, `zeroed` не несёт.

Нули нужны там, где программа читает память раньше, чем пишет: элемент области с полем-именем (`Blocks.Item?`)
читается как `null`, только если память нулевая. Приведение к такой области без `zeroed` — ошибка компиляции.

Поля вида нули не записывают. Вид, приведённый из нулевой памяти, всё равно пишет каждое поле до первого чтения: так
проверка не зависит от того, откуда пришла память.

## Область layout: `area` и `set area`, число элементов у переменной

Статус: дескрипторы `area` и `set area` описаны в [компоновке](addresses.md#структуры-и-дескрипторы). Где пишется число
элементов, решил Edmond 2026-10-25: дескриптор — объявление формы, конструктора в нём нет; число элементов указывает
переменная, которая держит область. Правила приведения и раздачи ниже предложены в Amber S74.8c и S74.6g и не
утверждены.

Дескриптор области в `layout` объявляет только тип элемента:

```efen
layout {
    set area Blocks: Block
    area Classes: Class

    struct Class {
        var size: Int = 0
        var firstAvailable: Blocks.Item? = null
    }

    struct Pool {
        own var classes: Classes.Area? { value == null || value.count == CLASSES } = null
    }
}
```

`Classes.Area` — чистый указатель на начало области, одно машинное слово; ёмкость он не хранит
([компоновка](addresses.md#производные-типы-дескриптора)). Число элементов — уточнение переменной, сразу после её
типа, по форме [уточнённых типов](../types/refinement-types.md):

```efen
let table: Classes.Area { value.count == CLASSES } = memory as Classes.Area
```

- у необязательного поля — `{ value == null || value.count == N }`, у остальных — `{ value.count == N }`;
- `N` — число или имя константы, значение которой — число; две переменные с одним значением числа держат область
  одного типа, с разными — разных типов;
- приведение к области бывает только начальным значением такой переменной и только из `Pointer`;
- переменная без записанного типа берёт тип начального значения: `if let table = take pool.classes`;
- область без числа — тип параметра, результата, поля или переменной — ошибка компиляции.

Шаг элемента — `sizeOf(Class)`. Приведение `memory as Classes.Area` поглощает `Pointer`. Компилятор доказывает:

1. размер памяти не меньше `count · sizeOf(E)` для `area` и равен ему для `set area`: у набора каждый байт принадлежит
   элементу;
2. выравнивание не меньше `alignOf(E)`;
3. `zeroed`, если у элемента есть поле не целого типа.

Элементы `area` — значения. `table[i].size = 16` пишет поле элемента `i`, `table[i] = Class(...)` — элемент целиком.
Индекс доказан в границах `0 ..< count` или проверяется при выполнении. Поля элемента — целые и необязательные имена;
владеющее поле в элементе области — ошибка компиляции.

Стирание `table as Pointer` возвращает память без размера, как стирание вида; её отдают системе с тем размером, с
которым отображали. `Classes.Area` бывает типом переменной и владеющего поля, но не параметра и не результата.

Элементы `set area` не индексируются: набор раздаётся целиком циклом ниже.

## Поле-область: доступ на месте `!`

Статус: предложено в Amber S74.8c1b, не утверждено.

Владеющее поле `own var classes: Classes.Area? { value == null || value.count == CLASSES }` хранит область. `pool.classes![i].size` читает и пишет элемент на
месте: поле не забирается, `!` утверждает, что оно не пусто. Пустое поле останавливает программу при выполнении.

```efen
fn countUse(pool: mut Pool, index: Int) {
    if index >= 0 && index < CLASSES {
        pool.classes![index].used = pool.classes![index].used + 1
    }
}
```

`!` после поля пишется только перед `[`. В индексе и в правой части такой записи вызова нет: вызов мог бы забрать
поле, пока доступ к нему открыт.

## Раздача набора: `for element in take region`

Статус: предложено в Amber S74.8c3, не утверждено. В спецификации есть `for x in take v` для коллекций; для набора
памяти форма новая.

```efen
fn growPool(pool: mut Pool) -> Bool {
    guard let memory = System.map(bytes: REGION_BLOCKS * BLOCK, aligned: BLOCK) else {
        return false
    }

    let region: Blocks.Area { value.count == REGION_BLOCKS } = memory as Blocks.Area
    for element in take region {
        pool.firstFreeBlock = newFreeBlock(memory: take element, next: take pool.firstFreeBlock)
    }
    return true
}
```

Цикл поглощает набор и выдаёт его элементы по одному. Каждый `element` — `own Pointer` размером в шаг элемента,
выровненный по `alignOf(Block)`; тело обязано передать его дальше: привести, отдать владеющему параметру или полю.
Элемент, который тело оставило, — утечка, ошибка компиляции.

Выйти из такого цикла раньше нельзя: `break`, `continue` и `return` в его теле, в том числе во вложенном цикле, —
ошибки компиляции, а исключение из тела — утечка. Иначе элементы после точки выхода не достались бы никому.

## Займы частей памяти: `lend`

Статус: форма `lend memory[a ..< b]` принята Edmond 2026-10-24 (19:06–19:27), обрезка — как `map_aligned` в
limelight-lang/model; `address` и `isAligned` предложены в Amber S74.19b3 и не утверждены.

Заём делит память владельца на части без копирования:

```efen
let skip = (aligned - address(memory) % aligned) % aligned
let head = lend memory[0 ..< skip]
let block = lend memory[skip ..< skip + bytes]
let tail = lend memory[skip + bytes ..< total]
System.unmap(memory: take head, bytes: skip)
System.unmap(memory: take tail, bytes: total - skip - bytes)
guard block.isAligned(to: aligned) else {
    System.unmap(memory: take block, bytes: bytes)
    return null
}
return take block
```

- Займы одной группы идут подряд, их границы не меняются после займа; последний кончается на размере владельца и
  поглощает его.
- Заём отдаётся системе (`System.unmap`, длина проверяется при выполнении, ноль байт — без системного вызова), читается
  `address` и проверяется `isAligned`. Один `take` займа делает его владельцем.
- `address(memory)` читает адрес как `Int` и `Pointer` не поглощает.
- `guard x.isAligned(to: k) else { ... }` проверяет выравнивание при выполнении; после него компилятор знает, что `x`
  выровнен по `k`.

Заём места области, `lend block.slots[k]`, Edmond принял в тот же день; он относится к выдаче слотов и описан в
разделе «Иерархия владения».

## Память, пришедшая из C

Адрес, переданный через контракт `Allocator` (из C или из Efen), становится элементом
только в `@trusted` (раздел «Стирание и восстановление»). Отладочная сборка проверяет:

- Р1: адрес лежит в известном блоке кучи;
- Р2: адрес — начало места;
- Р3: место выдано (метка слота);
- Р4: у большого блока и отображения — `used == 1` и смещение `offset`.

## Порядок байтов

Если структура читает готовые байты, порядок которых не совпадает с порядком байтов
цели сборки, это ошибка компиляции.

## Не решено

Эти места модели пока описаны эскизом; синтаксис для них не утверждён:

- как отображение ОС, взятое не регионом, входит в множество блоков и выходит из него;
- условная компиляция отладочных проверок (`#if debug()` в спецификации нет);
- условие на параметре `{ used > 0 }` (форма условия поля, перенесённая на параметр);
- `@trusted` на функции;
- `own<block>` — origin-форма, у ссылок она есть, для `own` не записана;
- `x.taken` и `x.index(element)` как имена, известные компилятору;
- уточнение типа поля заголовка условием вида (`next: own FreeBlock?`);
- импликация `==>` в условии вида;
- цикл, который берёт несколько элементов: нужен инвариант по `taken`;
- происхождение `Pointer` через границу контракта (`tryAllocate -> own Pointer?`);
- как отображение покидает множество блоков при `unmap`.
- структурное условие `tree from self.root by Item.left, Item.right` — пара к `chained` для дерева.
