# Генератор доказательств Efen → Viper

> Статус: проект алгоритма, редакция 2026-09-06. Документ описывает проверяющий
> прототип, а не принятую часть языка. Обязательства provenance, liveness,
> initialization, bounds и rights остаются актуальны. Surface-примеры
> `.pointer`, `inverse`, `region suspend` и старые операции населения относятся
> к редакции 2026-09-06 и не являются текущим синтаксисом. Нормативная модель:
> [Layout и дескрипторы памяти](addresses.md).

## Задача

Компилятор должен по исходному коду Efen построить программу Viper, проверить её
Silicon или Carbon и вернуть ошибку в координатах Efen. Viper не исполняет
программу и не выбирает алгоритм за автора: он доказывает, что написанный
алгоритм соблюдает членство, права доступа и инварианты `layout`.

Обязательный результат — доказанная безопасность памяти. Первый прототип
отвечает на четыре вопроса:

1. происходит ли ссылка из населения конкретного экземпляра layout;
2. обращается ли код только к живым и инициализированным блокам;
3. остаются ли индексы и ячейки в границах своего живого хранилища;
4. имеет ли операция права чтения, записи, перемещения и изъятия.

Компилятор порождает эти обязательства даже для `set Nodes: Node` без
пользовательских инвариантов. Они действуют при исключениях, `defer`, повторном
входе и уничтожении layout; `region suspend` их не отключает.

Достижимость, отсутствие потерянных узлов, распределение по корзинам, счётчики
и завершение — дополнительные свойства. Их недоказанность сама по себе не
блокирует принятие программы по безопасности памяти. Если свойство используется
для доказательства безопасности, его доказательство обязательно: например,
`inverse`, по которому удаление находит входящие ссылки.

Неподтверждённое обязательство безопасности означает отказ компиляции либо
предусмотренную семантикой runtime-проверку (граница индекса, разрешение `weak`).
Общего автоматического runtime-проверяющего для произвольной формулы нет.
Тайм-аут означает «не доказано», а не обнаруженный дефект программы. Отчёт
разделяет безопасность, дополнительные свойства и непроверенные свойства.

Генерация машинного кода, конкурентность, сырые адреса, FFI и доказательство
завершения произвольной рекурсии в прототип не входят.

## Архитектура

Прямой перевод AST Efen в строки Viper слишком рано связывает язык с одним
прувером. Между ними нужен нейтральный проверочный IR:

```text
исходный текст Efen
        │
        ▼
parser → AST → разрешение имён и типов
        │
        ▼
       VIR                 Verification IR
        │
        ├──→ Viper emitter → Silicon / Carbon
        └──→ другой backend в будущем
```

Frontend отвечает за правила самого Efen: происхождение ссылок, доступность
полей, якорь зависимого типа, законность `remove`, точки наблюдения. Backend
отвечает только за перевод уже явных обязательств VIR в язык конкретного
прувера.

Каждый узел VIR хранит `SourceSpan`: файл, начало и конец выражения Efen. Ни одно
сообщение Viper не должно показываться пользователю без обратного отображения.

## Проверяемое подмножество

Первая версия принимает:

- `layout`, `set`, `struct`, `var`, `let` и `fn`;
- ссылки на население одного экземпляра `layout`;
- чтение и запись полей;
- `if`, `while`, ограниченный `for`;
- `create`, `remove` и `take`;
- именованные инварианты населения `invariant name(item)`;
- `inverse`;
- контракты `requires`, `ensures`, `reads`, `modifies`, `creates`, `removes`;
- `region suspend` без выхода в непроверенный внешний код.

Слова контрактов в этом списке — предложение для проверяемого диалекта. Они не
считаются принятой грамматикой Efen до отдельного решения.

## Семантическая модель VIR

### Идентичность и живость

Ссылка и право разыменовать её — разные значения. Любой блок получает
стабильную логическую идентичность `Ref`. Для каждого населения существует
призрачное множество живых идентичностей:

```text
Population Nodes {
    element = Node
    live    = Set<Ref>
}
```

Типизированная ссылка гарантирует происхождение из `Nodes`, но доступ к полям
требует ещё и `p ∈ Nodes.live`. После изъятия идентичность `p` можно сравнивать,
однако разыменовывать её нельзя.

### Права принадлежат layout

Несколько ссылок на один блок не порождают несколько прав. Экземпляр `layout`
владеет правами на поля всех живых блоков:

```text
owns(Nodes) ≜
    ∀ n ∈ Nodes.live:
        write(n.value) * write(n.next) * ...
```

Знак `*` здесь означает разделяющую конъюнкцию, а не синтаксис Efen. Viper
backend реализует права через `acc`. Для первого прототипа операция получает
полные права на свой `layout`; дробные права для параллельного чтения можно
добавить позже.

### Сильные и слабые хранимые ссылки

Для каждого сильного поля `f`, ведущего в `Nodes`, frontend создаёт обязательство:

```text
∀ holder ∈ Holders.live:
    holder.f == null ∨ holder.f ∈ Nodes.live
```

Такой инвариант означает отсутствие висячих сильных ссылок. Он не сообщает, как
найти держателей во время исполнения. Изъятие допустимо, только если входящие
рёбра перечислимы через `inverse`, объявленное строение или явный обход. Иное
хранимое поле при возможности изъятия обязано быть `weak` и проверять поколение
при доступе. Неудаляемое население может хранить произвольные внутренние сильные
ссылки. Корни layout и элементы массивов также входят в список держателей;
живость сильных целей не является отключаемым инвариантом автора.

### Якоря, места и срок жизни

VIR хранит `LayoutId`, `PopulationId(LayoutId, declaration)`, `BlockId`,
`StorageId` и `Place` (переменная, поле, ячейка). Доступ `b.sub.root`
перепривязывает зависимый тип к `b.sub`; generic не стирает якорь экземпляра.
Новая жизнь физически переиспользованного места получает новый `BlockId`:
свежесть нужна относительно всех ранее выданных идентичностей, а не только `live`.

Для [колоночного storage](columnar-layouts.md) `BlockId` является логической
identity и не совпадает с `StorageId` или номером physical row. VIR дополнительно
хранит kind и прямые/обратные отображения common и payload rows. Он проверяет,
что каждая живая identity имеет ровно одну инициализированную common-строку и
payload своего вида, а каждая опубликованная physical row имеет ровно одного
логического владельца.

`create`, `remove`, `replace` и `compact` получают normal и exceptional
переходы над всеми участвующими stores. Ошибка подготовки сохраняет прежние
`live` и mappings и уничтожает каждый provisional fragment ровно один раз.
`swap-remove` обновляет обе стороны отображения перемещённого соседа.
`managed` у скрытого backing slot не служит доказательством безопасности
публичного `Place`: projected access по-прежнему требует membership, origin,
rights, initialization и отсутствие конфликтующего borrow.

Runtime-open family добавляет в VIR `KindCatalog`, `KindDescriptor`,
`StorageWitness`, `CatalogEpoch`, `FieldPlace(identity, path)`, physical
`StoreId`/`RowId` и прямые/обратные maps. Обязательный закон квантифицируется по
всем зарегистрированным видам, а не по полям исходного `BaseNode`:

```text
forall kind in KindCatalog:
    Admitted(kind) && DescriptorValid(kind) && WitnessValid(kind)

forall id in Live:
    CatalogContains(Kind(id))
    && CommonMapsTo(id)
    && PayloadMapsTo(id, Kind(id))
    && FieldsAndOwnershipValid(id, Descriptor(Kind(id)))
```

Регистрация вида требует exclusive catalog guard и увеличивает epoch.
Специализированное доказательство, предполагавшее закрытый список видов,
зависит от этого epoch и после регистрации перепроверяется либо становится
неприменимым. Общие операции перечисляют owning и reference fields через
descriptor, поэтому поздний вид не скрывает новое входящее ребро.

VIR-операции `ValidateKind`, `RegisterKind`, `ResolveField`, `PrepareStorage`,
`CommitStorage` и `AbortStorage` различают fallible prepare и no-throw commit.
Формулы `CommonMapsTo`, `PayloadMapsTo`, `ReverseOwner`, `Borrowable`,
`Addressable` и `StableUntil` связывают logical place с physical storage. Это
внутренние операции проверяющего backend, а не новый surface-синтаксис Efen.

Кроме прав на поля отслеживаются `owner(block): Place?` и инициализированные
поля. `own` нельзя получить копированием `read`. Перемещение очищает источник;
перезапись назначения отсоединяет прежнего жильца, но не удаляет его из `live`.
Блок без `owner` остаётся живым до изъятия или уничтожения населения. Это допустимо
по безопасности; отсутствие потерянных блоков проверяется отдельно.

Локальное заимствование удерживает нужные факты до последнего использования:
ссылка — живость блока, индекс — границы конкретного хранилища, ячейка — живость
держателя и идентичность места. В первой версии изменение членства консервативно
конфликтует с живыми обычными заимствованиями населения. Удаление после последнего
использования заимствования допустимо. Замена массива и перемещение или уничтожение
layout запрещены при конфликтующих заимствованиях. Запись элемента массива не
меняет его длину и не конфликтует с индексом.

Возвращённое заимствование привязано к получателю или явно названному параметру.
Хранимые `.index` и `.slot` в первом подмножестве запрещены; вычисляемые свойства
допустимы. Ячейка не выходит из `region suspend`. `buckets.index(i)` доказывает
`0 <= i < length` либо проверяет границу до создания индекса; неуспех имеет
исключительное ребро CFG. Числовой перевод сохраняет ширину и переполнение Efen:
безграничный Viper `Int` не заменяет машинное число без ограничений диапазона.
Неподдержанная битовая формула не позволяет предположить успешность проверки.

Разрешение `weak` проверяет живость и поколение и выдаёт временное заимствование,
которое запрещает удаление до своего окончания. Источник хранит поколение вне
уничтожаемой нагрузки. При переполнении он прекращает повторное использование
места либо отказывает в выдаче; старое поколение не должно совпасть повторно.

## Синтаксис контрактов проверяемого диалекта

Clauses располагаются после обычной подписи перед телом. Это предлагаемые
контекстные слова, а не новые жёсткие ключевые слова основного языка:

```text
Clause := requires Expr
        | ensures Expr
        | ensures on throw { Expr }
        | reads PlaceSet (, PlaceSet)*
        | modifies PlaceSet (, PlaceSet)*
        | creates Population (, Population)*
        | removes Population (, Population)*
        | opens InvariantName (, InvariantName)*
PlaceSet := receiver.field | Population.field | container[*]
```

Каждый clause начинается с новой строки и заканчивается переводом строки вне
вложенных скобок. Многострочное выражение заключается в круглые скобки;
`ensures on throw { Expr }` продолжается до закрывающей скобки. Тело начинается
на следующей строке. Контекстное слово внутри выражения не начинает новый clause.
Повторные `requires` и `ensures` соединяются конъюнкцией; повторные списковые
clauses объединяются. `old(expr)` — входное значение,
`result` — результат нормального выхода; на исключительном выходе его нет.
Контракт наблюдает `own` без перемещения и может называть входную идентичность
потреблённого параметра; тело не вправе читать потреблённую переменную.

`reads` разрешает чтение, `modifies` — чтение и запись. `creates` и `removes`
задают верхние границы изменения членства, а конкретный результат — `ensures`.
Инициализация нового блока входит в `creates`, потребление прав изъятого — в
`removes`; изменения остальных блоков входят в `modifies`. Неуказанное членство
сохраняется. Селекторы следа вычисляются во входном состоянии; свежие блоки
учитываются отдельно. Порождённые записи в `inverse` входят в расширенный след
прямой связи, а перемещение включает очищаемое исходное место.

Если ни один clause следа не написан, весь след выводится. Если указан хотя бы
один из `reads`, `modifies`, `creates`, `removes`, неуказанные категории пусты;
при этом `modifies` по определению включает чтение и порождённые записи связи.
Логические чтения для автоматически порождённых доказательств учитываются
отдельно от runtime-следа тела и не дают ему дополнительных прав записи.

След локальной функции можно вывести; у публичной он сохраняется в интерфейсе
даже при выводе. Явный след — верхняя граница. Очевидные нарушения отклоняет
frontend; включение мест с учётом алиасов и сохранность полей вне следа на обоих
выходах доказывает Viper. Полные права на layout сами по себе не обеспечивают
неизменность полей вне `modifies`.

Формулы не имеют побочных эффектов и не бросают исключений. Вызванная из формулы
функция имеет проверенные тело, след чтения и завершение либо входит в явно
перечисленную доверенную библиотеку. `nothrows` не означает чистоты; `key.hash()`
нельзя автоматически считать логической функцией.

При вызове с `removes P` проверяются якорь населения и все алиасы: запрещено
любое локальное заимствование P, которое требуется после вызова. `read`-аргумент
такого метода даёт временный доступ до изъятия, а не обещание сохранить живость
аргумента. Его borrow и reborrow завершаются на обоих выходах; нормальный и
исключительный контракт не возвращают живость автоматически. Если она нужна
после вызова, её должен явно гарантировать контракт; это позволяет создать новое
заимствование, а не продлить прежнее. Сохранённая до вызова идентичность для
сравнения не удерживает живость и не считается продолжающимся borrow.
Сильные хранимые поля
проверяются отдельно: окончание локального borrow не очищает поле.

## Минимальный VIR

VIR не должен содержать `acc`, `inhale`, `exhale` или другие понятия Viper.
Базовые сущности:

```text
Module
  types:       Record[]
  populations: Population[]
  fields:      Field[]
  invariants:  Invariant[]
  procedures:  Procedure[]

Procedure
  parameters
  result
  preconditions
  postconditions
  footprint: { reads, writes, creates, removes }
  body

Statement :=
  Assign(place, value)
  Read(place)
  Assert(formula, obligationId)
  Assume(formula)
  If(condition, then, else)
  Loop(condition, invariants, body)
  Create(population, result, fields)
  Remove(population, reference)
  OpenInvariant(name)
  CloseInvariant(name)
  Call(procedure, arguments)

Formula :=
  Live(population, reference)
  CanRead(place)
  CanWrite(place)
  Eq | And | Or | Not | Implies
  ForEvery(domain, variable, formula)
  Old(formula)
```

Backend может выбирать собственное представление множеств, разрешений и
предикатов, пока сохраняет смысл этих операций.

Дополнительно обязательны `MovePlace`, `Borrow`, `EndBorrow`, `Allocate`,
`Initialize`, `Publish`, `Retire`, `RelationMove`, `Snapshot` и `Invoke` с
нормальным и исключительным рёбрами. Формулы значений отделяются от ресурсных
утверждений: ресурсная композиция не является обычным булевым `And`.
Перед VIR строится CFG с явным порядком вычисления и раскрытыми `defer`.
Будущий машинный backend должен использовать те же нормализованные операции.

## Алгоритм генерации

### 1. Разобрать и типизировать Efen

Parser строит обычный AST. Затем frontend:

1. разрешает экземпляр `layout`, которому принадлежит каждое население;
2. привязывает каждый `.pointer`, `.slot` и `.index` к вместилищу;
3. классифицирует ссылочные поля как `own`, сильные заимствованные или `weak`;
4. разворачивает поля, неявно объявленные через `inverse`;
5. отклоняет сырой адрес, который пытаются принять за ссылку населения.

После этого в VIR не должно остаться неразрешённых имён или ссылки с неизвестным
происхождением.

### 2. Построить описание layout

Для каждого `set Nodes: Node` создаются:

- символ населения `Nodes`;
- призрачное множество `Nodes.live`;
- список полей `Node`, требующих прав;
- инварианты населения;
- перечень входящих сильных отношений.

Для каждого обычного поля создаётся функция кучи `Field(holder) → value`. Поля
значений и поля-ссылки различаются типом результата, но права доступа к ним
вычисляются одинаково.

### 3. Развернуть `inverse`

Объявление:

```efen
inverse prev of next
```

порождает в VIR поле `prev`, инвариант пары и единственную атомарную операцию
перепривязки:

```text
RelationMove(destination, source):
    evaluateAndCheckPlaces(destination, source)
    if destination == source: return
    value = detach(source)       // очистить источник и его inverse
    detach(destination)         // прежний жилец остаётся в населении
    attach(destination, value)  // новое место own и новый inverse
```

Прямой `Assign(y.prev, ...)` frontend запрещает. Поэтому промежуточное нарушение
пары отсутствует в пользовательском VIR, а backend доказывает один шаблон
`RelationMove`, а не каждую половину связи отдельно. Проверки выполняются до
записей; внутри шаблона нет пользовательских вызовов или исключений. Все
допустимые совпадения держателей и целей входят в доказательство шаблона.
Входное `own` не имеет второго владельца. Для невладеющего прямого поля с
одиночным inverse необходимо дополнительно доказать отсутствие другого прямого
ребра к новой цели; простая перезапись `new.prev` этого не обеспечивает.
`cell.take()` использует тот же шаблон перемещения в локальное место.

Для `{left, right}` в обратной стороне хранится также различитель ребра. Без него
равенство обратной пары неоднозначно.
Корневые ячейки участвуют в учёте владельца, хотя `prev` первого узла равен `null`.

### 4. Вычислить след операции

Из тела и явного контракта вычисляются четыре множества:

```text
reads    = места, значения которых читаются
writes   = места, в которые выполняется запись
creates  = населения, куда добавляются блоки
removes  = населения, откуда изымаются блоки
```

Явный контракт служит верхней границей. Если тело пишет в поле вне `modifies`,
frontend выдаёт ошибку до запуска Viper. Если контракт опущен, прототип может
вывести след для локальной функции, но публичная операция обязана сохранить его
в интерфейсе.

Слово `effect` для этого не используется: в Efen оно уже обозначает зависимость
от окружения.

### 5. Построить контракт прав

Для каждого чтения frontend добавляет `CanRead`, для записи — `CanWrite`. Для
публичной операции права группируются по населению и полю, а не перечисляются по
отдельным выражениям.

Концептуально:

```text
requires ∀ n ∈ Nodes.live: CanWrite(n.value)
ensures  ∀ n ∈ Nodes.live': CanWrite(n.value)
```

Viper backend переводит это в quantified permissions:

```viper
requires forall n: Ref :: { n.value }
    n in nodes ==> acc(n.value)

ensures forall n: Ref :: { n.value }
    n in nodesAfter ==> acc(n.value)
```

Триггеры выбирает backend; они не являются частью VIR и не видны в Efen.

### 6. Перевести выражения и разыменования

Перед чтением `p.value` VIR требует:

```text
Assert(Live(Nodes, p), use-after-remove)
Assert(CanRead(p.value), missing-read-permission)
Assert(Initialized(p.value), uninitialized-read)
Read(p.value)
```

Проверка инициализации относится также к полям самого layout и локальным
местам после перемещения. Членство блока само по себе не заменяет её.

Перед записью требуются живость и `CanWrite`. Сравнение `p == q` не разыменовывает блок и
не требует его живости. Именно поэтому ссылку на изъятый объект допустимо
сравнить с `null` или другой идентичностью, но нельзя использовать для доступа к
полю.

### 7. Перевести `create`

`Nodes.create(...)` порождает свежую идентичность `n` и следующие шаги VIR:

```text
Assert(FreshIdentity(n))              // свежесть за всю историю выделений
AcquireFields(n)
InitializeFields(n)
Nodes.live' = Nodes.live ∪ {n}
Assert(MemorySafety(Nodes.live'))
```

Viper backend получает права нового блока через `inhale` либо через контракт
операции источника. Второй вариант предпочтителен для окончательной модели:
источник, а не пользовательский код, создаёт память.

До публикации блок имеет только права построения и недоступен обычным ссылкам.
При отказе уничтожаются только инициализированные поля и возвращается выделенная
память, членство не меняется. Cleanup не бросает и не допускает повторного входа.
Достижимость нового блока проверяется на требующей её границе после присоединения,
а не немедленно при `create`. Источник обязан гарантировать размер, выравнивание,
свежесть, правила перемещения блоков и отсутствие обратного вызова в layout.

### 8. Перевести `remove`

Для `Nodes.remove(victim)` frontend выполняет алгоритм:

1. доказать `victim ∈ Nodes.live` и наличие единственного `own`;
2. доказать право изменения членства `Nodes`;
3. найти все объявленные сильные отношения, способные указывать в `Nodes`;
4. проверить, что тело обнулило или перенаправило каждое входящее ребро;
5. завершить конфликтующие заимствования, восстановить `inverse`, обработать
   исходящие ссылки; в первом подмножестве ссылочные поля жертвы должны быть пусты;
6. потребить `own` и установить `Nodes.live' = Nodes.live − {victim}`;
7. отдать backend операцию `ReleaseFields(victim)`;
8. доказать отсутствие сильных ссылок относительно нового населения и не
   возвращать вызывающему прав на поля `victim`.

`take` выполняет то же изъятие и перемещает нагрузку в результат без копии;
`remove` уничтожает её. Зависимости от изымаемого блока или от покидаемого layout
не должны утечь с результатом. Потенциально бросающие вычисления выполняются до
изъятия; завершающая последовательность и деструктор нагрузки в первом
подмножестве не бросают и не допускают повторного входа. Rollback содержимого
не обещается, операция возвращения блока не требуется для безопасности.

Viper backend реализует последний шаг потреблением разрешений:

```viper
exhale acc(victim.value) && acc(victim.next) && acc(victim.prev)
```

Это логическое изъятие, а не вызов `free`. Реальное освобождение, tombstone или
возврат блока арене выбирает runtime/source Efen.

Если произвольное число ссылок очищается проходом, автор пишет этот проход сам:

```efen
fn compact(victim: own Nodes.pointer)
    modifies Links.target
    removes Nodes
    ensures victim not in Nodes
{
    for link in Links {
        if link.target == victim {
            link.target = null
        }
    }

    Nodes.remove(victim)
}
```

Контракт задаёт доказываемый результат, но не генерирует обход. `Links` должен
быть перечислимым в реализации. Для двусвязного списка `inverse` уже является
локальным индексом входящего ребра, поэтому полного прохода нет.

Условие отсутствия ссылки на изъятый блок генерируется автоматически. Автор
может дополнительно дать ему имя, но не отключить его:

```efen
set Links: Link {
    invariant targetIsLive(link) {
        link.target == null || link.target in Nodes
    }
}
```

После `Nodes.remove(victim)` восстановление `targetIsLive` само требует доказать,
что обработан каждый `link`. Квантор появляется только в VIR и Viper, но не в
исходном Efen.

### 9. Перевести циклы

Viper требует инварианты циклов. Прототип получает их из четырёх источников:

1. права на неизменяемую часть `layout`;
2. инварианты населения, которые цикл не приостанавливает;
3. границы курсора и структурный факт обхода;
4. пользовательские `invariant`, если автоматического шаблона недостаточно.

Для очистки ссылок основной инвариант имеет вид:

```text
0 ≤ i ≤ holders.count
∀ j < i: holders[j].target != victim
∀ h ∈ holders: CanWrite(h.target)
```

Перечисление обязано покрывать всех держателей. Для повторяющихся держателей
нужно доказать сохранение уже установленного свойства; идемпотентность очистки
это позволяет. Если права кодируются через индекс последовательности, backend
отдельно доказывает инъективность отображения индекса в место либо квантифицирует
по множеству уникальных держателей, чтобы не дублировать разрешения.

Обязательны только инварианты, нужные для безопасности дальнейших доступов.
Дополнительная запись автора:

```efen
while condition
    invariant bounds { i >= 0 && i <= limit }
    decreases limit - i
{
    // тело
}
```

`decreases` отдельно запрашивает доказательство неотрицательной строго убывающей
целой меры. Без него безопасность проверяется независимо от завершения.
`times n` фиксирует неотрицательный счётчик при входе; завершение тела остаётся
отдельным свойством. `until p` само по себе не доказывает достижение `p`.
Для кольца начальное равенство проверяется после первого шага; `null` также
завершает обход. `*` — рефлексивное транзитивное замыкание по ненулевым блокам,
`+` требует хотя бы одного шага. Достижимость допускает цикл. Первый emitter
может не поддерживать такие структурные формулы: тогда из них не выводятся
факты безопасности. Позднее добавляются доказанные шаблоны путей, а не аксиомы
о желаемой достижимости.

Обычный обход удерживает членство населения. Курсор `split write` допускает
специальный шаблон удаления: забрать цель, перенести продолжение в текущую ячейку,
закончить заимствования цели, изъять блок. Держатель ячейки остаётся живым.
После замены цели рассматривается та же ячейка; иначе шаг идёт в поле продолжения.
Прочие изменения членства через такой курсор в первой версии отклоняются.

### 10. Обработать точки наблюдения

Инварианты `layout` должны быть закрыты перед возвратом, `throw`, внешним вызовом
и другим событием, перечисленным в `addresses.md`. В VIR это записывается явно:

```text
OpenInvariant(Nodes)
... изменения ...
CloseInvariant(Nodes)
ExternalCall(...)
```

Это относится к структурным инвариантам, выбранным для проверки; обязательства
безопасности не открываются. Любой вызов, включая соседний метод, требует
инвариантов своего контракта. Проверенный внутренний помощник может объявить
`opens Entries.reachable`: принять и вернуть свойство открытым, не предполагая
его истинности. Маска открытых свойств передаётся явно и не выдаёт прав доступа.
Непроверенный callback с доступом к нарушенному состоянию запрещён.

На каждом выходе из региона сначала выполняются `defer` в порядке LIFO,
затем восстанавливаются приостановленные свойства. Вложенный регион не закрывает
свойство, уже открытое при его входе. Исключения и следы вычисляются до CFG
до неподвижной точки по графу вызовов; внешним функциям нужны контракты.
Отсутствие `throws` в исходнике не стирает исключительное ребро. На нём действуют
безопасность, frame conditions и `ensures on throw`, но не обычное `ensures`.

### 11. Сгенерировать Viper

Emitter создаёт:

- `field` для полей структур;
- `Set[Ref]` или доменный предикат для живого населения;
- `predicate` либо quantified permissions для владения населением;
- `method` для операций;
- `requires` и `ensures` из контрактов VIR;
- `assert` с устойчивым `obligationId`;
- `inhale`/`exhale` только для приобретения и потери прав;
- инварианты `while`.

Для каждого сгенерированного диапазона сохраняется таблица:

```text
Viper span → obligationId → Efen SourceSpan → код ошибки
```

### 12. Запустить backend и вернуть диагностику

Порядок проверки:

1. запустить Silicon как основной быстрый backend;
2. разобрать структурированный результат ViperServer;
3. найти `obligationId` или ближайший сгенерированный диапазон;
4. заменить внутренние термины `permission`, `exhale`, `Ref` понятиями Efen;
5. показать исходную строку и причину.

Например, сообщение Viper `insufficient permission to access m.value`
превращается в:

```text
error[memory.use-after-remove]: `m` мог быть изъят
  --> example.efen:24:10
   |
24 | echo m.value
   |      ^^^^^^^ поля изъятого блока недоступны
```

Carbon полезен как второй backend в тестах. Результаты сохраняются раздельно;
тайм-аут одного и успех другого не доказывают ошибку генератора. Расхождение
воспроизводится на сохранённых VIR и Viper. Код ошибки определяется исходным
обязательством: отсутствие разрешения не всегда означает use-after-remove.

## Пример понижения изъятия

Исходный фрагмент Efen:

```efen
layout List {
    set Nodes: Node

    struct Node {
        var value: Int
        var next: own other Nodes.pointer?
    }

    inverse prev of next

    fn unlinkMiddle(node: read Nodes.pointer)
        requires node.prev != null
        modifies Nodes.next
        removes Nodes
    {
        let before = node.prev
        var victim = before.next.slot.take()
        before.next = victim.next
        Nodes.remove(victim)
    }
}
```

Существенная часть VIR:

```text
procedure List.unlinkMiddle(node):
    requires Live(Nodes, node)
    requires Read(node.prev) != null
    requires OwnsPopulation(Nodes)
    writes Relation(next, prev)
    removes Nodes[node]

    before = Read(node.prev)
    victim = MovePlace(before.next, local.victim)
    RelationMove(before.next, victim.next)
    EndBorrow(node)
    Assert(NoStrongIncoming(victim), dangling-strong-reference)
    Remove(Nodes, Consume(local.victim))
```

Существенная часть Viper:

```viper
method unlink(node: Ref, nodes: Set[Ref])
  requires node in nodes
  requires forall n: Ref :: { n.next }
    n in nodes ==> acc(n.next) && acc(n.prev) && acc(n.value)
  ensures forall n: Ref :: { n.next }
    n in nodes && n != node ==>
      acc(n.next) && acc(n.prev) && acc(n.value)
{
  // Сгенерированное раскрытие перемещений, проверки пары и нового live.
  ...
  exhale acc(node.next) && acc(node.prev) && acc(node.value)
}
```

Это схема разрешений, а не исполняемый полный пример Viper: многоточие включает
состояние владельца, проверку входящих ссылок и обновление живого населения.
Контракт реального метода возвращает также новое членство и frame conditions.

## Что является доверенной базой

Доказательство остаётся корректным только при согласованности четырёх частей:

1. parser и type checker правильно понимают исходный Efen;
2. перевод Efen AST → VIR сохраняет семантику;
3. Viper emitter сохраняет смысл VIR;
4. runtime реализует `create`, `remove`, поколения и источники так же, как они
   смоделированы.

Viper доказывает только полученную `.vpr`-программу. Ошибка генератора способна
породить доказанную программу, не соответствующую Efen. Поэтому каждый шаблон
понижения нуждается в положительных и отрицательных тестах.

Backend не должен использовать `assume` для факта, который обязан доказать
пользовательский код. Допустимые `assume` ограничиваются аксиомами уже
проверенной типовой системы и контрактами доверенных операций runtime.

## План реализации прототипа

### Этап 1. Сквозной минимальный пример

- parser одного файла и подмножества выше;
- типизация одного `layout`;
- VIR с `SourceSpan`;
- генерация Viper для полей, функций, контрактов и `remove`;
- запуск ViperServer;
- одна ошибка, отображённая обратно в Efen.

Критерий готовности: население без пользовательских инвариантов и несколько
алиасов живого блока приняты; чужой якорь, копирование `own` и use-after-remove
отвергнуты в координатах `.efen`. Ошибка в порождённой обратной записи выявляется
отдельным негативным тестом шаблона генератора.

### Этап 2. Населения и произвольные алиасы

- quantified permissions;
- автоматические обязательства живости над населением;
- циклы с явными инвариантами;
- операция, очищающая произвольное число входящих ссылок;
- проверка `modifies` и frame conditions.

Критерий готовности: `compact` доказывается для любого числа держателей, а не для
заранее перечисленных `h1`, `h2`.

### Этап 3. Полный жизненный цикл и границы

- индексы и ячейки, замена хранилища и конфликты заимствований;
- перемещения, `inverse` и курсор удаления;
- `create`, `take`, исключительные рёбра и частичная инициализация;
- проверка источников и уничтожения layout.

### Этап 4. Дополнительные свойства

- автоматическое открытие и закрытие;
- точки наблюдения;
- `region suspend`;
- вызовы между операциями одного экземпляра;
- инварианты структуры и завершение обходов по запросу.

### Этап 5. Независимость backend

- стабилизировать VIR отдельно от Viper emitter;
- прогонять корпус через Silicon и Carbon;
- добавить второй экспериментальный emitter или интерпретатор VIR;
- запретить появление Viper-специфичных конструкций во frontend.

## Набор обязательных тестов

Положительные:

- изменение значения живого блока;
- несколько локальных ссылок на один живой блок;
- удаление узла двусвязного списка;
- очистка всех сильных ссылок проходом;
- сравнение идентичности после `remove` без разыменования;
- `weak`-ссылка сообщает отсутствие после смены поколения.

Отрицательные:

- чтение поля после `remove`;
- забытая входящая сильная ссылка;
- запись вне `modifies`;
- изъятие при живом несовместимом обходе;
- ручная запись в поле, объявленное через `inverse`;
- выход из `region suspend` с невосстановленным инвариантом;
- передача ссылки между населениями одного типа;
- принятие сырого адреса за `Nodes.pointer`.

Каждый отрицательный тест проверяет не только отказ Viper, но и стабильный код
ошибки Efen и правильный `SourceSpan`.

## Открытые решения

Контрактный синтаксис и ограничения первой версии предложены выше. Остаются
расширениями: конкурентность, массовый перенос между населениями, произвольный
FFI, хранимые позиционные типы, общий язык замыканий и автоматический вывод
нетривиальных инвариантов. Неподдерживаемая операция, необходимая для безопасности,
отклоняется явно.

Первый emitter использует quantified permissions по живым идентичностям,
упакованные предикатом на границах методов. Права не дублируются при упаковке.
Для массивов требуется инъективное отображение `(StorageId, index)` в место.
См. [quantified permissions](https://viper.ethz.ch/tutorial/quantified-permissions.html)
и [представление массива](https://viper.ethz.ch/tutorial/domains-array.html).
Восстановление свойства генерирует доказательство, а не `inhale` формулы:
[семантика inhale/exhale](https://viper.ethz.ch/tutorial/permissions-inhale-exhale.html).

Для one-block storage перечислимость может предоставлять источник. Для
multi-store storage живые identities и kind перечисляет directory самого
storage. Retained witness вида уничтожает каждое инициализированное логическое
поле ровно один раз; затем source освобождает physical columns, maps и chunks.
Внешних заимствований нет, drop не следует внутренним ссылкам, не бросает и не
входит повторно в уничтожаемый layout. Kind не может существовать исключительно
в пользовательских ссылках на элемент.

К корпусу обязательных проверок добавляются: население без инвариантов; безопасное
кольцо без доказательства завершения; потерянный, но живой блок; индекс и ячейка
после замены хранилища; дублирование `own`; совпадающие места перемещения;
занятая цель `inverse`; висячий корень или элемент массива; удаление держателя
курсора; исключение при частичной инициализации; повторный вход источника;
переполнение поколения; утечка зависимости через `take`; двойное уничтожение.
Тайм-аут отрицательного теста не засчитывается как обнаружение ожидаемой ошибки.
Проверка отсутствия потерянной цепочки при rehash относится к дополнительным
свойствам и не подменяет доказательство безопасности.
