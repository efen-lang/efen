# Генератор доказательств Efen → Viper

> Статус: проект алгоритма от 2026-09-05. Документ описывает проверяющий
> прототип, а не принятую часть языка. Модель памяти берётся из
> [«Адреса и структуры данных»](addresses.md); ограничения хранимых ссылок и
> изъятия — из [аудита модели](addresses-defects.md).

## Задача

Компилятор должен по исходному коду Efen построить программу Viper, проверить её
Silicon или Carbon и вернуть ошибку в координатах Efen. Viper не исполняет
программу и не выбирает алгоритм за автора: он доказывает, что написанный
алгоритм соблюдает членство, права доступа и инварианты `layout`.

Первый прототип отвечает на четыре вопроса:

1. сохраняет ли операция объявленные инварианты;
2. обращается ли код только к живым блокам;
3. не остаётся ли сильных хранимых ссылок на изъятый блок;
4. не меняет ли операция память вне объявленного следа.

Генерация машинного кода, конкурентность, сырые адреса, FFI и доказательство
завершения произвольной рекурсии в прототип не входят.

## Архитектура

Прямой перевод AST Efen в строки Viper слишком рано связывает язык с одним
прувером. Между ними нужен нейтральный проверочный IR:

```text
исходный текст Efen
        │
        ▼
parser → AST → разрешение имён и типов
        │
        ▼
       VIR                 Verification IR
        │
        ├──→ Viper emitter → Silicon / Carbon
        └──→ другой backend в будущем
```

Frontend отвечает за правила самого Efen: происхождение ссылок, доступность
полей, якорь зависимого типа, законность `remove`, точки наблюдения. Backend
отвечает только за перевод уже явных обязательств VIR в язык конкретного
прувера.

Каждый узел VIR хранит `SourceSpan`: файл, начало и конец выражения Efen. Ни одно
сообщение Viper не должно показываться пользователю без обратного отображения.

## Проверяемое подмножество

Первая версия принимает:

- `layout`, `set`, `struct`, `var`, `let` и `fn`;
- ссылки на население одного экземпляра `layout`;
- чтение и запись полей;
- `if`, `while`, ограниченный `for`;
- `create`, `remove` и `take`;
- именованные инварианты населения `invariant name(item)`;
- `inverse`;
- контракты `requires`, `ensures`, `reads`, `modifies`, `creates`, `removes`;
- `region suspend` без выхода в непроверенный внешний код.

Слова контрактов в этом списке — предложение для проверяемого диалекта. Они не
считаются принятой грамматикой Efen до отдельного решения.

## Семантическая модель VIR

### Идентичность и живость

Ссылка и право разыменовать её — разные значения. Любой блок получает
стабильную логическую идентичность `Ref`. Для каждого населения существует
призрачное множество живых идентичностей:

```text
Population Nodes {
    element = Node
    live    = Set<Ref>
}
```

Типизированная ссылка гарантирует происхождение из `Nodes`, но доступ к полям
требует ещё и `p ∈ Nodes.live`. После изъятия идентичность `p` можно сравнивать,
однако разыменовывать её нельзя.

### Права принадлежат layout

Несколько ссылок на один блок не порождают несколько прав. Экземпляр `layout`
владеет правами на поля всех живых блоков:

```text
owns(Nodes) ≜
    ∀ n ∈ Nodes.live:
        write(n.value) * write(n.next) * ...
```

Знак `*` здесь означает разделяющую конъюнкцию, а не синтаксис Efen. Viper
backend реализует права через `acc`. Для первого прототипа операция получает
полные права на свой `layout`; дробные права для параллельного чтения можно
добавить позже.

### Сильные и слабые хранимые ссылки

Для каждого сильного поля `f`, ведущего в `Nodes`, frontend создаёт обязательство:

```text
∀ holder ∈ Holders.live:
    holder.f == null ∨ holder.f ∈ Nodes.live
```

Такой инвариант означает отсутствие висячих сильных ссылок. Он не сообщает, как
найти держателей во время исполнения. Изъятие допустимо, только если входящие
рёбра перечислимы через `inverse`, объявленное строение или явный обход. Иное
хранимое поле обязано быть `weak` и проверять поколение при доступе.

## Минимальный VIR

VIR не должен содержать `acc`, `inhale`, `exhale` или другие понятия Viper.
Достаточны следующие сущности:

```text
Module
  types:       Record[]
  populations: Population[]
  fields:      Field[]
  invariants:  Invariant[]
  procedures:  Procedure[]

Procedure
  parameters
  result
  preconditions
  postconditions
  footprint: { reads, writes, creates, removes }
  body

Statement :=
  Assign(place, value)
  Read(place)
  Assert(formula, obligationId)
  Assume(formula)
  If(condition, then, else)
  Loop(condition, invariants, body)
  Create(population, result, fields)
  Remove(population, reference)
  OpenInvariant(name)
  CloseInvariant(name)
  Call(procedure, arguments)

Formula :=
  Live(population, reference)
  CanRead(place)
  CanWrite(place)
  Eq | And | Or | Not | Implies
  ForEvery(domain, variable, formula)
  Old(formula)
```

Backend может выбирать собственное представление множеств, разрешений и
предикатов, пока сохраняет смысл этих операций.

## Алгоритм генерации

### 1. Разобрать и типизировать Efen

Parser строит обычный AST. Затем frontend:

1. разрешает экземпляр `layout`, которому принадлежит каждое население;
2. привязывает каждый `.pointer`, `.slot` и `.index` к вместилищу;
3. классифицирует ссылочные поля как `own`, сильные заимствованные или `weak`;
4. разворачивает поля, неявно объявленные через `inverse`;
5. отклоняет сырой адрес, который пытаются принять за ссылку населения.

После этого в VIR не должно остаться неразрешённых имён или ссылки с неизвестным
происхождением.

### 2. Построить описание layout

Для каждого `set Nodes: Node` создаются:

- символ населения `Nodes`;
- призрачное множество `Nodes.live`;
- список полей `Node`, требующих прав;
- инварианты населения;
- перечень входящих сильных отношений.

Для каждого обычного поля создаётся функция кучи `Field(holder) → value`. Поля
значений и поля-ссылки различаются типом результата, но права доступа к ним
вычисляются одинаково.

### 3. Развернуть `inverse`

Объявление:

```efen
inverse prev of next
```

порождает в VIR поле `prev`, инвариант пары и единственную атомарную операцию
перепривязки:

```text
RelinkNext(x, new):
    old = x.next
    if old != null: old.prev = null
    x.next = new
    if new != null: new.prev = x
```

Прямой `Assign(y.prev, ...)` frontend запрещает. Поэтому промежуточное нарушение
пары отсутствует в пользовательском VIR, а backend доказывает один шаблон
`RelinkNext`, а не каждую половину связи отдельно.

Для `{left, right}` в обратной стороне хранится также различитель ребра. Без него
равенство обратной пары неоднозначно.

### 4. Вычислить след операции

Из тела и явного контракта вычисляются четыре множества:

```text
reads    = места, значения которых читаются
writes   = места, в которые выполняется запись
creates  = населения, куда добавляются блоки
removes  = населения, откуда изымаются блоки
```

Явный контракт служит верхней границей. Если тело пишет в поле вне `modifies`,
frontend выдаёт ошибку до запуска Viper. Если контракт опущен, прототип может
вывести след для локальной функции, но публичная операция обязана сохранить его
в интерфейсе.

Слово `effect` для этого не используется: в Efen оно уже обозначает зависимость
от окружения.

### 5. Построить контракт прав

Для каждого чтения frontend добавляет `CanRead`, для записи — `CanWrite`. Для
публичной операции права группируются по населению и полю, а не перечисляются по
отдельным выражениям.

Концептуально:

```text
requires ∀ n ∈ Nodes.live: CanWrite(n.value)
ensures  ∀ n ∈ Nodes.live': CanWrite(n.value)
```

Viper backend переводит это в quantified permissions:

```viper
requires forall n: Ref :: { n.value }
    n in nodes ==> acc(n.value)

ensures forall n: Ref :: { n.value }
    n in nodesAfter ==> acc(n.value)
```

Триггеры выбирает backend; они не являются частью VIR и не видны в Efen.

### 6. Перевести выражения и разыменования

Перед чтением `p.value` VIR требует:

```text
Assert(Live(Nodes, p), use-after-remove)
Assert(CanRead(p.value), missing-read-permission)
Read(p.value)
```

Перед записью требуется `CanWrite`. Сравнение `p == q` не разыменовывает блок и
не требует его живости. Именно поэтому ссылку на изъятый объект допустимо
сравнить с `null` или другой идентичностью, но нельзя использовать для доступа к
полю.

### 7. Перевести `create`

`Nodes.create(...)` порождает свежую идентичность `n` и следующие шаги VIR:

```text
Assert(n ∉ Nodes.live)
AcquireFields(n)
InitializeFields(n)
Nodes.live' = Nodes.live ∪ {n}
Assert(PopulationInvariant(Nodes.live'))
```

Viper backend получает права нового блока через `inhale` либо через контракт
операции источника. Второй вариант предпочтителен для окончательной модели:
источник, а не пользовательский код, создаёт память.

### 8. Перевести `remove`

Для `Nodes.remove(victim)` frontend выполняет алгоритм:

1. доказать `victim ∈ Nodes.live`;
2. доказать право изменения членства `Nodes`;
3. найти все объявленные сильные отношения, способные указывать в `Nodes`;
4. проверить, что тело обнулило или перенаправило каждое входящее ребро;
5. восстановить `inverse` и инварианты населения;
6. установить `Nodes.live' = Nodes.live − {victim}`;
7. отдать backend операцию `ReleaseFields(victim)`;
8. не возвращать вызывающему прав на поля `victim`.

Viper backend реализует последний шаг потреблением разрешений:

```viper
exhale acc(victim.value) && acc(victim.next) && acc(victim.prev)
```

Это логическое изъятие, а не вызов `free`. Реальное освобождение, tombstone или
возврат блока арене выбирает runtime/source Efen.

Если произвольное число ссылок очищается проходом, автор пишет этот проход сам:

```efen
fn compact(victim: read Nodes.pointer)
    modifies Links.target
    removes victim from Nodes
{
    for link in Links {
        if link.target == victim {
            link.target = null
        }
    }

    Nodes.remove(victim)
}
```

Контракт задаёт доказываемый результат, но не генерирует обход. `Links` должен
быть перечислимым в реализации. Для двусвязного списка `inverse` уже является
локальным индексом входящего ребра, поэтому полного прохода нет.

Условие отсутствия ссылки на изъятый блок объявляется один раз при населении:

```efen
set Links: Link {
    invariant targetIsLive(link) {
        link.target == null || link.target in Nodes
    }
}
```

После `Nodes.remove(victim)` восстановление `targetIsLive` само требует доказать,
что обработан каждый `link`. Квантор появляется только в VIR и Viper, но не в
исходном Efen.

### 9. Перевести циклы

Viper требует инварианты циклов. Прототип получает их из четырёх источников:

1. права на неизменяемую часть `layout`;
2. инварианты населения, которые цикл не приостанавливает;
3. границы курсора и структурный факт обхода;
4. пользовательские `invariant`, если автоматического шаблона недостаточно.

Для очистки ссылок основной инвариант имеет вид:

```text
0 ≤ i ≤ holders.count
∀ j < i: holders[j].target != victim
∀ h ∈ holders: CanWrite(h.target)
```

Frontend обязан явно сохранить различность держателей или доказать, что
повторная запись идемпотентна. Иначе SMT-решатель справедливо допускает, что
текущая запись изменила уже обработанный элемент.

### 10. Обработать точки наблюдения

Инварианты `layout` должны быть закрыты перед возвратом, `throw`, внешним вызовом
и другим событием, перечисленным в `addresses.md`. В VIR это записывается явно:

```text
OpenInvariant(Nodes)
... изменения ...
CloseInvariant(Nodes)
ExternalCall(...)
```

Вызов соседней операции того же `layout` не становится внешней точкой
наблюдения, но вызываемая операция должна знать, какие инварианты сейчас открыты.
Для MVP такой вызов внутри `region suspend` лучше запретить; позже VIR может
передавать маску открытых инвариантов.

### 11. Сгенерировать Viper

Emitter создаёт:

- `field` для полей структур;
- `Set[Ref]` или доменный предикат для живого населения;
- `predicate` либо quantified permissions для владения населением;
- `method` для операций;
- `requires` и `ensures` из контрактов VIR;
- `assert` с устойчивым `obligationId`;
- `inhale`/`exhale` только для приобретения и потери прав;
- инварианты `while`.

Для каждого сгенерированного диапазона сохраняется таблица:

```text
Viper span → obligationId → Efen SourceSpan → код ошибки
```

### 12. Запустить backend и вернуть диагностику

Порядок проверки:

1. запустить Silicon как основной быстрый backend;
2. разобрать структурированный результат ViperServer;
3. найти `obligationId` или ближайший сгенерированный диапазон;
4. заменить внутренние термины `permission`, `exhale`, `Ref` понятиями Efen;
5. показать исходную строку и причину.

Например, сообщение Viper `insufficient permission to access m.value`
превращается в:

```text
error[memory.use-after-remove]: `m` мог быть изъят
  --> example.efen:24:10
   |
24 | echo m.value
   |      ^^^^^^^ поля изъятого блока недоступны
```

Carbon полезен как второй проверяющий backend в тестах. Несогласие Silicon и
Carbon считается ошибкой генератора, пока не доказано обратное.

## Пример полного понижения

Исходный фрагмент Efen:

```efen
layout List {
    set Nodes: Node

    struct Node {
        var value: Int
        var next: own other Nodes.pointer?
    }

    inverse prev of next

    fn unlinkMiddle(node: read Nodes.pointer)
        requires node.prev != null
        modifies Nodes.next
        removes node from Nodes
    {
        let before = node.prev
        before.next = node.next
        Nodes.remove(node)
    }
}
```

Существенная часть VIR:

```text
procedure List.unlinkMiddle(node):
    requires Live(Nodes, node)
    requires Read(node.prev) != null
    requires OwnsPopulation(Nodes)
    writes Relation(next, prev)
    removes Nodes[node]

    before = Read(node.prev)
    RelinkNext(before, Move(node.next))
    Assert(NoStrongIncoming(node), dangling-strong-reference)
    Remove(Nodes, node)
```

Существенная часть Viper:

```viper
method unlink(node: Ref, nodes: Set[Ref])
  requires node in nodes
  requires forall n: Ref :: { n.next }
    n in nodes ==> acc(n.next) && acc(n.prev) && acc(n.value)
  ensures forall n: Ref :: { n.next }
    n in nodes && n != node ==>
      acc(n.next) && acc(n.prev) && acc(n.value)
{
  // Сгенерированное раскрытие RelinkNext и проверки пары.
  ...
  exhale acc(node.next) && acc(node.prev) && acc(node.value)
}
```

Многоточие здесь означает механическое понижение `inverse`, а не доверенный
пользовательский код.

## Что является доверенной базой

Доказательство остаётся корректным только при согласованности четырёх частей:

1. parser и type checker правильно понимают исходный Efen;
2. перевод Efen AST → VIR сохраняет семантику;
3. Viper emitter сохраняет смысл VIR;
4. runtime реализует `create`, `remove`, поколения и источники так же, как они
   смоделированы.

Viper доказывает только полученную `.vpr`-программу. Ошибка генератора способна
породить доказанную программу, не соответствующую Efen. Поэтому каждый шаблон
понижения нуждается в положительных и отрицательных тестах.

Backend не должен использовать `assume` для факта, который обязан доказать
пользовательский код. Допустимые `assume` ограничиваются аксиомами уже
проверенной типовой системы и контрактами доверенных операций runtime.

## План реализации прототипа

### Этап 1. Сквозной минимальный пример

- parser одного файла и подмножества выше;
- типизация одного `layout`;
- VIR с `SourceSpan`;
- генерация Viper для полей, функций, контрактов и `remove`;
- запуск ViperServer;
- одна ошибка, отображённая обратно в Efen.

Критерий готовности: корректный двусвязный список принят, забытая обратная запись
и use-after-remove отвергнуты в координатах `.efen`.

### Этап 2. Населения и произвольные алиасы

- quantified permissions;
- именованные инварианты над перечислимым населением;
- циклы с явными инвариантами;
- операция, очищающая произвольное число входящих ссылок;
- проверка `modifies` и frame conditions.

Критерий готовности: `compact` доказывается для любого числа держателей, а не для
заранее перечисленных `h1`, `h2`.

### Этап 3. Инварианты layout

- автоматическое открытие и закрытие;
- точки наблюдения;
- `region suspend`;
- вызовы между операциями одного экземпляра;
- `create`, `take` и обработка всех выходов.

### Этап 4. Независимость backend

- стабилизировать VIR отдельно от Viper emitter;
- прогонять корпус через Silicon и Carbon;
- добавить второй экспериментальный emitter или интерпретатор VIR;
- запретить появление Viper-специфичных конструкций во frontend.

## Набор обязательных тестов

Положительные:

- изменение значения живого блока;
- несколько локальных ссылок на один живой блок;
- удаление узла двусвязного списка;
- очистка всех сильных ссылок проходом;
- сравнение идентичности после `remove` без разыменования;
- `weak`-ссылка сообщает отсутствие после смены поколения.

Отрицательные:

- чтение поля после `remove`;
- забытая входящая сильная ссылка;
- запись вне `modifies`;
- изъятие при живом несовместимом обходе;
- ручная запись в поле, объявленное через `inverse`;
- выход из `region suspend` с невосстановленным инвариантом;
- передача ссылки между населениями одного типа;
- принятие сырого адреса за `Nodes.pointer`.

Каждый отрицательный тест проверяет не только отказ Viper, но и стабильный код
ошибки Efen и правильный `SourceSpan`.

## Открытые решения

До реализации полного frontend нужно зафиксировать:

1. точную грамматику `reads`, `modifies`, `creates`, `removes`;
2. является ли контракт обязательным у публичной операции;
3. как в Efen записываются пользовательские инварианты цикла;
4. когда население физически перечислимо и какой ценой;
5. представляется ли владение population predicate или quantified permissions;
6. какие свойства источника памяти считаются доверенными;
7. какие операции разрешены при открытом `region suspend`;
8. обязаны ли Silicon и Carbon принимать один и тот же поддерживаемый фрагмент.

Эти решения не блокируют первый сквозной прототип. Для него достаточно одного
`layout`, полного права на экземпляр, последовательности перечислимых держателей
и явного контракта операции.
