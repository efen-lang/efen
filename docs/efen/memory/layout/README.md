# Layout

[Память](../README.md) · [Таблица правил](../memory-rules.md) · [Сырая память](../pointer.md) ·
[Примеры](../layout-examples/README.md) · [Каталог структур](../layout-catalogue.md) · [Условия и доказательства](../../conditions.md)

`layout` описывает указатели между разными структурами так, чтобы компилятор мог формально проверить корректность
работы с памятью.

Структуры данных чаще всего сложные: они состоят из указателей на другие структуры. Многие языки программирования
этого никак не выражают, поэтому компилятор не может доказать корректность такого кода.

## Зачем нужен `layout`

В структуре со связями на один узел указывает несколько указателей. Когда узел освобождён, остальные указатели на
него становятся висячими. В двусвязном списке на каждый узел указывают `next` предыдущего узла и `prev` следующего:

```c
struct Node { struct Node *next, *prev; int value; };

void remove_first(struct List *list) {
    struct Node *first = list->head;
    list->head = first->next;
    free(first);                  // list->head->prev по-прежнему хранит адрес first
}
```

Компилятор C эту функцию принимает: он не знает, что `prev` связан с `next`. В безопасном Rust такая связь не
выражается, потому что у узла один владелец. Второй указатель на узел там пишут двумя способами.
`Rc<RefCell<Node>>` добавляет счётчик и проверку при выполнении. Сырой указатель в `unsafe` оставляет
доказательство программисту.

В Efen программист объявляет связь. Он пишет, что `next` владеет узлом, а `prev` только указывает на него. Он
пишет и условие, верное для каждого узла: `next!.prev == self`. Из этой записи компилятор знает, где хранится
каждый указатель на узел. Функцию удаления он принимает, только если до освобождения узла она переписала все эти
указатели. Счётчик, проверка при выполнении и `unsafe` не нужны.

## 1. Что такое layout

**Правило.** `layout` объявляет память структуры данных: множества элементов, владение ими, указатели между ними и
то, что получает внешний код. Всё, чего `layout` не объявил, запрещено.

**Пример.** Двусвязный список. Узлы составляют множество `Items`, поле `next` владеет следующим узлом, поле `prev`
только указывает на предыдущий.

```efen
layout {
    set Items: Item

    struct Item {
        var value: Int
        var next: anchor Items.Item? = null      // владеет следующим узлом
        var prev: Items.Item? = null             // указывает на предыдущий, не владеет
    }
}
```

**Запрещено.** У каждого множества есть владелец: владеющее поле или строка `public own Nodes`. В этой строке `Nodes`
называет множество: она разрешает функциям кода `layout` отдавать внешнему коду элемент множества `Nodes` целиком и
принимать его обратно (раздел 3.5). Множество, у которого нет ни такого поля, ни такой строки, вызывает ошибку (раздел
3.4). Хранимый невладеющий указатель указывает только внутрь своей публичной структуры (разделы 3.3 и 4.3). Внешний
код получает во владение только то, что `layout` назвал. Указатель, использованный после уничтожения его цели,
вызывает ошибку компиляции: компилятор показывает её в строке изменения структуры и отдельно показывает строку
использования.

**Почему.** Два поля или два параметра указывают на одну память, только если это объявлено явно
([поля не делят память](../../types/ownership.md#поля-не-делят-память)). Способов объявить два. Первый способ:
право с источником, `право<поле или параметр>`. Так пишутся поле-псевдоним `current: read<self.children> Node?`,
поле `items: read<Src> Array<T>` и параметр `src: read<dst?> T`. Второй способ: `layout`. По объявлениям `layout`
компилятор доказывает два свойства. Ни один указатель не используется после уничтожения цели. Каждый слот, выданный
внешнему коду, возвращается, а каждый элемент, которым владеет поле или переменная, доведён до конца: компилятором по плану или явным кодом
(раздел 7.4).

Доказывает эти свойства FLOW, анализатор потока в компиляторе. Условия, которые FLOW не доказывает сам, он
передаёт решателю Z3. Место, где компилятор принимает факт без доказательства, называется точкой доверия. Точка
доверия бывает только объявленной. Видов шесть: строка `assume`; условие результата у вставки
`@asm`; объявление без тела, которому компилятор верит по записи (функция C с правами из `@fill`, код `model`);
приведение адреса к элементу множества или к выданному слоту (раздел 4.5); объявление функции `@abi(c)` с телом;
запись `thread var x: own T` со значением типа, который не соответствует `ImplicitlyDestroyable` (раздел 7.4).
Аргументы функции `@abi(c)` выбирает C. О функции без слова `shared` компилятор ещё принимает, что C вызывает её в одном
потоке этого контекста и не одновременно с остальным его кодом; у `shared @abi(c)` этого предположения нет, остальное доверие то же (раздел 9.1, правило 4). Все точки
доверия пакета печатает `efen proofs`. Полный список мест, которые компилятор принимает на веру, приведён в статье о
[системных вызовах](../system.md#кому-доступно-доверие).

Экземпляров у `layout` нет. `layout` стоит на уровне модуля и только описывает память. Значения создают его
структуры (раздел 2.3).

<a id="layout-в-теле-класса"></a>

Слово `layout` в теле класса, интерфейса или контракта означает другое. Там оно описывает не байты, а то, что
заимствует внешний код, и физических объявлений (`set`, `area`, `one`, `struct`) не содержит. Его правила стоят в
статье о классах: [`layout` в теле класса](../../classes.md#layout-в-теле-класса).

Куда дальше: что именно объявляется, перечисляет раздел 2.
