## 10. Расширение layout

Расширение добавляет к базовому `layout` свои множества и структуры с указателями в его множества. Базовый `layout`
при этом не меняется: его множества, структуры, функции и доказательства остаются в одном экземпляре. Раздел
опирается на границу кода `layout` (2.5), владение (3.4), правило чистоты (4.3 и 4.4), сводку функции (8.4) и
интерфейс пакета (8.7).

Два примера ниже используются во всех подразделах.

```efen
// Пример D: базовый layout, пакет lists, модуль linked
open layout Lists<T: Movable> {
    set Nodes: Node

    public struct Node {
        protected var value: T                           // пишет код расширений; внешний код читает функцией
        protected var next: anchor Nodes.Item? = null
        protected var prev: Nodes.Item? = null
        invariants { next == null || next!.prev == self }
    }

    public struct DoublyList {
        protected var head: anchor Nodes.Item? = null
        protected var tail: Nodes.Item? = null
        public var length: Int = 0 { value >= 0 }

        invariants {
            let nodes = Nodes.chain(from: head, by: Node.next, until: null)
            tail == nodes.last
            length == nodes.count
        }
    }
}

strategy<T> for DoublyList<T> {
    public read fn first -> read T? {
        // тело не важно для примера: читает protected-поле value первого узла
    }
    public edit fn pushFirst(value: own T) {
        // тело не важно для примера: новый узел записан в head
    }
    public mut fn removeLast -> own T? {
        // тело не важно для примера; сводка: уничтожает узел tail
    }
}

strategy<T> for DoublyList<T> {
    implements Disposable

    fn dispose {                                         // вызывает только компилятор (раздел 7.4)
        tail = null                                      // хранимого указателя на последний узел не остаётся
        while let node = tie head {
            head = tie node.next
            if let next = head { next.prev = null }      // указатель на node переписан до as own
            let dead = node as own Nodes<T>.Item         // в конце шага value уничтожается, память возвращается
        }
        length = 0
    }
}

// Пример E: расширение, пакет cache
use lists::linked

layout<K: Hashable, V: Movable>: lists::Lists<Entry<K, V>> {     // расширение без open имени не имеет
    area Buckets: Bucket

    public struct Entry { let key: K; var value: V }
    struct Bucket { var node: Lists<Entry>.Nodes.Item? = null }      // указатель в множество базового

    public struct Lru {
        DoublyList<Entry>                                // значение базовой структуры первым полем
        private var buckets: Int = 0 { value >= 0 }
        private var table: own Buckets.Area? = null { value == null || value.count == buckets }
        invariants {                                     // на узел указывает только корзина его ключа
            forall i in 0 ..< buckets: table![i].node == null || hash(table![i].node!.value.key) % buckets == i
        }
    }
}

strategy<K, V> for Lru<K, V> {
    public edit fn touch(key: read K) {
        let n = find(key) ?? return
        moveToFront(n)                                   // узел n переставлен в начало списка
    }

    public override mut fn removeLast -> own Entry<K, V>? {
        let last = tail ?? return null
        clearBucket(last.value.key)                      // указатель на узел убран из таблицы до вызова
        return self.DoublyList.removeLast()              // функция базового: уничтожает узел tail
    }

    private read fn find(key: read K) -> read<self> Lists<Entry<K, V>>.Nodes.Item? {
        // тело не важно для примера: читает корзину ключа
    }
    private edit fn moveToFront(node: read<self> Lists<Entry<K, V>>.Nodes.Item) {
        // тело не важно для примера: пишет protected-поля next, prev, head и tail
    }
    private edit fn clearBucket(key: read K) {
        // тело не важно для примера: записывает null в корзину ключа
    }
}

strategy<K, V> for Lru<K, V> {
    implements Disposable

    fn dispose {                                         // освобождает таблицу; список освобождает его dispose
        if let old = take table {
            var i = 0
            while i < buckets {
                let bucket = take old[i]                 // корзина хранит только невладеющий указатель
                i += 1
            }
        }                                                // old кончается: ни один слот не инициализирован
        buckets = 0
    }
}
```

### 10.1 open layout и запись расширения

**Правило.** Расширяется только `layout`, объявленный со словом `open`. У `open layout` есть имя, и расширение
называет его после двоеточия вместе с аргументами: `layout<K, V>: lists::Lists<Entry<K, V>>`.

Дополнительные правила:

1. Имя пишется после слова `layout`, параметры после имени: `open layout Lists<T: Movable>`. Имя есть только
   у `open layout`. Расширение без `open` имени не имеет и пишет параметры сразу после слова `layout`:
   `layout<K, V>: lists::Lists<Entry<K, V>>`. Расширение со словом `open` получает имя, как любой
   `open layout`: `open layout Cache<K, V>: lists::Lists<Entry<K, V>>`.
2. Имя `layout` типом не служит: экземпляров у `layout` по-прежнему нет (раздел 2.3).
3. Аргументом базового `layout` может быть структура самого расширения: `Entry<K, V>`. Так расширение передаёт свои
   данные в каждый элемент базового (раздел 10.2, правило 5).
4. Базовый `layout` у расширения один. Расширение само может быть объявлено `open`, и тогда оно служит базовым для
   следующего расширения.
5. Свои множества, области и структуры расширение объявляет по общим правилам: у каждого множества есть владелец
   (раздел 3.4). К базовому `layout` оно ничего не добавляет: ни поля, ни инварианта, ни строки `public own` или
   `public lend` к его структурам и множествам.
6. Вне базового `layout` его множество пишется через имя `layout` с аргументами: `Lists<Entry>.Nodes.Item`.
   Структуры пишутся, как у любого `layout` с параметрами: `DoublyList<Entry>` (раздел 2.4, правило 2).
7. Расширению нужен только интерфейс базового `layout` (раздел 10.6). Тела его функций расширение не читает.

**Пример.** Пример D объявляет `open layout Lists<T>`. Пример E расширяет его: расширение добавляет область
`Buckets` и структуры `Entry`, `Bucket` и `Lru`, а узлы списка остаются элементами множества
`Lists<Entry<K, V>>.Nodes`.

**Запрещено.**

- Имя у `layout` без `open` вызывает ошибку, в том числе у расширения.
- `private open layout` вызывает ошибку: `open` разрешает расширение из других пакетов, а `private` закрывает
  `layout` в одном модуле.
- После двоеточия стоит одно имя `open layout`. Имя структуры и второе имя вызывают ошибку.
- Поле, инвариант или строка `public own` и `public lend`, которые расширение добавляет к структуре или множеству
  базового, вызывают ошибку.

**Почему.** Базовый `layout` остаётся в одном экземпляре, поэтому расширение не затрагивает ни его доказательств,
ни его памяти, ни его собранного кода: тела его функций повторно не проверяются, а размеры его элементов не
меняются. Имя нужно, чтобы расширение назвало, какой `layout` оно расширяет и с какими аргументами.

### 10.2 Указатели в множества базового

**Правило.** Структура расширения хранит невладеющие указатели на элементы множеств базового `layout` и хранит
значение базовой структуры, которой эти элементы принадлежат.

Дополнительные правила:

1. Держателем ниже называется поле структуры расширения, которое хранит указатель в множество базового: прямо
   (`var node: Lists<Entry>.Nodes.Item?`) или в аргументе типа (`Map<K, Lists<Entry>.Nodes.Item>`).
2. По правилу чистоты (раздел 4.3) держатель и его цель находятся в одной публичной структуре. Поэтому структура
   расширения хранит значение базовой структуры: первым полем без имени
   ([наследование по началу](../pointer.md#встраивание-первым-полем--наследование-по-началу)) или в поле с именем.
3. Элементами базовых множеств владеют поля базовой структуры. Полей `own` и `anchor` с типом элемента базового
   множества расширение не объявляет.
4. Права `edit` и `mut` на значение базовой структуры внутри структуры расширения получает только код расширения.
   Внешний код это значение только читает, а изменяет структуру функциями расширения.
5. Данные расширения на каждый элемент базового передаются аргументом типа: при `Lists<Entry<K, V>>` каждый узел
   хранит `Entry`. Значение аргумента подчиняется разделу 2.4 (правило 4).
6. Аргумент типа может сам хранить указатели в множества того же `layout` с теми же аргументами: `Entry` с полем
   типа `Lists<Entry>.Nodes.Item?`. Значение базовой структуры с таким аргументом с правами `edit`, `mut` и `own`
   использует только код расширения.

**Пример.** В примере E держателем служит `Bucket.node`. `Lru` хранит `DoublyList<Entry>` первым полем, поэтому
узлы списка и корзины таблицы составляют одну публичную структуру, и `Lru` чиста. Внешний код работает с ней
функциями расширения:

```efen
var cache = Lru<String, Int>()
cache.touch("a")
let entry = cache.removeLast()                 // функция расширения: держатель переписан до вызова базовой
print(cache.length)                            // можно: чтение
cache.pushFirst(value: Entry(key: "b", value: 2))   // ошибка: функция базового с получателем edit во внешнем коде
```

**Запрещено.**

- Поле `own` или `anchor` с типом элемента базового множества в структуре расширения вызывает ошибку.
- Держатель, цель которого находится в другой публичной структуре, вызывает ошибку у записи указателя (раздел 4.3).
- Вызов функции базового `layout` с получателем `edit` или `mut` у значения внутри структуры расширения во внешнем
  коде вызывает ошибку.

**Почему.** Указатели таблицы в узлы списка существуют только внутри одной публичной структуры (раздел 4.5).
Значение базовой структуры в поле структуры расширения делает узлы и держатели частями одной публичной структуры, и
она переходит к другому владельцу и в другой поток целиком. Функция базового о держателях не знает и инвариантов
расширения не восстанавливает. Поэтому внешний код вызывает её только через функцию расширения, даже когда она
объявлена `edit` и ни одного элемента не уничтожает.

### 10.3 Вызов, который уничтожает цель держателя

**Правило.** Перед вызовом, сводка которого уничтожает элемент X базового множества или выводит его из структуры
(раздел 8.4), ни один держатель расширения не равен X и ничему из того, чем X владеет.

Дополнительные правила:

1. Что вызов делает с элементами, код расширения узнаёт из сводки вызванной функции: пометки «уничтожает» и
   «отдаёт» называют элемент путём от параметра или получателя (`tail`).
2. Условие доказывает FLOW в строке вызова по инвариантам расширения. Держатель переписан до вызова, а не к выходу
   функции расширения.
3. Сводка, которая не называет элемент точно («может уничтожить»), требует очистить до вызова каждый держатель в
   это значение базовой структуры.
4. Вызов `edit` держателей не затрагивает: ни один элемент не перенесён и не уничтожен (раздел 6.1).
5. Локальные указатели и ссылки кода расширения подчиняются разделу 7.1 без изменений.

**Пример.** В примере E `removeLast` сначала вызывает `clearBucket`, а затем функцию базового. Инвариант `Lru`
говорит, что на узел указывает только корзина его ключа, поэтому после `clearBucket(last.value.key)` ни один
держатель не равен `tail`. Без этой строки компилятор отвергает вызов:

```efen
public override mut fn removeLast -> own Entry<K, V>? {
    // ошибка: Bucket.node может указывать на узел, который уничтожает этот вызов
    return self.DoublyList.removeLast()
}
```

**Запрещено.** Вызов без доказательства вызывает ошибку в своей строке. Сообщение называет держатель и пометку
сводки.

**Почему.** В одном `layout` функция, которая освобождает элемент, сама находит указатели на него по инвариантам
(раздел 6.5). Функция базового инвариантов расширения не видит и держателей найти не может. Поэтому доказательство
переходит к вызывающему: свои держатели он знает, а действие функции читает из её сводки. Держатель, переписанный
только после вызова, во время вызова указывал бы на освобождённую память.

### 10.4 protected

**Правило.** Поле с пометкой `protected` в `open layout` читает и пишет код базового `layout` и код его расширений.
Функцию `protected fn` вызывает тот же код.

Дополнительные правила:

1. Правила `self`, которое действует на `protected` в классах ([видимость](../../visibility.md)), здесь нет: код
   расширения пишет `protected` поле любого значения базовой структуры, на которое у него есть право записи.
2. Остальные поля базового `layout` код расширения из другого пакета не пишет: для них он внешний код (раздел 2.5).
   Расширение из пакета базового `layout` относится к коду базового: оно пишет все его поля, и правила 5 и 6 на
   него не действуют.
3. Инвариант базового `layout`, который читает `protected` поле, читает только поля `protected` и `public`. Такой
   инвариант входит в интерфейс (раздел 10.6).
4. Функция расширения, которая пишет `protected` поля, проверяется как функция базовой структуры: она доказывает
   эти инварианты в местах раздела 5.1.
5. Запись `protected` полей в коде расширения остаётся в пределах `edit`: каждый элемент базового остаётся в своей
   структуре, на своём адресе и в своём виде.
6. Создаёт элемент базового, уничтожает его, выводит из структуры и меняет его вид только функция базового
   `layout`.
7. `protected fn` принимает и возвращает `anchor`: для неё код расширения не внешний код (разделы 3.2 и 3.5).
   Освободить элемент под таким якорем код расширения не может (правило 6): он возвращает якорь функции базового.
8. Данные, которые расширение передаёт в элемент базового аргументом типа (`Node.value`), базовый `layout`
   объявляет `protected`. Право сужается вдоль пути, поэтому запись внутрь `n.value` идёт по модификатору базового
   поля `value`: код расширения её пишет, а внешний код читает значение функцией базового (`first` в примере D).
9. По цепочке расширений `protected` действует на каждом уровне: расширение расширения читает и пишет `protected`
   поля каждого `layout` под собой. Условие раздела 10.3 каждый уровень доказывает для своих держателей по сводкам
   функций уровня под ним.

**Пример.** `moveToFront` из примера E пишет `protected` поля `next`, `prev`, `head` и `tail`. Все узлы остаются в
списке, поэтому функция объявлена `edit` и доказывает инварианты `Node` и `DoublyList`. Функции, которые передают
якорь коду расширения, базовый `layout` объявляет так:

```efen
strategy<T> for DoublyList<T> {
    protected mut fn cut(node: read<self> Lists<T>.Nodes.Item) -> anchor Lists<T>.Nodes.Item {
        // тело не важно для примера: вырезает узел из цепочки и отдаёт его якорь
    }
    protected edit fn linkFirst(node: anchor Lists<T>.Nodes.Item) requires node.next == null {
        // тело не важно для примера: записывает узел в head
    }
}
```

**Запрещено.**

- Инвариант, который читает `protected` поле вместе с полем без `protected` и без `public`, вызывает ошибку у
  инварианта.
- Приведения элемента базового (`as`, `as own`, `as Pointer`, смена вида) в коде расширения вызывают ошибку.
- Запись `protected` поля в коде расширения, после которой элемент базового ушёл из своей структуры, вызывает
  ошибку.
- Пометки «читает любой код, пишут расширения» нет. Для чтения внешним кодом базовый `layout` объявляет функцию.
- Слово `protected` у поля или функции в `layout` без `open` вызывает ошибку: расширений у такого `layout` нет.

**Почему.** Код, который пишет поле, восстанавливает каждый инвариант над этим полем, а для этого видит все поля,
которые инвариант читает. Поэтому инвариант над `protected` полем скрытых полей не читает и входит в интерфейс.
Предел `edit` оставляет за базовым кодом всё, что требует поиска указателей: создание, уничтожение и переход
элемента. Поэтому выводы базовых функций о времени жизни верны при любом расширении.

### 10.5 Переопределение функции

**Правило.** Функция расширения с именем, параметрами и правом получателя функции базовой структуры пишется со
словом `override`. Какая из двух функций вызвана, определяет статический тип получателя.

Дополнительные правила:

1. Правило относится к стратегии структуры, которая хранит значение базовой структуры первым полем без имени. У
   значения такой структуры по имени вызываются и функции базовой структуры: в коде расширения все, во внешнем коде
   только с получателем `read` (раздел 10.2, правило 4).
2. Код базового `layout` всегда вызывает функции базового: на его вызовы переопределение не действует. Таблицы
   виртуальных функций у структуры нет.
3. Функцию базового код расширения вызывает через встроенное поле: `self.DoublyList.removeLast()`.
4. Слов `super` и `open fn` в `layout` нет.
5. Соответствие контрактам (`conforms`) структура расширения объявляет сама и целиком: от базовой структуры оно не
   переходит.
6. `dispose` структуры расширения освобождает поля расширения. Встроенное значение базовой структуры после него
   освобождает `dispose` базовой стратегии, как любое поле, которое соответствует `ImplicitlyDestroyable`
   (раздел 7.4). Слово `override` у `dispose` не пишется: у каждой структуры своя реализация `Disposable`.
7. Слово `override` требует функции базовой структуры с тем же именем, теми же параметрами и тем же правом
   получателя. Функция с тем же именем и другими параметрами или другим правом получателя составляет перегрузку и
   пишется без `override`. Среди перегрузок, которые различаются только правом получателя, вызов выбирает по
   своему праву: самую узкую подходящую или ту, которую вызов называет, `(mut self).f()`
   ([правила выбора стратегии](../../strategies.md#правила-выбора-стратегии)).

**Пример.** В примере E `Lru.removeLast` объявлена `override`: у `DoublyList` есть функция с тем же именем,
параметрами и правом получателя `mut`. Вызов `cache.removeLast()` у значения типа `Lru` попадает в функцию
расширения, а вызов `removeLast` в коде пакета `lists` попадает в функцию базового.

**Запрещено.** Функция расширения с именем, параметрами и правом получателя функции базовой структуры без слова
`override` вызывает ошибку. Функция с тем же именем и параметрами, но с другим правом получателя составляет
перегрузку по праву ([части объекта](../../types/parts.md)) и пишется без `override`. Слово `override` у функции,
которой в базовой структуре нет соответствия по правилу 7, тоже вызывает ошибку.

**Почему.** Базовый код собран и доказан без расширения, поэтому вызов из него в функцию расширения попасть не
может. Слово `override` сообщает читателю, что у значения расширения это имя вызывает другую функцию, чем у
значения базовой структуры.

Куда дальше: что базовый `layout` публикует для расширений, перечисляет раздел 10.6.

### 10.6 Интерфейс open layout

**Правило.** У `open layout` в интерфейс пакета входят, кроме строк и функций из раздела 8.7, поля `protected`,
инварианты над ними и сводки функций `public` и `protected`.

Дополнительные правила:

1. Тела функций в интерфейс не входят. Расширение пишется и проверяется по интерфейсу, поэтому базовым может
   служить `open layout` из пакета без исходного текста.
2. Изменение, после которого сводка функции уничтожает или выводит из структуры больше, чем раньше, несовместимо:
   расширение доказало условие раздела 10.3 по прежней сводке.
3. Добавить функцию в базовый `layout` значит сделать изменение, совместимое для доказательств и для собранного
   кода: внешний код не вызывает её с правом записи у значения внутри структуры расширения (раздел 10.2,
   правило 4). Расширение, у которого уже есть функция с тем же именем, параметрами и правом получателя, при
   следующей сборке добавляет к ней слово `override` (раздел 10.5).
4. Печать называет базовый `layout` в заголовке расширения и в имени множества, на которое указывает внутренняя
   структура расширения.
5. Точки доверия кода расширения `efen proofs` печатает в пакете расширения.

**Пример.** Печать для примера E:

```
layout: lists::Lists, пакет cache

Buckets     по полю: Lru.table (own); наружу не уходит
Lru         значение; освобождает dispose; публичная
Bucket      внутренняя в Lru; нечистая: указывает на lists::Lists.Nodes
```

**Запрещено.** Расширение не опирается на тело функции базового `layout`: условие, которого нет в её сводке и в
опубликованных инвариантах, для кода расширения не доказано.

**Почему.** Интерфейс перечисляет всё, на что расширение вправе опираться: какие поля оно пишет, какие инварианты
восстанавливает и что каждая функция базового делает с элементами. Тела для этого не нужны, поэтому расширяется и
`open layout` из собранного пакета.
