## Зачем она нужна

Безопасный код Efen компилятор доказывает до запуска: происхождение, живость,
инициализацию, границы и права ([компоновка](addresses.md)). Непроверенными остаются
места, где программа верит на слово. Чаще всего это адрес, пришедший из C или из
аллокатора ([«Память, пришедшая из C»](pointer.md#память-пришедшая-из-c)): программа
верит, что по адресу лежит память и что в этих байтах нет другого живого объекта.

Проверочная сборка записывает каждое такое обещание в таблицу и останавливает
программу при первом нарушении. Так же поступает Miri для Rust, только Miri
проверяет каждую операцию: небезопасный код Rust может нарушить правила где угодно.
В Efen безопасный код уже доказан, поэтому проверяются только границы доверия.

Пример ошибки, которую без этой сборки не видит ничто. Пул блоков на Efen получает
память от ОС через `mmap` и раздаёт блоки коду на C. C по ошибке возвращает один
блок дважды:

```c
uint64_t a = poolGet();
poolPut(a);
poolPut(a);          // второй возврат того же блока
uint64_t b = poolGet();
uint64_t c = poolGet();  // b == c: один блок у двух владельцев
```

Блок попадает в список свободных дважды, и два следующих `poolGet` отдают его двум
владельцам. Обычная сборка молчит. ASan тоже молчит: память получена через `mmap`,
а не через `malloc`, и в его теневой памяти её нет.

## Что делает компилятор

Исходный код не меняется. В проверочной сборке компилятор вставляет вызовы
проверки в пять видов мест:

| Место | Что записывается или проверяется |
|---|---|
| Байты становятся объектом структуры | Запись «жив, принят здесь». Наложение на чужой живой объект — ошибка |
| Обращение к полю через указатель, передача адреса в C | Объект ещё жив |
| Объект отдан наружу и закончился | Запись «отпущен здесь». Отпустить мёртвый — ошибка |
| Объект класса создан выделением памяти | Запись «жив, создан здесь». Наложение на живой объект класса — ошибка |
| Объект класса уничтожается | Он жив и ещё не умирает; после деструктора запись «уничтожен здесь» |

В обычной сборке ничего из этого нет: передача адреса наружу и завершение объекта
дают тот же машинный код, что и без проверки.

Таблица хранит записи в дереве, упорядоченном по адресу начала, с кэшем последних
найденных записей. Память под таблицу берётся прямо у ОС, мимо `malloc`: проверяемая
программа сама может быть аллокатором, и запись, выделенная её же `malloc`, снова
вызвала бы проверку.

## Жизнь экземпляра

Объект структуры, принятый в байтах пула или аллокатора:

```
нет записи ──принят──▶ жив ──отдан наружу──▶ отпущен (помнит, где)
                        ▲                         │
                        └──те же байты приняты────┘
```

Объект класса:

```
память от malloc ──создан──▶ жив ──начал умирать──▶ умирает ──деструктор──▶ уничтожен
```

Закончившийся объект не стирается сразу. Запись помнит, где он родился и где умер,
пока эти байты снова не станут объектом. Поэтому отчёт говорит не только «мёртв»,
но и «где умер».

Принять живой объект ещё раз по тому же адресу и с тем же видом можно: так функция
смотрит на адрес, который держит C. Ошибка — только другие байты поверх живого
объекта или те же байты под другим видом.

## Что ловится

Отчёт называет место ошибки, место рождения объекта и, если он умер, место смерти.
Затем программа аварийно останавливается.

**Два живых объекта в одних байтах.** Новый объект кладут поверх живого, например
когда C освободил память, которую Efen ещё считает своей.

**Двойной возврат блока.** Пример из начала статьи ловится при второй выдаче блока:

```
amber check: a use of no live instance at 0x7f7861df0000 in poolGet, node 12;
the instance of Blocks at 0x7f7861df0000 was accepted in poolPut, node 32
and released in poolGet, node 28
```

Ловится при выдаче, а не при втором возврате: возврат может быть просто взглядом на
адрес, который держит C, и отличить его от передачи владения можно будет только по
владеющему указателю.

**Обращение к мёртвому объекту класса.** C уничтожает объект дважды:

```c
void* item = makeTracked(1);
efen_object_die(item);
efen_object_die(item);
```

Второе уничтожение ловится до того, как деструктор запустится снова. Если аллокатор
уже отдал эти байты под другое, отчёт называет обоих:

```
amber check: a use of no live instance at 0x7ffff79f0100 in efen_object_die;
the instance of Slots at 0x7ffff79f0100 was accepted in freeSlot, node 6;
before it, an instance of Tracked there ended in efen_object_die
```

Так же ловятся изменение счётчика ссылок у мёртвого объекта и обращение к полю
мёртвого объекта.

Проверка уже нашла две ошибки в аллокаторе, написанном на Efen: освобождённый слот
выдавался наружу живым, а свободные слоты пустого блока оставались живыми после
возврата блока в пул.

## Утечки при выходе

Когда программа завершается через возврат из `main` или `exit`, проверка ищет
живые объекты класса, до которых больше нельзя дойти:

```c
makeTracked(1);                       // C бросает объект и не уничтожает его
efen_object_die(makeTracked(2));
printf("ok dropped\n");
```

```
ok dropped
amber check: a leak at 0x7ffff79f0100: the instance of Tracked was made in makeTracked, node 1
amber check: 1 class instances live at exit that nothing reaches
```

Корни поиска те же, что у LeakSanitizer на одном потоке:

- записываемые сегменты всех загруженных модулей: статические данные Efen и
  глобальные переменные C;
- стек от места поиска до дна, то есть все кадры вызова `exit`.

Объект достижим, если машинное слово в корне или в уже достижимом объекте равно
адресу его начала. Заголовок объекта (счётчик и описатель) не просматривается.
Указатель внутрь объекта не считается: Efen таких не делает, база наследника лежит в
его начале.

Поиск идёт после всех деструкторов C, потому что они ещё могут уничтожать объекты.
Сначала печатается вывод самой программы, затем первые десять утечек и их общее
число.

Поиск консервативный. Число, случайно равное адресу объекта, или старая ячейка
стека спасают объект от отчёта. Поэтому поиск скорее пропустит редкую утечку, чем
назовёт утечкой нужный объект.

## Цена

Замер на тесте аллокатора: 100 000 операций, около миллиона живых объектов в
таблице, по одному прогону (2026-10-23):

| Оптимизация | Обычная сборка | Проверочная | Во сколько раз |
|---|---|---|---|
| -O2 | 0,7 с | 3,7 с | ≈5× |
| -O0 | 1,0 с | 5,3 с | ≈5× |

На коде, который почти не работает с указателями из-за границы доверия, добавка
меньше: проверки стоят только в местах доверия.

## Сравнение с ASan и Miri

| Инструмент | Как работает | Что видит | Цена |
|---|---|---|---|
| ASan | теневая память на каждые 8 байт, запретные зоны вокруг выделений | выход за границы и обращение к освобождённому в памяти `malloc`; пулы на `mmap` не видит | ≈2× |
| Valgrind Memcheck | двоичная трансляция готовой программы | обращение к освобождённому и за границы кучи, часть чтений неинициализированного | 10–50× |
| Miri | интерпретатор: у каждого байта состояние, у указателя происхождение | больше всех, включая нарушения заимствований; вызовы C почти не поддерживает | 100–1000× |
| Проверочная сборка Efen | вызовы только на границах доверия, таблица по адресам | наложение объектов, двойной возврат, доступ к мёртвому, утечки; работает с C и с собственным аллокатором | ≈5× |

Цифры ASan, Valgrind и Miri взяты из их документации, мы их не мерили.

Указатель в проверочной сборке остаётся голым адресом. Метку в старших битах, как у
HWASan, отвергли: указатель записывается в память, которую читает C, и сравнение
указателей изменилось бы.

## Чего она пока не ловит

- Запись сырых байтов поверх живого объекта и объекты, оставшиеся живыми после
  уничтожения пула.
- Старый указатель на адрес, где уже живёт новый объект того же вида (ABA).
  Сюда же — вторая смерть объекта класса после того, как аллокатор отдал адрес новому
  объекту. Нужен карантин освобождённых адресов.
- Запись из C по адресу, который C получил законно.
- Обращение к мёртвому объекту класса через прямой вызов метода, который не читает
  полей.
- Утечку, которую прикрыло старое слово на стеке, и объект в глобальной переменной,
  которым больше никто не пользуется.
- Гонки: в сгенерированном коде пока нет потоков.
- Ложные доказательства самого компилятора. Это появится, когда компилятор начнёт
  снимать проверки по доказательствам: в проверочной сборке снятая проверка останется
  и сообщит «доказательство ложно».
- Песочницу проверочная сборка не принимает: объекты песочницы умирают вместе с
  памятью, которую освобождает хозяин, и таблица этого не видит.

Все модули Efen в программе должны быть собраны в проверочном режиме. Если смешать
проверочный модуль с обычным, первая же смерть объекта даст ложный отчёт.

## Нет в спецификации

Эти части описаны по поведению Amber и в спецификации языка не закреплены:

- как включить проверочную сборку: ни атрибута в исходнике, ни флага `efenc`, ни
  записи в [режимах компиляции](../compilation-modes.md) нет;
- как она соотносится с отладочной сборкой и её проверками Р1–Р4 из
  [«Память, пришедшая из C»](pointer.md#память-пришедшая-из-c);
- операции, на которых стоят проверки: принять байты как объект структуры и отдать
  адрес объекта наружу, завершив его. В Amber это `Blocks.accept` и
  `Blocks.release` из тестов; в [операциях дескриптора](addresses.md#операции-дескриптора)
  таких нет, ближайшее — `@trusted`, тоже в списке нерешённого;
- текст отчёта (сейчас по-английски, с номером узла вместо строки исходника) и
  аварийная остановка при первой ошибке;
- отказ песочнице в проверочной сборке;
- функции `efen_object_die`, `makeTracked`, `poolGet`, `poolPut` в примерах взяты
  из тестов Amber и не входят в стандартную библиотеку.
