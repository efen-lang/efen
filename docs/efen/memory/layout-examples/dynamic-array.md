# Динамический непрерывный массив

[К примерам](README.md) · [Исходник](dynamic-array.efen) ·
[Пространство `layout`](../layout/declaration.md#пространство-layout)

`Vector` объявлена структурой в `layout<T>`: корневая ссылка на область, ёмкость и длина. Методы записаны стратегией.
При росте массив выделяет новую область, переносит элементы и освобождает старую.

## Построчный разбор

| Строки | Почему код написан так |
|---|---|
| 1 | Параметр `T` стоит на `layout`. Область `Area<T>` состоит из непрерывных элементов формы `T`, и для каждого `T` она своя. `layout` объявлен `private`: поля пишут функции этого модуля. |
| 2 | Типом, которым пользуется программа, служит именованная структура из `layout`. Обёртки, `Self` и аспекта нет. |
| 3 | `items` владеет областью и допускает `null`: нулевая ёмкость не выделяет памяти. Инвариант поля: область есть ровно тогда, когда `capacity` больше нуля, и число её элементов равно `capacity`. |
| 4–5 | `capacity` и `count` читает любой код, пишет модуль. Инвариант `count <= capacity` верен на каждом выходе публичной функции. |
| 6 | Заняты элементы `0 ..< count`, остальные не инициализированы: так говорит инвариант `items.initialized == count` ([слоты области](../layout/operations.md#частичная-инициализация-и-очистка)). |
| 10–11 | `grow` — помощник (`private`) с правом `mut` на вектор: он перевыделяет область под ёмкость `to`, которую выбирает вызывающий. Выделение идёт до первого изменения вектора. |
| 13–19 | Старая область снимается из поля (`take v.items`). Каждый из `count` занятых элементов уходит `take` из старой области и записывается в неинициализированный элемент новой. Ссылки на старые элементы умирают в строке `take`. |
| 19 | В конце блока старая область `old` кончается: ни один её слот не инициализирован, и компилятор возвращает область аллокатору ([ничего не теряется](../layout/lifetime.md#74-ничего-не-теряется)). |
| 21–22 | Новая область и ёмкость записываются после переноса; к выходу `grow` инвариант поля `items` верен. |
| 25–26 | Стратегия для `Vector<T>`; вне `layout` имя пишется с аргументом. `Movable` нужен для `take` элемента. Стратегия соответствует `RoomAppendable`, а с ним `Appendable` и `Reservable`: `v[] = x` вызывает `append`, член выбирает право получателя ([контракты операторов](../../runtime/lang-roles.md#контракты-операторов)). |
| 28–39 | `reserve(room:)` — публичная функция: даёт место ещё для `room` элементов. Ёмкость растёт теми же шагами, что при добавлении по одному, поэтому одно выделение заменяет несколько. Право `mut`: рост перевыделяет область. |
| 41–47 | `append` с правом `mut`: худший путь (`grow`) перевыделяет область, ёмкость растёт геометрически, поэтому `append` амортизированно `O(1)`; `nothrows`: `AllocationError` — сбой и проходит. Запись в неинициализированный элемент `count` инициализирует его; `count` растёт той же операцией. |
| 49–54 | `append` с правом `edit` вызывает получатель, у которого есть только `edit`. Он требует `count < capacity`: место для него заранее берёт `reserve(room:)`. В обходе того же вектора `v[] = x` требует заголовка `for x in mut v` ([итератор как структура](../../types/access-regions.md#итератор-как-структура)). Запись в неинициализированный слот `count` не двигает ни одного слота, поэтому ссылки на слоты элементов после вызова действительны ([права](../memory-rules.md#права)). |
| 56–69 | `append(moving:)` переносит элементы другого вектора после одного `reserve`. Источник передан как `mut`, а не `own`: если `reserve` бросит, ничего не перенесено и `source` хранит свои элементы. После `reserve` перенос не бросает; источник остаётся пустым, с `items == null` и нулевой ёмкостью. `v.append(moving: v)` вызывает ошибку: параметры не пересекаются ([проверка пересечения](../../types/access-regions.md#проверка-пересечения)). |
| 71–78 | `append(contentsOf:)` добавляет значения итератора. `reserve` стоит первым, только когда итератор соответствует `CountedIterator` и знает число оставшихся значений (`remaining`). Добавляет значения член `mut`, поэтому записи за границу области не бывает и при неверном `remaining`. Сам неверный `remaining` нарушает `ensures` метода `next` у `CountedIterator`: недоказанное условие проверяется на возврате из `next` и по умолчанию останавливает программу ([условия](../../conditions.md#обычная-сборка-и-диагностики)). |
| 80–91 | `insert` берёт место для одного элемента (`reserve(room: 1)`), затем сдвигает суффикс справа налево. Каждая запись попадает в неинициализированный элемент: первый неинициализированный — `items![count]`, следующий освобождён предыдущим `take`. |
| 93–103 | `remove` возвращает `own T?`, как `remove` списков и контракт [`ResizableSequence`](array-contracts.md): индекс вне границ даёт `null`. Дальше элемент снимается `take items![index]`, суффикс сдвигается слева направо в освободившиеся элементы, `count` уменьшается. Право `mut`: `take` элемента. |
| 105–111 | `replace` снимает прежнее значение и записывает новое. Между `take` и записью нет вызова, который мог бы прервать функцию. |
| 113–124 | `drain` опустошает вектор для типа `T`, который не соответствует `ImplicitlyDestroyable`: забирает каждый занятый элемент, передаёт его функции `each`, возвращает память и оставляет `items == null`, `count == 0` и `capacity == 0`. После неё выход из области видимости допустим: владеющее поле доказанно равно `null` ([ничего не теряется](../layout/lifetime.md#74-ничего-не-теряется), значение структуры, правило 4). Параметр `each` объявлен `nofail` ([nofail](../../throws.md#nofail-системная-точка-ответственности)): исключение из него застало бы локальную область с заполненными слотами, а значение `T` здесь неявно не уничтожается. |
| 126–140 | Память структуры возвращает `dispose`: стратегия пишет `implements Disposable`, а вызывает функцию компилятор там, где значение кончается. Она забирает занятые элементы, возвращает область и оставляет `items == null`. В теле `dispose` условие `T conforms ImplicitlyDestroyable` верно без `requires` ([ничего не теряется](../layout/lifetime.md#74-ничего-не-теряется), значение структуры, правила 1 и 6). |
| 67–68, 121–122, 137–138 | При пустой области `count` и `capacity` равны нулю: так инвариант поля `items` верен на выходе. |
| 142–147 | Чтение возвращает копию элемента, написанную словом `copy`, поэтому оно вынесено в стратегию для `T: Copyable`. `read` не пишет полей и права `edit` не требует. Индекс проверяет `requires`. |
| 149–158 | `append(contentsOf:)` над срезом `Slice<T>` копирует элементы, поэтому стоит в той же стратегии: один `reserve`, затем копия каждого элемента. `count` растёт после каждой копии, и копии, сделанные до броска `copy`, остаются в векторе. Для `T: ImplicitlyCopyable` копия бросить не может, и генератор кода пишет цикл одним блочным копированием. |
| 161–166 | Использование. В конце области видимости и на выходе через исключение из `append` компилятор вызывает `dispose`. |
| 168–182 | `VectorAccess` соответствует `Sliceable` с правом `read` и `edit`. `at` даёт ровно слот `index` (`Access<&self.items![index]> T`), `slice` — ровно слоты `start ..< end` срезом `Slice<T>`, который хранит свою длину; индекс вне границ бросает `BoundsError`. `v[i]` в позиции чтения вызывает член `read`, в позиции записи `edit`. Ссылка из члена `edit` разрешает `mut` над значением слота, поэтому `v[i] = x` для `T`, который владеет памятью, пишется под `edit`. Проверка пересечения сравнивает `v[i]` и `v[j]` как два слота ([контракты операторов](../../runtime/lang-roles.md#контракты-операторов), [проверка пересечения](../../types/access-regions.md#проверка-пересечения), правило 3). |
| 184–194 | `VectorSwap` соответствует `Swappable`: `swapAt` переставляет два элемента под `edit`, им переставляет элементы обобщённый код, которому путь к слоту не виден. |

## Перевыделение области

Перевыделения как особой операции нет: рост — код `grow`. Старая область снимается из поля, каждый элемент
переносится парой «`take` из старого, запись в новый», старая область кончается локальным значением, и компилятор возвращает её аллокатору. Таблица
[«`edit` и `mut` в `layout`»](../layout/operations.md#edit-и-mut-в-layout) относит перевыделение области к `mut` на
владельца: ссылки и указатели внутрь прежней области умирают. Поэтому `append`, чей худший путь растит область, —
`mut`. Запись в пределах ёмкости идёт членом `append` с правом `edit`, который требует `count < capacity`; место для
него заранее берёт `reserve(room:)`.

Какие ссылки вызов делает недействительными, решает сводка его тела, а не слово `mut` в сигнатуре
([что делает ссылку недействительной](../memory-rules.md#что-делает-ссылку-недействительной)):

| Вызов | Что становится недействительным |
|---|---|
| `reserve`, `append` с правом `mut`, `append(moving:)`, `append(contentsOf:)`, `insert` | все ссылки и указатели внутрь области: худший путь заменяет область |
| `append` с правом `edit` | ни одна ссылка на слот элемента: запись идёт в неинициализированный слот `count` в пределах ёмкости |
| `remove(index:)` | ссылки на элементы с номерами от `index`: сдвиг забирает каждый из них `take` |
| `replace(index:)` | ссылки на элемент `index`: его значение забрано `take` |
| `drain` | все ссылки и указатели внутрь области: область возвращена |
| `append(moving: source)` у источника | все ссылки и указатели внутрь области `source`: область возвращена |

Поэтому `let r = &v[0]; v.replace(index: 1, value: x); print(r)` допустимо: `replace` забирает только слот 1.

## Ошибки и очистка

Выделение в `grow` стоит до первой записи в вектор, поэтому `AllocationError` формы `Area<T>(count: to)` оставляет вектор прежним.
Слово `throws` в сигнатурах не записано: у функции с телом список исключений выводится
([throws](../../throws.md)). На выходе через исключение из `append` вектор освобождает `dispose`, который вызывает
компилятор.

`append` имеет амортизированную сложность `O(1)`; `insert` и `remove` — `O(count - index)`; `read` и `replace` — `O(1)`.
`append(contentsOf:)` над срезом и `append(moving:)` растят область не больше одного раза, `append(contentsOf:)` над
итератором — тоже, когда итератор соответствует `CountedIterator`.
