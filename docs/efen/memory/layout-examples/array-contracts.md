# Общие контракты массива

Исходник: [array-contracts.efen](array-contracts.efen).

## Построчный разбор

| Строки | Почему код написан так |
|---|---|
| 1 | `IndexedSequence<Element>` задаёт общий наблюдаемый смысл всех представлений. |
| 2 | `count` — свойство только для чтения: число логических элементов, независимо от физической формы. Контракт [допускает требование свойства](../../contracts.md); поле `count` реализаций его выполняет. |
| 3–4 | `read` получает обычный индекс; возврат отдельного значения требует `Copyable`. |
| 5–6 | `replace` — `mut fn`: принимает новый владеющий элемент и возвращает прежний; операция условно доступна для `Movable`. |
| 7 | Закрывается основной контракт. |
| 9 | Изменение длины вынесено в отдельный контракт. |
| 10–15 | `append`, `insert` и `remove` — `mut fn`: они меняют структуру. `remove` возвращает `own Element?`, как списки: индекс вне границ даёт `null`. Все три требуют `Movable` для явного переноса. |
| 16 | Закрывается дополнительный контракт. |

`IndexedSequence<Element>` задаёт общий наблюдаемый смысл всех вариантов:
`count`, чтение и замену позиции. Метод, меняющий структуру, пишется `mut fn`: без слова метод контракта только
читает `self`. Реализация `edit fn` (`append` и `insert` списков) сохраняет существующие элементы и подходит под
требование `mut fn` ([доступ метода к `self`](../../contracts.md#доступ-метода-к-self)). Ограничение `Copyable` стоит только на
`read`, потому что чтение возвращает отдельное значение. `replace` принимает
`own Element` и возвращает прежний элемент, поэтому уничтожение не происходит
посреди изменения массива. `requires Element conforms Movable` делает используемые `take`
законными. В примерах `replace` снимает прежнее значение и записывает новое без вызова между этими строками,
поэтому неинициализированный элемент снаружи не виден.

`ResizableSequence<Element>` отделён от основного контракта. Фиксированный
`FixedArray` остаётся массивом без `append`, `insert` и `remove`.

Для доказательства и межмодульного использования библиотечный контракт также публикует
поведенческую цель последовательности: `replace` меняет одну позицию, `append`
добавляет в конец, `insert` вставляет перед выбранной позицией, а `remove`
удаляет и возвращает её элемент. Условия результата пишутся словом `ensures`
([условия функций](../../conditions.md)). Конкретные условия результата здесь не вводятся: компилятор сохраняет
эту семантику в данных контракта и проверяет каждое представление относительно неё.

Пока обычные поведенческие условия контракта не представлены в HIR, доказательство
ограничивается обязательной безопасностью памяти и не называет выведенный
физический порядок доказательством функциональной семантики Array. Желаемый порядок
нельзя придумать из реализации: его задаёт обычный библиотечный
контракт. Это общий этап работы над системой контрактов, а не специальная аннотация
для каждого Array.

Контракты подключаются строкой `conforms` в стратегии структуры из `layout`
([пространство `layout`](../layout-reference.md#пространство-layout)). Структуры примеров
([динамический массив](dynamic-array.md) и остальные) называют свои методы теми же именами и теми же типами
(`Int` для индекса и длины, `own T?` у `remove`), а `count` у них — поле с тем же именем; строки `conforms` в них
не записаны. Прежний эскиз `Array` с параметром-аспектом
представления убран: `layout-reference.md` не описывает, как один тип выбирает форму хранения, и здесь это не придумывается.
Добавочное соответствие `ResizableSequence` предоставляют только изменяемые варианты; точный синтаксис их
объявления остаётся открытым.
