# Общие контракты массива

Исходник: [array-contracts.efen](array-contracts.efen).

## Построчный разбор

| Строки | Почему код написан так |
|---|---|
| 1 | `IndexedSequence<Element>` задаёт общий наблюдаемый смысл всех представлений. |
| 2 | `count` возвращает число логических элементов, независимо от физической формы. |
| 3 | `read` получает обычный индекс; возврат отдельного значения требует `Copyable`. |
| 4–5 | `replace` принимает новый владеющий элемент и возвращает прежний; операция условно доступна для `Movable`. |
| 6 | Закрывается основной контракт. |
| 8 | Изменение длины вынесено в отдельный контракт. |
| 9–11 | `append`, `insert` и `remove` определяют наблюдаемые изменения последовательности и требуют `Movable` для явного переноса. |
| 12 | Закрывается дополнительный контракт. |
| 14 | `Array` является обычной структурой стандартной библиотеки. |
| 15 | `Element` — тип элемента, известный во время компиляции. |
| 16 | `R` — аспект представления, принимающий исходный тип под именем `Target`. |
| 18 | Любой конкретный `Array` обязан выполнить основной индексируемый контракт. |
| 19 | Аспект получает `Target = Element`, а конкретный `Array` входит в него неявно как `Self`. |
| 20 | Закрывается исходное определение `Array`. |

`IndexedSequence<Element>` задаёт общий наблюдаемый смысл всех вариантов:
`count`, чтение и замену позиции. Ограничение `Copyable` стоит только на
`read`, потому что чтение возвращает отдельное значение. `replace` принимает
`own Element` и возвращает прежний элемент, поэтому уничтожение не происходит
посреди изменения массива. `where Element: Movable` делает используемые `take`
законными. Реализация использует единую compiler-known операцию
`replace(place, value)`, у которой нет наблюдаемого промежуточного пустого места.

`ResizableSequence<Element>` отделён от основного контракта. Фиксированный
`Contiguous` остаётся массивом без `append`, `insert` и `remove`.

Для proof и межмодульного использования библиотечный контракт также публикует
поведенческую цель последовательности: `replace` меняет одну позицию, `append`
добавляет в конец, `insert` вставляет перед выбранной позицией, а `remove`
удаляет и возвращает её элемент. Конкретный surface-синтаксис postconditions
здесь не вводится; compiler сохраняет эту семантику как contract metadata и
проверяет каждую representation относительно неё.

Пока обычные поведенческие условия контракта не представлены в HIR, Viper-proof
ограничивается обязательной безопасностью памяти и не называет выведенный
physical order доказательством функциональной семантики Array. Желаемый порядок
нельзя придумать из реализации: он должен прийти из обычного библиотечного
контракта. Это общий milestone контрактной системы, а не специальная аннотация
для каждого Array.

В `struct Array` строка `generic Element: Type` объявляет тип элемента.
`generic R<Target>: Representation<Target>` принимает аспект представления,
параметризованную исходным типом. `use R<Element>` связывает
`Target = Element`, а сам конкретный `Array<Element, R>` неявно передаёт
аспекту как `Self`.

`conforms IndexedSequence<Element>` требует от результата применения аспекта
операции общего массива. Добавочное соответствие `ResizableSequence`
предоставляют только изменяемые варианты; точный синтаксис их объявления остаётся
открытым.
