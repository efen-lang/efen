# Общие контракты массива

Исходник: [array-contracts.efen](array-contracts.efen).

## Построчный разбор

| Строки | Почему код написан так |
|---|---|
| 1 | `IndexedSequence<Element>` задаёт общий наблюдаемый смысл всех представлений. |
| 2 | `count` возвращает число логических элементов, независимо от физической формы. |
| 3–4 | `read` получает обычный индекс; возврат отдельного значения требует `Copyable`. |
| 5–6 | `replace` принимает новый владеющий элемент и возвращает прежний; операция условно доступна для `Movable`. |
| 7 | Закрывается основной контракт. |
| 9 | Изменение длины вынесено в отдельный контракт. |
| 10–15 | `append`, `insert` и `remove` определяют наблюдаемые изменения последовательности и требуют `Movable` для явного переноса. |
| 16 | Закрывается дополнительный контракт. |

`IndexedSequence<Element>` задаёт общий наблюдаемый смысл всех вариантов:
`count`, чтение и замену позиции. Ограничение `Copyable` стоит только на
`read`, потому что чтение возвращает отдельное значение. `replace` принимает
`own Element` и возвращает прежний элемент, поэтому уничтожение не происходит
посреди изменения массива. `requires Element conforms Movable` делает используемые `take`
законными. В примерах `replace` снимает прежнее значение и записывает новое без вызова между этими строками,
поэтому пустой элемент снаружи не виден.

`ResizableSequence<Element>` отделён от основного контракта. Фиксированный
`FixedArray` остаётся массивом без `append`, `insert` и `remove`.

Для proof и межмодульного использования библиотечный контракт также публикует
поведенческую цель последовательности: `replace` меняет одну позицию, `append`
добавляет в конец, `insert` вставляет перед выбранной позицией, а `remove`
удаляет и возвращает её элемент. Форма postconditions — `ensures` ([условия функций](../../conditions.md)); конкретные postconditions
здесь не вводятся; compiler сохраняет эту семантику как contract metadata и
проверяет каждую representation относительно неё.

Пока обычные поведенческие условия контракта не представлены в HIR, доказательство
ограничивается обязательной безопасностью памяти и не называет выведенный
physical order доказательством функциональной семантики Array. Желаемый порядок
нельзя придумать из реализации: он должен прийти из обычного библиотечного
контракта. Это общий milestone контрактной системы, а не специальная аннотация
для каждого Array.

Контракты подключаются строкой `conforms` в стратегии структуры `layout`
([пространство `layout`](../layout.md#пространство-layout)). Структуры примеров
([динамический массив](dynamic-array.md) и остальные) называют свои методы теми же именами, но с проверкой индекса
через `requires` и без `Size`-типа; строки `conforms` в них не записаны. Прежний эскиз `Array` с параметром-аспектом
представления убран: `layout.md` не описывает, как один тип выбирает форму хранения, и здесь это не придумывается.
Добавочное соответствие `ResizableSequence` предоставляют только изменяемые варианты; точный синтаксис их
объявления остаётся открытым.
