# Массив из блоков

[К примерам](README.md) · [Исходник](chunked-array.efen) ·
[Основная модель](../addresses.md)

Значения `Target` лежат в блоках `Items.Area`; структуры с корневыми указателями
и размерами блоков лежат в каталоге `Chunks.Area`. Оба вида `Area` являются
чистыми указателями.

## Закон общего префикса

Для каждого directory index `0 <= i < self.directoryLength`:

Все операнды следующей формулы сначала инъектируются в неограниченные
математические целые proof logic. Это не runtime-вычисление над `Size`.

```text
chunk[i].length = min(
    CHUNK_SIZE,
    max(0, self.length - i * CHUNK_SIZE)
)
```

Требуемое число блоков не превышает `directoryLength`; оставшийся сохранённый
suffix directory допустим и имеет `chunk.length == 0`.

```text
requiredChunks(n) =
    if n == 0 then 0 else 1 + (n - 1) / CHUNK_SIZE

requiredChunks(self.length) <= self.directoryLength
```

Все chunk roots живы и попарно различны. `chunkItems[i]` — последовательность
identity occupants slots `0..<chunk[i].length`; location каждой identity точно
соответствует своему `(root,index)`. `flatItems == concat(chunkItems)` не имеет
повторных identity и его множество точно равно `Items`. Значения образуют
отдельную проекцию `flatValues[j] == valueOf(flatItems[j])`: равные `Target`
допустимы, повторная identity — нет. Сумма длин равна `self.length`. Закон
генерируется компилятором из descriptor transitions, полного тела representation
и поведенческой цели Array. Descriptor operations дают точные membership,
location и initialization; `own Chunk.root` исключает двух владельцев одной area.
Записи длин и направление moves отдельно доказывают distribution и порядок, а
контракт Array задаёт ожидаемое поведение append/insert/remove. Пользовательский
cross-descriptor квантор не требуется, но compiler обязан доказать base и
preservation generated invariant, а не получить его через `assume`.

## Ошибки и очистка

`growDirectory` вызывается до выделения нового блока. Если рост завершается
ошибкой, нового блока ещё нет. Если завершается ошибкой `Items.allocateArea`,
выросшая ёмкость каталога может сохраниться, но логическая последовательность не
меняется. `Chunks.initialize` может иметь exceptional prepare до публикации;
его normal commit и следующие записи служебных полей безотказны и не вызывают
код, способный обратиться к изменяемой структуре.

Между `Items.allocateArea` и успешным `Chunks.initialize` compiler-generated
exceptional CFG переносит один `ChunkCleanup`: из local `block` во временный
`Chunk`, затем в callee argument. Token инкапсулирует `AllocationOwn`, а не
дублирует его. После `take block` прежнее имя уже нельзя использовать даже в
cleanup. Exceptional callee path вызывает именованную операцию:

```efen
Items.free(
    root: take cleanup.root,
    capacity: cleanup.capacity,
    initializedCount: 0
)
```

На normal path тот же token становится drop-obligation опубликованного `Chunk`
и хранится в owning payload его `root`. Это реальный runtime CFG/resource
artifact, а не ghost утверждение. Порядок drop и no-reentry cleanup остаются
открытыми контрактами.

При уничтожении каждого `Chunk` вызывается:

```efen
Items.free(
    root: take chunk.root,
    capacity: chunk.capacity,
    initializedCount: chunk.length
)
```

Затем `Chunks.free` получает корневой указатель каталога, `directoryCapacity` и
`directoryLength`. Рост каталога переносит только структуры `Chunk`; выделенные
области `Target` остаются на месте.

Индексирование имеет сложность `O(1)`, `append` — амортизированную `O(1)`,
`insert` и `remove` — `O(length - index)`.

Для сдвигов, публикации блока и очистки действует
[общее правило безотказного окна](README.md#общее-правило-применимости).
`Movable` делает явные `take` и `Items.move` законными, но не является гарантией
no-throw placement.
