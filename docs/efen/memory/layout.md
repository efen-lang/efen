# Layout и описание памяти

[Память](README.md) · [Компоновка и дескрипторы](addresses.md) · [Сырая память](pointer.md) ·
[Модели поведения](../models.md) · [Условия и доказательства](../conditions.md)

`layout` описывает память так, чтобы FLOW сам доказал: каждое имя живёт не дольше того, на что указывает, и каждый
выданный кусок памяти возвращается. Программист описывает множества, их вложенность и связи между ними; время жизни,
предусловия и постусловия функций компилятор выводит сам. Порядок, баланс и суммы, которые FLOW не выражает, доказывает
Z3. На слово принимается только то, что помечено точкой доверия: `assume`, `@asm`, функция C.

Статус: разделы описывают модель целиком. Что из неё сегодня реализовано в Amber, перечислено в разделе
[Состояние в компиляторе](#состояние-в-компиляторе); остальное — нормативный текст, который компилятор ещё не проверяет.

## Вопросы, на которые отвечает layout

Описание памяти отвечает на восемь вопросов. Каждый ответ даёт FLOW отношение «это живёт не дольше того»:

1. **Какие множества есть.** Каждый элемент живёт не дольше своего множества.
2. **Как устроено множество.** Непрерывная область мест по индексу или независимые экземпляры. От этого зависит, что
   кончает жизнь имён внутри.
3. **Какое множество лежит внутри какого.** Элемент живёт не дольше элемента, внутри которого лежит.
4. **Как указатель одного множества относится к другому.** Указатель живёт не дольше своей цели.
5. **Кто владеет элементом.** У элемента одно владеющее ребро; по нему FLOW считает, когда элемент умирает.
6. **Что выдано наружу.** Пока элемент выдан, у его родителя нет владельца.
7. **Что кончает жизнь.** Возврат элемента, смена вида, возврат памяти, изменение структуры области.
8. **Где доверие.** Место, где отношение принимается на слово, а не выводится.

Законы над числами (`used == slots.taken.count`), порядок и физическая форма времени жизни не задают. Они нужны Z3 и
генератору кода и описаны в разделах [виды](#виды-и-приведение-as) и [законы](#законы-и-цепочки).

## Множества и области

Память описывают дескрипторы. Дескриптор объявляет форму элемента и то, как элементы лежат; сколько их, говорит тот,
кто держит множество.

| Дескриптор | Что это |
|---|---|
| `area X: T` | одна непрерывная область мест одной формы; места по индексу `0 ..< count` |
| `set area X: T` | множество независимых непрерывных областей; каждый байт памяти принадлежит элементу |
| `set X: T` | множество экземпляров без обещания непрерывности |
| `one X` | один экземпляр |

```efen
layout {
    set area Blocks: Block            // блоки по 64 КБ
    area Classes: Class               // 32 класса размеров подряд

    struct Pool {
        own var classes: Classes.Area? { value == null || value.count == CLASSES }
    }
}
```

Число мест области указывает держатель (`value.count == CLASSES` у поля `classes`) или строка `invariants` вида
(`slots.count == PAYLOAD / SIZES[sizeClass]`). Место области — значение: `table[i].size = 16` пишет поле места `i`.
Индекс доказан в границах или проверяется при выполнении. Владеющее поле в месте области — ошибка: владеть может только
элемент множества. Элементы `set area` не индексируются; набор раздаётся целиком циклом
[`for element in take region`](pointer.md#раздача-набора-for-element-in-take-region).

## Вложенность

Множество физически лежит внутри элементов другого множества, если оно — поле структуры этих элементов:

```efen
@align(BLOCK)
struct SlotBlock {
    Header
    @align(LINE) area slots: Slot     // места слотов внутри блока
    invariants {
        sizeOf(slots.Item) == SIZES[sizeClass]
        slots.count == PAYLOAD / SIZES[sizeClass]
    }
}

struct Slot {
    var next: Int = NONE
    var key: Int = SLOT_KEY
    area rest: Byte                   // хвост слота внутри слота
}
```

Память блока выдана из множества `Blocks`; область `slots` лежит в байтах блока, хвост `rest` — в байтах слота.
Вложенность задаёт два правила:

1. Элемент живёт не дольше элемента, внутри которого лежит: слот не дольше блока, блок не дольше памяти, из которой он
   взят.
2. Родителя нельзя вернуть, пока внутри него выдан хотя бы один элемент. Первый `lend` превращает `own SlotBlock` в
   `mut SlotBlock`; `own` восстанавливается, когда вернулись все места (`used == 0`).

Множество как целое живёт, пока жива память его родителя: `slots` — пока блок остаётся `SlotBlock`.

## Ссылки

Указатель внутри `layout` — имя элемента множества, место области по индексу или владеющая ссылка.

| Запись | Что это |
|---|---|
| `var next: Blocks.Item?` | имя элемента множества `Blocks`; не владеет, цель обязана быть живой |
| `own var reserve: SlotBlock?` | владеющая ссылка: она уничтожает цель |
| `var next: Int` с концом `NONE` | место своей области по индексу (цепочка свободных мест) |
| `var key: read<layout.Keys> Int` | место области `Keys` того же `layout` |
| `own other Items.Item?` | владеющая ссылка на другой элемент того же множества |
| `own block.slots.Item` | место, выданное из `block.slots`, у получателя |

Строка в `invariants` вида уточняет поле для этого вида: `next: SlotBlock?` — цель есть `SlotBlock`;
`next: own FreeBlock?` — в виде `FreeBlock` поле владеет, в других видах оно только имя.

Указатель из одного множества в другое объявлять особо не нужно: это обычное имя, и FLOW видит каждую его запись.
Обратные указатели (`prev`, `parent`) разрешены только внутри `layout`.

Имя адреса без множества получается только на доверии:
`(address(m) & ~(BLOCK - 1)) as Blocks.Item` — блок, в котором лежит адрес из C.

## Время жизни

Время жизни элемента выводится из вложенности и событий выдачи и возврата; операций «создать элемент» и «уничтожить
элемент» в `layout` нет. Для множества, лежащего внутри другого, FLOW знает четыре события:

1. Память родителя создана: приведение `Pointer` к виду, `System.map`.
2. Число мест известно формально: строка числа у держателя или у вида.
3. Элемент выдан: `lend block.slots[k]`, раздача `for element in take region`.
4. Элемент вернулся через `own`: `block.slots[k] = take slot`.

Элемент рождается при выдаче и умирает при возврате. При возврате умирает каждое имя на него, в том числе имя,
хранимое в поле другой структуры; использовать его после возврата — ошибка в месте использования.

**Карта жизни элемента.** По телам функций FLOW строит путь каждого вида элемента: рождение, повторная выдача, смена
вида (`SlotBlock` → `FreeBlock` → `SlotBlock`), возврат памяти. Из карты выводится время жизни через вызовы:

```
slot жив  от  результата acquireSlot(block)
          до  входа в releaseSlot(block: block, slot: slot)
```

**Полнота карты.** FLOW доказывает:

1. каждый выданный элемент на каждом пути возвращается или передаёт владельца дальше; иначе — утечка в конце пути;
2. ничего не возвращается дважды и не возвращается на чужое место;
3. родитель умирает только пустым: перед возвратом блока все его места вернулись;
4. элемент покидает множество только событиями карты или через точку доверия.

**Условия функций выводятся.** Из тела функции FLOW выводит её предусловия и постусловия о выданных и возвращённых
элементах и добавляет их в прототип: у `acquireSlot` — «результат — место, выданное из `block.slots`», у `releaseSlot`
— «`slot` выдан из `block.slots`». Вызывающий код проверяется по прототипу. У функции без тела (интерфейс, контракт,
функция C) пишется код [модели](../models.md#модель-model), и условия выводятся из него. Условия руками не пишутся.

## Выдача и возврат

```efen
fn reuse(block: own SlotBlock) {
    let a = lend block.slots[0]         // block теперь mut SlotBlock
    let b = lend block.slots[1]
    block.slots[0] = take a             // место 0 вернулось
    freeBlock(take block)               // ошибка: место 1 выдано, own SlotBlock не восстановлен
}
```

1. `lend block.slots[k]` выдаёт место `k`: `own block.slots.Item` с одним владельцем; байты не переносятся, `k` входит
   в `slots.taken`. Выдать выданное место — ошибка.
2. `block.slots[k] = take slot` возвращает место; `k` выходит из `slots.taken`. Вернуть можно только на своё место.
3. Поля выданного места через блок не читаются и не пишутся: память держит получатель.
4. На каждом выходе функции изменение `used` равно числу выдач минус число возвратов.
5. Диапазон: `lend block.bytes[a ..< b]` и возврат тем же куском.
6. Раздача `for element in take region`: каждый элемент тело передаёт дальше; `break`, `continue` и `return` в теле —
   ошибка; оставленный элемент — утечка.

Подробно: [иерархия владения](pointer.md#иерархия-владения).

## Виды и приведение `as`

Одни и те же байты бывают разными видами. Блок mm бывает `PoolBlock`, `FreeBlock`, `SlotBlock`, `LargeBlock`; первым
полем у каждого идёт общий `Header`, и у каждого свои `invariants`. Смена вида — приведение:

```efen
let spare = block as SlotBlock(slots: Slot(size: SIZES[index]))
```

Приведение `Pointer` к виду поглощает `Pointer`. Компилятор доказывает, что размер памяти не меньше вида, выравнивание
не меньше `@align` вида, а память обнулена, если у элемента есть поле не целого типа. Стирание `block as Pointer`
возвращает память без вида; её отдают системе с тем размером, с которым брали.

## Законы и цепочки

Строки `invariants` вида — законы, которые держатся в каждой точке передачи вида дальше. На входе функции FLOW
принимает их верными; в точке передачи (`return`, аргумент вызова, запись в поле, выход параметра `mut`) доказывает.
Внутри функции закон можно временно нарушить.

```efen
invariants {
    used == slots.taken.count
    frontier <= slots.count
    forall k in frontier ..< slots.count: !slots.taken.contains(k)
    let freeSlots = slots.chain(from: firstFreeSlot, by: Slot.next, until: NONE)
    forall k in freeSlots: 0 <= k && k < frontier && !slots.taken.contains(k)
}
```

Цепочка `A.chain(from: H, by: T.L, until: END)` — узлы, достижимые от головы по полю-ссылке до конца. Какие узлы на
цепочке после каждой записи головы и ссылки, FLOW знает сам: снятие головы, вставка, вырезание из середины. Программист
пишет только законы о её узлах. Ключевого слова под каждую структуру нет: список, очередь, стек и дерево
описываются одной формой цепочки и законами. Подробно: [цепочка](../conditions.md#цепочка).

## Что доказывается

| Описано | Доказывается |
|---|---|
| вид и `as` | размер, выравнивание, обнулённость памяти |
| число мест области | индекс в границах; что не доказано, проверяется при выполнении |
| `lend` / `take` на своё место | один владелец места, нет повторной выдачи, возврат только на своё место |
| `used == slots.taken.count` | счёт сходится на каждом выходе; блок не отдаётся, пока внутри есть выданное |
| `for element in take region` | каждый элемент отдан дальше |
| вложенность и выдача | время жизни каждого имени, полнота карты жизни элемента |
| `invariants` вида | закон держится в каждой точке передачи |
| цепочка и её законы | форма цепочки по записям (FLOW); законы о её узлах и предпосылки событий (Z3) |

## `layout` в теле класса

Блок `layout { … }` бывает и в теле класса, интерфейса или контракта. Там он описывает не байты, а то, что держит
внешняя сторона ([класс над внешним значением](../classes.md#класс-над-внешним-значением)), и содержит только:

- объявления `var` — поля `layout`. Их нет в памяти объекта, их не исполняют, их читает только FLOW; пишет их
  [модель](../models.md#модель-model);
- строки условий в форме [декларативных условий](addresses.md#декларативные-условия): `forall`, `==`, `if` как импликация
  ([отношения в `layout`](../models.md#отношения-в-layout-класса)).

Физические описания (`set`, `one`, `area`, `struct Self`) остаются в аспекте representation; в `layout` класса они —
ошибка.

Тип поля `layout`:

- `read T`, `edit T` — удержание слота Efen;
- `mut U`, `read U`, где `U` — класс над внешним значением, — зависимость от внешнего объекта: пока держатель жив,
  `U` нельзя уничтожить и отдать;
- `own T` — значение, которое забрала внешняя сторона. Замыкание `own` вида `own` упаковывает сгенерированный вход
  и освобождает после единственного вызова. Другому значению `own` нужна память Efen, а поле `layout` её не занимает
  ни в каком классе, — ошибка. Класс с настоящими полями хранит такое значение в настоящем поле: модель пишет его туда
  ([удержания](../models.md#удержания));
- коллекция или optional из таких типов;
- простое значение (`errmsg: CString`) — только как источник ссылок, которые возвращают методы.

Поля `layout` бывают у класса без счётчика (класс над внешним значением — один из таких классов), у интерфейса и у
контракта. Класс со счётчиком пишет в `layout` только строки условий: его поля — `managed`, и внешняя сторона держит
через них только то, что называет отношение ([удержания](../models.md#удержания)).

`obj.field` вне модели и вне условия `layout` — ошибка. Настоящее поле и поле `layout` с одним именем — ошибка.
Настоящие поля класса пишутся вне `layout`, как обычно; у класса над внешним значением их нет.

**Порядок уничтожения — опубликованная гарантия.** Объект уничтожается раньше каждого слота, который держит, и
раньше каждого объекта, от которого зависит; остальное идёт в порядке, обратном объявлению. Круг удержаний в
конце области — ошибка с именами обоих объектов. Среди полей класса порядок тот же, и отношение `forall` его
задаёт: при `forall s in cache.values: s.db == db` поле `cache` уничтожается раньше `db`.

## Многопоточность

Не решено. Сегодня действуют правила [общей памяти](../shared.md): общая структура объявляет `invariants`, компилятор
принимает их верными после захвата мьютекса и доказывает в каждой точке, где блокировка отпускается; удержания
держателя, попавшего в многопоточную корутину или в объект `shared layout`, становятся областями доступа этого режима.
Структуры без блокировок, где ячейки делят больше двух потоков, — примитивы стандартной библиотеки, доказанные один
раз; их `layout` не описывает. Какие множества `layout` может принадлежать потоку, делиться между потоками по ролям или
переходить из потока в поток, ещё не определено.

## Состояние в компиляторе

На 2026-11-08 Amber проверяет:

- `area`, `set area` и структуру с полем `area` и `invariants`; имя элемента `X.Item`;
- выдачу и возврат: `lend`, `take` на своё место, `slots.taken`, счёт `used` на выходе, раздачу
  `for element in take region`;
- приведение `as`, `@align`, `Pointer`;
- строки `invariants`: поле против константы, число мест, `sizeOf` и таблицу размеров, `used == x.taken.count`, одну
  цепочку свободных мест;
- смерть имени, полученного приведением, на вызове, который может сменить вид.

Ещё не проверяет: результат функции `own` элемента множества (`-> own Nodes.Item?`) и поэтому списки, деревья и
хеш-таблицы с узлами, которые передаются владельцем ([проверочные структуры](layout-examples/checks/README.md)); `one`, `set X` с законами над множеством (`forall n in Items: …`), `struct Self` и аспект
`Representation`, ссылки `own other` и `read<layout.Area>`, смерть хранимых имён при возврате элемента, карту жизни
элемента и её полноту, выведенные условия о выданных элементах в прототипе, `layout` в теле класса и код `model`.
Законы цепочек целиком доказывает Z3 в тестовом режиме чтения; обычная сборка видит из цепочки только правило
свободных мест.
