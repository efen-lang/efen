# Слои

[Документация](README.md) · [Словарь](glossary.md) · [Пакеты](packages.md) · [Контексты и эффекты](context-and-effects.md)

Слой — логическое объединение пакетов и пространств имён, которое называет их
место в архитектуре и отношения с другими слоями. Членство задаётся именами
пакетов, а не отдельными модулями: модуль получает слой своего пакета. Можно
назвать и пространство имён — тогда в слой входят все пакеты под ним.

Ни пакет, ни пространство имён не встречаются в двух `contains`, поэтому у
вопроса «в каком слое лежит этот код» один ответ. Пространство имён и его пакет
лежат в одном слое: назвать пространство в одном слое, а пакет из него в другом
нельзя.

Слой отличается от пакета и от пространства имён назначением. Пакет — единица
зависимости и версионирования: он объявляет, что ему нужно, и поставляется
целиком. Пространство имён разводит одинаковые имена и задаёт путь вида
`Billing::Core::Invoice`. Слой не участвует ни в поставке, ни в разрешении имён;
он говорит, кто кого вправе использовать.

Слой — прежде всего объявление. Компилятор проверяет его только в группе
диагностик `Layer`, и по умолчанию нарушение сборку не останавливает — об этом
раздел «Проверка».

## Объявление

Слои объявляются в файле `layers.efen` в корне рабочего пространства. Объявление
относится к нескольким пакетам сразу, поэтому лежит над ними.

Объявление вводится словом `layer`. Членство перечисляет `contains`, принимая
имена пакетов и пространств имён. Пакет называется путём его пространства имён —
`Billing::Core`, — как в [`packages.md`](packages.md). Названное пространство
имён включает в слой все пакеты под ним; другого способа взять поддерево нет.

В примере ниже семь пакетов — `Billing::Core`, `Billing::Model`,
`Billing::Services`, `Billing::Db`, `Billing::Http`, `Billing::Web` и
`Billing::Tests` — лежат в пространствах имён под `Billing`, по одному пакету на
пространство имён.

```efen
layer Domain {
    contains Billing::Core, Billing::Model
}

layer Application {
    contains Billing::Services
    uses Domain
    exposes Billing::Services::Api
}

layer Infrastructure {
    contains Billing::Db, Billing::Http
    uses Application, Domain
    provides Domain::Repository with Billing::Db::SqlRepository
}

layer Presentation {
    contains Billing::Web
    uses Application
}

layer Tests {
    contains Billing::Tests
    uses *
}
```

## Отношения

### `uses`

`uses A, B` даёт пакетам слоя право писать `use` для абстракций слоёв `A` и `B`.
Право не транзитивно: `Infrastructure uses Application`, а `Application uses
Domain`, но доступ к `Domain` из `Infrastructure` этим не появляется — в примере
выше он назван отдельной строкой. Поэтому список `uses` перечисляет все слои, на
которые слой опирается, и меняется только правкой самого `layers.efen`.

Граф `uses` ацикличен. Цикл — ошибка при любом уровне проверки, потому что при
цикле деление на слои перестаёт что-либо утверждать.

Тестовый слой пишет `uses *` и получает право использовать все слои, кроме тех,
что сами написали `uses *`. Слой с `uses *` нельзя назвать в чужом `uses`,
поэтому и цикла через него не возникает.

### `exposes`

`exposes` перечисляет полные пути модулей (`Package::Module`, по разделу «Полное
имя абстракции» в [`packages.md`](packages.md)) или пространства имён пакетов
слоя и сужает то, что `use` из другого слоя вправе импортировать. В примере выше
`Billing::Services::Api` — модуль `Api` пакета `Billing::Services`. Слой без
`exposes` отдаёт наружу всё своё публичное содержимое, как `Domain` в примере.

`exposes` — проверка на `use`, а не уровень видимости. `use` публичного, но не
перечисленного в `exposes` имени — диагностика группы `Layer`, по умолчанию
предупреждение. Само имя остаётся `public` по правилам
[`visibility.md`](visibility.md): его видимость `exposes` не меняет.

`exposes` ограничивает именно разрешение имён. Он не удаляет скрытые эффекты,
контракты или контексты из сигнатур и ambient-контекста. Публичная функция может
создать скрытую зависимость и вызвать замыкание, внутри которого другая
публичная функция этой зависимостью пользуется. Внешний код способен неявно
переносить такую запись контекста, но не может обратиться к её скрытому имени.

### `provides … with …`

`provides X with Y` объявляет, что слой связывает абстракцию `X` с реализацией
`Y` из своих пакетов. Слева стоит то же, что связывает `with { }`: эффект,
контракт или контекст, объявленный в одном из слоёв, которые слой использует, или
во внеслойном пакете. Форма и смысл связывания те же, что в разделе «Статическое
связывание эффектов и контекстов»
([`context-and-effects.md`](context-and-effects.md)).

Проверка одна: `Y` связывается ровно так, как связало бы `with { X: Y }`.
Потребитель получает реализацию тем же механизмом — через `%Repository` или через
`in Repository` в сигнатуре, — и о слое, который её подставил, ничего не знает.

Так реализация контракта, объявленного в нижнем слое, попадает в него из
верхнего, а нижний слой верхний не импортирует. В примере `Domain` объявляет
`Repository` и о базе данных ничего не знает; `Infrastructure` использует
`Domain`, поэтому вправе назвать `Repository` и подставить
`Billing::Db::SqlRepository`.

### Пакеты вне слоёв

Пакет, не названный ни в одном `contains`, — внеслойный. Его вправе использовать
любой слой, а сам он вправе использовать только другие внеслойные пакеты. Это
оставляет место утилитам и внешним зависимостям, которые в архитектуре не
участвуют, и не даёт им передать зависимость между слоями.

## Проверка

Нарушения слоёв попадают в группу диагностик `Layer`
([`diagnostic-groups.md`](diagnostic-groups.md)) и по умолчанию сообщаются
предупреждением. Уровень поднимается флагом `-Werror Layer`, а группа целиком
снимается флагом `-Wno-warn Layer`. Поэтому слои вводятся постепенно: сначала
объявление, потом список нарушений, потом ошибка.

Проверяется три вещи:

1. каждый `use` — против списка `uses` того слоя, в котором он написан;
2. каждый `use` через границу слоя — против `exposes` слоя, откуда берётся имя;
3. цель `provides` — что она связывается так же, как связало бы `with { X: Y }`.

Цикл в графе `uses` — исключение из настройки уровня: он остаётся ошибкой и при
выключенной группе.

Диагностика называет обе стороны нарушения:

```text
warning[layer.forbidden-import]: Presentation uses Billing::Db, which belongs to Infrastructure [#Layer]
  note: layer Presentation declares `uses Application`
```

## Эффекты и контексты на границе слоя

`provides … with …` — место, где слой выбирает реализации эффектов, контрактов и
контекстов. Связывание действует на все пакеты слоя, поэтому выбор записан один
раз и в одном файле:

```efen
layer Infrastructure {
    contains Billing::Db, Billing::Http
    uses Application, Domain

    provides Domain::Repository with Billing::Db::SqlRepository
    provides Logger with Billing::Http::RequestLogger
}
```

Это те же связывания, что `with { Repository: SqlRepository, Logger:
RequestLogger }` на подключении модуля, только записанные на границе слоя. В
примере `Logger` объявлен во внеслойном пакете, а реализацию ему даёт
`Infrastructure`.

Модуль, у которого есть собственное `with { X: Y }`, использует своё связывание;
`provides` слоя работает как умолчание для тех модулей слоя, которые не связали
`X` сами. Расхождение диагностикой не сопровождается: модульное связывание —
обычный способ сказать «здесь иначе».

`provides X with null` не допускается: слой не отключает эффект целиком. Пустое
связывание остаётся на уровне модуля, где видно, какой именно код работает без
реализации.

## Чужой опыт

Похожие проверки существуют, но живут вне языка.
[Deptrac](https://deptrac.github.io/deptrac/concepts/) для PHP собирает слои
коллекторами по именам классов и сверяет их с набором правил; запускает проверку
CI, а не компилятор. [`boundary`](https://github.com/sasa1977/boundary) для
Elixir объявляет границу через `deps` и `exports` прямо в коде и проверяет её
плагином компилятора. [`package_group`](https://bazel.build/concepts/visibility)
в Bazel задаёт список пакетов, которым разрешено видеть цель, то есть решает ту
же задачу списком доступа сборочной системы. ArchUnit проверяет
[`layeredArchitecture()`](https://www.archunit.org/userguide/html/000_Index.html)
обычным тестом на JVM. Ни в одном из четырёх слой не является конструкцией языка;
ближе всех `boundary`, но и он остаётся плагином.

## Граница рабочего пространства

Библиотека владеет своим `layers.efen`. Приложение не может перемещать её пакеты
между слоями, добавлять им разрешённые зависимости или расширять их `exposes`.
Оно может считать публичную поверхность библиотеки внешним слоем и наложить на
собственный код более строгие ограничения.

В первой версии у слоя нет runtime-представления. Выбор стратегии также не
становится свойством слоя: он остаётся пакетным решением по правилам
[`strategies.md`](strategies.md).
