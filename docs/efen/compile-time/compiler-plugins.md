# Плагины компилятора

[Документация](../README.md) · [Плагины и метакод](plugins.md) · [Сертификация](../certification.md) · [Условия](../conditions.md) · [Конфигурация сборки](../build-config.md)

Плагин компилятора добавляет к проверкам Amber свои: анализ, диагностики с исправлениями, доказательства,
вставку кода в названном режиме, выходные файлы. Без сертификата компилятор доверяет только ядру:
запечатыванию тела, FLOW (анализу владения, ссылок и условий), эффектам, условиям и типам-состояниям. Каждый
другой анализ — плагин с одним интерфейсом, включая проверки самого Amber. Они поставляются с компилятором и
работают в каждой сборке, а проект понижает уровень любой из них или отключает её секцией
[`diagnostics`](#диагностики), как у стороннего плагина (агент).

Плагины компилятора попросил Edmond 2026-10-29: «нет плагинов самого компилятора. например плагины которые
добавляют доп анализ коду и так далее». Проект и обоснование — amber dev/plans/S90.md §12. Всё, что не
приписано Edmond, — предложения агента; решения, которые легко оспорить, отмечены «(агент)».

Плагин анализа добавляет знание и диагностики. Он не снимает находку ядра и не понижает её уровень. Проверку
при выполнении он убирает только фактом, который доказало само ядро ([предложения](#предложения-и-требования))
(агент).

## Способы

| Способ | Что это | Когда работает | Что даёт | Пример |
|---|---|---|---|---|
| A. Типы-состояния библиотеки | расширение ядра данными | внутри прохода FLOW | находки ядра `typestate.…` | чтение `File` после `close` |
| B. Новый вид эффекта | расширение ядра данными | при сборе эффектов | эффект у каждой функции; нарушенный запрет | `Allocates`: функция не выделяет память |
| C0. Осмотр | плагин | после ядра, по функции или объявлению | диагностики | вызов функции C без причины; публичная функция без документации |
| C. Анализ потока данных | плагин | после ядра, по функции, группами взаимной рекурсии | факты, сводка функции, диагностики, записи реестра | ввод извне доходит до SQL; единицы измерения; порядок блокировок |
| D. Анализ программы | плагин | при сборке программы целиком | диагностики, отчёт | цикл в порядке блокировок; мёртвый код |
| E. Вставка кода | плагин, в названном режиме | последний шаг метакода | новое тело, которое проверяет ядро | счётчики покрытия |
| F. Выходные файлы | плагин | после успешной сборки | файлы в выходном каталоге | заголовки C для библиотеки Efen; SBOM |
| H. Доказательство | плагин | на записях реестра со статусом «неизвестно» | доказательство, которое проверяет ядро | другой решатель вместо Z3; доказательство по индукции |
| G. После запечатывания | доверенный плагин | между запечатыванием и машинным кодом | код, который ядро уже не перепроверит | оптимизация MLIR; своя цель |

A и B — данные, которым смысл даёт ядро: метакод им не нужен, и они расширяют само ядро. C0–H называются
в секции `plugins` конфигурации. Код меняют только E (в названном режиме, до запечатывания) и G; G —
доверенный плагин ([проверяемые и доверенные плагины](plugins.md#проверяемые-и-доверенные-плагины)): за него
ручаются сертификаты.

## Реестр свойств

Ядро ведёт для каждой функции реестр свойств: каждое `requires`, `ensures`, инвариант, `assert`, предложение
или требование плагина и каждую проверку при выполнении, которую генератор может убрать. Плагины обмениваются
фактами прежде всего через реестр: свойство, которое доказал один плагин, другой читает в терминах ядра, поэтому
два плагина не привязаны к версиям друг друга (агент).

| Поле | Смысл |
|---|---|
| свойство | условие в терминах ядра: место, состояние, отношение целых |
| точка | узел программы, к которому относится свойство |
| статус | доказано FLOW · доказано проверенным доказательством · на вере ([сертификация](../certification.md)) · неизвестно, проверяется при выполнении · нарушено |
| кем | FLOW, Z3 или плагин доказательств с именем, версией и ключом содержимого |
| опирается на | другие записи; свойство доказано не больше, чем то, на чём оно держится |

`amber trust <функция>` печатает эту таблицу ([реестр свойств](../certification.md#реестр-свойств-и-amber-trust)).

## A. Типы-состояния библиотеки

Проверка состояний — это [типы-состояния](../types/typestate.md): класс объявляет оси состояний, а методы —
переходы. Библиотека, которая объявляет класс с состояниями, расширяет ядро данными: проверяет их FLOW, и
метакод для этого не нужен.

```efen
/// Файл читают, пока он открыт, и закрывают один раз.
class File {
    state Lifecycle {
        initial Open
        Closed
    }

    fn read(into: mut Bytes) -> Int state Lifecycle.Open
    fn close state Lifecycle.Open >> Lifecycle.Closed
}

fn load(file: own File, buffer: mut Bytes) {
    file.close()
    file.read(into: buffer)        // error[typestate.invalid-call]: `read` requires state `Lifecycle.Open`
}
```

- Находка типа-состояния — находка ядра: её код не принимают ни секция `diagnostics`, ни `@allow`.
- В коде зависимости ядро только выводит переходы для сводок функций и ничего не сообщает, поэтому новые
  состояния в библиотеке не ломают код, который проект не может исправить (агент).
- Оси нескольких источников упорядочены по полному имени, а не по порядку загрузки, поэтому сводка не зависит
  от порядка сборки (агент).

## B. Новый вид эффекта

Новый вид эффекта стоит рядом с `Throws`, и компилятор собирает его по вызовам, как остальные эффекты:
функция, которая вызывает выделяющую память, сама выделяет. Запрет пишется так же, как для своих эффектов: `without Allocates`.

- Вызов, эффект которого неизвестен (замыкание, функция C), нарушает `without X`, как неизвестный `Throws`
  нарушает `nothrows`.
- Вид эффекта, источники которого лежат в std или рантайме (`Allocates`), объявляет сама std или сам рантайм, а
  не сторонняя библиотека.
- Такой эффект у публичной функции входит в её публичный набор эффектов; его изменение — изменение API
  пакета.

## C0. Осмотр

Большинству проверок решатель не нужен: это обход, который ищет форму кода. Осмотр читает одно запечатанное
тело, одно объявление или объявления модуля, по запросу получает факты ядра и записи реестра и выдаёт
диагностики. Уровень кода по умолчанию объявляет регистрация, а конфигурация его меняет. Проверка стиля получает ещё синтаксическое дерево своего модуля: ей нужны расположение текста и
комментарии.

```efen
use compiler

/// Требует причину у каждого вызова функции C.
struct Audit {
    conforms compiler::Plugin

    fn register(entries: mut compiler::Entries) {
        entries.inspect(code: "audit.foreign-call", level: .deny, run: checkForeignCalls)
    }
}

fn checkForeignCalls(body: compiler::SealedBody, report: mut compiler::Diagnostics) {
    for call in body.calls where call.target.isForeign {
        if !call.attributes.has("reason") {
            report.add(at: call.span, "вызову функции C нужна причина: @reason(\"…\")")
        }
    }
}
```

## C. Анализ потока данных

Плагин даёт тип факта и правила перехода; Amber даёт граф потока управления, факты ядра, решатель и порядок
обхода.

```efen
/// Данные, прочитанные извне, не доходят до запроса SQL без проверки.
struct Taint {
    conforms compiler::Fact            // низ, верх, объединение, порядок
    var tainted: Set<compiler::Place>
}

struct TaintSummary {
    var taintedResult: Bool
    var taintedArguments: Set<Int>
}

struct TaintAnalysis {
    conforms compiler::Analysis<Taint, TaintSummary>

    let bound = 64
    let reads = [compiler::kernelFacts]

    fn transfer(node: compiler::Node, fact: mut Taint) { … }
    fn call(callee: compiler::Callee<TaintSummary>, arguments: [compiler::Place], fact: mut Taint) { … }
    fn summary(exit: Taint) -> TaintSummary { … }
    fn finish(facts: compiler::Facts<Taint>, report: mut compiler::Diagnostics) { … }
}

struct TaintPlugin {
    conforms compiler::Plugin

    fn register(entries: mut compiler::Entries) {
        entries.analysis(TaintAnalysis(), codes: ["taint.sql-injection"], level: .deny)
    }
}
```

- **Верх и предел.** `Fact` объявляет не только низ, но и верх. Цикл или группа рекурсии, которые не сошлись за
  `bound` шагов, получают верх — безопасный ответ — и диагностику плагина у цикла. Несошедшейся сводки не бывает.
  Группа рекурсии всегда начинается с низа, поэтому частичная сборка и полная дают одно.
- **Вызываемые.** `Callee` — сводка, функция C, косвенный вызов или функция, у которой сводки ещё нет. Каждый
  случай решает плагин; по умолчанию — верх.
- **Модели чужих функций.** Плагин держит свои данные о функциях, которые ему не принадлежат: `readLine` —
  источник, `query` — приёмник. Объявление функции и то, во что верит ядро, от этого не меняются.
- **Сводки.** Сводка — простые данные с хешем. Изменился хеш — вызывающие функции проверяются заново, даже если
  их модуль не менялся, поэтому переиспользованный результат не пропустит новой находки.
- **Зависимости.** На функциях зависимости анализ только строит сводки и ничего не сообщает. Предел, превышенный
  внутри зависимости, сообщается у вызова из проекта.
- **Порядок.** Анализ объявляет в `reads`, что читает: факты ядра, записи реестра или другой анализ по имени. Эти связи
  образуют граф без циклов, который проверяется при чтении конфигурации; анализы без связи между собой могут
  идти одним обходом.

## Диагностики

Диагностика плагина имеет ту же форму, что и диагностика ядра: код, уровень, сообщение, место, примечания,
связанные шаги и цепочку происхождения ([происхождение](plugins.md#происхождение-и-отчёт-доверия)).

- **Коды по пространству имён плагина:** `taint.sql-injection`. Префиксы кодов ядра (`flow.`, `typestate.`,
  кодов эффектов и условий) плагину не выдаются. Группы проверок Amber (стиль `S`, заметки `Proof`) — коды
  Amber, их уровни задаются так же ([группы диагностик](../diagnostic-groups.md)).
- **Уровни** `deny`, `warn`, `allow`, `notice` задаются для кода в секции `diagnostics` конфигурации. Секция
  сливается по уровням конфигурации запись за записью: глобальный файл задаёт уровни проверок Amber, проект
  меняет нужные (агент). Флаги командной строки `-W…` действуют поверх конфигурации. Находку ядра не понизить.
- **Уровни и пересборка.** `deny` останавливает компиляцию функции, поэтому набор кодов с уровнем `deny` входит
  в идентичность сборки. Смена между `warn`, `allow` и `notice` применяется к сохранённым находкам при выводе и
  ничего не пересобирает (агент).
- **Подавление в одном месте:** `@allow("taint.sql-injection", reason: "…")` у оператора или объявления, только
  для кода плагина и только с причиной. Одна ложная находка не требует понижать уровень во всём проекте.
- **Исправления:** правка текста пользователя, которую можно применить автоматически. `amber fix` применяет её,
  сервер языка предлагает как действие. Правка вне пакетов проекта отклоняется.

```efen
config server {
    plugins {
        taint: "^1.2"
    }

    diagnostics {
        "taint.sql-injection": deny
        "audit.foreign-call": warn
    }
}
```

```efen
@allow("taint.sql-injection", reason: "запрос собирается из констант, проверено в review 412")
let report = database.run(text)
```

## Предложения и требования

**Предложение.** Анализ предлагает факт, которого ядро само не находит: `assert` или инвариант цикла внутри
одного тела. Предложение для другой функции (`requires` вызываемой) не принимается: новый вызывающий
сделал бы убранную проверку устаревшей. Ядро проверяет все предложения тела вместе и отбрасывает
недоказанные, пока остальные не докажутся, поэтому результат не зависит от порядка. Доказанное предложение
становится записью реестра и позволяет генератору убрать проверку при выполнении. Предложения проверяются
за один проход: доказанные не возвращаются анализу как новые факты, поэтому проверка конечна (агент).

**Требование.** Плагин добавляет свойство, которое программа обязана выполнить: каждая публичная функция модуля
объявляет `ensures`, каждый цикл — `decreases`. Требование входит в реестр как неизвестное; его решают FLOW, Z3
или плагин доказательств. Нерешённое требование — диагностика плагина на уровне её кода.

## E. Вставка кода в режиме

Проход, названный в конфигурации для режима, вставляет код во все функции проекта. Это единственный
проверяемый плагин, который меняет не только место, назвавшее его (Edmond, 2026-10-29: «да может»).

```efen
config server {
    mode testing {
        plugins {
            coverage: "^1.0"
        }
    }
}
```

- Код вставляется только в названных точках: вход, выход, ветки. Несколько проходов применяются по порядку
  имён, поэтому результат один.
- Проход читает ограничения функции (функция вызывается из условий, `nothrows`, `without Allocates`) и
  пропускает функцию, которую не может дополнить в их рамках, с уведомлением. Счётчик покрытия — запись в
  память, и можно ли её делать в функции, которую вызывают условия, решает ядро; правило ещё не написано.
- Результат проходит ядро. `amber expand` показывает вставленный код; доказательства тестовой сборки
  относятся к дополненному телу.

## D, F, H, G

- **D, анализ программы** работает при сборке программы по всем сводкам и графу вызовов функций. Его ошибка
  останавливает сборку программы. Он работает один раз на сборку программы, а не на каждую правку.
- **F, выходные файлы** читает запечатанную программу после успешной сборки и пишет только в выходной каталог,
  который назвала конфигурация, через импорт песочницы, который выдаётся только этому способу. Его результат
  кэшируется по входам.
- **H, доказательство** получает записи реестра со статусом «неизвестно» с их контекстом и возвращает доказательство,
  которое проверяет ядро (формат LRAT или Alethe). Голый ответ «верно» не принимается. Запись реестра
  помнит, какой плагин, какой версии и за какое время её доказал.
- **G, после запечатывания** — оптимизация MLIR или своя цель. Ядро этот код не перепроверяет, поэтому плагин
  доверенный, и записи реестра, которые на него опираются, помечаются «на вере».

## Пределы

- Плагин читает запечатанный HIR, синтаксическое дерево своего модуля, факты ядра и реестр. После
  запечатывания он ничего не меняет; исключение — доверенный G.
- Плагин не снимает находку ядра, не понижает её уровень и убирает проверку при выполнении только доказанным
  предложением.
- Плагин детерминирован, ограничен в шагах и компилируется в песочнице.
- Время каждого плагина — своя строка в `--timings`, по плагину и по функции.
- Ключ содержимого плагина и его настройки входят в идентичность сборки, уровни диагностик — нет.

## Порядок появления в Amber

1. A: проверка типов-состояний в FLOW, сводки на зависимостях. Метакод для этого не нужен.
2. Пространства имён кодов, уровни, `@allow`, исправления, `amber fix`, действия сервера языка.
3. Одна проверка Amber как осмотр, написанный на C++ по точной форме `compiler::Plugin`, чтобы проверить
   интерфейс до того, как заработает метакод; затем она переносится на Efen.
4. Реестр свойств; `amber trust` по нему.
5. Когда заработает метакод: C0 на Efen; C с общим решателем и сводками; время по плагинам.
6. B: новые виды эффектов и `without` для них.
7. Предложения и требования; H; D; F; E.
