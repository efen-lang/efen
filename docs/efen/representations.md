# Репрезентации (Representations)

Representation задаёт способ физической укладки памяти конкретного типа. Она
принадлежит объявлению типа, а не переменной. У каждого конкретного типа ровно
одна representation.

## Структура

Структура указывает форму непосредственно в теле:

```efen
struct Name {
    representation SoA

    // поля
}
```

`SoA` обозначает форму, доступную реализации этого типа. Контракт объявления
самих форм и стандартное значение при отсутствии строки `representation` ещё
требуют отдельной спецификации.

## Контейнер

Форма контейнера включает не только форму одного элемента, но и способ
размещения множества элементов. Поэтому `AoS` и `SoA` являются формами массива,
а не отдельного `Particle`.

Контейнер может открыть выбор формы compile-time параметром. Значения такого
параметра — значения enum, объявленные самим контейнером. Например, `Array`
объявляет варианты:

```efen
struct Array {
    enum Representation {
        aos
        soa
    }
}
```

Точная грамматика объявления enum-параметра в generic-сигнатуре пока не
определена. При инстанциации значение передаётся вторым compile-time аргументом.

Конкретная инстанциация имеет одну форму:

```efen
type ParticleAoS: Array<Particle, aos>
type ParticleSoA: Array<Particle, soa>
```

`AoS` хранит целые элементы последовательно. `SoA` строит отдельное хранилище
для соответствующих полей элементов. Compile-time код `Array` определяет точную
укладку, операции доступа, создание, уничтожение, копирование и перемещение для
каждого поддерживаемого значения `form`.

`[T]` является поверхностным сахаром для `Array<T, default>`. Значение `default`
выбирает стандартную representation, объявленную самим `Array`.

Если программе одновременно нужны разные формы, она использует разные
конкретные типы или разные инстанциации generic-типа. Преобразование между ними
задаётся явно, в том числе отдельной стратегией `Coerce`.

## Колоночные storage projections

Приведённый ниже синтаксис `storage` относится к более раннему исследованию и
ещё не перенесён на текущие
[дескрипторы памяти](memory/addresses.md). Он не является нормативным
синтаксисом исходного языка.

Layout может связать логическое население обычных структур с несколькими
физическими хранилищами. Например, поля `Particle` могут лежать отдельными
columns, а общая встроенная часть HIR-узлов — отдельно от payload каждого вида.

Это не вторая representation типа `Particle` или `Function`. Самостоятельное
значение сохраняет representation своего типа; член `storage` внутри layout
задаёт projection логической identity населения в физические rows и columns.

```efen
layout World {
    source memory: Arena
    set Particles: Particle from memory

    storage columns for Particles {
        representation Columnar<Particle>
    }
}
```

Программа продолжает использовать обычные `particle.position` и
`function.body`. Accessors layout находят physical coordinate по logical
identity и field path. Подробный контракт, split-by-kind HIR, транзакции,
ссылки и сериализация описаны в [колоночных layout](memory/columnar-layouts.md).

## Границы ответственности

- тип задаёт логическую семантику и единственную выбранную representation;
- representation задаёт физическую укладку и операции жизненного цикла;
- layout задаёт область принадлежности памяти и происхождение ссылок;
- allocator предоставляет память по запросу реализации типа.

Нижнерегистровая конструкция `layout Name { ... }` задаёт область
принадлежности, населения и происхождение ссылок. Отдельный универсальный
generic-тип для описания allocation текущей модели не требуется: операции
выделения принадлежат конкретным дескрипторам памяти.

Layout управляет памятью средствами HIR и может помечать созданные им слоты как
`managed`. Для скрытого physical slot borrow checker отключён; layout, аспект
или метакод строит операции создания, хранения, перемещения и освобождения.
Публичный projected place населения сохраняет обычную проверку origin, rights,
liveness и borrows. Пользователь не пишет `managed` как модификатор переменной —
это свойство порождённого HIR-слота.

Сам HIR также описывается обычными структурами Efen и пользуется тем же
механизмом representation. Логическое поле HIR может иметь естественный тип
`String`, `[HirNodeId]` или `Type`, тогда как representation кодирует его строковым
ID, диапазоном, side table или другой физической формой. Поэтому C++ record
начального Amber является одной bootstrap-реализацией, а не пределом модели HIR.

В частности, layout HIR может применить разнесённое хранение видов: общие поля
`BaseNode` находятся в columns всех узлов, а поля `Function`, `Call` и
динамически добавленных видов — в отдельных payload stores. Для пользователя и
метакода они всё равно остаются обычными структурами Efen со встраиванием.

Срез коллекции является невладеющим view её storage. Он сохраняет origin,
диапазон и доступные права, но не получает отдельную representation и не копирует
элементы. Representation владельца определяет, как view обращается к данным.

Representation обязана сохранять наблюдаемую семантику типа. Компилятор
диагностирует несовместимый доступ, скрытое дорогое преобразование, скрытое
выделение памяти и нарушение ownership.
