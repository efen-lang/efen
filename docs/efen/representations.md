# Представления типов в памяти

Представление типа определяет, как его данные хранятся в памяти
и как выполняются операции над этим хранилищем. Оно выбирается для конкретного
типа, а не для отдельной переменной. У каждого конкретного типа одно
представление; его задаёт строка `representation` в объявлении.

Логический тип и способ хранения рассматриваются отдельно. Например,
элементы массива можно хранить целыми записями или разнести их поля
по отдельным массивам, сохранив смысл доступа к элементу.

## Структура

Структура указывает форму непосредственно в теле:

```efen
struct Name {
    representation SoA

    // поля
}
```

`SoA` обозначает форму, доступную реализации этого типа. Контракт объявления
самих форм и стандартное значение при отсутствии строки `representation` ещё
требуют отдельной спецификации.

## Контейнер

Форма контейнера включает не только форму одного элемента, но и способ
размещения множества элементов. Поэтому `AoS` и `SoA` являются формами массива,
а не отдельного `Particle`.

Контейнер может открыть выбор формы параметром времени компиляции. Значения такого
параметра — элементы перечисления, объявленные самим контейнером. Например, `Array`
объявляет варианты:

```efen
struct Array {
    enum Representation {
        aos
        soa
    }
}
```

Значение перечисления передаётся вторым аргументом времени компиляции.
Объявление таких параметров описано в статье [о параметрах типов](generics.md#compile-time-значения).

Конкретная инстанциация имеет одну форму:

```efen
type ParticleAoS: Array<Particle, aos>
type ParticleSoA: Array<Particle, soa>
```

`AoS` хранит целые элементы последовательно. `SoA` строит отдельное хранилище
для соответствующих полей элементов. Код времени компиляции `Array` определяет точную
укладку, операции доступа, создание, уничтожение, копирование и перемещение для
каждого поддерживаемого значения `form`.

`[T]` является сокращённой записью для `Array<T, default>`. Значение `default`
выбирает стандартное представление, объявленную самим `Array`.

Отдельный параметр `indirection` выбирает, лежит ли в ячейке значение или указатель на него
([параметры типов](generics.md), [библиотеки на C](foreign.md#массивы)).

Если программе одновременно нужны разные формы, она использует разные
конкретные типы или разные экземпляры параметризованного типа. Преобразование между ними
задаётся явно, в том числе отдельной стратегией `Coerce`.

## Встроенные формы `Raw` и `Packed`

Две формы встроены в язык и пишутся строкой `representation` в теле класса или варианта:

- `representation Raw<I>` в классе: объект — одно значение целого типа `I` или его уточнения, без заголовка и своей
  памяти ([класс над внешним значением](classes.md#класс-над-внешним-значением)). У класса `@abi(c)` без этой
  строки сырое значение — тип C класса;
- `representation Packed<I>` в варианте: значение — одно `I`, случаи различаются диапазонами
  ([`Packed`](types/variant.md#представление-packed)).

Представление опционального типа для конкретного `T` объявляет модуль `T`:

```efen
@platform(os: "linux")
public type Option<File> {
    representation Raw<Int32>
    null: -1
}
```

Это не номинальный тип: `File?` и `Option<File>` — один тип, объявление задаёт только способ хранения. `File?` — одно
`Int32`, `-1` — пустое значение; компилятор проверяет, что `-1` не входит в уточнение `File`. Подробно —
[опциональные типы](types/optional.md#внутреннее-представление).

## Проекции колоночного хранилища

Колоночное хранение элементов множества `layout` (каждое поле в своём столбце, общая часть узлов отдельно от данных
видов узлов) правилами `layout` пока не описано. Значение отдельного типа хранится по его собственному
представлению. Раннее исследование колоночных форм хранится в истории проекта amber
(`dev/research/columnar-layouts.md`, `dev/research/layout-representations.md`).

## Границы ответственности

- тип задаёт логическую семантику и единственное выбранное представление;
- представление задаёт физическую укладку и операции жизненного цикла;
- компоновка задаёт область принадлежности памяти и происхождение ссылок;
- распределитель памяти предоставляет память по запросу реализации типа.

Блок [`layout`](memory/layout-reference.md) стоит на уровне модуля, экземпляров у него нет: он задаёт множества элементов,
их вложенность и законы, а по ним FLOW доказывает происхождение и время жизни указателей. Память входит в
множество приведением `as` и выдачей `lend`, а не операцией «выделить».

Скрытые слоты с режимом `managed`, которые создаёт компилятор, обычной проверке заимствований не подчиняются;
операции создания, хранения, переноса и освобождения для них формирует метакод.

Доступный программе логический слот по-прежнему проверяется по источнику,
правам и времени жизни. Внутренний режим физического хранилища не отменяет
проверку пользовательских ссылок. Модификатор `managed` у переменной
в исходном коде не пишется: это свойство созданного слота HIR.

Сам HIR также описывается обычными структурами Efen и пользуется тем же
механизмом представлений. Логическое поле HIR может иметь естественный тип
`String`, `[HirNodeId]` или `Type`, тогда как представление кодирует его строковым
ID, диапазоном, вспомогательной таблицей или другой физической формой. Первоначальная C++-структура Amber — одна из возможных реализаций HIR;
общая модель не ограничивается её физическим устройством.

В частности, компоновка HIR может применить разнесённое хранение видов: общие поля
`BaseNode` находятся в столбцах всех узлов, а поля `Function`, `Call` и
динамически добавленных видов — в отдельных хранилищах данных. Для пользователя и
метакода они всё равно остаются обычными структурами Efen со встраиванием.

Срез коллекции даёт невладеющий доступ к части её хранилища. Он сохраняет
источник, диапазон и права, не копируя элементы и не выбирая для них другое
представление. Способ доступа к данным определяется представлением владельца.

Представление обязано сохранять наблюдаемую семантику типа. Компилятор
диагностирует несовместимый доступ, скрытое дорогое преобразование, скрытое
выделение памяти и нарушение правил владения.
