# Построение класса аспектами

> Статус: модель языка. Политика позднего подключения аспектов и раздел
> «Открытые вопросы» сохраняют решения, которые ещё требуют подтверждения.

`ClassDefinition` — встроенный контракт аспекта, определяющего построение
класса. Аспект работает со структурой `lang::Class` внутри HIR и может изменять
её до начала окончательной обработки тел методов.

Аспект класса является расширением компилятора для всех операций, относящихся
к классу. Он может контролировать построение создания и уничтожения экземпляра,
присваивания, доступа и изменения свойства, копирования, перемещения, вызова и
диспетчеризации. Компилятор передаёт ему известные compile-time входы операции;
аспект строит HIR, который затем проходит общие проверки и понижение Amber.

## Выбор определения класса

Для корня иерархии выбирается ровно один аспект, реализующий
`ClassDefinition`. Две явные реализации на одном корневом классе являются
ошибкой компиляции.

Если определение указано на корневом классе явно, используется оно. Иначе
директивы `provide` из конфигурации сборки выбирают реализацию по умолчанию,
например определение класса из подключённого runtime.

Производный класс не может применить или заменить `ClassDefinition`. При
построении каждого класса иерархии компилятор использует определение, выбранное
её корнем. Это правило не задаёт отражение эффективного аспекта в
`getAspects()` и число экземпляров compile-time аспекта: эти детали относятся к
реализации compile-time API.

Основной аспект может использовать готовые реализации отдельных операций и
предоставлять функции, через которые другие аспекты расширяют структуру
производного класса. Такое расширение изменяет производный класс, а не
физическую структуру его базы.

## Исходный и рабочий виды

После чтения объявления компилятор сохраняет его исходное отображение в HIR —
С0. Этот вид содержит записанные программистом члены и тела и остаётся
неизменяемым после любых преобразований. Он не обещает окончательного
разрешения типов, членов и порождённых объявлений.

Параллельно компилятор создаёт рабочий `lang::Class`. В начале построения он
соответствует С0, затем аспекты изменяют его. Обычные операции compile-time API
читают текущий рабочий вид; исходный вид запрашивается явно и доступен на всех
последующих шагах.

`primaryClassDefinition` вызывается в начале структурного построения и видит
класс в исходном состоянии. Он изменяет рабочий `lang::Class`, а не сохранённый
С0. `finallyClassDefinition` вызывается после остальных шагов и получает
последнюю возможность изменить рабочий класс.

Схематическая форма контракта:

```efen
contract ClassDefinition {
    meta fn primaryClassDefinition(class: lang::Class) in compiler
    meta fn finallyClassDefinition(class: lang::Class) in compiler
}
```

Методы контракта ничего не возвращают: результатом являются разрешённые
изменения рабочего `lang::Class`.

## План построения

Компилятор создаёт базовый `ClassDefinitionPlan`. Сначала основной аспект
расширяет план, затем остальные аспекты могут зарегистрировать обработчики и
добавить собственные уникальные шаги.

Дополнительный аспект, который участвует в сборке своей цели наряду с основным
определением класса, реализует `ClassDefinitionHandler`. Во время регистрации
операция этого контракта получает план и добавляет в него шаги или обработчики;
точное имя операции compile-time API пока не закреплено.

Шаг задаёт только:

- уникальное имя;
- ограничения порядка `before` и `after`;
- зарегистрированные обработчики.

Готовность данных обслуживает обычная модель запросов компилятора, а право
изменить HIR — свойства соответствующих узлов. План не дублирует эти механизмы
полями `requires`, `produces` или `mayChange`.

Аспект одного класса может подписать обработчик на конкретный результат плана
другого класса. Зависимость строится между результатами стадий, а не между
классами целиком. Поэтому взаимная ссылка типов сама по себе не создаёт цикл:
план `A` может ждать полного списка свойств `B`, пока плану `B` уже достаточно
ранней идентичности `A`. Для настоящей взаимной зависимости общего решения нет;
аспект работает с частичным классом, выбирает другой результат плана либо
сообщает ошибку.

Регистрация отделена от изменения класса:

```text
прочитать класс и сохранить С0
→ выбрать эффективный ClassDefinition корня
→ создать базовый план
→ дать ClassDefinition расширить план
→ зарегистрировать шаги и обработчики остальных аспектов
→ проверить и зафиксировать план
→ primaryClassDefinition
→ упорядоченные шаги
→ finallyClassDefinition
→ зафиксировать структуру класса
→ обработать необходимые тела методов
```

Регистрационная часть не изменяет поля, методы и тела `lang::Class`.
`primaryClassDefinition` и `finallyClassDefinition` являются крайними
структурными шагами. После `finallyClassDefinition` компилятор проверяет и
публикует окончательный состав класса; обработчики разрешения членов могут
порождать выражения в телах, но не открывают состав класса заново.

Неизвестное имя в `before` или `after`, повторное объявление имени шага и цикл
порядка являются ошибками. При нескольких допустимых топологических порядках
компилятор выбирает воспроизводимый порядок, не зависящий от числа потоков.

### Подключение новых аспектов

Правило первой версии: исполняемый состав аспектов и план расширяются только во
время регистрации. Добавление аспекта в этот момент регистрирует новое
применение, после чего регистрация продолжается до тех пор, пока новых
применений не останется. Одно применение не регистрируется повторно.

После начала `primaryClassDefinition` нельзя подключить compile-time аспект,
которому нужны новые шаги или обработчики текущего плана. Такая попытка является
ошибкой. Перезапуск уже выполненных шагов и откат рабочего класса в первую
версию модели не входят.

Это ограничение закрывает случай, когда поздно добавленный аспект требует шаг
`before` уже выполненного. В будущем его можно заменить отдельной моделью
ревизий и повторного построения, не меняя минимальный контракт шага.

## Права изменения HIR

Любой узел HIR может содержать режимы доступа и запрет дальнейшего изменения.
Запрет действует и на поддерево узла с учётом режимов, выданных до его
установки. После запрета нельзя добавить новое разрешение, чтобы обойти его.

Компилятор сохраняет происхождение каждого изменения и ограничения: запущенный
аспект или метафункцию, место применения и позицию операции в исходном коде.
Диагностика нарушения показывает как место установки запрета, так и попытку
изменения.

Запрет проверяется и при косвенной мутации. Нельзя удалить защищённый метод,
заменив список членов родительского узла, перенести его в другое место или
заменить содержащий его узел вместе с ограничением.

## Изменение поверхности класса

Без отдельного разрешающего контракта аспект может физически создать в целевом
классе только приватный метод. Создание нового неприватного метода требует
явного контракта, предоставляющего соответствующее право. Методы `ClassBuilder`
являются операциями, а не сами по себе разрешениями.

Уже объявленный метод или свойство нельзя удалить либо изменить с нарушением
контракта класса. Аспект может заменить реализацию и физическое представление:
например, логическое свойство может не занимать отдельного места в памяти, а
его чтение, запись и присваивание реализуются созданным аспектом HIR.

Внешний модуль не изменяет чужой builder напрямую. Библиотека может установить
аспект, который публикует функцию изменения либо принимает замыкание с
ограниченным объектом изменения. Внешний код пользуется этим API; `provide` сам
по себе не создаёт полномочий.

Стратегия предоставляет публичное поведение отдельным механизмом разрешения.
Вызов метода стратегии через значение не означает, что этот метод добавлен в
физический список методов `lang::Class`, поэтому стратегии не обходят описанное
ограничение.

Даже приватный порождённый метод подчиняется правилам имён, текущего шага и
ограничениям HIR. Конфликт двух приватных методов не приводит к молчаливой
замене одного из них.

## Анализ тел и владение

Аспекты, метафункции и обработчики разрешения сначала порождают относящийся к
телу HIR. Анализ владения выполняется над получившимся кодом. Компилятор сам
определяет места поддерживаемых операций ARC и других моделей владения и
вставляет обращения к предоставленным реализациям `retain`, `release` и других
операций.

Это зависимость отдельного обрабатываемого тела, а не требование сначала
выполнить все аспекты всей программы. Итог анализа тела нельзя публиковать,
пока влияющая на него генерация не завершена.

Код `meta` должен быть скомпилирован до исполнения. Runtime-зависимость того же
аспекта сама по себе не создаёт compile-time цикл; ошибкой является цикл
результатов, действительно необходимых для текущего compile-time вызова.

## Обобщённые классы

`ClassGenericDefinition` строит параметризованный generic. При его раскрытии
контракт получает конкретные compile-time аргументы и сам решает, создавать ли
новый реальный класс или использовать уже существующую реализацию. Затем
обычный `ClassDefinition` достраивает выбранный реальный класс.

Группы стёртых реализаций не выводятся компилятором автоматически. Если общей
реализации нужна информация о конкретном типе, компилятор передаёт её аспекту
как compile-time вход операции. Аспект может контролировать построение `=` и
сохранить нужную runtime-информацию в созданном HIR.

## Открытые вопросы

- Как новый план сопрягается с поздними стадиями, межклассовыми запросами и
  структурными декораторами.
- Технический bootstrap первоначального исполняемого compile-time кода.

В первой версии продукт зависимости полный: он сохраняет исходные атрибуты,
планы, provenance, metadata и требуемый исполняемый compile-time код. Режима
сокращённого продукта и повторного исполнения удалённых аспектов у потребителя
нет.
