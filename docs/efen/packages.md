# Пакеты, модули и программы

Код на Efen живёт на четырёх уровнях (решение Edmond от 2026-10-30, вопрос Q61):

| Уровень | Что это | На диске | Что задаёт |
|---|---|---|---|
| Рабочее пространство | Несколько пакетов, которые разрабатывают вместе | папка с `workspace.efen` | список пакетов (`members`), общие версии зависимостей, `efen.lock`, среду сборки, слои |
| Пакет | Единица версии, зависимости и публикации; область `internal` | папка с `project.efen` | имя, версию, зависимости, свои программы |
| Модуль | Файл `.efen` пакета; область имён и `private` | файл | имена, `use`, видимость определений |
| Программа | Исполняемый файл, который объявляет пакет; собирается целиком вместе со всеми зависимостями | раздел пакета в `project.efen` | точку входа, аллокатор, рантайм, платформу, `provide`, `effects` |

«Проект» — другое название пакета: так его называет тот, кто в нём работает, а «пакетом» — тот, кто от него
зависит. Один пакет без `workspace.efen` — рабочее пространство из одного пакета.

```
shop/
├── workspace.efen        # config shop { members: ["model", "server"] }
├── model/                # пакет model: только библиотека
│   ├── project.efen      # config model { version: "1.2.0" }
│   ├── invoice.efen      # модуль model::invoice
│   └── tax/
│       └── rates.efen    # модуль model::tax::rates
└── server/               # пакет server: библиотека и две программы
    ├── project.efen      # config server { dependencies { model: path("../model") } … }
    ├── main.efen         # точка входа программы server
    ├── migrate.efen      # точка входа программы migrate
    └── routes.efen       # модуль server::routes
```

## Рабочее пространство

`workspace.efen` в корне перечисляет пакеты (`members`) путями или шаблонами и задаёт общие версии зависимостей,
которые пакеты берут значением `workspace` ([конфигурация сборки](build-config.md)). У пространства нет своего
имени для зависимостей, версии и выхода сборки: собираются и публикуются пакеты. Один сервер компилятора обслуживает
всё пространство; файл блокировки `efen.lock` и база компилятора `.amber/` лежат в его корне.

## Пакет

Пакет — папка с `project.efen`. Его имя — имя объявления `config` в этом файле; другого имени у пакета нет, и
отдельного объявления `package` в исходных файлах нет. Тот, кто зависит от пакета, называет его этим именем в
`dependencies` и в `use`.

Пакет поставляется целиком и имеет одну версию. Из своих модулей он даёт:

- **библиотеку** — его модули, доступные пакетам, которые от него зависят; у пакета одна библиотека или ни одной;
- **программы** — сколько угодно исполняемых файлов, каждый со своей точкой входа `fn main`
  ([конфигурация сборки](build-config.md#программы));
- тесты и примеры, которые компилятор собирает сам ([тесты](tests/tests.md)).

Соседний пакет того же рабочего пространства подключается путём: `model: path("../model")`. Значение `workspace`
у зависимости — это версия, записанная в `workspace.efen`, а не пакет пространства.

Вложенных пакетов нет: папка с `project.efen` внутри пакета — другой пакет, и в модули первого не входит.

Имя пакета может начинаться с приставки пространства имён: `Billing::Core`, `Billing::Model`. Приставка только
разводит одинаковые имена и собирает пакеты в [слоях](layers.md); видимости у пространства имён нет. Как такое имя
записывается в `config` — открыто.

## Модуль

Модуль — файл `.efen` пакета, кроме `project.efen`, `workspace.efen` и `layers.efen`. Он не требует объявления.
Имя модуля — путь файла от папки пакета без расширения, части пути через `::`: `invoice.efen` — модуль `invoice`,
`tax/rates.efen` — модуль `tax::rates`.

Внутри файла можно объявить вложенный модуль блоком; его имя продолжает имя файла:

```efen
// limits.efen — модуль limits
module network {                        // модуль limits::network
    public const DEFAULT_PORT = 8080
}
```

Полное имя определения — пакет, путь модуля и имя через `::`:

```efen
model::invoice::Invoice
model::tax::rates::vat
```

`::` пишется только в пути к пакету и модулю, `.` — для членов и статического доступа (Q49).

## Импорт: `use`

Имя другого модуля доступно только через `use` или по полному пути, но не просто так.

```efen
use model::invoice                      // имена модуля без приставки: Invoice
use model::invoice as inv               // приставка inv: inv::Invoice
use model::invoice::{Invoice, total}    // только названные имена
use model::invoice::*                   // все видимые имена модуля

fn report {
    let a = Invoice()                   // через use
    let b = model::tax::rates::vat()    // по полному пути, без use
}
```

- `use` действует на весь свой модуль, где бы ни стоял.
- Путь из одного слова — модуль своего пакета (`use routes`) или пакет-зависимость (`use model`); модуль своего
  пакета ищется первым, а модуль и пакет одного имени — ошибка у `use`.
- Модуль своего пакета пишется без имени пакета: `use tax::rates`.
- Своё имя и импортированное, или два импорта с одним именем — конфликт, ошибка в месте использования имени. Порядок
  `use` его не решает (как у диалектов, Q36); `use … as` даёт одному из них другое имя.
- Модули могут ссылаться друг на друга по кругу (Q35).
- `use` даёт доступ только к тому, что видно из этого модуля ([видимость](visibility.md)).

## Локальная конфигурация зависимостей

Каждый пакет является корнем конфигурации для собственного компилируемого кода.
Это не особый «главный пакет» приложения: библиотека, которая использует другие
пакеты, имеет то же право локально выбрать предоставленную ими стратегию.

`use` подчиняет стратегию обычным правилам видимости символов, но сам по себе не
активирует стратегию из другого пакета. Для этого текущий пакет использует
`provide`:

```efen
// модуль пакета Reports
use Documents
use JsonStrategies

provide JsonDocument for Documents::Document
```

Такой выбор действует при компиляции `Reports` и не экспортируется. Пакет,
который позже сделает `use Reports`, не наследует `provide JsonDocument` для
своего кода. Вызов уже скомпилированной функции `Reports` сохраняет её внутреннее
поведение, но разрешение операций вызывающего пакета строится из его собственной
локальной конфигурации.

Если пакет не выбрал стратегию сам, действует выбор программы: секция `provide`
конфигурации исполняемого проекта ([выбор программы](strategies.md#выбор-программы)).

Право импортировать стратегию не равно праву объявить её для чужого типа. Пакет
типа всегда может объявлять свои стратегии; внешний пакет может сделать это
только после явного разрешения в объявлении типа. Полные правила описаны в
[«Стратегиях»](strategies.md).

## Подпись и происхождение

Зависимости из реестра и git закрепляются по хешу дерева, а не по тегу. С версии v1 в режимах
`trust: required` сборка принимает такую версию, только если её подписал ключ автора, который назван в
конфигурации или в подписанном выпуске родителя. Зависимостей `path(…)` и `workspace` это не касается. Подробно —
[подпись библиотек](signing.md).
