# Пакеты и модули

Код на Efen живёт на трёх уровнях (решения Edmond от 2026-10-30 и 2026-10-31, вопрос Q61):

| Уровень | Что это | На диске | Что задаёт |
|---|---|---|---|
| Рабочее пространство | Несколько пакетов, которые разрабатывают вместе | папка с `workspace.efen` | список пакетов (`members`), общие версии зависимостей, `efen.lock`, среду сборки, слои |
| Пакет | Единица версии, зависимости и публикации; область `internal`; одна цель сборки — программа или библиотека | папка с `project.efen` | имя, версию, зависимости, поля программы или виды библиотеки |
| Модуль | Файл `.efen` пакета; область имён и `private` | файл | имена, `use`, видимость определений |

«Проект» — другое название пакета: так его называет тот, кто в нём работает, а «пакетом» — тот, кто от него
зависит. Один пакет без `workspace.efen` — рабочее пространство из одного пакета.

```
shop/
├── workspace.efen        # config shop { members: ["model", "site", "import"] }
├── efen.lock
├── model/                # библиотека: есть lib.efen
│   ├── project.efen      # config model { version: "1.2.0" }
│   ├── lib.efen          # корневой модуль: model::…
│   ├── product.efen      # модуль model::product
│   └── tax/
│       └── rates.efen    # модуль model::tax::rates
├── site/                 # программа: есть main.efen
│   ├── project.efen      # config site { dependencies { model: path("../model") } }
│   ├── main.efen         # fn main
│   └── routes.efen       # модуль программы, наружу не виден
└── import/               # программа
    ├── project.efen      # зависит от model и от библиотеки CSV
    └── main.efen
```

## Рабочее пространство

`workspace.efen` в корне перечисляет пакеты (`members`) путями или шаблонами и задаёт общие версии зависимостей,
которые пакеты берут значением `workspace` ([конфигурация сборки](build-config.md)). У пространства нет своего
имени для зависимостей, версии и выхода сборки: собираются и публикуются пакеты. Один сервер компилятора обслуживает
всё пространство; файл блокировки `efen.lock` и база компилятора `.amber/` лежат в его корне.

`efen build` в папке пакета собирает этот пакет, а в корне пространства — все пакеты из `members`, каждую программу
отдельно (Edmond 2026-10-31).

## Пакет

Пакет — папка с `project.efen`. Его имя — имя объявления `config` в этом файле; другого имени у пакета нет, и
отдельного объявления `package` в исходных файлах нет. Тот, кто зависит от пакета, называет его этим именем в
`dependencies` и в `use`. Настройки пакета живут только в `project.efen`, не в исходных файлах: компилятор читает
их раньше кода, а реестр и инструменты читают только их.

У пакета одна цель сборки, и её видно по корневому файлу. В пакете ровно один из двух:

- **`main.efen`** — пакет-программа. В файле лежит `fn main`; сборка даёт исполняемый файл со всеми зависимостями.
  Поля программы — аллокатор, рантайм, платформа, `provide`, `effects` — пишутся прямо в `project.efen`
  ([конфигурация сборки](build-config.md#программа)). Остальные модули пакета принадлежат программе и наружу не
  видны: от программы зависеть нельзя, такая запись в `dependencies` — ошибка.
- **`lib.efen`** — пакет-библиотека. Это корневой модуль: `use model` даёт его видимые имена, а `model::Product`
  ищется сначала в нём. В нём же пакет объявляет свои атрибуты ([видимость](visibility.md#атрибуты-пакета)).
  `fn main` в библиотеке — ошибка. Из каких видов выхода собирается библиотека, задаёт поле `library`
  ([конфигурация сборки](build-config.md#виды-библиотеки)).

Пакет без `main.efen` и `lib.efen` или с обоими — ошибка. Тесты лежат внутри пакета, компилятор собирает их сам, и
отдельной целью они не считаются ([тесты](tests/tests.md)).

Плагин, аллокатор, рантайм, std и фреймворк тестов — обычные библиотеки: роль им даёт контракт, которому
соответствует их тип, и секция конфигурации, которая их подключает (`plugins`, `allocator`, `runtime`), а не свой
вид пакета ([плагины](compile-time/plugins.md)).

Если утилите нужен код программы, этот код выносят в пакет-библиотеку, и от неё зависят обе программы. Так у
каждой программы свои зависимости: библиотека CSV нужна только `import`, и `site` её не тянет.

Соседний пакет того же рабочего пространства подключается путём: `model: path("../model")`. Значение `workspace`
у зависимости — это версия, записанная в `workspace.efen`, а не пакет пространства.

Вложенных пакетов нет: папка с `project.efen` внутри пакета — другой пакет, и в модули первого не входит.

### Путь пакета

Имя пакета может начинаться с пространства имён: `Billing::Core`, `Billing::Model`. Пространство имён — путь
папки пакета от корня рабочего пространства; сам корень в путь не входит. Пакет пишет полное имя в своём конфиге,
и компилятор проверяет, что оно совпадает с путём папки:

```
shop/
├── workspace.efen
└── Billing/
    ├── Core/
    │   └── project.efen  # config Billing::Core { }
    └── Model/
        └── project.efen  # config Billing::Model { }
```

`config Core` в папке `Billing/Core/` или `config Billing::Core` в папке `Core/` — ошибка. Пакет из реестра или git
сохраняет имя из своего конфига. Пространство имён только разводит одинаковые имена и собирает пакеты в
[слоях](layers.md); видимости у него нет. Внутри пакета путь не пишется: свои модули называются без него.

## Модуль

Модуль — файл `.efen` пакета, кроме `project.efen`, `workspace.efen` и `layers.efen`. Он не требует объявления.
Имя модуля — путь файла от папки пакета без расширения, части пути через `::`: `product.efen` — модуль `product`,
`tax/rates.efen` — модуль `tax::rates`. Имена пакетов и модулей совпадают с именами папок и файлов буква в букву,
регистр тоже; компилятор их не переводит.

Внутри файла можно объявить вложенный модуль блоком; его имя продолжает имя файла:

```efen
// limits.efen — модуль limits
module network {                        // модуль limits::network
    public const DEFAULT_PORT = 8080
}
```

Полное имя определения — пакет, путь модуля и имя через `::`:

```efen
model::product::Product
model::tax::rates::vat
```

`::` пишется только в пути к пакету и модулю, `.` — для членов и статического доступа (Q49).

## Импорт: `use`

Имя другого модуля доступно только через `use` или по полному пути.

```efen
use model::product                      // имена модуля без приставки: Product
use model::product as prod              // приставка prod: prod::Product
use model::product::{Product, price}    // только названные имена
use model::product::*                   // все видимые имена модуля
use model                               // имена корневого модуля lib.efen

fn report {
    let a = Product()                   // через use
    let b = model::tax::rates::vat()    // по полному пути, без use
}
```

- `use` действует на весь свой модуль, где бы ни стоял.
- Путь из одного слова — модуль своего пакета (`use routes`) или пакет-зависимость (`use model`); модуль своего
  пакета ищется первым, а модуль и пакет одного имени — ошибка у `use`.
- Модуль своего пакета пишется без имени пакета: `use tax::rates`.
- Корневой модуль своего пакета модуль зовёт по имени пакета, как и чужой: в пакете `model` модуль `product.efen`
  пишет `use model` или `model::helper()` (Edmond 2026-10-31). Голое имя корня из другого модуля без `use` — ошибка.
- Корневой модуль отдаёт свои `public` определения другим пакетам, только если объявлен `public module`, как любой
  модуль ([видимость](visibility.md)).
- Своё имя и импортированное, или два импорта с одним именем — конфликт, ошибка в месте использования имени. Порядок
  `use` его не решает (как у диалектов, Q36); `use … as` даёт одному из них другое имя.
- Модули могут ссылаться друг на друга по кругу (Q35).
- `use` даёт доступ только к тому, что видно из этого модуля ([видимость](visibility.md)).

## Локальная конфигурация зависимостей

Каждый пакет является корнем конфигурации для собственного компилируемого кода.
Это не особый «главный пакет» приложения: библиотека, которая использует другие
пакеты, имеет то же право локально выбрать предоставленную ими стратегию.

`use` подчиняет стратегию обычным правилам видимости символов, но сам по себе не
активирует стратегию из другого пакета. Для этого текущий пакет использует
`provide`:

```efen
// модуль пакета Reports
use Documents
use JsonStrategies

provide JsonDocument for Documents::Document
```

Такой выбор действует при компиляции `Reports` и не экспортируется. Пакет,
который позже сделает `use Reports`, не наследует `provide JsonDocument` для
своего кода. Вызов уже скомпилированной функции `Reports` сохраняет её внутреннее
поведение, но разрешение операций вызывающего пакета строится из его собственной
локальной конфигурации.

Если пакет не выбрал стратегию сам, действует выбор программы: секция `provide`
конфигурации пакета-программы ([выбор программы](strategies.md#выбор-программы)).

Право импортировать стратегию не равно праву объявить её для чужого типа. Пакет
типа всегда может объявлять свои стратегии; внешний пакет может сделать это
только после явного разрешения в объявлении типа. Полные правила описаны в
[«Стратегиях»](strategies.md).

## Подпись и происхождение

Зависимости из реестра и git закрепляются по хешу дерева, а не по тегу. С версии v1 в режимах
`trust: required` сборка принимает такую версию, только если её подписал ключ автора, который назван в
конфигурации или в подписанном выпуске родителя. Зависимостей `path(…)` и `workspace` это не касается. Подробно —
[подпись библиотек](signing.md).
