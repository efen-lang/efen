# Эффекты и контексты

[Документация](README.md) · [Словарь](glossary.md) · [Throws](throws.md) · [Code regions](code-regions.md)

> Эффекты - это внешняя зависимость, 
> которая не передаётся явно в параметры функции,
> но может быть использована внутри функции через механизм эффектов.

> Контекст — это набор значений, доступных во всём текущем окружении выполнения.

## Зачем эффекты?

Рассмотрим пример функции, которая использует Logger для вывода сообщений:

```efen
fn saveUser(name: String) {
    Logger.log("Saving user: ${name}")
    // Логика сохранения пользователя
}
```

В этом примере функция `saveUser` напрямую зависит от глобального состояния `Logger`,
что затрудняет её тестирование. Вместо этого мы можем использовать эффект для
описания зависимости:

```efen
contract Logger {
    fn log(message: String) -> Void
}

fn saveUser(name: String) in Logger {
    %Logger.log("Saving user: ${name}")
    // Логика сохранения пользователя
}
```

Реализацию `Logger` выбирает конфигурация сборки, а не код: в обычной сборке — запись в файл, в тестах —
запись в память.

```efen
config server {
    provide {
        Logger: FileLogger
    }

    mode testing {
        provide {
            Logger: MemoryLogger
        }
    }
}
```

Если реализацию нужно выбрать во время выполнения, эффект объявляют интерфейсом и привязывают значением в `with`
(см. [Эффект-интерфейс в `with`](#эффект-интерфейс-в-with)).

## Зачем контексты?

Рассмотрим пример из нескольких функций:

```php
function handle(): void {
    $tenantId = getTenantId();                 // 1) определяем параметр в F1
    $pdf = buildInvoice(1001, $tenantId);      // прокидываем дальше
    sendPdf($pdf);
}

function buildInvoice(int $orderId, string $tenantId): string {
    $items = loadItems($orderId);              // F2 делает полезную работу
    $email = fetchCustomerEmail($orderId, $tenantId); // вызывает F3
    return renderInvoice($items, $email);      // сам $tenantId F2 не нужен
}

function fetchCustomerEmail(int $orderId, string $tenantId): string {
    // F3 реально требует tenantId (изолированные БД/схемы)
    return db($tenantId)->value(
        'SELECT email FROM customers WHERE order_id = ?', [$orderId]
    );
}
```

`$tenantId` это уникальный идентификатор арендатора (тенанта) в системе с поддержкой мультиарендности.
Он используется в функции `fetchCustomerEmail`, чтобы выбрать правильную базу данных для запроса
клиента. Однако, чтобы передать `$tenantId` в `fetchCustomerEmail`,
мы вынуждены прокидывать его через `buildInvoice`, которая сама по себе не нуждается в этом параметре.
Это приводит к тому, что функции становятся менее читаемыми и сложными в сопровождении,
так как приходится передавать множество параметров, которые не используются напрямую.

Более того, если в будущем появится необходимость добавить ещё один параметр,
например, `$locale` для локализации, то придётся менять сигнатуры всех функций,
что может привести к ошибкам и усложнить поддержку кода. Иначе говоря это сделает рефакторинг кода
и его сопровождение более трудоёмким и подверженным ошибкам.

С другой стороны, использование глобальных переменных для хранения таких параметров
может привести к проблемам с тестированием, так как глобальное состояние может быть изменено
вне контекста теста, что затрудняет изоляцию и воспроизводимость тестов.

Использование глобальных переменных так же усложняет понимание кода,
делает функции не чистыми, так как они зависят от внешнего состояния,
что может привести к неожиданным побочным эффектам и ошибкам.

Контексты решают эту проблему, предоставляя механизм для передачи таких параметров
без необходимости явно прокидывать их через все функции. Контексты позволяют функциям и классам
использовать внешние зависимости, которые доступны во всём текущем окружении выполнения,
без необходимости изменять их сигнатуры или использовать глобальные переменные.

## Определение контекстов и эффектов

Эффект — обычный контракт или интерфейс. Особой пометки у него нет: эффектом его делает использование.
Функция пишет `in Logger` или вызывает `%Logger.log("start")`, и с этого места `Logger` для неё — эффект.

```efen
contract Logger {
    fn log(message: String) -> Void
}
```

Вид объявления задаёт, как эффект связывается:

| Объявление | Связывание | Вызов |
|---|---|---|
| `contract` | одна реализация на пакет, выбирается при сборке ([статическое связывание](#статическое-связывание-эффектов)) | прямой |
| `interface` | значение в `with` во время выполнения ([эффект-интерфейс в `with`](#эффект-интерфейс-в-with)) | через таблицу интерфейса |

`with` не делает контракт эффектом. Контекст, тип которого реализует контракт, привязывается в `with` как контекст,
а эффект этого контракта по-прежнему берётся из конфигурации.

Контекст определяется с помощью ключевого слова `context`,
за которым следует имя контекста и блок с определением свойств контекста.

```efen
context Environment {
    let db: Database
    let cache: Cache
}
```

Вы можете думать о контексте, как о наборе разных эффектов или значений.
В то время как эффект - это контракт для одного аспекта внешней зависимости, 
контекст — коллекция зависимостей.

## Описание зависимости

Для описания зависимости функции от контекста или эффекта используется синтаксис `in`:

```efen
fn fetchData(query: String) in Environment {
    return %Environment.db.execute(query)
}
```

Параметром для `in` может быть:
- имя контекста
- имя интерфейса или контракта, который используется как эффект

Пример:

```efen
context Environment {
    let db: Database
    let cache: Cache
}

fn fetchData(query: String) in Environment {
    // Вызывает объект из контекста, который виден для функции в момент вызова
    let results = %Environment.db.execute(query)
}

fn main {

    let MainEnv = Environment(
        db: Database(connectionString: "localhost"),
        cache: Cache(size: 1024)
    )

    // Выполнение функции в контексте MainEnv
    with MainEnv {
        fetchData("SELECT * FROM users")
    }
}
```

## Оператор доступа к переменным контекста и эффектам

Порой намного удобнее использовать контекстные переменные напрямую,
без необходимости каждый раз указывать имя контекста.
Для этого используется оператор `%`, который позволяет получить доступ
к свойствам контекста или эффектам напрямую.

```efen
context Environment {
    let db: Database
}

fn fetchData(query: String) in Environment {
    // Использование оператора % для доступа к свойствам контекста
    let results = %db.execute(query)
    return results
}
```

Оператор `%` может быть использован рядом с именем эффекта, 
чтобы вызвать метод эффекта напрямую:

```efen
contract Logger {
    fn log(message: String) -> Void
}

fn fetchData(query: String) {
    %Logger.log("Fetching data with query: ${query}")
    // Логика получения данных
}
```

Компилятор преобразует использование оператора `%` в явные обращения к контексту или эффекту,
что позволяет сохранять читаемость кода, не жертвуя при этом безопасностью типов.

Если несколько несвязанных активных контекстов содержат поле с одним именем,
`%name` является ошибкой неоднозначности. Квалификация выбирает номинальный
контекст: `%Database.db`, через точку, как путь права в сигнатуре (`in mut Database.db`).
Совпадение имён и типов полей не делает контексты эквивалентными.

## Указание зависимостей внутри функции

Контекст или эффект можно указать внутри функции с помощью выражения `in`.
```efen
context Environment {
    let db: Database
}

contract Logger {
    fn log(message: String) -> Void
}

fn fetchData(query: String) {
    in Environment: Environment
    in logger: Logger

    let results = %db.execute(query)
    logger.log("Query executed: ${query}")
    return results
}
```

`in logger: Logger` даёт эффекту короткое имя: `logger.log("start")` — то же, что `%Logger.log("start")`.

## Указание контекста, эффектов для класса, интерфейса, контракта, модуля или пакета

Контекст может быть указан не только для функции, но и для класса, интерфейса, контракта, модуля или пакета.
В этом случае все функции внутри области видимости будут автоматически иметь указанный контекст, 
если они используют переменные с `%`.

Такой подход позволяет избежать необходимости указывать контекст для каждой функции отдельно,
что особенно полезно, когда множество функций внутри класса или модуля зависят от одного и того же контекста.

```efen
context Environment {
    let db: Database
    let cache: Cache
    let logger: Logger
}

class DataService {
    in Environment

    fn getData(query: String) {
        let results = %db.execute(query)
        %logger.log("Data fetched for query: ${query}")
        return results
    }

    fn cacheData(key: String, data: Any) {
        %cache.store(key, data)
        %logger.log("Data cached with key: ${key}")
    }
    
    fn withoutContextMethod {
        // Эта функция не использует контекст
        print("This method does not in the context.")
    }
}
```

Контекст может быть указан для контракта:

```efen
context Environment {
    let db: Database
    let cache: Cache
}

contract DataContract {
    in Environment
    fn getData(query: String) -> Any
    fn cacheData(key: String, data: Any)
}

class DataService {

    conforms DataContract

    fn getData(query: String) -> Any {
        let results = %db.execute(query)
        return results
    }

    fn cacheData(key: String, data: Any) {
        %cache.store(key, data)
    }
}

```

В этом случае все классы, которые реализуют этот контракт, автоматически требуют контекста `Environment`.

## Гарантии этапа компиляции

Компилятор использует информацию о контексте для проверки корректности использования
переменных с `%` в функциях, классах, интерфейсах и контрактах.
Для этого он анализирует пути вызовов функций и проверяет, что в момент вызова функции
существует доступный контекст, удовлетворяющий требованиям функции.

Компилятор автоматически переносит required контексты из функций вызывающего кода
в вызываемые функции. То есть:

```efen
context EnvA {
    let a: String
}

fn funcB in EnvA {
    print(%a)
}

fn funcA {
    print(%a)
    funcB()
}

fn main {
    let context = EnvA(a: "Hello, World!")

    with context {
        funcA()
    }
}
```

`funcA` наследует required контекст `EnvA` от `funcB`, поэтому в функции `main` компилятор
проверит, что в момент вызова `funcA` доступен контекст `EnvA` и свойство `a` может быть использовано.
Если это не так, компилятор выдаст ошибку времени компиляции.

Требование закрывает корень: блок `with`, функция `main`, корутина, которую запустил планировщик, и `offload`.
Выше корня требование не идёт. Требования к [контекстам процесса и потока](#контексты-процесса-и-потока) корень не
закрывает. Реализация эффекта нужна, только если его методы вызывают через `%`: контракт без
методов, например `Waiting`, достаточно дать корнем, привязывать его не нужно.

Требование сохраняется в сводке функции при любой привязке эффекта, в том числе пустой: `isolated` и сообщения
об ошибках одинаковы во всех режимах сборки.

## Эффекты в типе функции

Эффекты и контексты входят в тип функции, как `throws`. Значение-функция несёт их в своём
типе:

```efen
fn load -> Int in Database

let callback = load                 // тип выведен: () -> Int in Database
let plain: () -> Int = load         // ❌ load требует Database

fn caller {
    callback()                      // caller получает `in Database`
}
```

Внутри одной сборки компилятор выводит эффекты колбэка сам. На публичной границе библиотеки тип колбэка обязан
их назвать: библиотеку собирают без вызывающего кода, и вывести требование не из чего.

```efen
public fn retry(times: Int, action: () -> Void in Writer) in Writer {
    for _ in 0 ..< times {
        action()
    }
}
```

Функция без эффекта подходит туда, где тип разрешает эффект; функция с эффектом туда, где тип его не называет, —
ошибка компиляции. Права на пути контекста в типе — [там же](#права-на-пути-контекста); эффекты ожидания колбэк
передаёт функции при вызове по [своему правилу](shared.md#эффекты-ожидания).

## Управление распространением контекста

Автоматический вывод `in` удобен, но иногда сигнатура должна образовать закрытую
границу. `isolated` запрещает неявно добавлять контексты и другие внешние эффекты.

```efen
context EnvA {
    let a: String
}
fn funcB in EnvA {
    print(%a)
}
isolated fn funcA {
    funcB() // Ошибка: для вызова пришлось бы неявно добавить `in EnvA`.
}
fn main {
    let context = EnvA(a: "Hello, World!")
    with context {
        funcA()
    }
}
```

Явно объявленный контекст остаётся доступен:

```efen
isolated fn explicitContext in EnvA {
    print(%a)
}
```

Тот же принцип применяется к исключениям и другим эффектам: они разрешены,
когда перечислены в сигнатуре или обработаны внутри границы. `isolated` не
означает `pure` и не запрещает локальные изменения.

`without ContextName` закрывает распространение требования к названному
контексту через границу блока. Он не удаляет значение из контекста. Вызовы
внутри могут использовать привязку, уже доступную в области, либо создать её
локальным `with`, но требование `in ContextName` не добавляется к сигнатуре
окружающей функции. Если внутри границы оно осталось несвязанным, ошибка
возникает на `without`, а не заражает функции выше по графу вызовов.

```efen
context EnvA {
    let a: String
}

fn funcA in EnvA {
    print(%a)
}

fn funcB {
    funcA() // Корректно: funcB наследует контекст EnvA
}

fn funcC {
    without EnvA {
        let local = makeLocalEnvA()
        with local {
            funcB() // EnvA обеспечен внутри границы.
        }
    }
}
```

Без локальной привязки то же требование останавливается ошибкой:

```efen
context EnvA {
    let a: String
}

fn funcA in EnvA {
    print(%a)
}

fn funcB {
    funcA()
}

fn main {
    without EnvA {
        funcB() // Ошибка: EnvA не связан внутри закрытой области.
    }
}
```

Семантика границы принята; слово `without` для неё остаётся кандидатом и может
быть переименовано без изменения модели.

`without` пишут и у функции: `fn onFrame without Waiting`, а также у
класса, модуля и пакета, как `in`; на функции C без тела строка модуля, пакета или класса не действует, для них —
[блок объявлений](foreign.md#блок-объявлений-c). У интерфейса и контракта `without` — требование ко всем реализациям: каждая
их функция обязана обходиться без названного эффекта, и вызывающий знает это, не видя реализации:

```efen
interface Renderer without Waiting {
    fn draw(frame: Frame)
}
```

Для эффекта, который даёт только рантайм, запрет строгий: `without` убирает его и все производные от него эффекты из области,
даже если снаружи они доступны, и внутри их не вернёт никто. Так блок захвата
мьютекса запрещает ждать (см. [Эффекты ожидания](shared.md#эффекты-ожидания)).

## Права на пути контекста

Путь в контексте, `Env.cache` или `Env.cache.entries`, для компилятора то же, что путь в параметре, `self.items`:
это источник ссылки, и сводка функции помнит право на каждый путь. У функции с телом права выводятся из тела, как
выводится `in`. Их можно написать в `in` словом перед путём:

```efen
fn lookup(key: Key) -> read<Env.cache> Value? in read Env.cache
fn store(key: Key, value: own Value) in mut Env.cache
fn report in Logger, mut Env.cache
```

- Право — `read`, `edit` или `mut`; `in Env` без права остаётся и значит «права выведены из тела». Если функция
  пишет права на путях контекста, они полный предел для этого контекста: тело не трогает других его путей и не
  берёт больше написанного. Контексты, которых `in` не называет, выводятся как обычно, кроме `isolated`.
- Результат может быть ссылкой из пути контекста: `-> read<Env.cache> Value?`. Право результата не шире права
  в `in` на этот путь. Источник результата пишется всегда, он не выводится.
- Права упорядочены как у параметров: `mut Env` шире `mut Env.cache`, тот шире `edit Env.cache`, тот шире
  `read Env.cache`. Вызов с `mut` на путь меняет его структуру: умирают ссылки из этого пути и из всего, что под
  ним. Ссылки из соседнего пути, `Env.logger`, живут. Что именно меняет вызов функции с телом, говорит её сводка
  (добавляет, перемещает или уничтожает ячейки, см.
  [Рост без перемещения](types/access-regions.md#рост-без-перемещения)): интернер, который только добавляет
  строки, старые ссылки не убивает.

```efen
let entry = lookup(key: k)!          // read<Env.cache>
log(text: "found")                   // трогает Env.logger: entry жива
store(key: k2, value: v)             // mut Env.cache: entry умирает
print(entry)                         // ошибка
```

Обычный контекст — скрытый параметр, поэтому пути разрешаются по привязке. В `override Env(cache: other) { load() }`
вызов с `mut Env.cache` меняет внутреннюю привязку; ссылки из внешней, взятые до блока, живут. Ссылка из обычного
контекста умирает в конце блока `with` или `override`, который его привязал. Вернуть ссылку из `Env.cache`
функция может, только если `Env` — её требование, то есть пришёл снаружи; контекст, привязанный внутри функции,
источником результата быть не может. Внутри `with x { }` прямое обращение к `x` — обращение к той же привязке.

В типе функции права пишутся так же: `() -> Void in mut Env.cache`. Функция с меньшими правами подходит туда,
где тип разрешает большие (`in read Env.cache` подходит под `in mut Env.cache`, а тот — под `in mut Env`);
функция с бо́льшими правами — ошибка. Источником результата в типе функции путь контекста быть может: это имя,
а не позиция параметра.

### Пачка контекстов

Функция высшего порядка, которой всё равно, какие контексты трогает колбэк, пишет пачку, как `throws ...Errors`:

```efen
fn map(items: [T], transform: (T) -> U in ...Ctx) -> [U] in ...Ctx {
    generic T: Type
    generic U: Type
    generic ...Ctx: Context

    // тело не важно для примера: вызывает transform для каждого элемента
}
```

Пачку берут `offload`, `spawn`, `group.spawn` и функции высшего порядка std. Тип колбэка без `in` и без пачки
принимает только колбэки, которые контекстов не трогают: вызываемую функцию проверили без них, и добавить права
колбэка при вызове нельзя.

## Контексты процесса и потока

Обычный контекст создаёт `with`, и живёт он до конца блока. Два других вида никто не привязывает: они есть всегда.

| Вид | Сколько экземпляров | Как код до него добирается |
|---|---|---|
| `context` | столько, сколько привязок `with` | скрытым параметром |
| `process context` | один на программу | один блок памяти |
| `thread context` | свой у каждого потока | блок текущего потока, найденный заново при каждом обращении и после каждой точки ожидания |

```efen
process context Stats {
    let hits: AtomicInt = AtomicInt(0)
}

thread context Scratch {
    var buffer: Vector<Byte> = Vector<Byte>()
}

fn handle {
    %Stats.hits.fetchAdd(1)           // первое обращение в программе: Stats создан
    %Scratch.buffer.clear()           // первое обращение в этом потоке: Scratch этого потока создан
}
```

### Объявление

- Объявляется на верхнем уровне любого модуля. Видимость — как у любого определения
  ([видимость](visibility.md)): `public process context`, поля со своей видимостью.
- Поля пишутся только в объявлении: другой модуль их не добавит. Контекст процесса или потока не расширяет другой
  через `extends` и не собирается композицией, и сам не бывает основой или частью другого контекста.
- Это не значение. Его нельзя привязать через `with`, перекрыть `override`, захватить `capture in`, скопировать,
  передать аргументом. `take` из поля, которое не опционально, вызывает ошибку. `take` из опционального поля
  контекста потока забирает значение и оставляет в поле `null`, как у поля `thread var` класса
  ([классы](classes.md#статические-методы)).
- К полю обращаются только с именем контекста, `%Stats.hits`: библиотека, которая добавила свой контекст
  процесса, не делает неоднозначным `%hits` в чужом коде.
- У каждого поля типа Efen есть начальное значение.
- Поле контекста потока принимает только тип, который соответствует `ImplicitlyDestroyable`: при завершении потока
  нет выхода, на котором программа освобождает значение. `Vector<Byte>` соответствует, и его память освобождает
  `dispose` ([освобождение структуры](disposable.md#освобождение-структуры-disposable)). Поле `var x: own T` со
  значением другого типа (`Vector<Thread>`) служит точкой доверия
  ([`ImplicitlyDestroyable`](disposable.md#implicitlydestroyable)).
- Требование к такому контексту не закрывает ни один корень (`main`, `offload`, корутина, `with` группы задач,
  вход потока): права идут по сводкам до каждого вызывающего.

Снаружи кода, которому поле не видно, путь к нему в сводке показывается и проверяется как весь контекст: публичная
функция, которая трогает закрытое `Scratch.buffer`, для другого пакета — `in mut Scratch`. Закрытый контекст потока,
из которого ни одна публичная функция не возвращает ссылку, из публичных сводок убирается совсем.

### Создание и уничтожение

Контекст создаётся лениво, при первом обращении к любому его полю: контекст потока — в каждом потоке своим флагом,
без синхронизации; контекст процесса — один раз на программу. Правило одно для программы и для библиотеки, у
которой нет `main`. Общего порядка создания нет: если начальное значение читает другой контекст, тот создаётся
тут же, внутри. К чему программа не обратилась, то не создаётся.

- Начальное значение не бросает, не ждает (`without Waiting`), не запускает потоков и не требует обычного
  контекста. Исключение, вылетевшее из него, останавливает программу с именем контекста. Поэтому обращаться к
  таким контекстам можно и из кода `nofail`: из колбэка C, из `deinit`.
- Обращение, которое может создать контекст, несёт права его начальных значений, как вызов: если начальное значение
  меняет `Log.sink`, первое обращение к контексту убивает ссылки из `Log.sink`.
- Круг (начальное значение `A` читает `B`, а `B` читает `A`) — ошибка сборки. Круг, который виден только во время
  работы (библиотека загружена на ходу), ловит флаг: тот же поток снова пришёл к контексту, который создаётся, —
  программа останавливается с именем контекста; другой поток ждёт. Круг через два потока во время работы
  зависает, как в C++ и Rust.
- Контекст процесса уничтожается после возврата из `main`, когда закончились все потоки, запущенные Efen: группа
  задач и `offload` кончаются внутри своей области, а `Thread` кончается только явным `pthread_join`
  ([внешние деструкторы](disposable.md#явный-деструктор)). Каждый контекст при первом обращении записывается в реестр
  процесса, и реестр уничтожается с конца, в обратном порядке фактического создания: контекст, который начальное
  значение другого прочитало, создан раньше и уничтожается позже.
- Контекст потока уничтожается, когда завершается поток, любой, в том числе запущенный C, в обратном порядке
  создания. Куча менеджера памяти этого потока разбирается после всех его контекстов и полей `thread var`. Контексты
  главного потока уничтожаются, когда `main` возвращает управление.
- Обращение к уничтоженному контексту останавливает программу с его именем. Так ловится поток или колбэк C, который
  читает контекст процесса после `main`: каждый вход `@abi(c)` проверяет один флаг, код Efen за это не платит.
- При необработанном исключении и выходе процесса без возврата из `main` контексты не уничтожаются.
- Динамическая библиотека с контекстом потока не выгружается. Две динамические библиотеки, в каждой из которых
  собран один пакет, получают две копии его контекста процесса.

### `static`

`static process context` и `static thread context` лежат в памяти с самого старта:

```efen
static process context Limits {
    let maxConnections: Int = 1024
    let requests: AtomicInt = AtomicInt(0)
}

static thread context Depth {
    var level: Int = 0
}
```

Все начальные значения вычисляются при сборке, как `const`; если какое-то вычислить нельзя (вызов, который
читает файл или выделяет память), это ошибка компиляции. Контекст процесса лежит в сегменте данных, контекст потока — в
сегменте потока (TLS), и каждый новый поток получает готовую копию. Флага, создания при первом обращении, начальных
значений во время работы и кругов нет. Без `static` контекст ленивый.

Поля `thread let` и `thread var` в классе — тоже переменные потока, с правилами контекста потока; поле `static let`
в классе — одно на процесс, с правилами контекста процесса ([классы](classes.md#статические-методы)).

### Контекст процесса — общая память

Его видят все потоки, включая потоки, созданные C, и потоки программы, которая загрузила динамическую библиотеку.
Поэтому поле Efen в контексте процесса — только `let`, и его тип — `shared`-тип, атомарный, `immutable T` или
`shared readonly class` ([общая память](shared.md#пометка-shared), [неизменяемость](immutability.md)). Обычный
`readonly class` в контексте процесса допустим только в программе, по доказательству FLOW всех обращений, и никогда в
библиотеке. Гонке не на чем случиться, кто бы ни выполнял код. Ссылка в такое поле
умереть не может, поэтому права на эти поля в сводках, типах функций и интерфейсах не пишутся и не выводятся:
счётчик метрик не меняет ни одной сигнатуры. `isolated` их не проверяет, как и выделение памяти.

### Ссылка из контекста потока

Корутина может уснуть на одном потоке и проснуться на другом, а пока она спит, её поток выполняет чужие корутины.
Поэтому ссылка из контекста потока и всё, что компилятор знал о его полях, умирают в каждой непрозрачной точке. Так же умирает указатель `layout`, источник которого — структура в поле контекста потока:

- вызов, который может ждать: со `Suspending` в сводке, с пометкой или без (вход в мьютекс, `await`, ввод-вывод);
- конец асинхронного блока `with`;
- шаг генератора — и у потребителя, и в теле генератора;
- вызов через значение-функцию или метод интерфейса, тип которого не называет прав на контекст потока;
- вызов функции без тела (функции C), которой передали значение-функцию.

```efen
let s = strerror(errnum: e)
await(take job)                   // может проснуться на другом потоке
print(s)                          // ошибка: s умерла в точке ожидания

print(strerror(errnum: e))        // тоже ошибка: print может ждать
print(copy strerror(errnum: e))   // можно
```

Правило одно для `let` и `var`: даже неизменяемое поле лежит в копии конкретного потока, и после переезда
корутины эта копия может быть уже уничтожена. Обращение через `%` после пробуждения само находит копию нового
потока, поэтому неизменяемое поле просто читают заново. Правило проверяется по одной функции, без корня.

Отсюда же: реализация интерфейса, которая трогает контекст потока, подходит к интерфейсу без пометок, а колбэк —
к типу без прав на контекст потока. Вызывающий всё равно теряет свои ссылки на таком вызове.

Два обращения к контексту потока из разных корутин не конфликтуют: на одном потоке код между точками ожидания
выполняется один. Тип с источником в контексте потока не бывает результатом `offload`, `spawn`, `await` и входа
потока. Корутина и тело `offload` не захватывают ссылку из контекста потока: внутри пишут `%`, снаружи — `copy`.
Замыкание, которое выполняет поток внешнего кода ([`shared layout`](shared.md#shared-layout)), проверяется как тело
`offload`: асинхронного контекста вызывающего в нём нет, ссылку из контекста потока оно не захватывает.

`without` для контекста процесса или потока запрещает обращаться к нему внутри блока и требования не закрывает.

Как этим описывают память, которую библиотека C отдаёт до следующего вызова, —
[foreign.md](foreign.md#память-которую-функция-отдаёт-до-следующего-вызова).

## Наследование контекстов

Контекст расширяет другой контекст через `extends`:

```efen
context Transaction extends Database {
    let transaction: TransactionHandle
}
```

`extends` отличает это отношение от `:` — записи основы типа — и от композиции
контекстов ниже.

## Композиционное объединение контекстов

Контексты могут объединяться без наследования с помощью композиции.
```efen
context ContextA {
    let valueA: String
}
context ContextB {
    let valueB: Int
}
context CombinedContext {
    ContextA
    ContextB
}

// физическое хранение может быть таким же плоским, но семантически
// CombinedContext сохраняет identities ContextA и ContextB.
```

Композиционный контекст можно создать так же на месте операции `with`:
```efen
context ContextA {
    let valueA: String
}
context ContextB {
    let valueB: Int
}
fn useCombinedContext in ContextA, ContextB {
    print(%valueA)
    print(%valueB)
}
fn main {
    with ContextA(valueA: "Hello"), ContextB(valueB: 42) {
        useCombinedContext()
    }
}
```

Блок `with` принимает и значения контракта `Scoped`: он
вызывает их `enter` на входе и `exit` на каждом выходе и ничего не привязывает.
Правило ниже к ним не относится: `with a.mutex, b.mutex` допустим (см.
[Мьютекс и `with`](shared.md#мьютекс-и-with)).

Одновременно нельзя активировать два значения одного номинального контекста,
а также base context вместе с его derived context. В частности, `with primary,
replica`, где оба имеют тип `Database`, и `with database, transaction`, где
`Transaction extends Database`, являются ошибками. Явный `override` временно
заменяет конкретную активную binding, а не добавляет вторую.

## Композиционное перекрытие контекстов override

Контексты могут быть перекрыты с помощью ключевого слова `override`, что позволяет изменять или дополнять свойства
существующего контекста в новом контексте. В этом случае новый контекст "наследует" все свойства базового контекста.
Он так же может переопределять свойства базового контекста без изменения самого базового контекста и свойств в нём.

```efen
context BaseContext {
    let value: String
}

fn useContext in BaseContext {
    print(%value)
}

fn main {
    
    with BaseContext(value: "Base Value") {
        useContext() // Выведет: Base Value
        
        override BaseContext(value: "Overridden Value") {
            useContext() // Выведет: Overridden Value
        }        
    }
}
```

В отличие от композиционного объединения или наследования, 
где от программиста требуется явно указать все необходимые контексты,
перекрытие позволяет изменять существующий контекст в определённой области видимости,
прямо во время выполнения.

## Эффект-интерфейс в `with`

Эффект-интерфейс привязывают значением: `with x { }` привязывает все интерфейсы, которые реализует класс `x`. Внутри блока `%Writer.write("done")` вызывает метод `x` через таблицу интерфейса.

```efen
interface Writer {
    fn write(text: String)
}

class FileWriter {
    implements Writer
    // остальные объявления не важны для примера
}

fn report in Writer {
    %Writer.write("done")
}

fn main {
    with FileWriter(path: "out.txt") {
        report()
    }
}
```

`with` — корень: блок ничего не ждёт снаружи. Если интерфейс, который он привязывает, иначе пришёл бы снаружи
(его требует сама функция, её колбэк или уже привязал внешний `with`), молча заменить его нельзя: нужен
`override`. Так замена видна в коде, а добавление нового — нет.

| Запись | Что привязывает |
|---|---|
| `with x { }` | все интерфейсы класса `x`; ни один не должен приходить снаружи |
| `with Writer = x { }` | только `Writer` |
| `override Reader, Writer = x { }` | заменяет `Reader` и `Writer`; если заменять нечего, работает как `with` |

```efen
fn audit in Writer {
    override Writer = MemoryWriter() {
        report()                    // пишет в память, а не туда, куда писал вызывающий
    }
}
```

Остальные правила:

- значение `Scoped` (файл, мьютекс) в `with` эффекты не привязывает, если их не назвали: `with Writer = file { }`;
- два значения одного `with`, которые дают один интерфейс, — ошибка;
- интерфейс без методов — тоже эффект: `with x { }` привязывает его, если класс `x` его реализует, и требование
  `in Admin` закрывает только такой `with`. Вызывать у него нечего, проверка идёт при сборке;
- контракт таким `with` не привязывается: `with Logger = x { }`, где `Logger` — контракт, — ошибка
  («привяжите контракт в конфигурации или объявите интерфейс»).

## Асинхронный контекст

Асинхронный контекст — контекст, который реализует асинхронный контракт. Только внутри него можно запустить корутину `spawn` (см.
[Замыкания](closure.md#корутина-spawn)); вне его `spawn` — ошибка компиляции.
Реализации принадлежат рантайму, а не языку: группа корутин, пул потоков,
однопоточный планировщик — библиотечные типы. Отдельного блока вроде
`parallel { }` в языке нет.

Вид контекста задаёт контракт, которому соответствует его тип:

| Контракт | Как идут корутины | Когда компилятор сверяет доступ корутины |
|---|---|---|
| `SingleThreadConcurrency` | в потоке создателя, по очереди, пока создатель стоит в точке ожидания | в точках ожидания |
| `MultiThreadConcurrency` | в нескольких потоках одновременно | на всём отрезке жизни корутины |

Соответствовать `SingleThreadConcurrency` может любой тип; компилятор не даёт
такому контексту переместить память в другой поток. Смысл
«в потоке создателя, пока он ждёт»: только он делает правило точек
ожидания верным. Для этого возобновление корутины — примитив рантайма, который
компилятор знает и разрешает только внутри слотов ожидания: метод
планировщика, который выполняет корутины посреди обычного вызова, иначе
обходил бы проверку.

Общий базовый контракт `Concurrency`, которому соответствуют оба
вида. Функция, которая запускает корутины вне своего блока
`with`, требует контекст как обычно, `in Concurrency`, и требование выводится по
коду. `in Concurrency` — требование контекста, а не эффекта-контракта: ему
соответствует тип контекста. Для кода, которому известен только `Concurrency`, компилятор применяет
правило многопоточного вида.

```efen
fn spread(values: [Int]) -> Int {
    with makeTaskGroup() {                    // рантайм: тип соответствует MultiThreadConcurrency
        let low = spawn { minimum(values) }
        let high = maximum(values)
        return high - await(take low)
    }                                         // здесь корутин группы больше нет
}
```

Блок `with` асинхронного контекста гарантирует на каждом выходе, что его корутин
больше нет:

- на обычном выходе и на `return` блок дожидается, пока все корутины закончатся;
- исключение, которое покидает тело блока, или исключение корутины, которую никто
  не ждёт, сразу отменяет все корутины контекста; блок ждёт, пока они остановятся, и исключение вылетает
  из конца блока. Если за это время бросили и другие корутины, вылетает первое исключение, а остальные
  прикрепляются к нему в `suppressed` по старшинству, как два исключения в `defer` ([throws](throws.md)):
  `AssertionError`, сбой, отмена, остальные. Исключение корутины, которую ждут, вылетает из её слота
  завершения;
- асинхронные контексты вкладываются. Исключение, которое вылетело из конца внутреннего `with`, — обычное
  исключение в коде вокруг него: его ловит `try` вокруг, а что не поймал никто, ловит внешний `with`. Так
  исключение корутины из `with` внутри вызванной функции выходит из самого вызова:

```efen
fn load -> Data {
    with makeTaskGroup() {
        let a = spawn { fetch("a") }       // бросает NetworkError
        return parse(await(take a))
    }
}

with makeTaskGroup() {
    try {
        load()
    } catch e: NetworkError {          // ловит: исключение вышло из load()
        print("нет сети")
    }
}
```

Ещё правила:

- отмена совместная: корутина замечает её в точке ожидания. Корутина, которая не
  доходит до точки ожидания, работает до конца, и блок ждёт её: ссылку, которую
  она держит, нельзя бросить;
- тело блока при отмене тоже отменяется в своей ближайшей точке ожидания;
  `spawn` в отменённый контекст бросает исключение отмены;
- при вложении `spawn` отдаёт корутину ближайшему контексту; конец вложенного
  блока — конец только его корутин; отмена внешнего контекста отменяет и
  вложенные. Если хоть один из уровней (внутренний или внешний) многопоточный,
  корутины внутреннего контекста считаются идущими одновременно со всеми корутинами
  каждого внешнего уровня;
- отмена не доставляется внутри тел `nofail`, `dispose`, `deinit` и `defer`:
  уборку отмена не обрывает.

Исключение корутины, которое вылетает из её слота завершения, известно по типу корутины: тип несёт список исключений
её корутины, как тип функции, и компилятор выводит его сам. Тип корутины — `Coroutine<F>`, где `F` — тип замыкания корутины, и
список — хвост этого типа функции: граница, вывод у `let` и скобки — как у
[типа функции](types/function-type.md):

```efen
fn dispatch(r: Request) -> Response {
    conforms RedirectHandler

    let c = spawn { route(r) }                 // c: Coroutine<() -> Response throws Redirect>
    return await(take c)                       // Redirect вылетает здесь; право проверяется у dispatch
}
```

Конец корутины — вход `CoroutineEntry` ([кто ловит всё](throws.md#входы-кто-ловит-всё)): он поглощает отмену, а остальное
кладёт в слот завершения как [`Thrown`](throws.md#thrown-исключение-любого-корня); `await` бросает это исключение
заново с типом из хвоста `F` у `Coroutine<F>`: `fn await<T>(c: own Coroutine<() -> T>) -> T` бросает то, что
бросает замыкание корутины `c`, и это выводится, как у вызова через значение функции.

Отмена — особый вид брошенного, как в True Async: свой корень `Cancellation`, а не
`Exception`, отдельный канал `SpecialThrowable`. Видов
два: операция успела пройти, но отмена подана, и операция не успела пройти.

Асинхронность прозрачная: функции не делятся на `async` и обычные. Какие функции приостанавливают корутину, компилятор знает по
эффектам ожидания: методы рантайма и модулей платформы
объявлены `in Suspending` (ждёт корутина, поток свободен) или `in Blocking` (ждёт
поток), а остальные функции получают эффект по сводкам. Контракт асинхронного
контекста объявляет, какие из них получают его корутины; в корутинах однопоточного
контекста `Blocking` — ошибка. Подробно — [Эффекты ожидания](shared.md#эффекты-ожидания).

## Реализации эффектов

Эффект-контракт — всегда статика: компилятор знает реализацию при сборке пакета, и `%Logger.log("start")` становится
прямым вызовом её метода. У методов контракта-эффекта нет `self`; реализации, которой нужно состояние, нужен
интерфейс.

Эффект-интерфейс — значение во время выполнения: вызов идёт через таблицу интерфейса, пока оптимизация не докажет,
что значение одно. Девиртуализация не меняет смысла: `with` по-прежнему привязывает значение.

## Контексты и эффекты как зависимости для модулей и пакетов

Эффекты и контексты входят в сигнатуры и записи символов как обычные
зависимости. Публичная функция экспортирует своё требование даже тогда, когда
имя зависимости скрыто слоем: внешний код может переносить соответствующую
запись контекста неявно и пользоваться публичными функциями, но не получает
права назвать или извлечь скрытую зависимость. Правила видимости имён задаёт
[`layers.md`](layers.md).

## Статическое связывание эффектов

Эффект-контракт — зависимость программы: его реализацию выбирает сборка, а функция, которая его вызывает, получает
эффект. Реализацию называет секция `provide` конфигурации, по пакетам и по режимам. Код связываний не пишет: `with` на контракт — ошибка. Пакеты, от которых зависит пакет,
перечисляет другая секция, `dependencies`: её ключи — имена пакетов, а ключи `provide` — объявления в коде.

```efen
config server {
    dependencies {
        log: path("../log")
    }

    provide {
        Logger: FileLogger
    }
}
```

Записи `provide`:

- `Logger: FileLogger` — контракт и его реализация;
- `Trace: null` — `optional contract` без реализации ([пустое связывание](#пустое-связывание)), только в программе;
- `http { Logger: MemoryLogger }` — секция пакета-зависимости: связывание только для его кода, только в программе;
- `"shop::Key" { Hashable: FastHash }` — тип и стратегия его контракта, только в программе
  ([выбор программы](strategies.md#выбор-программы)).

Контракт пишется коротким именем, если оно одно на сборку, иначе полным путём (`log::Logger`); ключи сравниваются
после разрешения имён. Режим сливается с основной секцией запись за записью, до контракта внутри секции пакета или
типа. Формы «снять связывание в режиме» нет.

### Умолчание

Реализацию по умолчанию помечают `@default` на самой реализации; программа может её переопределить записью
`provide`:

```efen
// log/lib.efen
public contract Logger {
    fn note(code: Int)
}

// log_console/lib.efen
use log

@default
public class ConsoleLogger {
    conforms log::Logger
    static fn note(code: Int) { /* тело не важно для примера */ }
}

// log_file/lib.efen
use log

public class FileLogger {
    conforms log::Logger
    static fn note(code: Int) { /* тело не важно для примера */ }
}
```

```efen
// программа без записи: работает ConsoleLogger
config server {
    dependencies {
        log: path("../log")
        log_console: path("../log_console")
    }
}

// программа с записью: работает FileLogger
config server {
    dependencies {
        log: path("../log")
        log_file: path("../log_file")
    }

    provide {
        Logger: log_file::FileLogger
    }
}
```

`@default` берётся из пакетов, которые есть в сборке: подключённый пакет даёт свою реализацию сам, контракт и его
пакет о ней не знают. Пометку ставят на тип, который `conforms` контракту, на блок `implementation` или на аспект, который реализует
контракт извне ([реализация извне](contracts.md#реализация-извне)).

Если `@default` одного контракта даёт несколько пакетов, побеждает пакет, который включает другой: его `@default`
бьёт `@default` его зависимостей, прямых и дальних.

```text
server ─→ app_logging   (@default JsonLogger)     ← побеждает
              └─→ log_console (@default ConsoleLogger)
```

Два `@default` на параллельных ветках, когда ни один из пакетов не включает другой (`server → a`, `server → b`), —
ошибка, называющая оба пакета; программа выбирает одну реализацию в `provide`.

Нет `@default` и нет записи — нет реализации: отдельной пометки «без умолчания» нет.

### Кто побеждает

Для кода пакета реализацию контракта даёт первое из списка:

1. секция этого пакета в `provide` программы;
2. `provides` слоя ([слои](layers.md#provides-x-with-y));
3. запись верхнего уровня в `provide` самого пакета; у программы это её собственный код;
4. реализация с `@default`;
5. иначе ошибка сборки: она называет контракт и код, который его вызывает, и предлагает подключить пакет с
   `@default` или указать реализацию в `provide`.

Каждый пакет собирается один раз; связь вызова с реализацией разрешает линковка программы, поэтому копий
пакета под разные связывания нет. Исключение — класс в контракте ([контракты](contracts.md#классы-в-контракте)): его
раскладку задаёт реализация, поэтому пакет, который наследует такой класс или читает его поля, собирается заново,
когда программа выбирает другую реализацию.

Стратегия устроена наоборот: собственный `provide X for T` пакета в коде побеждает запись программы, потому что
стратегия меняет, как компилируется код пакета, а зависимость разрешает линковка ([выбор
программы](strategies.md#выбор-программы)).

### `@unique`

Контракт, у которого в программе может быть только одна реализация, помечают `@unique`:

```efen
@unique
contract ErrorNumber {
    fn get -> Int
    fn set(value: Int)
}
```

Для него действуют только запись верхнего уровня `provide` программы — она связывает всю программу — и `@default`.
Секция пакета, `provides` слоя и запись библиотеки для `@unique` контракта — ошибка: иначе две библиотеки дали бы
две реализации.

Пункты рантайма объявлены в файлах `lang::`, а реализации рантайма помечены `@default`:

```efen
// рантайм
@default
@platform(os: "linux", arch: "x86_64")
implementation ProgramEntry { /* тело не важно для примера */ }

// программа заменяет вход
config server {
    provide {
        ProgramEntry: myapp::Start
    }
}
```

В тестовой сборке `Trap` даёт `@default` фреймворка тестов: фреймворк включает рантайм, поэтому его реализация
бьёт реализацию рантайма ([тесты](tests/tests.md)). У цели, где у `ProgramEntry` нет
реализации, программа запускается входом на C ([пункты рантайма](runtime/lang-roles.md#запуск-процесса)).

Аллокатор — не эффект, а поле `allocator` конфигурации программы ([конфигурация сборки](build-config.md)).

### Пустое связывание

Эффект, без которого программа может обойтись, объявляют `optional contract`:

```efen
optional contract Trace {
    fn note(code: Int)
}
```

Такой контракт можно связать с `null`: `Trace: null`. Вызов тогда пишут с `?`: `%Trace?.note(code: 1)`; без `?`
вызов — ошибка. При `null` компилятор удаляет вызов целиком, аргументы не вычисляются, как у `assert` в выпускной
сборке; если в аргументе есть побочное действие, компилятор предупреждает.

Методы `optional contract` не возвращают результат, объявлены `nothrows`, не требуют своих эффектов и принимают
параметры только для чтения: удалённый вызов не должен менять смысл программы.
