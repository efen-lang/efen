# Уничтожение объектов и освобождение ресурсов

[Документация](README.md) · [Контракты](contracts.md) · [Runtime языка Efen](runtime/README.md) · [Память](memory/README.md)

Пользовательский деструктор класса и низкоуровневый `Disposable` — разные
механизмы.

## Запись

Пользовательский деструктор класса с памятью Efen объявляется атрибутом, как
конструктор: `@destructor fn deinit`, без параметров и результата, не больше
одного в классе. Деструктор есть только у класса с `conforms Destructible`
([встроенные контракты](runtime/built-in-contracts.md#destructible)); без этой строки
`@destructor` — ошибка компиляции. `implements Disposable` строки `Destructible` не
требует. Деструкторы класса над внешним значением —
[ниже](#внешние-деструкторы). Низкоуровневый этап задаёт `Disposable` с методом `fn dispose`.

```efen
class File {
    conforms Constructible, Destructible
    implements Disposable

    var handle: Int

    @constructor
    fn init(handle: Int) -> Self {
        self.handle = handle
    }

    @destructor
    fn deinit {
        flush()
    }

    fn dispose {
        closeHandle(handle)
    }
}
```

Ни `deinit`, ни `dispose` не вызываются как обычные методы: их вызывает только
уничтожение объекта. Роли внешних деструкторов, наоборот, вызываются и как методы.

<a id="automatic-destruction"></a>

## Автоматическое уничтожение

Когда исчезает последний владелец объекта, компилятор запускает пользовательский деструктор
только внутри неявной `clean`-области. После него выполняется низкоуровневое освобождение через `Disposable`,
которое не выбрасывает исключений. У наследника этапы идут от наиболее производного класса
к базе: `deinit` и `dispose` наследника, затем `deinit` и `dispose` базы. После
всей цепочки освобождаются поля, затем память объекта. Эта последовательность не является обычным `defer`:
правила `suppressed`-исключений для `defer` не переносятся на автоматическое
уничтожение без отдельного решения.

Обычный деструктор, который может выбросить исключение, не вызывается автоматически: это явная операция
автора с обычной семантикой исключений.

## Освобождение структуры: `Disposable`

Структуры на стеке, `static` и `thread` уничтожаются в заданных точках; правило для них ещё проектируется.

У структуры нет пользовательского деструктора: `@destructor` и `conforms Destructible` у неё вызывают ошибку.
Компилятор освобождает значение структуры сам там, где его жизнь кончается: в конце области видимости, в конце
инструкции у временного значения, на выходе через исключение и при записи в слот целиком. Он строит план
освобождения по объявлению: поле обычного типа и поле со структурой уничтожаются как любое поле; элемент `own`,
который не может снова владеть элементом своего множества, освобождается так же, по своим полям. Инвариантов план не
читает.

Структуру, которую по объявлению не освободить, план не обходит: структуру с полем `anchor`, с цепочкой владения
внутри одного множества (список, граф) или с полем-областью, слоты которой могут быть не инициализированы
(`Vector`). Такая структура пишет низкоуровневый этап `Disposable`: стратегия пишет `implements Disposable` и тело
`fn dispose`. Компилятор вызывает `dispose` в тех же точках перед планом; обычным вызовом `dispose` не вызывается и
исключений не бросает.

```efen
private layout<T: Movable> {
    area Items: T
    public struct Vector {
        private var items: own Items.Area? = null {
            (value == null) == (capacity == 0) && (value == null || value.count == capacity)
        }
        private var capacity: Int = 0 { value >= 0 }
        public  var count: Int = 0 { value >= 0 && value <= capacity }
    }
}

strategy<T> for Vector<T> {
    implements Disposable

    fn dispose {
        if let old = take items {
            var i = 0
            while i < count {
                let dead = take old[i]          // значение T уничтожается в конце шага
                i += 1
            }
        }                                       // old кончается: ни один слот не инициализирован, область возвращается
        count = 0
        capacity = 0
    }
}

fn loadValues -> Vector<Int> {
    var values = Vector<Int>()
    values.append(1)
    return take values
}

print(loadValues().count)      // временный Vector освобождается в конце инструкции: dispose, затем план по полям
```

Список обходит цепочку узлов:

```efen
strategy<T> for List<T> {
    implements Disposable

    fn dispose {
        while let node = tie head {
            head = tie node.next
            let dead = node as own Nodes<T>.Item     // указателей на узел нет; в конце шага память вернётся аллокатору
        }
        count = 0
    }
}
```

Правила:

1. `dispose` структуры проверяется как функция кода `layout`: на каждом его выходе поля, которые план не обходит,
   равны `null`, и после него ни один указатель в освобождённую память не используется
   ([время жизни](memory/layout/lifetime.md#74-ничего-не-теряется)).
2. `dispose`, который может бросить исключение, вызывает ошибку объявления.
3. Структура соответствует `ImplicitlyDestroyable`, если каждое значение, которое уничтожают план и `dispose`, само
   соответствует контракту. У обобщённой коллекции это условие на её параметр: `Vector<Int>` соответствует,
   `Vector<own Jobs.Item>` нет.
4. Структура, которой нужен `dispose` и у которой его нет, не уничтожается неявно: её расходует явный код.

<a id="low-level-disposable"></a>

## Низкоуровневое освобождение: `Disposable`

`Disposable` задаёт внутренний этап освобождения ресурсов после
пользовательского деструктора. Он не выбрасывает исключений. Сам по себе
`Disposable` не означает уничтожение при выходе из лексической области:
момент автоматического уничтожения определяется последним владельцем объекта.

## Внешние деструкторы

У [класса над внешним значением](classes.md#класс-над-внешним-значением) деструктор — внешняя функция или метод с
телом. Его роль пишут атрибутом у `own fn` класса; класс, как и любой другой, пишет `conforms Destructible`:

- `@destructor` бывает у нескольких методов. Результат допустим и при неявном вызове отбрасывается. Лишние
  параметры — с умолчаниями (`value: mut Pointer? = null`, [сырая память](memory/pointer.md#память-пришедшая-из-c)).
  Каждую роль деструктора можно вызвать как метод.
- Неявно компилятор вызывает единственный безусловный деструктор без `explicit`. Условный деструктор
  (метод с `ensures taken(self) == (result == SQLITE_OK)`) неявным не бывает. Классу с внешними ролями нужен
  ровно один неявный деструктор, или все его деструкторы `explicit`.
- `@destructor fn deinit` из [записи](#запись) остаётся для классов с памятью Efen. Класс без счётчика может вместо
  него объявить `@destructor(explicit) own fn имя` с телом.

```efen
@abi(c) class sqlite3 {
    conforms Destructible

    nocontext {
        @destructor own fn sqlite3_close_v2 -> Int32                                     // неявный
        @destructor own fn sqlite3_close -> Int32  // только явный вызов
            ensures taken(self) == (result == SQLITE_OK)
    }
}
```

### Явный деструктор

`@destructor(explicit)` компилятор не вызывает на обычном выходе: его вызывает программа, иначе ошибка компиляции на
выходе с именем объекта. На пути исключения его вызывает компилятор.

```efen
@destructor(explicit) own fn pthread_join(value: mut Pointer? = null) -> Int32

(take t).pthread_join()                          // обязателен на каждом обычном пути
```

### `ImplicitlyDestroyable`

Встроенный контракт `ImplicitlyDestroyable` ([контракты](runtime/value-operations.md#контракты-копирования-и-перемещения))
разрешает компилятору уничтожить значение там, где программа этого не называет. Соответствие вычисляется, а не
пишется. Ему соответствует каждый тип, кроме:

- класса, у которого все роли деструктора `explicit`;
- класса, у которого написанный деструктор без `explicit` может бросить исключение: такой деструктор автоматически
  не вызывается ([автоматическое уничтожение](#automatic-destruction)), и программа вызывает его сама;
- структуры, память которой план освобождения не обходит (поле `anchor`, цепочка владения внутри множества,
  поле-область, слоты которой могут быть не инициализированы), если её стратегия не задала `dispose`
  ([освобождение структуры](#освобождение-структуры-disposable)), и структуры, которая уничтожает элементы
  несоответствующего типа;
- структуры, варианта и окружения замыкания с полем или захватом несоответствующего типа;
- класса с полем несоответствующего типа, у которого нет написанного деструктора без `explicit`, не бросающего
  исключений;
- коллекции и опционального типа с несоответствующим типом элемента.

Поэтому ни один деструктор такого типа не вызывается неявно на обычном пути. Значение несоответствующего типа на
каждом обычном пути расходуется: явным деструктором (`(take t).pthread_join()`), `take` в параметр, поле или
результат `own`, вызовом `(take f)()` у замыкания, операцией контейнера, которая возвращает элемент
(`removeLast() -> own T?`); или FLOW доказывает, что значения нет (`== null`). У структуры с владеющим полем
`layout` он доказывает, что каждое владеющее поле равно `null`: пустой коллекции (`count == 0`) для этого мало,
потому что её область ещё не возвращена. Иначе ошибка на выходе
с именем значения. Класс без счётчика с таким полем объявляет деструктор, который его расходует: обычный
`@destructor`, и тогда класс соответствует контракту, или `@destructor(explicit)`, который вызывает программа.
Структуру с таким полем, которую `dispose` не освобождает, целиком расходует параметр `own`, который это делает,
или публичная функция структуры вроде `drain(each:)`, после которой FLOW доказывает, что владеющих полей нет
(`== null`).

Класс с написанным деструктором, который не `explicit` и не бросает исключений, соответствует
`ImplicitlyDestroyable`, какие бы поля он ни хранил. Деструктор без `explicit`, который может бросить исключение,
оставляет класс вне контракта: значение такого класса программа расходует явным вызовом на каждом обычном пути.
Соответствие читается по объявлению класса, а не по телу деструктора, поэтому класс с полем из объектов
своего же типа (`class Node { var children: [Node] }`) отдельного правила не требует. Тело такого деструктора на
каждом пути расходует каждое поле несоответствующего типа. У поля со структурой из `layout`, которая контракту не
соответствует, оно оставляет владеющие поля равными `null` (`workers.drain(each:)`). Иначе объявление класса
вызывает ошибку ([ничего не теряется](memory/layout/lifetime.md#74-ничего-не-теряется)). `@destructor(explicit)`
остаётся у класса, который объявил его сам.

Где соответствие требуется:

- Обобщённый метод, который уничтожает элемент, не возвращая его (`removeAll`, `remove(k)`, который не возвращает
  элемент, перезапись по индексу, `truncate`), объявляет `requires T conforms ImplicitlyDestroyable`
  ([ограничения параметров](generics.md#ограничения-параметров), [коллекции](types/collections.md#методы-которые-уничтожают-элементы)).
  Метод, который возвращает элемент (`replace`, `removeLast`), требования не несёт; отброшенный результат
  несоответствующего типа — ошибка в точке вызова по правилу выше.
  Сам тип коллекции принимает любой `T`. Коллекция из `layout` с `dispose` уничтожается неявно, когда её `T`
  соответствует контракту ([освобождение структуры](#освобождение-структуры-disposable)).
- `managed`-слот (поле класса со счётчиком, элемент коллекции внутри него): у последнего освобождения нет выхода,
  на котором программа расходовала бы значение.
- Слот `thread var`: при завершении потока нет выхода, на котором программа расходовала бы значение. Запись
  `thread var x: own T` со значением несоответствующего типа служит точкой доверия
  ([кому доступно доверие](memory/system.md#кому-доступно-доверие)): компилятор не доказывает, что к завершению
  потока значение освобождено.
- Замыкание, которое захватило несоответствующее значение, само не соответствует: его вызывают на каждом обычном
  пути, и тело расходует захват. На пути отказа условного `take` замыкание остаётся у вызывающего, и правило
  действует для него.

```efen
fn runTwo(job: edit Job) {
    var ts: Vector<Thread> = []                // вектор владеет областью: неявно он не уничтожается
    var t: Thread
    guard Thread.pthread_create(self: t, attr: null, start: () -> Pointer? { job.run(); return null }) == 0 else { return }
    ts.append(take t)
    ts.removeAll()                               // ошибка: removeAll требует T: ImplicitlyDestroyable
    if let w = ts.removeLast() { (take w).pthread_join() }      // можно: элемент возвращён, программа его расходует
    ts.drain(each: (w: own Thread) -> Void { (take w).pthread_join() })
                                                 // drain отдал элементы и вернул область: владеющее поле вектора
                                                 // равно null, выход из области допустим
}

fn joinLater(t: own Thread) {
    let f = () -> Void { capture u = take t; (take u).pthread_join() }   // вид own выведен; f не ImplicitlyDestroyable
    (take f)()                                   // обязателен на каждом обычном пути
}

class Pool {                                     // класс без счётчика
    conforms Destructible
    var workers: [Thread]                // Pool не ImplicitlyDestroyable
    @destructor(explicit) own fn joinAll {
        workers.drain(each: (t: own Thread) -> Void { (take t).pthread_join() })
                                                 // элементы отданы, область возвращена: владеющее поле массива равно null
    }
}

class Registry {
    conforms ArcClass
    var worker: own Thread                       // ошибка: managed-слот требует ImplicitlyDestroyable
}
```

### Порядок и эффекты внешних деструкторов

Держатель уничтожается раньше того, что держит, и раньше объектов, от которых зависит
([`layout` в теле класса](classes.md#layout-в-теле-класса)).

Эффекты деструктора (у роли C по умолчанию `Blocking`, [блок объявлений C](foreign.md#блок-объявлений-c)) входят в
сводку каждого выхода, где он может выполниться, неявного и явного, включая путь исключения у явного. В контексте
без этого эффекта такой выход — ошибка с подсказкой `offload`; сам компилятор `offload` не вставляет.
Взаимоблокировка на пути исключения, когда поток ждёт того, что послал бы раскручиваемый код, — принятый риск
живости, как у `thread::scope` в Rust. `pthread_detach` её не исправляет: он забирает объект, только если тот не
держит ни одного слота Efen.

```efen
fn runJob(job: edit Job) throws ThreadError {
    var t: Thread
    let rc = Thread.pthread_create(self: t, attr: null, start: () -> Pointer? { job.run(); return null })
    if rc != 0 { throw ThreadError() }
    risky()                                      // при исключении компилятор вызывает pthread_join (Blocking):
                                                 // под SingleThreadScheduler ошибка с подсказкой offload
    (take t).pthread_join()
}
```

## Граница модели

Этот документ описывает действующие правила жизненного цикла. Старые формы `let
disposable`, `forget`, автоматический бросающий `dispose()` и примеры, которые
приравнивали `Disposable` к `defer`, не являются частью текущего Efen.
