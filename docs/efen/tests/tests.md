# Тесты

[Документация](../README.md) · [Словарь](../glossary.md) · [Диагностики](../diagnostic-groups.md) · [Условия](../conditions.md)

Тест — объявление языка, `assert` — инструкция языка. Компилятор читает и проверяет тесты в каждой сборке, а
запускает их фреймворк тестов. Компилятор знает только `test`, `assert`, `assert throws` и форму таблицы тестов,
которую передаёт фреймворку.

Фреймворк — один пакет из трёх частей (агент):

- **прогонщик** — библиотека на Efen, которую тестовая сборка связывает с программой, как аллокатор;
- **родительская программа** — тот же пакет фреймворка, собранный второй раз как программа в своей конфигурации, без
  режимов тестируемого пакета: она запускает рабочие процессы, ведёт журнал и выставляет код завершения;
- **плагин компилятора** ([плагины](../compile-time/plugins.md)) — определения атрибутов теста (`@group`) и своя
  секция конфигурации с сюитами ([конфигурация сборки](../build-config.md#секции-плагинов)).

В тестовой сборке фреймворк даёт и третью часть — ловушку, которая останавливает программу: она передаёт запись
об остановке родительскому процессу прогонщика. Её подставляет то же поле, без `replace` (агент).

Все части берёт из пакета одно поле конфигурации (имя открыто), одной версией, поэтому прогонщик и плагин разных
версий или разных фреймворков встретиться не могут; отдельно в `plugins` фреймворк не пишут. Поле задаётся вне
режимов: тесты, а с ними атрибуты, проверяются в каждой сборке, и плагин фреймворка нужен каждой. Глобальный файл
даёт фреймворк по умолчанию. Поле разрешено и в библиотеке, чтобы `efen test` на ней, в том числе на самом
фреймворке, брал прогонщика из её конфигурации (агент).

Форма таблицы тестов — контракт файла `lang::`, который идёт с компилятором. Плагин добавляет в неё только
атрибуты и данные сюит, через отведённые поля. Пока плагинов нет, определения атрибутов тоже лежат в этом файле
(агент).

Решено Edmond 2026-10-29 (Amber S88, amber dev/plans/S88.md): `assert` бросает исключение, которое ловит
прогонщик; `let e = assert throws E { … }`; прогонщик не часть компилятора; строки данных — `case` у теста с
параметрами; `assert` проверяется в отладочной и тестовой сборках, в выпускной — только по полю режима. Остальное —
решения агента, отмеченные «(агент)»; их проверили Мудрец и Критик.

```efen
fn add(a: Int, b: Int) -> Int {
    return a + b
}

test add "складывает два числа" {
    assert add(2, 3) == 5
    assert add(-1, 1) == 0, "сумма с нулём"
}
```

## Объявление теста

`test ИМЯ "описание" ТЕЛО`. Имя называет проверяемое объявление в области видимости: функцию, тип, метод
(`Stack.push`) или модуль.

```efen
test Stack.push "кладёт элемент наверх" {
    var stack = Stack()
    stack.push(7)

    assert stack.top() == 7
}
```

- Неизвестное имя — ошибка с подсказкой ближайшего: переименование функции ломает её
  тесты при сборке (агент).
- В устойчивое имя теста входит найденное объявление, а не его запись: его полный путь
  (`shop::cart::add`). Псевдоним импорта имя теста не меняет, перегрузки одного имени — одно имя (агент).
- Два теста с одним именем и описанием в одном модуле — ошибка (агент).
- Тест пропускает себя при выполнении броском `SkipTest(reason: "…")`; тип объявлен в файле `lang::` тестов, поэтому
  тест не зависит от фреймворка (агент).
- Тело теста ничего не возвращает. Обработка исключений в нём та же, что в функции: исключение `MustHandle` тело
  обрабатывает само, любое другое исключение, вышедшее из тела, — провал теста. Тест видит закрытые объявления
  своего модуля.
- У каждого случая теста есть устойчивое имя: модуль, имя, описание и, для строки данных, имя строки. Журнал,
  фильтры, сохранённые провалы и кэш сборки называют случай по нему (агент).

## Где лежат тесты

- В файле модуля, рядом с кодом.
- В файле `имя.test.efn` рядом с `имя.efn`: это часть того же модуля.
- В папке `tests/` модуля, в файлах, оканчивающихся на `.test.efn`, когда тестов много.

Код модуля не может называть объявление из тестового файла: такой код собирался бы только в тестовой сборке
(агент).

## Сборка

- Каждая сборка проверяет тесты своего пакета, FLOW тоже, поэтому тест, который перестал собираться, ломает и
  обычную сборку, и тесты не устаревают молча. Тесты зависимостей не проверяются и не запускаются: это делает
  `efen test` на самой зависимости (агент).
- Проверка тестов — отдельный проход без кода: весь пакет со своими тестами проверяется ещё раз в конфигурации
  режима `testing`, с его зависимостями только для тестов, `replace` и `MODE == "testing"`. Тест видит модуль таким,
  каким его собрал бы `testing`, поэтому помощник под `#if MODE == "testing"` и подменённый `replace` модуль ему
  доступны в любой сборке. Неизменённый тест сервер компилятора берёт из кэша (агент).
- `assert` в тесте, который FLOW опроверг, — заметка, а не ошибка: тест, написанный раньше кода, не мешает выпуску.
  Из опровергнутых `assert` в обычном коде ошибка — только тот, что ложный или неопределённый всегда, на каждом пути к нему; контрпример на части входов — заметка, как
  недоказанное условие ([условия](../conditions.md#обычная-сборка-и-диагностики)) (агент).
- Записывает тесты в программу только сборка режима `testing` или режима, который начинается с него через `from`;
  тогда проход проверки идёт в конфигурации этого режима. Остальные сборки отбрасывают тесты после проверки (агент).

## assert

`assert УСЛОВИЕ` и `assert УСЛОВИЕ, СООБЩЕНИЕ` — инструкции. Ложное условие бросает `AssertionError`. Сообщение —
строковый литерал, в том числе с интерполяцией `"блок ${size}"`; другое выражение — ошибка. Интерполяция
вычисляется только при провале (агент).

Каким может быть условие (агент):

- Вне тестового кода условие `assert` чистое: без записи и без бросков, как у вызовов в [условиях](../conditions.md).
  Только тогда пропуск доказанного `assert` и его отсутствие в выпускной сборке не меняют поведения программы:
  `assert q.pop() != null` — ошибка.
- Требование условий доказать, что каждая операция определена, на `assert` не переходит. Операция условия, которая не
  определена (переполнение, деление на ноль, индекс вне границ, `!` от `null`), везде, и в тестовом коде тоже, даёт
  провал этого `assert`, а не своё исключение. `assert total / count > 2` собирается, а при `count == 0`
  проваливается; недоказанная определённость — заметка. В выпускной сборке расходится только путь провала.
- Правило касается операций самого выражения условия — встроенных операций примитивов, `!` от optional любого
  типа, индексации и среза `Array` любой формы, в том числе `[T]` и уточняющих типов над ним
  ([представления](../representations.md)), и `Slice` любого источника, — а не тел вызываемых функций и замыканий:
  деление в теле замыкания `xs.all { $0 / k > 0 }` бросает своё исключение. Индексация прочих коллекций (`String`,
  `Range`) и оператор над типом с контрактом (`Money + Money`) — вызовы функций, и их исключение идёт как из вызова.
  Определённость операций условия снимает проверки только вместе с самим условием, при доказанном или проверенном
  `assert`. `requires` функции, вызванной в условии, в части, которая
  проверяема при выполнении ([условия](../conditions.md#обычная-сборка-и-диагностики)), — такое же обязательство
  определённости, как деление: при `fn ratio(a: Int, b: Int) -> Int requires b != 0` недоказанное `count != 0` в
  `assert ratio(total, count) > 2` — заметка, а нарушение — провал этого `assert` с текстом
  `не определено: requires ratio`. Требование состояния (`requires x is State`) подчиняется typestate, а часть,
  которую при выполнении не проверить (`forall k:` без `in`, `reachable`, `chained`), нечем поймать: недоказанные, они —
  ошибка. Вне тестов вызов в условии обязан быть чистым: `ratio` с `requires b != 0` чистая, её тело доказано, а
  `ratio` без `requires` делит без доказанного делителя, и `assert ratio(total, count) > 2` с ней — ошибка, хотя
  `assert total / count > 2` собирается.
- На неопределённой операции вычисление условия останавливается. Сторона без значения, а для условия без сторон
  само условие, печатается как `не определено: деление на ноль`; сторона, до которой вычисление не дошло, — как
  `не вычислено`.
- В тестовом коде, где `assert` проверяется всегда, условие — любое выражение: `assert parse(text) == expected`.
  Фактом для FLOW оно становится, только если чистое.
- Помощник с `assert` для тестов кладут в `.test.efn`: под `#if MODE == "testing"` в коде модуля он остаётся обычным
  кодом.

```efen
assert count > 0
assert user.name == "Ann", "имя после сохранения"
```

Сообщение о провале называет место, текст условия и, для сравнения, значения обеих сторон. Сторона, у типа которой
нет контракта интерполяции, печатается именем типа: `<User>` (агент).

```
add.efn:7: assert add(2, 3) == 5 failed: 6 != 5
```

- **Где проверяется.** Включает `assert` поле режима (имя открыто, кандидат — `enableAssertions` из [режимов
  компиляции](../compilation-modes.md)). По умолчанию оно включено; готовый режим `release` его выключает, режим с
  `from` наследует значение. Значит, `debug`, `testing` и `checking` проверяют `assert`, а `release` и
  `mode production from release` — нет, пока поле не включено явно (агент).
- **FLOW.** `assert` — факт для кода после него. Доказанный `assert` (истинность и определённость каждой операции условия) вне тестов не проверяется при выполнении и
  ничего не стоит. Для диагностик FLOW считает `assert` фактом в любом режиме, поэтому ошибки и заметки одинаковы во
  всех сборках. В сборке, где `assert` выброшен, остаются проверки при выполнении, которые он снял бы: вызов `f(i)` с
  `requires i >= 0` после выброшенного `assert i >= 0` проверяет условие сам (агент).
- Поэтому факт от `assert` снимает только обязательства, у которых есть проверка при выполнении: `requires` и
  `ensures` из [проверяемых при выполнении](../conditions.md#обычная-сборка-и-диагностики), границы, арифметику.
  Состояние typestate, сужение `as` по условию вида и другие обязательства, где без доказательства ошибка, `assert` не
  уточняет ни в каком режиме: `assert f is Lifecycle.Open` перед `f.close()` не заменяет `if f is Lifecycle.Open` или
  `guard` (агент).
- **В тестах.** Тестовая сборка проверяет `assert` в тестовом коде всегда, даже доказанный и даже если поле режима
  его выключает: тест проверяет скомпилированный код, а не доказательство. Тестовый код — тела тестов и файлы
  `.test.efn`, в том числе в `tests/`. Поле режима действует на остальной код, помощник под `#if MODE == "testing"`
  тоже (агент).
- **`AssertionError`** — сбой, как `OverflowError` ([исключения](../throws.md)). Он соответствует `CatchRestriction`,
  поэтому общий `catch` и `catch e: Exception` в коде под тестом его не ловят и не превращают провал в зелёный тест.
  Ловят его только `assert throws AssertionError` и прогонщик, который объявляет контракт-обработчик из файла `lang::`
  (имя открыто). Объявить этот контракт может только функция пакета, который конфигурация сборки называет
  фреймворком; в любом другом коде это ошибка сборки (агент).
- **Граница.** `AssertionError` не входит в сводку исключений функции и проходит сквозь `nothrows`, `throws only` и
  `isolated`, как любой сбой проходит `nothrows` ([исключения](../throws.md), правило 7). Только там, где раскрутка
  невозможна, — функция `nofail`, `deinit`, `dispose`, вход из C — он останавливает программу с сообщением провала,
  как `halt()`; ещё один случай остановки — в пункте «Точки броска» ниже. Сводка и ошибки компиляции поэтому одинаковы
  в любом режиме; прогонщик видит остановку случая и записывает провал (агент).
- **Условия.** На выходе по `AssertionError` `ensures` и строки с `result` не доказываются и не проверяются
  ([условия](../conditions.md#выход-по-исключению-и-halt)). Все остальные проверки выхода FLOW делает и для этого
  выхода, как для выхода любым исключением: состояние typestate на выходе и запрет бросков после необратимого шага,
  тела `defer`, код после `assert throws AssertionError`, инвариант при отпускании блокировки, условия вида на выходе
  операции `layout`. Состояние `mut`- и `own`-параметров на этом выходе выводится отдельной записью, вне сводки; для
  мест, захваченных задачей, берётся запись её тела; у вызова без известной цели и у задачи с неизвестным телом оно
  любое (агент).
- **Точки броска.** Бросить `AssertionError` может недоказанный `assert` (в тестовом коде — любой), вызов функции с
  признаком «может провалить `assert`», вызов, цель которого статически неизвестна, и любое ожидание задачи, которое
  доставляет её провал. Признак компилятор выводит транзитивно, как сводку, но отдельно от неё и одинаково в любом
  режиме, и он виден сквозь `isolated`, как выведенные состояния. У обобщённой функции при монотипизации (по умолчанию
  или `@monomorphize`) признак считается по каждой подстановке: `==` для `Int` его не даёт. Неизвестна цель только у
  значения интерфейса, при `@erase`, у эффекта-интерфейса через `with` и у значения-функции. У функции `in Concurrency` кроме
  своего признака есть признак задач, которые она отдала контексту вызывающего. Он вызов точкой броска не делает:
  конец блока задач — точка броска, если хотя бы у одной задачи, которую он ждёт, своей или отданной вызванной
  функцией, признак есть или неизвестен. Где проверка выхода для точки не проходит, компилятор не выдаёт ошибку, а
  ставит у точки обработчик, который останавливает программу, как в `nofail`: раскрутки по сломанному состоянию нет,
  новых ошибок компиляции нет, сводка не меняется. Отчёт доказательства называет такие точки, поэтому видно, почему
  `assert throws AssertionError { f.close() }` гасит процесс. Функция, у которой каждая точка броска закрыта таким
  обработчиком, признака не имеет (агент).
- Функция с признаком «может провалить `assert`» или с таким обработчиком не чистая: в условиях её звать нельзя
  (агент).
- Исключение, брошенное при построении провала (интерполяция сообщения или значения стороны), записывается в провал
  причиной, а главным остаётся `AssertionError`. В сводку функции такие исключения не входят (агент).
- **Без кучи.** Бросок `AssertionError` не выделяет память. Провал хранится в месте, своём у каждой задачи (поток без
  задач — одна задача; место выделяется вместе со стеком задачи): место и текст условия — постоянные данные, значения
  сторон и сообщение пишет [контракт интерполяции](../runtime/lang-roles.md#контракты-операторов) в постоянный буфер,
  обрезая лишнее. Поэтому `assert` работает и в слое `lang`, и в аллокаторе, и в коде, который аллокатор вызывает
  (агент).
- В месте задачи лежит один провал. Второй провал в той же задаче, пока первый не обработан (например, `assert` в
  `defer` во время раскрутки первого или в интерполяции значения стороны), останавливает программу и печатает оба.
  `AssertionError` никогда не попадает в `suppressed` и всегда становится главным; исключение, которое было в полёте,
  и исключения из `defer` во время его раскрутки записываются в место как имя типа и текст и освобождаются
  ([исключения](../throws.md), правило 8). Причин может быть несколько: список постоянного размера, лишние
  отбрасываются с пометкой (агент).
- Провал задачи, которая закончилась, ждёт в её месте, пока его не перенесут. Переносит его в место получателя, без
  кучи, любое ожидание задачи: слот завершения (`await`), `cancel()`, ожидание при выходе из блока по исключению и
  конец блока задач для задач, которых никто не ждал. Если в получателе уже летит обычное исключение, `AssertionError`
  становится главным (правило 8). Доставленный провал никогда не считается вторым: если место получателя занято, он
  дописывается туда причиной. Главный — собственный провал получателя, если он есть, иначе первый доставленный.
  Остановка по второму провалу — только для `assert`, вычисленного в той же задаче (агент).
- Место освобождают `assert throws AssertionError` и обработчик прогонщика. `assert throws AssertionError` возвращает
  копию провала постоянного размера, а не само место; её поля (место, текст условия, значения, сообщение, причины)
  задаёт файл `lang::` (агент).

## assert throws

`assert throws E БЛОК` — выражение: выполняет блок, который обязан бросить `E`, и возвращает это исключение. Без
`let` значение отбрасывается без предупреждения.

```efen
test find "называет ненайденный ключ" {
    let table = makeTable()

    let e = assert throws MissingKey {
        table.find(-1)
    }

    assert e.key == -1
}
```

Что делает исключение из блока (агент):

| Из блока вышло | Результат |
|---|---|
| `E` или его наследник, который не сбой и не `CatchRestriction` | значение выражения |
| сбой, кроме `AssertionError`, если `E` — этот сбой или его предок, который тоже сбой (`assert throws OverflowError { Int.max + 1 }`) | значение выражения |
| `AssertionError`, если `E` — ровно `AssertionError` | значение выражения |
| `AssertionError` при любом другом `E` | проходит дальше как есть: провал внутри блока остаётся провалом |
| другой сбой (`AllocationError`) | проходит дальше как есть |
| другое исключение с `CatchRestriction` (`CancellationException`) | проходит дальше как есть |
| другое исключение | `AssertionError` «ожидалось MissingKey»; имя типа и текст исключения пишутся в провал как причина, само исключение освобождается |
| ничего | `AssertionError` «ожидалось MissingKey» |

Общий предок вроде `Exception` сбоев не ловит: `assert throws Exception { assert 1 == 2 }` — провал, а не
пройденный тест.

- `return` внутри блока — ошибка. Для FLOW и для `MustHandle` блок — это `catch` для `E` (агент).
- Исключение с `CatchRestriction`, кроме `AssertionError`, можно назвать как `E` только в функции с его
  контрактом-обработчиком, как в явном `catch` (агент).
- Если `makeTable()` бросит до блока, тест упадёт, а не пройдёт: проверяется только блок.

## Тесты с параметрами

У теста могут быть параметры с типами, как у функции. Предложения `case` перед телом дают строки данных; без них
значения генерирует фреймворк.

### Строки данных

```efen
test add "складывает" (a: Int, b: Int, sum: Int)
    case (2, 3, 5)
    case (0, 0, 0)
    case "минус" (-1, 1, 0)
{
    assert add(a, b) == sum
}
```

Каждая строка — отдельный случай; провал одной не останавливает остальные:

```
ok    add "складывает" [2, 3, 5]
ok    add "складывает" [0, 0, 0]
FAIL  add "складывает" [минус]  add.efn:9: assert add(a, b) == sum failed: -2 != 0
```

`cases ВЫРАЖЕНИЕ` берёт список строк из любого выражения: константы или функции-провайдера.

```efen
fn addCases -> [(a: Int, b: Int, sum: Int)] {
    var cases = [(a: 0, b: 0, sum: 0)]

    for i in 1 ..< 100 {
        cases.append((a: i, b: -i, sum: 0))
    }

    return cases
}

test add "складывает противоположные" (a: Int, b: Int, sum: Int)
    cases addCases()
{
    assert add(a, b) == sum
}
```

- **Тип строки** — кортеж параметров теста: здесь `(a: Int, b: Int, sum: Int)`. Строка без имён полей связывается по
  порядку; строка с именами обязана назвать те же поля в том же порядке, иначе это ошибка типа. Провайдер
  `-> [(sum: Int, a: Int, b: Int)]` не подходит и не перепутает поля молча. У теста с одним параметром строка — само
  значение: `case [1, 2]`, а `cases` даёт `[[Int]]` (агент).
- **Имя строки** — её название из `case "имя"`, иначе запись её значений литералами. Номер строки в имя не входит:
  строка, вставленная в начало, не сдвигает сохранённые провалы и фильтры. Постоянная строка, у значения которой нет
  литеральной записи (объект класса), обязана иметь название. Строки провайдера без литеральной записи называются
  номером в списке провайдера (агент).
- **Одинаковые имена.** Две постоянные строки с одним именем — ошибка сборки. Провайдер, выдавший повтор, — провал
  теста до запуска его строк (агент).
- Провайдер вычисляется до строк своего теста и может иметь эффекты. Его исключение — провал этого теста, а не всего
  прогона (агент).

### Генерируемые значения

Тест с параметрами без `case` проверяет свойство на многих значениях: их придумывает фреймворк, `requires` и
[уточняющие типы](../types/refinement-types.md) говорят, какие годятся.

```efen
test reverse "двойной разворот возвращает исходный список" (list: [Int])
    requires list.count <= 100
{
    assert reverse(reverse(list)) == list
}

test divide "восстанавливает делимое" (a: Int, b: Int)
    requires b != 0 && !(a == Int.min && b == -1)
{
    assert (a / b) * b + a % b == a
}
```

- Обычный прогон короткий: сохранённые провалы, граничные значения из условий и небольшое число случайных значений с
  зерном, которое печатается в журнале. Долгий поиск — отдельный режим прогона.
- Компилятор передаёт фреймворку области значений, выведенные из условий, чтобы значения строились сразу в них, а не
  отбрасывались (агент).
- Найденный провал фреймворк уменьшает до самого короткого значения, на котором тест ещё падает, и сохраняет в файле
  рядом с тестом; следующий прогон проверяет его первым. Значение с литеральной записью хранится строкой `case`,
  значение без неё — записью выборов генератора, из которой оно строится снова, с печатью значения в комментарии
  (агент).

### `requires` теста

Тест никто из программы не вызывает, поэтому его `requires` не останавливает программу, как у функции, а решает,
какие значения годятся. Перед телом условия проверяются всегда, и итог зависит от того, откуда значение (агент):

| Откуда значение | Не подходит под `requires` |
|---|---|
| постоянная строка `case` | ошибка сборки, если условие вычисляется при компиляции; иначе — провал строки |
| строка из `cases` | провал этой строки |
| сгенерированное значение | отброшено, доля отброшенных — в журнале |
| сохранённый провал | помечен устаревшим, в тело не попадает |

`requires` теста, которое нельзя проверить при выполнении (`forall k:` без `in`, `reachable`, `chained`), — ошибка: значения,
которые под него не подходят, нечем отбросить (агент).

## Подмена зависимостей

Моков нет: зависимость — эффект ([эффекты и контексты](../context-and-effects.md)). Эффект-интерфейс тест
подменяет значением в `with`; эффект-контракт — в конфигурации сборки, секцией `effects` режима, в котором собирают
тесты. Часть рантайма, которая не эффект (`System`), подменяется в конфигурации сборки через `replace`.

```efen
test getUserProfile "сообщает об отсутствии профиля" {
    with FailingDataBase(error: DataBaseError()) {      // класс реализует интерфейс DataBase
        assert throws DataBaseError {
            getUserProfile(7)
        }
    }
}
```

## Атрибуты теста

Декоратор на `test` — атрибут теста, обычный [декоратор](../decorators.md): его определение даёт фреймворк, и его
аргументы — значения с типами, а не текст. Неизвестный декоратор — ошибка, как везде. Декоратор на `test`, который
делает что-то кроме metadata (добавляет объявления, меняет тело), — ошибка. Компилятор не знает ни одного атрибута по
имени и кладёт metadata атрибутов в таблицу тестов (агент).

```efen
@group("db", "slow")
test getUserProfile "читает профиль из базы" { … }
```

Какие атрибуты есть (группы, пропуск, повтор) и как выбираются сюиты, описывает фреймворк, а не язык: их определения
даёт плагин фреймворка, а до плагинов — файл `lang::` для тестов. До плагинов сторонний фреймворк поэтому не может
добавить свой атрибут (агент).

## Что делает компилятор, что — фреймворк

| Часть | Что делает |
|---|---|
| Компилятор | Читает `test`, `assert`, `assert throws`; проверяет тесты; строит в тестовой сборке таблицу тестов |
| Файл `lang::` с компилятором | Типы записи таблицы, областей значений, атрибутов и данных сюит, отметка «все `assert` случая доказаны», контракт прогонщика, номер версии формы |
| Фреймворк тестов | Прогонщик: запуск случаев, генерация и уменьшение значений, журнал, статусы. Плагин: атрибуты, секция с сюитами |

Нарушенное `requires` или `ensures` и `AssertionError` на границе `nofail`, `deinit`, `dispose`, входа из C или в
точке броска, где проверка выхода не прошла ([выше](#assert)), останавливают программу, как `halt()`
([условия](../conditions.md)). Остановку в процессе не поймать, поэтому фреймворк обязан запускать случаи
так, чтобы она гасила один случай, а не весь прогон: например, пулом рабочих процессов. Процесс выполняет случаи
подряд, провал `assert` его не убивает; остановка гасит один процесс, и прогонщик запускает новый со следующего
случая (агент).

`efen test` на библиотеке собирает её тесты отдельной программой, поэтому у аллокатора, std и самого фреймворка тоже есть тесты
со своими зависимостями для тестов (агент).

## Открытые вопросы

- Имена: поле конфигурации для фреймворка, типы и контракт-обработчик в `lang::`, файл сохранённых провалов, поле
  режима, которое включает `assert`.
- Как код спрашивает «режим начинается с `testing`»: в режиме `from testing` `MODE` равен его собственному имени.
- Строки данных и генерация в одном тесте.
- Строит ли таблицу после плагинов сбор помеченных объявлений плагином
  ([сбор](../compile-time/plugins.md#сбор-помеченных-объявлений)): `test` — объявление без атрибута, и сбор по виду
  объявления пока не описан.
- Генераторы значений для типов программы: из полей, метафункцией фреймворка или плагином.
