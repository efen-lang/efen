# Общая память

[Документация](README.md) · [Словарь](glossary.md) · [Асинхронный контекст](context-and-effects.md#асинхронный-контекст) · [Области доступа](types/access-regions.md#задачи-spawn)

Общая память — значение, тип которого помечен `shared`, вместе со всем, что из
него достижимо. К нему одновременно могут обращаться несколько потоков. Задачи
многопоточного контекста не могут писать в место, которое трогает другой код того
же отрезка (см. [Области доступа](types/access-regions.md#задачи-spawn)); этот
раздел описывает, как такую память всё же делить. Компилятор доказывает каждое
обращение, скрытых блокировок нет.

Решения Edmond от 2026-10-27; что решил агент, помечено. Обзор языков и алгоритмов,
на котором держатся решения, — в исследовании `shared-research-2026-10-26` проекта
(вне репозитория).

## Четыре способа

У общей ячейки четыре безопасных способа доступа:

| Способ | Когда | Цена |
|---|---|---|
| зона `sync` | несколько ячеек меняются согласованно | блокировка |
| атомарный метод | одна ячейка, одна операция | одна атомарная инструкция |
| роль | структура без блокировок на два потока | атомарные счётчики и обычный доступ к ячейкам |
| обычный доступ | компилятор доказал, что параллельного доступа нет | ничего |

Последний способ — общее правило FLOW: до запуска задач и после конца блока
`with` общая память ведёт себя как обычная.

## Карта параллельности

Компилятор видит все зоны `sync` и все запуски задач программы, поэтому строит
формальную карту того, какой код может выполняться параллельно (Edmond). Задачи
живут внутри `with`, и их запуски образуют дерево. Две задачи параллельны, если
во время работы пересекаются их блоки `with`: две функции, каждая со своим `with`,
вызванные из двух задач внешней группы, тоже параллельны (агент).

Карта всегда с запасом: задачи из цикла считаются «многими», задача внутри `if` —
возможной. Правильная программа может получить отказ, неправильная пройти не
может (агент). Карта нужна остальным правилам раздела: обычному доступу, порядку
памяти, ролям и снятию лишних блокировок.

Код, собранный отдельно, карта видит только по сводке. Поэтому решения, которым
нужен весь код программы (снять блокировку, ослабить порядок памяти, предупредить
о лишней зоне), компилятор
принимает только при окончательной сборке программы; в библиотеке остаётся
безопасный вариант (агент).

## Пометка `shared`

Структура, к которой могут обращаться несколько потоков, помечена `shared`
(Edmond):

```efen
shared struct Stats {
    var requests: Int
    var errors: Int
}
```

Форма пометки — модификатор перед `struct` или `class` (агент; Edmond допустил и
атрибут). Пометка — часть типа: компилятор знает общую память по типу, а не
выводит её из того, какие задачи что захватили (Edmond).

К полям `shared`-структуры обращаются только внутри `sync` (Edmond, 2026-10-27):
и читают, и пишут. Место целиком (присваивание всего значения, `take`) проверяется
по обычной таблице, см. [право в зоне](#право-в-зоне). Исключения:

- атомарные методы;
- роли;
- код, где карта доказала, что параллельного доступа нет: создание структуры до
  запуска задач, чтение после конца `with`.

```efen
var stats = Stats(requests: 0, errors: 0)
stats.errors = 0                          // можно: задач ещё нет

with makeTaskGroup() {
    background {
        sync stats.errors += 1            // зона
    }

    print(stats.errors)                   // ошибка: shared-поле вне sync
}

print(stats.errors)                       // можно: задачи закончились
```

Пометка `shared` говорит, какие типы могут жить в общей памяти (Edmond). Поэтому
поле `shared`-структуры — либо тоже `shared`-тип, либо простое значение (агент):

- копируемое (`Int`, `Bool`, структура из таких);
- атомарный тип (`AtomicInt`);
- переносимое (`Movable`), которое владеет всем, до чего достаёт: без слотов ARC и
  без указателей layout за пределы значения. Такое значение кладут и забирают
  целиком через `take`;
- неизменяемое.

```efen
class Config {
    var timeout: Int
}

shared struct Registry {
    var current: Config                   // ошибка: Config — класс под ARC, не shared
}
```

Ссылка на `shared class`, полученная в зоне, сама общая: поля объекта доступны
только в зоне над ним. Копия такой ссылки в другом потоке требует атомарного
счётчика ссылок, поэтому `shared class` под ARC ждёт решения о счётчике ссылок;
до тех пор многопоточная задача его не берёт (см.
[Области доступа](types/access-regions.md#задачи-spawn)).

## Зона `sync`

Зона — участок кода, где компилятор знает, что с этими объектами работает только
один поток (Edmond). Формы:

```efen
sync stats.requests += 1

let total = sync stats.requests + stats.errors

sync {
    from.balance -= amount
    to.balance += amount
}
```

`sync` без блока охватывает одну операцию до конца строки: присваивание, вызов или
выражение. Во втором примере зона охватывает всю сумму, и значение зоны —
значение выражения. Блок значения не даёт (агент).

### Правила Edmond

- объекты в заголовке не перечисляются. Компилятор сам собирает общие объекты, с
  которыми работает код зоны, включая вызванные функции по их сводкам;
- все блокировки берутся сразу при входе. Вложенная зона, в том числе спрятанная в
  методе, ничего не берёт: её объекты уже взяты внешней зоной;
- режим каждого объекта выводится из тела: только чтение — общий доступ, другие
  читатели не ждут; запись — исключительный;
- ждать в зоне можно только явным ожиданием, которое написал программист.
  Неявная точка ожидания (запись в лог, чтение файла через вложенный вызов) в зоне —
  ошибка. Форма явного ожидания открыта;
- два параметра не указывают на одну память — обычное правило FLOW. Вызов
  `transfer(acc, acc, 10)` — ошибка у вызывающего; `transfer(accounts[i],
  accounts[j], 10)` допустим, только если доказано `i != j`; для массива ссылок
  нужно ещё различие объектов (см. [порядок блокировок](#порядок-блокировок));
- перегрузки операций для общей памяти нет: блокировку компилятор не вставляет
  сам (неявное поведение тяжело поддерживать);
- если в зоне нет операций, которым зона действительно нужна, компилятор
  предупреждает (Edmond, 2026-10-27). По прочтению агента такая операция — доступ
  к общему объекту, который по карте параллельности может трогать другой поток.
  Предупреждение относится к зоне, а не к вызову: оно выдаётся, только если ни
  одно место вызова зоны не идёт параллельно. Карта нужна целиком, поэтому
  предупреждение выдаёт окончательная сборка и только для кода самой программы, не
  библиотек.

Обвязку можно один раз написать в методе типа:

```efen
fn record(stats: mut Stats, failed: Bool) {
    sync {
        stats.requests += 1

        if failed {
            stats.errors += 1
        }
    }
}

stats.record(failed: result.failed)
```

Набор блокировок зоны в тексте не виден: он следует из кода зоны и сводок
вызванных функций. Вызов метода-обвязки зоны не показывает вовсе, её показывает
сводка метода. Это цена короткого кода; среда разработки показывает набор
подсказкой (агент).

### Порядок блокировок

Блокировки берутся в одном порядке для всей программы — по идентичности объекта во
время работы, а не по месту в тексте (агент). Иначе `transfer(a, b)` в одной задаче
и `transfer(b, a)` в другой ждали бы друг друга вечно.

Различие индексов доказывает различие мест, но не объектов: два элемента массива
ссылок могут указывать на один объект. Для таких элементов нужна идентичность
объектов, а если её не доказать, параметры объявляют возможное совпадение
(`maybe<a>`, см. [Области доступа](types/access-regions.md)); зона берёт такой
объект один раз (агент).

### Право в зоне

- зона даёт объекту то право, которое нужно телу (обычно `mut`), но не больше
  права, с которым объект пришёл. У параметра `shared`-типа право (`mut`, `edit`
  или чтение) действует внутри зоны и для атомарных методов (агент);
- зона нужна для доступа к полям. Место `shared`-типа целиком — присваивание
  всего значения, `take`, копия, уничтожение — проверяется по обычной таблице
  многопоточного вида (агент);
- к полю атомарного типа в зоне обращаются только атомарными методами: другие
  задачи вызывают их без зоны (агент);
- из зоны выходит по значению то же, что может лежать в поле `shared`-структуры:
  копируемое, отданное целиком через `take` или неизменяемое. Место, полученное в
  зоне, за зону не выходит (агент).

### Конец зоны

- на конце зоны факты о защищённой памяти умирают (агент);
- инвариант layout объекта (например, `count <= capacity`) проверяется на конце
  зоны (агент);
- зона в публичной функции попадает в её сводку («входит в зону над параметром»,
  «ждёт»); смена внутренней блокировки библиотеки меняет сводку (агент).

### Чего зона не доказывает

- объект, который вызванная функция выбирает по данным (полоса таблицы по
  `hash(key)`), до входа не узнать. Это ошибка с подсказкой получить объект до
  зоны (агент);
- две зоны подряд не исключительны вместе: проверка в одной зоне и запись в другой
  безопасны для памяти, но по смыслу это гонка. Компилятор её в общем случае не
  отличит от намеренного кода; такие операции пишутся в одной зоне (агент).

### Блокировка во время работы

Зона берёт блокировку во время работы, только если карта не доказала, что объект
трогает один поток. Задачи однопоточного контекста сменяются только в точках
ожидания, поэтому зона без ожидания, чьи объекты не видят другие потоки, в таком
контексте блокировки не берёт. Однопоточного контекста для этого мало: если тот
же объект трогает многопоточная задача, блокировка нужна (агент).

## Атомики

Атомарные операции — не часть языка, а рантайм (Edmond): рантайм определяет
методы, а компилятор знает их контракт. Атомарное число — отдельный номинальный
тип с той же памятью, что у `Int`:

```efen
@align(sizeOf(Int))
type AtomicInt: Int {
    inherit +, -, +=, ==, <
}
```

- `@align` — то же выравнивание, что у структур и полей (см.
  [Выравнивание](memory/pointer.md#выравнивание-align)). Невыровненное место для
  `AtomicInt` — ошибка компиляции (Edmond);
- `inherit` перечисляет операции `Int`, которые тип получает. Это обычные,
  **неатомарные** операции (Edmond): код, где ячейкой владеет один поток, не
  платит за атомарность, а `+=` остаётся обычной записью, которую таблица уже
  проверяет;
- атомарны только методы рантайма (Edmond). Имена `load`, `store`, `fetchAdd`,
  `fetchSub`, `exchange`, `compareExchange` взяты из C++ и Rust (агент).

Обычная операция над `AtomicInt` разрешена только там, где карта доказала, что
параллельного доступа к ячейке нет:

```efen
var hits = AtomicInt(0)
hits += 10                          // можно: задач ещё нет

with makeTaskGroup() {
    background { hits.fetchAdd(1) } // атомарно

    hits += 1                       // ошибка: задача может трогать hits
}

print(hits + 1)                     // можно: задачи закончились
```

В таблице многопоточного вида атомарные методы совместимы друг с другом (агент).
Против обычного доступа `load` считается чтением, остальные методы — записью; для
них нужно право `edit` на ячейку: параметр без права записи только читает.

Контракт атомарного метода называет его смысл: чтение, запись или
«прочитать-изменить-записать» (агент). Без этого компилятор не выведет порядок
памяти. Там, где параллельного доступа нет, компилятор вправе заменить атомарный
метод обычной операцией: смысл не меняется (агент).

Общее правило `inherit` для любого `type X: T` описано в
[Алиасах типов](type-aliases.md#отличие-от-нового-type).

## Порядок памяти

Порядок памяти решает, увидит ли другой поток записи, сделанные до атомарной
операции. По умолчанию порядок в коде не пишется (Edmond):

- атомарная запись — release, атомарное чтение — acquire;
- relaxed — только если компилятор доказал, что от атомика ничего не зависит;
- seq_cst — только явно, для схемы «записал свой флаг, читаю чужой» (алгоритм
  Деккера), которую release/acquire не покрывают.

Операция «прочитать-изменить-записать» (`fetchAdd`, `fetchSub`, `exchange`,
`compareExchange`) — и чтение, и запись, поэтому по умолчанию она acq_rel
(агент). Например, последнее уменьшение счётчика ссылок должно увидеть записи
других потоков до освобождения объекта.

Доказательство relaxed идёт по парам «запись — чтение, которое может её увидеть»
по всей программе, через карту параллельности (агент). Relaxed разрешён, только
если выполнены все правила:

- запись может быть relaxed, только если ни одно чтение, которое может увидеть её
  значение, не ведёт к другому доступу к общей памяти: через условие, выход из
  цикла, адрес (`let node = top.load()`, затем `node.value`) или значение,
  которое уходит из функции;
- чтение может быть relaxed, только если ни одна запись, значение которой оно
  может увидеть, ничего не публикует: перед ней в том же потоке нет доступа к
  памяти, которую видят другие потоки. Доступ — и запись, и чтение, и
  инициализация нового объекта, который запись делает видимым;
- значение чтения, которое уходит из функции (результат, поле, аргумент),
  оставляет чтение acquire, если сводка не говорит обратного;
- всё, что не доказано, остаётся release/acquire.

Одно исключение отменяет правило о чтении: поле, которое пишет только одна роль,
она сама читает relaxed. Своё значение поток видит всегда, а передача роли другому
потоку (запуск задачи, конец `with`) уже синхронизирует (агент).

Явный seq_cst — параметр метода рантайма:
`flag.store(1, ordering: .sequentiallyConsistent)`. Он делает seq_cst все
обращения к этому атомику, а не одно: seq_cst с одной стороны схему Деккера не
спасает (агент). Ослабить порядок параметром нельзя: это противоречило бы правилу
«relaxed только с доказательством».

## Роли

Роль описывает структуру без блокировок на два потока — например, кольцевой буфер
с одним писателем и одним читателем. Роль — это [projection](types/projection.md)
общего значения (Edmond):

```efen
shared struct Ring {
    let capacity: Int { value > 0 }
    var head: AtomicInt                  // сколько забрал читатель, только растёт
    var tail: AtomicInt                  // сколько положил писатель, только растёт
    var slots: [Job?] { count == capacity }

    0 <= tail - head <= capacity
}

projection Producer for Ring {
    var tail, slots
    let head, capacity
}

projection Consumer for Ring {
    var head, slots
    let tail, capacity
}
```

Тип поля роли берётся из `Ring`: projection пишет тип только там, где его сужает
(Edmond, 2026-10-27; см. [Projection](types/projection.md#именованная-projection)).

### Роль — место в памяти кольца

Роли выдаёт функция типа `split` (имя выбрал агент). Роль — место в памяти кольца
(Edmond, 2026-10-27): кольцом владеет его переменная, роль в поле не кладётся.
Пока роли живы, само кольцо трогать нельзя; роль умирает после последнего
использования, как заём в FLOW, и тогда кольцо снова целиком у владельца.

Возврат места из функции ownership сейчас запрещает (см.
[Ownership](types/ownership.md#чем-язык-обходится-без-хранимых-ссылок)). Роль —
отдельный механизм по «правилу на будущее» оттуда: `split` компилятор знает, как
[`replace`](memory/layout-examples/README.md), и проверяет его отдельно. Он опирается на решение Edmond от 2026-10-26
о возврате места из памяти параметра, которое в Ownership ещё не записано.

Единственность роли доказуема: `split` — единственный способ её получить, а
скопировать роль нельзя. Одну роль две задачи одновременно не захватят: доступ
роли совместим только с доступом другой роли того же раздела, а одна роль в двух
задачах — две записи в одно место по обычной таблице. Роль переходит в задачу при
запуске и возвращается на конце `with`, а эти точки синхронизируют потоки.
Отдельного счётчика писателей не нужно.

```efen
var ring = Ring(capacity: 64)            // агент: конструктор заполняет slots значениями null
let (producer, consumer) = ring.split()

with makeTaskGroup() {
    background {
        for job in loadJobs() {
            var rest = push(producer, take job)

            while let back = take rest {
                rest = push(producer, take back)
            }
        }
    }

    background {
        while let job = pop(consumer) {
            run(take job)
        }
    }
}

print(ring.head.load())                  // можно: роли умерли
```

Пример упрощён: `pop` возвращает `null` и при пустом кольце, и когда писатель
закончил, поэтому читатель может выйти раньше времени, а писатель — крутиться
вечно. В рабочей версии писатель закрывает кольцо, а пустое кольцо ждут; форма
ожидания открыта.

### Методы ролей

Метод роли — обычная функция, порядок памяти выводится:

```efen
// возвращает job назад, если места нет
fn push(ring: mut Producer, job: own Job) -> own Job? {
    let t = ring.tail.load()             // relaxed: tail пишет только эта роль
    let h = ring.head.load()             // acquire: от h зависит запись в slots

    if t - h == ring.capacity {
        return take job
    }

    ring.slots[t % ring.capacity] = take job
    ring.tail.store(t + 1)               // release: до него была запись в slots
    return null
}

fn pop(ring: mut Consumer) -> own Job? {
    let h = ring.head.load()             // relaxed: head пишет только эта роль
    let t = ring.tail.load()             // acquire: от t зависит чтение slots

    if h == t {
        return null
    }

    let job = take ring.slots[h % ring.capacity]
    ring.head.store(h + 1)               // release: до него было чтение slots
    return take job
}
```

Метод получает роль с правом `mut`: запись и `take` целого `Job?` в ячейку — смена
структуры, а `edit` её не позволяет (см.
[Области доступа](types/access-regions.md)). На общее поле ролей это право
действует только по ячейкам (агент):

- можно положить в ячейку целое значение или забрать его через `take`;
- нельзя менять само поле, пока роли живы: присвоить его целиком, перевыделить,
  переставить ячейки (`append`, `removeAll`, `swap`, `sort`);
- индекс каждой ячейки должен быть доказан внутри раздела этой роли.

### Раздел общего поля

Решил агент:

- ячейка `slots` принадлежит писателю, если лежит в `[tail, head + capacity)`, и
  читателю, если в `[head, tail)`;
- устаревшее значение чужого счётчика безопасно, только если счётчик растёт;
- поэтому «только растёт» — условие поля, которое компилятор проверяет при каждой
  записи;
- передача ячейки между ролями требует release на записи счётчика и acquire на
  его чтении у другой роли. Вывод порядка памяти обязан это дать, и проверка ролей
  это сверяет;
- кроме общего поля с разделом, каждое поле пишет не больше одной роли. Две роли с
  правом записи на одно поле без раздела — ошибка в объявлении.

Синтаксиса для раздела пока нет: компилятор выводит его из условий структуры и из
того, какие счётчики пишет каждая роль. Это открыто.

## Библиотека и менеджер памяти

Структуры без блокировок, где ячейки делят больше двух потоков (очередь «много
писателей — много читателей», дек для кражи работы, стек с несколькими
забирающими), — примитивы стандартной библиотеки, доказанные один раз (агент).
Освобождение памяти, которую ещё может читать чужой поток, гарантирует менеджер
памяти, например эпохами (Edmond, 2026-10-26).

## Открыто

- форма явного ожидания в зоне, что зона делает с блокировками во время ожидания
  и как не зависнуть, если условие так и не станет истинным. Edmond хочет, чтобы
  программист явно описывал вход в зону, как в X10 (`atomic`, `when`, часы), где
  на этом строится анализ параллельности; предложение агента — условие входа
  `sync when условие { … }`;
- форма условия «только растёт» у поля и синтаксис раздела общего поля ролей;
- возврат места из функции в [Ownership](types/ownership.md) (решение Edmond от
  2026-10-26, на нём держатся роли);
- форма размера типа: здесь `sizeOf(Int)`, в [памяти рантайма](runtime/memory.md)
  `sizeOf(Node.self)`;
- доказательство связи счётчиков ролей: план [Viper](memory/viper-proof-plan.md)
  пока не включает многопоточность;
- общий объект, до которого добираются через другой общий объект
  (`acc.owner.points`): его блокировку нельзя назвать до входа в зону;
- как рантайм реализует блокировку `shared`-объекта и какой контракт это описывает;
- распознавание схемы Деккера, чтобы подсказать seq_cst;
- замороженные данные (только чтение после публикации) как отдельный вид доступа;
- факты типов-состояний у общего объекта: на конце зоны они умирают;
- как пометка `shared` у объявления соотносится со старым правом `shared` в
  типовых выражениях (`User shared read` в [Ownership](types/ownership.md#права-как-часть-типа),
  `shared write` в [Типах-состояниях](types/typestate.md)).
