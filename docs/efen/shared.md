# Общая память

[Документация](README.md) · [Словарь](glossary.md) · [Асинхронный контекст](context-and-effects.md#асинхронный-контекст) · [Области доступа](types/access-regions.md#задачи-spawn) · [Projection](types/projection.md) · [Типы-состояния](types/typestate.md)

Общая память — значение, тип которого помечен `shared`, вместе со всем, что из
него достижимо. К нему одновременно обращаются несколько потоков. Задачи
многопоточного контекста не могут писать в место, к которому обращается другой
код того же отрезка (см. [Области доступа](types/access-regions.md#задачи-spawn));
этот раздел описывает, как такую память делить.

Доступ к полям общей структуры — получение её [projection](types/projection.md)
приведением `as`. Приведение разрешено, только когда выполнены условия
projection, например «мьютекс захвачен этой задачей». Блокировка — поле с
[типом-состоянием](types/typestate.md), захват — блок `with`. Компилятор
доказывает каждое обращение; скрытых блокировок нет.

```efen
shared struct Pool {
    var mutex: Mutex
    var idle: [Connection]
    var openCount: Int
    let maxConnections: Int
}

projection PoolEditor for Pool {
    var idle, openCount
    let maxConnections
} {
    mutex is Mutex.Held
}

fn release(pool: mut Pool { mutex is Mutex.Free }, connection: own Connection) {
    with pool.mutex {                              // enter; exit на каждом выходе
        (pool as PoolEditor).idle.append(take connection)
        pool.mutex.notify()
    }
}
```

Решения Edmond от 2026-10-27; что решил агент, помечено. Раздел заменяет первую
модель того же дня с зонами `sync`: Edmond убрал `sync`, пока не доказана его
польза, а доступ построил на projection и типах-состояниях. Обзор языков и
алгоритмов, разборы критика и мудреца — в исследовании `shared-research-2026-10-26`
проекта (вне репозитория). Синтаксис, которого до этого раздела в языке не было,
собран в [списке новых форм](#новые-формы).

## Гарантии

Компилятор доказывает для программы целиком:

- **нет гонки данных.** Каждое изменяемое поле общей структуры охраняет одна
  блокировка либо оно поделено между ролями; обращение без охраны — ошибка;
- **под блокировкой задача не ждёт.** Исключения — `wait()` на той же
  блокировке, если она единственная, и вложенный `with` другой блокировки.
  Доказательство идёт через [эффекты ожидания](#эффекты-ожидания); какие
  ожидания где разрешены, объявляет рантайм, а не язык;
- **блокировки не ждут друг друга по кругу.** Порядок захвата проверяется по
  графу всей программы;
- **объявленный инвариант структуры верен** в каждой точке, где блокировка
  отпускается.

Не ловится:

- бесконечный цикл под блокировкой — это задача остановки (Edmond);
- ожидание циклом на атомике (`while !ready.load() {}`) и самодельная
  спин-блокировка: в них нет вызова, который нёс бы эффект ожидания. Для
  ожидания на атомике рантайм даёт метод с эффектом `Blocking` (агент; имя
  `spinUntil` — агент);
- логическая гонка двух блоков подряд: проверка в одном `with` и запись в другом
  безопасны для памяти, но по смыслу это гонка. Такие операции пишутся в одном
  блоке (агент).

## Пометка `shared`

Структура, к которой могут обращаться несколько потоков, помечена `shared`
(Edmond). Форма пометки — модификатор перед `struct` или `class` (агент; Edmond
допустил и атрибут). Пометка — часть типа: компилятор знает общую память по типу,
а не выводит её из того, какие задачи что захватили (Edmond).

Пометка говорит, какие типы могут жить в общей памяти, поэтому поле
`shared`-структуры — либо тоже `shared`-тип (например, `Mutex`), либо простое
значение (агент):

- копируемое (`Int`, `Bool`, структура из таких);
- атомарный тип (`AtomicInt`);
- переносимое (`Movable`), которое владеет всем, до чего достаёт: без слотов ARC и
  без указателей layout за пределы значения. Под своей охраной такое поле
  меняется на месте (`idle.append(...)`); вне охраны его кладут и забирают только
  целиком через `take`;
- неизменяемое.

```efen
class Config {
    var timeout: Int
}

shared struct Registry {
    var current: Config                   // ошибка: Config — класс под ARC, не shared
}
```

`shared class` под ARC ждёт решения о счётчике ссылок: копия ссылки в другом
потоке требует атомарного счётчика. До тех пор многопоточная задача его не берёт
(см. [Области доступа](types/access-regions.md#задачи-spawn)).

## Карта параллельности

Компилятор видит все блоки `with` асинхронного контекста и все запуски задач
программы, поэтому строит формальную карту того, какой код может выполняться
параллельно (Edmond). Задачи живут внутри таких `with`, и их запуски образуют
дерево. Две задачи параллельны, если во время работы пересекаются их блоки
`with` асинхронного контекста (агент). Карта всегда с запасом: задачи из цикла
считаются «многими», задача внутри `if` — возможной.

Где карта доказала, что параллельного доступа нет, поля общей структуры доступны
напрямую, без projection: при создании структуры до запуска задач и после конца
`with`, который дождался задач.

```efen
shared struct Stats {
    var requests: AtomicInt
}

var stats = Stats(requests: AtomicInt(0))
stats.requests += AtomicInt(1)            // можно: задач ещё нет, обычная операция

with makeTaskGroup() {
    background { stats.requests.fetchAdd(1) }

    stats.requests += AtomicInt(1)        // ошибка: задача может обращаться к requests
}

print(stats.requests)                     // можно: задачи закончились
```

Решения, которым нужен весь код программы (ослабить порядок памяти, граф порядка
блокировок), компилятор принимает при окончательной сборке программы; в
библиотеке остаётся безопасный вариант (агент).

## Доступ через projection

Чтобы прочитать или записать поля общей структуры, код получает её projection
приведением `as` (Edmond). Приведение ничего не пишет и не копирует: это другой
вид той же памяти. Условия приведения записаны отдельным блоком `{ }` после
projection — той же формой, что [условия вида](memory/pointer.md#условия-вида) в
layout (Edmond). `pool as PoolEditor` из примера выше разрешено там, где
компилятор доказал `mutex is Mutex.Held`: внутри `with pool.mutex`. Без
доказательства приведение — ошибка компиляции.

- **projection живёт, пока верно её условие** (Edmond). Когда блокировка
  отпускается — выходом из `with` или на время `wait()`, — все projection, чьё
  условие её называет, кончаются, и обращение к ним — ошибка. Для `wait()` это
  особое правило: тип-состояние мьютекса до и после вызова одно (`Held`), но
  `wait()` объявлен как отпускающий блокировку (см. [Мьютекс](#мьютекс-и-with));
- **факты о защищённых полях** (`idle.count > 0`) умирают при захвате и при
  `wait()` (Edmond). Тело `with` доказывается только из условия входа,
  [инварианта](#инвариант) и проверок, сделанных после захвата. «Проснулся и
  взял без новой проверки» — ошибка компиляции;
- **условие называет только доверенные состояния.** Состояние, открывающее доступ
  к общей памяти (`Mutex.Held`), объявляет только рантайм или стандартная
  библиотека. Пустой переход без кода пользователь может объявить только для
  состояний, которые ничего в общей памяти не открывают (Edmond);
- **без условия** обходятся projection, все поля которых объявлены `let` в самой
  структуре: неизменяемое читается без охраны (агент). Projection без условия с
  изменяемыми полями — [роль](#роли).

Несколько projection одного значения живут одновременно, если поля и разделы,
которые они пишут, не пересекаются (агент). Остальные правила `as` из layout здесь
не действуют: исходное имя (`pool`) остаётся доступным для полей вне projection,
например `pool.mutex.notify()` (агент). Projection общей структуры применяется
только через `as`; форма с аннотацией типа (`let view: PoolEditor = pool`) для неё
запрещена, чтобы проверка не обходилась (агент).

`Mutex.Held` — короткая форма `Mutex.Lock.Held`: у типа одна ось, как у
`Pointer.Zeroed` (см. [Pointer](memory/pointer.md)). Тип поля, который не
сужается, projection не повторяет (Edmond, см.
[Projection](types/projection.md#именованная-projection)).

Projection, которая пишет поля `shared`-структуры, объявляют только в модуле
этой структуры (агент): охрану поля компилятор выводит из всех таких projection
сразу, и чужой модуль не может добавить вторую.

## Мьютекс и `with`

Блокировка — поле, тип которого даёт рантайм. Захват меняет его тип-состояние
(Edmond):

```efen
contract Scoped {
    mut fn enter in Waiting
    mut fn exit nofail
}

shared struct Mutex {
    conforms Scoped
    body without Waiting

    state Lock {
        initial Free
        Held
    }

    mut fn enter state Lock.Free >> Lock.Held in Suspending(ordered)
    mut fn exit state Lock.Held >> Lock.Free nofail
    mut fn wait state Lock.Held in Suspending(releasing self)
    mut fn notify state Lock.Held
}
```

`Mutex` — `shared`-структура без ARC; её не копируют, и её адрес не меняется,
пока она жива (агент).

Блок `with` принимает два вида значений (Edmond):

- **контекст** привязывает значение: доступ через `%`, два значения одного
  контекста одновременно — ошибка (см. [Эффекты и контексты](context-and-effects.md#композиционное-объединение-контекстов));
- **значение контракта `Scoped`** вызывает `enter` на входе и `exit` на каждом
  выходе. Привязки нет, два значения одного типа допустимы. Компилятор различает
  виды по типу, и их можно смешивать в одном `with`.

Порядок на каждом выходе (агент): `enter()`; тело; `defer` тела; `exit()`;
уничтожение переменных верхнего уровня тела (см. [деструкторы](#деструкторы-под-блокировкой)).
Если `enter` бросил исключение, например отмену, блокировка не захвачена,
мьютекс остаётся `Free`, и `exit` не вызывается. `exit`
объявлен `nofail`: мьютекс отпускается и при исключении в теле, поэтому забытой
разблокировки нет. Строка `body without Waiting` говорит, что в теле блока ждать
нельзя: это правило мьютекса из рантайма, язык его не знает (см.
[Эффекты ожидания](#эффекты-ожидания)).

- **Блокировку берут только блоком `with`** (Edmond). Ручных `lock()` и
  `unlock()` нет, и блокировка не переживает функцию. Тогда набор занятых
  блокировок виден из вложенности блоков. Цена: не выразить передачу по цепочке
  («взять следующий узел, отпустить предыдущий»). Ручной захват можно добавить
  позже: тип-состояние `Held` для этого уже есть;
- **`with a.mutex, b.mutex`** берёт блокировки одной вершины графа (одного поля
  одного типа) в порядке адресов во время работы и отпускает в обратном
  (Edmond); блокировки разных вершин — в порядке записи (агент, см.
  [порядок блокировок](#порядок-блокировок)). Так `transfer(a, b)` и
  `transfer(b, a)` в двух задачах не ждут друг друга;
- **повторный захват** ловит тип-состояние: `enter` требует `Free`;
- **поле мьютекса нельзя перезаписать целиком** (`pool.mutex = Mutex()`): иначе
  охрану подменили бы на ходу (агент);
- **видимость записей.** `exit` — release, `enter` — acquire: записи под
  блокировкой видит следующая задача, захватившая её. Это контракт методов
  рантайма (агент);
- **ожидание захвата приостанавливает задачу, а не поток** (агент): `enter`
  занятого мьютекса — эффект `Suspending`. Мьютекс принадлежит задаче: после
  вложенного `enter` задача может продолжить в другом потоке.

Состояние мьютекса в параметре функции компилятор выводит и сверяет с
объявленным (см. [Вывод состояний](types/typestate.md#вывод-состояний)). Edmond
просил писать его в примерах явно; форма уточнения типа в параметре — агент:

```efen
fn acquire(pool: mut Pool { mutex is Mutex.Free }) -> own Connection {
    with pool.mutex {
        while true {
            let editor = pool as PoolEditor

            if editor.idle.count > 0 {
                return editor.idle.removeLast()
            }

            if editor.openCount < editor.maxConnections {
                editor.openCount += 1
                break
            }

            pool.mutex.wait()
        }
    }

    try {
        return connect()
    } catch e: Error {
        with pool.mutex {
            (pool as PoolEditor).openCount -= 1
            pool.mutex.notify()
        }

        throw e
    }
}
```

`editor` получают заново на каждом круге: после `wait()` прежняя projection
кончилась, а проверки `idle.count` и `openCount` повторяются после пробуждения.

### Методы общей структуры

`self` метода общей структуры — обычный параметр: к полям метод обращается
через `self as P` по тем же правилам (агент).

```efen
shared struct Pool {
    // поля из примера выше

    mut fn resetCount {                      // выведено: self.mutex приходит Free
        with mutex {
            (self as PoolEditor).openCount = 0
        }
    }
}
```

## Охрана полей

Каждое изменяемое поле общей структуры охраняет ровно одна блокировка либо оно
принадлежит одному разделу ролей (Edmond, 2026-10-27). Поле `shared`-типа
(мьютекс, атомик) охраняет себя само: к нему обращаются напрямую, его методами,
а перезаписать его целиком нельзя (агент).
Охрану компилятор выводит из условий projection: если projection пишет поле
(`var`), охрана поля — блокировка из её условия. Две projection, которые пишут
одно поле под разными блокировками, — ошибка в объявлении:

```efen
shared struct Inbox {
    var first: Mutex
    var second: Mutex
    var letters: [Letter]
}

projection FirstEditor for Inbox {
    var letters
} {
    first is Mutex.Held
}

projection SecondEditor for Inbox {
    var letters
} {
    second is Mutex.Held
}
```

```text
error: field `letters` is written under two different locks
  --> inbox.efn:13
   |  projection FirstEditor ... { first is Mutex.Held }
   |  projection SecondEditor ... { second is Mutex.Held }
   = help: guard `letters` by one lock in both projections
```

- условие, требующее обе блокировки сразу (`first is Mutex.Held && second is
  Mutex.Held`), — тоже одна охрана (агент);
- поле, которое охраняет блокировка, не может быть `var` в projection без этой
  блокировки в условии, то есть в роли; поле роли не может появиться в projection
  под блокировкой (агент);
- поле, которое пишет хоть одна projection, кроме атомарных, читается только
  под его охраной (агент);
- место общей структуры целиком — присваивание всего значения, `take`, копия,
  уничтожение — проверяется по обычной таблице многопоточного вида (агент);
- к полю атомарного типа обращаются только атомарными методами — под
  блокировкой и в роли: другие задачи вызывают их без блокировки (агент).

## Ожидание условия

Ожидание условия под мьютексом — методы рантайма (Edmond; имена `wait` и
`notify` — агент):

- `wait()` отпускает мьютекс, приостанавливает задачу и снова захватывает мьютекс
  при пробуждении. Пометка `releasing self` в его объявлении говорит
  компилятору, что на время вызова блокировка свободна: projection над ней
  кончаются, факты о защищённых полях умирают;
- `notify()` будит одну задачу, ждущую на этом мьютексе;
- `wait()` разрешён, только если задача держит ровно эту одну блокировку. С двумя
  блокировками `wait()` отдаёт одну, а вторая остаётся занятой: тот, кто должен
  разбудить, может ждать её вечно. Проверка — в [эффектах](#эффекты-ожидания);
- `wait(timeout:)` подчиняется тем же правилам (агент).

Несколько условий на одном мьютексе («не пусто», «не полно») и блокировка
«много читателей — один писатель» — типы рантайма на тех же механизмах: состояния,
условия projection и эффекты. В язык они не входят (агент).

## Эффекты ожидания

Что под блокировкой задача не ждёт, компилятор доказывает
[эффектами](context-and-effects.md), а не списком запрещённых операций (Edmond).
Сами правила — где ждать можно, а где нельзя — объявляет рантайм контрактами; язык
их не хардкодит (Edmond, 2026-10-27).

**Ждать** — значит ждать события от другой задачи, потока или устройства
неопределённо долго (агент). Выделение памяти, промах страницы и ограниченный
повтор атомарной операции ожиданием не считаются; распределитель памяти помечен
как неждущий. Вывод в терминал и в файл — ожидание.

```efen
contract Waiting: Effect {}
contract Suspending: Waiting {}           // ждёт задача-корутина, поток свободен
contract Blocking: Waiting {}             // ждёт поток целиком
```

| Эффект | Источники |
|---|---|
| `Suspending` | `await`, ожидание задачи, `enter` занятого мьютекса, `wait()`, асинхронный ввод-вывод |
| `Blocking` | синхронные системные вызовы, функции C |

Имена выбраны по обзору языков: `suspend` в Kotlin, `spawn_blocking` в Tokio,
`@Blocking` у JetBrains (выбор Edmond поручил агенту).

**Источники объявлены вручную, остальное выводится.** Методы рантайма и модулей
платформы, которые ждут, объявлены `in Suspending` или `in Blocking`; это
доверенное место, как условия `@asm`. Кто их вызвал, получает тот же эффект в
сводке, и так вверх до корня задачи (Edmond). В своём коде эффект писать не нужно
(агент).

**Блок закрывает эффект.** Форма `without` закрывает распространение требования
через блок (см. [Управление распространением контекста](context-and-effects.md#управление-распространением-контекста)).
Для эффекта, который даёт только рантайм, `without` строже (агент): он убирает
эффект и все производные от него эффекты из области, даже если снаружи они
доступны, и внутри их не вернёт никто. `without Waiting` убирает и `Suspending`,
и `Blocking`. Форма работает и для функции (Edmond):

```efen
fn onFrame() without Waiting {            // кадр игры не имеет права ждать
    draw()
}

without Waiting {
    updatePhysics()
}
```

Блок `with pool.mutex { }` — это `without Waiting` вокруг тела плюс `enter` и
`exit`: так объявлено в `Mutex` строкой `body without Waiting`.

```efen
fn handle(pool: mut Pool { mutex is Mutex.Free }) {   // in Suspending выведено
    let data = download()

    with pool.mutex {
        download()                        // ошибка
    }
}
```

```text
error: `download` may wait while `pool.mutex` is held
  --> pool.efn:5
   |  with pool.mutex {
   |      download()
   = note: `download` waits via `readSocket` (net.efn:88)
```

### Исключения: `ordered` и `releasing self`

Два ожидания под блокировкой допустимы, и рантайм объявляет их пометками у
эффекта (агент). Обе пометки снимают только запрет, который поставил
`body without Waiting` блокировки вокруг вызова. `without Waiting`, написанный
пользователем (`onFrame`), и запрет в колбэке из C остаются полными: там нельзя
ни захватить мьютекс, ни ждать на нём.

- **`in Suspending(ordered)`** у `enter`: вызов разрешён и там, где `Waiting`
  убран, если захват не замыкает цикл в [графе порядка](#порядок-блокировок).
  Так работает вложенный `with` другой блокировки;
- **`in Suspending(releasing self)`** у `wait`: вызов отпускает свою блокировку на
  время ожидания. Он разрешён, если `Waiting` есть снаружи блока `with`, который
  захватил эту блокировку, и между этим блоком и вызовом не захвачено ничего
  другого. Поэтому `with a.mutex { a.mutex.wait() }` можно, а
  `with a.mutex { with b.mutex { b.mutex.wait() } }` и
  `with a.mutex, b.mutex { b.mutex.wait() }` — нельзя.

Обе пометки входят в сводку отдельно от обычного `Suspending`. Функция
`fn g(p: mut Pool) { with p.mutex { } }` получает «захватывает `Pool.mutex`
(`ordered`)», и её можно вызвать под другой блокировкой, если граф без цикла;
функция, которая вдобавок вызывает `download()`, получает и обычный `Suspending`,
и под блокировкой её вызвать нельзя. Пометка `releasing` записывается
относительно параметра. Функция
`fn park(pool: mut Pool { mutex is Mutex.Held }) { pool.mutex.wait() }` получает
в сводке «ждёт, отпуская блокировку параметра `pool`», и правило проверяется у
вызывающего: `with p.mutex { park(p) }` можно, `with q.mutex { with p.mutex {
park(p) } }` нельзя (агент).

### Что дают корни задач

Контракт асинхронного контекста объявляет, какие эффекты получают его задачи
(Edmond; строка `gives` — агент):

```efen
class SingleThreadScheduler {
    conforms SingleThreadConcurrency
    gives Suspending
}

class ThreadPool {
    conforms MultiThreadConcurrency
    gives Suspending, Blocking
}
```

Задачи однопоточного рантайма идут в одном потоке по очереди и переключаются
только в точках ожидания. `Blocking`-вызов, например `read` из C на сокете, держит
весь поток, и все задачи стоят. Поэтому там `Blocking` — ошибка «не хватает
эффекта» (Edmond). Такой вызов выносят в отдельный поток примитивом рантайма
`offload`; задача на это время засыпает как корутина (имя — агент):

```efen
fn offload<T>(body: own () -> T in Blocking) -> T in Suspending
```

`main` получает `Suspending` и `Blocking`: обычный код вне задач, например
консольная программа без рантайма, поток блокировать может, там некого
останавливать (Edmond; для `main` — агент).

Блок `with` асинхронного контекста (агент):

- тело получает пересечение внешних эффектов и `gives`: в `main`
  `with SingleThreadScheduler() { cRead() }` — ошибка, `Blocking` там нет;
- конец блока ждёт задач, а это `Suspending`. Поэтому блок асинхронного
  контекста там, где `Waiting` убран, например под мьютексом, — ошибка;
- в `with`, где смешаны контекст и значения `Scoped`, сначала привязываются
  контексты, затем захватываются блокировки: блокировка отпускается раньше, чем
  блок ждёт задач.

**Где тела нет** (агент):

- функция C (`@abi(c)`) по умолчанию `Blocking`, если модуль платформы не
  пометил её как неждущую (`memcpy`, `strlen`, распределитель памяти). Пометка
  доверенная;
- метод контракта без пометки не ждёт. Реализация, которая ждёт, — ошибка на
  `conforms`, как для контекстов у контрактов. Поэтому `Scoped.enter` объявлен
  `in Waiting`;
- колбэк, который вызывает код C, выполняется без `Waiting`, если не объявлено
  иное;
- эффект ожидания входит в публичный интерфейс библиотеки, как `throws` и `in`:
  строка лога в библиотечной функции меняет её сводку.

**Функции в параметрах.** Для эффектов ожидания параметр функционального типа
без них в типе — исключение из фиксированной границы
[функционального типа](types/function-type.md): функция высшего порядка
(`forEach`, `map`) получает эффекты ожидания переданного замыкания в месте
вызова (агент). Поэтому `urls.forEach { download($0) }` под блокировкой —
ошибка, а без блокировки — нет. У функции, сохранённой в поле или переменной,
граница фиксирована по правилам [функционального типа](types/function-type.md).

**Задачи под блокировкой** (агент). `spawn` в области без `Waiting` — ошибка: при
исключении блок ждёт недождавшуюся задачу (см. [Q58](../../dev/language-design-questions.md#q58--решено-2026-10-26--задачи-живут-внутри-асинхронного-контекста)),
а ждать здесь нельзя. `background` не ждут, поэтому он разрешён там, где запуск
задач вообще разрешён: в коде создателя контекста и в однопоточном контексте.

### Деструкторы под блокировкой

Деструктор — такой же вызов, и его эффекты входят в сводку (Edmond, 2026-10-27).
Поэтому ожидание бывает и в строке без видимого вызова:

```efen
shared struct Cache {
    var mutex: Mutex
    var connections: [String: Connection]
}

projection CacheEditor for Cache {
    var connections
} {
    mutex is Mutex.Held
}

fn replace(cache: mut Cache { mutex is Mutex.Free }, key: String, fresh: own Connection) {
    with cache.mutex {
        let editor = cache as CacheEditor
        editor.connections[key] = take fresh   // ошибка: старое соединение уничтожается здесь
    }
}
```

У старого соединения не остаётся владельца, и его `deinit` закрывает сокет. При
TLS закрытие отправляет `close_notify` и может ждать сеть, а мьютекс всё это
время занят. То же при `connections.removeAll()`. Подсказка компилятора
предлагает вынуть значение и уничтожить его после блока или в отдельной задаче:

```efen
fn replace(cache: mut Cache { mutex is Mutex.Free }, key: String, fresh: own Connection) {
    var old: Connection?

    with cache.mutex {
        let editor = cache as CacheEditor
        old = take editor.connections[key]
        editor.connections[key] = take fresh
    }
}                                              // old уничтожается здесь, мьютекс свободен
```

Порядок (агент): у блока `with` значения `Scoped` вызов `exit` идёт раньше, чем
уничтожаются локальные переменные верхнего уровня его тела, как у асинхронного
`with` (Q58). Переменные вложенных блоков уничтожаются под блокировкой.

## Порядок блокировок

Компилятор строит граф по всей программе: ребро `X → Y`, если `Y` захватывают,
пока занят `X`. Цикл — ошибка (Edmond, 2026-10-27). Граф учитывает захваты в
вызванных функциях по их сводкам, в том числе в библиотеках; проверка идёт при
окончательной сборке (агент).

Вершина графа — поле блокировки типа (`Pool.mutex`), а не объект: объектов во
время работы компилятор не знает (агент). Поэтому:

- `with a.mutex { with b.mutex { } }`, где `a` и `b` одного типа, — ребро
  `Pool.mutex → Pool.mutex`, то есть цикл и ошибка. Две блокировки одного вида
  берут одним `with a.mutex, b.mutex`;
- в одном `with` блокировки одной вершины захватываются в порядке адресов, и
  рёбра между ними не добавляются. Блокировки разных вершин захватываются в
  порядке записи и дают рёбра в этом порядке: `with pool.mutex, inbox.first` —
  ребро `Pool.mutex → Inbox.first`, и вложенный где-то `with inbox.first { with
  pool.mutex { } }` замыкает цикл;
- каждая блокировка `with` получает рёбра к блокировкам, которые берутся внутри
  блока, и от блокировок, занятых снаружи;
- мьютекс вне поля структуры (локальная переменная, параметр) — вершина
  `Mutex`;
- мьютекс в элементе массива — вершина `Тип.поле[]`. Если `with locks[i],
  locks[j]` не доказал `i != j`, один и тот же мьютекс захватывается один раз.

## Инвариант

Общая структура может объявить инвариант (Edmond, 2026-10-27; форма — агент).
Пусть у `Pool` из примера выше есть ещё поле `busy`, а `PoolEditor` его пишет:

```efen
shared struct Pool {
    var mutex: Mutex
    var idle: [Connection]
    var busy: Int
    var openCount: Int
    let maxConnections: Int

    invariant counted {
        idle.count + busy == openCount
    }
}
```

Объявлять инвариант не обязательно. Объявленный компилятор принимает верным
после захвата и после `wait()`, а доказывает в каждой точке, где блокировка
отпускается: обычный выход из `with`, выход по исключению, `wait()`. Кроме того,
он доказывается в конце создания структуры и после каждой прямой записи там, где
карта доказала, что задач нет (агент). Внутри блока инвариант может быть временно
нарушен. Инвариант называет поля под одной блокировкой, атомарные поля разделов
ролей и поля `let` (агент).

```efen
fn release(pool: mut Pool { mutex is Mutex.Free }, connection: own Connection) {
    with pool.mutex {
        let editor = pool as PoolEditor
        editor.busy -= 1
        editor.idle.append(take connection)   // ошибка: append бросает AllocationError,
    }                                         // а busy уже уменьшен
}
```

Гонки данных здесь нет и без инварианта, но сломанное состояние, которое видят
другие задачи, — частая ошибка с мьютексами. Исправление — переставить строки или
вернуть `busy` при исключении.

## Атомики

Атомарные операции — не часть языка, а рантайм (Edmond): рантайм определяет
методы, а компилятор знает их контракт. Атомарное число — отдельный номинальный
тип с той же памятью, что у `Int`:

```efen
@align(sizeOf(Int))
type AtomicInt: Int {
    inherit +, -, +=, ==, <
}
```

- `@align` — то же выравнивание, что у структур и полей (см.
  [Выравнивание](memory/pointer.md#выравнивание-align)). Невыровненное место для
  `AtomicInt` — ошибка компиляции (Edmond);
- `inherit` перечисляет операции `Int`, которые тип получает. Это обычные,
  **неатомарные** операции (Edmond): код, где ячейкой владеет один поток, не
  платит за атомарность;
- атомарны только методы рантайма (Edmond). Имена `load`, `store`, `fetchAdd`,
  `fetchSub`, `exchange`, `compareExchange` взяты из C++ и Rust (агент).

Обычная операция над `AtomicInt` разрешена только там, где карта доказала, что
параллельного доступа к ячейке нет (см. [пример](#карта-параллельности)). В
инварианте и в границах раздела ролей атомарное поле означает его текущее
значение `Int`, без операции (агент).

В таблице многопоточного вида атомарные методы совместимы друг с другом (агент).
Против обычного доступа `load` считается чтением, остальные методы — записью; для
них нужно право `edit` на ячейку: параметр без права записи только читает.

Контракт атомарного метода называет его смысл: чтение, запись или
«прочитать-изменить-записать» (агент). Без этого компилятор не выведет порядок
памяти. Там, где параллельного доступа нет, компилятор вправе заменить атомарный
метод обычной операцией.

Общее правило `inherit` для любого `type X: T` описано в
[Алиасах типов](type-aliases.md#отличие-от-нового-type).

### Порядок памяти

Порядок памяти решает, увидит ли другой поток записи, сделанные до атомарной
операции. По умолчанию порядок в коде не пишется (Edmond):

- атомарная запись — release, атомарное чтение — acquire;
- relaxed — только если компилятор доказал, что от атомика ничего не зависит;
- seq_cst — только явно, для схемы «записал свой флаг, читаю чужой» (алгоритм
  Деккера), которую release/acquire не покрывают.

Операция «прочитать-изменить-записать» (`fetchAdd`, `fetchSub`, `exchange`,
`compareExchange`) — и чтение, и запись, поэтому по умолчанию она acq_rel
(агент). Например, последнее уменьшение счётчика ссылок должно увидеть записи
других потоков до освобождения объекта.

Доказательство relaxed идёт по парам «запись — чтение, которое может её увидеть»
по всей программе, через карту параллельности (агент). Relaxed разрешён, только
если выполнены все правила:

- запись может быть relaxed, только если ни одно чтение, которое может увидеть её
  значение, не ведёт к другому доступу к общей памяти: через условие, выход из
  цикла, адрес (`let node = top.load()`, затем `node.value`) или значение,
  которое уходит из функции;
- чтение может быть relaxed, только если ни одна запись, значение которой оно
  может увидеть, ничего не публикует: перед ней в том же потоке нет доступа к
  памяти, которую видят другие потоки;
- значение чтения, которое уходит из функции (результат, поле, аргумент),
  оставляет чтение acquire, если сводка не говорит обратного;
- всё, что не доказано, остаётся release/acquire.

Одно исключение отменяет правило о чтении: поле, которое пишет только одна роль,
она сама читает relaxed. Своё значение поток видит всегда, а передача роли другому
потоку (запуск задачи, конец `with`) уже синхронизирует (агент).

Явный seq_cst — параметр метода рантайма:
`flag.store(1, ordering: .sequentiallyConsistent)`. Он делает seq_cst все
обращения к этому атомику, а не одно: seq_cst только с одной стороны схему
Деккера не исправляет (агент). Ослабить порядок параметром нельзя.

Барьеры памяти в [API рантайма](runtime/index.md) — низкоуровневый уровень для
кода рантайма; согласовать их с выводом порядка ещё предстоит.

## Роли

Роль описывает структуру без блокировок на два потока — например, кольцевой буфер
с одним писателем и одним читателем. Роль — projection общего значения без
условия блокировки; её получают тем же приведением `as` (Edmond, 2026-10-27).

Обе роли пишут в поле `slots`, но в разные ячейки: писатель кладёт в свободные,
читатель забирает из заполненных. Раздел записан в projection диапазоном номеров
(Edmond, 2026-10-27; запись диапазона в projection — агент):

```efen
shared struct Ring {
    let capacity: Int { value > 0 }
    var head: AtomicInt                  // сколько забрал читатель
    var tail: AtomicInt                  // сколько положил писатель
    var slots: [Job?] { count == capacity }

    invariant bounded {
        head <= tail && tail <= head + capacity
    }
}

projection Producer for Ring {
    var tail, slots[tail ..< head + capacity]     // свободные ячейки
    let head, capacity
}

projection Consumer for Ring {
    var head, slots[head ..< tail]                // заполненные ячейки
    let tail, capacity
}
```

В разделе поля номер `i` из диапазона означает ячейку `slots[i % slots.count]`
(агент). Для диапазона внутри `0 ..< slots.count` это обычный индекс; здесь
номера — значения счётчиков, а `slots.count == capacity`. Компилятор доказывает,
что разделы не пересекаются, из трёх фактов (агент):

- инвариант `head <= tail <= head + capacity`;
- каждый счётчик только растёт, и пишет его только своя роль: `tail` есть в
  `var` только у `Producer`, `head` — только у `Consumer`;
- чужой счётчик может быть устаревшим, но тогда свой раздел только меньше, а не
  больше. Это довод Лэмпорта для кольца с одним писателем и одним читателем.

«Только растёт» и инвариант кольца компилятор проверяет при каждой записи
счётчика: блокировки, на отпускании которой проверялся бы инвариант, у кольца
нет (агент). Форма условия «только растёт» у поля открыта.

**Порядок памяти выводится из раздела** (Edmond). Границу раздела писателя
задаёт `tail`, поэтому запись в ячейку должна стать видна раньше нового `tail`:
увеличение `tail` — release, а читатель читает `tail` с acquire и только потом
ячейку. То же для `head` в обратную сторону.

```efen
// возвращает job, если места нет
fn push(ring: mut Producer, job: own Job) -> own Job? {
    let t = ring.tail.load()             // relaxed: tail пишет только эта роль
    let h = ring.head.load()             // acquire: от h зависит запись в slots

    if t - h == ring.capacity {
        return take job
    }

    ring.slots[t % ring.capacity] = take job
    ring.tail.store(t + 1)               // release: tail открывает ячейку читателю
    return null
}

fn pop(ring: mut Consumer) -> own Job? {
    let h = ring.head.load()             // relaxed: head пишет только эта роль
    let t = ring.tail.load()             // acquire: от t зависит чтение slots

    if h == t {
        return null
    }

    let job = take ring.slots[h % ring.capacity]
    ring.head.store(h + 1)               // release: head возвращает ячейку писателю
    return take job
}
```

Метод получает роль с правом `mut`: запись и `take` целого `Job?` в ячейку — смена
структуры, а `edit` её не позволяет (см. [Области доступа](types/access-regions.md)).
На поле с разделом это право действует только по ячейкам своего раздела (агент):
само поле нельзя присвоить целиком, перевыделить или переставить (`append`,
`removeAll`, `swap`, `sort`), пока роли живы.

### Единственность роли

Роль — право на всё время жизни задачи, которая её получила (агент по разбору
критика). Внутри одного потока выполнения второй вид с пересекающимися полями
запрещает правило `as`; между задачами единственность даёт таблица многопоточного
вида: доступ роли совместим только с доступом другой роли того же раздела, а одна
роль в двух задачах — две записи в одно место.

```efen
var ring = Ring(capacity: 64)            // конструктор заполняет slots значениями null
let writer = ring as Producer
let reader = ring as Consumer            // можно: разделы не пересекаются

with makeTaskGroup() {
    background {
        for job in loadJobs() {
            var rest = push(writer, take job)

            while let back = take rest {
                rest = push(writer, take back)
            }
        }
    }

    background {
        while let job = pop(reader) {
            run(take job)
        }
    }
}

print(ring.head.load())                  // можно: роли кончились
```

Второй `ring as Producer` при живом `writer` — ошибка; в двух задачах — тоже, даже
если в каждой задаче вид один. Роль живёт до последнего использования, как заём в
FLOW; потом кольцо снова целиком у владельца.

Пример упрощён: `pop` возвращает `null` и при пустом кольце, и когда писатель
закончил, а писатель при полном кольце повторяет попытку без паузы. В рабочей
версии писатель закрывает кольцо, а пустое и полное кольцо ждут через метод
рантайма.

## Задачи

- **Состояние блокировки в задачу не переходит** (Edmond, 2026-10-27). В вызов
  функции состояние мьютекса передаётся как есть. В задаче, захватившей
  структуру, мьютекс не захвачен ею, что бы ни делал запустивший код: `as
  PoolEditor` там — ошибка, пока задача сама не войдёт в `with`. Для проверки
  `enter` это значит `Free` с точки зрения задачи (агент);
- **`Held` принадлежит задаче**, которая захватила блокировку (агент по разбору
  критика). Переход оси блокировки в одной задаче не отменяет фактов о ней в
  другой: правило типов-состояний «переход рвёт чужие факты» для осей блокировки
  не действует. В таблице многопоточного вида `enter`, `exit`, `wait` и `notify`
  одной блокировки совместимы между задачами;
- **тело блока `with` асинхронного контекста** получает пересечение внешних
  эффектов и `gives` (агент, см. [корни задач](#что-дают-корни-задач));
- задача получает эффекты от контракта своего контекста, а не от места, где её
  запустили: `background` внутри `with mutex` может ждать (агент).

## Библиотека и менеджер памяти

Структуры без блокировок, где ячейки делят больше двух потоков (очередь «много
писателей — много читателей», дек для кражи работы, стек с несколькими
забирающими), — примитивы стандартной библиотеки, доказанные один раз (агент).
Освобождение памяти, которую ещё может читать чужой поток, гарантирует менеджер
памяти, например эпохами (Edmond, 2026-10-26).
