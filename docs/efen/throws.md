# Throws Contracts

> **Throws контракт** — система автоматического отслеживания исключений с точками ответственности,
> обеспечивающая статический контроль обработки ошибок без явного указания throws в каждой функции.

## Зачем?

В традиционных системах обработки исключений существует несколько проблем:

1. **Избыточная декларация**: Необходимость писать `throws` в каждой функции
2. **Сложность рефакторинга**: При добавлении нового исключения нужно менять все сигнатуры
3. **Неясная ответственность**: Непонятно, где именно должно обрабатываться исключение
4. **Дублирование информации**: Список исключений копируется по всей цепочке

Efen решает эти проблемы через **автоматическое распространение** и **точки ответственности**.

## Основная концепция

Функции автоматически наследуют все исключения от вызываемых функций:

```efen
class DatabaseError: Exception { }
class ValidationError: Exception { }

fn queryDatabase {
    throw DatabaseError("Connection failed")
}

fn validateData(data: String) {
    throw ValidationError("Empty data")
}

fn processData(data: String) {
    // Список throws выводится автоматически.
    validateData(data)
    queryDatabase()
    // processData автоматически может бросить: ValidationError, DatabaseError
}
```

## Иерархия

Бросить можно только значение, которое соблюдает контракт `Throwable`. Его соблюдают четыре класса-корня из файлов
`lang::` ([что компилятор берёт у рантайма](runtime/lang-roles.md)), `AssertionError` тоже: прогонщик тестов его
не объявляет, а только получает право его ловить. Свой класс программы наследует один из корней; своего корня у
программы нет: класс-исключение без предка вне `lang::` — ошибка компиляции (Edmond, 2026-10-31, пересмотр
утреннего решения о своих корнях). Поэтому `nothrows` держит ровно `Exception` и его наследников и выпускает три
остальных корня.

```efen
contract Throwable {
    fn reason() -> Reason nofail
    fn stackTrace(limit: Int = 64, frames: TraceFrames = .all) -> Trace    // трасса стека ниже
    fn throwTrace(limit: Int = 64, frames: TraceFrames = .all) -> Trace
}

open enum Reason {
    program          // баг: код неверен
    environment      // код верен, мир не дал: память, диск, сеть
    user             // неверный ввод: текст можно показать пользователю
    cancellation     // никто не виноват: задачу отменили
    unknown          // класс не назвал причину
}
```

`Reason` открыт: программа добавляет свои причины расширением ([enum](types/enum.md#расширение)). `match` по
`reason()` пишет `_` или `@extended _`:

```efen
enum StorageReason: Reason {
    quota
}

class QuotaError: Exception {
    fn reason() -> Reason nofail {
        return StorageReason.quota
    }
}
```

```text
Throwable                      контракт: reason(), трассы
├─ Exception                   ошибки, которые обрабатывает код: нет файла, неверный ввод, свои
├─ Fault                       сбой: код в месте броска его не исправит
│  ├─ OverflowError            .program
│  ├─ DivisionByZeroError      .program
│  ├─ NullUnwrapError          .program      x! на null
│  ├─ BoundsError              .program      индекс или диапазон вне коллекции
│  ├─ AllocationError          .environment
│  └─ StackExhaustedError      .environment
├─ Cancellation                .cancellation  отмена задачи
└─ AssertionError              .program      провал assert
```

- **Корни не наследуют друг друга.** `Fault`, `Cancellation` и `AssertionError` — не исключения в смысле `Exception`:
  правила для ошибок (сводка, `nothrows`, общий `catch`) к ним применяются только там, где сказано явно.
- **Кто виноват, говорит `reason()`, а не место в дереве.** Конкретные классы строит программист. Класс без полей
  возвращает постоянное значение; класс с полем может ответить по месту броска:

  ```efen
  class ParseError: Exception {
      var source: Reason                      // поле формы → .user, свой файл → .program
      fn reason() -> Reason nofail {
          return source
      }
  }
  ```

- **`catch` ловит то, что в нём названо, и его потомков.** Общий `catch` — то же, что `catch e: Exception`; сбой
  ловит только `catch e: Fault` или `catch` его подкласса. `catch e: Throwable` в программе — ошибка компиляции: всё
  брошенное ловит только рантайм (обработчик непойманных и контекст задач).
- **`Throwable` во время выполнения.** Контракт существует только при компиляции, но параметр типа `Throwable`
  (обработчик непойманных) принимает значение любого брошенного класса. Программа собирается целиком, поэтому
  классы, которые соблюдают `Throwable`, известны все; вызов `thrown.reason()` компилятор строит сам: выбор по
  классу значения или адрес реализации в константе класса. Только для `Throwable`; общее правило для любого
  контракта ждёт отдельного решения (Edmond, 2026-10-31; amber PRINCIPLES P7.9).
- **Непроверенный индекс бросает `BoundsError`.** Индекс или диапазон, который FLOW не доказал, проверяется во время
  выполнения, и выход за границы — сбой, как переполнение, а не остановка программы.

Решение Edmond от 2026-10-31.

- **Причина по умолчанию.** Класс, который не объявил `reason()`, берёт его у предка; корни `Exception` и `Fault`
  возвращают `.unknown`. Сбой возвращает любую причину, кроме `.cancellation` (Edmond, 2026-10-31).
- **Имена** `NullUnwrapError`, `UncaughtHandler.handle` и `TraceFrames` выбрал агент (Edmond 2026-10-31: «имена решай
  сам»).

## Синтаксис

### Без throws (автоматическое наследование)

```efen
fn process {
    operation()  // Наследует все исключения
}
```

### nothrows (точка ответственности)

```efen
fn handler nothrows {
    try {
        process()
    } catch e: Exception {
        logError(e)
    }
}
```

### nofail (системная точка ответственности)

Потомок класса `Fault` — **сбой**: отказ машины или проверяемой операции, который
код бизнес-уровня не может предотвратить в месте, где он случился. Сбои, которые
бросает сам компилятор, объявлены в файлах `lang::`
([что компилятор берёт у рантайма](runtime/lang-roles.md)): `AllocationError`,
`OverflowError`, `DivisionByZeroError`, `NullUnwrapError`, `BoundsError`.
Свой сбой программа объявляет подклассом:

```efen
class CorruptedIndex: Fault { }
```

`nothrows` запрещает все исключения, кроме сбоев: сбой проходит сквозь функцию
и остаётся в её сводке. `nofail` запрещает всё, сбои тоже. Коротко: из
`nothrows` не выходят ошибки, из `nofail` не выходит ничего (кроме остановки по `AssertionError`, правило 7).

```efen
fn handleRequest(req: Request) -> Response nothrows {
    try {
        return render(load(req.id))
    } catch e: NotFound {
        return Response.notFound()
    }
    // AllocationError и OverflowError могут выйти: это сбои
}

fn release(block: Pointer, size: Int) nofail {
    try {
        used = used - size
    } catch e: OverflowError {
        corrupted = true
    }
    // ничего не выходит
}
```

`nofail` пишут в системном коде: аллокатор, рантайм, деструкторы. `deinit` и
`dispose` являются `nofail` без объявления. Функция, которую вызывает код на C,
обязана быть `nofail`: иначе ошибка компиляции.

Правила:

1. `nofail` строже `nothrows`: реализация `nofail` может заменить объявление
   `nothrows`, обратное запрещено.
2. `throws only E` пропускает сбои, как `nothrows`. Если список называет сбой,
   он строг и для сбоев: `throws only AllocationError` не выпускает
   `OverflowError`.
3. Сбой, `Cancellation` и `AssertionError` не могут быть `Expected` и не могут быть `MustHandle` (для `Cancellation` и
   `AssertionError` — агент).
4. Исчерпание стека тоже сбой, но `nofail` от него не защищает: защитная
   страница срабатывает на любом вызове.
5. Сбой, брошенный в `defer`, пока функцию покидает обычное исключение, не
   уходит в `suppressed`: главным становится сбой, обычное исключение
   прикрепляется к нему.
6. Общий `catch` и `catch e: Exception` сбои не ловят: `Fault` не потомок `Exception`. Сбой ловит только `catch`,
   который называет `Fault` или его подкласс (Edmond, 2026-10-31).
7. `AssertionError` ([тесты](tests/tests.md)) не входит в сводку исключений функции и проходит сквозь
   `nothrows`, `throws only` и `isolated`: `assert` выбрасывается в выпускной сборке, и сводка не должна зависеть
   от режима. Там, где раскрутка невозможна (`nofail`, `deinit`, `dispose`, вход из C), он останавливает
   программу, как `halt()`. Это единственное, что выходит за обещание «из `nofail` не выходит ничего».
   Остановка бывает и там, где проверка выхода по `AssertionError` не проходит
   ([тесты](tests/tests.md#assert)) (агент, S88).
8. `AssertionError` никогда не попадает в `suppressed` и всегда становится главным, над обычным исключением и
   над сбоем; правило 5 к нему не относится. Исключение, которое было в полёте, и любое исключение из `defer`
   во время его раскрутки записываются в провал как имя типа и текст, а сами освобождаются. Провал хранится
   в месте своей задачи, без кучи ([тесты](tests/tests.md#assert)) (агент, S88).

Решение Edmond от 2026-10-23; сбой как класс-корень и правило 6 — 2026-10-31. Право любого
модуля объявлять свои сбои пока принято по умолчанию и ждёт его подтверждения.

### throws (добавление исключения)

```efen
fn processWithExtra throws CustomError {
    operation()          // Наследует исключения
    throw CustomError()  // Добавляет своё
}
```

Generic-функция может переносить точный pack исключений callback без сведения к
общему базовому типу:

```efen
fn map(items: [T], transform: (T) -> U throws ...Errors) -> [U] throws ...Errors {
    generic T: Type
    generic U: Type
    generic ...Errors: Type
    where ...Errors: Throwable

    // ...
}
```

`Errors` является compile-time массивом типов, совместимых с `Exception`. При
инстанциации pack связывается с опубликованным итоговым `throws` переданной
функции и раскрывается в `throws` функции `map`. Если callable прошёл через тип,
который не сохранил его точное итоговое множество исключений, вывести `Errors`
из такого значения нельзя: требуется явный аргумент либо более точная
сигнатура callable.

### throws only (ограничение исключений)

```efen
fn limitExceptions throws only NetworkError {
    try {
        operation()  // Все исключения должны быть обработаны
    } catch e: Exception {
        throw NetworkError(cause: e)
    }
}
```

## Точки ответственности

> **Точка ответственности** — функция, которая не может выбросить исключения (или ограничивает их).

Три вида точек ответственности:
1. **Полный запрет** (`nofail`) — функция не может бросить ничего, сбои тоже (`AssertionError` останавливает программу, правило 7)
2. **Запрет ошибок** (`nothrows`) — функция не может бросить исключения, кроме сбоев
3. **Ограничение** (`throws only`) — функция может бросить только указанные исключения и сбои

## Responsibility зоны

```efen
responsibility DatabaseLayer handles DatabaseError {
    
    fn query {
        throw QueryError()  // Свободно внутри зоны
    }
    
    // На границе зоны - точка ответственности
    fn publicAPI nothrows {
        try {
            query()
        } catch e: DatabaseError {
            logError(e)
        }
    }
}
```

`responsibility X handles E` и `region handles E` решают одну задачу на разных
масштабах: зона — это объявление, границей которого служат её функции с
`nothrows`, а регион — блок, который проверяется на каждом выходе из него.

## Сравнение режимов

| Режим               | Точка ответственности | Наследование | Добавление | Обработка требуется |
|---------------------|-----------------------|--------------|------------|---------------------|
| (без объявления)    | ❌                     | ✅ Все        | ❌          | ❌                   |
| `throws E`          | ❌                     | ✅ Все        | ✅ E        | ❌                   |
| `throws only E`     | ✅                     | ❌            | ✅ E        | ✅ Все кроме E и сбоев |
| `nothrows`          | ✅                     | ❌            | ❌          | ✅ Все кроме сбоев   |
| `nofail`            | ✅                     | ❌            | ❌          | ✅ Все (кроме `AssertionError`, правило 7) |

## Управление распространением

### isolated функция

```efen
isolated fn load throws IOError {
    readFile() // Допустимо: IOError объявлен явно.
}
```

`isolated` запрещает не сами исключения, а их неявное добавление к контракту.
Каждое исключение должно быть перечислено в `throws` либо обработано внутри
функции, сбой тоже: вызывающий читает только объявление `isolated`. Вызов,
который потребовал бы расширить `throws`, является ошибкой.

`isolated` закрывает только эффекты. Состояния параметров, изменение структуры
памяти и источники ссылок компилятор выводит из тела `isolated` функции так же,
как из любой другой, и вызывающий их видит:

```efen
isolated fn prepare(file: mut File) { file.open() }   // выведено: file Closed >> Open

fn use(file: mut File) {
    prepare(file)
    file.read(4)   // допустимо: после prepare file в состоянии Open
}
```

### region nothrows

Блок `without throws` из языка убран; его место занял регион `nothrows`
([`code-regions.md`](code-regions.md)):

```efen
fn process {
    validate()  // ValidationError

    region nothrows {
        try {
            saveData()  // DatabaseError - обработан здесь
        } catch e: DatabaseError {
            logError(e)
        }
    }

    notify()  // NotificationError
}
// process может бросить: ValidationError, NotificationError (но НЕ DatabaseError)
```

Выход по `return` и `break` проверяется так же, как конец блока: до него не
должно быть непойманного выброса.

## Контракты на обработку исключений

Contract может уточнять другой contract через `:`:

```efen
contract ErrorHandler : CatchRules {
    required catch DatabaseError
}
```

`CatchRules` разрешает требования `required catch`.

Функция соответствует контракту через объявление `conforms` в теле:

```efen
fn dataOperation {
    conforms ErrorHandler

    try {
        queryDatabase()
    } catch e: DatabaseError {
        // Обработка DatabaseError обязательна
        logError(e)
    }
}
```

### Ограничение обработки исключений

Обычно любая функция может обрабатывать исключения, которые она **не добавляет**.
Однако, иногда требуется создать исключение, 
которое может быть обработано только в определённых точках ответственности.

Так устроены корни `Cancellation` (отмена задачи) и `AssertionError` (провал `assert`): `Cancellation` ловит только
контекст задач рантайма, `AssertionError` — только `assert throws` и прогонщик тестов ([тесты](tests/tests.md)).

Для того чтобы ограничить обработку исключения,
следует использовать контракт `CatchRestriction`.
Он указывает компилятору, что это исключение ловят не везде, а только в особых точках. Где именно программе
разрешено ловить отмену и как прогонщик тестов получает право ловить `AssertionError`, пока не решено (Edmond,
2026-10-31: прежний пример контракта-обработчика `CancellationHandler` убран, его назначение неясно).

`CatchRestriction` объявляют только корни `Cancellation` и `AssertionError`. Под `Exception` или `Fault`
ограничение — ошибка компиляции, поэтому `catch e: Exception` и общий `catch` ловят ровно то, что называют, и
ограниченное исключение не встречают. Корни открыты для наследования, подкласс несёт ограничение корня (Edmond,
2026-10-31).

```efen
class LeaseExpired {                 // ошибка: своего корня у программы нет
    conforms Throwable
    conforms CatchRestriction
}

class Timeout: Cancellation { }      // отмена по таймауту; ловит её только контекст задач

class Wrong: Exception {
    conforms CatchRestriction        // ошибка: ограничение под Exception
}
```

```efen
class Cancellation {
    conforms Throwable
    conforms CatchRestriction

    fn reason() -> Reason nofail {
        return .cancellation
    }
}
```

`Cancellation` — не ошибка, поэтому правила для `Exception` её не касаются: она не входит в сводку исключений,
проходит сквозь `nothrows`, `throws only` и `isolated` и не доставляется внутри `nofail`, `deinit`, `dispose` и
`defer` ([контексты](context-and-effects.md)). Иначе `nothrows` функция с точкой ожидания не собралась бы: поймать
отмену она не вправе, выпустить — тоже (Edmond, 2026-10-31).

Рантайм не доставляет отмену внутри `nofail`, а бросок самой программы туда может дойти. `nofail` не выпускает
отмену, как и всё остальное: если `throw` подкласса `Cancellation` может дойти до границы `nofail`, это ошибка
компиляции (Edmond, 2026-10-31).

```efen
class LeaseExpired: Cancellation { }

fn release() nofail {
    throw LeaseExpired()             // ошибка: отмена не выходит из nofail
}
```

## Примеры

### Пример 1: Автоматическое распространение

```efen
fn funcC {
    throw ErrorC()
}

fn funcB {
    funcC()  // ErrorC автоматически наследуется
}

fn main nothrows {
    try {
        funcB()
    } catch e: ErrorC {
        print("Handled")
    }
}
```

### Пример 2: Многоуровневая архитектура

```efen
// Слой данных
responsibility DataLayer handles DataError {
    fn query {
        throw DatabaseError()
    }
    
    fn publicSave -> Bool nothrows {
        try {
            query()
            return true
        } catch {
            return false
        }
    }
}

// Бизнес-логика
responsibility BusinessLayer handles BusinessError {
    fn register {
        DataLayer.publicSave()  // nothrows
        throw RegistrationError()
    }
    
    fn publicRegister nothrows {
        try {
            register()
        } catch {
            logError()
        }
    }
}
```

## Интеграция с контекстами

```efen
context ErrorHandler {
    let logger: Logger
}

responsibility Service handles ServiceError in ErrorHandler {
    fn process {
        try {
            operation()
        } catch e: ServiceError {
            %logger.error(e)
            throw e
        }
    }
}
```

interface Repository {

class UserRepository {

## Ковариантность

При переопределении можно только **сужать** исключения:

```efen
interface Service {
    fn process throws only ErrorA, ErrorB
}

class ConcreteService {
    implements Service

    fn process throws only ErrorA {  // ✅ Убрали ErrorB
    }
}

class BrokenService {
    implements Service

    fn process throws only ErrorA, ErrorB, ErrorC {  // ❌ Добавили ErrorC
    }
}
```

## `throws` в типе функции

Выведенный `throws` входит в тип функции (Edmond, 2026-10-28): компилятор сам
выводит, бросает ли функция, и значение-функция несёт это в своём типе. Функция,
которая не бросает, подходит туда, где ожидают бросающую; бросающая туда, где
ожидают не бросающую, — ошибка компиляции.

```efen
fn parse(text: String) -> Int { ... }      // внутри throw: выведен throws
fn twice(x: Int) -> Int { return x * 2 }  // не бросает

let f: (Int) -> Int throws = twice      // ✅
let g: (String) -> Int = parse          // ❌ parse бросает
```

## Must-handle исключения

Обязанность поймать исключение объявляется у типа или у области. Отдельной
формы `throws!` у функции нет: она дублировала типовой `MustHandle`.

У типа она записывается контрактом `MustHandle` в объявлении класса исключения —
той же формой, что `CatchRestriction` выше. Обязанность действует везде, где это
исключение возникает, независимо от сигнатуры функции:

```efen
class CriticalError: Exception {
    conforms MustHandle
}
```

Функция перечисляет исключение обычным `throws`; `MustHandle` типа заставляет
вызывающую сторону обработать его по описанному ниже правилу:

```efen
fn critical throws CriticalError {
    throw CriticalError()
}
```

У области обязанность задаёт свойство региона `handles`, а запрет исключений
целиком — свойство `nothrows`; оба описаны в разделе «Гарантии по исключениям»
документа [«Области кода»](code-regions.md):

```efen
region handles CriticalError {
    try {
        critical()
    } catch e: CriticalError {
        handleCritical(e)
    }
}
```

### Что значит «немедленно»

`MustHandle` требует явного перехвата в непосредственном вызывающем. Обработчик
может поглотить исключение либо явно бросить его снова. Повторный `throw` не
является молчаливым распространением: он создаёт новый выход того же типа и
сохраняет его `MustHandle` для следующего вызывающего:

```efen
fn rethrowing throws CriticalError {
    try {
        critical()
    } catch e: CriticalError {
        logError(e)
        throw e
    }
}
```

Функция, которая пробрасывает такое исключение, объявляет обычный `throws E`.
Отдельный `!` не нужен: `MustHandle` сохраняется свойством типа `E`, поэтому
следующий непосредственный вызывающий также обязан поставить обработчик.

Немедленно — значит в той же функции, где лексически написан вызов. Пропустить
такое исключение дальше по стеку молча нельзя:

```efen
fn caller {
    // ❌ Ошибка: CriticalError должен быть обработан немедленно
    critical()
}

fn correctCaller {
    try {
        critical()
    } catch e: CriticalError {
        handleCritical(e)
    }
    // CriticalError НЕ распространяется дальше
}
```

Замыкание, которое не покидает функцию, для этого правила прозрачно: оно
выполняется внутри вызова, поэтому `try` вокруг вызова требование выполняет.

```efen
fn correctInClosure(items: [Item]) {
    try {
        items.forEach => critical(item)
    } catch e: CriticalError {
        handleCritical(e)
    }
}
```

Тело `defer` выполняется на выходе из области, где он записан (см.
[defer](blocks/guard.md#defer--отложенное-выполнение)), а не на месте инструкции, поэтому
`try` вокруг самой инструкции его не покрывает. `catch` пишется внутри тела
`defer`:

```efen
fn withDefer(path: String) {
    defer {
        try {
            critical()
        } catch e: CriticalError {
            handleCritical(e)
        }
    }

    process(path)
}
```

Обычное исключение из `defer` может выйти наружу. Если другое исключение уже
покидает область, оно остаётся главным, а новая ошибка добавляется в его
упорядоченный список `suppressed`. Если активного исключения нет, первая ошибка
cleanup становится главной; последующие ошибки остальных `defer` добавляются к
ней. Все тела продолжают выполняться в порядке LIFO.

`cause` и `suppressed` имеют разный смысл. `cause` задаётся явно, когда одна
ошибка объясняет другую. `suppressed` хранит независимые ошибки cleanup,
которым не разрешено заменить уже выбранный основной выход. Обычный `catch`
сопоставляется с главным исключением; прикреплённые ошибки доступны через
`error.suppressed` и показываются диагностикой вместе с ним.

Для `MustHandle` сохраняется более сильное правило выше: такое исключение
нельзя только прикрепить к цепочке, его нужно явно поймать внутри `defer`.

Блок `flow { }` для этого правила считается отдельной функцией, а его оператор
`catch Err` — обработчиком. Выбор по типу в `catch Err` определяет раздел
«Оператор catch» в [`flow.md`](flow.md).

Тело `flow generator` выполняется на вызове `next()`, то есть после того, как
вызов генератора вернул управление. Поэтому оно тоже считается отдельной
функцией — так же, как сохранённое для последующего вызова замыкание.

Сохранённое замыкание переживает вызов регистрации и выполняется отдельно,
поэтому `try` вокруг регистрации ничего не ловит. Получатель выражает это право
модификатором `@escaping` в функциональном типе:

```efen
fn wrongForStoredCallback(register: (@escaping () -> Void) -> Void) {
    try {
        // ❌ Ошибка: вызов уйдёт за пределы try
        register => critical()
    } catch e: CriticalError {
        handleCritical(e)
    }
}

fn correctForStoredCallback(register: (() -> Void) -> Void) {
    register => {
        try {
            critical()
        } catch e: CriticalError {
            handleCritical(e)
        }
    }
}
```

### Сложение требований

Требования складываются. `MustHandle`, `required catch` контракта и `region
handles` должны быть выполнены все; старшинства между ними нет, и выполнение
одного не снимает остальные.

`throws only E`, объявленный или выведенный `throws E` сохраняют `MustHandle`
типа `E` через сигнатуру. На каждой непосредственной границе вызова исключение
должно быть обработано; обычный `throws` не снимает эту обязанность и не требует
дублирующего знака `!`.

## Как исключение передаётся: раскрутка стека и `Expected`

Для программы все исключения одинаковы: `throw`, `catch`, `finally` и
сводки `throws` работают одинаково. Различается только цена. По умолчанию
исключение передаётся раскруткой стека, как в C++: вызов, который ничего не
бросил, не выполняет ни одной лишней инструкции, а сам бросок дорогой —
обработчик ищется по таблицам, кадр за кадром. Так передаются редкие сбои:
нехватка памяти, переполнение, отмена.

Класс исключения, который объявляет контракт `Expected`, передаётся вторым
значением возврата, как `Result` в Rust: бросок почти бесплатный, но после
каждого вызова функции, которая может его бросить, стоит проверка. Так
передаются ожидаемые сбои обычной работы: нет ключа, неверный ввод, файл не
найден.

```efen
class NotFound: Exception {
    conforms Expected
}

fn lookup(key: String) -> Int {
    throw NotFound()        // возвращается вызывающему вторым значением
}

fn load -> Pointer<Byte> {
    return allocate(4096)   // AllocationError раскручивает стек
}
```

Правила:

1. Без `Expected` исключение раскручивает стек. `AllocationError`, в том
   числе при создании экземпляра класса, раскручивает стек: функция, которая
   создаёт экземпляр класса, может бросить `AllocationError` по своей сводке.
   Это сбой: функция `nofail`, которая
   неявно выделяет память, обязана поймать его явно, а `nothrows` его
   пропускает. Где компилятор доказал, что
   память уже есть (рост коллекции после `reserve`), бросок снимается.
2. `Expected` наследуется: подкласс класса с `Expected` тоже передаётся
   возвратом.
3. Функция может бросать исключения обоих видов сразу: `Expected` уходят
   возвратом, остальные раскруткой. Функция, которая не бросает `Expected`,
   сохраняет обычную сигнатуру.
4. Там, где раскрутки нет (песочница WebAssembly без обработки исключений),
   компилятор передаёт возвратом все исключения; поведение программы то же.

Решение Edmond от 2026-10-23. Реализация — amber dev/plans/S57.md.

## Трасса стека

Трасса — список кадров, через которые прошло исключение: функция, файл, строка.
Её снимают только для того исключения, которое кто-то прочитает. Бросок, чей
`catch` трассу не читает, не платит за неё ничего.

```efen
fn load(path: String) -> Config {
    try {
        return parse(read(path))
    } catch e: ParseError {
        log("${e.message}\n${e.throwTrace(frames: .program)}")
        return Config.default
    }
}
```

Синтаксиса на `catch` нет. Компилятор видит всю программу и сам находит
`catch`, который читает трассу: тот, чей код вызывает у пойманного исключения
`stackTrace()` или `throwTrace()` прямо или через функции, которым передаёт
исключение. Такой `catch` получает пометку в таблице раскрутки, и при броске
стек обходится один раз, пока он ещё цел.

### Два метода

| Метод | Какие кадры |
|---|---|
| `e.stackTrace()` | От `throw` до входа в программу (`main`, функции, которую вызывает C, или входа песочницы) |
| `e.throwTrace()` | От `throw` до кадра этого `catch` включительно |

Оба принимают одни и те же параметры:

- `limit: Int` — сколько кадров вернуть, по умолчанию 64. Кадры, не вошедшие
  в трассу, считаются в `dropped`, печать заканчивается строкой `... ещё N`.
- `frames:` — `.all` (по умолчанию): код программы, std и рантайма;
  `.program` — только пакеты самой программы. С `.program` кадров может
  вернуться меньше `limit`.

Кадры самой раскрутки (бросок, разбор кадров) в трассу не попадают.
Встроенная (inline) функция даёт свой кадр с `inlined: true`; `limit` считает
такие кадры наравне с остальными.

Если параметры известны при компиляции, стек обходится ровно настолько,
насколько просили. Если нет, обход берётся самый широкий, а лишнее
отрезается при вызове.

### Результат

`Trace` — список `TraceFrame`:

| Поле | Тип | Значение |
|---|---|---|
| `function` | `String?` | Имя функции с пакетом |
| `file` | `String?` | Файл исходника |
| `line`, `column` | `Int?` | Место вызова |
| `inlined` | `Bool` | Функция встроена в вызывающую |
| `offset` | `Int` | Смещение адреса в исполняемом файле |

Имена и места есть, когда таблица мест встроена в программу (уровень
`embedded`, по умолчанию в отладочной сборке). В выпуске (`offsets`) у кадра
есть только `offset`; напечатанная трасса содержит идентификатор сборки, и
`amber trace decode` превращает её в имена и строки по файлу таблицы этой
сборки. Формат печати тот же, что у отчёта об исключении, которое никто не
поймал.

Трасса пустая, если снимать её было не для кого: исключение ещё не брошено,
сборка без трасс (`none`), или брошено туда, где трассу не читают. Пустая
трасса называет причину в `reason`; чтение трассы никогда не останавливает
программу.

### Когда исключение покидает `catch`

- **Сохранённое исключение уносит трассу.** Исключение, которое `catch`
  кладёт в поле, в коллекцию, передаёт как `cause` или в C, получает трассу,
  если программа где-то читает трассу у сохранённых исключений этого класса.
  Решение Edmond от 2026-10-29.
- **Повторный `throw e` продолжает трассу.** Кадры копятся от первого
  `throw`: внешний `catch` видит и путь до повторного броска, и путь после
  него.
- **`Expected`.** Исключение, передаваемое возвратом, собирает кадры по пути
  возврата, только если его класс ловит помеченный `catch`.

### Исключение, которое никто не ловит

Такое исключение останавливает программу в тот момент, когда раскрутка
понимает, что обработчика нет, — до того, как снят хоть один кадр. Поэтому
`defer`, `finally` и `on` в этом случае не выполняются, а стек цел для
отчёта. Что попадает в отчёт, задаёт опция компилятора: ничего, имя класса,
смещения кадров или имена и строки.

Отчёт печатает обработчик непойманных, после чего процесс завершается
с кодом 1, как в Python, Java, Node и .NET: снаружи такой выход отличим от
падения по сигналу. Обработчик — `@unique` контракт из файлов `lang::`; реализацию по умолчанию даёт рантайм, а
программа может связать свою в конфигурации, как любой `@unique` контракт
([статическое связывание](context-and-effects.md#статическое-связывание-эффектов)) (Edmond, 2026-10-31):

```efen
// lang::
@unique
contract UncaughtHandler {
    fn handle(thrown: Throwable) -> Never nofail
}

// server/project.efen
config server {
    effects {
        UncaughtHandler: CrashReporter
    }
}
```

Обработчик вызывается там, откуда брошенному дальше некуда идти, например на выходе из `main`. Вызов идёт до
раскрутки: обработчик возвращает `Never`, кадры снимать незачем. Поэтому обработчик ничего не выделяет (он мог быть
вызван из-за `AllocationError`) и работает на своём запасном стеке (из-за `StackExhaustedError`) (агент).

Решение Edmond от 2026-10-28 и 2026-10-29; код выхода 1 — 2026-10-30. Реализация — amber dev/plans/S81.md.

## Диагностика

```efen
fn handler nothrows {
    processData()
}

// Ошибка компиляции:
// error: function 'handler' is nothrows but may throw:
//   - DatabaseError (from processData -> queryDB)
//   - ValidationError (from processData -> validate)
```

## Правила

1. **Автоматическое распространение**: Исключения автоматически наследуются
2. **Точки ответственности**: `nofail` обязан обработать всё (кроме `AssertionError`, правило 7), `nothrows` и `throws only` — всё, кроме сбоев
3. **Два режима throws**:
   - `throws E` — **добавляет** E
   - `throws only E` — **ограничивает** до E
4. **Ковариантность**: Можно только сужать исключения при переопределении
5. **Responsibility**: Зоны ответственности с автоматической проверкой на границах
6. **Канал передачи**: по умолчанию раскрутка стека, `Expected` — вторым значением возврата
