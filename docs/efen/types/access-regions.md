# Области доступа

[Документация](../README.md) · [Словарь](../glossary.md) · [Ownership](ownership.md) · [Коллекции](collections.md) · [Layout](../memory/addresses.md)

> Статус: проект спецификации (Edmond, 2026-10-20). Решённое помечено как правило, остальное — как
> предложение. Компилятор правила ещё не проверяет.

Безопасность ссылок в Efen сводится к одному вопросу: совместимы ли права всех участков кода, которые
в данной точке программы держат доступ к одной памяти. Такой участок называется **областью доступа**.
Области выводит компилятор; программист пишет режим доступа и origin только там, где нужен контракт.

## Понятия

| Понятие | Значение |
|---|---|
| **Слот** | Логическое место, где живёт значение: параметр, локальная переменная, результат вызова, элемент коллекции, поле. Ссылка указывает на слот, а не на имя (см. [Ownership](ownership.md#явное-извлечение)) |
| **Владелец** | Имя, которое отвечает за уничтожение слота. Владение передаётся только явно, через `take` |
| **Структура значения** | Слоты значения и всё, чем оно владеет, транзитивно: буфер строки, узлы списка, payload optional, `own`-поля, — вместе с их адресами |
| **Смена структуры** | Операция, которая создаёт, уничтожает или перемещает слоты структуры. Ссылку портит только уничтожение или перемещение её слота |
| **Область доступа** | Участок кода, где живо право на слоты: от взятия ссылки до её последнего использования на каждом пути. Это не блок `{ }`, а часть графа программы |
| **Договор области** | Память, на которую область держит право (origin), и само право (режим доступа) |

Владение и доступ — разные вещи. Итератор не владеет коллекцией: он берёт право доступа на время
своей области и возвращает его.

Слово «область» в Efen встречается в трёх смыслах, поэтому здесь оно всегда с уточнением: область
доступа (этот документ), лексический [`region`](../code-regions.md) с гарантиями на выходе и область
памяти layout (`Items.Area`, «перевыделение области»).

## Договор области записывается типом ссылки

| Часть области | Пример | Где записано |
|---|---|---|
| какая память | `values`, `doc.title` | origin в квадратных скобках |
| какое право | `read`, `edit`, полное | режим ссылки |
| на каком участке кода | от взятия до последнего использования | нигде: выводит компилятор |

```efen
fn first(values: &read Array<Int>) -> &read[values] Int
```

Тип `&read[values] Int` — договор: «держу `read` на память `values`». В каждой точке программы
компилятор сверяет живые договоры по таблице совместимости.

**Правило.** Origin может указывать путь внутрь места: поле или элемент. В скобках всегда место
(параметр, переменная, параметр-память), а не тип; типы в Efen пишутся с большой буквы, поэтому
`doc.title` и `Document` не путаются.

```efen
fn header(doc: &read Document) -> &read[doc.title] String
```

Смена структуры `doc.body` не трогает ссылку с origin `[doc.title]`.

## Права

| Право | Ссылка | Параметр | Разрешает |
|---|---|---|---|
| чтение | `&read T` | `T` | читать |
| правка | `&edit T` | `edit T` | писать значения в слоты, которые ничем не владеют; структуру не меняет |
| полное | `&T` | `mut T` | всё, включая смену структуры |

**Правило.** `edit` — режим доступа [Ownership](ownership.md#аспекты-владения), седьмого права он не
создаёт. `&T` даёт полное право, как `mut`.

**Правило (уточнение агента к решению Edmond «`edit` запрещает менять любые указатели структуры»).**
Структура транзитивна по владению. Под `edit` можно записать только слот, тип которого ничем не
владеет, не имеет вариантов и не содержит указателей: число, флаг, структуру из таких полей. Поле
`Items.Item`, `Items.Area` или хранимая ссылка — указатель структуры, даже если ничем не владеет. Запись значения, которое
владеет памятью (строка, вложенный вектор, `own`-поле, optional, enum), уничтожает старую память и
считается сменой структуры старого значения. Ссылка, полученная через область `edit`, получает не
больше `edit`: право ссылки ограничено правом области, из которой она взята.

```efen
fn reset(rows: edit Vector<Vector<Int>>) {
    for row in &rows {
        row[0] = 0           // можно: Int ничем не владеет
        row.append(1)        // ошибка: row получил edit, append меняет структуру
        row = []             // ошибка: уничтожает старый буфер row
    }
}
```

В generic-коде запись `x = value` под `edit` допустима, только если про `T` известно, что он ничем
не владеет.

### Что делает полное право

Полное право — это всё, что сводка операции говорит о структуре. Удобные ступени между `edit` и
полным правом — не новые права, а то, какие слоты операция создаёт, уничтожает или перемещает:

| Действие | Что со слотами |
|---|---|
| удалить текущий элемент | уничтожается один слот; в массиве сдвигаются все после него |
| добавить | создаются новые слоты; в массиве при росте перемещаются все |
| произвольная смена | любые |

## Совместимость

| держит одна область \ хочет другая | чтение | правка | смена структуры |
|---|---|---|---|
| чтение | можно | можно | нельзя |
| правка | можно | можно | нельзя\* |
| смена структуры | нельзя\* | нельзя\* | нельзя\* |

\* Только для слотов, которые смена структуры уничтожает или перемещает. Создание новых слотов
рядом (узел, добавленный в связный список) с живыми ссылками не конфликтует.

Две пишущие области на одну память допустимы, как и две пишущие ссылки (см.
[Ownership](ownership.md#ссылки)): запись значения слот не уничтожает. Запрет даёт только смена
структуры, и только для тех слотов, которые она уничтожает или перемещает. Удаление узла списка не
трогает остальные узлы; удаление из массива сдвигает элементы после удалённого, и ссылки на них
умирают. Какие слоты затрагивает операция, говорит сводка функции.

**Правило.** `mut` и `&T` не исключительные. Другие ссылки живут рядом с полным правом и умирают,
только когда оно меняет структуру той части, на которую они смотрят. Один участок кода может читать
слот, пока другой в него пишет: запись не уничтожает слот, и читатель каждый раз читает его заново.
Умирает только то, что читатель получил из старого значения указателя, когда писатель этот указатель
меняет. Это правило для одного потока; потоки (`spawn`, `shared`) пока не проектируются.

Ссылка на сам слот переживает запись в него владеющего значения: слот остаётся, читатель увидит
новое значение. Умирают ссылки внутрь старой памяти, которой значение владело: в буфер старой строки,
в элементы старого вектора.

**Правило (агент).** Внутри функции параметры считаются разными местами. Пересечение проверяет
вызывающий: если сводка функции меняет структуру через один параметр, пока держит область на другом,
аргументы этих параметров не должны пересекаться. Аргументы сравниваются по путям: `doc` и
`doc.tags` пересекаются, `doc.tags` и `doc.items` нет. Захват замыкания, которое передано в тот же
вызов, считается ещё одним аргументом.

```efen
fn extend(dst: &Vector<Int>, src: &read Vector<Int>) {
    for x in src.reading() { dst.append(x) }   // внутри: dst и src разные
}

extend(a, b)          // можно
extend(v, v)          // ошибка: append меняет структуру dst, пока обход держит src, а это одна память
```

Так функция, которая принимает две коллекции одного типа и растит одну, пишется без особых пометок,
а `v.extend(v)` ловится в месте вызова.

## Как компилятор выводит области

- Граница области — живость ссылки. Ссылка, которая больше не используется, не мешает смене структуры.
- Право области — из операций в ней и из сводок вызванных функций. Сводка помнит путь до поля
  (`self.items`), поэтому вызов метода, который меняет `self.cache`, не мешает обходу `self.items`.
- После ветвления ссылка указывает на множество слотов, и проверяется каждый.
- Вызов получает право области через параметр и возвращает его после вызова.

**Правило.** Слот переменной блока умирает в конце блока, где объявлен. Ссылка жизнь не продлевает,
потому что ничем не владеет. `take` в уже существующее место (`outer = take a`) переносит значение и
убивает все ссылки на слот-источник; общий слот остаётся только у новой переменной
(`let moved = take a`), как в [Ownership](ownership.md#явное-извлечение):

```efen
let fallback = makeItem()
let r: &Item
if ready() {
    let a = makeItem()
    r = &a
} else {
    r = &fallback
}
print(r)          // ошибка: слот a умер в конце блока if
```

Значение, которое должно пережить блок, отдают внешнему владельцу:

```efen
var chosen: Item? = null
if ready() {
    chosen = makeItem()
}
let r = if let item = chosen { &item } else { &fallback }
print(r)
```

Здесь `item` — не новая переменная, а имя для payload `chosen`, поэтому `&item` ссылается на слот
внутри `chosen` и живёт, пока жив `chosen`.

**Правило (агент).** Временное значение без имени принадлежит инструкции, в которой создано, и
умирает в её конце. Уточнения для составных инструкций:

- источник обхода `for` живёт до конца цикла;
- временное значение в условии `if`, `while` и в выражении `match` умирает сразу после проверки, если
  ничего из него не связано; если `if let`, `while let` или ветвь `match` связывает имя с его частью,
  оно живёт до конца этой ветви или этой итерации.

Ссылка жизнь временного значения не продлевает, как и жизнь переменной блока:

```efen
for x in &loadValues() { print(x) }   // можно: источник обхода живёт до конца for
if v.reading().any(isBig) {           // курсор умер после условия
    v.append(1)                       // можно
}
let r = &read loadValues()[0]         // ошибка: значение умирает в конце инструкции
print(r)                              // подсказка: let values = loadValues(); let r = &read values[0]
```

## Итератор как область

```text
область 1: функция, владеет коллекцией v
└─ область 2: цикл, курсор держит право на v
   └─ область 3: итерация, тело получает текущий элемент
```

Курсор держит право на коллекцию. На каждой итерации он **одалживает** телу текущий элемент.

**Правило.** Пока курсор жив, коллекция закрыта для смены структуры через сам объект: удалять и
добавлять можно только через курсор, потому что операция над объектом — это операция над внешней
областью, а не над областью обхода. Компилятор проверяет отношение между областями: операцию через
объект он разрешает, если по сводке она не задевает места, на которые смотрит курсор, или задевает их
без конфликта по таблице совместимости. Курсор, который сам меняет структуру (виды 3, 4, 5 и 7),
конфликтует с любым доступом к своей коллекции мимо него: между итерациями сжатие не закончено, и
мимо курсора видны пустые слоты. Для такого курсора разрешены только операции над непересекающимися
путями.

```efen
for item in doc.items.reading() {
    doc.tags.append(item.id)     // можно: tags не пересекается с областью обхода items
    doc.items.append(item)       // ошибка: append может перенести буфер items, курсор смотрит в него
}
```

**Правило.** Обход и срез изменяемого источника держат его в `edit` (см.
[Коллекции](collections.md#контракты-обхода), [циклы](../blocks/loops.md#итерация-с-модификацией)).
Пока такой обход идёт, тело может читать коллекцию заново (`v.count`, `v[i]`), но не может сменить её
структуру.

Ссылка, которая ушла из области 3 дальше итерации, проверяется общим правилом: пока ничто не
уничтожает и не перемещает её слот, она годна.

### Виды итераторов (предложение)

| # | Вид | Право курсора | Доступ к коллекции мимо курсора |
|---|---|---|---|
| 1 | только чтение | чтение | чтение |
| 2 | правка значений | правка | чтение и правка |
| 3 | удалить текущий, с отдачей владения | полное | только непересекающиеся пути |
| 4 | добавлять через курсор, обход видит новые элементы | полное | только непересекающиеся пути |
| 5 | любое изменение через курсор (`insert`, `remove`, `sort`); курсор сам поправляет позицию | полное | только непересекающиеся пути |
| 6 | потребляющий, `for x in take v` | `own` всей коллекции | коллекции больше нет |
| 7 | опустошающий | полное, коллекция остаётся пустой | только непересекающиеся пути |
| 8 | по снимку | чтение копии | любой |
| 9 | по индексу | чтение слота коллекции (указатель на буфер, длина) и номер элемента | любой; ссылка на текущий элемент умирает при смене структуры |

Виды 3, 4, 5 и 7 держат коллекцию исключительно. Причина: в массиве удаление через курсор идёт
сжатием, и между итерациями часть слотов уже сдвинута; чтение `v` мимо курсора увидело бы пустые или
чужие слоты. По той же причине в коллекциях, где удаление или добавление перемещает слоты, ссылка на
текущий элемент живёт одну итерацию: следующий `next()` после удаления сдвигает элементы.

**Правило.** Обход с добавлением идёт до живого конца: элементы, добавленные во время обхода, он
тоже посетит. Так работают очередь задач и обход графа в ширину.

**Правило.** Итератор по индексу (вид 9) держит не буфер, а слот самой коллекции только для чтения и
номер текущего элемента. На каждом шаге он заново читает указатель на буфер и сравнивает номер с
живой длиной, поэтому коллекция может менять свою структуру, а перевыделение итератору не мешает.
Конфликт остаётся только у ссылки на текущий элемент: она смотрит в буфер.

```efen
for item in queue.byIndex() {
    let next = item.childId      // Int копируется, ссылки в буфер не остаётся
    queue.append(Task(next))     // можно: итератор держит номер, а не буфер
    // print(item.name)          // ошибка: append мог перенести буфер, item умер
}
```

Вид 5 доказуем без поддержки во время выполнения: курсор держит смену структуры исключительно, а
каждая его операция сама поправляет позицию. Позиция — номер, а не адрес, поэтому ошибка в коде
курсора уводит обход не туда, но память не портит. Вариант, где объект сам меняется мимо курсора и
обновляет все живые итераторы, возможен только через layout: итераторы входят в структуру объекта,
а «позиция каждого живого итератора верна» — инвариант структуры (см.
[план доказательств](../memory/viper-proof-plan.md)).

Если тело бросает исключение посреди сжатия, курсор при уничтожении заканчивает сжатие, и каждый
элемент уничтожается ровно один раз.

**Правило удаления при обходе.** `remove` — метод только курсора. Он получает ссылку на текущий
элемент, которую выдал этот же курсор, и забирает его слот окончательно, через `take`. После вызова
слот мёртв: ни переменной цикла, ни ссылками, взятыми из неё, пользоваться нельзя. Удаление — это уход
слота из структуры, как передача в `own`-параметр. `remove` возвращает `own T`; если результат никто
не забрал, элемент уничтожается в конце инструкции.

```efen
for item in items.removing() as cursor {
    if item.dead {
        let body = cursor.remove(take item)   // слот item забран, элемент теперь у body
        // print(item.hp)                     // ошибка: слот item удалён
        // items.remove(0)                    // ошибка: items закрыта, пока жив cursor
    }
}
```

Компилятор проверяет, что в `remove` передан текущий элемент этого курсора: `next()` выдаёт ссылку с
origin самого курсора (`&edit[self] T`), а другого доступа к коллекции, пока курсор жив, нет. Элемент
другого обхода или прошлой итерации не подойдёт. `remove` убивает все ссылки с этим origin, в том числе
копии ссылки (`let a = item`), поэтому второй `remove` того же элемента — ошибка. После удаления обход
продолжается со следующего элемента без пропуска; это обязанность курсора.

Запись `as cursor` даёт имя курсору цикла `for` (предлагаемый синтаксис). Без неё курсор пишут явно:

```efen
let cursor = items.removing()
while let item = cursor.next() {
    if item.dead { cursor.remove(take item) }
}
```

Простой фильтр без обхода пишут через `retain` или `filter`; курсор нужен, когда тело делает с
удалённым элементом что-то ещё.

### Как автор коллекции описывает области

Отдельного синтаксиса не нужно. Автор даёт по курсору на каждое право, и `for` выбирает подходящий
по полному типу и правам источника (см. [Коллекции](collections.md#контракты-обхода)). Права
параметров объявляет сигнатура (см. [Ownership](ownership.md#параметры)), поэтому курсор с удалением —
отдельная операция с `mut`, а не «условная запись».

Значение, внутри которого хранится ссылка, получает параметр-память (см.
[Ownership](ownership.md#хранимые-и-захваченные-ссылки)):

```efen
class Vector<T> {
    fn reading() -> ReadCursor<T, self>        // для чтения, self только читается
    fn editing(self: edit) -> EditCursor<T, self>
    fn removing(self: mut) -> RemoveCursor<T, self>
}

class EditCursor<T, Mem: Origin> {
    fn next() -> &edit[Mem] T?     // ссылка в коллекцию, а не в курсор
}

class RemoveCursor<T, Mem: Origin> {
    fn next() -> &edit[self] T?                    // живёт одну итерацию: удаление сдвигает элементы
    fn remove(take item: &edit[self] T) -> own T   // сводка: слот item уходит из структуры Mem
}
```

Запись режима для `self` в этом примере условная.

## Итератор как структура (Edmond, 2026-10-21)

Итератор — не особая сущность, а обычная структура данных, и проверяется по общим правилам. Поля
итератора массива — указатели layout:

```efen
struct ArrayIter<T, Src: Origin> {
    current: read[Src] Items.Item   // указатель на элемент именно этого массива
    size: Size                      // конец вычисляется: Src.root + size
}
```

Запись `read[Src] Items.Item` условная: как обычный код называет набор чужого layout, решает раздел
«Ссылка на элемент структуры» ниже.

Шаг обхода доказывается без решателя: инвариант `Src.root ≤ current ≤ end` линейный, сдвиг
`current + 1` его сохраняет при условии `current != end`.

**Правило.** Компилятор проверяет не код, а **отношения** между значениями: что на что указывает,
что из чего взято. Для `for x in v`:

```text
v ──владеет──▶ v.Items ◀──указывает в── it.current ◀──взят из── x
```

Операция проверяется по этой линии: смена структуры `v.Items` рвёт звено «указывает в», и вместе с
ним умирает всё, что ниже. Запись значения в слот звеньев не рвёт. Место, у которого с `v` нет
отношения, линию не задевает; есть ли отношение между двумя параметрами, решает правило о пересечении
аргументов выше.

**Правило.** Звено — не только указатель, но и факт, выведенный из структуры: длина, граница,
«элемент жив». Число `size`, снятое с `v.length`, держит факт `size == v.length`, и смена структуры
этот факт рвёт так же, как указатель.

**Правило.** Тело `for` для компилятора — скрытое замыкание. Замыкания в коде нет, компилятор
выводит его из тела вместе с правами, как права обычного замыкания (см.
[Замыкания](../closure.md#захват-переменных)). Колбэк и тело цикла проверяются одинаково:

```efen
for item in items { item.hp += 1 }
updateAll(items) => { item.hp += 1 }   // то же самое
```

**Правило.** Что итератор позволяет телу, следует из его отношения с данными. Отдельной записи
«что разрешено телу» нет:

```efen
struct IndexIter<T, Src: Origin> {
    array: read[Src] Array<T>       // только слот самого вектора
    index: Size
}
```

- `ArrayIter` держит адрес внутри `Src.Items` через вызов тела, поэтому тело не может перемещать
  элементы `Src`.
- `IndexIter` держит слот вектора и число, поэтому тело может менять структуру `Src` как угодно.
  После вызова тела итератор обязан вычислить адрес заново: старые указатели и факты мертвы, и
  компилятор это проверяет. Обход идёт по позициям: элемент, вставленный перед текущим, будет посещён
  ещё раз; память при этом цела.

**Правило.** Если тело делает то, чего итератор не позволяет, это ошибка. Коллекция может дать
несколько итераторов, и `for` выбирает подходящий. Если подходят несколько, берётся тот, что
позволяет меньше всего (агент): обычно он и самый быстрый, например с сохранённым указателем вместо
пересчёта.

### Мысли для дальнейшего (обсуждение 2026-10-21, не решено)

- **Две оси права.** Право — это пара: что делаю я (сравниваю адрес, читаю, пишу значения, перемещаю
  или уничтожаю слоты) и что запрещено остальным (ничего, писать, перемещать, всё). Прецедент — права
  ссылок Pony (deny capabilities, Clebsch и др., 2015: `iso`, `val`, `ref`, `box`, `tag`) и
  rely-guarantee Джонса.

  | Я | Остальным запрещено | Пример |
  |---|---|---|
  | пишу и перемещаю | всё | `&mut Vec<T>` в Rust |
  | пишу, не перемещаю | всё | `&mut [T]` в Rust |
  | пишу, не перемещаю | только перемещать | `edit` |
  | читаю | писать и перемещать | замороженное значение |
  | читаю | перемещать | обход для чтения |
  | только сравниваю | ничего | `tag` в Pony |

- **Исключительное право записи.** Итератор может держать исключительную запись в любой элемент
  (Edmond). В одном потоке память от неё не зависит: запись слот не уничтожает. Она нужна для логики
  алгоритма (сортировка не должна видеть запись компаратора в тот же массив), для скорости (`noalias`,
  векторизация) и для будущих потоков. Как её записывать, не решено.
- **Отношение итератора с телом** (второй путь Edmond): явно сказать, что тело может делать с
  данными итератора. Отношение с данными его почти покрывает; явная запись нужна только для сужения
  без причины в памяти, то есть для исключительности.
- **Право на сохранение.** Ссылка `x` привязана либо к слоту, на который смотрел `current`, и тогда
  переживает сдвиг итератора (`next() -> &read[Mem] T`), либо к самому курсору, и тогда умирает на
  следующем шаге (`RemoveCursor`, `next() -> &edit[self] T`). Права на `x` по видам итератора:
  чтение; чтение и запись; только сравнение с указателем; право взять указатель через особую функцию
  и сохранить его дольше итерации (Edmond, гипотетически).
- **Часть layout.** Итератор, чьи поля — указатели layout, живёт снаружи и цены во время выполнения
  не имеет. Экземпляр, который сам знает свои живые итераторы и поправляет их, — отдельный случай
  (см. вид 5 выше).

## Аксессоры и колбэки (предложение)

Итератор — частный случай. **Аксессор** — значение, которое держит область с определённым правом и
открывает наружу только безопасные операции: запись словаря, две половины массива (`split`),
редактор графа, пакетная правка. Правила областей проверяют код, который пользуется аксессором;
операции самого аксессора проверяет тот же анализ или, если они работают с памятью напрямую,
доказательство условий layout.

Колбэк без `@escaping` — тоже область: его нельзя сохранить, поэтому выданное право не утечёт (см.
[Замыкания](../closure.md#сохранение-замыкания-после-вызова)).

```efen
fn updateAll(values: mut Vector<Item>, action: (&edit Item) -> Void)

updateAll(items) => {
    item.hp += 1             // можно
    // items.append(...)     // ошибка: items держит область updateAll
}
```

Захват проверяется по пути, как ещё один аргумент вызова (см. правило о пересечении аргументов
выше). Колбэк, который захватил `items` и меняет его структуру, пересекается с аргументом `values`:
ошибка. Если колбэк захватил `self` и вызывает `self.spawn()`, который по сводке меняет структуру
`self.items`, это ошибка, пока `updateAll` держит `self.items`. Вызов метода, который трогает только
другое поле, допустим.

## Ссылка на элемент структуры

Указатель на элемент конкретного набора записывается так же, как в layout: `Items.Item` (см.
[Адреса и дескрипторы](../memory/addresses.md)). Такой указатель помнит и набор, и экземпляр, и
указатель на элемент другой структуры с ним несовместим.

**Правило.** Обычный код называет набор конкретного объекта путём к месту, как в origin:

```efen
fn connect(g: &Graph, from: g.Nodes.Node, to: g.Nodes.Node)
```

Узел другого графа сюда не подойдёт. Запись `Graph.Nodes.Node` (узел любого графа) не вводится:
перепутанный экземпляр ловился бы только во время выполнения. Путь в такой записи начинается с
неизменяемого имени: `let`, параметра или параметра-памяти. Путь через индекс или `var`
(`graphs[i].Nodes.Node`) не допускается, потому что он может назвать другой экземпляр.

## Одна модель с layout

Области доступа и [layout](../memory/addresses.md) описывают одно и то же с двух сторон: layout
объявляет места памяти и операции над ними, области доступа говорят, кто и когда этими местами
пользуется. Понятия совпадают один к одному:

| Области доступа | layout |
|---|---|
| слот | место: элемент дескриптора (`set`, `one`, `area`), поле структуры; локальные переменные функции — неявный `one` её кадра |
| структура значения | дескрипторы экземпляра, их места и адреса, вместе со всем, чем владеют элементы |
| смена структуры | операция дескриптора: `allocate` создаёт место, `free` и `extract` уничтожают или опустошают, `reallocateArea` и `move` перемещают |
| запись значения | запись поля найденного элемента при `write`-праве на layout; не операция дескриптора |
| origin `[v]`, `[doc.title]` | происхождение указателя из дескриптора и экземпляра layout (`addresses.md`, «Производные типы дескриптора») |
| ссылка на элемент | `Items.Item` |
| таблица совместимости | «живое заимствование блокирует удаление элемента, перемещение его физического места и уничтожение экземпляра layout» (`addresses.md`, «Владение, живость и доступ») |
| правка (`edit`) | `write` на поля элементов, которые ничем не владеют, без права вызывать операции дескриптора и писать поля-указатели (`Items.Item`, `Items.Area`) |
| `split` | подобласти над непересекающимися местами одного дескриптора: разные ячейки `area`, разные элементы `set` |
| окно, где условие layout временно нарушено | область с исключительным полным правом: до её конца нельзя вызвать код, способный обратиться к структуре, и опубликовать ссылку (`addresses.md`, «Декларативные условия») |
| скрытые `managed`-слоты layout | внутренние места, недоступные внешним областям; публичная ссылка сохраняет origin |

Отсюда два следствия.

**Действия полного права выводятся из операций дескриптора.** «Удалить текущий» — `free` или
`extract` одного элемента. «Добавить» для `set` — `allocate`, старые места на месте; для `area` — ещё
и `reallocateArea`, то есть перемещение всех мест. Поэтому `append` связного списка и `append`
вектора имеют разные сводки, и это видно из их layout, а не из отдельной пометки.

**Две проверки, одна теория.** Внутри representation операции над дескрипторами доказывает
компилятор, вместе с условиями layout (см. [план доказательств](../memory/viper-proof-plan.md)).
Результат доказательства — сводка операции: какие места она создаёт, уничтожает и перемещает. Код
снаружи, который пользуется коллекцией, проверяется по этим сводкам правилами областей, без
доказательства. Права с долями, на которых построен Viper, — та же таблица совместимости.

Курсор обхода на языке layout — указатель `Items.Item` на текущий элемент плюс право области на
`Items`; удаление через курсор — `Items.free` или `Items.extract` этого элемента.

## Промежуточные области

Когда двум областям нужно одно сильное право, его разводит третья:

- передача права параметру и возврат после вызова;
- отложенные операции: собрать, что удалить или добавить, применить после обхода;
- кладбище удалённых: элемент исключён, память живёт до конца внешней области, ссылки годны;
- надгробия: элемент помечен мёртвым, обход его пропускает, сжатие потом.

## Границы

Правила выводятся из кода. Безопасность, которая зависит от значений, требует проверки во время
выполнения или доказательства условий layout (см. [план доказательств](../memory/viper-proof-plan.md)):

- `&cells[i]` и `take cells[j]` при `i != j`;
- удаление узла списка мимо курсора, если узел не текущий и не следующий;
- удаление узла графа, на который не осталось рёбер;
- завершение обхода графа без циклов.

## Что решено 2026-10-20

| Вопрос | Решение |
|---|---|
| Как удалять при обходе | только `cursor.remove(take item)`; слот после вызова мёртв (Edmond) |
| Можно ли менять коллекцию мимо курсора | нет, кроме операций, которые не задевают область курсора или задевают её без конфликта; курсор, меняющий структуру, допускает только непересекающиеся пути (Edmond, уточнение агента) |
| Видит ли обход добавленные элементы | да, обход идёт до живого конца; итератор по индексу видит их по природе (Edmond) |
| Любое изменение при обходе | через курсор без цены во время выполнения; объект, который сам обновляет итераторы, — только через layout (Edmond) |
| Один читает, другой пишет | допустимо в одном потоке (Edmond) |
| Что исключает `mut` | ничего: другие ссылки умирают только при смене структуры; пересечение аргументов проверяет вызывающий (агент) |
| Как назвать набор чужой структуры | путь к месту, `g.Nodes.Node` (агент, по правилу origin) |
| Когда умирает временное значение | в конце инструкции, включая тело `for`/`if`/`match`/`while` (агент, по правилу слота блока) |

## Отложено до проектирования layout

- Права на отдельные ячейки (`split`) и правка внутренних указателей.
- Объект, который меняется мимо курсора и сам обновляет живые итераторы.
