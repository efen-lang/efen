>

> ([ownership](ownership.md#ссылки-только-внутри-функции)). Результат-ссылка, ссылка в поле и ссылка в

> [«Курсор без результата-ссылки»](#курсор-без-результата-ссылки).

Безопасность ссылок в Efen сводится к одному вопросу: совместимы ли права всех участков кода, которые
в данной точке программы держат доступ к одной памяти. Такой участок называется **областью доступа**.
Области выводит компилятор; программист пишет режим доступа и origin только там, где нужен контракт.

## Понятия

| Понятие | Значение |
|---|---|
| **Слот** | Логическое место, где живёт значение: параметр, локальная переменная, результат вызова, элемент коллекции, поле. Ссылка указывает на слот, а не на имя (см. [Ownership](ownership.md#явное-извлечение)) |
| **Владелец** | Имя, которое отвечает за уничтожение слота. Владение передаётся только явно, через `take` |
| **Структура значения** | Слоты значения и всё, чем оно владеет, транзитивно: буфер строки, узлы списка, payload optional, `own`-поля, — вместе с их адресами |
| **Смена структуры** | Операция, которая создаёт, уничтожает или перемещает слоты структуры. Ссылку портит только уничтожение или перемещение её слота |
| **Область доступа** | Участок кода, где живо право на слоты: от взятия ссылки до её последнего использования на каждом пути. Это не блок `{ }`, а часть графа программы |
| **Договор области** | Память, на которую область держит право (origin), и само право (режим доступа) |

Владение и доступ — разные вещи. Итератор не владеет коллекцией: он берёт право доступа на время
своей области и возвращает его.

Слово «область» в Efen встречается в трёх смыслах, поэтому здесь оно всегда с уточнением: область
доступа (этот документ), лексический [`region`](../code-regions.md) с гарантиями на выходе и область
памяти layout (`Items.Area`, «перевыделение области»).

## Договор области

| Часть области | Пример | Где записано |
|---|---|---|
| какая память | `values[0]`, `doc.title` | у ссылки — место, от которого она взята; у параметра и колбэка — origin в угловых скобках (Edmond, 2026-10-21) |
| какое право | `read`, `edit`, полное | форма ссылки (`&read x`, `&x`) или право параметра |
| на каком участке кода | от взятия до последнего использования | нигде: выводит компилятор |

```efen
let first = &read values[0]
```

Ссылка `first` — договор: «держу `read` на место `values[0]`». В каждой точке программы компилятор сверяет
живые договоры по таблице совместимости.

**Правило.** Origin указывает место, а может и путь внутрь места: поле или элемент. У ссылки он всегда
известен из её взятия и не пишется. Там, где origin пишется (отношение параметров, тип колбэка), в скобках
всегда место (параметр, переменная, параметр-память), а не тип; типы в Efen пишутся с большой буквы,
поэтому `doc.title` и `Document` не путаются.

```efen
let title = &read doc.title
doc.body.append(line)    // можно: смена структуры doc.body не трогает место doc.title
```

## Права

| Право | Ссылка в теле | Параметр | Разрешает |
|---|---|---|---|
| чтение | `&read x` | `T` | читать |
| правка | — | `edit T` | писать значения в слоты, которые ничем не владеют; структуру не меняет |
| полное | `&x` | `mut T` или `&T` | всё, включая смену структуры |

**Правило.** `edit` — режим доступа [Ownership](ownership.md#аспекты-владения), седьмого права он не
создаёт. `&x` в теле даёт полное право, как `mut`; `&T` в параметре — то же, что `mut T`. Ссылки с правом
`edit` в теле нет: оно бывает у параметра и у области, из которой ссылка взята.

**Правило (уточнение агента к решению Edmond «`edit` запрещает менять любые указатели структуры»).**
Структура транзитивна по владению. Под `edit` можно записать только слот, тип которого ничем не
владеет, не имеет вариантов и не содержит указателей: число, флаг, структуру из таких полей. Поле
`Items.Item`, `Items.Area` или хранимая ссылка — указатель структуры, даже если ничем не владеет. Запись значения, которое
владеет памятью (строка, вложенный вектор, `own`-поле, optional, enum), уничтожает старую память и
считается сменой структуры старого значения. Ссылка, полученная через область `edit`, получает не
больше `edit`: право ссылки ограничено правом области, из которой она взята.

```efen
fn reset(rows: edit Vector<Vector<Int>>) {
    for row in &rows {
        row[0] = 0           // можно: Int ничем не владеет
        row.append(1)        // ошибка: row получил edit, append меняет структуру
        row = []             // ошибка: уничтожает старый буфер row
    }
}
```

В generic-коде запись `x = value` под `edit` допустима, только если про `T` известно, что он ничем
не владеет.

### Что делает полное право

Полное право — это всё, что сводка операции говорит о структуре. Удобные ступени между `edit` и
полным правом — не новые права, а то, какие слоты операция создаёт, уничтожает или перемещает:

| Действие | Что со слотами |
|---|---|
| удалить текущий элемент | уничтожается один слот; в массиве сдвигаются все после него |
| добавить | создаются новые слоты; в массиве при росте перемещаются все |
| произвольная смена | любые |

## Совместимость

| держит одна область \ хочет другая | чтение | правка | смена структуры |
|---|---|---|---|
| чтение | можно | можно | нельзя |
| правка | можно | можно | нельзя\* |
| смена структуры | нельзя\* | нельзя\* | нельзя\* |

\* Только для слотов, которые смена структуры уничтожает или перемещает. Создание новых слотов
рядом (узел, добавленный в связный список) с живыми ссылками не конфликтует.

Две пишущие области на одну память допустимы, как и две пишущие ссылки (см.
[Ownership](ownership.md#что-ссылке-можно-и-нельзя)): запись значения слот не уничтожает. Запрет даёт только смена
структуры, и только для тех слотов, которые она уничтожает или перемещает. Удаление узла списка не
трогает остальные узлы; удаление из массива сдвигает элементы после удалённого, и ссылки на них
умирают. Какие слоты затрагивает операция, говорит сводка функции.

**Правило.** `mut` и `&T` не исключительные. Другие ссылки живут рядом с полным правом и умирают,
только когда оно меняет структуру той части, на которую они смотрят. Один участок кода может читать
слот, пока другой в него пишет: запись не уничтожает слот, и читатель каждый раз читает его заново.
Умирает только то, что читатель получил из старого значения указателя, когда писатель этот указатель
меняет. Это правило для одного потока; задачи `spawn` сверяются по правилам
[раздела о задачах](#задачи-spawn), право `shared` пока не проектируется.

Ссылка на сам слот переживает запись в него владеющего значения: слот остаётся, читатель увидит
новое значение. Умирают ссылки внутрь старой памяти, которой значение владело: в буфер старой строки,
в элементы старого вектора.

**Правило (Edmond, 2026-10-26).** Параметры по умолчанию не пересекаются. Внутри функции они разные
места, и вызывающий обязан передать аргументы, которые не делят память, что бы ни делало тело.
Пересечение допустимо, только если сигнатура его объявила (`maybe<dst>`, отношение «внутри», см.
ниже). Аргументы сравниваются по путям: `doc` и `doc.tags` пересекаются, `doc.tags` и `doc.items` нет.
Захват замыкания, которое передано в тот же вызов, проверяется не этим правилом, а по типу колбэка (ниже):
колбэк может читать и писать значения памяти параметра, пока функция не держит её одна.

```efen
fn extend(dst: &Vector<Int>, src: Vector<Int>) {
    for x in src.reading() { dst.append(x) }   // внутри: dst и src разные
}

extend(a, b)          // можно
extend(v, v)          // ошибка: dst и src — одна память, а пересечение не объявлено
```

Прежнее правило (агент, 2026-10-21) требовало непересечения только там, где оно нужно сводке функции;
оно заменено этим.

### Отношение между параметрами (Edmond, 2026-10-21)

**Правило.** Отношение между двумя параметрами бывает трёх видов, и каждое можно записать в
сигнатуре (право и origin после типа, как у колбэка; слова `not` и `maybe` условные):

```efen
fn insertAfter(list: mut List<Item>, node: Item read<list>)        // node внутри list
fn extend(dst: mut Vector<Int>, src: Vector<Int> not<dst>)         // src точно не часть dst
fn copyWithin(dst: edit Array<Int>, src: Array<Int> maybe<dst>)    // src может быть частью dst
```

С 2026-10-26 «точно не часть» — умолчание, и `not<dst>` можно не писать. Запись `node: Item read<list>`
вместо прежней `node: &read<list> Item` — предложение агента: ссылочного типа у параметра больше нет.

- **Внутри.** Origin у параметра называет другой параметр. Внутри функции
  компилятор знает звено «`node` указывает в `list.Items`» и проверяет операции над `list` по линии
  отношений: вставка в связный список `node` не трогает, `list.remove(node)` его убивает. В месте
  вызова компилятор проверяет, что аргумент взят из `list`; путь начинается с неизменяемого имени, как
  у `g.Nodes.Node`.
- **Точно не часть.** Вызывающий доказывает, что аргументы не связаны. Пометка фиксирует обещание
  как контракт: правка тела не меняет того, что могут вызывающие. Компилятор вправе считать память
  непересекающейся (`restrict` в C, но проверенный в месте вызова).
- **Может быть частью.** Тело обязано быть безопасным в обоих случаях: снять копию или пересчитывать
  адреса.

**Правило (Edmond, 2026-10-22; уточнено 2026-10-26).** Права и действия параметров без пометки выводятся
из тела у любой функции, публичной тоже. Непересечение аргументов выводить не нужно: это умолчание.
Сводка функции всегда доступна: её вычисляет компилятор по телу или привозит пакет в скомпилированных заголовках. `public`
меняет только то, кто может вызвать функцию. Записанная пометка остаётся контрактом и проверяется в
месте вызова. Правило от 2026-10-21 «у публичной функции правило для вызывающих берётся из заголовка»
отменено: Edmond перепутал его с контрактом и интерфейсом, где явная запись нужна (см. ниже).

**Правило (агент, по замечанию критика 2026-10-22).** Колбэк — граница функционального типа:
вызываемая функция не видит замыкания, поэтому что колбэку можно делать с её параметрами, говорит
тип параметра-колбэка ([тип функции](function-type.md)). Без пометки захват колбэка не меняет
структуру памяти параметров функции:

```efen
fn sortBy(items: mut Vector<Int>, less: (a: Int, b: Int) -> Bool)

data.sortBy((a: Int, b: Int) -> Bool {
    data.append(0)       // ошибка: замыкание меняет структуру data, а у less нет пометки mut<items>
    return a < b
})
```

Запись значения (`data[0] = 0`) из колбэка допустима, пока `sortBy` не держит эту память одна; вынутый
опорный элемент — такое удержание, но сводка его пока не записывает (BACKLOG Amber).

**Правило (Edmond, 2026-10-21).** Метод контракта — та же граница. Обобщённая функция знает о методах
`T` только их сигнатуры в контракте: `<` у `Comparable` без пометок ничего чужого не трогает.
Реализация, чей `<` обращается к чужим слотам, не подходит к контракту, и ошибка выдаётся там, где
реализация написана. Источник, который `T` несёт в своём типе (`Node<items>`), виден в месте вызова как
обычное пересечение аргументов.

```efen
fn sort<T: Comparable>(items: mut Vector<T>) {
    let pivot = take items[0]     // окно открыто: слот items[0] пуст
    if items[1] < pivot { ... }   // можно: < по контракту не трогает items
}
```

**Правило (агент).** Пометки пишутся для ясности или как обещание на будущее: «внутри» и
`not<dst>` требуют от вызывающего, `maybe<dst>` — то, что функция и так обязана выдержать. Скрытые
параметры-контексты (`in Env`) сравниваются с аргументами так же, как обычные параметры.

## Как компилятор выводит области

- Граница области — живость ссылки. Ссылка, которая больше не используется, не мешает смене структуры.
- Право области — из операций в ней и из сводок вызванных функций. Сводка помнит путь до поля
  (`self.items`), поэтому вызов метода, который меняет `self.cache`, не мешает обходу `self.items`.
- После ветвления ссылка указывает на множество слотов, и проверяется каждый.
- Вызов получает право области через параметр и возвращает его после вызова.

**Правило.** Слот переменной блока умирает в конце блока, где объявлен. Ссылка жизнь не продлевает,
потому что ничем не владеет. `take` в уже существующее место (`outer = take a`) переносит значение и
убивает все ссылки на слот-источник; общий слот остаётся только у новой переменной
(`let moved = take a`), как в [Ownership](ownership.md#явное-извлечение):

```efen
let fallback = makeItem()
let r: &Item
if ready() {
    let a = makeItem()
    r = &a
} else {
    r = &fallback
}
print(r)          // ошибка: слот a умер в конце блока if
```

Значение, которое должно пережить блок, отдают внешнему владельцу:

```efen
var chosen: Item? = null
if ready() {
    chosen = makeItem()
}
let r = if let item = chosen { &item } else { &fallback }
print(r)
```

Здесь `item` — не новая переменная, а имя для payload `chosen`, поэтому `&item` ссылается на слот
внутри `chosen` и живёт, пока жив `chosen`.

**Правило (агент).** Временное значение без имени принадлежит инструкции, в которой создано, и
умирает в её конце. Уточнения для составных инструкций:

- источник обхода `for` живёт до конца цикла;
- временное значение в условии `if`, `while` и в выражении `match` умирает сразу после проверки, если
  ничего из него не связано; если `if let`, `while let` или ветвь `match` связывает имя с его частью,
  оно живёт до конца этой ветви или этой итерации.

Ссылка жизнь временного значения не продлевает, как и жизнь переменной блока:

```efen
for x in &loadValues() { print(x) }   // можно: источник обхода живёт до конца for
if v.reading().any(isBig) {           // курсор умер после условия
    v.append(1)                       // можно
}
let r = &read loadValues()[0]         // ошибка: значение умирает в конце инструкции
print(r)                              // подсказка: let values = loadValues(); let r = &read values[0]
```

## Итератор как область

```text
область 1: функция, владеет коллекцией v
└─ область 2: цикл, курсор держит право на v
   └─ область 3: итерация, тело получает текущий элемент
```

Курсор держит право на коллекцию. На каждой итерации он **одалживает** телу текущий элемент.

**Правило.** Пока курсор жив, коллекция закрыта для смены структуры через сам объект: удалять и
добавлять можно только через курсор, потому что операция над объектом — это операция над внешней
областью, а не над областью обхода. Компилятор проверяет отношение между областями: операцию через
объект он разрешает, если по сводке она не задевает места, на которые смотрит курсор, или задевает их
без конфликта по таблице совместимости. Что запрещено мимо курсора, который сам меняет структуру
(виды 3, 4, 5 и 7), следует из того, какие части источника он держит (см. [правило об
опустошающем курсоре](#итератор-как-структура-edmond-2026-10-21)); отдельного списка исключительных
видов нет.

```efen
for item in doc.items.reading() {
    doc.tags.append(item.id)     // можно: tags не пересекается с областью обхода items
    doc.items.append(item)       // ошибка: append может перенести буфер items, курсор смотрит в него
}
```

**Правило.** Обход и срез изменяемого источника держат его в `edit` (см.
[Коллекции](collections.md#контракты-обхода), [циклы](../blocks/loops.md#итерация-с-модификацией)).
Пока такой обход идёт, тело может читать коллекцию заново (`v.count`, `v[i]`), но не может сменить её
структуру.

Ссылка, которая ушла из области 3 дальше итерации, проверяется общим правилом: пока ничто не
уничтожает и не перемещает её слот, она годна.

### Виды итераторов (предложение)

| # | Вид | Право курсора | Доступ к коллекции мимо курсора (выводится) |
|---|---|---|---|
| 1 | только чтение | чтение | чтение |
| 2 | правка значений | правка | чтение и правка |
| 3 | удалить текущий, с отдачей владения | полное | только непересекающиеся пути |
| 4 | добавлять через курсор (`cursor.append(x)`), обход видит новые элементы | полное | только непересекающиеся пути |
| 5 | любое изменение через курсор (`insert`, `remove`, `sort`); курсор сам поправляет позицию | полное | только непересекающиеся пути |
| 6 | потребляющий, `for x in take v` | `own` всей коллекции | коллекции больше нет |
| 7 | опустошающий | полное, коллекция остаётся пустой | только непересекающиеся пути |
| 8 | по снимку | чтение копии | любой |
| 9 | по индексу | чтение слота коллекции (указатель на буфер, длина) и номер элемента | любой; ссылка на текущий элемент умирает при смене структуры |

«Только непересекающиеся пути» в таблице — вывод для курсора, который держит все элементы, а не
отдельное правило (агент, по замечанию критика 2026-10-21). В массиве удаление через курсор идёт
сжатием, и между итерациями часть слотов уже сдвинута; обращение к элементам `v` мимо курсора увидело
бы пустые или чужие слоты, а `v.count` элементов не читает. По той же причине в коллекциях, где удаление или добавление перемещает слоты, ссылка на
текущий элемент живёт одну итерацию: следующий `next()` после удаления сдвигает элементы.

**Правило.** Обход с добавлением идёт до живого конца: элементы, добавленные во время обхода, он
тоже посетит. Так работают очередь задач и обход графа в ширину.

**Правило.** Итератор по индексу (вид 9) держит не буфер, а слот самой коллекции только для чтения и
номер текущего элемента. На каждом шаге он заново читает указатель на буфер и сравнивает номер с
живой длиной, поэтому коллекция может менять свою структуру, а перевыделение итератору не мешает.
Конфликт остаётся только у ссылки на текущий элемент: она смотрит в буфер.

```efen
for item in queue.byIndex() {
    let next = item.childId      // Int копируется, ссылки в буфер не остаётся
    queue.append(Task(next))     // можно: итератор держит номер, а не буфер
    // print(item.name)          // ошибка: append мог перенести буфер, item умер
}
```

Вид 5 доказуем без поддержки во время выполнения: пока курсор держит элементы, структуру меняет только
он, а каждая его операция сама поправляет позицию. Позиция — номер, а не адрес, поэтому ошибка в коде
курсора уводит обход не туда, но память не портит. Вариант, где объект сам меняется мимо курсора и
обновляет все живые итераторы, возможен только через layout: итераторы входят в структуру объекта,
а «позиция каждого живого итератора верна» — инвариант структуры (см.
[план доказательств](../memory/viper-proof-plan.md)).

Если тело бросает исключение посреди сжатия, курсор при уничтожении заканчивает сжатие, и каждый
элемент уничтожается ровно один раз.

**Правило удаления при обходе.** `remove` — метод только курсора. Он получает ссылку на текущий
элемент, которую выдал этот же курсор, и забирает его слот окончательно, через `take`. После вызова
слот мёртв: ни переменной цикла, ни ссылками, взятыми из неё, пользоваться нельзя. Удаление — это уход
слота из структуры, как передача в `own`-параметр. `remove` возвращает `own T`; если результат никто
не забрал, элемент уничтожается в конце инструкции.

```efen
for item in items.removing() as cursor {
    if item.dead {
        let body = cursor.remove(take item)   // слот item забран, элемент теперь у body
        // print(item.hp)                     // ошибка: слот item удалён
        // items.remove(0)                    // ошибка: items закрыта, пока жив cursor
    }
}
```

Компилятор проверяет, что в `remove` передан текущий элемент этого курсора: элемент взят из курсора, а
другого доступа к коллекции, пока курсор жив, нет. Элемент
другого обхода или прошлой итерации не подойдёт. `remove` убивает все ссылки с этим origin, в том числе
копии ссылки (`let a = item`), поэтому второй `remove` того же элемента — ошибка. После удаления обход
продолжается со следующего элемента без пропуска; это обязанность курсора.

Запись `as cursor` даёт имя курсору цикла `for` (предлагаемый синтаксис). Без неё курсор пишут явно:

```efen
let cursor = items.removing()
while let item = cursor.next() {
    if item.dead { cursor.remove(take item) }
}
```

Простой фильтр без обхода пишут через `retain` или `filter`; курсор нужен, когда тело делает с
удалённым элементом что-то ещё.

### Как автор коллекции описывает области

Отдельного синтаксиса не нужно. Автор даёт по курсору на каждое право, и `for` выбирает подходящий
по полному типу и правам источника (см. [Коллекции](collections.md#контракты-обхода)). Права
параметров объявляет сигнатура (см. [Ownership](ownership.md#параметры)), поэтому курсор с удалением —
отдельная операция с `mut`, а не «условная запись».

Курсор связан с коллекцией параметром-памятью, как указатель layout со своим экземпляром:

```efen
class Vector<T> {
    fn reading() -> ReadCursor<T, self>        // для чтения, self только читается
    fn editing(self: edit) -> EditCursor<T, self>
    fn removing(self: mut) -> RemoveCursor<T, self>
}
```

Запись режима для `self` в этом примере условная.

### Курсор без результата-ссылки

До 2026-10-26 курсор отдавал элемент результатом-ссылкой: `fn next() -> &edit<Mem> T?`, у курсора с
удалением — `&edit<self> T?` и `fn remove(take item: &edit<self> T) -> own T`. Результат-ссылка теперь
запрещён ([ownership](ownership.md#ссылки-только-внутри-функции)). Тело `for` — скрытое замыкание, а
элемент — место, которое курсор даёт этому телу с правом курсора; так уже устроены заголовки циклов
(Edmond, 2026-10-22). Как автор коллекции записывает такой курсор без результата-ссылки, пока не решено и
ждёт Edmond. Правила ниже о том, что курсор отдаёт и что убивает `remove`, остаются в силе.

## Итератор как структура (Edmond, 2026-10-21)

Итератор — не особая сущность, а обычная структура данных, и проверяется по общим правилам. Поля
итератора массива — указатели layout:

```efen
struct ArrayIter<T, Src: Origin> {
    current: Items.Position<Src>    // позиция в области Src.Items, может стоять за последним элементом
    left: Size                      // сколько элементов осталось; конец — current + left
}
```

**Правило (агент, по замечанию критика).** `Items.Item` — указатель на живой элемент, поэтому он не
может стоять за концом или быть пустым у пустого вектора (`root == null`). Поле `current` — позиция в
области; разыменование даёт `Items.Item` только при `left > 0`. Имя `Items.Position` условное.

**Правило (агент, по замечанию критика 2026-10-21).** Итератор хранит остаток `left`, а не размер:
конец `начало + size` требует начала области, которого в итераторе нет, а `current + left` его не
требует. Шаг обхода доказывается без решателя: инвариант `current + left == конец` линейный, шаг
`current + 1`, `left - 1` его сохраняет при условии `left > 0`.

**Правило.** Компилятор проверяет не код, а **отношения** между значениями: что на что указывает,
что из чего взято. Для `for x in v`:

```text
v ──владеет──▶ v.Items ◀──указывает в── it.current
                  ▲
                  └──── взят из слота ──── x
```

`x` связан со слотом, на который смотрел `current` в момент взятия, а не с самим `current`: сдвиг
итератора `x` не убивает (агент, по замечанию критика; так и в [Коллекциях](collections.md#чтение-и-обход)). Origin `<self>` у элемента берут только курсоры, которые сами перемещают слоты.

Операция проверяется по этой линии: смена структуры `v.Items` рвёт звено «указывает в», и вместе с
ним умирает всё, что ниже. Запись значения в слот звеньев не рвёт. Место, у которого с `v` нет
отношения, линию не задевает; есть ли отношение между двумя параметрами, решает правило о пересечении
аргументов выше.

**Правило.** Звено — не только указатель, но и факт, выведенный из структуры: длина, граница,
«элемент жив». Число `n`, снятое с `v.length`, держит факт `n == v.length`, и смена структуры
этот факт рвёт так же, как указатель. Факт — доказательное знание: смена структуры забывает
утверждение `n == v.length`, а само число `n` остаётся годным (агент). Так же и `left` у `ArrayIter`.
Если смена известна целиком, забывается только та половина факта, которую она ломает: `append`
длину только растит, и `n <= v.length` после него верно; `removeLast` только уменьшает, и верно
`v.length <= n` (агент, amber S47). Поэтому рабочий список `for i in 0..<v.length { v.append(…);
v[i..<i + 1] }` проходит проверку границ.

**Правило (агент, по замечанию критика).** Поле, которое называет условие layout (длина, ёмкость),
— поле структуры, даже если его тип ничем не владеет: под `edit` его писать нельзя, запись в него —
смена структуры, и пишет его только представление.

**Правило.** Тело `for` для компилятора — скрытое замыкание. Замыкания в коде нет, компилятор
выводит из тела права, как права обычного замыкания (см. [Замыкания](../closure.md#захват-переменных)).
Колбэк и тело цикла проверяются одинаково:

```efen
for item in &items { item.hp += 1 }
updateAll(items) => { item.hp += 1 }   // то же самое
```

Скрытое замыкание — единица только для сводки доступа: что тело делает с захваченными путями, пока
итератор держит свои данные. Перенос (`take`), инициализация и состояния проверяются на обычном графе
цикла: `take job` и `break` в теле, присваивание `let` внутри цикла работают как в обычном коде
(агент, по замечанию критика). Права захвата — `read`, `edit` и полное, как у параметров.

**Правило.** Что итератор позволяет телу, следует из его отношения с данными. Отдельной записи
«что разрешено телу» нет:

```efen
struct IndexIter<T, Src: Origin> {
    array: read<Src> Array<T>       // только слот самого вектора
    index: Size
}
```

- `ArrayIter` держит позицию внутри `Src.Items` через вызов тела, поэтому тело не может перемещать
  элементы `Src`.
- `IndexIter` держит слот вектора и число, поэтому тело может менять структуру `Src` как угодно.
  После вызова тела итератор обязан вычислить адрес заново: старые указатели и факты мертвы, и
  компилятор это проверяет. Обход идёт по позициям: элемент, вставленный перед текущим, будет посещён
  ещё раз; память при этом цела.

**Правило.** Итератор — стратегия (Edmond). Контракт выбирает заголовок цикла, тело итератор не
выбирает, а только проверяется (Edmond, 2026-10-21: «заголовок — это красивее»):

| Заголовок | Контракт | Тело может |
|---|---|---|
| `for x in v` | `Iterable` | читать |
| `for x in &v` | `EditIterable` | писать значения |
| `for x in mut v` | `MutIterable` | менять структуру `v` |
| `for x in take v` | `Consuming` | забирать элементы |

Имена контрактов условные. У типа одна активная стратегия на контракт; действуют [правила выбора
стратегий](../strategies.md#правила-выбора-стратегии): две подходящие стратегии одного приоритета —
конфликт, автор коллекции задаёт выбор через `Resolve<Contract>`, стратегия из пакета-зависимости
включается через `provide`. Обобщённый код называет контракт: `fn dropOdd<C: MutIterable>(c: mut C)`.
Если тело делает то, чего контракт заголовка не позволяет, это ошибка. Каждая реализация
`MutIterable` описывает, что значит позиция: у вектора — номер, у списка — узел, который умирает
вместе с узлом.

**Правило.** Менять структуру источника во время обхода тело может только в обходе `for x in mut v`
(Edmond). Заголовок цикла называет режим источника:

```efen
for n in numbers { ... }          // тело не меняет структуру numbers
for n in &numbers { n *= 2 }      // правка значений
for n in mut numbers {            // тело может менять структуру: обход по позициям
    if n % 2 == 0 { numbers.remove(at: numbers.firstIndex(of: n)!) }
}
for n in take numbers { ... }     // потребление
```

Без `mut` тело, которое удаляет или добавляет мимо курсора, — ошибка с подсказкой: написать
`mut` или удалять через курсор. Обход, мимо которого меняют структуру, идёт по позициям, а не по
элементам, и программист говорит об этом в заголовке; молча `for` такой обход не выбирает.

**Правило (Edmond, 2026-10-21).** Итератор объявляет, какие части источника он держит, например
только элементы `Src.Items`. Тело может обращаться ко всему, чего эти части не касаются; компилятор
выводит это из прототипов и сводок вызываемых функций:

```efen
for job in queue.draining() {     // курсор держит элементы queue, между шагами в них пустые слоты
    print(queue.count)            // можно: count читает длину, а не элементы
    print(queue[0].name)          // ошибка: обращение к элементам, которые держит курсор
}
```

Курсор, который оставляет между шагами открытое условие layout (опустошающий: пустые слоты),
держит его только на объявленной части, и закрывает его `exit` на любом выходе из цикла (см.
[исключение в адресах](../memory/addresses.md)). Длину и другие поля, которые читает тело, курсор
поддерживает верными на каждом шаге. Запрет по номерам слотов («мимо курсора можно читать элементы,
которые он ещё не тронул») отложен. Автор курсора может обойтись без открытого условия: забрать буфер
себе при входе и вернуть в `exit`, оставив в источнике пустой, но целый вектор; тогда `queue[0]` в
теле — обращение к пустому вектору, а не ошибка компиляции.

**Правило (amber S65).** Добавлять во время обхода можно через сам курсор:
`cursor.append(x)`, так же как удалять через `cursor.remove(take item)`. Так пишется рабочий список,
например обход графа в ширину: обход идёт до живого конца и посетит добавленное, а `exit`
опустошающего курсора уничтожит и его остаток. Имя опустошающего курсора годится только для `append`:
его ручка достаёт до элементов, которые курсор держит. По той же причине имя курсора с удалением
годится только для `remove` и `append`, а замыкание не захватывает имя курсора.

`append` курсора — операция самого курсора, а не `append` коллекции: позади курсора слоты пусты или
сдвинуты, поэтому курсор пишет в живой конец, считает новый элемент в остаток обхода, после
перевыделения пересчитывает позицию и держит `count` верным на каждом шаге. Шаг опустошающего курсора
уменьшает `count`, и факт о длине, взятый до цикла, после шага не действует.

```efen
for job in queue.draining() as cursor {
    if job.depth > 0 {
        cursor.append(Job(depth: job.depth - 1))   // можно: добавляет сам курсор
    }
    queue.append(Job(depth: 0))                    // ошибка: мимо курсора
    run(take job)
}
```

У курсора с удалением текущий элемент — ссылка в буфер. Если `append` коллекции может перенести
элементы (`Vector`), ссылка умирает на `cursor.append`; если не переносит (связный список, вектор с
заранее зарезервированной областью), ссылка живёт дальше.

### Выход из цикла (Edmond, 2026-10-21)

**Правило.** Досрочный выход из цикла (`break`, `return`, исключение) разрешён для любого итератора
(Edmond). Что делать с остатком, решает итератор: если у него есть метод выхода, `for` вызывает его с
причиной, иначе работает обычный деструктор. Имена `exit` и `LoopExit` условные.

```efen
class DrainCursor<T, Src: Origin> {
    fn exit(self: mut, reason: LoopExit) {    // completed, broken или thrown
        if reason != .completed { /* уничтожить остаток */ }
    }
}
```

Опустошающий курсор уничтожает остаток, курсор с удалением сдвигает его к началу: выбор принадлежит
автору итератора, а не языку. Редкий итератор, которому досрочный выход недопустим, объявляет это
контрактом (имя `MustComplete` условное): тогда `break`, `return`, `break` и `continue` внешней
метки в теле — ошибка, а тело обязано не бросать.

**Правило (агент, по замечанию критика).**
- Выходы цикла: обычное завершение, `break`, `break метка`, `continue метка`, `return`, проброс ошибки
  (`try`), `throw`. Выход через внешнюю метку закрывает все внутренние циклы.
- `exit` вызываются от внутреннего цикла к внешнему, после вычисления возвращаемого значения; сводка
  `exit` применяется на этом выходе.
- `for` вызывает `exit`, только если владеет итератором: обход `for l in &lines` чужого итератора его
  не вызывает.
- `exit` не бросает исключений и восстанавливает условия layout: после него в буфере нет пустых
  слотов. Это доказывается, как любая операция представления.
- Отдельного метода входа нет: его роль выполняет конструктор итератора, который берёт право.
- Курсор, который добавляет при обходе (вид 4), — итератор, чьё отношение с данными позволяет телу
  менять структуру: он держит номер и пересчитывает адрес после тела (`byIndex()`, заголовок `mut v`).
  Курсор, который держит элементы, добавляет сам: `cursor.append(x)` (см. правило выше). Отдельного
  правила нет.

### Сохранённый колбэк (Edmond, 2026-10-21)

**Правило (Edmond, 2026-10-21).** Тип сохранённого колбэка может назвать, что колбэк заимствует и с
каким правом, а может не называть. Если не называет, колбэк ничего не заимствует: он владеет тем, что
захватил (копия, `take`, `capture`), и сохранить под таким типом замыкание с заимствованием — ошибка в месте
сохранения. Колбэк, который читает или меняет чужой слот, объявляет это в типе явно. Право и источник
пишутся после типа, как у параметров (`edit<items>` у `less` выше):

```efen
class Log {
    var handlers: Vector<@escaping () -> Void>                // колбэки ничего не заимствуют
}
class Bus<Mem: Origin> {
    var handlers: Vector<@escaping () -> Void mut<Mem>>       // колбэки могут менять память Mem
}

fn main() {
    var items: Vector<Item> = [Item(hp: 1), Item(hp: 2)]
    var orders: Vector<Order> = []
    var log = Log()
    var bus = Bus<items>()

    let total = items.count
    log.on(() -> Void { print(total) })               // можно: total скопирован
    log.on(() -> Void { print(items.count) })         // ошибка: Log не разрешает заимствовать items
    bus.on(() -> Void { items.append(Item(hp: 0)) })  // можно
    bus.on(() -> Void { orders.append(Order()) })     // ошибка: orders нет в Bus<items>

    for x in items {
        log.fire()                                    // можно
        bus.fire()                                    // ошибка: bus может сменить структуру items
    }
}
```

`Bus<items>` связывает значение `bus` со слотом `items`: `bus` не переживает этот слот, а вызов, который
по сводке вызывает колбэки, проверяется так, будто сам делает с `items` то, что разрешает тип колбэка.
Источник может быть набором: `Bus<items, orders>`. `on` проверяет, что каждый захват колбэка лежит
внутри `Mem` (агент, по замечанию критика).

**Правило (агент).** Для локальной переменной набор источников выводится: это объединение захватов
всех `bus.on(...)` в функции, и хватает `var bus = Bus()`. Явно `Bus<items>` пишут в поле другой
структуры и в типе сохранённого колбэка; у параметра и результата набор выводится в сводку, если не
записан (Edmond, 2026-10-22: публичная функция читается по сводке).

**Правило (2026-10-26).** Хранимых ссылок нет, поэтому прежнее правило (Edmond, 2026-10-22) о том, что
источник пишется в модификаторе ссылки (`&read<pool> Int`), и пример `Watch` с полем-ссылкой отменены.
Источник пишут у типа колбэка (`mut<Mem>`), у отношения параметров и в параметре-памяти структуры, как у
`Bus`.

### Запрет остальным выводится (Edmond, 2026-10-21)

**Правило.** Что запрещено остальным, пока право живо, не пишется: это следует из того, что делает
владелец права, из фактов и из открытых условий layout. Открытое условие (пустой слот у опустошающего
курсора, вынутый опорный элемент у сортировки) — звено, на которое опирается любое обращение к
источнику. Переход состояния рвёт факты о состоянии, которые держат другие ссылки. Отсутствие
пересечения для оптимизации компилятор видит сам. Вывод из тела работает у любой функции; у метода
контракта и у сохранённого колбэка запрет берётся из заголовка и типа (см.
[отношение между параметрами](#отношение-между-параметрами-edmond-2026-10-21) и [сохранённый
колбэк](#сохранённый-колбэк-edmond-2026-10-21)). Прецедент той же идеи с явной записью — права
ссылок Pony (deny capabilities, Clebsch и др., 2015) и rely-guarantee Джонса.

```efen
var data = [5, 3, 8, 1]
sort(data, (a: Int, b: Int) -> Bool {
    data[0] = 100          // ошибка: захват data пересекается с аргументом items,
    return a < b           // а sort вызывает less, пока держит вынутый элемент
})
```

Удержание вынутого элемента сводка Amber ещё не записывает (BACKLOG Amber).

**Правило.** Явная пометка у отношения параметра не запрещает, а разрешает пересечение с более
узким правом. Владелец права `mut` может выдать вызываемому им замыканию `edit` на ту же память:

```efen
fn sortLoose(items: mut Vector<Int>, less: (Int, Int) -> Bool edit<items>)
```

- В месте вызова захват `data` может пересекаться с `items`, но только в пределах `edit`: писать
  значения можно, менять структуру и указатели нельзя.
- Внутри `sortLoose` после каждого вызова `less` умирают факты о значениях `items`, и открытое окно
  вокруг `less` — ошибка; такая сортировка пишется обменами значений.
- Указатель на `items` замыкание этим не получает: доступ у него свой, через захват. Передать сам
  массив — обычный параметр прототипа: `(a: Int, b: Int, items: edit Vector<Int>) -> Bool`.

### Диапазон как цель права (Edmond, 2026-10-21)

**Правило.** Целью права может быть диапазон слотов: `&edit v[i..<j]`. Компилятор запоминает, из
каких переменных выведены границы, и доказывает, что диапазоны не пересекаются (Edmond):

```efen
let left = &edit v[0..<k]
let right = &edit v[k..<n]    // можно: граница одна и та же, k
let a = &edit v[i..<j]
let b = &edit v[p..<q]        // доказано j <= p или q <= i: проверки нет; иначе проверка при выполнении
```

**Правило (Edmond, 2026-10-22).** Пересечение пишущих диапазонов — ошибка, только если компилятор его
доказал: оба диапазона не пусты и каждый начинается раньше, чем кончается другой. Если не доказано ни
пересечение, ни непересечение, ошибки нет: программа сравнивает диапазоны при взятии второго и
останавливается, если они пересекаются. Цикл по пишущему диапазону, `for x in &edit v[a..<b]`, держит
свой диапазон всё время, пока выполняется тело, и проверяется так же, как `let`:

```efen
let a = &edit v[0..<4]
for x in &edit v[2..<6] { }        // ошибка: v[2] и v[3] в обоих
for x in &edit v[j..<v.count] { }  // про j ничего не известно: проверка при выполнении
for row in &edit rows[0..<2] {
    let head = &edit row[0..<2]    // можно: диапазон внутри текущего элемента цикла
}
```

**Правило.** Диапазон запоминает значения границ в момент взятия, а не переменные: после `i = i + 4`
ссылка по-прежнему покрывает прежние слоты, и переменную можно менять, пока ссылка жива, если
компилятор доказывает непересечение по запомненным значениям (Edmond). Условия на индексы
(`0 <= i <= j <= v.count`) проверяются при взятии; смена структуры `v` рвёт факт о длине и вместе с
ним право на диапазон.

**Правило (Edmond, 2026-10-22).** Компилятор старается доказать условия на индексы и у диапазона, и у
одиночного индекса `v[i]` (`0 <= i < v.count`). Доказанное взятие обходится без проверки во время
выполнения. Недоказанное — не ошибка: программа проверяет индекс при выполнении и останавливается, если
он вне коллекции. «Компилятор старается не проверять диапазон каждый раз. Но если доказать нельзя, он
это делает» (Edmond).

```efen
for i in 0..<v.count {
    total = total + v[i]          // доказано: проверки нет
}
let mid = (low + high) / 2
if v[mid] == x { … }              // деление не доказать: проверка при выполнении
while i < v.count && v[i] > 0 {   // доказано: правая часть `&&` выполняется, только если левая верна
    i = i + 1
}
```

```efen
var i = 0
while i + 4 <= v.count {
    let chunk = &edit v[i..<i + 4]
    i = i + 4                     // можно: chunk остаётся на прежних слотах
    process(chunk)
}
```

**Правило (Edmond, 2026-10-21).** Два диапазона на запись (`edit` или полное право), которые
пересекаются, — всегда ошибка, даже два `edit`:

```efen
let a = &edit v[0..<4]
let b = &edit v[2..<6]    // ошибка: v[2] и v[3] в обоих диапазонах
```

Диапазоны только для чтения пересекаться могут (агент). Одиночные ссылки строже не становятся: две
ссылки `&edit` на один слот по-прежнему допустимы.

**Правило (агент).** Если непересечение не доказано, это ошибка, как любое недоказанное свойство, от
которого зависит безопасность (см. [адреса](../memory/addresses.md)). Условия на индексы под это
правило больше не подпадают: их недоказанность стоит проверки во время выполнения (см. выше).
Разрезание `v.split(at: k)` остаётся библиотечным способом получить две части с разными origin без
арифметики в месте вызова.

### Мысли для дальнейшего (обсуждение 2026-10-21, не решено)

- **Право — тройка.** Что делаю, над чем (origin: значение, поле, часть layout, один слот, диапазон,
  другая структура) и что запрещено остальным. Действия по операциям дескриптора: иметь указатель и
  сравнивать; читать указатель (идти по `next`); читать значение; писать значение; переписать указатель
  структуры (перецепить узел); создать слот; забрать элемент из множества; уничтожить слот на месте;
  переместить слоты физически; уничтожить весь экземпляр; временно нарушить условие layout. Сейчас
  `mut` — мешок из пяти таких прав; сводка знает, какие операции дескриптора делает функция, поэтому
  разложить `mut` можно выводом, без новых слов. Список собран Edmond и агентом.
- **Право на сохранение.** Право взять указатель на элемент через особую функцию и сохранить его
  дольше итерации (Edmond, гипотетически).
- **Необязательный блок `layout`** (Edmond). Структура, поле которой имеет тип `Items.Item` или
  `Items.Area`, уже входит в layout, поэтому границу layout задают типы указателей, а не блок.
  Выводится: состав структур, экземпляр (владелец `own Items.Area`), условия на полях. Не выводится
  без потерь вид дескриптора (`area` или `set`): от него зависит, перемещает ли `append` элементы.
  Явной остаётся одна строка `area Items: T` в теле типа или `representation` (предложение агента,
  Edmond согласен 2026-10-21; детали — при проектировании layout). Членом layout делает только
  неквалифицированный `Items.Item` внутри типа, который объявляет `area Items`; указатель
  `Items.Position<Src>` или `v.Items.Item` во внешнем итераторе — внешний (агент, по замечанию
  критика).
- **Вывод origin у структур с указателями layout** (предложение Мудреца после разбора Goose,
  2026-10-22). Внутри пакета origin-параметр не пишется, а выводится тремя правилами: из конструктора
  (`ArrayIter(current: v.Items.first, left: v.count)` даёт `Src = v`); у локального значения без
  origin — объединение всех записей в него, как у `Bus`; сводка функции помнит, что параметр-хранитель
  получил источник другого параметра (`register(bus, items)`), иначе источник теряется на вызове.
  Публичная функция читается так же, по сводке (Edmond, 2026-10-22). Опустошение (`refs = []`) снимает прежние источники до следующей
  записи.
- **Часть layout.** Итератор, чьи поля — указатели layout, живёт снаружи и цены во время выполнения
  не имеет. Экземпляр, который сам знает свои живые итераторы и поправляет их, — отдельный случай
  (см. вид 5 выше).

## Аксессоры и колбэки (предложение)

Итератор — частный случай. **Аксессор** — значение, которое держит область с определённым правом и
открывает наружу только безопасные операции: запись словаря, две половины массива (`split`),
редактор графа, пакетная правка. Правила областей проверяют код, который пользуется аксессором;
операции самого аксессора проверяет тот же анализ или, если они работают с памятью напрямую,
доказательство условий layout.

Колбэк без `@escaping` — тоже область: его нельзя сохранить, поэтому выданное право не утечёт (см.
[Замыкания](../closure.md#сохранение-замыкания-после-вызова)).

```efen
fn updateAll(values: mut Vector<Item>, action: (&edit Item) -> Void)

updateAll(items) => {
    item.hp += 1             // можно
    // items.append(...)     // ошибка: items держит область updateAll
}
```

Захват проверяется по пути, как ещё один аргумент вызова (см. правило о пересечении аргументов
выше). Колбэк, который захватил `items` и меняет его структуру, пересекается с аргументом `values`:
ошибка. Если колбэк захватил `self` и вызывает `self.spawn()`, который по сводке меняет структуру
`self.items`, это ошибка, пока `updateAll` держит `self.items`. Вызов метода, который трогает только
другое поле, допустим.

## Ссылка на элемент структуры

Указатель на элемент конкретного набора записывается так же, как в layout: `Items.Item` (см.
[Адреса и дескрипторы](../memory/addresses.md)). Такой указатель помнит и набор, и экземпляр, и
указатель на элемент другой структуры с ним несовместим.

**Правило.** Обычный код называет набор конкретного объекта путём к месту, как в origin:

```efen
fn connect(g: &Graph, from: g.Nodes.Node, to: g.Nodes.Node)
```

Узел другого графа сюда не подойдёт. Запись `Graph.Nodes.Node` (узел любого графа) не вводится:
перепутанный экземпляр ловился бы только во время выполнения. Путь в такой записи начинается с
неизменяемого имени: `let`, параметра или параметра-памяти. Путь через индекс или `var`
(`graphs[i].Nodes.Node`) не допускается, потому что он может назвать другой экземпляр.

**Правило (Edmond, 2026-10-22).** Указатель layout всегда называет ровно один экземпляр. Указатели
разных экземпляров — разные типы, и значение, которое по разным путям получает указатель то одного,
то другого экземпляра, — ошибка типа. Набор источников бывает только у ссылки в теле функции: ею можно
читать и писать, но операции идентичности (`remove(node)`, `cursor.remove`, членство в наборе) её не
принимают.

```efen
let g1 = Graph()
let g2 = Graph()
let n = if c { g1.Nodes.first } else { g2.Nodes.first }   // ошибка: g1.Nodes.Node и g2.Nodes.Node — разные типы
let r = if c { &g1.Nodes.first } else { &g2.Nodes.first }   // можно: источники {g1, g2}
r.weight = 1                                               // можно
g1.remove(r)                                               // ошибка: remove ждёт g1.Nodes.Node
```

Поэтому анализу не нужно помнить, указывает ли значение точно в один экземпляр: это говорит тип.
Выбирать между экземплярами можно на уровне экземпляра: `let g = if c { g1 } else { g2 }`, затем
`g.Nodes.first` и `g.remove(n)`. Открыто (агент): контейнер с узлами разных экземпляров требует пары
с зависимым типом поля (экземпляр и его узел; ссылкой поле экземпляра быть не может), а перенос узла между
экземплярами — отдельной операции с `take`, не присваивания указателя.
Прецедент с обратным выбором — Goose (набор корней у каждой ссылки, операции идентичности требуют
единственного точного корня; разбор 2026-10-22).

## Одна модель с layout

Области доступа и [layout](../memory/addresses.md) описывают одно и то же с двух сторон: layout
объявляет места памяти и операции над ними, области доступа говорят, кто и когда этими местами
пользуется. Понятия совпадают один к одному:

| Области доступа | layout |
|---|---|
| слот | место: элемент дескриптора (`set`, `one`, `area`), поле структуры; локальные переменные функции — неявный `one` её кадра |
| структура значения | дескрипторы экземпляра, их места и адреса, вместе со всем, чем владеют элементы |
| смена структуры | операция дескриптора: `allocate` создаёт место, `free` и `extract` уничтожают или опустошают, `reallocateArea` и `move` перемещают |
| запись значения | запись поля найденного элемента при `write`-праве на layout; не операция дескриптора |
| origin `<v>`, `<doc.title>` | происхождение указателя из дескриптора и экземпляра layout (`addresses.md`, «Производные типы дескриптора») |
| ссылка на элемент | `Items.Item` |
| таблица совместимости | «живое заимствование блокирует удаление элемента, перемещение его физического места и уничтожение экземпляра layout» (`addresses.md`, «Владение, живость и доступ») |
| правка (`edit`) | `write` на поля элементов, которые ничем не владеют, без права вызывать операции дескриптора и писать поля-указатели (`Items.Item`, `Items.Area`) |
| `split` | подобласти над непересекающимися местами одного дескриптора: разные ячейки `area`, разные элементы `set` |
| окно, где условие layout временно нарушено | область с исключительным полным правом: до её конца нельзя вызвать код, способный обратиться к структуре, и опубликовать ссылку (`addresses.md`, «Декларативные условия») |
| скрытые `managed`-слоты layout | внутренние места, недоступные внешним областям; публичная ссылка сохраняет origin |

Отсюда два следствия.

**Действия полного права выводятся из операций дескриптора.** «Удалить текущий» — `free` или
`extract` одного элемента. «Добавить» для `set` — `allocate`, старые места на месте; для `area` — ещё
и `reallocateArea`, то есть перемещение всех мест. Поэтому `append` связного списка и `append`
вектора имеют разные сводки, и это видно из их layout, а не из отдельной пометки.

**Две проверки, одна теория.** Внутри representation операции над дескрипторами доказывает
компилятор, вместе с условиями layout (см. [план доказательств](../memory/viper-proof-plan.md)).
Результат доказательства — сводка операции: какие места она создаёт, уничтожает и перемещает. Код
снаружи, который пользуется коллекцией, проверяется по этим сводкам правилами областей, без
доказательства. Права с долями, на которых построен Viper, — та же таблица совместимости.

### Рост без перемещения (Edmond, 2026-10-22)

Сводка метода коллекции выводится формально из кода, по худшему пути, из четырёх действий с памятью
указателя layout:

| действие | что делает | что со ссылками |
|---|---|---|
| `allocate` | выделяет новые места: новая область, узел, страницы внутри резерва; существующие места не двигает | живут |
| `move` | перемещает значение места в другое место | на старое место и на всё, что лежит прямо внутри него, умирают; на память, которой место владеет через указатель, живут |
| `free` | уничтожает место или область; запись поверх владеющего поля — уничтожение старого значения по сводке его деструктора | умирают ссылки, сохранённые указатели layout и факты об этом месте |
| `take` | память ушла из дерева владения экземпляра: `take`, `replace`, `swap` | через прежнего хозяина умирают |

`take` считается по итогу, а не по тексту: смотрится, где память оказалась к точке, где на неё может
посмотреть внешний код (возврат, вызов, публикация ссылки). Ушла из экземпляра — `take`; вернулась в
ту же структуру — перепривязка (вставка узла списка через `item.next = take self.head`). Перепривязка
не относится ни к одному из четырёх: это запись указателя, она требует `mut` и запрещена `edit`,
ссылки живут. `self.head = null` — `free` узлов, а не перепривязка. `move` требует `Movable`;
значение со смещениями от самого себя не `Movable`.

На дне — примитивы без тела с одним контрактом на все платформы, реализация у каждой своя (`mmap`,
`VirtualAlloc`, `memory.grow`, свой аллокатор). Единица — элемент, а не страница:

| примитив | действие |
|---|---|
| `reserve` | диапазон адресов, мест ещё нет |
| `commit`, `Items.allocate`, `Items.allocateArea` | `allocate` |
| `Items.initialize` | запись значения в пустое место |
| `Items.at` | ничего: адрес места |
| `Items.move` | `move` |
| `Items.extract` | забирает значение, место пусто: ссылки на него умирают, память, которой значение владеет, уходит вместе с ним (`take`) |
| `Items.free`, `decommit`, `release` | `free` |

`reallocateArea` и рост на месте — код на Efen поверх них, их сводки тоже выводятся.

```efen
public fn append(value: own Target) {        // обычный вектор
    reserve(self.length + 1)                 // → reallocateArea: allocate + move + free → ссылки умирают
    ...
}

public fn append(value: own Target) {        // коллекция с заранее зарезервированной областью (Goose)
    Items.commit(self.root, count: self.length + 1)   // allocate: ничего не перемещается → ссылки живут
    ...
}
```

Обещание «область не переедет» записывается без нового слова: поле-указатель layout объявляется
`let` (Edmond, 2026-10-22). Его задаёт только конструктор, после этого значение указателя не меняется,
пока жив экземпляр, и область остаётся на своём адресе. Это проверяется по коду: запись в поле после
конструктора (`reallocateArea(&self.root, ...)`, `swap`, `take`) — ошибка компиляции в коде коллекции,
а не у её пользователей. Перемещения элементов внутри области (`Items.move`, `extract` и `initialize`
на другом месте) `let` не запрещает: ссылки на эти места умирают по выводу, на остальные живут.

```efen
layout {
    struct Self {
        let root: own Items.Area          // выделяется и резервируется в конструкторе
        var length: Size
    }
}

public fn append(value: own Target) {
    Items.commit(self.root, count: self.length + 1)   // поле не меняется: можно
    ...
}
```

Снаружи коллекции эти слова не видны: пользователь пишет `mut` и `edit`, а вызывающий читает выведенную
сводку метода.

Когда резерв исчерпан или памяти нет, операция аллокатора бросает `AllocationError` или, в виде
`try…`, возвращает `null` (`false`), и ничего не меняется (`../memory/allocator.md`, Edmond 2026-10-22).

Режимы отказа платформ — в `../memory/allocator.md`; рост на месте в модели доказательств сохраняет
epoch (`viper-proof-model.md` §4.8a). Открыто: generic-код (`C: Collection`) видит худший случай. Позже: сводка с условием
(«перемещает, только если `count == capacity`») и какие именно места перемещает `insert`. Разбор:
критик и мудрец Amber S39.2.

Курсор обхода на языке layout — указатель `Items.Item` на текущий элемент плюс право области на
`Items`; удаление через курсор — `Items.free` или `Items.extract` этого элемента.

## Промежуточные области

Когда двум областям нужно одно сильное право, его разводит третья:

- передача права параметру и возврат после вызова;
- отложенные операции: собрать, что удалить или добавить, применить после обхода;
- кладбище удалённых: элемент исключён, память живёт до конца внешней области, ссылки годны;
- надгробия: элемент помечен мёртвым, обход его пропускает, сжатие потом.

## Задачи `spawn`

Решение Edmond (2026-10-26): задача вносит в проверку областей новый элемент —
поток выполнения со своими областями. Компилятор знает, где поток стартует
(`spawn`, `background`), где стоит (точки ожидания), где сливается с создателем
(слот завершения) и где кончается в любом случае: конец блока асинхронного
контекста — точка схождения всех его задач (см.
[Асинхронный контекст](../context-and-effects.md#асинхронный-контекст)).

Области задачи выводятся из её тела, как у замыкания (см.
[Аксессоры и колбэки](#аксессоры-и-колбэки-предложение)), и держатся от запуска
до слота завершения (в том числе `cancel()`) или выхода из блока дескриптора, а
для фоновой задачи — до конца блока `with` (агент).
Жизнь места проверяется отдельно и жёстко (см.
[Замыкания](../closure.md#что-задача-может-взять)). Сводка функции, которая
оставляет задачу работать дольше себя, называет области этой задачи, её
исключения и места, которые она держит; вызывающий сверяет их со своим кодом до
конца своего блока `with` (агент).

**Многопоточный контекст.** На всём отрезке жизни задачи её доступ и доступ
любого другого кода (создателя, других задач того же отрезка) считаются
одновременными (Edmond, 2026-10-26):

| задача \ другой код | чтение | правка | смена структуры | переход состояния |
|---|---|---|---|---|
| чтение | можно | нельзя | нельзя | нельзя |
| правка | нельзя | нельзя | нельзя | нельзя |
| смена структуры | нельзя | нельзя | нельзя | нельзя |
| переход состояния | нельзя | нельзя | нельзя | нельзя |

Правило «две пишущие области допустимы» здесь не действует: оно держится на
том, что записи идут по очереди, а в разных потоках это не доказано. Столбец
перехода состояния добавил агент по [Типам-состояниям](typestate.md): переход
через общий доступ требует синхронизации.

```efen
fn refresh(stats: &Stats, values: [Int]) {
    with makeTaskGroup() {                              // MultiThreadConcurrency
        let low = spawn { stats.min = minimum(values) }
        let n = values.count     // можно: обе стороны читают values
        stats.min = 0            // ошибка: задача может писать в stats.min
        print(stats.min)         // ошибка: задача может писать в stats.min
        await(low)
        stats.min += 1           // можно: задача закончилась
    }
}
```

Решил агент:

- один литерал `spawn` в цикле даёт много задач, и они сверяются друг с другом.
  `out[i]` в разных задачах допустим, только если различие индексов доказано, как
  для двух областей в одном потоке; недоказанное пересечение — ошибка;
- слоты под ARC (`managed`) таблица не видит, поэтому многопоточная задача их не
  берёт, пока не спроектировано право `shared`. По той же причине многопоточная
  задача пока не может писать в общий контекст, например `%logger`, и запускать
  задачи в свой контекст: запуск меняет группу задач;
- внутри функции параметры — разные места, поэтому сводка функции называет пары
  параметров, которые её задачи и её код трогают одновременно; вызывающий
  сверяет аргументы этих пар по таблице многопоточного вида. Колбэк, вызванный
  из задачи, пока функция пишет в другой параметр, с аргументом, который этот
  колбэк пишет, — ошибка у вызывающего. В однопоточном контексте сводка так же
  называет параметры, структуру которых задачи меняют в точках ожидания
  функции;
- значение, привязанное к потоку, нельзя передать в многопоточную задачу без
  права `shared` (см. [Ownership](ownership.md#ссылка-не-покидает-функцию)).

**Однопоточный контекст.** Задачи идут в одном потоке по очереди (Edmond,
2026-10-26): в потоке создателя и только в его точках ожидания (агент). Между ними код
выполняется один, и действует таблица [совместимости](#совместимость) для
одного потока: записи значений допустимы. В каждой точке ожидания компилятор
считает, что выполнилось всё, что по своим сводкам делают живые задачи, как при
вызове функции с такой сводкой. Смена структуры в задаче убивает области,
которые код держит через эту точку; переход состояния в задаче убивает факты о
состоянии (агент). Точка ожидания — вызов слота ожидания: функции, которая останавливает текущую
корутину ради чего-то (другой корутины, ввода-вывода, таймера), прямо или через
вложенные вызовы. Асинхронность прозрачная, и компилятор знает такие функции по
всей программе (Edmond, 2026-10-26).

```efen
with makeLocalTasks() {                            // SingleThreadConcurrency
    background { stats.items.append(1) }           // смена структуры items
    stats.count = 0              // можно: один поток, запись не уничтожает слот

    for item in stats.items {    // обход держит items
        log(item)                // ошибка: log пишет в файл, это точка ожидания,
    }                            // здесь может выполниться append
}
```

Запуск (`spawn`, `background`) сам не точка ожидания: тело новой задачи начинает
выполняться в ближайшей точке ожидания создателя (агент).

Проверка симметрична (агент): задача, которая держит область через свою точку
ожидания, сверяется с кодом создателя и других задач, который может выполниться
в это время.

Открыто: право `shared` (общая запись через атомарные операции и блокировки,
логирование и распределитель памяти в многопоточных задачах).

## Границы

Правила выводятся из кода. Безопасность, которая зависит от значений, требует проверки во время
выполнения или доказательства условий layout (см. [план доказательств](../memory/viper-proof-plan.md)):

- `&cells[i]` и `take cells[j]` при `i != j`;
- удаление узла списка мимо курсора, если узел не текущий и не следующий;
- удаление узла графа, на который не осталось рёбер;
- завершение обхода графа без циклов.

## Что решено 2026-10-20

| Вопрос | Решение |
|---|---|
| Как удалять при обходе | только `cursor.remove(take item)`; слот после вызова мёртв (Edmond) |
| Можно ли менять коллекцию мимо курсора | нет, кроме операций, которые не задевают область курсора или задевают её без конфликта; курсор, меняющий структуру, допускает только непересекающиеся пути (Edmond, уточнение агента) |
| Видит ли обход добавленные элементы | да, обход идёт до живого конца; итератор по индексу видит их по природе (Edmond) |
| Любое изменение при обходе | через курсор без цены во время выполнения; объект, который сам обновляет итераторы, — только через layout (Edmond) |
| Один читает, другой пишет | допустимо в одном потоке (Edmond) |
| Что исключает `mut` | ничего: другие ссылки умирают только при смене структуры; аргументы по умолчанию не пересекаются (Edmond, 2026-10-26) |
| Как назвать набор чужой структуры | путь к месту, `g.Nodes.Node` (агент, по правилу origin) |
| Когда умирает временное значение | в конце инструкции, включая тело `for`/`if`/`match`/`while` (агент, по правилу слота блока) |

## Отложено до проектирования layout

- Права на отдельные ячейки (`split`) и правка внутренних указателей.
- Объект, который меняется мимо курсора и сам обновляет живые итераторы.
