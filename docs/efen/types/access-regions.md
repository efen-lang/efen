# Области доступа

[Документация](../README.md) · [Словарь](../glossary.md) · [Ownership](ownership.md) · [Коллекции](collections.md) · [Layout](../memory/addresses.md)

> Статус: проект спецификации (Edmond, 2026-10-20). Решённое помечено как правило, остальное — как
> предложение или открытый вопрос. Компилятор правила ещё не проверяет.

Безопасность ссылок в Efen сводится к одному вопросу: совместимы ли права всех участков кода, которые
в данной точке программы держат доступ к одной памяти. Такой участок называется **областью доступа**.
Области выводит компилятор; программист пишет режим доступа и origin только там, где нужен контракт.

## Понятия

| Понятие | Значение |
|---|---|
| **Слот** | Логическое место, где живёт значение: параметр, локальная переменная, результат вызова, элемент коллекции, поле. Ссылка указывает на слот, а не на имя (см. [Ownership](ownership.md#явное-извлечение)) |
| **Владелец** | Имя, которое отвечает за уничтожение слота. Владение передаётся только явно, через `take` |
| **Структура значения** | Слоты значения и всё, чем оно владеет, транзитивно: буфер строки, узлы списка, payload optional, `own`-поля, — вместе с их адресами |
| **Смена структуры** | Операция, которая создаёт, уничтожает или перемещает слоты структуры. Ссылку портит только уничтожение или перемещение её слота |
| **Область доступа** | Участок кода, где живо право на слоты: от взятия ссылки до её последнего использования на каждом пути. Это не блок `{ }`, а часть графа программы |
| **Договор области** | Память, на которую область держит право (origin), и само право (режим доступа) |

Владение и доступ — разные вещи. Итератор не владеет коллекцией: он берёт право доступа на время
своей области и возвращает его.

Слово «область» в Efen встречается в трёх смыслах, поэтому здесь оно всегда с уточнением: область
доступа (этот документ), лексический [`region`](../code-regions.md) с гарантиями на выходе и область
памяти layout (`Items.Area`, «перевыделение области»).

## Договор области записывается типом ссылки

| Часть области | Пример | Где записано |
|---|---|---|
| какая память | `values`, `doc.title` | origin в квадратных скобках |
| какое право | `read`, `edit`, полное | режим ссылки |
| на каком участке кода | от взятия до последнего использования | нигде: выводит компилятор |

```efen
fn first(values: &read Array<Int>) -> &read[values] Int
```

Тип `&read[values] Int` — договор: «держу `read` на память `values`». В каждой точке программы
компилятор сверяет живые договоры по таблице совместимости.

**Правило.** Origin может указывать путь внутрь места: поле или элемент. В скобках всегда место
(параметр, переменная, параметр-память), а не тип; типы в Efen пишутся с большой буквы, поэтому
`doc.title` и `Document` не путаются.

```efen
fn header(doc: &read Document) -> &read[doc.title] String
```

Смена структуры `doc.body` не трогает ссылку с origin `[doc.title]`.

## Права

| Право | Ссылка | Параметр | Разрешает |
|---|---|---|---|
| чтение | `&read T` | `T` | читать |
| правка | `&edit T` | `edit T` | писать значения в слоты, которые ничем не владеют; структуру не меняет |
| полное | `&T` | `mut T` | всё, включая смену структуры |

**Правило.** `edit` — режим доступа [Ownership](ownership.md#аспекты-владения), седьмого права он не
создаёт. `&T` даёт полное право, как `mut`.

**Правило (уточнение агента к решению Edmond «`edit` запрещает менять любые указатели структуры»).**
Структура транзитивна по владению. Под `edit` можно записать только слот, тип которого ничем не
владеет и не имеет вариантов: число, флаг, структуру из таких полей. Запись значения, которое
владеет памятью (строка, вложенный вектор, `own`-поле, optional, enum), уничтожает старую память и
считается сменой структуры старого значения. Ссылка, полученная через область `edit`, получает не
больше `edit`: право ссылки ограничено правом области, из которой она взята.

```efen
fn reset(rows: edit Vector<Vector<Int>>) {
    for row in &rows {
        row[0] = 0           // можно: Int ничем не владеет
        row.append(1)        // ошибка: row получил edit, append меняет структуру
        row = []             // ошибка: уничтожает старый буфер row
    }
}
```

В generic-коде запись `x = value` под `edit` допустима, только если про `T` известно, что он ничем
не владеет.

### Что делает полное право

Полное право — это всё, что сводка операции говорит о структуре. Удобные ступени между `edit` и
полным правом — не новые права, а то, какие слоты операция создаёт, уничтожает или перемещает:

| Действие | Что со слотами |
|---|---|
| удалить текущий элемент | уничтожается один слот; в массиве сдвигаются все после него |
| добавить | создаются новые слоты; в массиве при росте перемещаются все |
| произвольная смена | любые |

## Совместимость

| держит одна область \ хочет другая | чтение | правка | смена структуры |
|---|---|---|---|
| чтение | можно | можно | нельзя |
| правка | можно | можно | нельзя |
| смена структуры | нельзя | нельзя | нельзя |

Две пишущие области на одну память допустимы, как и две пишущие ссылки (см.
[Ownership](ownership.md#ссылки)): запись значения слот не уничтожает. Запрет даёт только смена
структуры, и только для тех слотов, которые она уничтожает или перемещает. Удаление узла списка не
трогает остальные узлы; удаление из массива сдвигает элементы после удалённого, и ссылки на них
умирают. Какие слоты затрагивает операция, говорит сводка функции.

Ссылки одного типа внутри функции могут указывать на одну память, поэтому проверка берёт худший
случай: смена структуры через одну такую ссылку убивает ссылки, взятые через другую.

```efen
fn f(p: &Doc, q: &Doc) {
    let t = &read p.title
    q.title = "x"            // смена структуры q.title: старый буфер строки уничтожен
    print(t)                 // ошибка: p и q могут быть одним документом
}
```

## Как компилятор выводит области

- Граница области — живость ссылки. Ссылка, которая больше не используется, не мешает смене структуры.
- Право области — из операций в ней и из сводок вызванных функций. Сводка помнит путь до поля
  (`self.items`), поэтому вызов метода, который меняет `self.cache`, не мешает обходу `self.items`.
- После ветвления ссылка указывает на множество слотов, и проверяется каждый.
- Вызов получает право области через параметр и возвращает его после вызова.

**Правило.** Слот переменной блока умирает вместе со своим последним владельцем, в конце блока.
Ссылка жизнь не продлевает, потому что ничем не владеет:

```efen
let fallback = makeItem()
let r: &Item
if ready() {
    let a = makeItem()
    r = &a
} else {
    r = &fallback
}
print(r)          // ошибка: слот a умер в конце блока if
```

Значение, которое должно пережить блок, отдают внешнему владельцу:

```efen
var chosen: Item? = null
if ready() {
    chosen = makeItem()
}
let r = if let item = chosen { &item } else { &fallback }
print(r)
```

## Итератор как область

```text
область 1: функция, владеет коллекцией v
└─ область 2: цикл, курсор держит право на v
   └─ область 3: итерация, тело получает текущий элемент
```

Курсор держит право на коллекцию. На каждой итерации он **одалживает** телу текущий элемент.

**Правило.** Обход и срез изменяемого источника держат его в `edit` (см.
[Коллекции](collections.md#контракты-обхода), [циклы](../blocks/loops.md#итерация-с-модификацией)).
Пока такой обход идёт, тело может читать коллекцию заново (`v.count`, `v[i]`), но не может сменить её
структуру.

Ссылка, которая ушла из области 3 дальше итерации, проверяется общим правилом: пока ничто не
уничтожает и не перемещает её слот, она годна.

### Виды итераторов (предложение)

| # | Вид | Право курсора | Доступ к коллекции мимо курсора |
|---|---|---|---|
| 1 | только чтение | чтение | чтение |
| 2 | правка значений | правка | чтение и правка |
| 3 | удалить текущий, с отдачей владения | полное | никакого |
| 4 | добавлять | полное | никакого |
| 5 | любое изменение | полное плюс поддержка во время выполнения | никакого |
| 6 | потребляющий, `for x in take v` | `own` всей коллекции | коллекции больше нет |
| 7 | опустошающий | полное, коллекция остаётся пустой | никакого |
| 8 | по снимку | чтение копии | любой |

Виды 3, 4, 5 и 7 держат коллекцию исключительно. Причина: в массиве удаление через курсор идёт
сжатием, и между итерациями часть слотов уже сдвинута; чтение `v` мимо курсора увидело бы пустые или
чужие слоты. По той же причине в коллекциях, где удаление или добавление перемещает слоты, ссылка на
текущий элемент живёт одну итерацию: следующий `next()` после удаления сдвигает элементы.

Если тело бросает исключение посреди сжатия, курсор при уничтожении заканчивает сжатие, и каждый
элемент уничтожается ровно один раз.

**Правило для удаления через курсор (предложение).** Удаление элемента из коллекции — это уход
слота из структуры, как передача в `own`-параметр, а не локальный `take`: ссылки на удалённый элемент
умирают, в том числе переменная цикла.

```efen
for x, cursor in items {
    if x.dead {
        let item = cursor.remove()   // элемент ушёл из items, владение у item
        // print(x)                  // ошибка: слот x покинул структуру
    }
}
```

Удалить при обходе другой элемент можно только через курсор: курсор помнит следующий элемент и
должен его поправить. Удаление мимо курсора зависит от значения («это не следующий элемент») и
относится к разделу «Границы».

### Как автор коллекции описывает области

Отдельного синтаксиса не нужно. Автор даёт по курсору на каждое право, и `for` выбирает подходящий
по полному типу и правам источника (см. [Коллекции](collections.md#контракты-обхода)). Права
параметров объявляет сигнатура (см. [Ownership](ownership.md#параметры)), поэтому курсор с удалением —
отдельная операция с `mut`, а не «условная запись».

Значение, внутри которого хранится ссылка, получает параметр-память (см.
[Ownership](ownership.md#хранимые-и-захваченные-ссылки)):

```efen
class Vector<T> {
    fn reading() -> ReadCursor<T, self>        // для чтения, self только читается
    fn editing(self: edit) -> EditCursor<T, self>
    fn removing(self: mut) -> RemoveCursor<T, self>
}

class EditCursor<T, Mem: Origin> {
    fn next() -> &edit[Mem] T?     // ссылка в коллекцию, а не в курсор
}

class RemoveCursor<T, Mem: Origin> {
    fn next() -> &edit[Mem] T?     // живёт одну итерацию: удаление сдвигает элементы
    fn remove() -> own T           // сводка: текущий слот уходит из структуры Mem
}
```

Запись режима для `self` в этом примере условная.

## Аксессоры и колбэки (предложение)

Итератор — частный случай. **Аксессор** — значение, которое держит область с определённым правом и
открывает наружу только безопасные операции: запись словаря, две половины массива (`split`),
редактор графа, пакетная правка. Правила областей проверяют код, который пользуется аксессором;
операции самого аксессора проверяет тот же анализ или, если они работают с памятью напрямую,
доказательство условий layout.

Колбэк без `@escaping` — тоже область: его нельзя сохранить, поэтому выданное право не утечёт (см.
[Замыкания](../closure.md#сохранение-замыкания-после-вызова)).

```efen
fn updateAll(values: mut Vector<Item>, action: (&edit Item) -> Void)

updateAll(items) => {
    item.hp += 1             // можно
    // items.append(...)     // ошибка: items держит область updateAll
}
```

Захват проверяется по пути: если колбэк захватил `self` и вызывает `self.spawn()`, который по сводке
меняет структуру `self.items`, это ошибка, пока `updateAll` держит `self.items`. Вызов метода,
который трогает только другое поле, допустим.

## Ссылка на элемент структуры (предложение)

Указатель на элемент конкретного набора записывается так же, как в layout: `Items.Item` (см.
[Адреса и дескрипторы](../memory/addresses.md)). Такой указатель помнит и набор, и экземпляр, и
указатель на элемент другой структуры с ним несовместим. Открыто: как обычный код называет набор
чужой структуры (`a.Items.Item`) и как это сочетается с origin.

## Одна модель с layout

Области доступа и [layout](../memory/addresses.md) описывают одно и то же с двух сторон: layout
объявляет места памяти и операции над ними, области доступа говорят, кто и когда этими местами
пользуется. Понятия совпадают один к одному:

| Области доступа | layout |
|---|---|
| слот | место: элемент дескриптора (`set`, `one`, `area`), поле структуры; локальные переменные функции — неявный `one` её кадра |
| структура значения | дескрипторы экземпляра, их места и адреса, вместе со всем, чем владеют элементы |
| смена структуры | операция дескриптора: `allocate` создаёт место, `free` и `extract` уничтожают или опустошают, `reallocateArea` и `move` перемещают |
| запись значения | запись поля найденного элемента при `write`-праве на layout; не операция дескриптора |
| origin `[v]`, `[doc.title]` | происхождение указателя из дескриптора и экземпляра layout (`addresses.md`, «Производные типы дескриптора») |
| ссылка на элемент | `Items.Item` |
| таблица совместимости | «живое заимствование блокирует удаление элемента, перемещение его физического места и уничтожение экземпляра layout» (`addresses.md`, «Владение, живость и доступ») |
| правка (`edit`) | `write` на поля элементов, которые ничем не владеют, без права вызывать операции дескриптора и писать поля-указатели (`Items.Item`, `Items.Area`) |
| `split` | подобласти над непересекающимися местами одного дескриптора: разные ячейки `area`, разные элементы `set` |
| окно, где условие layout временно нарушено | область с исключительным полным правом: до её конца нельзя вызвать код, способный обратиться к структуре, и опубликовать ссылку (`addresses.md`, «Декларативные условия») |
| скрытые `managed`-слоты layout | внутренние места, недоступные внешним областям; публичная ссылка сохраняет origin |

Отсюда два следствия.

**Действия полного права выводятся из операций дескриптора.** «Удалить текущий» — `free` или
`extract` одного элемента. «Добавить» для `set` — `allocate`, старые места на месте; для `area` — ещё
и `reallocateArea`, то есть перемещение всех мест. Поэтому `append` связного списка и `append`
вектора имеют разные сводки, и это видно из их layout, а не из отдельной пометки.

**Две проверки, одна теория.** Внутри representation операции над дескрипторами доказывает
компилятор, вместе с условиями layout (см. [план доказательств](../memory/viper-proof-plan.md)).
Результат доказательства — сводка операции: какие места она создаёт, уничтожает и перемещает. Код
снаружи, который пользуется коллекцией, проверяется по этим сводкам правилами областей, без
доказательства. Права с долями, на которых построен Viper, — та же таблица совместимости.

Курсор обхода на языке layout — указатель `Items.Item` на текущий элемент плюс право области на
`Items`; удаление через курсор — `Items.free` или `Items.extract` этого элемента.

## Промежуточные области

Когда двум областям нужно одно сильное право, его разводит третья:

- передача права параметру и возврат после вызова;
- отложенные операции: собрать, что удалить или добавить, применить после обхода;
- кладбище удалённых: элемент исключён, память живёт до конца внешней области, ссылки годны;
- надгробия: элемент помечен мёртвым, обход его пропускает, сжатие потом.

## Границы

Правила выводятся из кода. Безопасность, которая зависит от значений, требует проверки во время
выполнения или доказательства условий layout (см. [план доказательств](../memory/viper-proof-plan.md)):

- `&cells[i]` и `take cells[j]` при `i != j`;
- удаление узла списка мимо курсора, если узел не текущий и не следующий;
- удаление узла графа, на который не осталось рёбер;
- завершение обхода графа без циклов.

## Открытые вопросы

1. Как удалять при обходе: `retain` как обычный путь и курсор с удалением для сложных случаев?
2. Видит ли обход с добавлением новые элементы: живой конец или снимок длины?
3. Нужен ли вид 5 в стандартной библиотеке, учитывая цену во время выполнения?
4. Как обычный код называет набор чужой структуры.
5. Права на отдельные ячейки (`split`) и правка внутренних указателей через layout.
6. Что именно исключает `mut`: только чужую смену структуры или и чужую запись? `mut` описан как
   «исключительный `write`», но две пишущие ссылки допустимы, а `&T` даёт полное право.
7. Когда умирает временное значение без имени: `let r = &read loadValues()[0]` — в конце инструкции
   (ошибка) или продлевается до конца блока, как в Rust?
