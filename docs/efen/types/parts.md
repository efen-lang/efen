# Части объекта

[Документация](../README.md) · [Словарь](../glossary.md) · [Области доступа](access-regions.md) · [Владение и доступ](ownership.md) · [Контракты](../contracts.md)

> Статус: проект спецификации, принят 2026-11-11. Amber частей не реализует.

Часть — имя, которым контракт или интерфейс называет память объекта, не зная его полей. Пометка метода говорит, структуру
каких частей он меняет, а реализация привязывает каждую часть к своим полям. По именам частей компилятор решает, какие
ссылки переживают вызов, тела которого он не видит.

```efen
contract Storage {
    layout { part items, cache }

    fn first -> read<self.items> Item?       // место из части items
    mut<self.cache> fn clearCache            // меняет структуру только части cache
    mut fn compact                           // может сменить структуру всего объекта
}

fn work<S: Storage>(s: mut S) {
    if let item = s.first() {
        s.clearCache()                       // можно: item взят из items, вызов меняет cache
        print(item.name)
        s.compact()                          // item больше не действует
    }
}
```

## Задача

Вызов функции с телом компилятор проверяет по её сводке, и сводка помнит путь до поля: метод, который меняет структуру
`self.cache`, не мешает ссылке в `self.items` ([как компилятор выводит области](access-regions.md#как-компилятор-выводит-области)).
У метода контракта и интерфейса тела нет, и вызывающий читает одну пометку
([доступ метода к self](../contracts.md#доступ-метода-к-self)). `mut fn` по пометке может сменить структуру всего объекта,
поэтому после его вызова умирает каждая ссылка внутрь объекта, даже если ни одна реализация её память не трогает.

Назвать в пометке поле контракт не может: полей у него нет, а требование свойства `var x: T { get set }` описывает
доступ и памяти не задаёт ([поля, которые требует контракт](../contracts.md#поля-которые-требует-контракт)). Части дают
контракту имена для памяти без самих полей.

## Объявление частей

**Правило.** Части объявляет строка `part` в блоке `layout { }` контракта или интерфейса. Имена перечисляются через
запятую:

```efen
contract Storage {
    layout { part items, cache }
}

interface Journal {
    layout { part entries, index }
}
```

- `part` — контекстное слово: вне `layout` это обычное имя.
- У части нет типа, значения и байт в объекте. Её читает только FLOW, как и поля `layout` контракта
  ([`layout` в теле класса](../memory/layout.md#layout-в-теле-класса)).
- Имя части не совпадает с именем поля `layout` и с именем требуемого свойства того же контракта: совпадение — ошибка.
- Интерфейс, созданный из контракта (`interface StorageInterface from Storage`), получает его части и пометки методов и
  ничего не повторяет.
- Одноимённые части разных предков контракта — ошибка в объявлении наследника. Один предок, достигнутый двумя путями,
  считается один раз, как и его требования ([наследование контрактов](../contracts.md#наследование-контрактов)).
- `part` в `shared layout` — ошибка.

**Что не допускается.** Часть не стоит в `requires`, `ensures`, `invariants`, `previous(…)` и в `model { }`: у неё нет
значения, которое можно сравнить или удержать.

## Пометка метода

**Правило.** Пометка с путём называет части, которые метод изменяет. Путь начинается с `self.`
(кроме [записи про весь объект](#запись-про-весь-объект)): голое имя в угловых
скобках уже означает параметр ([место в результате функции](ownership.md#место-в-результате-функции)).

| Запись | Что обещает метод |
|---|---|
| `mut<self.cache> fn clearCache` | меняет структуру только части `cache` |
| `mut<self.cache, self.items> fn rebuild` | меняет структуру частей `cache` и `items` |
| `edit<self.items> fn touch` | пишет значения в часть `items`, структуру не меняет |
| `access<mut self.cache, edit self.items> fn refresh` | меняет структуру `cache`, в `items` пишет значения |
| `mut fn compact` | может сменить структуру всего объекта, как и прежде |

**Правило.** Всё, что пометка с путём не называет, метод только читает. Вызывающий сохраняет ссылки в остальные части и
факты о них.

**Правило.** Одно право записывается короткой формой, `mut<…> fn` или `edit<…> fn`. Форма `access<…> fn` служит только
для разных прав: `access<…>` с одним правом — ошибка. Внутри `access<…>` стоят слова `edit` и `mut`; параметр права
там не пишется.

```efen
access<mut self.cache> fn clearCache                 // ошибка: одно право пишется mut<self.cache> fn
access<mut self.cache, mut self.items> fn rebuild    // ошибка: mut<self.cache, self.items> fn
```

- `read<self.x> fn` — ошибка: чтение пометка с путём даёт и без записи.
- `own` и `out` с путём не пишутся; параметр права со значением `own` в записи с путём — ошибка.
- Параметр права пишется в короткой форме: `Access<self.items> fn`
  ([право доступа как параметр](../generics.md#право-доступа-как-параметр)). При `Access == read` это обычный `read fn`.
- Метод с пометкой `mut<…>` или с `mut` внутри `access<…>` вызывается у получателя `mut`. Метод, у которого все права —
  `edit`, вызывается у получателя `edit` и `mut`.
- Пути не различают перегрузки. Метод с путём сравнивается с одноимёнными по самому широкому праву своей пометки.
- Переход состояния самого объекта требует `mut fn` без пути ([состояния типов](typestate.md)).

**Место в результате.** Источником результата служит часть: `-> read<self.items> Item?`. Прежнее правило сохраняется:
метод, который отдаёт место с правом `edit` или `mut`, сам имеет это право на ту же часть.

```efen
edit<self.items> fn item(at: Int) -> edit<self.items> Item?
```

## Привязка в реализации

**Правило.** Тип, который соблюдает контракт или реализует интерфейс с частями, привязывает каждую часть к своим полям
явно. Строка привязки называет объявление, которому часть принадлежит:

```efen
class Index {
    conforms Storage
    part Storage.items = data
    part Storage.cache = memo, stats

    var data: Vector<Item>
    var memo: Map<Key, Item>
    var stats: Stats
    var log: Vector<String>                          // ни в какой части

    fn first -> read<self.data> Item? { return data[0] }
    mut fn clearCache { memo.clear() }               // путь не написан: тело сверяется с привязкой
    mut fn compact { log.clear(); data.shrink() }
}
```

- Справа — список путей по полям. Путь строится по тем же правилам, что путь источника: только через поля, без
  индексов, не через опциональное поле ([место в результате функции](ownership.md#место-в-результате-функции)).
- Часть без памяти пишется явно: `part Storage.cache = none`. Пропущенная строка привязки — ошибка.
- Часть обобщённого контракта называется с аргументами: `part Storage<Int>.items = …`.
- Привязку пишет объявление, которому принадлежат поля: класс, структура или аспект
  [реализации извне](../contracts.md#реализация-извне). Стратегия привязку не пишет.
- Класс, который реализует интерфейс, созданный из контракта, называет в строке контракт.

**Правило.** Привязка одна на пару «тип, контракт» во всей программе. Все стратегии и все пакеты видят одну и ту же
привязку; вторая привязка той же пары — ошибка сборки. Поэтому выбор стратегии при выполнении
([динамическая стратегия](../strategies.md#динамическая-стратегия)) смысла части не меняет.

## Проверка привязки

Часть означает память. Привязка принимается, если части одного контракта не делят память, и это решается по
объявлениям: поле не хранит ссылку, поэтому общая память у двух полей бывает только там, где она объявлена
([ссылки только внутри функции](ownership.md#ссылки-только-внутри-функции)).

**Правило.** Часть владеет привязанными полями и всем, чем они владеют единолично.

**Правило.** Привязка — ошибка в строке привязки, если:

| Условие | Пример |
|---|---|
| один путь привязан к двум частям контракта | `items = data` и `cache = data` |
| путь одной части начинает путь другой | `items = data` и `cache = data.index` |
| привязано поле `static` или `thread` | такое поле не принадлежит экземпляру |
| поле-связь и её источник лежат в разных частях | `var current: read<self.data> Item?` в `cache`, `data` в `items` |
| поле одной части зависит через `layout` с правом `mut` от того, чем владеет другая | запрос в `cache` держит `db: mut sqlite3`, а `db` в `items` |

Последние два условия читаются из объявлений: источник связи записан в типе поля
([модель FLOW, связи полей](https://github.com/efen-lang/amber/blob/main/design/compilation/flow-memory-model.md)), зависимость — в
`layout` класса ([модели поведения](../models.md)).

**Правило.** Место, путь к которому проходит через ссылку на объект со счётчиком, части не принадлежит: такие ссылки
свободно копируются, и два поля разных частей могут указывать на один объект. Метод не отдаёт такое место как
`read<self.items>`. То же относится к памяти за полем с правом на источник (`Mem: Origin`): два поля разных частей
могут смотреть в один источник, и части он не принадлежит.

## Проверка реализации

**Правило.** У метода с телом путь в пометке не пишется: компилятор выводит сводку из тела и сверяет её с пометкой
контракта через привязку. Ошибка выдаётся в строке тела, которая выходит за объявленные части, и называет часть и строку
привязки.

```efen
mut fn clearCache { data.clear() }       // ошибка: data привязано к Storage.items, а clearCache объявлен mut<self.cache>
```

- Слово права у реализации не шире самого широкого слова пометки контракта: `mut<self.cache> fn` реализуют `mut fn`,
  `edit fn` или `read fn`. Что именно тело изменяет, сравнивается по сводке, а не по слову.
- Путь у метода с телом можно написать, и тогда он служит проверяемым пределом. В классе путь называет настоящее поле:
  `mut<self.memo> fn clearCache`. Имена частей класс пишет в строках привязки и в путях через поле-обёртку
  ([обёртка](#обёртка)).
- Источник результата пишется всегда и тоже настоящим полем: `-> read<self.data> Item?`. По привязке `data` лежит в
  `Storage.items`, и это совпадает с контрактом.
- Поле вне частей (`log` выше) метод с путём в пометке контракта не изменяет. Его меняет метод, который контракт
  объявил `mut fn` или `edit fn` без пути, и методы класса, которых в контракте нет.

**Класс над внешним значением.** У такого класса настоящих полей нет, и путь в пометке метода без тела называет его
поле `layout` простого типа, которое служит источником ссылок
([`layout` в теле класса](../memory/layout.md#layout-в-теле-класса)). Привязки ему не нужно: поле объявил сам класс.
Поле-удержание (`var kept: [read [UInt8]]`) в пометке — ошибка.

## Что видит вызывающий

**Правило.** Код, который знает о типе только контракт или интерфейс, сравнивает части по именам:

| Ссылка взята из | Вызван метод | Ссылка |
|---|---|---|
| части `items` | `mut<self.cache> fn` | действует |
| части `items` | `mut<self.items> fn`, `mut fn` | умирает |
| части `items` | `edit<self.items> fn` | действует: структура не меняется |
| всего `self` | любой метод с `mut` | умирает |
| части `items` контракта `Storage` | `mut<self.index> fn` контракта `Other` на том же объекте | умирает |

Последняя строка — правило о двух контрактах: части разных контрактов одного типа считаются пересекающимися, потому что
привязки проверяются внутри одного контракта.

- Зависимость `layout` — не часть. Вызов метода с `mut`, с путём или без, по-прежнему гасит ссылки в объектах,
  достижимых через поля `layout` получателя с правом `mut`
  ([как компилятор выводит области](access-regions.md#как-компилятор-выводит-области)).
- Пересечение аргументов считается по частям. Аргумент, взятый из части, которую метод только читает, с получателем не
  пересекается: `s.put(item: s.first()!)` допустим, если `put` объявлен `mut<self.cache> fn`.
- При выполнении ничего не проверяется: у части нет адреса, и в таблице методов интерфейса от частей ничего нет.
- Код, который видит конкретный тип, проверяется по сводкам и настоящим полям, как и раньше. Части ему не нужны.

## Где сообщается ошибка

| Ошибка | Место сообщения |
|---|---|
| совпали имена части и поля `layout`, одноимённые части предков | объявление контракта |
| `access<…>` с одним правом, `read<self.x> fn`, часть в условии или модели | строка пометки или условия |
| нет строки привязки, нарушено условие привязки | строка привязки или строка `conforms`/`implements` |
| две привязки одной пары «тип, контракт» | обе строки привязки, при сборке программы |
| тело выходит за части пометки | строка тела; сообщение называет часть и строку привязки |
| ссылка убита вызовом в обобщённом коде | место использования ссылки; сообщение называет часть и пометку вызванного метода |

## Запись про весь объект

Служебное поле, которое изменяют методы разных частей (счётчик версий, признак «изменено»), ни в одной части лежать не
может. Для него в списке `access<…>` есть запись про весь объект.

**Правило.** `edit self` в списке `access<…>` разрешает методу писать значения в любое место объекта, включая поля вне
частей. Структуру метод меняет только у частей, названных с `mut`.

```efen
access<mut self.cache, edit self> fn touch(key: Key)
```

- У вызывающего ссылки в остальные части действуют: структура там не меняется. Факты о значениях объекта после вызова
  забываются.
- Получатель такого метода пересекается с аргументом из любой части: `s.touch(key: s.first()!.key)` с местом в
  аргументе — ошибка.
- `edit<self> fn` и `mut self` в списке — ошибки: это `edit fn` и `mut fn`.
- Служебное состояние, структуру которого меняют, привязывают к части.

## Обёртка

Обёртка хранит значение типа, который сам соблюдает контракт с частями, и привязывает свои части к его частям.

**Правило.** Последний шаг пути может назвать контракт и часть поля: `поле.Контракт.часть`. Имя контракта начинается с
заглавной буквы, поэтому с полем такая запись не путается.

```efen
class Logged<S: Storage> {
    conforms Storage
    part Storage.items = inner.Storage.items
    part Storage.cache = inner.Storage.cache

    var inner: S
    var log: Vector<String>

    fn first -> read<self.inner.Storage.items> Item? { return inner.first() }
    mut fn clearCache { inner.clearCache() }
}
```

- Запись `поле.Контракт.часть` допустима везде, где класс пишет путь: в привязке, в источнике результата и в пометке.
- Части одного контракта поля не пересекаются: это уже проверено привязкой его типа. Части двух разных контрактов
  одного поля в разных частях обёртки — ошибка привязки.
- Если на место `S` подставлен класс со счётчиком, привязка через его части — ошибка при подстановке типа: место за
  ссылкой со счётчиком части не принадлежит.

## Наследник класса

**Правило.** Наследник дописывает в унаследованную часть свои новые поля строкой `+=`. Привязку полей предка он не
меняет.

```efen
class Fancy: Index {
    var bloom: Bloom
    part Storage.cache += bloom

    override mut fn clearCache { memo.clear(); bloom.reset() }
}
```

- Условия привязки проверяются на расширенной привязке, `override` сверяется с ней же.
- Наследник дописывает поля и тогда, когда базовый класс объявлен в другом пакете.
- Вызов `open`-метода у конкретного типа читается по частям: вызывающий знает, что `data` лежит в `items`, а
  `clearCache` меняет `cache`, какие бы поля ни добавил наследник. Поэтому `open fn`, который реализует метод с путём,
  настоящего поля в пометке не пишет.
- Класс, которому нужен узкий `open`-метод, соблюдает контракт с частями. Контракт виден не уже самого метода.

## Обход по части

Обход через `Iterable` держит объект целиком: `for item in s` не даёт менять структуру ни одной части. Контракт с
частями объявляет собственный обход, и его курсор держит одну часть.

**Правило.** Метод обхода пишет удержание курсора с путём к части, в скобках, как удержание генератора
([генераторы](../generators.md)). Тип курсора — параметр контракта.

```efen
contract Storage<Cursor> {
    layout { part items, cache }

    fn each -> (read<self.items> Cursor)             // курсор держит часть items
    mut<self.cache> fn clearCache

    invariants { Cursor conforms Iterator<read Item> }
}

fn work<S: Storage>(s: mut S) {
    for item in s.each() {
        s.clearCache()                               // можно: cache курсор не держит
    }
}
```

- Источник элемента — путь удержания: `item` выше — место в `s.items`.
- На каждое право свой метод: `edit<self.items> fn eachEdit -> (edit<self.items> EditCursor)`. Обход со сменой
  структуры части объявляется так же, с правом `mut` на неё.
- Реализация называет настоящее поле: `fn each -> ArrayIterator<read Item, Src: self.data>`. По привязке `data` лежит в
  `Storage.items`.
- `-> read<self.items> Cursor` без скобок — место типа `Cursor` внутри части, а не курсор, который её держит.

## Граница пакета

**Правило.** Части контракта видны либо каждому, кто его использует, либо никому. Пока хранилище пакетов не несёт
список частей, пути пометок, источники результатов и привязки, контракт из зависимости проверяется как контракт без
частей: вызывающий считает, что метод с `mut` меняет получателя целиком. Проверка от этого строже, но остаётся верной.

Изменения опубликованного контракта, которые ломают его пользователей:

| Изменение | Кого ломает |
|---|---|
| добавлена часть | реализации: нужна строка привязки |
| метод перенесён в другую часть, путь заменён на `mut fn`, добавлена запись `edit self` | вызывающих |
| пометка сужена | реализации |

## Чего части не выражают

| Случай | Что делать |
|---|---|
| Наследник хочет новую часть, которой нет в контракте | части объявляет только контракт; наследник дописывает поля в имеющиеся |
| Привязка для типа из другого пакета | привязку пишет владелец полей; чужой тип оборачивают ([обёртка](#обёртка)) |
| Поле обёртки `inner: S?` или `[S]` | путь не идёт через опциональное поле и через элементы; такое поле привязывают целиком |
| Структура с `Src: Origin`, которая хранит заимствование | держит весь `Src`; путь к части пишется только в удержании результата |
| Путь в типе функции | запись смены структуры в типе функции ещё не выбрана ([тип функции](function-type.md)) |
| Путь через зависимость `layout` в другой объект | не пишется: путь называет часть, поле или поле `layout` самого получателя |
