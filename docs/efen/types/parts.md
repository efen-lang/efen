# Части объекта

[Документация](../README.md) · [Словарь](../glossary.md) · [Области доступа](access-regions.md) · [Владение и доступ](ownership.md) · [Контракты](../contracts.md) · [Правила доступа к памяти](../memory/memory-rules.md)

> Статус: проект спецификации, принят 2026-11-11. Amber частей не реализует.

Часть — имя, которым контракт или интерфейс называет память объекта, не зная его полей. Пометка метода говорит, структуру
каких частей он меняет, а реализация привязывает каждую часть к своим полям. По именам частей компилятор решает, какие
ссылки переживают вызов, тела которого он не видит.

```efen
contract Storage {
    layout { part items, cache }

    fn first -> read<self.items> Item?       // ссылка в часть items
    mut<self.cache> fn clearCache            // меняет структуру только части cache
    mut fn compact                           // может сменить структуру всего объекта
}

fn work<S: Storage>(s: mut S) {
    if let item = s.first() {
        s.clearCache()                       // можно: item взят из items, вызов меняет cache
        print(item.name)
        s.compact()                          // item больше не действует
    }
}
```

`Item` и `Key` в примерах этой статьи — обычные типы, объявленные рядом с контрактом.

## Задача

Вызов функции с телом компилятор проверяет по её сводке, и сводка помнит путь до поля: метод, который меняет структуру
`self.cache`, не мешает ссылке в `self.items` ([как компилятор выводит области](access-regions.md#как-компилятор-выводит-области)).
У метода контракта и интерфейса тела нет, и вызывающий читает одну пометку
([доступ метода к self](../contracts.md#доступ-метода-к-self)). `mut fn` по пометке может сменить структуру всего объекта,
поэтому после его вызова умирает каждая ссылка внутрь объекта, даже если ни одна реализация её память не трогает.

Назвать в пометке поле контракт не может: полей у него нет, а требование свойства `var x: T { get set }` описывает
доступ и памяти не задаёт ([поля, которые требует контракт](../contracts.md#поля-которые-требует-контракт)). Части дают
контракту имена для памяти без самих полей.

## Объявление частей

**Правило.** Части объявляет строка `part` в блоке `layout { }` контракта или интерфейса. Имена перечисляются через
запятую:

```efen
contract Storage {
    layout { part items, cache }
}

interface Journal {
    layout { part entries, index }
}
```

- `part` — контекстное слово: вне `layout` и вне [строки привязки](#привязка-в-реализации) это обычное имя.
- У части нет типа, значения и байт в объекте. Её читает только FLOW, как и поля `layout` контракта
  ([`layout` в теле класса](../memory/layout.md#layout-в-теле-класса)).
- Имя части не совпадает с именем поля `layout` и с именем требуемого свойства того же контракта: совпадение — ошибка.
- Интерфейс, созданный из контракта (`interface StorageInterface from Storage`), получает его части и пометки методов и
  ничего не повторяет.
- `part` в `shared layout` — ошибка.

**Наследование.** Контракт-наследник получает части предков и может объявить свои. Правила те же для интерфейса и его
предков.

- Одноимённые части разных предков — ошибка в объявлении наследника. Один предок с теми же аргументами, достигнутый
  двумя путями, считается один раз, как и его требования ([наследование контрактов](../contracts.md#наследование-контрактов)).
- Один метод, полученный от двух предков с разными путями в пометке, — ошибка в объявлении наследника.

**Что не допускается.** Часть не стоит в `requires`, `ensures`, `invariants`, `previous(…)` и в `model { }`: у неё нет
значения, которое можно сравнить или заимствовать.

## Пометка метода

**Правило.** Пометка с путём называет части, которые метод изменяет. Путь начинается с `self.`: голое имя в угловых
скобках уже означает параметр ([ссылка в результате функции](ownership.md#место-в-результате-функции)). Единственная
запись без пути — `edit self` внутри скобок ([запись про весь объект](#запись-про-весь-объект)).

| Запись | Что обещает метод |
|---|---|
| `mut<self.cache> fn clearCache` | меняет структуру только части `cache` |
| `mut<self.cache, self.items> fn rebuild` | меняет структуру частей `cache` и `items` |
| `edit<self.items> fn touch` | пишет значения в часть `items`, структуру не меняет |
| `mut<self.cache, edit self.items> fn refresh` | меняет структуру `cache`, в `items` пишет значения |
| `mut fn compact` | может сменить структуру всего объекта, как и прежде |

**Правило.** Всё, что пометка с путём не называет, метод только читает. Вызывающий сохраняет ссылки в остальные части;
какие факты он сохраняет, сказано в разделе [«Что видит вызывающий»](#что-видит-вызывающий).

**Правило.** Слово перед скобками — право на каждый путь списка. Путь, перед которым стоит своё слово, получает это
право вместо общего: в `mut<self.cache, edit self.items>` часть `cache` получает `mut`, а `items` — `edit`.

```efen
mut<self.cache, self.stats, edit self.items> fn refresh    // cache и stats — mut, items — edit
mut<self.cache, mut self.items> fn rebuild                 // ошибка: слово внутри повторяет общее
edit<self.items, mut self.cache> fn refresh                // ошибка: слово внутри шире общего, пишется mut<self.cache, edit self.items>
```

- Слово внутри скобок уже общего: внутри `mut<…>` это `edit`. Внутри `edit<…>` своего слова у пути нет.
- Слово перед скобками — самое широкое право пометки; по нему метод вызывается и сравнивается с одноимёнными.

- `read<self.x> fn` — ошибка: читать объект может любой метод, путь пишется только для `edit` и `mut`. Исключение —
  генератор-метод: его пометка называет и то, что он держит, поэтому `read<self.items> generator` допустим
  ([генератор-метод](../generators.md#генератор-метод)).
- Часть стоит в пометке один раз: `mut<self.cache, edit self.cache> fn` и `mut<self.cache, self.cache> fn` — ошибки.
- `own` и `out` с путём не пишутся; параметр права со значением `own` в записи с путём — ошибка.
- Параметр права пишется в короткой форме: `Access<self.items> fn`
  ([право доступа как параметр](../generics.md#право-доступа-как-параметр)). При `Access == read` путь отбрасывается и это обычный `read fn`; ошибка — только написанное слово `read` с путём.
- Метод с пометкой `mut<…>` вызывается у получателя `mut`, метод с пометкой `edit<…>` — у получателя `edit` и `mut`.
- Пути не различают перегрузки: `mut<…> fn` сравнивается с одноимёнными как `mut fn`, `edit<…> fn` — как `edit fn`.
- Переход состояния самого объекта требует `mut fn` без пути ([состояния типов](typestate.md)).

**Ссылка в результате.** Источник результата может назвать часть: `-> read<self.items> Item?`. Результат без пути,
`-> read Item?`, по-прежнему означает ссылку во весь `self`.

**Правило.** Право ссылки в результате не шире права метода на ту же часть. Результат без пути с правом `edit` или
`mut` требует того же права на весь объект: `edit fn`, `mut fn` или записи `edit self`.

```efen
edit<self.items> fn item(at: Int) -> edit<self.items> Item?
edit<self.items> fn slot(at: Int) -> mut<self.items> Item?     // ошибка: метод имеет на items только edit
mut<self.cache> fn pick -> edit<self.items> Item?              // ошибка: items метод только читает
```

## Привязка в реализации

**Правило.** Тип, который соблюдает контракт или реализует интерфейс с частями, привязывает каждую часть к своим полям
явно. Строка привязки называет объявление, которому часть принадлежит:

```efen
class Index {
    conforms Storage
    part Storage.items = data
    part Storage.cache = memo, stats

    var data: Vector<Item>
    var memo: Map<Key, Item>
    var stats: Stats
    var log: Vector<String>                          // ни в какой части

    fn first -> read<self.data> Item? { return data[0] }
    mut fn clearCache { memo.clear() }               // путь не написан: тело сверяется с привязкой
    mut fn compact { log.clear(); data.shrink() }
}
```

- Справа — список путей по полям. Путь строится по правилам пути источника: через поля, без индексов, не через
  опциональное поле ([ссылка в результате функции](ownership.md#место-в-результате-функции)). Последним шагом пути может
  стоять часть поля-обёртки ([обёртка](#обёртка)).
- Часть без памяти пишется явно: `part Storage.cache = none`. Слово `none` зарезервировано только здесь.
  Пропущенная строка привязки — ошибка.
- Аргументы контракта в строке привязки пишутся, только когда тип соблюдает один контракт с разными аргументами:
  `part Storage<Int>.items = …`. Иначе пишется одно имя контракта.
- Класс, который реализует интерфейс, созданный из контракта, называет в строке контракт.
- Привязку пишет объявление, которому принадлежат поля: класс, структура или аспект
  [реализации извне](../contracts.md#реализация-извне). Стратегия привязку не пишет. Структура, методы которой и строку
  `conforms` даёт стратегия, пишет строки привязки сама, без `conforms`; если их нет, ошибка выдаётся в строке
  `conforms` стратегии.
- Класс над внешним значением настоящих полей не имеет и привязывает часть к своему полю `layout` простого типа
  ([`layout` в теле класса](../memory/layout.md#layout-в-теле-класса)).
- Часть привязывают к одному полю `var` или к нескольким. Тип, память которого описана в `layout`, привязывает
  часть к своим полям так же: `part Storage.items = items, capacity, count` у динамического массива. К множеству
  или области часть не привязывают.
- Строка привязки стоит в том же `#if`, что и её `conforms`: без соответствия нет и привязки. Строка привязки вне
  `#if` при условном `conforms` — ошибка.

**Правило.** Привязка одна на тип с его аргументами и контракт с его аргументами во всей программе: две ветки `#if`
привязывают по-разному, потому что дают разные типы. Все стратегии и все пакеты видят одну
и ту же привязку; вторая привязка того же типа к тому же контракту — ошибка сборки. Поэтому выбор стратегии при
выполнении ([динамическая стратегия](../strategies.md#динамическая-стратегия)) смысла части не меняет.

## Проверка привязки

Часть означает память. Привязка принимается, если части не делят память, и это решается по объявлениям: два поля не смотрят в
одну память, пока это не объявлено, поэтому общая память у двух полей бывает только там, где она видна в типе поля
([поля не делят память](ownership.md#поля-не-делят-память)).

**Правило.** Часть владеет привязанными полями и всем, чего они достигают через владеющие поля и элементы, без ссылки
на объект со счётчиком и без права на источник.

**Правило.** Привязка проверяется на всех частях контракта вместе с частями его предков и принимается, если ни одно
условие таблицы не выполнено. Иначе это ошибка в строке привязки.

| Условие | Пример |
|---|---|
| один путь привязан к двум частям | `items = data` и `cache = data` |
| путь одной части начинает путь другой | `items = data` и `cache = data.index`; `items = inner` и `cache = inner.Storage.cache` |
| привязано поле `static` или `thread` | такое поле не принадлежит экземпляру |
| поле со связью внутрь объекта привязано не к той части, что его источник | `kids = children` и `cursor = current` при `current: read<self.children> Node?` |
| в типе есть поле со связью `read<self> T?` | такое поле смотрит во все части сразу |
| поле одной части зависит через `layout` с правом `mut` от того, чем владеет другая | запрос в `cache` держит `db: mut sqlite3`, а `db` в `items` |
| поля двух частей владеют слотами одной области или одного множества типа | `head: own Nodes.Item?` в `items` и `free: own Nodes.Item?` в `cache`: рост `Nodes` перемещает слоты обеих частей |

Зависимость читается из `layout` класса ([модели поведения](../models.md)).

**Правило.** Три вида памяти части не принадлежат, даже когда поле, через которое до них добираются, привязано:

- объект со счётчиком: ссылки на него свободно копируются, и два поля разных частей могут указывать на один объект;
- память источника за полем с правом на него (`Mem: Origin`): два поля могут смотреть в один источник;
  [поле со связью внутрь своего объекта](ownership.md#поле-со-связью-внутрь-своего-объекта)
  (`current: read<self.children> Node?`) к ним не относится: оно принадлежит части своего источника, и ссылка,
  прочитанная через него, — ссылка в эту часть;
- объект, достижимый через зависимость `layout`.

Ссылку в такую память метод с частью в источнике результата не отдаёт. Что метод делает с такой памятью, пометка
получателя не описывает: это изменения другого объекта.

## Проверка реализации

**Правило.** У метода с телом путь в пометке можно не писать: компилятор выводит сводку из тела и сверяет её с пометкой
контракта через привязку. Ошибка выдаётся в строке тела, которая выходит за объявленные части, и называет часть и строку
привязки.

```efen
mut fn clearCache { data.clear() }       // ошибка: data привязано к Storage.items, а clearCache объявлен mut<self.cache>
```

- Слово права у реализации не шире самого широкого слова пометки контракта: `mut<self.cache> fn` реализуют `mut fn`,
  `edit fn` или `read fn`. Что именно тело изменяет, сравнивается по сводке, а не по слову.
- Написанный путь служит проверяемым пределом. В классе путь называет настоящее поле: `mut<self.memo> fn clearCache`.
  Имена частей класс пишет в строках привязки и в шаге `поле.Контракт.часть` ([обёртка](#обёртка)).
- Источник результата не выводится. Если контракт назвал часть, реализация пишет настоящее поле из этой части:
  `-> read<self.data> Item?`. Результат без пути, `-> read Item?`, шире и к такому требованию не подходит.
- Поле вне частей (`log` выше) метод с путём в пометке контракта только читает. Его изменяет метод, который контракт
  объявил `mut fn` или `edit fn` без пути, метод с записью `edit self` и методы класса, которых в контракте нет.
- Часть, привязанная к `none`, памяти не имеет. Метод с такой частью в источнике результата пишет путь контракта,
  `-> read<self.Storage.items> Item?`, и каждый его `return` возвращает `null`. Курсор с заимствованием такой части ничего
  не держит.
- Метод, который реализует требования двух контрактов, не связанных наследованием, сверяется с пометкой каждого.

Что реализация пишет сама и что выводит компилятор:

| Факт | У метода с телом | Почему |
|---|---|---|
| слово права (`read`, `edit`, `mut`) | пишется | по нему метод вызывают и различают перегрузки |
| путь в пометке | выводится из тела; написанный путь — проверяемый предел | тело видно, и сводка точнее пометки |
| путь в пометке `open`-метода | не пишется; берётся из контракта и привязки | наследник дописывает свои поля в часть |
| источник результата | пишется | это обещание вызывающему, а не свойство одного тела |
| привязка частей | пишется, включая `= none` | одна на всю программу, и от неё зависят все вызывающие |

**Класс над внешним значением.** Путь в пометке его метода без тела называет поле `layout` простого типа:
`mut<self.errmsg> fn`. Такой метод меняет только память, из которой берутся ссылки с источником `self.errmsg`; ссылки с
другими источниками получателя действуют. Поле-заимствование (`var kept: [read [UInt8]]`) в пометке — ошибка.

## Что видит вызывающий

**Правило.** Код, который знает о типе только контракт или интерфейс, сравнивает части по именам:

| Ссылка взята из | Вызван метод | Ссылка |
|---|---|---|
| части `items` | `mut<self.cache> fn` | действует |
| части `items` | `mut<self.items> fn`, `mut fn` | умирает |
| части `items` | `edit<self.items> fn` | действует: структура не меняется |
| ссылки с источником `self` без пути | `mut fn`, `mut<…> fn` | умирает |
| части `items` контракта `Storage` | `mut<self.index> fn` контракта `Other` на том же объекте | умирает |

**Правило.** Части контракта и его предков между собой не пересекаются: привязка проверена на них вместе. Части двух
контрактов, не связанных наследованием, считаются пересекающимися; то же относится к одному контракту с разными
аргументами.

**Правило.** Факт о значении сохраняется после вызова, только если он выведен из ссылки с источником-частью, которую
вызов не изменяет. Факты из требуемых свойств и из результатов без источника (`let n = s.count`) забываются при любом
вызове с `mut` или `edit`: свойство ни к какой части не относится.

- Зависимость `layout` — не часть. Вызов метода с `mut`, с путём или без, по-прежнему гасит ссылки в объектах,
  достижимых через поля `layout` получателя с правом `mut`
  ([как компилятор выводит области](access-regions.md#как-компилятор-выводит-области)).
- Получатель — пишущий параметр только для частей, которые метод изменяет. Для остальной памяти получателя `noalias`
  по сигнатуре не предполагается ([отношение между параметрами](access-regions.md#отношение-между-параметрами)).
- Для правила о колбэке, который меняет структуру памяти параметра, параметром считается получатель целиком, а не
  названные части ([отношение между параметрами](access-regions.md#отношение-между-параметрами)).
- Код, который видит конкретный тип, проверяется по сводкам и настоящим полям. Исключения — метод без тела и
  `open`-метод: их читают по пометке, а `open`-метод, который реализует метод с путём, — по частям и привязке класса
  ([наследник класса](#наследник-класса)).

**Правило.** Аргумент-ссылка, переданный методу с путём в пометке, сравнивается с получателем по частям при
компиляции. При выполнении ничего не проверяется: у части нет адреса, и в таблице методов интерфейса от частей ничего
нет. Поэтому недоказанное непересечение — ошибка, а не проверка адресов.

| Аргумент взят из | Вызов метода `mut<self.cache> fn put(item: read Item)` |
|---|---|
| части, которую пометка не называет: `s.put(item: s.first()!)`, `first -> read<self.items> Item?` | допустим |
| части, которую пометка называет | ошибка: пересечение доказано |
| получателя без пути: `s.put(item: s.any()!)`, `any -> read Item?` | ошибка: ссылка может лежать в `cache` |
| части другого контракта того же объекта, не связанного наследованием | ошибка: такие части считаются пересекающимися |
| другого объекта; значение `ImplicitlyCopyable`, переданное копией | допустим |

**Правило.** Части разделяют ссылки, а не потоки. Между потоками метод с путём в пометке конфликтует с любым другим
методом того же объекта: всё, чего пометка не называет, он читает, а чтение рядом с записью другого потока —
конфликт ([корутины `spawn`](access-regions.md#корутины-spawn)).
## Где сообщается ошибка

| Ошибка | Место сообщения |
|---|---|
| совпали имена части и поля `layout`, одноимённые части предков | объявление контракта |
| слово внутри скобок не уже общего, `read<self.x> fn`, часть дважды в одной пометке, часть в условии или модели | строка пометки или условия |
| право результата шире права метода на ту же часть | строка объявления метода |
| аргумент-ссылка с источником, который не отделён от названной части | строка вызова |
| нет строки привязки | строка `conforms` или `implements` |
| нарушено условие привязки | строка привязки |
| две привязки одного типа к одному контракту | обе строки привязки, при сборке программы |
| тело выходит за части пометки | строка тела; сообщение называет часть и строку привязки |
| ссылка убита вызовом в обобщённом коде | строка, где ссылка используется; сообщение называет часть и пометку вызванного метода |

## Запись про весь объект

Служебное поле, которое изменяют методы разных частей (счётчик версий, признак «изменено»), ни в одной части лежать не
может. Для него в списке пометки есть запись про весь объект.

**Правило.** `edit self` в списке `mut<…>` разрешает методу писать значения в любую часть объекта и в поля вне
частей. Структуру метод меняет только у частей, названных с `mut`.

```efen
mut<self.cache, edit self> fn touch(key: Key)
```

- `edit self` стоит только внутри `mut<…>`, после частей. `edit<self> fn` и `mut<self> fn` — ошибки: это `edit fn` и
  `mut fn`.
- У вызывающего ссылки в остальные части действуют: структура там не меняется. Факты о значениях объекта после вызова
  забываются.
- Получатель такого метода пишет весь объект и пересекается с аргументом-ссылкой в любую часть. Значение
  `ImplicitlyCopyable` передаётся копией и не пересекается.
- Служебное состояние, структуру которого меняют, привязывают к части. Если его перестраивают методы нескольких частей,
  каждый из них объявляет `mut` и на эту часть.

## Обёртка

Обёртка хранит значение типа, который сам соблюдает контракт или реализует интерфейс с частями, и привязывает свои
части к его частям.

**Правило.** Последний шаг пути может назвать контракт и часть поля: `поле.Контракт.часть`. В пути привязки и в пути
источника шаг с заглавной буквы после поля — всегда контракт или интерфейс.

```efen
class Guarded<S: Storage> {
    conforms Storage
    part Storage.items = inner.Storage.items
    part Storage.cache = inner.Storage.cache

    var inner: S

    fn first -> read<self.inner.Storage.items> Item? { return inner.first() }
    mut fn clearCache { inner.clearCache() }
    mut fn compact { inner.compact() }
}
```

- Запись `поле.Контракт.часть` допустима везде, где класс пишет путь: в привязке, в источнике результата и в пометке.
- Так же называет часть путь внутрь параметра, тип которого известен по контракту: `-> read<s.Storage.items> Item?`
  у функции `fn pick<S: Storage>(s: read S)`, и роль `yield` генератора ([отдача ссылки](../generators.md#отдача-ссылки)).
- Части одного контракта поля не пересекаются: это проверено привязкой его типа. Части двух контрактов поля, не
  связанных наследованием, в разных частях обёртки — ошибка привязки.
- Поле привязывают либо настоящими полями, либо частями: `inner.data` рядом с `inner.Storage.cache` — ошибка. Поле
  целиком в одной части и его часть в другой — тоже ошибка, по правилу о начале пути.
- Если вместо `S` подставлен класс со счётчиком, привязка через его части — ошибка в строке подстановки типа;
  сообщение называет строку привязки. Память за ссылкой со счётчиком части не принадлежит.

## Наследник класса

**Правило.** Наследник дописывает в унаследованную часть свои новые поля строкой `+=`. Строка `+=` называет только
поля, объявленные в этом наследнике: унаследованное поле в ней — ошибка, даже если предок оставил его вне частей.
Привязку полей предка наследник не меняет.

```efen
open class Catalog {
    conforms OpenClass, Storage
    part Storage.items = data
    part Storage.cache = memo

    var data: Vector<Item>
    var memo: Map<Key, Item>

    fn first -> read<self.data> Item? { return data[0] }
    open mut fn clearCache { memo.clear() }
    mut fn compact { data.shrink() }
}

class Fancy: Catalog {
    var bloom: Bloom
    part Storage.cache += bloom

    override mut fn clearCache { memo.clear(); bloom.reset() }
}
```

- Условия привязки проверяются на расширенной привязке, `override` сверяется с ней же.
- `open`-метод, который реализует метод контракта с путём, пишется без пути. Вызывающий берёт путь из контракта и
  привязку класса: `data` лежит в `items`, а `clearCache` меняет `cache`, какие бы поля ни дописал наследник.
- Путь к настоящему полю у `open`-метода — ошибка: наследник не смог бы изменить свои поля. Узкий `open`-метод класс
  получает, соблюдая контракт с частями; видимость контракта не уже видимости метода.
- `override` может отдать ссылку в другое поле той же части: вызывающий читает источник по части.
- Наследник привязывает поля, в том числе унаследованные и видимые ему, и к контракту, который предок не соблюдает:
  это новая привязка другого типа. К контракту, который предок соблюдает, унаследованные поля не привязываются:
  методы предка, которых в контракте нет, меняют поле вне частей, и вызывающий по типу предка этого не увидел бы.

## Обход по части

Обход через `Iterable` держит объект целиком: `for item in s` и `for item in edit s` не дают менять структуру ни
одной части, а `for item in mut s` даёт ([контракты обхода](collections.md#контракты-обхода)). Контракт с частями объявляет собственный обход, и его курсор
держит одну часть.

**Правило.** Метод обхода пишет заимствование курсора с путём к части, в скобках, как заимствование генератора
([генераторы](../generators.md)). Тип курсора — параметр контракта.

```efen
contract Shelf<Cursor> {
    layout { part items, cache }

    fn each -> (read<self.items> Cursor)             // курсор держит часть items
    mut<self.cache> fn clearCache

    invariants { Cursor conforms Iterator<read Item, Src: self.items> }
}

fn sweep<S: Shelf>(s: mut S) {
    for item in s.each() {
        s.clearCache()                               // можно: cache курсор не держит
    }
}

class Rack {
    conforms Shelf<Cursor: _>
    part Shelf.items = data
    part Shelf.cache = memo

    var data: Vector<Item>
    var memo: Map<Key, Item>

    fn each -> ArrayIterator<read Item, Src: self.data> { … }
    mut fn clearCache { memo.clear() }
}
```

- Источник элемента называет инвариант: `Src: self.items`, тот же путь, что в заимствовании. `item` выше — ссылка в
  `s.items`. Часть аргументом `Src` пишется только в тексте контракта.
- Обход с записью значений — второй метод со вторым параметром курсора: `Cursor` один на соблюдение, и курсор для
  чтения им уже занят.
- Реализация скобок не пишет и называет в `Src` настоящее поле. По привязке `data` лежит в `Shelf.items`, поэтому
  требование контракта выполнено ([контракты обхода](collections.md#контракты-обхода)).
- `for item in s.each()` обходит готовый курсор ([цикл `for` с итератором](collections.md#цикл-for-с-итератором)).
- `-> read<self.items> Cursor` без скобок — ссылка на значение типа `Cursor` внутри части, а не курсор, который её держит.
- Обход по части пишется и генератором-методом: `read<self.items> generator each yield read<self.items> Item`
  ([генератор-метод](../generators.md#генератор-метод)).

## Граница пакета

**Правило.** Части входят в опубликованное объявление контракта: список частей, пути в пометках и источники
результатов. Привязка входит в опубликованное объявление типа. Пакет, который видит контракт, видит и его части, иначе
проверенный вызывающий встретил бы реализацию, сверенную с пометкой без пути.

Изменения опубликованного контракта и кого они ломают:

| Изменение | Реализации | Вызывающие |
|---|---|---|
| добавлена часть | нужна строка привязки | — |
| часть удалена или переименована | строки привязки, пути обёрток | пути источников |
| метод перенесён в другую часть | тело выходит за пометку | ссылки в новую часть умирают |
| путь заменён на `mut fn`, добавлена запись `edit self` | — | ссылки и факты, которые раньше сохранялись |
| пометка сужена | тело выходит за пометку | — |
| изменён источник результата | источник у реализации | ссылки с прежним источником |
| добавлен параметр контракта | строка `conforms`, привязка с аргументами | — |

## Чего части не выражают

| Случай | Что делать |
|---|---|
| Наследник хочет новую часть, которой нет в контракте | части объявляет только контракт; наследник дописывает поля в имеющиеся |
| Привязка для типа из другого пакета | привязку пишет владелец полей; чужой тип оборачивают ([обёртка](#обёртка)) |
| Поле обёртки `inner: S?` или `[S]` | путь не идёт через опциональное поле и через элементы; такое поле привязывают целиком |
| Ссылка то в одно, то в другое поле одной части | источник результата один; часть привязывают к одному полю или отдают ссылку без пути |
| Структура с `Src: Origin`, которая хранит заимствование | держит то, что названо в `Src`: получателя (`Src: self`) или его поле (`Src: self.data`); часть в `Src` у структуры не пишется, её называет только контракт |
| Путь к части в типе колбэка | не пишется: пометка колбэка `mut<items>` называет параметр целиком ([сохранённый колбэк](access-regions.md#сохранённый-колбэк)) |
| Путь через зависимость `layout` в другой объект | не пишется: путь называет часть, поле или поле `layout` самого получателя |
