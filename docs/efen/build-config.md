# Конфигурация сборки

[Пакеты](packages.md) · [Режимы компиляции](compilation-modes.md) · [Что компилятор берёт у рантайма](runtime/lang-roles.md)

Конфигурация говорит компилятору, как собрать программу: какие зависимости взять, какой рантайм и аллокатор
подключить, под какую платформу собирать и в каком режиме. Она пишется на Efen, отдельным объявлением `config`.
Компилятор читает и вычисляет её во время сборки и никогда не компилирует в программу: в ней только постоянные
значения, поэтому одни и те же файлы с одной и той же командной строкой дают одну и ту же конфигурацию. Машина сборки
входит в неё только двумя путями: как значение по умолчанию для `os` и `arch`, которое не меняет, на каких машинах этой
платформы работает программа, и через явный `--cpu native` ([процессор](#процессор)).

```efen
// server/project.efen
config server {
    version: "0.3.0"

    dependencies {
        json: "^1.0"
        mm: git("https://github.com/efen-lang/mm", tag: "v0.1")
        tools: path("../tools")
    }

    mode production from release {
        target {
            os: "linux"
            arch: "x86_64"
        }
    }
}
```

Уровни кода — рабочее пространство, пакет, модуль — описаны в [пакетах](packages.md).

## Три уровня

| Уровень | Файл | Где ищется |
|---|---|---|
| Глобальный | `config.efen` | Ставится вместе с компилятором; без него сборка не начинается |
| Пространство сборки | `workspace.efen` | Ближайший выше исходного файла; его папка — верх пространства сборки |
| Пакет | `project.efen` | Ближайший выше исходного файла, не выше верха пространства сборки |

Уровни ищутся от исходного файла, а не от текущей папки, по настоящим путям (символические ссылки раскрыты).
Пакет вне пространства сборки сам себе верх.

Ближний уровень побеждает дальний по каждому полю отдельно: пакет — пространство сборки, пространство сборки —
глобальный. Секция сливается поле за полем, словарь — ключ за ключом, список заменяется целиком.

```efen
// workspace.efen                       // server/project.efen
config shop {                           config server {
    members: ["server", "tools/*"]          target {
    target {                                    arch: "aarch64"
        os: "linux"                         }
        arch: "x86_64"                  }
    }
}
// server собирается под linux на aarch64
```

`members` перечисляет пакеты пространства сборки, путями или шаблонами. Сборка всего пространства берёт только
их; случайный `project.efen` в примерах тестов в неё не попадает.

## Как пишется

- В файле ровно одно объявление `config Имя { }` и ничего больше. Имя — имя пакета (его единственное имя: под ним
  пакет пишут в `dependencies` и `use`), пространства сборки или `amber` в глобальном файле.
- Внутри: поля `имя: значение`, по одному на строке, и секции `имя { }`. Запятых нет, кроме набора флагов ниже;
  кавычки у ключей не нужны;
  ключ, который не является именем (`"efen-mm"`), пишется в кавычках.
- Значение — константа: текст в кавычках, `true`/`false`, число, список `[…]`, `null`, вариант по имени (`none`,
  `workspace`) или вызовом (`git("…", tag: "v0.1")`, `path("../tools")`). Голая строка у зависимости означает
  версию из реестра: `json: "^1.0"`.
- Набор флагов — секция, в которой голое имя включает флаг, а `имя: false` выключает:
  `features { avx512f, fma: false }`. Флаги в одной строке разделяет запятая. Флаг с точкой или дефисом в имени
  пишется в кавычках, как такой же ключ: `features { "sse4.2" }`. Набор сливается по уровням флаг за флагом, как
  словарь.
- Путь отсчитывается от папки файла, в котором написан.
- Словарь секций принимает именованные секции: `mode release { }` — запись `release` словаря `mode`. Запись может
  начинаться с другой: `mode production from release { }`.
- Секция плагина пишется под именем плагина: `efql.sql { }`.

## Программа

У пакета одна цель сборки: программа, если в нём есть `main.efen`, или библиотека, если есть `lib.efen`
([пакеты](packages.md#пакет)). Программа — исполняемый файл с точкой входа
`fn main` в `main.efen`; она собирается целиком вместе со всеми зависимостями, и её поля действуют на весь этот код.

```efen
// site/project.efen
config site {
    version: "0.3.0"
    allocator: path("../fast-mm")

    dependencies {
        model: path("../model")
    }
}
```

- `fn main` вне `main.efen` — ошибка.
- От программы зависеть нельзя: запись в `dependencies`, которая называет пакет-программу, — ошибка.
- Вторая программа над тем же кодом — второй пакет; общий код выносят в пакет-библиотеку.

Точка входа — функция `main` в одной из двух форм:

```efen
fn main {             // процесс завершается с кодом 0
}

fn main -> Int {      // результат — код завершения процесса
    return 42
}
```

От результата система берёт столько бит, сколько хранит код завершения: на Linux младшие 8, так что `return 256`
завершает процесс с кодом 0. Исключение, которое никто не поймал, печатается обработчиком рантайма, и процесс
завершается с кодом 1 ([исключения](throws.md#исключение-которое-никто-не-ловит)).

Вызывает `main` рантайм: процесс начинается в его пункте `ProgramEntry`, без стартовых файлов C ([пункты
рантайма](runtime/lang-roles.md#запуск-процесса)). Программа, которая не зовёт ничего из C, собирается без библиотеки C.

### Поля программы

Часть полей принадлежит всей программе: аллокатор, рантайм, `std`, платформа (`target`), оптимизация и замены чужих
зависимостей (`patch`). Куча, рантайм и платформа в одном исполняемом файле одни, поэтому эти поля пишет
пакет-программа в своём `project.efen`. В `provide` программе принадлежат стратегии типов, секции пакетов, `null` и
записи о `@unique` контрактах, включая пункты рантайма; запись о контракте пишет и библиотека — для своего кода.
Реализацию по умолчанию задаёт не конфигурация, а пометка `@default` на реализации ([статическое
связывание](context-and-effects.md#умолчание)).

- В библиотеке поле программы — ошибка: библиотека собирается внутрь чужой программы и получает её поля.
- Библиотека, которую берут две программы с разными полями, компилируется для каждой своей; сборка всего
  пространства собирает каждую программу.

```efen
// json/project.efen
config json {
    allocator: path("../fast-mm")   // ошибка: json — библиотека, кучу выбирает программа
}
```

## Виды библиотеки

Поле `library` перечисляет, во что собирается библиотека:

```efen
config json {
    library: [efen, dynamic, static]
}
```

| Вид | Что получается | Для кого |
|---|---|---|
| `efen` | библиотека Efen; по умолчанию, писать не нужно | программы и библиотеки на Efen, которые от неё зависят |
| `dynamic` | разделяемая библиотека: `.so`, `.dll`, `.dylib` | чужой процесс, который её загружает: программа на C, Python |
| `static` | статическая библиотека: `.a`, `.lib` | программа на C, которая подключает её при линковке |

- В `dynamic` и `static` наружу идут только функции с `@abi(c)` ([внешние функции](foreign.md)).
- `dynamic` работает в чужом процессе и берёт кучу хозяина: у хозяина на Efen — его рантайм той же версии, раскладки
  совпадают. Если её грузит программа не на Efen, она берёт аллокатор по умолчанию из глобального файла и наружу
  владение памятью не отдаёт, только копии в буфер вызывающего.
- `library` в пакете-программе — ошибка.

## Зависимости пространства сборки

Зависимости пространства сборки — общий набор версий, а не значение по умолчанию: пакет их не наследует, а берёт
нужные по имени, значением `workspace`.

```efen
// workspace.efen                       // server/project.efen
config shop {                           config server {
    dependencies {                          dependencies {
        json: "^1.4"                            json: workspace   // ^1.4
        http: "^0.9"                            log: "^2.0"
    }                                       }
}                                       }
```

Пакет, который не пишет `dependencies`, зависимостей не имеет. `workspace` без такой записи в пространстве
сборки — ошибка. Плагины (`plugins`) устроены так же.

## Режимы: виды сборки

Режим (`mode`) — это вид сборки: отладка, выпуск, тестирование, своя сборка для продакшена или песочницы.

- Режим задаёт поля программы и зависимости поверх остальной конфигурации: аллокатор, платформу, оптимизацию,
  замены, зависимости только для тестов.
- `from` начинает режим с другого: меняется только написанное.
- Глобальный файл даёт готовые режимы `debug`, `release`, `testing`, `checking`; пакет меняет их или добавляет свои.
  Режим одного имени сливается по уровням, как любая секция, потом применяется `from`.
- Одна сборка — один режим: `--mode production`. Смесь двух режимов — третий режим с `from`.
- Код узнаёт режим через `#if MODE == "testing"` ([режимы компиляции](compilation-modes.md)).

```efen
config server {
    mode testing {
        dependencies {
            mock: "^2.0"
        }
    }

    mode production from release {
        target {
            cpu: "x86-64-v3"
        }
    }
}
```

Режим задаёт и `proofs` — для всей сборки ([доказательства](#доказательства)).

Режим не задаёт `library`, `suite`, `version`, `members`, `environment`, поле фреймворка тестов и другой `mode`: это
свойства пакета и пространства при любой сборке.

## Платформа

Секция `target` называет машину, для которой собирается программа: систему `os`, архитектуру `arch`, уровень
процессора `cpu` и флаги процессора `features`. Каждое поле можно опустить.

```efen
config server {
    target {
        os: "linux"
        arch: "x86_64"
        cpu: "x86-64-v3"
        features { aes, fma: false }
    }
}
```

`os` и `arch` по умолчанию берутся у машины сборки. От этого не зависит, на каких машинах программа работает: на
любой машине той же системы и архитектуры, у процессора которой есть команды уровня `cpu` и флаги `features`.

Секция `target` сливается по уровням поле за полем, а `features` — флаг за флагом. Уровень, который пишет `arch`,
отбрасывает `cpu` и `features` дальних уровней: они называли процессор другой архитектуры. Так `target { arch:
"aarch64" }` в пакете не наследует `cpu: "x86-64-v3"` пространства сборки.

### Процессор

`cpu` — уровень или модель процессора под именем, которое знает генератор кода: для LLVM это `"x86-64-v2"`,
`"x86-64-v3"`, `"znver4"`, `"neoverse-v1"`. На AArch64 уровень — версия архитектуры (`"armv8-a"`, `"armv8.2-a"`);
LLVM не знает её как процессор, и компилятор передаёт ему общую модель с флагами этой версии. Программа использует
команды этого уровня и не использует более новых. Имя проверяется по `arch`: модель другой архитектуры — ошибка.

Без `cpu` берётся переносимый уровень архитектуры, в каждом режиме, отладочном и выпускном одинаково:

| `arch` | `os` | Уровень по умолчанию |
|---|---|---|
| `"x86_64"` | любая | `"x86-64-v2"` |
| `"aarch64"` | кроме `"macos"` | `"armv8-a"` |
| `"aarch64"` | `"macos"` | `"apple-m1"` |

Дистрибутив может назначить свой уровень в глобальном файле, например `"x86-64-v3"` для пакетов RHEL 10.

Процессор машины сборки берётся только флагом командной строки `--cpu native`; файл конфигурации его не пишет, и
`cpu: "native"` в файле — ошибка. Иначе программа, собранная из одних и тех же файлов, падала бы на другой машине
той же платформы, а CI, который собирает на одной машине и проверяет на другой, не проходил бы проверку при старте.
`--cpu native` заменяет `cpu` моделью и флагами машины, на которой запущен компилятор, и вычисляет их до начала
сборки; `features` конфигурации применяются поверх. Так `features { avx512f: false }` выключает AVX-512 и при
`--cpu native`. `--cpu native` при `arch` другой архитектуры, чем у
этой машины, — ошибка.

### Флаги процессора

`features` добавляет к уровню `cpu` флаги процессора или убирает их. Флаги пишутся так, как их пишет LLVM: `avx2`,
`avx512f`, `fma`, `aes`, `neon`, `sve`, `dotprod`; список для каждой архитектуры печатает компилятор. Имя
проверяется по `arch`: флаг другой архитектуры или неизвестный — ошибка с подсказкой ближайшего имени.

- Включённый флаг включает и флаги, которые ему нужны, прямо или через другие: `avx512f` включает `avx2`, `avx` и
  `fma`.
- Выключенный флаг выключает флаги, которым он нужен: `fma: false` на уровне `"x86-64-v4"` выключает и `avx512f`.
- Флаг, включённый явно, и нужный ему прямо или через другие флаг, выключенный явно, — ошибка, называющая оба.
  Проверка идёт после слияния уровней и `from`: `features { avx512f, fma: false }` не собирается, потому что
  `avx512f` нужен `fma`. LLVM в таком случае молча выбросил бы `avx512f`.
- Флаг самого старого уровня архитектуры (`sse2` на `x86_64`, `neon` на `aarch64`) выключить нельзя: без него
  вещественные аргументы передаются в других регистрах, и вызовы между частями программы разошлись бы.

Флаг, которого нет ни в одном уровне `x86-64-vN` (`aes`, `avx512vbmi`), может назвать и версия функции или встроенная функция
платформы, которой он нужен ([векторные значения std](types/simd.md#версии-функции)): тогда программа работает и
на процессорах без него.

### Проверка при старте

Программа проверяет процессор раньше любого своего кода. Точка входа процесса и всё, что она зовёт до проверки
(роль рантайма `CpuFeatures`), собраны для самого старого уровня архитектуры (`x86-64` для `x86_64`). Точка входа
читает флаги процессора и сравнивает их с флагами `cpu` и `features`. Если флага нет, программа печатает имена
недостающих флагов в стандартный поток ошибок и завершается с кодом 132; его
оболочка показывает, когда процессор встречает незнакомую инструкцию (128 + SIGILL), так что скрипты уже читают
его как «не тот процессор», а от непойманного исключения, кода 1, он отличим. Флаг доступен, только если
его поддерживают и процессор, и система: для AVX система сохраняет регистры YMM. Таблицу «флаг — бит процессора —
что нужно от системы» хранит компилятор.

Библиотеки видов `dynamic` и `static` проверяют процессор при первом вызове функции `@abi(c)`: у них нет своей точки
входа.

Модель и флаги после `--cpu native` и `features` входят в ключ кэша сборки: библиотека, собранная для двух уровней,
хранится дважды.

## Поля

Поля описаны на Efen в файле `lang::`, который идёт вместе с компилятором (в Amber — `frontend/efen/lang/config.efen`).
Новое поле — строка в этом файле, без изменений в коде компилятора. Конфигурация читается раньше, чем выбран рантайм,
поэтому типы полей — собственные виды читателя: `Text`, `Bool`, `Int`, `Path`, список, словарь с ключами `Text`,
структура, перечисление, вариант, набор флагов.

| Поле | Значение | Кто задаёт |
|---|---|---|
| `library` | виды библиотеки: `efen`, `dynamic`, `static` ([виды библиотеки](#виды-библиотеки)) | библиотека |
| `version` | текст | пакет |
| `dependencies` | словарь зависимостей | каждый уровень свой |
| `plugins` | словарь плагинов компилятора | каждый уровень свой |
| `members` | список путей и шаблонов | только `workspace.efen` |
| `environment` | имя среды сборки (установленных пакетов); команда может заменить | только `workspace.efen` |
| `runtime`, `allocator` | зависимость; `allocator: none` — программа без кучи | программа |
| `std` | `true`/`false` | программа |
| `testRunner` | зависимость: пакет фреймворка ([тесты](tests/tests.md)) | программа и библиотека, вне режимов; по умолчанию — глобальный файл |
| `target` | секция платформы: `os`, `arch`, `cpu`, `features` ([платформа](#платформа)) | программа |
| `optimization` | `none`, `basic`, `aggressive` | программа |
| `patch` | зависимость зависимости → другая | программа |
| `provide` | контракт → реализация (`Logger: FileLogger`), `null` для `optional contract`, секция пакета-зависимости; тип в кавычках → секция «контракт: стратегия» ([статическое связывание](context-and-effects.md#статическое-связывание-эффектов), [выбор программы](strategies.md#выбор-программы)) | запись о контракте — любой пакет, для своего кода; остальное — программа; не в глобальном файле и не в `workspace.efen`; сливается по уровням и режимам запись за записью |
| `mode` | именованные секции режимов | программа; библиотека — только `testing` для своих тестов |
| `suite` | именованные секции наборов тестов: имя — папка в `tests/`, поля описывает фреймворк ([тесты](tests/tests.md#где-лежат-тесты)) | пакет, вне режимов |
| `capabilities` | список возможностей, до которых дотягивается библиотека ([подпись библиотек](signing.md#потолок-возможностей)); предложение | библиотека |
| `diagnostics` | уровни кодов проверок Amber и плагинов компилятора ([плагины компилятора](compile-time/compiler-plugins.md#диагностики)) | сливается по уровням запись за записью |
| `proofs` | какие доказанные проверки сборка всё же пишет: `keep`, `distrust` ([доказательства](#доказательства)) | пакет — для своего кода; режим и флаг `--keep-checks` — для всей сборки; сливается по уровням имя за именем |
| `trust` | центры сертификации и правила ([сертификация](certification.md)) | каждый уровень свой, кроме файла, который ставится с компилятором; в зависимости не действует |

Зависимость: `"^1.0"` (реестр), `path("…")`, `git("url", tag:, branch:, revision:)`, `workspace`, `none`.
Зависимость может быть секцией: `version` или `source` (`git(…)`), ключ автора `key`, разрешения `submodules` и
`lfs` ([подпись библиотек](signing.md#ключ-записан-в-конфигурации)); форма секции — предложение.

## Секции плагинов

Плагин компилятора (диалект, плагин фреймворка тестов с сюитами, генератор) описывает свои секции в своём коде через API
компилятора; пакет пишет их под именем плагина.

```efen
config server {
    plugins {
        efql: "^0.4"
    }

    efql.sql {
        dialect: "sqlite"
        migrations: path("db/migrations")
    }
}
```

Сначала компилятор читает всё, кроме секций плагинов, и по `plugins` находит плагины. Плагин описывает свои
секции, и компилятор проверяет и сливает их по уровням, как свои. Секция плагина не меняет того, что выбрано до
неё: рантайм, аллокатор, платформу, зависимости, сами плагины. Секция плагина, которого нет в `plugins`, —
ошибка; плагин фреймворка тестов подключает поле фреймворка, а не `plugins` ([тесты](tests/tests.md)). Плагин получает готовые значения и читает файлы только по путям из своей
секции ([плагины](compile-time/plugins.md#чтение-мира-и-внешние-программы)).

## Доказательства

FLOW доказывает, что проверка при выполнении никогда не сработает, и сборка её не пишет. Секция `proofs` оставляет
такие проверки: чтобы искать ошибку в самом доказательстве, а не ради скорости.

```efen
config server {
    mode debug {
        proofs {
            keep { overflow }       // проверки переполнения остаются, даже доказанные
        }
    }
}
```

- `keep` называет виды проверок, которые пишутся и там, где они доказаны: `bounds` (границы), `overflow`
  (переполнение), `divisor` (делитель ноль), `null` (пустое значение), `conditions` (условия полей, `requires`,
  `ensures`), `all` — все.
- `distrust` называет виды рассуждения, чьи доказательства не снимают ни одной проверки: `linear`, `evaluation`,
  `loops`, `products`, `solver`. Вид — тот, что дал ответ последним. Сегодня все доказательства FLOW — `linear`.
- Ключ называет то, что оставить: голое имя включает его, `overflow: false` выключает. Уровни сливаются имя за
  именем, ближний уровень заменяет дальний.
- `proofs` пакета действует на его код; режим и флаг `--keep-checks overflow,bounds` (или `all`) — на всю сборку.
- Доказанная, но оставленная проверка, если сработает, останавливает программу, как нарушенное условие, а не
  бросает исключение: обработчик, который доказательство сделало недостижимым, может не стоять. `efen proofs`
  пишет у неё `proved` и `kept` после видов рассуждения: `proved    FLOW::linear, kept`.
- Секция не меняет того, что FLOW доказывает: `throws`, `nothrows`, ошибки и заметки одни при любых настройках. Она
  выбирает только, какие доказательства снимают проверки. Бюджет работы FLOW она не задаёт.

## Доверие и сертификаты

Секция `trust` называет центры сертификации и правила, по которым сборка принимает плагины на веру. Она
стоит на любом уровне, уровни сливаются как остальные поля, а конфигурация зависимости её не добавляет.
Подробно — [сертификация](certification.md); ключи авторов библиотек — [подпись библиотек](signing.md).

## Ограничения

- Путь в `workspace.efen` и `project.efen` не выходит за верх пространства сборки. Глобальный файл может называть
  любые пути.
- `git` — только по `https://` или `ssh://`.
- Пакет, скачанный из реестра или git, читается со своим `project.efen` как отдельный верх, без `path` и `patch`.

## Ошибки

Каждая ошибка указывает файл, строку и столбец:

- поле, которого нет в схеме, с подсказкой ближайшего: «нет поля `alocator`; может быть, `allocator`?»;
- значение не того вида, поле или запись словаря дважды, значение вместо секции и наоборот;
- второе объявление `config` или другое объявление в файле;
- поле программы в библиотеке, кроме поля фреймворка тестов ([тесты](tests/tests.md): его
  читает только `efen test` на самой библиотеке, а в зависимости оно не действует); `members` или `environment`
  вне `workspace.efen`;
- `fn main` вне `main.efen`; пакет без `main.efen` и `lib.efen` или с обоими; зависимость от пакета-программы;
  `library` в пакете-программе;
- `workspace` без записи в пространстве сборки;
- неизвестный режим, `from` без такого режима или по кругу;
- `cpu: "native"` в файле, неизвестное имя `cpu` или модель другой архитектуры, флаг `features` другой архитектуры
  или неизвестный, флаг включён явно, а нужный ему выключен явно, выключен флаг самого старого уровня архитектуры;
  `--cpu native` при `arch` другой архитектуры, чем у машины сборки;
- путь за верхом пространства сборки, `git` не по `https://` или `ssh://`;
- секция плагина, которого нет в `plugins`, кроме плагина фреймворка тестов;
- в `provide`: две записи одного типа после разрешения имён (путь реэкспорта, алиас) на одном уровне, неизвестный
  тип или стратегия, стратегия не `conforms` контракту записи, стратегия не видна
  программе, у типа нет `allow strategies` для стратегии чужого пакета, `provide` в глобальном файле или в
  `workspace.efen`; в библиотеке — стратегия типа, секция пакета, `null` или запись о чужом `@unique` контракте;
  ключ, который не называет ни контракт, ни пакет-зависимость, ни тип;
- секция `effects` — её заменила `provide`; подсказка переносит записи в `provide`, сливая с уже
  написанной;
- нет глобального файла.

## Открыто

- Синтаксис API, которым плагин описывает секции (имена `ConfigSections`, `describe` в черновике Amber —
  предложение).
- Пометки схемы `@program`, `@workspace`, `@pool` — форма Amber, в спеке не закреплена.
- Ключ секции в кавычках внутри словаря (`provide { "shop::Key" { … } }`) — новая форма грамматики; ключи
  сравниваются после разрешения имён, при слиянии ближний уровень побеждает. Обобщённый тип ключом (`"Array<shop::Key>"`)
  не определён.
- Вид значения «ссылка на объявление» (`hashing::FastHash`, `FileLogger` в `provide`) и момент, когда
  читатель её разрешает: после загрузки зависимостей. Контракт в `provide` пишется
  коротким именем, если оно одно на сборку, иначе полным путём (`log::Logger`); два контракта одного короткого имени
  — ошибка, называющая оба.
- Как запись `provide` выбирает `ClassDefinition` ([определение класса](aspects/compile-time/class.md)): у аспекта
  нет типа-цели, и порядок там другой — явное определение на корне, затем конфигурация.
- `efen test` на библиотеке идёт без записей `provide` программы и проверяет другие тела, чем в программе.
- `dynamic` собирается без записей программы-хозяина: интерфейс `dynamic` должен нести выбранные стратегии инстанциаций своего
  ABI, а расхождение — давать ошибку загрузки.
- Значение `--config` в командной строке; функции, `if` и `match` в значениях — когда появится вычисление во время
  компиляции.
- Возможности пакета для `#if` (их имя `features` совпало бы с флагами процессора `target.features`), вид линковки
  (`link`).
- `#if` по флагам процессора.
- Для какого `cpu` собирается библиотека `dynamic` или `static`: `target` — поле программы. Как проверка при первом
  вызове устроена в ней.
- Имена `cpu` и флагов берутся у LLVM, поэтому их список зависит от версии LLVM в компиляторе.
- Уровень дистрибутива в глобальном файле для нескольких архитектур сразу.
- Имена `os` и `arch`: в примерах `"linux"`, `"macos"`, `"windows"`, `"x86_64"`, `"aarch64"`, список не утверждён.
- Поле `capabilities` и зависимость секцией (`version`, `source`, `key`, `submodules`, `lfs`) — предложения
  amber dev/plans/S90.md §14.
- Описание пакета для реестра: `description`, `authors`, `license` (были в прежнем примере `packages.md`).
