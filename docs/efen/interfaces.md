# Интерфейсы

[Документация](README.md) · [Словарь](glossary.md) · [Контракты](contracts.md)

Интерфейс — тип, через который код обращается к разным реализациям
одного набора операций. Вызывающий знает доступные методы и их требования,
но конкретная реализация может определяться только при выполнении программы.

Например, функция, принимающая `Logger`, может работать с файловым
и консольным журналом без отдельных версий своего исходного кода.

## Интерфейс и контракт

| Вопрос | Интерфейс | Контракт |
|---|---|---|
| Для чего нужен | Работать с разными реализациями через общий тип значения | Задавать требования к устройству и поведению кода |
| Как используется | Как тип параметра, поля или результата | Как ограничение обобщённого объявления или требование к типу |
| Как выбирается реализация | При выполнении, через таблицу методов | Проверяется при компиляции для конкретного типа |
| Как выполняется вызов | Обычно косвенно через таблицу виртуальных методов (VTBL) | При известной реализации возможен прямой вызов |

Сам контракт не является типом значения и не требует собственной таблицы
виртуальных методов. Это не означает, что любой использующий контракт код
не имеет затрат при выполнении: они зависят от представления данных и
способа вызова. Интерфейс, в свою очередь, не гарантирует бинарную
совместимость любых версий реализации. Для неё должны сохраняться
двоичный интерфейс (ABI) и соглашения о вызовах.

### Явное создание интерфейса

Интерфейс не создаётся из контракта автоматически. Объявление
`interface Name from Contract` создаёт интерфейс и сохраняет связь
с исходным контрактом. Через интерфейс вызываются методы, доступные
при выполнении. Связанные типы, представление данных и другие статические
требования остаются предметом проверки компилятора.

Стратегия также не становится интерфейсом по совпадению методов.
Отдельное объявление создаёт интерфейс по образцу выбранной стратегии:

```efen
interface Drawing from CircleDrawing

let shape: Drawing = CircleDrawing
```

Без `interface Drawing from CircleDrawing` последнее присваивание запрещено.
Другая стратегия может реализовать `Drawing` только при явном соответствии
общему контракту исходной стратегии и после проверки всех методов интерфейса.
Подробнее — [динамическая стратегия](strategies.md#динамическая-стратегия).

### Практический пример

```efen
// Вызовы через интерфейс используют таблицу виртуальных методов
interface Logger {
    fn log(message: String)
    fn level -> Int
}

class FileLogger {
    implements Logger  // Создается VTBL в бинарнике

    fn log(message: String) {
        writeToFile("/var/log/app.log", message)
    }

    fn level -> Int {
        return 3
    }
}

class ConsoleLogger {
    implements Logger  // Другая VTBL

    fn log(message: String) {
        print(message)
    }

    fn level -> Int {
        return 5
    }
}

// Одна функция работает с разными реализациями Logger
fn processLogs(logger: Logger, messages: [String]) {
    for msg in messages {
        logger.log(msg)  // Выбор реализации через таблицу методов
    }
}

// Работает с любым Logger
let fileLogger = FileLogger()
let consoleLogger = ConsoleLogger()

processLogs(logger: fileLogger, messages: ["Error 1", "Error 2"])
processLogs(logger: consoleLogger, messages: ["Debug info"])
```

При вызове через `Logger` выбирается таблица методов фактической реализации:
у `FileLogger` и `ConsoleLogger` она содержит разные функции. Так работает
**динамическая диспетчеризация**. Компилятор может заменить косвенный вызов
прямым, если ему удаётся установить конкретную реализацию.

### Доступ метода к self

Метод интерфейса объявляет право доступа к `self` так же, как метод контракта: `mut fn`
может менять `self`, `edit fn` не перемещает и не уничтожает существующие слоты
`self`, `own fn` забирает `self`, `read fn` и метод без пометки только читают его
([«Контракты»](contracts.md#доступ-метода-к-self)). При вызове через интерфейс код опирается на объявленное право, а не на тело
выбранной реализации.

```efen
interface Counter {
    mut fn increment
    fn value -> Int
}
```

Интерфейс может объявить `layout { var … }`, а его метод — [модель](conditions.md#модель-model), по правилам
контракта ([`layout` и модель в контракте](contracts.md#layout-и-модель-в-контракте)): вызов через интерфейс берёт
модель интерфейса как сводку, а реализация уточняет её по удержаниям.

### Когда нужен интерфейс

Интерфейс удобен, когда выбор реализации происходит при выполнении:
например, конфигурация выбирает журнал, хранилище или обработчик.

```efen
fn createLogger(kind: String) -> Logger {
    return match kind {
        "file": FileLogger()
        "console": ConsoleLogger()
        _: NullLogger()
    }
}
```

Его также можно использовать для передачи зависимостей: объект хранит
значение интерфейсного типа, а вызывающий выбирает конкретную реализацию.

```efen
class App {
    conforms Constructible

    var logger: own Logger
    var database: own Database

    @constructor
    fn init(logger: own Logger, db: own Database) -> Self {
        self.logger = take logger
        self.database = take db
    }
}
```

Если общий код должен проверяться для конкретных типов при компиляции,
используйте параметры типов и контракт. Выбор между ними определяется
требуемым способом работы с реализациями, а не правилом «интерфейс всегда
медленный, контракт всегда быстрый». Подробнее — [контракты](contracts.md).

Пример интерфейса:
```efen
interface MyInterface {
    var myProperty: Int { get set }
    fn myMethod
}
```

Пример использования интерфейса:
```efen
fn useInterface(value: mut MyInterface) {
    value.myProperty = 42
    value.myMethod()
}
```

Код, работающий с интерфейсом, использует только его объявленные операции.
Соответствие конкретной реализации этим требованиям проверяет компилятор.

Интерфейсы имеют множественное наследование и могут задавать публичный
протокол состояний, но не владеют собственной памятью для полей. Реализующий тип явно
сопоставляет свои состояния и переходы интерфейсному протоколу.

<a id="множественное-наследование-и-конфликты-members"></a>

### Множественное наследование и конфликты членов

Если два предка дают член с одним именем, интерфейс явно выбирает источник
через `use Parent.member`. Запись с `as` вводит член под новым именем:

```efen
interface Reader {
    fn read -> [Byte]
}

interface Writer {
    fn read -> [Byte]
}

interface Duplex : Reader, Writer {
    use Reader.read
    use Writer.read as write
}
```

Здесь `Duplex.read` взят из `Reader.read`, а `Duplex.write` — из
`Writer.read`. Внутри тела интерфейса `use` разрешает конфликт наследуемого
члена, а не импортирует модуль; путь `Parent.member` всегда называет
исходный член. Если конфликт не разрешён явным `use`, это ошибка с указанием
обоих путей. Новое имя не должно совпадать с другим доступным членом.
